PART 1 · THE BIG PICTURE

Chapter 1 — Operating System কেন দরকার?

Hardware আর application-এর মাঝখানে একটা layer কেন লাগে, আর সেই layer-টা আসলে কী কী responsibility নেয়।

Problem-টা আগে বুঝি

Computer hardware মানে মূলত চারটা জিনিস — CPU (instruction execute করে), RAM (running data রাখে), storage (persistent data রাখে), আর network interface (বাইরের দুনিয়ার সাথে কথা বলে)। এগুলো ভয়ংকর রকমের "dumb"। CPU শুধু raw instruction চেনে, disk শুধু block number চেনে — "file" বলে কিছু চেনে না, network card শুধু raw packet পাঠাতে জানে।

অন্যদিকে application মানে তোমার লেখা code — যে চায় "এই file-টা পড়ো", "এই port-এ listen করো", "এই object-টা memory-তে রাখো"। এখন ভাবো, OS না থাকলে প্রতিটা application-কে নিজে নিজে disk-এর electronics-এর সাথে কথা বলতে হতো, নিজে RAM-এর কোন byte কার সেটা track করতে হতো, নিজে network card-এর driver লিখতে হতো।

তার উপর আরেকটা বড় সমস্যা — এক computer-এ একসাথে অনেকগুলো program চলে। Chrome, VS Code, node server, Spotify — সবাই একই CPU, একই RAM চায়। কে কখন CPU পাবে? কার data কোন RAM-এ থাকবে? একজন আরেকজনের memory-তে হাত দিলে কী হবে? এই ঝগড়া মেটানোর জন্য একজন referee লাগে।

MENTAL MODEL

Operating System = Resource Manager + Abstraction Layer। Resource manager হিসেবে ঠিক করে কে কখন CPU/RAM/disk/network পাবে। Abstraction layer হিসেবে dumb hardware-কে ঢেকে সুন্দর interface দেয় — raw disk block-এর বদলে file, raw packet-এর বদলে socket, raw physical memory-র বদলে virtual memory, raw CPU time-এর বদলে process।

Kernel, user space, kernel space

OS-এর core অংশটার নাম kernel। এটা একটা special program যেটা machine boot হওয়ার সময় load হয় এবং সবসময় memory-তে থাকে। Kernel-ই আসল resource manager — process schedule করা, memory ভাগ করা, filesystem চালানো, network stack চালানো, driver দিয়ে device-এর সাথে কথা বলা — সব kernel-এর কাজ।

CPU-তে hardware level-এ দুইটা privilege mode আছে (Chapter 31-এ deep dive করবো):

  • User mode / user space — তোমার application এখানে চলে। Restricted। Hardware-এ direct হাত দিতে পারে না, অন্য process-এর memory ছুঁতে পারে না।
  • Kernel mode / kernel space — kernel এখানে চলে। Full power। যেকোনো memory, যেকোনো device access করতে পারে।

তাহলে তোমার app file পড়ে কীভাবে? উত্তর: system call। Application kernel-কে অনুরোধ করে — "আমার হয়ে এই কাজটা করে দাও।" CPU controlled ভাবে kernel mode-এ ঢোকে, kernel কাজটা করে, তারপর result নিয়ে আবার user mode-এ ফেরত আসে। read(), write(), open(), socket() — এগুলো সব system call।

পুরো বইয়ে এই ছবিটা বারবার ফিরে আসবে — নীল মানে user space, amber মানে kernel space।

একজন engineer-এর কেন এটা জানা দরকার

কারণ তোমার code-এর performance-এর বড় অংশ ঠিক হয় এই boundary-গুলোতে। একটা slow API-এর কারণ হতে পারে excessive system call, হতে পারে disk I/O, হতে পারে memory pressure — এগুলো তোমার JavaScript-এ দেখা যায় না, দেখা যায় OS layer-এ। Black box-টা খুললে debugging আর optimization দুটোই অন্য level-এ চলে যায়।

EXPERIMENT

Terminal-এ চালাও: uname -a — এটা তোমার kernel-এর নাম আর version দেখায় (macOS-এ Darwin, Linux-এ Linux)। তারপর ps aux | head -15 — এই মুহূর্তে চলা process-এর list। খেয়াল করো, তুমি কিছু run না করলেও কত process চলছে — এদের সবাইকে kernel-ই manage করছে।

CAN I EXPLAIN THIS?

  • Kernel কী, আর সেটা user space থেকে আলাদা কেন?
  • Application hardware-এ direct হাত দিতে পারে না — তাহলে কাজ করায় কীভাবে?
  • System call এক কথায় কী?

End-to-end example: একটা file read

ধরো তোমার Node.js code লিখলো fs.readFileSync("config.json")। Broadly যা ঘটে:

1. Application:  readFileSync("config.json") call করলো
2. Runtime/libc: ভিতরে গিয়ে read() system call বানালো
━━━━━━━━━━ user → kernel mode switch ━━━━━━━━━━
3. Kernel:       request receive করলো
4. File system:  "config.json" মানে disk-এর কোন block? বের করলো
5. Page cache:   data আগেই cache-এ আছে কি? (থাকলে shortcut!)
6. Block layer:  না থাকলে disk-এর জন্য read request queue করলো
7. Driver:       storage device-কে command পাঠালো
8. Device:       data পড়ে DMA দিয়ে memory-তে দিলো
9. Kernel:       data process-এর buffer-এ copy করলো
━━━━━━━━━━ kernel → user mode switch ━━━━━━━━━━
10. Application: data হাতে পেলো, কাজ চললো

প্রতিটা step এখনই পুরোপুরি বোঝার দরকার নেই — page cache, DMA, block layer সব সামনের chapter-গুলোতে আসবে। এখন শুধু structure-টা মাথায় গাঁথো: application কখনো disk-কে সরাসরি দেখে না। মাঝখানে সবসময় kernel থাকে।

MENTAL MODEL

যেকোনো I/O-এর গল্প আসলে একই pattern: user space request → system call → kernel-এর layer গুলো → hardware → ফেরার পথ উল্টো। File হোক, network হোক — pattern এক, শুধু মাঝের layer বদলায়।

COMMON MISCONCEPTION

"OS মানে UI — desktop, window, icon।" না। Desktop environment একটা application মাত্র। আসল OS হলো kernel + তার service গুলো, যেটা server-এ UI ছাড়াই দিব্যি চলে। তুমি যে production server-এ deploy করো, সেখানে OS পুরোদমে কাজ করছে — কোনো UI ছাড়াই।

  • Driver জিনিসটা kernel-এর ভিতরে কেন থাকে?

PART 2 · FROM PROGRAM TO PROCESS

Chapter 3 — Program vs Process

এই পার্থক্যটা পরিষ্কার না হলে সামনের অর্ধেক বই ঝাপসা লাগবে। তাই আলাদা করে একটা পুরো chapter।

Program: disk-এ শুয়ে থাকা file

Program হলো একটা executable file — disk-এ পড়ে থাকা bytes। এর ভিতরে আছে machine instructions (CPU-র ভাষায় compiled code), কিছু initial data, আর metadata (কোথা থেকে execution শুরু হবে ইত্যাদি)। Linux-এ এই file format-এর নাম ELF। গুরুত্বপূর্ণ কথা: program একটা passive জিনিস। /usr/bin/node file-টা disk-এ পড়ে আছে — কিছুই করছে না।

Process: সেই file-এর একটা running instance

তুমি যখন node server.js চালাও, OS ওই executable-টা নিয়ে একটা process বানায়। Process মানে শুধু "চলছে" না — process মানে OS একগাদা জিনিস তৈরি করে দিয়েছে:

  • একটা PID (Process ID) — kernel-এর খাতায় unique নাম্বার
  • নিজস্ব virtual address space — process-এর নিজের "private" memory জগৎ (Chapter 9)
  • Memory-তে load হওয়া code, data, heap আর stack (Chapter 5)
  • CPU state — registers, program counter (এখন কোন instruction-এ আছে)
  • Open file/socket-দের list — file descriptor table
  • Kernel-এর bookkeeping — state (running/waiting), owner, parent কে, ইত্যাদি
MENTAL MODEL

Program = recipe (কাগজে লেখা, passive)। Process = রান্না চলছে (চুলা জ্বলছে, উপকরণ কাটা হচ্ছে, নির্দিষ্ট state আছে)। একই recipe থেকে একসাথে দুই হাঁড়িতে রান্না চলতে পারে — দুইটা আলাদা process, আলাদা state, আলাদা হাঁড়ি (memory)।

একই program, দুইটা process

দুইটা terminal খুলে দুই জায়গায় node চালাও। Executable file একটাই, কিন্তু process দুইটা — আলাদা PID, আলাদা memory, আলাদা variables। একটাতে crash হলে আরেকটার কিছু হয় না। এটাই isolation — OS-এর অন্যতম প্রধান উপহার। তোমার Chrome-এর প্রতিটা tab আলাদা process রাখার পিছনেও এই একই logic — এক tab মরলে বাকিরা বাঁচে।

COMMON MISCONCEPTION

"Process = program in execution" — শুরুর জন্য ঠিক আছে, কিন্তু অসম্পূর্ণ। Process-এর নিজস্ব identity (PID), নিজস্ব address space, নিজস্ব resources আছে। শুধু "চলমান code" না — বরং code + memory + state + kernel bookkeeping-এর একটা পুরো package। আর সামনে দেখবে, একটা process-এ একাধিক thread-ও থাকতে পারে — তখন "in execution" অংশটা আসলে thread-এর কাজ।

EXPERIMENT

দুইটা terminal-এ চালাও: sleep 300 (দুই জায়গায়)। তৃতীয় terminal-এ: ps aux | grep sleep। দেখবে একই program (/bin/sleep) কিন্তু দুইটা আলাদা PID। Linux হলে ls /proc/<PID>/ চালিয়ে দেখো — প্রতিটা process-এর জন্য kernel কত কিছু track করে।

CAN I EXPLAIN THIS?
  • Program passive আর process active — মানে কী?
  • Process বানাতে OS কী কী জিনিস তৈরি করে দেয়?
  • একই executable-এর দুই process একে অপরের variable দেখতে পায় না কেন?

Chapter 4 — Program কীভাবে execute হয়

Source code থেকে চলমান process পর্যন্ত পুরো pipeline — high level-এ।

Source থেকে executable

একটা ছোট C program ধরি (C এখানে শুধু tool — OS-এর সবচেয়ে কাছের ভাষা বলে):

#include <stdio.h>

int main() {
    printf("hello\n");
    return 0;
}

gcc hello.c -o hello চালালে ভিতরে কয়েকটা ধাপ ঘটে:

hello.c (source)
   ↓ compiler — C কে assembly/machine code-এ translate
hello.o (object file — machine code, কিন্তু অসম্পূর্ণ)
   ↓ linker — printf-এর মতো বাইরের function-এর ঠিকানা জোড়া লাগায়
hello (executable — ELF file, run করার জন্য ready)

Object file "অসম্পূর্ণ" কেন? কারণ তোমার code printf call করেছে, কিন্তু printf-এর code তোমার file-এ নেই — সেটা C library-তে। Linker-এর কাজ এই reference গুলো resolve করা। (Static vs dynamic linking Chapter 33-এ।)

ELF: executable-এর গঠন

Linux executable-এর format হলো ELF (Executable and Linkable Format)। ভিতরে মোটা দাগে থাকে: header (এটা কী ধরনের file, execution কোথা থেকে শুরু — entry point), machine code section, initialized data section, আর dynamic library-র dependency list। JavaScript developer হিসেবে ভাবতে পারো — ELF হলো compiled program-এর package.json + bundle একসাথে।

Run করার মুহূর্তে: loader

./hello চালালে shell একটা system call দিয়ে kernel-কে বলে "এই executable থেকে process বানাও"। তখন kernel-এর loader অংশ কাজ করে:

  1. নতুন process তৈরি করে (PID, address space)
  2. ELF header পড়ে code আর data segment গুলো process-এর memory-তে map করে
  3. Stack setup করে, dynamic libraries load করে
  4. CPU-র program counter (instruction pointer)-কে entry point-এ set করে দেয়

ব্যস — এখন CPU ওই address থেকে instruction fetch করে execute করা শুরু করে। Program "চলছে" মানে আসলে এটুকুই: CPU-র program counter তোমার code-এর ভিতর দিয়ে হাঁটছে।

তাহলে JavaScript/Python-এর বেলায়?

node server.js চালালে process টা আসলে node executable-এর — সেটাই ELF, সেটাই load হয়। তোমার server.js হলো ওই process-এর data, যেটা V8 engine পড়ে ভিতরে JIT compile করে চালায়। OS-এর চোখে process একটাই — node। এজন্যই ps দিলে দেখো "node", "server.js" না।

Chapter 5 — Anatomy of a Process

Process-এর memory-র ভিতরটা দেখতে কেমন — এই layout-টা বইয়ের সবচেয়ে বেশি ব্যবহৃত ছবিগুলোর একটা।

Process memory layout

High Address
+------------------------+
|   Stack                |  ← function call, local variable
|      ↓ (নিচের দিকে বাড়ে) |
+------------------------+
|                        |
|   Free space           |
|                        |
+------------------------+
|      ↑ (উপরের দিকে বাড়ে) |
|   Heap                 |  ← dynamic allocation (malloc, new, object)
+------------------------+
|   BSS                  |  ← uninitialized global (শূন্য দিয়ে শুরু)
+------------------------+
|   Data                 |  ← initialized global/static variable
+------------------------+
|   Code / Text          |  ← machine instructions (read-only)
+------------------------+
Low Address
  • Code/Text: Executable-এর machine instructions। Read-only রাখা হয় — নিজের code নিজে overwrite করা বন্ধ করতে। বোনাস: read-only বলেই একই program-এর একাধিক process এই অংশটা physical memory-তে share করতে পারে।
  • Data: যেসব global/static variable-এর initial value দেওয়া আছে (int count = 10;)।
  • BSS: Initial value ছাড়া global গুলো (int total;) — process শুরুতে zero-filled থাকে। ELF file-এ এদের জন্য জায়গা নষ্ট হয় না, শুধু size লেখা থাকে।
  • Heap: Runtime-এ চাওয়া memory — malloc, JS-এর object/array, সব এখানে। উপরের দিকে বাড়ে।
  • Stack: Function call-এর জায়গা। নিচের দিকে বাড়ে।

Stack ঠিক কীভাবে কাজ করে

প্রতিটা function call-এ stack-এ একটা stack frame push হয়। Frame-এর ভিতরে থাকে: function-এর local variables, arguments, আর সবচেয়ে গুরুত্বপূর্ণ — return address (function শেষ হলে CPU কোথায় ফিরবে)। Function return করলে frame টা pop হয়ে যায়।

এই flow-টা trace করি:

void foo() { int y = 2; bar(); }
int main()  { int x = 1; foo(); return 0; }
main() চলছে      foo() call        bar() call        bar() return      foo() return

|          |     |          |     | bar frame|     |          |     |          |
|          |     | foo frame|     | foo frame|     | foo frame|     |          |
| main     |     | main     |     | main     |     | main     |     | main     |
+----------+     +----------+     +----------+     +----------+     +----------+
                 frame push       আরেকটা push       pop              pop

Stack literally একটা stack — LIFO। এজন্যই recursion বেশি গভীরে গেলে "stack overflow" হয়: frame জমতে জমতে জায়গা শেষ।

MENTAL MODEL

Stack হলো "এখন আমি কোথায় আছি আর কীভাবে ফিরবো"-র হিসাব। তোমার debugger-এ যে call stack / stack trace দেখো — সেটা আক্ষরিক অর্থেই এই memory region-এর ছবি। Exception-এর stack trace মানে: crash-এর মুহূর্তে stack-এ কোন কোন frame জমা ছিল।

EXPERIMENT (Linux)

যেকোনো চলমান process-এর PID নিয়ে চালাও: cat /proc/<PID>/maps। Output-এ খুঁজে দেখো [heap], [stack], আর executable-এর path-ওয়ালা লাইনগুলো (ওগুলোই code/data)। এটা এই chapter-এর diagram-এর real-life version। r-xp (read+execute) দেখবে code segment-এ, rw-p দেখবে data/heap-এ — permission গুলোও layout-এর গল্প বলে।

Chapter 6 — Stack vs Heap

দুইটা আলাদা allocation strategy — কেন দুটোই লাগে, আর কার কী cost।

Stack কেন দরকার

Function-এর local variable-দের একটা সুন্দর property আছে — এদের lifetime একদম predictable। Function ঢুকলে জন্ম, function বের হলে মৃত্যু। এমন predictable lifetime-এর জন্য stack perfect: allocation মানে শুধু stack pointer-টা একটু সরানো, deallocation মানে ফেরত সরানো। কোনো bookkeeping লাগে না, কোনো খোঁজাখুঁজি লাগে না।

Heap কেন দরকার

কিন্তু সব data-র lifetime function-এর সাথে বাঁধা না। ধরো একটা function user object বানিয়ে return করলো — function শেষ, কিন্তু object টা বেঁচে থাকতে হবে। অথবা runtime-এ ঠিক হবে কত বড় array লাগবে। এই "যতদিন দরকার ততদিন বাঁচবে, size আগে থেকে জানা নেই" ধরনের data-র জন্য heap — malloc(size) দিয়ে চাও, free(ptr) দিয়ে ফেরত দাও।

SCOPE vs LIFETIME

Scope = code-এর কোথা থেকে variable-টা দেখা যায়। Lifetime = memory-টা কতক্ষণ বৈধ থাকে। Stack data-র বেলায় দুটো মিলে যায়। Heap data-র বেলায় না — pointer/reference টা scope-এর বাইরে চলে গেলেও heap-এর memory বেঁচে থাকতে পারে। C-তে এই ফাঁক থেকেই আসে dangling pointer আর memory leak; GC language-এ garbage collector এই lifetime tracking-টাই তোমার হয়ে করে।

Cost-এর আসল হিসাব

"Stack fast, heap slow" — এই oversimplification-টা এড়িয়ে যাই। আসল ছবিটা:

  • Stack allocation trivially simple — একটা pointer বাড়ানো/কমানো। প্রায় free।
  • Heap allocation-এ কাজ বেশি — allocator-কে free space খুঁজতে হয়, bookkeeping করতে হয়, মাঝে মাঝে kernel-এর কাছে আরো memory চাইতে হয় (system call!)। কতটা costly সেটা allocator, allocation pattern আর size-এর উপর নির্ভর করে।
  • Access speed-এ পার্থক্য allocation-এর না, locality-র — stack-এর data সাধারণত ছোট জায়গায় ঘেঁষাঘেঁষি করে থাকে বলে CPU cache-এ ভালো behave করে (Chapter 13)। Heap-এর data ছড়ানো-ছিটানো হলে cache miss বাড়ে। মানে পার্থক্যটা জায়গার "জাত"-এ না, access pattern-এ।

Heap-এর নিজস্ব রোগ

  • Fragmentation: বারবার ছোট-বড় allocate/free করতে করতে free memory টুকরা টুকরা হয়ে যায় — মোট জায়গা থাকলেও বড় এক টুকরা পাওয়া যায় না।
  • Memory leak: নেওয়া memory ফেরত না দেওয়া। GC language-এও হয় — যেমন global array-তে reference জমিয়ে রাখলে GC কিছুই করতে পারে না। Node.js app-এর memory ধীরে ধীরে বেড়ে যাওয়ার classic কারণ।
  • Stack overflow: Heap-এর রোগ না, stack-এর — infinite/গভীর recursion-এ frame জমে stack-এর সীমা পার হয়ে যাওয়া।
JS DEVELOPER-এর জন্য

V8-এ তোমার object/array/closure সব heap-এ থাকে, আর garbage collector সেই heap পরিষ্কার করে। "GC pause" মানে: collector heap ঘুরে ঘুরে মরা object খুঁজছে। Heap যত এলোমেলো আর বড়, GC-র কাজ তত বেশি। Chrome DevTools-এর Memory tab-এ যে heap snapshot নাও — সেটা আক্ষরিক অর্থেই এই chapter-এর heap region-এর ছবি।

  • "Stack faster than heap" কথাটার মধ্যে কতটুকু সত্যি আর কোথায় ভুল?
  • Fragmentation কীভাবে তৈরি হয়?

Chapter 7 — Physical Memory বোঝা

RAM আসলে কী, আর কেন সেটা যত fast ভাবো তত fast না।

RAM কী

RAM (Random Access Memory) হলো সেই hardware যেখানে চলমান process-দের code আর data থাকে। "Random access" মানে যেকোনো address-এ প্রায় সমান সময়ে পৌঁছানো যায় — disk-এর মতো ঘুরে ঘুরে খুঁজতে হয় না। আর RAM volatile — power গেলে সব মুছে যায়। এজন্যই "save" বলে একটা জিনিস আছে: RAM থেকে persistent storage-এ নেওয়া।

Physically RAM থাকে DIMM module-এ (motherboard-এর ওই লম্বা stick গুলো), আর আজকের প্রযুক্তির নাম DDR (DDR4/DDR5)। আমাদের জন্য এটুকু জানাই যথেষ্ট — এই বই memory hardware-এর encyclopedia না।

Physical address

RAM-কে ভাবো একটা বিশাল byte-এর array। প্রতিটা byte-এর একটা নাম্বার আছে — physical address। 16GB RAM মানে মোটামুটি 0 থেকে ১৬০০ কোটি+ পর্যন্ত address। CPU যখন memory access করে, শেষ পর্যন্ত এই physical address-ই ব্যবহৃত হয়। (কিন্তু তোমার process এই address কখনো সরাসরি দেখে না — সেই twist Chapter 9-এ।)

Memory infinitely fast না কেন

এখানেই একটা অস্বস্তিকর সত্য: CPU-র তুলনায় RAM ধীর। আধুনিক CPU প্রতি nanosecond-এ একাধিক instruction চালাতে পারে, কিন্তু RAM থেকে একটা data আনতে লাগে দশগুণ-শতগুণ বেশি সময় (exact number hardware-ভেদে ভিন্ন, তাই মুখস্থ করার দরকার নেই — অনুপাতটাই আসল)। কারণটা physics + engineering: RAM chip CPU থেকে physically দূরে, signal যেতে-আসতে সময় লাগে, আর DRAM cell পড়ার নিজস্ব latency আছে।

MENTAL MODEL

CPU হলো একটা দ্রুতগতির chef, RAM হলো storeroom। Chef-এর হাত যত দ্রুতই চলুক, প্রতিটা উপকরণের জন্য storeroom-এ হেঁটে গেলে রান্নার speed storeroom-এর হাঁটাপথেই আটকে যাবে। এই gap-টার নাম চলতি ভাষায় "memory wall" — আর এটা মেটানোর জন্যই cache-এর জন্ম (Chapter 8, 13)।

EXPERIMENT

Linux-এ free -h চালাও। used, free, আর buff/cache column গুলো দেখো। অবাক লাগতে পারে যে "free" এত কম — আসলে OS ইচ্ছা করেই অলস RAM-কে file cache হিসেবে ব্যবহার করে (Chapter 23-এ বুঝবে কেন এটা ভালো জিনিস)। available column-টাই আসল "কতটুকু পাওয়া যাবে"-র হিসাব।

Chapter 8 — CPU আর Memory-র কথাবার্তা

একটা memory access-এর ভিতরের যাত্রাপথ — cache-এর foundation এখানেই।

একটা load instruction-এর যাত্রা

ধরো CPU-র সামনে instruction: "address X থেকে value আনো" (load)। ঘটনা broadly এরকম:

CPU: "address X-এর data চাই"
  ↓
1. L1 cache-এ আছে?  ── হ্যাঁ → নিয়ে নাও  (দ্রুততম)
  ↓ না
2. L2 cache-এ আছে?  ── হ্যাঁ → নিয়ে নাও
  ↓ না
3. L3 cache-এ আছে?  ── হ্যাঁ → নিয়ে নাও
  ↓ না
4. RAM থেকে আনো    (সবচেয়ে ধীর ধাপ — শত শত cycle)
  └─ আনার সময় data-টা cache-এও রেখে দাও, পরেরবারের জন্য

মূল idea: CPU সরাসরি RAM-এ যায় না। মাঝে ছোট, দ্রুত memory-র কয়েকটা স্তর আছে — cache hierarchy। সম্প্রতি ব্যবহৃত data cache-এ থাকে; পাওয়া গেলে cache hit (সস্তা), না পেলে cache miss (দামি — RAM পর্যন্ত যাত্রা)।

MENTAL MODEL

Memory access-এর cost একটা fixed number না — এটা একটা lottery: data কোথায় বসে আছে তার উপর নির্ভর করে একই instruction সস্তাও হতে পারে, শতগুণ দামিও হতে পারে। Performance-sensitive code লেখার সময় আসল খেলা হলো এই lottery-তে জেতার সম্ভাবনা বাড়ানো — মানে cache-friendly access pattern। কীভাবে, সেটা Chapter 13-এ।

আরেকটা সূক্ষ্ম কথা: CPU byte ধরে ধরে RAM থেকে আনে না — আনে cache line ধরে (সাধারণত 64 bytes-এর chunk)। মানে address X চাইলে তার আশেপাশের byte গুলোও ফাউ হিসেবে cache-এ চলে আসে। এই এক তথ্যই sequential vs random access-এর পুরো পার্থক্যের বীজ — মাথায় রেখো।

  • Cache line ধরে data আনার ফলে কী সুবিধা তৈরি হয়?

PART 3 · MEMORY

Chapter 9 — Virtual Memory

এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ chapter-গুলোর একটা। ধীরে পড়ো — এটা clear হলে OS-এর অর্ধেক রহস্য খুলে যায়।

Problem: সবাই একই RAM চায়

ধরো process-রা সরাসরি physical address ব্যবহার করতো। তাহলে তিনটা মারাত্মক সমস্যা:

  1. Isolation নেই: Chrome ভুল করে (বা malware ইচ্ছা করে) তোমার password manager-এর memory পড়ে ফেলতে পারতো — শুধু address জানলেই হলো।
  2. Coordination নightmare: Compiler code বানানোর সময় জানেই না program-টা RAM-এর কোথায় বসবে, আর কোন address অন্য কেউ ব্যবহার করছে।
  3. RAM-এর সীমা = hard limit: 8GB RAM-এ সব process মিলে 8GB-র বেশি কিছুতেই না।

Idea: প্রত্যেককে নিজের একটা "নকল" memory জগৎ দাও

OS + hardware মিলে প্রতিটা process-কে একটা illusion দেয়: "পুরো memory তোমার একার।" প্রতিটা process পায় নিজস্ব virtual address space — address 0 থেকে শুরু করে বিশাল একটা range, যেখানে Chapter 5-এর সেই layout (code, data, heap, stack) সাজানো থাকে। Process-এর সব pointer, সব address — এগুলো virtual address। Physical RAM-এর সাথে এদের direct মিল নেই।

তাহলে আসল RAM-এ পৌঁছায় কীভাবে? Translation-এর মাধ্যমে। প্রতিটা memory access-এ virtual address → physical address-এ convert হয়।

Page, page frame, page table

Byte-by-byte translation রাখা অসম্ভব (mapping table-ই RAM খেয়ে ফেলতো)। তাই memory-কে ভাগ করা হয় fixed-size টুকরায়:

  • Page: Virtual address space-এর টুকরা — সাধারণত 4KB।
  • Page frame: Physical RAM-এর একই size-এর টুকরা।
  • Page table: প্রতিটা process-এর নিজস্ব "dictionary" — কোন virtual page কোন physical frame-এ বসেছে। Kernel এটা maintain করে।
Process A                                Process B
virtual addr 0x1000                       virtual addr 0x1000  ← একই address!
      ↓                                         ↓
A-এর Page Table                           B-এর Page Table
      ↓                                         ↓
Physical frame #87                        Physical frame #412  ← আলাদা RAM!

              Physical RAM
   [ frame 87: A-র data ] ... [ frame 412: B-র data ]

দুই process-এর virtual address এক হলেও page table আলাদা — তাই physical memory আলাদা। এটাই isolation-এর মূলমন্ত্র।

Translation-টা করে CPU-র ভিতরের একটা hardware unit — MMU (Memory Management Unit)। প্রতিটা memory access-এ MMU page table দেখে address translate করে। আর যেহেতু প্রতিবার page table (যেটা নিজেই RAM-এ থাকে) পড়া দামি, MMU-র ভিতরে থাকে TLB (Translation Lookaside Buffer) — সাম্প্রতিক translation-গুলোর একটা ছোট cache। বেশিরভাগ access TLB-তেই মিটে যায়।

Page fault: illusion-এর সবচেয়ে চালাক অংশ

Page table-এ একটা entry-র "এই page-এর পিছনে এখন কোনো physical frame নেই" অবস্থাও থাকতে পারে। Process সেই address ছুঁলেই MMU হাত তুলে দেয় — CPU একটা page fault তোলে, control চলে যায় kernel-এর কাছে। তখন kernel সিদ্ধান্ত নেয়:

  • Address টা বৈধ, কিন্তু data এখনো আনা হয়নি (যেমন executable-এর যে অংশ এখনো পড়া হয়নি, বা swap-এ পাঠানো page)? → RAM-এ frame জোগাড় করো, data আনো, page table update করো, process-কে আবার চালাও। Process টেরও পায় না।
  • Address টা আসলেই অবৈধ? → process-কে segmentation fault দিয়ে মেরে ফেলো। C-তে ভুল pointer-এর সেই বিখ্যাত segfault, এই ঘটনা।

এই design থেকে ফাউ পাওয়া superpower গুলো

  • Lazy loading: পুরো executable আগে load করার দরকার নেই — page fault হলে যে অংশ লাগবে সেটাই আসবে। বড় program-ও দ্রুত start হয়।
  • Shared memory: দুই process-এর page table-এ একই physical frame map করে দাও — ব্যস, memory shared। Shared library (libc) এভাবেই শত process-এ এক কপি থাকে।
  • Copy-on-write (CoW): Process copy করার সময় (fork, Chapter 15) memory সত্যি সত্যি copy না করে দুজনের page table-ই একই frame-এ point করাও, শুধু read-only mark করো। কেউ লিখতে গেলে তখনই সেই page-টা copy হবে। ফলে fork প্রায় instant।
  • Swap: RAM ভরে গেলে কম-ব্যবহৃত page disk-এ সরিয়ে frame খালি করা যায়। পরে দরকার হলে page fault-এর মাধ্যমে ফেরত আসবে।
COMMON MISCONCEPTION

"Virtual memory মানে disk-কে RAM হিসেবে ব্যবহার করা।" না — swap শুধু একটা side feature। Virtual memory-র আসল purpose হলো isolation আর address abstraction: প্রতিটা process-এর নিজস্ব, সুরক্ষিত, ধারাবাহিক address জগৎ। Swap বন্ধ থাকলেও (অনেক server-এ থাকে) virtual memory পুরোদমে চলে।

EXPERIMENT (Linux)

cat /proc/<PID>/status | grep -i vm চালাও। VmSize (virtual address space-এর মোট size) প্রায়ই VmRSS (আসলে physical RAM-এ বসে থাকা অংশ)-এর চেয়ে অনেক বড় হবে। এটাই lazy allocation-এর evidence — process অনেক address "reserve" করেছে, কিন্তু kernel frame দিয়েছে শুধু যেটুকু ছোঁয়া হয়েছে।

Chapter 10 — Memory-র Cost আর Trade-off

Virtual memory ফ্রি না — কোথায় কী দাম দিতে হয়, সেটার engineering হিসাব।

Page size-এর টানাটানি

Page 4KB কেন — 1 byte বা 1GB না কেন? দুই দিকেই খরচ আছে:

  • Page ছোট হলে → page table-এ entry বেশি → table-এর নিজেরই memory খরচ বাড়ে, TLB-তে কম range ধরে।
  • Page বড় হলে → internal fragmentation: 5KB data-র জন্য 2MB page দিলে বাকিটা অপচয়। (তুলনায়, heap allocator-এর free space টুকরা টুকরা হয়ে যাওয়াটা external fragmentation — Chapter 6-এ দেখেছিলে।)

4KB একটা historical sweet spot। Database/বড়-memory workload-এর জন্য Linux-এ "huge pages" (2MB) option-ও আছে — TLB-র উপর চাপ কমাতে।

কোন operation-এর কী দাম

Memory mapping: file-কে memory বানিয়ে ফেলা

Virtual memory-র আরেকটা elegant ব্যবহার — mmap। একটা file-কে process-এর address space-এ map করে দাও; এরপর file পড়া মানে স্রেফ memory পড়া। প্রথম access-এ page fault হবে, kernel disk থেকে page আনবে, তারপর থেকে direct। Database engine, dynamic linker (shared library load), বড় file processing — সবখানে এই কৌশল। এখানে দেখো কীভাবে concepts জোড়া লাগছে: page fault যেটা Chapter 9-এ "error handling" মনে হচ্ছিল, সেটাই এখানে একটা loading mechanism।

ENGINEERING INTUITION

Memory নিয়ে চিন্তা করার সময় দুইটা প্রশ্ন করো: (১) আমার working set (একই সময়ে দরকারি data) RAM-এ ধরে তো? না ধরলে major fault/swap শুরু হবে — তখন কোনো code optimization বাঁচাবে না। (২) আমার access pattern কি ঘেঁষাঘেঁষি (dense) নাকি ছড়ানো (sparse)? ছড়ানো হলে TLB আর cache দুটোই কাঁদবে।

Chapter 11 — DMA

Device আর memory-র মধ্যে data transfer-এ CPU-কে মুক্তি দেওয়ার কৌশল।

Problem: CPU-কে কুলি বানানো

ধরো disk থেকে 1GB data আনতে হবে। এক উপায়: CPU নিজে device থেকে টুকরো টুকরো data পড়ে RAM-এ লেখে — byte-কুলিগিরি। এতে দুইটা ক্ষতি: (১) দুনিয়ার সবচেয়ে দামি resource-টা (CPU) copy-র মতো বোকা কাজে আটকে থাকে, (২) সেই সময়ে সে আর কোনো process চালাতে পারে না।

Solution: Direct Memory Access

DMA-তে কাজটা এভাবে ভাগ হয়:

1. Kernel/driver: DMA controller-কে বলে —
   "disk-এর এই block গুলো, RAM-এর এই address-এ, এতটুকু data"
2. CPU: ততক্ষণে অন্য process চালাতে চলে যায়
3. DMA engine: device ↔ RAM data transfer নিজে নিজে করে
4. শেষ হলে device একটা interrupt দেয় — "কাজ শেষ!"
5. Kernel: interrupt handle করে, waiting process-কে জাগিয়ে দেয়

অর্থাৎ CPU-র ভূমিকা এখন শুধু setup আর completion handling — মাঝের ভারী transfer-টা hardware নিজে করে। আধুনিক প্রায় সব serious I/O (disk, network card) DMA-ই ব্যবহার করে।

MENTAL MODEL

এই chapter-টা আসলে একটা বড় সত্যের ছোট উদাহরণ: I/O চলাকালীন CPU সাধারণত বসে থাকে না — সে অন্য কাজ করে। "Disk read হচ্ছে" মানে CPU busy না; মানে তোমার process waiting, আর CPU অন্য কাউকে সময় দিচ্ছে। Async I/O, event loop, "I/O-bound vs CPU-bound" — এই সব আলোচনার ভিত্তি এখানেই।

Chapter 12 — CPU-র ভিতরে

যেখানে আসল "কাজ" হয় — সেই যন্ত্রটার minimum viable mental model।

ভিতরের যন্ত্রপাতি

  • ALU (Arithmetic Logic Unit): যোগ-বিয়োগ-তুলনা-bitwise — actual হিসাবের জায়গা।
  • Control Unit: Instruction পড়ে ঠিক করে কোন যন্ত্রাংশ কী করবে — অর্কেস্ট্রার conductor।
  • Registers: CPU-র ভিতরের হাতেগোনা কয়েকটা ultra-fast storage slot। যেকোনো হিসাবের operand আগে register-এ আসে। এর মধ্যে দুটো special:
    • Program Counter (PC): পরের instruction-এর address। "Program চলছে" মানে এই register এগোচ্ছে।
    • Instruction Register: এই মুহূর্তে execute হওয়া instruction।
  • Cores: আধুনিক CPU আসলে এক chip-এ একাধিক স্বাধীন CPU — প্রতিটা core-এর নিজস্ব ALU, registers, L1/L2 cache। 8-core মানে সত্যিকারের ৮টা কাজ একসাথে।
  • Clock speed: প্রতি second-এ কত cycle (3GHz = ৩০০ কোটি)। প্রতি cycle-এ CPU-র যন্ত্রপাতি এক ধাপ এগোয়।

একটা instruction-এর জীবনচক্র

Fetch    → PC যেখানে দেখাচ্ছে, memory থেকে সেই instruction আনো
Decode   → instruction-টা কী বলছে বোঝো (add? load? jump?)
Execute  → ALU দিয়ে কাজটা করো
Memory   → দরকার হলে memory read/write করো
Writeback→ result register-এ লেখো
   ↺ PC বাড়াও (বা jump হলে নতুন address বসাও), আবার Fetch

তোমার পুরো career-এর সব code — React component থেকে SQL query — শেষ বিচারে এই লুপ: fetch, decode, execute, কোটি কোটি বার প্রতি second-এ। High-level ভাষা যত জাদুই দেখাক, নিচে নেমে সবকিছু এই সরল চক্রে দাঁড়ায়।

CONNECTION

Chapter 5-এর stack pointer, Chapter 4-এর entry point, সামনের Chapter 17-এর context switch — সবকিছু ঘোরে registers-এর চারপাশে। Process-এর "execution state" মানে মূলত: registers + PC + stack pointer-এর snapshot। এই বাক্যটা মনে রেখো, context switching-এ কাজে লাগবে।

Chapter 13 — CPU Cache

Memory wall-এর জবাব — এবং তোমার code-এর speed-এর অন্যতম নীরব নিয়ন্ত্রক।

Cache কেন exists করে

Chapter 7-এ দেখেছি RAM CPU-র তুলনায় বহুগুণ ধীর। প্রতিটা instruction-এ RAM-এ গেলে 3GHz CPU-র বেশিরভাগ সময় কাটতো অপেক্ষায়। সমাধান: CPU-র গা ঘেঁষে ছোট কিন্তু অতি দ্রুত memory রাখো, আর সেখানে সম্ভবত-আবার-লাগবে data রাখো।

"সম্ভবত আবার লাগবে" — এটা অনুমান করা যায় কারণ program-দের behavior-এ দুইটা দারুণ predictable pattern আছে, একসাথে যাদের নাম locality:

  • Temporal locality: এইমাত্র যে data ছুঁয়েছ, শিগগিরই আবার ছোঁবে (loop-এর counter, hot object)।
  • Spatial locality: যে address ছুঁয়েছ, তার পাশের address-ও ছোঁবে (array-র পরের element, struct-এর পরের field)।

Hierarchy

CPU core
  │
  ├─ L1  — ক্ষুদ্র (KB-স্কেল), দ্রুততম, প্রতি core-এ নিজস্ব
  ├─ L2  — বড়, একটু ধীর, সাধারণত core-প্রতি
  ├─ L3  — আরও বড় (MB-স্কেল), সব core-এ shared
  ↓
 RAM   — বিশাল, সবচেয়ে ধীর

আর আগের অধ্যায়ের সেই কথা: data আনা-নেওয়া হয় cache line (~64 bytes) ধরে। একটা int চাইলে আশেপাশের আরও ১৫টা ফাউ আসে।

Sequential vs random: পার্থক্যটা কোথা থেকে আসে

একটা বড় array-র সব element sum করছো — দুইভাবে:

  • Sequential (index 0,1,2,3...): প্রথম access-এ এক cache line এলো — পরের ১৫টা element-ও সাথে এলো। ১৬টার মধ্যে ১৫টা access-ই cache hit। Spatial locality-র জয়।
  • Random (এলোমেলো index): প্রায় প্রতিটা access নতুন cache line — miss, miss, miss। একই পরিমাণ কাজ, কিন্তু বাস্তবে কয়েকগুণ ধীর হতে পারে।

এজন্যই linked list বনাম array-র পার্থক্য শুধু Big-O-তে ধরা পড়ে না: linked list-এর node গুলো heap-এ ছড়িয়ে থাকে (pointer chase = random access), array cache-এর প্রিয় বন্ধু। Big-O সমান হলেও বাস্তব ঘড়িতে array প্রায়ই জেতে।

COMMON MISCONCEPTION

"Cache মানে just faster RAM।" এতে দুটো জিনিস miss হয়: (১) cache একটা hierarchy — স্তরে স্তরে size/speed trade-off, (২) cache কাজই করে locality-র জুয়ায় — তোমার access pattern এলোমেলো হলে cache প্রায় অকেজো। Cache-এর সুবিধা automatic না; সেটা তোমার data layout আর access pattern-এর পুরস্কার।

CAN I EXPLAIN THIS?
  • Temporal আর spatial locality — একটা করে নিজের code-এর উদাহরণ?
  • Cache line কীভাবে sequential access-কে জেতায়?
  • L1/L2/L3-এর size ছোট → বড় আর speed দ্রুত → ধীর কেন সাজানো?

Chapter 14 — Pipelining আর Parallelism

CPU একটা instruction শেষ করে পরেরটা ধরে না — কেন এবং তার মানে কী।

Pipeline: assembly line-এর কৌশল

Chapter 12-র সেই fetch → decode → execute → memory → writeback ধাপগুলো ভাবো একটা garment factory-র line হিসেবে। এক instruction যখন decode হচ্ছে, পরেরটা তখন fetch হতে পারে — ধাপগুলো তো আলাদা যন্ত্রাংশে চলে। এটাই pipelining: এক মুহূর্তে pipeline-এর ভিতরে একাধিক instruction, প্রত্যেকে আলাদা stage-এ। ফলে প্রতিটা instruction-এর নিজের সময় না কমলেও প্রতি cycle-এ একটা করে instruction "বের হয়ে আসে"।

Pipeline-এর শত্রু হলো branch — if/else, loop-এর শর্ত। পরের instruction কোনটা, তা তো শর্তের result-এর আগে জানা যায় না! CPU তখন অনুমান করে (branch prediction) আগেভাগে কাজ চালিয়ে যায়; অনুমান ভুল হলে pipeline-এর আধখাওয়া কাজ ফেলে দিতে হয়। এজন্যই খুব unpredictable branching-ওয়ালা code (যেমন unsorted data-র উপর শর্ত) মাঝে মাঝে আশ্চর্যরকম ধীর হয়।

Parallelism-এর স্তরগুলো

  • Pipeline (এক core-এর ভিতরে): ধাপ overlap — উপরে দেখলাম।
  • Multiple cores: সত্যিকারের একসাথে একাধিক instruction stream। ৮ core = ৮টা process/thread আক্ষরিকভাবেই simultaneously।
  • SMT / Hyper-threading: এক physical core দুইটা "hardware thread" সাজে — এক thread memory-র জন্য wait করলে core-এর অলস যন্ত্রাংশ আরেক thread চালায়। দুই core-এর সমান না, কিন্তু utilization বাড়ে। এজন্যই ৪-core laptop-এ nproc ৮ দেখাতে পারে।
Side note: RISC vs CISC, 32-bit vs 64-bit

RISC vs CISC: Instruction set design-এর দুই দর্শন — ছোট-সরল instruction (RISC: ARM, তোমার M-series Mac) বনাম জটিল-শক্তিশালী instruction (CISC: x86)। আজকাল ভিতরের বাস্তবায়ন অনেকটা মিলে গেছে; app developer হিসেবে মূল takeaway: আলাদা instruction set মানে আলাদা machine code — এজন্যই ARM Mac-এ x86 binary সরাসরি চলে না (Rosetta translate করে)।

32-bit vs 64-bit: মূলত address-এর size। 32-bit-এ virtual address space সর্বোচ্চ 4GB — আধুনিক workload-এর জন্য হাস্যকর ছোট; 64-bit-এ কার্যত সীমাহীন। Registers-ও চওড়া হয়। ব্যস, এটুকুই দরকার।

ENGINEERING TAKEAWAY

CPU নিজে ভিতরে ভিতরে প্রচণ্ড parallel — কিন্তু এক core-এ তোমার single-threaded JS যতই optimize করো, বাকি ৭টা core বসে থাকবে। Multi-core কাজে লাগাতে হলে process/thread level-এ parallelism আনতে হয় — সেই গল্প Part 5-এ।

  • Branch prediction কেন লাগে, ভুল হলে কী দাম?
  • Core আর hardware thread (SMT)-এর পার্থক্য?

Chapter 15 — Process Management

Process-এর জীবনচক্র, state, আর জন্ম-রহস্য: fork।

Process-এর state

Kernel-এর খাতায় প্রতিটা process যেকোনো মুহূর্তে একটা state-এ থাকে:

          জন্ম
           ↓
        [Ready] ←──────────────┐
           ↓ scheduler CPU দিলো  │ সময় শেষ / বড় কেউ এলো
        [Running] ─────────────┘
           ↓ I/O চাইলো (disk, network, sleep...)
        [Waiting / Blocked]
           ↓ I/O শেষ → আবার Ready
           
        [Terminated] ← exit করলে
  • Running: এই মুহূর্তে কোনো core-এ চলছে। একটা core-এ একসাথে একটাই।
  • Ready: চলতে প্রস্তুত, কিন্তু CPU খালি নেই — লাইনে দাঁড়িয়ে।
  • Waiting/Blocked: কিছুর জন্য অপেক্ষা করছে (disk data, network packet, timer)। CPU চাইছেই না। তোমার server-এর বেশিরভাগ process দিনের বেশিরভাগ সময় এখানেই কাটায়।
  • Terminated: শেষ। Kernel exit code ইত্যাদি রেখে দেয় parent-এর জন্য।

এই state machine চালায় kernel-এর scheduler — কে Ready থেকে Running-এ যাবে সেই সিদ্ধান্ত তার। (Scheduling algorithm-এর academic জঙ্গলে আমরা ঢুকবো না; "fairness আর priority মিলিয়ে kernel সিদ্ধান্ত নেয়" — এই model-ই যথেষ্ট।)

fork(): process-এর জন্ম

Unix-এ নতুন process বানানোর মৌলিক উপায়টা মজার — "নতুন বানাও" না, বরং "নিজের কপি বানাও":

pid_t pid = fork();

if (pid == 0) {
    // এখানে child process চলছে
} else {
    // এখানে parent — pid-এ child-এর PID
}

fork() call করলে kernel চলমান process-এর একটা প্রায়-হুবহু copy বানায়: একই code, memory-র copy (আসলে copy-on-write — Chapter 9 মনে আছে? তাই প্রায় instant), একই open file-গুলো। মজাটা হলো — একই fork() call দুই process-এ দুইবার return করে: parent পায় child-এর PID, child পায় 0। ওই if/else দিয়েই দুজনের রাস্তা আলাদা হয়।

তারপর child সাধারণত exec() family-র একটা call দিয়ে নিজের ভিতরে নতুন executable load করে — পুরনো memory ছবি মুছে নতুন program বসে। Shell ঠিক এটাই করে: তুমি ls লিখলে shell fork করে, child-এ exec("ls") হয়, parent (shell) child শেষ হওয়ার wait করে। এই fork+exec ভাগাভাগির সুবিধা: fork আর exec-এর মাঝখানে child নিজের setup বদলাতে পারে (যেমন output redirect — ls > file.txt এভাবেই কাজ করে)।

এভাবেই পুরো system-এ process-দের একটা parent-child tree তৈরি হয় — সবার আদি পূর্বপুরুষ PID 1 (init/systemd)।

EXPERIMENT

ps -ef | head চালিয়ে PPID (parent PID) column দেখো। Linux-এ pstree | head -30 চালালে পুরো family tree দেখা যায় — systemd থেকে নেমে তোমার terminal, তার child shell, তার child তোমার command।

  • fork() "দুইবার return করে" — মানে কী?
  • fork+exec আলাদা দুই ধাপ রাখার সুবিধা কী?

PART 5 · PROCESS MANAGEMENT

Chapter 16 — Process vs Thread

Concurrency-র সব আলোচনার ভিত্তি — এই ছবিটা মাথায় গাঁথা চাই।

Thread কী

এতক্ষণ বলেছি "process চলে"। আরও সঠিকভাবে: process-এর ভিতরের thread চলে। Thread হলো execution-এর একক — একটা নিজস্ব instruction stream, নিজস্ব stack, নিজস্ব register state। প্রতিটা process অন্তত একটা thread নিয়ে জন্মায় (main thread), চাইলে আরও বানাতে পারে।

মূল কথা: process হলো resource-এর container, thread হলো execution-এর unit। Address space, heap, open files — এগুলো process-এর সম্পত্তি; process-এর সব thread এগুলো share করে।

Process (একটা address space)
├── Thread 1   ├── Thread 2   ├── Thread 3
│   নিজস্ব:      │   নিজস্ব:      │   নিজস্ব:
│   • Stack     │   • Stack     │   • Stack
│   • Registers │   • Registers │   • Registers
│   • PC        │   • PC        │   • PC
│
└── সবাই মিলে shared:
    • Code (text)  • Heap  • Global data  • Open files/sockets

যার যার execution state আলাদা, সবার data জগৎ এক।

Share করা: আশীর্বাদ ও অভিশাপ

দুই processএক process-এর দুই thread
Memoryসম্পূর্ণ আলাদা (isolation)Heap/global shared
Communicationকষ্টের — pipe, socket, shared memory setup লাগে, প্রায়ই kernel-এর মধ্য দিয়েসহজ — একই variable-এ লেখো, অন্যজন দেখে
একজনের crashঅন্যজন বাঁচেপুরো process মরে — সবাই একসাথে ডোবে
তৈরির খরচবেশি (নতুন address space, page table)কম (শুধু stack + thread state)
Bug-এর ধরনInterface-এ ভুলRace condition, data corruption (Chapter 18)
COMMON MISCONCEPTION

"Thread is a lightweight process" — অসম্পূর্ণ, আর আসল point-টা miss করে। হালকা তো বটেই, কিন্তু defining পার্থক্য ওজনে না — address space-এ: process-রা আলাদা জগতে থাকে, thread-রা এক জগৎ share করে। এই sharing-ই thread-এর সব শক্তি আর সব বিপদের উৎস।

তোমার দুনিয়ায়

Node.js-এর model: এক process, তোমার JS চলে এক main thread-এ, কিন্তু ভিতরে libuv-এর একটা thread pool কিছু কাজ (file I/O, crypto, DNS) চালায়, আর V8-এর GC-ও আলাদা thread ব্যবহার করে। worker_threads খুললে সত্যিকারের আলাদা JS thread পাও। আর PM2 cluster mode? সেটা thread না — আলাদা process, এজন্যই ওদের মধ্যে memory share হয় না।

  • Thread-দের মধ্যে কোনটা shared, কোনটা নিজস্ব?
  • প্রতিটা thread-এর আলাদা stack লাগে কেন? (Hint: function call)
  • Chrome tab-প্রতি process কেন — thread কেন না?

Chapter 17 — Context Switching

৪টা core-এ ৪০০টা process "একসাথে" চলার জাদু — আর সেই জাদুর দাম।

Context মানে কী

Chapter 12-র সেই বাক্যটা ফিরিয়ে আনি: একটা thread-এর execution state মানে registers + program counter + stack pointer-এর snapshot। এটাই তার context — "আমি কোন instruction-এ ছিলাম, আমার হিসাবের মাঝপথের value গুলো কী, আমার stack কোথায়।"

Switch-টা কীভাবে ঘটে

Process A চলছে...
   ↓ interrupt (timer) বা A নিজেই block হলো (I/O চাইলো)
━━━━━━ kernel mode-এ প্রবেশ ━━━━━━
1. A-র context (registers, PC, SP) kernel-এ save
2. Scheduler: "এরপর কে?" → B নির্বাচিত
3. Address space switch — B-র page table চালু
4. B-র সেভ-করা context registers-এ restore
━━━━━━ user mode-এ ফেরা ━━━━━━
Process B ঠিক সেখান থেকে চলা শুরু করলো,
যেখানে সে শেষবার থেমেছিল — যেন কিছুই হয়নি

Switch trigger হয় মূলত দুইভাবে: (১) process নিজে block হলো — I/O, sleep, lock-এর অপেক্ষা; (২) kernel জোর করে থামালো — timer interrupt-এ scheduler দেখলো অনেকক্ষণ চলেছে, এবার অন্যের পালা (preemption)। এই দ্বিতীয়টার জন্যই একটা infinite loop-ওয়ালা process পুরো machine জমিয়ে ফেলতে পারে না।

দামটা কোথায়

Context switch free না — কিন্তু দামটা যেখানে ভাবো সেখানে না। Register save/restore নিজে সস্তা। আসল খরচ:

  • Kernel-এ ঢোকা-বেরোনো — mode switch-এর overhead।
  • Cache দূষণ: A-র data দিয়ে গরম হয়ে থাকা CPU cache B-র কোনো কাজে লাগে না; B-র শুরুটা হয় ঠান্ডা cache-এ — miss-এর ঝড়। A ফিরে এলে তার cache-ও ততক্ষণে B-র data-য় ভরে গেছে।
  • TLB flush: Address space বদলালে পুরনো translation গুলোও অচল।

মানে switch-এর পরের কিছু সময় ধরে সবকিছুই একটু ধীর চলে। Exact nanosecond মুখস্থের দরকার নেই — takeaway হলো: switch যত ঘনঘন, "আসল কাজ"-এর ভাগ তত কম। হাজার হাজার thread বানিয়ে ফেললে CPU সময়ের বড় অংশ যায় জায়গা বদলাবদলিতেই — এই রোগের নাম thrashing। (এক process-এর দুই thread-এর মধ্যে switch একটু সস্তা — address space বদলায় না — কিন্তু cache-এর সমস্যা থেকেই যায়।)

MENTAL MODEL

CPU হলো এমন এক পাঠক যে হাজারটা বই "একসাথে" পড়ছে — প্রতিটা বইয়ে bookmark (context) রেখে রেখে লাফাচ্ছে। লাফানো এত দ্রুত যে মনে হয় সব বই একসাথে পড়া হচ্ছে। কিন্তু প্রতিটা লাফে bookmark রাখা-খোঁজা + "কোথায় যেন ছিলাম" মনে করার (cache warm-up) খরচ আছে।

EXPERIMENT (Linux)

vmstat 1 চালাও — cs column দেখায় প্রতি second context switch-এর সংখ্যা। একটা idle machine-এও হাজারে হাজারে দেখতে পারো। তারপর কোনো busy কাজ চালিয়ে দেখো সংখ্যাটা কীভাবে নড়ে।

Chapter 18 — Concurrency

Shared state + একাধিক thread = software engineering-এর সবচেয়ে কুখ্যাত bug-দের জন্মভূমি।

Concurrency vs parallelism

দুটো আলাদা জিনিস, প্রায়ই গুলিয়ে যায়:

  • Concurrency: একাধিক কাজ overlapping সময়ে এগোচ্ছে — এক core-ও হতে পারে, context switch করে করে। Structure-এর ব্যাপার।
  • Parallelism: একাধিক কাজ আক্ষরিক একই মুহূর্তে চলছে — একাধিক core লাগবেই। Execution-এর ব্যাপার।

একজন waiter ১০টা টেবিল সামলাচ্ছে = concurrency। ১০ জন waiter = parallelism। Node.js event loop হলো এক waiter-এর master class; multi-core কাজে লাগানো মানে waiter বাড়ানো।

Race condition: কুখ্যাত counter++

দুই thread একই shared counter বাড়াচ্ছে। Source code-এ counter++ এক লাইন, কিন্তু CPU-র চোখে তিনটা আলাদা instruction:

1. LOAD   counter → register     (পড়ো)
2. ADD    register + 1           (বাড়াও)
3. STORE  register → counter     (লেখো)

এখন এই interleaving-টা দেখো (counter = 5 থেকে শুরু):

Thread A                    Thread B
LOAD  → 5
                            LOAD  → 5      ← A এখনো লেখেনি!
ADD   → 6
                            ADD   → 6
STORE → 6
                            STORE → 6      ← A-র কাজ মুছে গেল

দুইবার increment, কিন্তু ফলাফল 6 — 7 না।

এটাই race condition: ফলাফল নির্ভর করছে কে-কখন-চললো তার timing-এর উপর। ভয়ংকর দিকটা হলো — বেশিরভাগ সময় ঠিকঠাক চলে; হাজারে একবার ভুল হয়, সেটাও production-এ, load-এর সময়, আর reproduce করা প্রায় অসম্ভব।

রক্ষার অস্ত্র

যে code shared state ছোঁয়, সেই অংশটার নাম critical section। নিয়ম: এক সময়ে এক thread-ই সেখানে ঢুকবে (mutual exclusion)। Tools:

  • Mutex (lock): Critical section-এর দরজার তালা। ঢোকার আগে lock নাও, বেরিয়ে ছাড়ো; অন্যরা lock না পাওয়া পর্যন্ত block থাকে। সরল, সর্বাধিক ব্যবহৃত। বিপদ: দুই thread দুই lock ধরে পরস্পরেরটার জন্য বসে থাকলে deadlock — কেউই আর নড়ে না। (এর mathematical treatment-এ যাচ্ছি না; "lock নেওয়ার order সব জায়গায় এক রাখো" — এই practical নিয়মটাই বেশিরভাগ deadlock ঠেকায়।)
  • Semaphore: Counter-ওয়ালা তালা — "সর্বোচ্চ N জন একসাথে"। যেমন DB connection pool: ১০টা connection, ১১তম আবেদনকারী অপেক্ষা করবে।
  • Atomic operations: Hardware-এর দেওয়া বিশেষ instruction যা load-modify-store-কে একটা অবিভাজ্য ধাপে করে — ছোট কাজে (counter!) lock-এর চেয়ে সস্তা।
"JS-এ তো race condition নেই!" — সত্যি?

Memory-level race (উপরের counter++) single-threaded JS-এ হয় না, ঠিক। কিন্তু logical race দিব্যি হয়: দুইটা async request-ই আগে DB থেকে balance পড়লো, তারপর দুজনেই লিখলো — একই lost-update গল্প, শুধু interleaving-টা instruction level-এ না, await point-এ। Race-এর মূল কারণ thread না — shared mutable state + non-atomic read-modify-write। সেটা DB row-তেও হয়।

  • counter++ কেন atomic না, আর সেটা থেকে bug কীভাবে জন্মায়?
  • Mutex আর semaphore-এর পার্থক্য?

Chapter 19 — Thread কখন ব্যবহার করবে?

Workload চেনো, তারপর tool বাছো — একটা practical decision framework।

প্রথম প্রশ্ন: তোমার workload কী-bound?

  • CPU-bound: সময় যাচ্ছে হিসাবে — image processing, encryption, বড় JSON parse, ML inference। CPU 100%-এ আটকে।
  • I/O-bound: সময় যাচ্ছে অপেক্ষায় — DB query, HTTP call, file read। CPU বেশিরভাগ সময় অলস; process টা Waiting state-এ (Chapter 15) পড়ে থাকে।

বেশিরভাগ web backend আসলে I/O-bound — request-এর জীবনের সিংহভাগ কাটে DB আর downstream service-এর অপেক্ষায়।

Framework

পরিস্থিতিভালো fitকেন
CPU-bound, কাজগুলো মোটামুটি স্বাধীন, data ভারী share করতে হয় নাMultiple processesসব core কাজে লাগে, isolation ফ্রি — একটার crash/leak অন্যদের ছোঁয় না। (PM2 cluster, worker process)
CPU-bound, কিন্তু বড় shared data structure-এর উপর সবাই কাজ করবেThreadsData copy না করে share করা যায়; process-এর মধ্যে বড় data পাঠানো দামি।
I/O-bound, অনেক concurrent connectionEvent loop / async I/Oঅপেক্ষার জন্য thread পোষা অপচয় — এক thread-ই non-blocking ভাবে হাজারটা সামলায় (Chapter 28-29)।
I/O-bound, কিন্তু blocking API/library ব্যবহার করতেই হবেThread poolBlocking call-গুলো pool-এর thread-এ ফেলে main flow মুক্ত রাখো। (Node-এর libuv নিজেই এটা করে।)

Thread-এর hidden bill

  • প্রতিটা thread-এর নিজস্ব stack (default প্রায়ই MB-স্কেলে reserve হয়) — দশ হাজার thread মানে memory-র বিশাল দাবি।
  • Thread যত বেশি, context switch তত বেশি (Chapter 17) — একটা সীমার পরে থread যোগ করলে throughput কমে।
  • Shared state এলেই lock, lock এলেই contention + deadlock-এর ঝুঁকি + মাথার ব্যথা (Chapter 18)।
RULE OF THUMB

CPU-bound হলে parallelism দরকার — core-সংখ্যার কাছাকাছি worker (process বা thread)। I/O-bound হলে parallelism না, দরকার অপেক্ষাটা সস্তায় করা — async I/O/event loop। আর isolation যত পাও নিয়ে নাও: shared state যত কম, রাতের ঘুম তত ভালো।

Chapter 20 — Persistent Storage

RAM-এর বাইরের জগৎ — যেখানে data power গেলেও বাঁচে, কিন্তু দাম দিতে হয় speed-এ।

কেন persistence আলাদা সমস্যা

RAM volatile — তাই database, file, log সবকিছুর একটা "স্থায়ী ঠিকানা" লাগে। সেই ঠিকানাই storage। কিন্তু storage-এর economics সম্পূর্ণ আলাদা: RAM-এর চেয়ে অনেক সস্তা আর বড়, কিন্তু অনেক ধীর। এই gap-টাই file I/O-র পুরো design-কে shape করে।

তিন প্রজন্ম

Deviceকীভাবে কাজ করেCharacter
HDDঘূর্ণায়মান চুম্বকীয় disk + নড়াচড়া করা read headMechanical বলে seek (head সরানো) ভীষণ দামি — random access-এ মরে, sequential-এ চলনসই। এখনো সস্তা bulk storage-এ রাজত্ব।

NVMe SSDFlash + PCIe দিয়ে সরাসরি CPU-র কাছেআজকের standard। বিশাল parallelism — একসাথে বহু request গিলতে পারে। তোমার Mac-এর ভিতরে এটাই।

Latency vs throughput — আলাদা করে ভাবো

  • Latency: একটা request-এর জবাব আসতে কত সময়। DB-র একটা ছোট read এখানে আটকায়।
  • Throughput: প্রতি second মোট কত data। বড় file copy/backup এখানে আটকায়।

দুটো আলাদা অক্ষ — একটা device-এর throughput দুর্দান্ত হয়েও latency মাঝারি হতে পারে। আর সব device-এই sequential access random-এর চেয়ে সুবিধাজনক (HDD-তে আকাশ-পাতাল, SSD-তেও লক্ষণীয়)। Database-রা এজন্যই append-only log (WAL) এত ভালোবাসে — লেখাগুলো sequential করে ফেলা।

মাত্রাজ্ঞান (মুখস্থ না, অনুপাত)

মোটা দাগে: CPU cache → RAM → NVMe → HDD → network storage — প্রতিটা ধাপে latency মোটামুটি এক-দুই মাত্রা (order of magnitude) করে বাড়ে। মানে RAM-এ যা চোখের পলক, disk-এ তা দুপুরের খাবার-বিরতি। এই অনুপাতটাই মনে রাখো — এটাই বোঝায় কেন OS এত মরিয়া হয়ে disk access এড়াতে চায় (Chapter 23-এর page cache)।

Chapter 21 — File I/O ভিতরে কীভাবে কাজ করে

fs.readFile() লেখা থেকে disk-এর data হাতে পাওয়া পর্যন্ত — পুরো stack-টা এবার সিরিয়াসলি।

Stack-টা

Application        — read(fd, buf, 4096)
      ↓ system call
VFS                — "file" ধারণাটা সামলায়, fd → আসল file
File System (ext4) — file-এর byte → disk-এর কোন block, হিসাব রাখে
Page Cache         — data RAM-এ আছে? থাকলে এখানেই শেষ ✓
Block Layer        — disk request-দের queue, merge, schedule
Driver             — device-এর ভাষায় command
      ↓
Storage Device     — data পড়ে DMA-তে RAM-এ দেয়

একটা read-এর গল্প, step by step

  1. open("config.json") — kernel file-টা খুঁজে বের করে, process-এর file descriptor table-এ একটা entry বসায়, তোমাকে দেয় একটা ছোট number — fd (ধরো 3)। এরপরের সব কথাবার্তা এই fd দিয়েই।
  2. read(3, buf, 4096) — system call। Kernel-এ ঢুকলো।
  3. Filesystem হিসাব করে: এই file-এর প্রথম 4096 bytes মানে disk-এর অমুক block গুলো।
  4. Page cache check — block গুলোর data কি আগে থেকেই RAM-এ? থাকলে সরাসরি copy করে দাও — disk ছোঁয়াই লাগলো না। বাস্তবের বেশিরভাগ read এখানেই মিটে যায়।
  5. Cache miss হলে: block layer-এ request → driver → device। ততক্ষণ তোমার process Waiting state-এ; CPU অন্য কাউকে চালায় (Chapter 15, 17 জোড়া লাগছে দেখো)।
  6. Device DMA-তে data page cache-এ দেয়, interrupt দেয় (Chapter 11)। Kernel process-কে জাগায়, data user buffer-এ copy করে, read() return করে।

Write-এর গল্প: একটা মোচড় আছে

write(fd, data, len) return করলো মানে data disk-এ পৌঁছে গেছে? না। Default behavior: kernel data-টা page cache-এ লিখে page-টাকে dirty mark করে সাথে সাথেই return করে দেয়। Disk-এ আসল লেখা হয় পরে, background-এ (writeback)। ফলে write অবিশ্বাস্য fast লাগে — কারণ তুমি আসলে RAM-এ লিখেছ।

Trade-off পরিষ্কার: মাঝখানে power গেলে সেই dirty data হারিয়ে যায়। এজন্যই "সত্যি সত্যি disk-এ নামাও" বলার আলাদা system call আছে — fsync(fd)। Database-রা transaction commit-এ এটাই করে; এজন্যই durable write ধীর, আর এজন্যই Postgres-এর WAL config-এ fsync নিয়ে এত কথা।

COMMON MISCONCEPTION

"write() সফল return করেছে মানে data নিরাপদ।" না — মানে data kernel-এর হাতে পৌঁছেছে। Durability চাইলে fsync (এবং তার দাম) লাগবে। এই এক ভুল বোঝাবুঝি থেকে বহু "power গেল, data গেল" ঘটনা জন্মেছে।

EXPERIMENT (Linux)

strace -e trace=openat,read,write,close cat /etc/hostname চালাও। নিজের চোখে দেখো cat-এর মতো সামান্য command-ও ঠিক এই system call গুলোই করে: open → fd পেলো → read → write (stdout-এ) → close। এই x-ray মেশিনটা (strace) মনে রেখো — Chapter 32-এ আবার আসবে।

  • Read path-এ page cache কোথায় বসে, কী বাঁচায়?
  • write() fast কেন, আর সেই speed-এর দাম কী?
  • fsync কখন লাগে?

Chapter 22 — File Systems

Disk তো শুধু নাম্বার-দেওয়া block-এর সমুদ্র — "file" জিনিসটা বানায় কে?

Problem আর idea

Storage device-এর ভাষা: "block #48211 পড়ো/লেখো।" আমাদের ভাষা: "/home/reza/notes.md খোলো।" মাঝের অনুবাদক-টাই file system — disk-এর block গুলোর উপর সে বানায় নাম, hierarchy, permission, size — পুরো একটা সাজানো জগৎ।

Core building blocks (ext4-এর ছবিতে)

  • File = data blocks + metadata। Metadata থাকে inode-এ: size, owner, permission, timestamps, আর সবচেয়ে জরুরি — data কোন কোন block-এ আছে তার map। মজার fact: inode-এ file-এর নাম নেই।
  • Directory আসলে একটা বিশেষ file — যার content হলো একটা তালিকা: নাম → inode number। "File-এর নাম" আসলে directory-র সম্পত্তি। এজন্যই hard link সম্ভব — দুই নাম, এক inode।
  • Path resolution: /home/reza/notes.md খুলতে kernel হাঁটে: root-এর inode → তার entry-তে "home" → সেই inode → entry "reza" → inode → entry "notes.md" → অবশেষে file-এর inode। প্রতিটা ধাপে permission check।
  • Allocation: নতুন data-র জন্য কোন free block দেবে সেটা filesystem-এর কৌশল — ভালো filesystem চেষ্টা করে এক file-এর block গুলো কাছাকাছি রাখতে (sequential read-এর সুবিধা, Chapter 20)।
directory entry          inode #5021              disk blocks
"notes.md" → 5021   →   size: 8KB           →    [block 300][block 301]
                        owner: reza
                        perms: rw-r--r--
                        blocks: 300, 301

ext4 আধুনিক Linux-এর default — এতে আছে journaling: metadata বদলানোর আগে একটা log-এ intention লিখে রাখা, যাতে crash-এর পরে filesystem অসঙ্গত (corrupt) না থাকে। আর FAT? সেই সাদাসিধে পুরনো filesystem — permission নেই, journaling নেই — আজও pendrive/SD card-এ বেঁচে আছে কারণ সবাই এটা পড়তে পারে।

শেষ টুকরো — VFS (Virtual File System): kernel-এর ভিতরের সেই abstraction layer যার কারণে ext4, FAT, নেটওয়ার্ক filesystem — সবাইকে application একই open/read/write দিয়ে দেখে। Abstraction on abstraction — OS design-এর প্রিয় খেলা।

EXPERIMENT

ls -li চালাও — প্রথম column-টাই inode number। তারপর stat <filename> — এক file-এর পুরো inode-এর গল্প: size, blocks, links, timestamps। df -T . দিয়ে দেখো তোমার filesystem-টা আসলে কী (Linux-এ ext4, macOS-এ apfs)।

  • Directory-কে "special file" বলা হয় কেন?
  • VFS কী সমস্যা solve করে?

Chapter 23 — Page Cache

Memory আর storage-এর জগৎ যেখানে মিলে যায় — এবং তোমার "দ্বিতীয়বার fast" রহস্যের সমাধান।

Idea

Disk RAM-এর চেয়ে মাত্রায়-মাত্রায় ধীর (Chapter 20)। আর RAM-এর খালি অংশ এমনিতেই বসে থাকে। Kernel-এর সিদ্ধান্ত: disk থেকে যা-ই পড়া হোক, RAM-এ রেখে দাও — কে জানে আবার লাগবে। এই জায়গাটার নাম page cache — file data-র page-size টুকরো, RAM-এ, kernel-এর জিম্মায়।

এজন্যই free -h-তে "buff/cache" এত বড় (Chapter 7-এর সেই ধাঁধা!) — এটা "দখল" না, এটা service। কোনো process-এর memory লাগলে kernel cache ছেড়ে দেয় — clean page ফেলে দেওয়া তো free।

Read path আর write path

READ:  read() → page cache-এ আছে? ── hit → copy, শেষ। (RAM speed!)
                    └── miss → disk থেকে এনে cache-এ রাখো → copy

WRITE: write() → cache-এর page-এ লেখো → page টা dirty → return!
                    ...পরে background-এ kernel dirty page গুলো disk-এ নামায়

Dirty page মানে: cache-এর version disk-এর চেয়ে নতুন। Kernel এগুলো সময়মতো/চাপে পড়ে flush করে; fsync মানে "এই file-এর dirty page গুলো এক্ষুনি নামাও" (Chapter 21-এর সেই গল্প)।

ফলাফল: চেনা চেনা কিছু behavior-এর ব্যাখ্যা

  • একই file দ্বিতীয়বার পড়া নাটকীয়ভাবে fast — প্রথমবার disk, দ্বিতীয়বার RAM। Benchmark করার সময় এটা মাথায় না রাখলে ভুল সিদ্ধান্তে পৌঁছাবে ("cold cache vs warm cache")।
  • Database server-এ "free RAM" প্রায় শূন্য দেখায় — এবং সেটাই কাম্য: পুরো RAM জুড়ে data file-এর cache।
  • Server restart-এর পর প্রথম কিছুক্ষণ সব ধীর — cache ঠান্ডা, ধীরে ধীরে গরম হয়।
MENTAL MODEL

এতক্ষণে খেয়াল করেছ নিশ্চয়ই — এই গল্পটা আগে শুনেছ: CPU-র জন্য cache (Chapter 13), address translation-এর জন্য TLB (Chapter 9), আর disk-এর জন্য page cache। যেখানেই দুই স্তরের speed-এ বিশাল ফারাক, মাঝখানে একটা cache — computing-এর সবচেয়ে পুনরাবৃত্ত design pattern। তোমার Redis layer-ও একই pattern-এর আরেক তলা।

EXPERIMENT (Linux)

একটা বড় file নাও (না থাকলে বানাও: dd if=/dev/zero of=big.bin bs=1M count=500)। তারপর: time cat big.bin > /dev/null — দুইবার চালাও। দ্বিতীয়বারের সময়টা দেখো। এটাই page cache, খালি চোখে।

  • "Linux ate my RAM" অভিযোগটা ভুল কেন?

Chapter 24 — File I/O-র Mode গুলো

Blocking, sync, async, O_SYNC, O_DIRECT — শব্দগুলোর পিছনের আসল প্রশ্ন দুটো মাত্র।

File I/O-র যাবতীয় mode আসলে দুইটা স্বাধীন প্রশ্নের উত্তর:

  1. আমার thread কি অপেক্ষা করবে? (blocking vs non-blocking/async)
  2. Page cache-এর সাথে সম্পর্ক কী হবে? (durability/caching)

প্রশ্ন ১: অপেক্ষা

  • Blocking (default): read() ডাকলে data না আসা পর্যন্ত thread টা Waiting-এ। সরল, বোঝা সহজ — আর এক thread-এ এক সময়ে একটাই I/O।
  • Asynchronous: "কাজটা শুরু করো, আমি অন্য কাজে যাচ্ছি — শেষ হলে জানিও।" Thread আটকায় না। Linux-এ আধুনিক উত্তর io_uring; Node.js তোমাকে যে async fs API দেয়, তার পিছনে (ঐতিহাসিকভাবে) থাকে thread pool — blocking read-গুলো অন্য thread-এ চালিয়ে তোমার thread-কে মুক্ত রাখা।

প্রশ্ন ২: cache-এর সাথে বোঝাপড়া

  • Default: সব page cache-এর মধ্য দিয়ে — write মানে cache-এ লেখা (fast, কিন্তু durable না যতক্ষণ না flush)।
  • O_SYNC: প্রতিটা write disk-এ পৌঁছানোর পরেই return করবে — যেন প্রতি write-এর সাথে ফাউ fsync। Durability সর্বোচ্চ, speed-এর দাম দিয়ে।
  • O_DIRECT: Page cache-কে পুরোপুরি bypass — data সরাসরি disk ↔ তোমার buffer। কে চায় এটা? যে নিজে আরও ভালো cache চালায় — যেমন কিছু database engine: "kernel, তোমার generic cache লাগবে না, আমি আমার data আমি-ই ভালো বুঝি।" সাধারণ application-এর জন্য এটা প্রায় সবসময় ভুল choice — kernel-এর cache-টা আসলে চমৎকার।
TRADE-OFF TRIANGLE

Speed, durability, simplicity — তিনটা একসাথে পুরোপুরি পাওয়া যায় না। Default mode: speed + simplicity। O_SYNC/fsync: durability কিনলে speed বেচতে হয়। O_DIRECT: control কিনলে simplicity বেচতে হয়। Database design-এর অর্ধেক আলোচনা এই ত্রিভুজের ভিতরে।

  • O_SYNC আর O_DIRECT-এর পার্থক্য — কে কী bypass/guarantee করে?
  • সাধারণ app-এ O_DIRECT bad idea কেন?

Chapter 25 — Socket কী?

Network-কে OS যেভাবে file বানিয়ে দেয়।

Abstraction-টা

Network hardware-এর জগৎ raw packet-এর জগৎ। কিন্তু তুমি চাও "ওই server-এর সাথে একটা connection, যেখানে আমি bytes লিখবো আর পড়বো।" এই চাওয়াটার OS-দেওয়া রূপ হলো socket — network communication-এর একটা endpoint, kernel-এর তৈরি ও রক্ষণাবেক্ষণ করা একটা object।

সবচেয়ে সুন্দর অংশ: socket-ও পাও একটা file descriptor হিসেবে — file-এর মতোই (Chapter 21)! একই read()/write() চালে, একই fd table-এ বসে। Unix-এর সেই বিখ্যাত দর্শন — "everything is a file (descriptor)" — এখানে পুরো জৌলুসে।

ঠিকানা: IP + port

একটা TCP connection-কে uniquely চেনা যায় চারটা জিনিসে: (client IP, client port, server IP, server port)। IP machine চেনায়, port সেই machine-এর ভিতরে কোন application চেনায়। Server একটা well-known port-এ বসে থাকে (443, 5432...); client-এর port টা OS নিজেই একটা খালি নাম্বার থেকে দিয়ে দেয় (ephemeral port)। এই চার-টুপল আলাদা হলেই connection আলাদা — এজন্যই এক server port-এ হাজারো client একসাথে ঝুলতে পারে।

Client app                              Server app
   │ write("GET /")                          ↑ read() → "GET /"
   ↓                                         │
socket fd                               socket fd
   ↓                                         ↑
Client kernel (TCP/IP stack)            Server kernel (TCP/IP stack)
   ↓                                         ↑
   └───────── network (packets) ─────────────┘

দুই পাশের application শুধু নিজ নিজ socket দেখে; packet-এর ঝামেলা পুরোটা দুই kernel-এর।

Server side-এর জীবনচক্র

Server-এ socket-এর ব্যবহারটা একটু আলাদা ছন্দে চলে — নামগুলো চিনে রাখো, সামনে লাগবে:

  1. socket() — একটা socket বানাও
  2. bind() — "আমি port 8080-এর মালিক"
  3. listen() — "connection নিতে প্রস্তুত" (এটা listening socket)
  4. accept() — একেকটা আগত connection-এর জন্য নতুন একটা socket ফেরত দেয় — data আদান-প্রদান ওটাতেই

খেয়াল করো: listening socket আর connection socket আলাদা জিনিস। app.listen(8080) লেখার সময় Node ভিতরে ঠিক এই চারটা ধাপই চালায়।

  • Socket-কে file descriptor বানানোর সুবিধা কী?
  • Connection-এর চার-টুপল কী, আর এক port-এ বহু client কীভাবে?
  • Listening socket আর accepted socket-এর পার্থক্য?

Chapter 26 — TCP Connection-এর ভিতরে

Connection "establish" হওয়া মানে আসলে কী তৈরি হয় — এবং কোথায়।

Three-way handshake

Client                          Server
  │── SYN ──────────────────────→│   "connection চাই" (+ আমার শুরুর sequence number)
  │←───────────────── SYN-ACK ───│   "রাজি, এই নাও আমারটাও"
  │── ACK ──────────────────────→│   "পাকা কথা"
  │                              │
  │═══════ connection ready ═════│

তিন ধাপ কেন? কারণ দুই পক্ষকেই নিশ্চিত হতে হবে — "আমার পাঠানো ওর কাছে পৌঁছায়, ওর পাঠানো আমার কাছে পৌঁছায়", আর দুজনের সেই শুরুর sequence number বিনিময় হতে হবে (এই নাম্বার দিয়েই TCP পরে হিসাব রাখে কোন byte পৌঁছেছে, কোনটা হারিয়েছে)।

সবচেয়ে জরুরি উপলব্ধি: "connection" জিনিসটা তারে-তারে কোথাও নেই। এটা দুই পাশের kernel-এর memory-তে রাখা state মাত্র — sequence number, window size, timers। মাঝের network শুধু স্বাধীন packet চেনে। TCP হলো দুই kernel-এর সম্মিলিত অভিনয়ে তৈরি "reliable stream"-এর illusion।

Buffers: প্রতিটা socket-এর দুই গুদাম

প্রতিটা established connection-এর জন্য kernel দুটো buffer রাখে:

  • Send buffer: তোমার write() data আগে এখানে জমা হয় → kernel নিজের গতিতে packet বানিয়ে পাঠায়। Buffer ভরা থাকলে (receiver ধীর!) write block করে — এটাই backpressure-এর জন্মস্থান।
  • Receive buffer: Network থেকে আসা data এখানে জমে → তুমি read() করলে এখান থেকেই পাও। তুমি না পড়লে জমতে থাকে; ভরে গেলে TCP অপর পক্ষকে বলে দেয় "আস্তে!" (flow control)।

দেখেছ pattern-টা? আবার সেই গল্প — দুই ভিন্ন গতির জগতের (তোমার app আর network) মাঝে buffer।

Server-এর দুই queue

Server-এর listening socket-এর পিছনে kernel দুটো লাইন রাখে:

SYN এলো → [SYN queue]          — handshake চলছে, আধা-পাকা connection
handshake শেষ → [accept queue]  — পুরো ready, app-এর accept()-এর অপেক্ষায়
app accept() করলো → connection app-এর হাতে

এই ভাগাভাগির মানে গভীর: handshake পুরোটাই kernel সামলায় — তোমার Node process ঘুমিয়ে থাকলেও connection establish হয়ে accept queue-তে জমা হতে থাকে। আর app যদি accept করতে ধীর হয় (event loop আটকে আছে?), accept queue ভরে যায় — নতুন connection তখন refuse/drop হয়। listen()-এর backlog parameter এই queue-র সাইজই ঠিক করে। Production-এ "connection refused under load"-এর একটা classic কারণ এই queue overflow।

  • "Connection দুই kernel-এর memory-র state" — এর মানে কী?

  • SYN queue আর accept queue-র পার্থক্য, আর accept queue ভরলে কী হয়?

Chapter 27 — Data পাঠানো আর পাওয়া

write() থেকে তার/বাতাস পর্যন্ত — এবং উল্টো পথে।

Send path

Application — write(fd, "GET / ...", n)
   ↓ system call — data send buffer-এ copy, return!
TCP  — buffer-এর data segment-এ কাটে, seq number দেয়,
       retransmission timer বসায় (হারালে আবার পাঠাবে)
IP   — segment-কে packet-এ মোড়ে: source/dest IP, routing
Driver — packet-কে NIC-এর queue-তে দেয়
   ↓ DMA
NIC (network card) — bits হিসেবে তারে/বাতাসে

লক্ষ করো: write() return মানে data পৌঁছে গেছে না — মানে kernel-এর send buffer-এ ঢুকেছে (file write-এর গল্পটার যমজ ভাই, Chapter 21)। পৌঁছানো নিশ্চিত করা, হারালে আবার পাঠানো, order ঠিক রাখা — সব TCP-র চাকরি, background-এ।

Receive path — উল্টো ছবি

NIC — packet এলো → DMA-তে memory-তে → interrupt: "data এসেছে!"
IP  — packet খুলে দেখে: আমার জন্যই তো?
TCP — চার-টুপল দেখে কোন connection-এর, seq number মিলিয়ে
      সঠিক জায়গায় বসায়, ACK পাঠায়, receive buffer-এ রাখে
      → এই socket-এ অপেক্ষারত process থাকলে জাগাও!
Application — read() → buffer থেকে data → তোমার হাতে

সেই "জাগাও" শব্দটা মন দিয়ে দেখো — data আসা মানে waiting process-এর Ready হয়ে যাওয়া (Chapter 15-এর state machine)। তোমার server-এর প্রতিটা request-handling শুরু হয় আসলে একটা NIC interrupt থেকে।

আর buffering কেন অনিবার্য, এখন পুরো ছবিটা বলা যায়: network-এর data আসে যখন খুশি (packet-এ, এলোমেলো সময়ে), app পড়ে যখন সুবিধা। দুই অসমান ছন্দের মাঝে kernel-এর buffer-ই একমাত্র শান্তিচুক্তি।

EXPERIMENT (Linux)

ss -t চালাও (macOS: netstat -an | grep ESTABLISHED | head)। Recv-Q আর Send-Q column দুটো এই chapter-এর সেই দুই buffer-এর জমে থাকা data-র লাইভ পরিমাপ। Recv-Q বড় হয়ে থাকা মানে — app data পড়ছে না; Send-Q বড় মানে — অপর পাশ নিতে পারছে না।

  • Receive path-এ process কখন, কীভাবে জাগে?

Chapter 28 — Blocking vs Non-blocking I/O

C10K সমস্যার শিকড় — এবং event-driven জগতের জন্মকথা।

Blocking model আর তার দেয়াল

Default socket blocking: read() ডাকলে data না আসা পর্যন্ত thread ঘুমায়। সরল model-এ তাই দাঁড়ায়: এক connection = এক thread — যে-যার connection-এর read-এ ঝুলে থাকে।

১০০ connection-এ চলে। ১০,০০০-এ? ১০,০০০ thread: প্রত্যেকের stack-এ memory, scheduler-এর ঘাড়ে ১০,০০০ জনের হিসাব, অগুনতি context switch (Chapter 17, 19-এর সেই bill)। অথচ মজার ব্যাপার — এই thread-গুলোর ৯৯% কোনো কাজই করছে না, শুধু অপেক্ষা করছে। অপেক্ষার জন্য এত দামি জিনিস (thread) পোষা — এটাই মূল অপচয়। এই সমস্যার ঐতিহাসিক নাম "C10K problem"।

Non-blocking: অপেক্ষা করতে অস্বীকার

Socket-কে non-blocking mode-এ দিলে চুক্তি বদলে যায়: read()-এ data থাকলে দাও, না থাকলে ঘুমিয়ো না — সাথে সাথে বলো "এখন নেই" (EWOULDBLOCK)। Thread মুক্ত।

কিন্তু একা non-blocking যথেষ্ট না — data আছে কি না বারবার জিজ্ঞেস করতে থাকলে (busy polling) CPU পোড়ে অকারণে। দরকার একটা তৃতীয় জিনিস: kernel-কে বলা — "এই ১০,০০০ socket-এর যেকোনোটায় কিছু ঘটলে আমাকে ডেকো।" এক thread, ঘুমাবে একবারে, জাগবে ঠিক তখনই যখন সত্যি কাজ আছে। এই mechanism-টাই I/O multiplexing — পরের chapter পুরোটা এটা নিয়ে।

MENTAL MODEL

Blocking model: প্রতি কাস্টমারের জন্য একজন dedicated কর্মচারী, যে কাস্টমার মেনু দেখার পুরোটা সময় পাশে দাঁড়িয়ে থাকে। Event-driven model: একজনই কর্মচারী, কিন্তু কাউন্টারে বেল আছে — যার দরকার সে বাজায়। কর্মচারীর সময় যায় শুধু কাজে, অপেক্ষায় না। শর্ত একটাই: প্রতিটা কাজ ছোট হতে হবে — কেউ কাউন্টার ২০ মিনিট আটকে রাখলে (event loop block!) বাকি সবাই আটকে যায়।

  • Non-blocking mode-এ read()-এর আচরণ কী বদলায়?
  • Non-blocking একা কেন যথেষ্ট না?

Chapter 29 — I/O Multiplexing

"এই হাজারটা fd-র কোনোটায় কিছু ঘটলে ডেকো" — nginx, Node, Redis সবার হৃদপিণ্ড।

Evolution-টা বোঝাই আসল

  • select / poll (আদি যুগ): প্রতিবার call-এ পুরো fd list kernel-কে দাও → kernel সবগুলো scan করে বলে কারা ready। কাজ চলে, কিন্তু connection N হলে প্রতি call-এ O(N) কাজ + পুরো list আনা-নেওয়া। ১০,০০০ fd-তে প্রতিটা event-এর জন্য ১০,০০০-এর scan — বাড়ে না (doesn't scale)।
  • epoll (Linux-এর উত্তর): Approach উল্টে দাও — kernel-এর ভিতরেই একটা স্থায়ী interest list রাখো:
    1. epoll_create() — kernel-এ একটা "watch center" বানাও
    2. epoll_ctl(ADD, fd) — "এটার উপর নজর রেখো" (একবারই বলতে হয়)
    3. epoll_wait() — ঘুমাও; kernel জাগাবে শুধু ready fd-দের list হাতে দিয়ে
    Data আসামাত্র kernel নিজেই (receive path-এর সেই "জাগাও" মুহূর্তে!) ready list-এ fd টা টুকে রাখে। ফলে কাজের খরচ ready event-এর সংখ্যার সমানুপাতিক — মোট connection যত-ই হোক। ১০,০০০ ঘুমন্ত connection কার্যত free।
  • আত্মীয়স্বজন: kqueue (macOS/BSD-র epoll-সমতুল্য), IOCP (Windows-এর — দর্শন একটু আলাদা: "ready হলে বলো" না, "কাজ শেষ হলে বলো"), আর io_uring (Linux-এর নতুন প্রজন্ম — shared memory-র ring-এ request/completion বিনিময় করে system call-এর সংখ্যাই কমিয়ে দেয়; Chapter 32-এর পরে এর মর্ম আরও বুঝবে)।

একটা event-driven server-এর কঙ্কাল

loop {
    events = epoll_wait()             // ঘুমাও, ঘটনা এলে জাগো
    for (e of events) {
        if (e.fd == listening_fd)     // নতুন connection!
            accept() → non-blocking করে epoll-এ ADD
        else                          // পুরনো connection-এ data
            read() → request process → write(response)
    }
}

এটাই — literally এটাই — Node.js-এর event loop-এর, nginx-এর worker-এর, Redis-এর মূল কাঠামো। তোমার প্রতিটা app.get(...) handler ওই process জায়গাটায় বসে চলে। আর এখন এটাও পরিষ্কার কেন event loop-এ CPU-ভারী synchronous কাজ বিষ — loop-টা epoll_wait-এ ফিরতে না পারলে জমে থাকা কারো সেবাই হয় না।

COMMON MISCONCEPTION

"Node.js single-threaded, তাই এক core-এ এক সাথে একটাই কাজ — slow।" আসল ছবি: I/O-bound জগতে "কাজ"-এর সংজ্ঞাই হলো ছোট ছোট CPU-র ঝলক, মাঝে বিশাল অপেক্ষা। Event loop সেই অপেক্ষাগুলো epoll-এ জমা দিয়ে ঝলকগুলো পরপর চালায় — এক thread-েই হাজারো connection। Single thread দুর্বলতা না, এই model-এর design choice — দুর্বলতা শুধু CPU-bound কাজে (তখন worker/process — Chapter 19)।

  • epoll কোন কাজটা "একবার" করে ফেলে বারবার করা এড়ায়?
  • Event loop block করলে ঠিক কী ঘটে — kernel level-এ ভেবে বলো।

Chapter 30 — Socket Programming: হাতেকলমে

একটা ন্যূনতম TCP server, C-তে — প্রতিটা লাইন এতক্ষণের theory-র প্রমাণ।

// ন্যূনতম echo server — error handling ইচ্ছা করে বাদ
int server_fd = socket(AF_INET, SOCK_STREAM, 0);   // ১

struct sockaddr_in addr = {0};
addr.sin_family = AF_INET;
addr.sin_port   = htons(8080);
bind(server_fd, (struct sockaddr*)&addr, sizeof(addr)); // ২

listen(server_fd, 128);                            // ৩

while (1) {
    int client_fd = accept(server_fd, NULL, NULL); // ৪
    char buf[1024];
    int n = read(client_fd, buf, sizeof(buf));     // ৫
    write(client_fd, buf, n);                      // ৬
    close(client_fd);                              // ৭
}

লাইন ধরে ধরে — OS-এর চোখে কী ঘটলো:

  1. socket(): System call → kernel একটা socket object বানালো, fd দিলো। SOCK_STREAM মানে TCP।
  2. bind(): "Port 8080 আমার" — kernel-এর port table-এ দাবি নথিভুক্ত। অন্য কেউ আগেই নিলে এখানেই EADDRINUSE — তোমার চেনা সেই "port already in use"।
  3. listen(fd, 128): Socket টা listening mode-এ; 128 হলো accept queue-র backlog (Chapter 26!)। এই মুহূর্ত থেকে kernel নিজে নিজে handshake করে connection জমাতে থাকবে।
  4. accept(): Accept queue খালি থাকলে process এখানে block — Waiting state। Connection এলে জাগে, হাতে পায় নতুন fd।
  5. read(): Receive buffer-এ data না থাকলে block; থাকলে copy। (এই যে ৪ আর ৫-এ blocking — এটাই এই server-এর সীমা: এক সময়ে এক client। Chapter 28-29 এর সমাধান তো এখন জানোই।)
  6. write(): Send buffer-এ copy → kernel পাঠাবে।
  7. close(): fd ছাড়ো → kernel TCP-র বিদায়-নৃত্য (FIN/ACK) চালায়।
আসল শিক্ষা

মাত্র ৭টা system call-এ একটা network server — কারণ ভারী কাজের সবটাই kernel-এ: handshake, reliability, buffering, retransmission। Application-এর ভূমিকা আসলে orchestration — kernel-এর তৈরি জিনিসগুলো চাওয়া, আর bytes-এর অর্থ বোঝা (HTTP parse করা ইত্যাদি)। Express দিয়ে যে server লেখো, সেটা এই ৭ call-এর উপরে সাজানো অনেকগুলো সুবিধার স্তর মাত্র।

EXPERIMENT

কোনো C লাগবে না — দুই terminal-এ: nc -l 8080 (server) আর nc localhost 8080 (client), টাইপ করো — chat! তারপর তৃতীয় terminal-এ ss -t | grep 8080 (macOS: netstat -an | grep 8080) — নিজের বানানো connection-টার state দেখো। Linux-এ strace nc -l 8081 চালালে উপরের socket→bind→listen→accept ধারাটা লাইভ দেখবে।

Chapter 31 — User Mode vs Kernel Mode

এই বইয়ের নীল-আর-amber রেখাটা এবার পুরো আলোয়।

Privilege: hardware-এ খোদাই করা নিয়ম

এটা কোনো software convention না — CPU নিজে দুই (বা ততোধিক) privilege level-এ চলে। Kernel mode-এ সব instruction, সব memory, সব device বৈধ। User mode-এ dangerous instruction (device-এ কথা বলা, page table বদলানো, interrupt বন্ধ করা) দিলে CPU নিজেই আটকে দিয়ে kernel-কে ডেকে দেয়। মানে যত বড় bug-ই লেখো, তোমার process hardware-এর ক্ষতি করতে বা অন্যের memory পড়তে পারবেই না — দারোয়ান silicon-এ বসানো।

কেন এত কড়াকড়ি? কারণ machine-টা shared। শত process, ভিন্ন user, আধা-বিশ্বাসী code — এদের মাঝে বিশ্বাসের সীমানা টানতেই হয়। Protection ছাড়া এক process-এর ভুল মানে পুরো machine-এর মৃত্যু (পুরনো DOS-যুগের বাস্তবতা)।

Mode বদলের আরও দুই দরজা আছে, ফাউ হিসেবে জেনে রাখো: interrupt (hardware-এর ডাক — NIC-এর "data এসেছে", timer-এর tick) আর exception/fault (তোমার code-এর কাণ্ড — page fault, zero-division)। তিন দরজাই এক জায়গায় নামে: kernel-এর নিয়ন্ত্রিত entry point।

MENTAL MODEL

Kernel হলো ব্যাংকের vault-এর কর্মকর্তা। তুমি (user process) vault-এ ঢুকতে পারো না — কাউন্টারে (syscall interface) slip জমা দাও, কর্মকর্তা ভিতরে গিয়ে কাজ করে ফলাফল আনে। Slip-এ যা-ই লেখো, কর্মকর্তা যাচাই করেই কাজ করবে। ব্যবস্থাটা একটু আনুষ্ঠানিক, তাই একটু ধীর — কিন্তু এজন্যই ব্যাংক লুট হয় না।

Chapter 32 — System Call আর তার দাম

Boundary পার হওয়ার হিসাব-নিকাশ — এবং সেটা ঘিরে গড়ে ওঠা engineering।

দামটা আসে কোথা থেকে

একটা syscall মানে সাধারণ function call না — মানে: mode switch (CPU state বদল), kernel-এ ঢুকে register বাঁচানো, syscall dispatch, argument validation, কাজ, তারপর পুরোটা উল্টো করে ফেরা। তার উপর আছে পরোক্ষ খরচ — kernel-এর code/data cache-এ ঢোকায় তোমার code-এর cache-এর কিছুটা দখল হয়ে যায় (Chapter 17-এর সেই cache দূষণের ছোট ভাই)।

কিন্তু ভারসাম্যটাও বলি: একটা syscall-এর নিজস্ব overhead nanoseconds-এর জগতে — আর তার ভিতরের কাজটা (disk read!) হতে পারে milliseconds-এর জগতে। অর্থাৎ overhead টা matter করে তখনই, যখন syscall গুলো ছোট এবং অনেক।

COMMON MISCONCEPTION

"System calls are slow — যত পারো এড়াও।" ভুল frame। সঠিক frame: syscall-এর একটা fixed per-call overhead আছে। ১টা syscall-এ 4MB পড়া = overhead তুচ্ছ। ১০ লাখ syscall-এ ৪ byte করে পড়া = overhead-ই মূল খরচ। শত্রু syscall না — শত্রু ছোট কাজে ঘনঘন boundary পারাপার।

এই হিসাব থেকে জন্ম নেওয়া কৌশলগুলো

  • Batching/buffering: ছোট ছোট write জমিয়ে এক syscall-এ পাঠানো। তোমার console.log-এর পিছনে stdout buffering, HTTP client-এর request pipelining — সব এই এক idea।
  • বড় buffer-এ পড়া: 64KB চেয়ে এক read, 1KB-র ৬৪ read না।
  • epoll-ই একটা জবাব: হাজার fd-র খোঁজ এক epoll_wait-এ (Chapter 29)।
  • io_uring — চূড়ান্ত রূপ: App আর kernel-এর মাঝে shared memory-র দুই ring (submission + completion)। App ring-এ request লিখে রাখে, kernel পড়ে কাজ করে result ring-এ রাখে — অনেক operation, প্রায় শূন্য boundary-পারাপার। পুরো design-টাই "syscall overhead"-এর বিরুদ্ধে যুদ্ধ।
  • vDSO (মজার fact): কিছু নিরীহ syscall (যেমন সময় জানা — gettimeofday) এত ঘনঘন ডাকা হয় যে kernel সেগুলোর জবাব user space-এই map করে দেয় — boundary পারই হতে হয় না।
EXPERIMENT (Linux)

দুটো তুলনা করো:
strace -c dd if=/dev/zero of=/dev/null bs=1 count=100000 (১ byte করে!)
strace -c dd if=/dev/zero of=/dev/null bs=100000 count=1 (এক চালানে)
-c flag syscall-এর গণনা আর সময়ের summary দেখায় — একই কাজ, syscall সংখ্যায় লক্ষগুণ পার্থক্য, সময়েও চোখে পড়ার মতো। এটাই এই chapter-এর পুরো থিসিস এক পরীক্ষায়।

Chapter 34 — Executable Load হওয়া

ELF file থেকে Chapter 5-এর সেই memory layout — বৃত্তটা পূর্ণ হলো।

exec()-এর মুহূর্তে ধাপে ধাপে

  1. Kernel ELF header পড়ে — বৈধ executable তো?
  2. Process-এর virtual address space সাজায় — কিন্তু চালাকিটা দেখো: .text আর .data RAM-এ copy করে না — file-টাকে address space-এ mmap করে দেয় (Chapter 10-এর সেই কৌশল!)। মানে "load" আসলে lazy: যে page ছোঁয়া হবে, page fault-এ সেটাই disk থেকে আসবে। এজন্যই বিশাল executable-ও প্রায় সাথে সাথে start হয়।
  3. BSS-এর জন্য zero-filled জায়গা, stack-এর জন্য জায়গা তৈরি; stack-এর গোড়ায় বসিয়ে দেয় argv আর environment variables — তোমার process.argv-র জন্ম এখানে।
  4. Dynamically linked হলে আগে চালু হয় dynamic linker (ld.so) — সে দরকারি .so গুলো address space-এ map করে, ঠিকানার জোড়াতালি (relocation) সারে।
  5. Program counter → entry point। User mode-এ যাত্রা শুরু।

সুতোগুলো জোড়া লাগলো

Executable loading = virtual memory-র feature-দের একটা orchestra: mmap (file→memory), demand paging (lazy load), page fault (loading mechanism), shared pages (libc সবার সাথে ভাগ), copy-on-write (fork-এর পরে)। Part 3 না বুঝে এই chapter পড়লে এগুলো জাদু লাগতো; এখন এগুলো স্রেফ চেনা যন্ত্রের নতুন ব্যবহার।

Chapter 35 — Virtualization

এক hardware-এ একাধিক "computer" — cloud-এর ভিত্তিপ্রস্তর।

Idea: illusion-এর আরেক ধাপ উপরে

এই বইয়ে বারবার দেখেছি OS process-কে illusion দেয় — "CPU তোমার, memory তোমার।" Virtualization সেই একই খেলা এক level উপরে: একটা পুরো OS-কে illusion দেওয়া যে hardware-টা তার একার।

  • Virtual machine (VM): Software দিয়ে বানানো একটা "computer" — virtual CPU, virtual RAM, virtual disk, virtual NIC।
  • Guest OS: সেই নকল computer-এ install হওয়া পূর্ণাঙ্গ OS — নিজের kernel সহ, যে জানেও না সে নকলের উপর চলছে।
  • Hypervisor: যে software এই সার্কাস চালায় — আসল hardware-কে ভাগ করে VM-দের দেয়, guest-দের বিপজ্জনক কাজগুলো ধরে ধরে সামলায়। Host hardware-এ সরাসরি বসতে পারে (server/cloud-এর ধরন), বা host OS-এর উপরে (তোমার laptop-এর VirtualBox/UTM)। আধুনিক CPU-তে hardware virtualization support থাকায় guest-এর সাধারণ code প্রায় native গতিতে চলে।

Isolation-টা এখানে খুবই শক্ত — দুই VM-এর মাঝে আস্ত দুইটা kernel আর hypervisor-এর দেয়াল। এজন্যই cloud provider-রা অচেনা customer-দের এক machine-এ রাখতে VM-এই ভরসা করে। তুমি EC2/DigitalOcean-এ যে "server" ভাড়া নাও — সেটা প্রায় নিশ্চিতভাবেই একটা VM।

দামটাও পরিষ্কার: প্রতিটা VM-এ পুরো একটা OS — শত শত MB memory, নিজস্ব boot, নিজস্ব kernel-এর যাবতীয় খরচ। ১০টা ছোট service-এর জন্য ১০টা VM মানে ১০ কপি OS পোষা। এই অপচয়ের অস্বস্তি থেকেই পরের chapter-এর জন্ম।

PART 10 · VIRTUALIZATION AND CONTAINERS

Chapter 36 — Containers

Docker-এর ভিতরের সত্য: নতুন কোনো জাদু না — এই বইয়ের চেনা জিনিসের চতুর সাজানো।

মূল সত্যটা আগে

Container কোনো VM না। Container হলো সাধারণ process — শুধু kernel তাকে সীমিত আর বিভ্রান্ত করে রাখে। কোনো guest OS নেই, নকল hardware নেই, আলাদা kernel নেই — host-এর kernel-ই সবার। docker run node মানে host-এ একটা node process-ই চলছে; host থেকে ps দিলে দেখাও যায় তাকে।

তাহলে "আলাদা machine" feeling-টা আসে কোথা থেকে? Linux kernel-এর দুটো feature থেকে:

  • Namespaces — "কী দেখতে পাবে": Process-এর বিভিন্ন দৃষ্টিশক্তির আলাদা আলাদা নকল সংস্করণ। PID namespace — container নিজেকে PID 1 দেখে, বাইরের কাউকে দেখে না; mount namespace — নিজের আলাদা filesystem গাছ (image-এর সেই ubuntu/alpine ফাইলগুলো — ব্যস, ফাইলই, kernel না!); network namespace — নিজস্ব IP, নিজস্ব port জগৎ। চেনা লাগছে? Virtual memory যা address-এর জন্য, namespace তা-ই বাকি সবকিছুর জন্য — প্রত্যেকে ভাবে জগৎটা তার একার।
  • cgroups — "কতটুকু পাবে": Process-দলের resource-এর রেশন কার্ড — এই দলের memory সর্বোচ্চ 512MB, CPU-র 50%, এতটুকু disk I/O। Docker-এর --memory/--cpus flag মানে স্রেফ cgroup-এর ঘর পূরণ। রেশন পার হলে? Memory-র বেলায় দলের কেউ খুন হয় — সেই কুখ্যাত OOM kill, তোমার Kubernetes pod-এর "OOMKilled"-এর জন্মস্থান।

│Guest│ │Guest│                  │ ns+ │ │ ns+ │      namespace-এ মোড়া
│ OS  │ │ OS  │ ← ২টা kernel!    │cgrp │ │cgrp │

এখন trade-off-টা নিজেই বলে দিতে পারবে: container start হয় process start-এর গতিতে (কোনো OS boot নেই), memory খায় process-এর মতো — কিন্তু সবাই এক kernel share করে, তাই isolation VM-এর মতো শক্ত না (kernel-এর ছিদ্র মানে সবার ছিদ্র), আর Linux container-এর Linux kernel-ই লাগে — এজন্যই তোমার Mac-এ Docker Desktop গোপনে একটা Linux VM চালিয়ে তার ভিতরে container চালায়। দুই chapter মিলে গেল।

EXPERIMENT (Docker থাকলে)

PART 11 · PUTTING EVERYTHING TOGETHER

Chapter 37 — একটা Program চালালে কী কী ঘটে?

পুরো বইয়ের প্রথম মহাসংযোগ। Terminal-এ লিখলে ./app আর Enter চাপলে —

  1. Shell পড়লো তোমার লাইন — সে নিজেও এক সাধারণ process, stdin-এ read() করে বসে ছিল (Waiting-এ)। তোমার Enter-এ keyboard-এর interrupt → kernel → shell জাগলো। [Ch 15, 31]
  2. Executable খোঁজা — PATH-এর directory-গুলোতে; প্রতিটা খোঁজ মানে filesystem-এ path resolution। [Ch 22]
  3. fork() — shell নিজের copy বানালো; copy-on-write-এ প্রায় বিনা খরচে। [Ch 15, 9]
  4. exec() — child-এর ভিতরে নতুন program: ELF header পড়া, নতুন virtual address space, code/data mmap (কিন্তু lazy!), stack-এ argv, dynamic linker-এর library জোড়া, PC → entry point। [Ch 34, 33, 5]
  5. প্রথম instruction-এই page fault! — code-এর page টা তো এখনো disk-এ। Kernel: filesystem → block layer → driver → device → DMA → page cache → page table update → আবার চালাও। প্রথম কিছু মুহূর্ত এভাবে fault-এ fault-এ program-টা "টুকরো টুকরো জন্মায়"। [Ch 9, 21, 11]
  6. এবার আসল দৌড় — fetch-decode-execute-এর কোটি কোটি চক্কর; কখনো cache hit-এর সুখ, কখনো miss-এর RAM-যাত্রা, TLB-র নীরব অনুবাদ প্রতি access-এ। [Ch 12, 13, 9]
  7. Program কিছু চাইলো — file পড়া? read() syscall → kernel → (ভাগ্য ভালো হলে page cache hit) → data। Network? socket path। প্রতিটা চাওয়ায় নীল-থেকে-amber-থেকে-নীল সেই যাত্রা। [Ch 21, 25-27, 31-32]
  8. মাঝে মাঝে সে-ও থামলো — I/O-র wait-এ Blocked, বা timer interrupt-এ scheduler-এর preemption; তার context save, অন্য কারো restore — machine-জুড়ে চলা হাজারো process-এর নাচের এক পা মাত্র সে। [Ch 15, 17]
  9. Output — তোমার terminal-এ লেখাও আসলে write() — terminal-ও এক file descriptor! [Ch 21, 25]
  10. exit() — শেষ syscall। Kernel memory ফেরত নিলো, fd গুলো বন্ধ করলো, exit code রেখে দিলো — shell (parent) wait() করে সেটা তুললো, prompt ফিরিয়ে দিলো। [Ch 15]
এখন পরীক্ষা করো নিজেকে

উপরের দশটা ধাপ বই বন্ধ করে, নিজের ভাষায়, কাউকে (বা রাবার হাঁসকে) বলে যাও — কোথায় আটকাও দেখো। যেখানে আটকাবে, সংশ্লিষ্ট chapter-টাই তোমার revision list। এই এক গল্প ঝরঝরে বলতে পারা মানে বইয়ের ৮০% হজম।

Chapter 38 — একটা Web Server-এ Request এলে কী ঘটে?

দ্বিতীয় মহাসংযোগ — এবং তোমার প্রতিদিনের কাজের সবচেয়ে কাছের গল্পটা। ধরি: Node/Express API, Postgres, এক user browser-এ চাপ দিলো।

  1. Browser-এর দিক: DNS, তারপর TCP handshake — SYN উড়ে এলো তোমার server-এ। তোমার Node process টেরও পেলো না — kernel একাই SYN queue → handshake → accept queue সামলালো। [Ch 26]
  2. Event loop-এর ঘুম ভাঙলো: Node epoll_wait-এ ঘুমিয়ে ছিল; listening fd ready → জাগলো → accept() → নতুন connection fd, non-blocking করে epoll-এ ADD। [Ch 29, 25]
  3. Request এলো: NIC → DMA → interrupt → kernel TCP: চার-টুপল মিলিয়ে সঠিক socket-এর receive buffer-এ HTTP bytes → epoll-এ সেই fd ready। Node read() করলো, HTTP parse হলো, তোমার route handler ডাক পেলো — এতক্ষণে, প্রথমবারের মতো, তোমার লেখা code মঞ্চে। [Ch 27, 29]
  4. Handler-এ await db.query(...): Postgres-এর দিকের socket-এ query write() (send buffer-এ জমা) — আর ব্যস, অপেক্ষা নয়: callback নথিভুক্ত করে event loop পরের event ধরলো। ওই এক thread এই ফাঁকে অন্য দশটা request-এর টুকরো এগোলো — এটাই সেই waiter-এর জাদু। [Ch 28-29, 19]
  5. ওদিকে Postgres (আলাদা process!): নিজের socket-এ query পেলো, plan করলো, data চাইলো — তার নিজের page cache-জগৎ, ভাগ্য খারাপে disk: block layer → driver → DMA। ফলাফল socket-এ ফেরত write()। [Ch 21, 23, 20]
  6. ফলাফল ফিরলো: আবার NIC → interrupt → TCP → Node-এর সেই fd ready → event loop জাগলো → তোমার await-এর পরের লাইন চললো। Response JSON বানানো — এটুকু খাঁটি CPU কাজ: V8-এর machine code, cache hit/miss, heap-এ object জন্ম (পরে GC-র খোরাক)। [Ch 12-13, 6]
  7. Response রওনা: res.json() → শেষমেশ socket-এ write() → send buffer → TCP segment → IP → NIC → ইন্টারনেটের ওপারে browser-এর kernel → তার receive buffer → browser-এর epoll-জাতীয় জিনিস → পর্দায় pixel। [Ch 27]

পুরো যাত্রায় হয়তো তোমার handler-এর CPU-সময় মিলিসেকেন্ডেরও ভগ্নাংশ — বাকিটা kernel-এর কারিগরি আর অপেক্ষার শিল্প। এবার production-এর চেনা রোগগুলোও নতুন চোখে দেখো: latency spike? — DB-র disk নাকি event loop কেউ আটকে রেখেছে নাকি accept queue উপচে পড়ছে? Memory বাড়ছে? — heap leak নাকি কেউ receive buffer পড়ছে না? প্রতিটা প্রশ্ন এখন এই map-এর কোনো না কোনো জায়গায় pin করা যায়।

প্রথম-স্তরের intuition: data যত নিচের স্তরে, ছোঁয়া তত দামি — design এমন করো যেন গরম data উপরের স্তরে থাকে। এটুকুই অনেক দূর নিয়ে যায়। কিন্তু "closer = always faster" বলে থেমে গেলে এই ফাঁদগুলোয় পড়বে:

  • Latency ≠ throughput: Network-এর latency জঘন্য হতে পারে, কিন্তু throughput disk-কে হারাতে পারে। "কোনটা দরকার" আগে ঠিক করো — একটা payment confirm (latency-র খেলা) আর একটা backup (throughput-এর খেলা) সম্পূর্ণ আলাদা design চায়।
  • Contention সব হিসাব উল্টে দেয়: কাগজে-কলমে দ্রুত জিনিসও লাইনে দাঁড়ালে ধীর। এক মিউটেক্সে দশ থ্রেড, এক DB row-এ শত transaction, এক NVMe-তে হাজার random write — resource-এর গতি না, queue-র দৈর্ঘ্য তখন তোমার latency। Load বাড়লে response time ধীরে না, hockey-stick-এ বাড়ে — queuing-এর স্বভাবই এই।
  • Cache মানেই দুই জগৎ: প্রতিটা স্তরে hit আর miss-এর পার্থক্য এত বড় যে "গড় সময়" প্রায়ই মিথ্যা বলে। Benchmark-এ warm/cold আলাদা মাপো; production-এ P99 দেখো, গড় না।
  • Parallelism মাত্রা বদলায়, জাত না: দশগুণ core দশগুণ throughput দিতে পারে — যদি কাজ ভাগ হয় আর shared state না আটকায়। Serial অংশটুকুই শেষমেশ সিলিং।
  • Bandwidth-ও ফুরায়: RAM-এরও bandwidth সীমা আছে — সব core মিলে বিশাল data চিবাতে গেলে দ্রুততম CPU-ও ভাতঘুমে যায়।
শেষ কথা — চারটা প্রশ্নের অভ্যাস

যেকোনো system/feature/bug-এর সামনে দাঁড়িয়ে জিজ্ঞেস করো: (১) Data কোন স্তরে বসে আছে, আর প্রতি request-এ কোন স্তর পর্যন্ত নামতে হচ্ছে? (২) কোথায় boundary পার হচ্ছি (syscall, network, process) — আর কতবার? (৩) কোথায় queue জমছে — কে কার জন্য অপেক্ষায়? (৪) কী shared — আর সেটাই কি লাইনের কারণ? এই চার প্রশ্ন সঙ্গে থাকলে এই বইয়ের প্রতিটা chapter তোমার হাতিয়ার।

The Operating Systems Mental Model

পুরো বই, এক ছবিতে — তারপর সুতোগুলোর জোড়া।

        Application (তোমার code)
        Runtime / Libraries (V8, libc, JVM)
┌─────────────  USER SPACE  ─────────────┐
│  process memory: code · data · heap · stack  │
└──────────────────┬─────────────────────┘
          system calls (একমাত্র দরজা)
┌────────────────  KERNEL  ──────────────┐
│ Process Mgmt   — scheduler, fork, states │
│ Memory Mgmt    — page tables, page cache │
│ File System    — VFS, ext4, inodes       │
│ Network Stack  — sockets, TCP/IP, queues │
│ Device Drivers — disk, NIC (DMA, IRQ)    │
└──────────────────┬─────────────────────┘
                   ↓
        Hardware:  CPU (+cache) · RAM · Storage · Network

সুতোগুলো

  • সব রাস্তার এক প্যাটার্ন: চাওয়া (নীল) → syscall → kernel-এর স্তর → hardware → ফেরা। File, network, memory — গল্প একটাই, চরিত্র আলাদা।
  • Illusion স্তরে স্তরে: Virtual memory প্রতিটা process-কে "memory তোমার একার" বলে; scheduler বলে "CPU তোমার একার"; TCP বলে "নির্ভরযোগ্য stream আছে"; namespace বলে "machine-টা তোমার একার"; hypervisor বলে "hardware তোমার একার"। OS মানে সুশৃঙ্খল মিথ্যার স্থাপত্য — যে মিথ্যাগুলো আমাদের সরল code লিখতে দেয়।
  • যেখানেই speed-ফারাক, সেখানেই cache/buffer: CPU cache, TLB, page cache, socket buffers, তোমার Redis — এক pattern-এর পাঁচ তলা।
  • সবকিছুর দাম আছে: syscall-এর boundary cost, context switch-এর cache-দূষণ, page fault-এর disk-যাত্রা, lock-এর লাইন। Engineering মানে এই দামগুলো জেনে খরচ করা।

আর সেই final goal-টা মিলিয়ে দেখো: এখন একটা running application-এর দিকে তাকালে তোমার চোখে ভাসা উচিত — process আর তার address space, stack-এ ওঠানামা করা frames, heap-এ জন্মানো objects, cache-এ hit-miss-এর জুয়া, boundary পেরোনো syscalls, kernel-এর queue আর buffer, disk আর NIC-এর DMA, আর scheduler-এর অদৃশ্য কাঁচি। যদি ভাসে — বইটা কাজ করেছে।
