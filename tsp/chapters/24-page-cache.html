Page cache — লেখা কোথায় যায়

Chapter 23 এ দেখেছি একটা খালি file বানাতে ~১০টা I/O লাগে। তবু আপনার program এ write() ফেরে microsecond এ। মাঝখানে যে layer টা আছে সেটাই page cache — আর "free memory কম" বা "RSS বাড়ছে" এর বেশিরভাগ রহস্য এখানেই।

Chapter 23 এর হিসাবটা মনে করুন: একটা file create এ ~১০টা disk I/O, একটা ৪KB লেখায় আরও ৫টা। Disk এ প্রতিটা I/O ~২০µs (NVMe) থেকে ~১০ms (HDD)। তাহলে একটা সাধারণ write() কেন ~১µs এ ফেরে?

কারণ সেটা disk এ যায়ই না। যায় page cache এ — RAM এ।

Crux

Disk RAM এর চেয়ে হাজার গুণ ধীর, কিন্তু একই data বারবার লাগে। OS কীভাবে RAM কে disk এর cache হিসেবে ব্যবহার করবে — আর কতটা RAM এতে দেবে?

Page cache কী

  ┌──────────────────────────────────────────────┐
  │  application:  read(fd, buf, 4096)           │
  └────────────────────┬─────────────────────────┘
                       │
  ┌────────────────────▼─────────────────────────┐
  │  PAGE CACHE  (RAM এ, page-আকারের খণ্ডে)      │
  │                                              │
  │  ┌────────┬────────┬────────┬────────┐       │
  │  │ file A │ file A │ file B │ file C │       │
  │  │ page 0 │ page 1 │ page 7 │ page 0 │  ...  │
  │  └────────┴────────┴────────┴────────┘       │
  │                                              │
  │  cache এ আছে?  ──▶ হ্যাঁ: সাথে সাথে ফেরত     │
  │                    (~১ µs, কোনো disk I/O নেই) │
  └────────────────────┬─────────────────────────┘
                       │ না: minor→major fault (ch 9)
  ┌────────────────────▼─────────────────────────┐
  │  file system → block layer → device          │
  └──────────────────────────────────────────────┘

  একক: একটা PAGE (৪KB) — chapter 9 এর সেই page।
  এই কারণেই file system এর block size ও ৪KB।

গুরুত্বপূর্ণ কথা: Linux এ page cache এর আকার স্থির নয়। সে যত RAM খালি আছে তার প্রায় সবটাই নিয়ে নেয়, আর দরকার হলে ছেড়ে দেয় (chapter 11 এর reclaim)। এটাই সবচেয়ে বড় বিভ্রান্তির উৎস।

ভুল ধারণা — সম্ভবত সবচেয়ে প্রচলিত

"free -h বলছে মাত্র ২০০MB free — আমার server এর RAM শেষ হয়ে যাচ্ছে!" 

$ free -h
              total   used   free   shared  buff/cache  available
Mem:           31Gi   8.2Gi  210Mi   1.1Gi      23Gi       22Gi
                             ↑ ভয় পাওয়ার মতো    ↑ এটাই আসল উত্তর
                                        ↑ এটা page cache

ওই ২৩GB buff/cache হলো page cache — আর সেটা reclaimable। কোনো process memory চাইলে kernel সাথে সাথে ওখান থেকে ছেড়ে দেবে (clean page ফেলে দিতে কোনো খরচ নেই, disk এ copy আছেই)।

দেখার সংখ্যাটা free নয়, available — ২২GB। Kernel নিজেই হিসাব করে বলে দেয় কতটা সত্যিই পাওয়া যাবে।

আসলে কম free থাকা ভালো লক্ষণ — মানে আপনার RAM কাজে লাগছে। খালি RAM অপচয়। "unused memory is wasted memory" — Linux এর নকশার একটা মৌলিক নীতি।

পড়ার পথ — আর readahead

  read(fd, buf, 4096)

  ১. offset থেকে page index হিসাব করো
  ২. page cache এ খোঁজো (একটা radix tree / xarray তে)
       │
       ├── পাওয়া গেল  → buf এ copy করো, ফেরত  (~১ µs)
       │                 ↑ এটাই "minor" পথ
       │
       └── নেই → disk থেকে আনতে হবে
             │
             ├── একটা page চাও, কিন্তu kernel বেশি আনে!
             │   ← READAHEAD
             ▼
           block layer → device → page cache এ বসাও
           তারপর copy করে ফেরত  (~২০ µs – ১০ ms)

Readahead টা গুরুত্বপূর্ণ: kernel যদি দেখে আপনি ক্রমিকভাবে পড়ছেন, সে আপনার চাওয়ার আগেই পরের page গুলো এনে রাখে। এই কারণেই sequential read এ প্রথম read ধীর আর বাকিগুলো দ্রুত। 

# readahead এর আকার (KB তে)
$ cat /sys/block/nvme0n1/queue/read_ahead_kb
128

# কোনো file এর কতটা এখন cache এ আছে
$ vmtouch -v /var/lib/postgresql/data/base/16384/1259
[OOo                    ] 12/1024   1%
#  ↑ প্রতিটা অক্ষর একটা page গুচ্ছ; O = cached

# নিজের application এ readahead নিয়ন্ত্রণ
$ # posix_fadvise() দিয়ে hint দেওয়া যায় — নিচে দেখুন
c 
/* Telling the kernel what you are about to do.
   These are hints, not commands — but they work well. */
#include <fcntl.h>

/* "I will read this whole file sequentially" → aggressive readahead */
posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);

/* "I will jump around" → disable readahead, stop wasting I/O */
posix_fadvise(fd, 0, 0, POSIX_FADV_RANDOM);

/* "I am done with this range" → drop it from the cache,
   so it does not evict data someone else needs.
   This is what a backup or a log-shipper should do. */
posix_fadvise(fd, offset, len, POSIX_FADV_DONTNEED);

/* "I will need this soon" → start reading now, in the background */
posix_fadvise(fd, offset, len, POSIX_FADV_WILLNEED);

ওই DONTNEED টা বিশেষভাবে কাজের, আর একটা বাস্তব সমস্যা সারায়: একটা nightly backup পুরো database পড়ে, আর তাতে page cache ভরে যায় backup এর data দিয়ে — যেটা আর কখনো লাগবে না। ফলে আপনার আসল hot data cache থেকে বেরিয়ে যায়, আর সকালে সব query ধীর। এটাই cache pollution, আর DONTNEED এর উত্তর।

লেখার পথ — writeback

এখন সবচেয়ে গুরুত্বপূর্ণ অংশ, আর যেটা chapter 25 এর ভিত্তি। 

  write(fd, buf, 4096)

  ১. page cache এ page টা খোঁজো (বা বানাও)
  ২. buf থেকে ওই page এ copy করো
  ৩. page টাকে DIRTY চিহ্নিত করো
  ৪. ফেরত যাও  ←── এখানেই write() শেষ!  (~১ µs)

     ┌───────────────────────────────────────┐
     │  ⚠  data এখন শুধু RAM এ আছে।          │
     │     power গেলে হারিয়ে যাবে।           │
     └───────────────────────────────────────┘

  পরে, স্বাধীনভাবে:

  ৫. kswapd বা একটা writeback thread (flusher)
     dirty page গুলো disk এ লেখে
  ৬. page টা CLEAN হয়ে যায়

  কখন ধাপ ৫ হয়? তিনটে কারণে:
    • সময় পার হয়েছে   (dirty_expire_centisecs, default ৩০s)
    • dirty অনুপাত বেশি (dirty_ratio, dirty_background_ratio)
    • কেউ জোর করেছে     (fsync, sync, umount)

এই বিলম্বটা ইচ্ছাকৃত, আর তিনটে সুবিধা দেয়:

  • Batching — অনেক ছোট লেখা একসাথে বড় করে পাঠানো। Chapter 21 এর write amplification এর জন্য এটা সরাসরি লাভ।
  • Write coalescing — একই page বারবার লিখলে disk এ একবারই যায়। একটা counter যদি সেকেন্ডে ১০০০ বার বদলায়, disk এ যায় ৩০ সেকেন্ডে একবার।
  • বাতিল হওয়া লেখা — একটা temp file লিখে মুছে ফেললে disk এ কিছুই যেতে পারে না। 
# এই মুহূর্তে কত dirty data RAM এ ঝুলে আছে
$ grep -E 'Dirty|Writeback' /proc/meminfo
Dirty:            524288 kB     ← ৫১২ MB এখনো disk এ যায়নি!
Writeback:          8192 kB     ← এই মুহূর্তে লেখা হচ্ছে

# writeback এর নিয়ন্ত্রণ
$ sysctl vm.dirty_background_ratio   # ১০% — flusher শুরু হয়
$ sysctl vm.dirty_ratio              # ২০% — লেখক নিজেই আটকে যায়!
$ sysctl vm.dirty_expire_centisecs   # ৩০০০ = ৩০ সেকেন্ড

# byte-ভিত্তিক বিকল্প (বড় RAM এ ratio বিপজ্জনক)
$ sysctl vm.dirty_background_bytes vm.dirty_bytes
ভুল ধারণা

dirty_ratio শুধু একটা tuning knob — বাড়িয়ে দিলে লেখা দ্রুত হবে।"

dirty_ratio ছাড়ালে যা হয় তা tuning নয়, একটা cliff: লেখক process নিজেই writeback করতে বাধ্য হয় (throttled write)। আপনার write() যেটা ~১µs ছিল, হঠাৎ কয়েকশো millisecond নেয়।

আর ৩২GB RAM এ dirty_ratio=20 মানে ৬.৪GB dirty data জমতে পারে। সেটা যখন একসাথে disk এ যাবে, আপনার latency তে একটা বিশাল কাঁটা পড়বে — আর সেই সময়ে অন্য সব I/O ও আটকে থাকবে।

এই কারণেই বড় RAM এর মেশিনে *_bytes variant ব্যবহার করা ভালো (যেমন dirty_background_bytes = 256MB) — একটা স্থির, পূর্বানুমেয় সীমা, RAM এর আকারের সাথে বাড়ে না।

mmap — cache টা সরাসরি দেখা

read() করলে page cache থেকে আপনার buffer এ একটা copy হয়। mmap() সেই copy টা বাদ দেয় — cache এর page গুলোই সরাসরি আপনার address space এ map করে দেয়। 

  read():
    disk → page cache → আপনার buffer     (দুটো copy)
                        ↑ এই copy টা বাদ দেওয়া যায়

  mmap():
    disk → page cache ←─ আপনার pointer সরাসরি এখানে
                         (কোনো copy নেই)

  ┌─────────────────────────────────────────┐
  │  process এর address space               │
  │  ┌───────────────────────────────┐      │
  │  │ mmap করা অঞ্চল                 │      │
  │  │  page table entry ────────────┼──┐   │
  │  └───────────────────────────────┘  │   │
  └─────────────────────────────────────┼───┘
                                        │
  page cache ┌────────┐ ◀───────────────┘
             │ file   │  একই physical page!
             │ page 7 │  একাধিক process ভাগ করতে পারে
             └────────┘
c 
/* mmap: the file becomes an array */
int fd = open("data.bin", O_RDWR);
struct stat st; fstat(fd, &st);

char *p = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE,
               MAP_SHARED, fd, 0);

p[1000] = 'X';          /* a write() with no syscall at all */

/* Force it to disk — the mmap equivalent of fsync */
msync(p, st.st_size, MS_SYNC);
munmap(p, st.st_size);

mmap copy বাদ দেয়, তাই এটা সবসময় দ্রুত।"

Copy বাঁচে, কিন্তু নতুন খরচ আসে:

  • প্রতিটা নতুন page ছোঁয়ায় একটা page fault (~১µs) — একটা বড় sequential scan এ হাজারো fault, যেটা একটা বড় read() এর চেয়ে বেশি খরচি।
  • munmap এ TLB shootdown (chapter 10) — বহু-core মেশিনে IPI ঝড়।
  • Error গুলো signal হয়ে আসে। Disk এ I/O error হলে আপনি SIGBUS পাবেন, errno নয়। একটা signal handler থেকে সুন্দরভাবে পুনরুদ্ধার করা কঠিন — এই কারণেই Postgres ইচ্ছাকৃতভাবে data file এ mmap ব্যবহার করে না, বরং নিজের shared_buffers রাখে।

আর SQLite এর mmap_size default ০ — একই কারণে। যারা ব্যবহার করে (LMDB, LevelDB এর কিছু অংশ) তারা সচেতনভাবে random-access pattern এর জন্য বেছে নেয়।

O_DIRECT — cache পাশ কাটানো

কখনো আপনি page cache চান না। একটা database এর নিজের buffer pool আছে, তাই OS এর cache টা double caching — একই data দুবার RAM এ।

c 
/* O_DIRECT — bypass the page cache entirely.
   The kernel DMAs straight into your buffer (chapter 20). */
int fd = open("data.db", O_RDWR | O_DIRECT);

/* Strict alignment requirements — this is the hard part:
   buffer address, offset, AND length must all be aligned
   to the logical block size (usually 512 or 4096). */
void *buf;
posix_memalign(&buf, 4096, 4096);      /* not malloc()! */
pread(fd, buf, 4096, 0);                /* offset and len aligned too */
কে ব্যবহার করেকেন
Postgres না (WAL এ কিছু ক্ষেত্রে) — page cache এর উপর নির্ভর করে, তাই shared_buffers RAM এর ২৫% রাখার পরামর্শ
MySQL/InnoDB হ্যাঁ (O_DIRECT default) — নিজের buffer pool RAM এর ~৭০%
Oracle, SQL Server হ্যাঁ — সম্পূর্ণ নিজের cache ব্যবস্থাপনা
Kafka না — ইচ্ছাকৃতভাবে page cache এর উপর নির্ভর করে, আর sendfile() দিয়ে zero-copy পাঠায়

Postgres আর MySQL এর এই বিপরীত পছন্দটা শিক্ষামূলক: একই সমস্যা, দুটো বৈধ উত্তর। Postgres বলে "kernel cache ভালো জানে, আমি ছোট buffer রাখি"; MySQL বলে "আমি আমার access pattern ভালো জানি, আমাকে নিয়ন্ত্রণ দাও"। তাই দুটোর memory tuning এর উপদেশ সম্পূর্ণ আলাদা — আর একটার নিয়ম অন্যটায় লাগালে RAM নষ্ট হয়।

আপনার কাজের সাথে যোগ

Container এ page cache একটা বিশেষ ফাঁদ তৈরি করে, আর chapter 11 এর সাথে এটা সরাসরি জোড়া: 

# cgroup এর memory.max এ page cache ও গোনা হয়!
$ cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file) '
anon 524288000       ← আপনার heap
file 402653184       ← page cache — এটাও limit এর ভিতরে

# তাই একটা service যা প্রচুর file পড়ে, তার page cache
# limit ভরিয়ে ফেলতে পারে। সৌভাগ্যক্রমে এটা reclaimable,
# তাই kernel আগে এটাই বের করে — কিন্তু তখন আপনার
# read গুলো আবার disk এ যাবে → হঠাৎ ধীর।

এই কারণেই একটা container এ memory.max শুধু heap এর হিসাবে দিলে performance অপ্রত্যাশিতভাবে খারাপ হয় — heap fit করে, কিন্তু cache এর জন্য জায়গা থাকে না, তাই প্রতিটা read disk এ যায়।

Kafka এর নকশাটা এই chapter এর সেরা উদাহরণ: সে ইচ্ছাকৃতভাবে নিজের cache রাখে না, page cache এর উপর নির্ভর করে, আর consumer কে data পাঠায় sendfile() দিয়ে — page cache থেকে সরাসরি socket এ, userspace ছোঁয়াই না। Producer এর লেখা তখনো cache এ গরম, তাই consumer প্রায়ই disk ছোঁয়াই না। এই কারণেই Kafka এত দ্রুত, আর এই কারণেই Kafka broker এ প্রচুর RAM (কিন্তু বড় JVM heap নয়) সুপারিশ করা হয়।

দেখার যন্ত্রপাতি

# cache hit/miss — bcc/eBPF দিয়ে
$ sudo cachestat 1
    HITS   MISSES  DIRTIES  HITRATIO   BUFFERS_MB  CACHED_MB
   14832      120      450    99.20%           82       4821

# কোন file cache এর কত জায়গা নিচ্ছে
$ sudo pcstat /var/lib/postgresql/data/base/*/[0-9]*
$ vmtouch -v /path/to/file

# একটা file cache এ গরম করে রাখা (test এর জন্য)
$ vmtouch -t /path/to/file
# বা cache পরিষ্কার করে benchmark করা:
$ sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
# ⚠ শুধু benchmark এ — production এ কখনো নয়

# writeback এখন কী করছে
$ cat /proc/meminfo | grep -E 'Dirty|Writeback'
$ sudo iotop -o                 # কে সত্যিই disk I/O করছে
ভুল ধারণা

"drop_caches দিয়ে memory মুক্ত করলে server দ্রুত হবে।"

উল্টোটা। Page cache ফেলে দিলে পরের প্রতিটা read disk এ যাবে — আপনি ইচ্ছে করে সব cache miss বানালেন। Server তাৎক্ষণিকভাবে ধীর হবে, তারপর ধীরে ধীরে cache আবার গরম হবে।

এর একমাত্র বৈধ ব্যবহার হলো benchmark — যখন আপনি cold-cache performance মাপতে চান। Production এ এটা চালানো একটা self-inflicted outage।

আর যা এখনো সমাধান হয়নি

এই chapter এ একটা জিনিস ইচ্ছাকৃতভাবে ঝুলিয়ে রেখেছি: write() ফেরার পরেও data শুধু RAM এ, আর power গেলে হারিয়ে যায়।

Chapter 1 এ এই ভুল ধারণাটা প্রথম flag করেছিলাম, আর বলেছিলাম "chapter 25 এর বিষয়"। এখন আমরা সেখানে পৌঁছেছি — পরের chapter সম্পূর্ণভাবে এই প্রশ্নের: কীভাবে নিশ্চিত হবেন যে data সত্যিই টিকে থাকবে? আর কেন সেই প্রশ্নের উত্তর fsync() ডাকার চেয়ে অনেক বেশি সূক্ষ্ম।

প্রশ্ন

  1. free -h এ free মাত্র ২০০MB কিন্তু available ২২GB। এই দুটো সংখ্যার পার্থক্যটা কী মাপে, আর কেন কম free থাকা ভালো লক্ষণ? Chapter 11 এর reclaim এর সাথে সম্পর্কটা বলুন।
  2. একটা nightly backup পুরো database পড়ে, আর সকালে সব query ধীর হয়ে যায়। কী ঘটেছে, আর posix_fadvise এর কোন flag দিয়ে backup script টা সংশোধন করবেন?
  3. ৩২GB RAM এ dirty_ratio=20। একটা bulk import ১০GB লিখছে। ঠিক কোন মুহূর্তে আপনার write() এর latency লাফিয়ে বাড়বে, আর কেন? dirty_background_bytes ব্যবহার করলে আচরণটা কীভাবে বদলাবে?
  4. Postgres mmap এড়ায় কিন্তু page cache ব্যবহার করে; MySQL O_DIRECT ব্যবহার করে আর নিজের buffer pool রাখে। দুটোই বৈধ — প্রতিটার পিছনের যুক্তি বলুন, আর বলুন কেন একটার memory tuning নিয়ম অন্যটায় প্রয়োগ করলে RAM নষ্ট হয়।
  5. mmap এ I/O error SIGBUS হিসেবে আসে, errno নয়। কেন এটা একটা database এর জন্য অগ্রহণযোগ্য? Chapter 10 এর TLB shootdown mmap এর আরেকটা কোন খরচ যোগ করে?
  6. একটা container এ memory.max = 1Gi, heap ৭০০MB। Service টা প্রচুর file পড়ে। Performance কেন অপ্রত্যাশিতভাবে খারাপ হবে, যদিও কোনো OOM kill হচ্ছে না? সমাধান কী — আর Kafka এর নকশা এই সমস্যাটা কীভাবে ব্যবহার করে নিজের সুবিধায়?
