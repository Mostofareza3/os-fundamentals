Memory model — volatile synchronization নয়

Chapter 1 এ OSTEP এর volatile int counter হুবহু রেখেছিলাম আর বলেছিলাম পরে সংশোধন করব। এটাই সেই chapter। আর সংশোধনটা "একটু ভুল" নয় — ওই code টা undefined behavior, আর সেটার অর্থ আপনার ধারণার চেয়ে গুরুতর।

Chapter 13 এ hardware এর দিকটা দেখলাম: coherence পাওয়া যায়, consistency চাইতে হয়। এখন প্রশ্ন — programming language এর স্তরে এর অর্থ কী? আমি C তে লিখি, hardware fence নিয়ে ভাবতে চাই না। কে আমাকে কী গ্যারান্টি দিচ্ছে?

Crux

একটা ভাষা যদি একাধিক architecture এ compile হয়, যার প্রত্যেকের আলাদা memory model, তাহলে programmer কীসের ভিত্তিতে যুক্তি করবে? ভাষাটাকেই একটা model দিতে হবে।

প্রথমে volatile — এটা কী আর কী নয়

volatile এর একটা আসল, সংকীর্ণ অর্থ আছে: compiler কে বলা যে এই variable এর access optimize করে সরিয়ে দিও না। প্রতিবার সত্যিই memory থেকে পড়ো, প্রতিবার সত্যিই লেখো।

এটা কেন দরকার হয়, সেটা একটা উদাহরণে পরিষ্কার:

c 
/* Without volatile, the compiler may hoist the read out of the
   loop — it sees nothing in the loop that changes `ready`,
   so it reads once and loops forever on a stale value. */

int ready = 0;              /* set by a signal handler, say */

void wait_for_it(void) {
    while (ready == 0)
        ;                   /* compiler: "ready never changes here" */
    /* may compile to:  if (ready == 0) for(;;);   ← infinite loop */
}

volatile এই নির্দিষ্ট optimization টা আটকায়। এর বৈধ ব্যবহার আছে:

  • Memory-mapped I/O — একটা hardware register পড়া, যার মান device বদলায় (chapter 20 এ দেখব)।
  • Signal handler এর সাথে যোগাযোগ — আর সেখানেও সঠিক type হলো volatile sig_atomic_t।
  • setjmp/longjmp এর সাথে ব্যবহৃত local variable।

এখন volatile যা করে না — আর এই তালিকাটাই গুরুত্বপূর্ণ: 

  volatile করে না:

  ✗ operation কে atomic করে না
      counter++ এখনো তিনটে ধাপ: load, add, store
      volatile শুধু নিশ্চিত করে তিনটে ধাপই সত্যিই ঘটবে

  ✗ CPU এর reordering আটকায় না
      hardware কোনো fence পায় না — chapter 13 এর
      store buffer আর পুনর্বিন্যাস অপরিবর্তিত

  ✗ অন্য core এ কখন দৃশ্যমান হবে তার কোনো নিশ্চয়তা দেয় না
      coherence শেষ পর্যন্ত পৌঁছে দেবে, কিন্তু কখন — অজানা

  ✗ data race কে বৈধ করে না
      C11 এর ভাষায় volatile object এ একসাথে লেখা
      এখনো একটা data race
ভুল ধারণা — এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ সংশোধন

"volatile দিলে shared variable thread-safe হয়ে যায়।"

Chapter 1 এ OSTEP এর code টা হুবহু রেখেছিলাম: 

volatile int counter = 0;
/* ... */
counter++;          /* দুটো thread থেকে */

এই code টা ভুল উত্তর দেয় — সেটা chapter 1 এ দেখেছি। কিন্তু আসল কথাটা আরও গুরুতর: C11/C++11 এর ভাষায় এটা data race, অর্থাৎ undefined behavior।

"ভুল উত্তর" আর "undefined behavior" এর পার্থক্যটা বিশাল। ভুল উত্তর মানে একটা অপ্রত্যাশিত সংখ্যা। UB মানে standard আপনার program এর কোনো আচরণের দায় নেয় না — compiler ধরে নিতে পারে যে UB কখনো ঘটে না, আর সেই অনুমানের ভিত্তিতে আপনার code এর অন্য অংশ মুছে ফেলতে পারে। Loop উড়ে যেতে পারে, condition check সরে যেতে পারে।

তাই volatile দিয়ে race "কম" করা যায় না। সঠিক হাতিয়ার atomic: 

/* WRONG */
volatile int counter = 0;
counter++;

/* RIGHT — C11 */
#include <stdatomic.h>
atomic_int counter = 0;
atomic_fetch_add(&counter, 1);
/* বা শুধু: counter++;  — atomic_int এ operator overload হয় */

নামের বিভ্রান্তি — Java আর C# এর volatile

এখানে একটা আসল বিভ্রান্তির উৎস আছে, আর polyglot developer রা নিয়মিত এতে পড়েন:

ভাষাvolatile এর অর্থSynchronization দেয়?
C / C++ শুধু compiler optimization আটকায় না
Java (5+) সত্যিকারের memory barrier — release/acquire semantics হ্যাঁ
C# Barrier দেয়, কিন্তু Java এর চেয়ে দুর্বল আংশিক

অর্থাৎ Java এ volatile boolean flag সঠিক একটা synchronization pattern, আর C তে একই লেখা ভাঙা code। একই শব্দ, সম্পূর্ণ আলাদা চুক্তি।

Java এ ও একটা সীমা আছে: volatile visibility দেয়, কিন্তু atomicity দেয় না। তাই Java তেও volatile int i; i++; ভাঙা — ওখানে AtomicInteger লাগে।

Data race এর সঠিক সংজ্ঞা

পরিভাষাটা ঠিক করা দরকার, কারণ "race condition" আর "data race" এক জিনিস নয়: 

  DATA RACE (ভাষার প্রযুক্তিগত সংজ্ঞা):

    দুটো thread একই non-atomic memory location ছোঁয়,
    অন্তত একটা লেখা,
    আর তাদের মধ্যে কোনো synchronization নেই
    → undefined behavior

  RACE CONDITION (যুক্তিগত সমস্যা):

    program এর ফল ঘটনাক্রমের উপর নির্ভর করে
    → হয়তো UB নয়, কিন্তু তবু bug

  পার্থক্য: সব data race একটা bug।
            কিন্তু একটা race condition atomic দিয়েও থাকতে পারে!

শেষ লাইনটা গুরুত্বপূর্ণ, আর এটা একটা সাধারণ ভুলের উৎস:

c 
/* No data race — every access is atomic.
   Still a race condition — the logic is broken. */
atomic_int balance = 100;

void withdraw(int amount) {
    if (atomic_load(&balance) >= amount) {     /* (1) check  */
        /* ← অন্য thread এখানে ঢুকে পড়তে পারে */
        atomic_fetch_sub(&balance, amount);    /* (2) modify */
    }
}

/* দুটো thread একসাথে withdraw(100) ডাকলে:
   দুজনেই (1) এ 100 দেখল, দুজনেই পাস করল,
   দুজনেই 100 কমাল → balance = -100
   কোনো data race নেই, তবু হিসাব ভুল। */

এটাকে check-then-act সমস্যা বলে। Atomic primitive প্রতিটা একক operation কে রক্ষা করে, কিন্তু একাধিক operation এর সমষ্টি কে নয়। সমাধান হয় একটা lock (chapter 15), নয় একটা atomic compare-and-swap loop:

c 
/* CAS loop — read, compute, swap only if nothing changed */
void withdraw_safe(int amount) {
    int cur = atomic_load(&balance);
    do {
        if (cur < amount) return;          /* not enough */
        /* Try to install cur-amount, but only if balance is still cur.
           If someone else changed it, CAS writes the new value into
           `cur` and we retry. */
    } while (!atomic_compare_exchange_weak(&balance, &cur, cur - amount));
}

CAS (Compare-And-Swap — একটা atomic operation যা শুধু তখনই লেখে যখন বর্তমান মান প্রত্যাশিত মানের সমান) হলো প্রায় সব lock-free algorithm এর ভিত্তি। Chapter 16 এ এর উপর ফিরব।

Happens-before — যুক্তির ভিত্তি

আধুনিক memory model গুলো একটা সম্পর্ক দিয়ে সব কিছু ব্যাখ্যা করে: happens-before। 

  A happens-before B  মানে:
    A এর সব প্রভাব B এর কাছে দৃশ্যমান

  এই সম্পর্ক তৈরি হয়:

  ১. একই thread এ program order
       a = 1;  b = 2;   → প্রথমটা দ্বিতীয়টার আগে

  ২. release/acquire জোড়া (chapter 13)
       T1: ...লেখা...; atomic_store(flag, 1, release)
       T2: atomic_load(flag, acquire) == 1; ...পড়া...
       → T1 এর লেখা T2 এর পড়ার আগে

  ৩. lock unlock → পরের lock
       T1: unlock(m)
       T2: lock(m)
       → T1 এর critical section T2 এর আগে

  ৪. thread create আর join
       pthread_create এর আগের সব কাজ নতুn thread দেখে
       pthread_join এর পরে thread এর সব কাজ দৃশ্যমান

  যদি দুটো access এর মধ্যে happens-before সম্পর্ক না থাকে,
  আর অন্তত একটা লেখা হয় → DATA RACE

এই কাঠামোটা কাজের কারণ: আপনাকে fence বা cache নিয়ে ভাবতে হয় না। শুধু জিজ্ঞেস করুন — "এই দুটো access এর মধ্যে কোনো happens-before আছে কি?" না থাকলে race।

ব্যবহারিক pattern

১. Counter

c 
/* Only the total matters, not the order → relaxed is enough */
atomic_long requests = 0;

void on_request(void) {
    atomic_fetch_add_explicit(&requests, 1, memory_order_relaxed);
}

/* Reading it for a metrics endpoint */
long snapshot(void) {
    return atomic_load_explicit(&requests, memory_order_relaxed);
}

২. একবার-সেট-করা flag (shutdown signal)

c 
atomic_bool shutting_down = false;

/* signal handler বা admin thread */
void request_shutdown(void) {
    atomic_store_explicit(&shutting_down, true, memory_order_release);
}

/* worker loop */
void worker(void) {
    while (!atomic_load_explicit(&shutting_down, memory_order_acquire)) {
        do_work();
    }
    cleanup();
}

৩. Publication — একবার তৈরি, অনেকে পড়ে

c 
/* Build a config, then publish the pointer.
   Readers who see the pointer see a fully-built object. */
typedef struct { int timeout; char *host; } config_t;

_Atomic(config_t *) current_config = NULL;

void publish(void) {
    config_t *c = malloc(sizeof(*c));
    c->timeout = 30;                  /* these writes must be visible */
    c->host = "api.example.com";       /* before the pointer is */

    /* release: everything above is visible to anyone who
       acquires this pointer and sees the new value */
    atomic_store_explicit(&current_config, c, memory_order_release);
}

void use(void) {
    config_t *c = atomic_load_explicit(&current_config,
                                       memory_order_acquire);
    if (c) printf("%s %d\n", c->host, c->timeout);   /* safe */
}

এই তৃতীয় pattern টা লক্ষ করুন: config_t এর field গুলো সাধারণ, atomic নয়। তবু নিরাপদ, কারণ release/acquire জোড়াটা সব আগের লেখা বাহিত করে — chapter 13 এর সেই "একটা জোড়া, সব data" ধর্ম।

তবে একটা ফাঁক আছে: পুরনো config টা কখন free() করবেন? কেউ হয়তো এখনো পড়ছে। এই সমস্যার নাম safe memory reclamation, আর এটাই lock-free programming এর সবচেয়ে কঠিন অংশ — chapter 16 এ RCU দিয়ে এর উত্তর দেখব।

ভুল ধারণা

"Atomic মানে lock-free, আর lock-free মানে দ্রুত। তাই lock এর বদলে atomic ব্যবহার করলেই performance ভালো।"

তিনটে আলাদা ভুল এখানে:

  • সব atomic lock-free নয়। বড় type এ (যেমন _Atomic একটা ১৬-byte struct) compiler ভিতরে একটা lock ব্যবহার করতে পারে। atomic_is_lock_free() দিয়ে যাচাই করা যায়।
  • Contended atomic lock এর চেয়ে ধীর হতে পারে। একটা contended fetch_add প্রতিবার cache line এর exclusive ownership চায় — chapter 13 এর ping-pong। N thread মানে O(N) coherence traffic। একটা futex-ভিত্তিক mutex ঘুমিয়ে পড়ে, তাই bus এ চাপ দেয় না।
  • Lock-free মানে অপেক্ষা-মুক্ত নয়। একটা CAS loop অনির্দিষ্টকাল retry করতে পারে যদি contention বেশি হয়।

ব্যবহারিক নিয়ম: uncontended fast path এ একটা mutex ~১৫–২৫ns (chapter 15 এ দেখব, futex fast path কোনো syscall করে না)। সেটা প্রায় একটা atomic operation এর সমান। তাই আগে mutex দিয়ে সঠিক code লিখুন, তারপর মেপে দেখুন সত্যিই সেটা bottleneck কি না।

অন্য ভাষায় একই ধারণা

go 
// Go — sync/atomic, and the typed wrappers (1.19+)
var counter atomic.Int64
counter.Add(1)
n := counter.Load()

// Go's memory model: a channel send happens-before the
// corresponding receive completes. So this is safe:
ch := make(chan *Config, 1)
go func() {
    c := buildConfig()      // all writes here...
    ch <- c                 // ...are visible to the receiver
}()
cfg := <-ch                 // acquire
rust 
// Rust — the type system enforces it at compile time.
use std::sync::atomic::{AtomicUsize, Ordering};

static COUNTER: AtomicUsize = AtomicUsize::new(0);
COUNTER.fetch_add(1, Ordering::Relaxed);

// Sharing a non-Sync value across threads simply does not compile.
// This is the one language where data races are a compile error,
// not a runtime surprise.
javascript 
// Node worker_threads — yes, JS has a memory model too
const sab = new SharedArrayBuffer(8);
const view = new Int32Array(sab);

// WRONG — a data race, just like in C
view[0]++;

// RIGHT
Atomics.add(view, 0, 1);
const n = Atomics.load(view, 0);
আপনার কাজের সাথে যোগ

এই chapter এর ব্যবহারিক সারমর্ম আপনার ভাষা অনুযায়ী:

  • Node (single-threaded) — আপনি এই সমস্যা পান না, যতক্ষণ worker_threads + SharedArrayBuffer ব্যবহার না করছেন।
  • Go — channel ব্যবহার করুন; সেটা memory model দ্বারা নিশ্চিত। Shared memory লাগলে sync/atomic, আর CI তে go test -race বাধ্যতামূলক করুন।
  • Java — volatile visibility এর জন্য কাজ করে (C এর মতো নয়), কিন্তু increment এ AtomicInteger লাগবে।
  • Rust — compiler আপনাকে আটকাবে। এটাই এই সমস্যার একমাত্র পূর্ণ সমাধান যা production ভাষায় আছে।
  • C/C++ — volatile কখনো synchronization এর জন্য নয়। <stdatomic.h> বা std::atomic, আর TSan চালান।

যাচাই তালিকা

  একটা shared variable দেখে নিজেকে জিজ্ঞেস করুন:

  ১. এটা একাধিক thread ছোঁয়?
       না  → কিছু করার নেই
  ২. অন্তত একজন লেখে?
       না  → read-only, নিরাপদ (কিন্তু নিশ্চিত হোন
              কেউ পরে লিখবে না — ch 12 এর config reload)
  ৩. access গুলোর মধ্যে happens-before আছে?
       হ্যাঁ → ঠিক আছে (lock, channel, join, release/acquire)
       না   → DATA RACE, ঠিক করতে হবে

  ঠিক করার পথ, পছন্দের ক্রমে:
    ক. ভাগ করাই বন্ধ করুন (message passing, thread-local)
    খ. একটা mutex দিন (সরল, সাধারণত যথেষ্ট দ্রুত)
    গ. atomic ব্যবহার করুন (একক operation হলে)
    ঘ. lock-free algorithm লিখুন (শেষ উপায়, বিশেষজ্ঞের কাজ)

ক্রমটা ইচ্ছাকৃত। সবচেয়ে ভালো সমাধান হলো সমস্যাটাই না থাকা — data ভাগ না করা। Go এর "share memory by communicating" পরামর্শ, বা Node এর single-threaded model, বা Rust এর ownership — তিনটেই একই অন্তর্দৃষ্টির ভিন্ন রূপ।

প্রশ্ন

  1. C তে volatile synchronization দেয় না, Java তে দেয়। একজন developer Java থেকে C তে এসে volatile bool done লিখল একটা shutdown flag এর জন্য। x86 এ এটা সম্ভবত কাজ করবে। কেন এটা তবু ভুল, আর কোন পরিস্থিতিতে ভাঙবে?
  2. "ভুল উত্তর" আর "undefined behavior" এর পার্থক্যটা ব্যাখ্যা করুন। একটা data race থাকা program এ compiler কী করার অনুমতি পায় যা আপনি প্রত্যাশা করবেন না?
  3. নিচের code এ কোনো data race নেই (সব access atomic), তবু এটা ভুল। সমস্যাটা কী, আর দুটো আলাদা উপায়ে সারান: 
    if (atomic_load(&count) > 0)
    atomic_fetch_sub(&count, 1);
  4. Publication pattern এ config_t এর field গুলো non-atomic, তবু নিরাপদ। কোন ধর্মটা এটা সম্ভব করে? এখন বলুন পুরনো config টা free() করার সমস্যাটা কী, আর কেন এটা সহজ নয়।
  5. Contended atomic_fetch_add একটা mutex এর চেয়ে ধীর হতে পারে। Chapter 13 এর coherence protocol দিয়ে ব্যাখ্যা করুন কেন, আর কেন একটা ঘুমিয়ে-পড়া mutex এখানে সুবিধা পায়।
  6. "সবচেয়ে ভালো সমাধান হলো ভাগ করাই বন্ধ করা।" Go এর channel, Node এর single thread, আর Rust এর ownership — তিনটেই এই নীতির প্রয়োগ। প্রতিটার কী দাম আছে, আর কোন পরিস্থিতিতে আপনাকে তবু shared mutable state এ ফিরতে হবে?
