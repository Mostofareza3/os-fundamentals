Data integrity — RAID থেকে erasure coding

Disk শুধু মরে না — সে নীরবে মিথ্যা বলে। একটা byte পচে যায়, একটা লেখা হারিয়ে যায়, আর কেউ জানতেই পারে না। Part 4 শুরু হচ্ছে এই প্রশ্নে: আপনি কীভাবে জানবেন যে আপনার data এখনো আপনার data?

এখন পর্যন্ত ধরে নিয়েছি device হয় কাজ করে, নয় মরে যায় — একটা fail-stop model। বাস্তবতা আরও খারাপ: device আংশিকভাবে, নীরবে ব্যর্থ হয়।

Crux

একটা device যদি ভুল data ফেরত দেয় কিন্তু কোনো error রিপোর্ট না করে, তাহলে storage system কীভাবে সেটা ধরবে আর সারাবে?

দুটো ব্যর্থতার ধরন

ধরনকী হয়ধরা পড়ে?
LSE
(Latent Sector Error)		 একটা sector পড়া যায় না; drive নিজেই error ফেরত দেয় হ্যাঁ — drive বলে দেয়
Silent corruption Drive ভুল data ফেরত দেয়, কিন্তু "সফল" বলে না — কেউ জানে না

প্রথমটা সহজ: drive যখন বলে "পড়তে পারছি না", তখন redundancy থেকে উদ্ধার করা যায়। দ্বিতীয়টাই ভয়ংকর, আর তার তিনটে উৎস: 

  ১. Bit rot
     NAND cell এর charge ধীরে ধীরে leak করে,
     বা platter এর magnetic domain দুর্বল হয়।
     ECC একটা সীমা পর্যন্ত সারায়, তারপর ব্যর্থ —
     কিন্তু কখনো ভুলভাবে "সফল" ও হতে পারে।

  ২. Misdirected write
     Firmware bug: data সঠিকভাবে লেখা হলো,
     কিন্তু ভুল জায়গায়। এখন দুটো জায়গা ভুল —
     যেখানে লেখা হলো, আর যেখানে হওয়া উচিত ছিল।

  ৩. Lost write
     Drive বলল "লিখেছি", কিন্তু লেখেইনি।
     পুরনো data রয়ে গেল, আর সেটা পড়লে
     কোনো checksum ব্যর্থ হবে না — কারণ পুরনো
     data নিজে বৈধ!  ← সবচেয়ে কঠিন ক্ষেত্র

তৃতীয়টা লক্ষ করুন: একটা সাধারণ checksum এটা ধরতে পারে না, কারণ পুরনো block আর তার checksum দুটোই পরস্পরসঙ্গত। ধরতে হলে প্রত্যাশিত version জানতে হবে — আর সেটাই ZFS এর merkle tree করে।

Checksum — কোথায় রাখলে কী ধরা পড়ে

Checksum এর অবস্থান ঠিক করে দেয় সে কী ধরতে পারবে। এটাই এই chapter এর মূল অন্তর্দৃষ্টি: 

  ১. Drive এর ভিতরে (প্রতিটা drive এ আছে)
     [data | ECC]  ← একই sector এ

     ধরে:    media error, bit rot
     ধরে না: misdirected write (ভুল জায়গায় লেখা
             data + তার সঠিক ECC = "বৈধ")
             lost write
             transport error (cable, PCIe)

  ২. Block এর সাথে, file system এ (ext4 metadata)
     [data][checksum]

     ধরে:    উপরের সব + transport error
     ধরে না: misdirected write (checksum ও সরে গেছে)
             lost write

  ৩. আলাদা জায়গায়, parent এ (ZFS, btrfs)
     inode/parent block এ child এর checksum

     ধরে:    misdirected write ✓ (parent বলছে
             এই block এর checksum X হওয়া উচিত)
     ধরে না: lost write (পুরনো data + পুরনো checksum)

  ৪. Merkle tree — প্রতিটা স্তর নিচের checksum ধরে,
     root পর্যন্ত (ZFS)

     ধরে:    সব — lost write ও, কারণ root
             পর্যন্ত শৃঙ্খলটা মিলবে না ✓

  পাঠ: "আমার checksum আছে" যথেষ্ট তথ্য নয়।
       প্রশ্ন হলো — কোথায়?
ভুল ধারণা

"আমার drive এ ECC আছে আর RAID এ parity আছে, তাই corruption end-to-end সামলানো।"

দুটো আলাদা ফাঁক থাকে:

  • ECC শুধু media রক্ষা করে। Data যখন PCIe bus, cable, HBA, RAM দিয়ে যায়, ECC ওখানে নেই। একটা ত্রুটিপূর্ণ cable বা non-ECC RAM নীরবে bit উল্টে দিতে পারে, আর drive সেই ভুল data নিখুঁতভাবে সংরক্ষণ করবে — তার নিজের ECC সহ।
  • RAID parity corruption ধরে না। Parity একটা ব্যর্থ drive থেকে উদ্ধার করতে পারে। কিন্তু দুটো drive যদি আলাদা data দেয়, RAID জানে না কোনটা সঠিক। এই সমস্যার নাম RAID write hole, আর এটাই ZFS তৈরির মূল প্রেরণা।

এই কারণেই ext4/XFS শুধু metadata checksum করে — আপনার file এর বিষয়বস্তু নয়। btrfs আর ZFS data ও করে, আর তাই তারা corruption ধরতে পারে। 

# ext4 এ metadata checksum আছে কি
$ sudo dumpe2fs -h /dev/nvme0n1p2 2>/dev/null | grep -i 'features'
# metadata_csum থাকলে metadata সুরক্ষিত — data নয়

# ZFS/btrfs এ corruption এর হিসাব
$ zpool status -v tank        # CKSUM কলাম
$ sudo btrfs device stats /mnt/data | grep corrupt

Scrubbing — সমস্যা খুঁজে বের করা

Checksum তখনই কাজে লাগে যখন আপনি data পড়েন। কিন্তু একটা archive যদি তিন বছর কেউ না পড়ে? ততদিনে হয়তো দুটো copy ই পচে গেছে।

সমাধান: নিয়মিত সবকিছু পড়ে যাচাই করো। এর নাম scrubbing, আর OSTEP নিজেই উল্লেখ করে যে বেশিরভাগ LSE এভাবেই ধরা পড়ে। 

# ZFS — সাপ্তাহিক বা মাসিক scrub
$ sudo zpool scrub tank
$ zpool status tank
  scan: scrub repaired 8K in 02:14:31 with 0 errors
                       ↑ নীরবে সারিয়ে দিয়েছে

# btrfs
$ sudo btrfs scrub start /mnt/data
$ sudo btrfs scrub status /mnt/data

# Linux MD RAID — check বা repair
$ echo check | sudo tee /sys/block/md0/md/sync_action
$ cat /sys/block/md0/md/mismatch_cnt     # শূন্য না হলে সমস্যা

# NVMe এর নিজের হিসাব
$ sudo nvme smart-log /dev/nvme0 | grep -E 'media_errors|num_err'

Scrub এর একটা খরচ আছে — সে পুরো array পড়ে, তাই bandwidth আর (SSD তে) read disturb যোগ করে। তাই সাধারণত কম-ব্যস্ত সময়ে চালানো হয়, আর একটা rate limit দেওয়া হয়।

RAID — সংক্ষেপে, আর কেন RAID-5 আর নিরাপদ নয়

Levelকীভাবেসহ্য করেখরচ
RAID-0 Striping — কোনো redundancy নেই কিছুই না ০%
RAID-1 Mirroring — প্রতিটা block দুবার ১টা drive ৫০%
RAID-5 একটা parity, ছড়ানো ১টা drive ১/N
RAID-6 দুটো parity ২টা drive ২/N

Parity এর গণিতটা সরল — XOR: 

  P = D0 ⊕ D1 ⊕ D2 ⊕ D3

  D2 হারালে:  D2 = P ⊕ D0 ⊕ D1 ⊕ D3
  (XOR এর নিজেরই বিপরীত হওয়ার ধর্ম)

  কিন্তু একটা ছোট লেখার খরচ বেশি —
  small-write problem:

  D1 এর একটা block বদলাতে:
    ১. পুরনো D1 পড়ো
    ২. পুরনো P পড়ো
    ৩. নতুন P = পুরনো P ⊕ পুরনো D1 ⊕ নতুন D1
    ৪. নতুন D1 লেখো
    ৫. নতুন P লেখো
       → ২টা read + ২টা write, একটা যুক্তিগত লেখার জন্য

  Chapter 21 এর ভাষায়: RAID-5 এ write amplification
  ৪×, আর সেটা FTL এর WAF এর সাথে গুণ হয়।
যেখানে source টা পুরনো — RAID-5 এর মৃত্যু

OSTEP RAID-5 কে একটা যুক্তিসঙ্গত পছন্দ হিসেবে উপস্থাপন করে। বড় drive এ এটা এক দশকের বেশি সময় ধরে অনিরাপদ বলে বিবেচিত।

কারণটা একটা হিসাব: 

একটা drive মরল → rebuild শুরু

Rebuild এ বাকি সব drive পুরোটা পড়তে হয়।
১৬ TB drive, ৮টা drive এর array:
  পড়তে হবে ~১১২ TB
  ~১৫০ MB/s এ → ~৯ দিন (হ্যাঁ, দিন)

ওই ৯ দিন আপনার কোনো redundancy নেই।
আর ঠিক তখনই সব drive সবচেয়ে বেশি চাপে —
যখন দ্বিতীয় ব্যর্থতার সম্ভাবনা সর্বোচ্চ।

আর UBER (Uncorrectable Bit Error Rate) ~10^-15 হলে
১১২ TB পড়ার সময় অন্তত একটা unrecoverable
read error পাওয়ার সম্ভাবনা উল্লেখযোগ্য —
তাতেই rebuild ব্যর্থ।

তাই আজকের সুপারিশ: RAID-6 সর্বনিম্ন (দুটো parity), বা আরও ভালো — erasure coding। RAID-4 তো সম্পূর্ণ অপ্রচলিত (একটা নিবেদিত parity disk = একটা bottleneck), তাই আমরা সেটা বাদ দিয়েছি।

Erasure coding — যা cloud ব্যবহার করে

RAID এর সাধারণীকৃত রূপ: k টা data খণ্ড থেকে m টা parity খণ্ড বানাও, আর যেকোনো k টা খণ্ড থেকে পুরোটা পুনর্গঠন করো। 

  Reed-Solomon (k=6, m=3) — একটা সাধারণ পছন্দ

  একটা object ৬ টুকরো + ৩ parity = ৯ খণ্ড
  ৯টা আলাদা জায়গায় (rack, host, AZ) রাখা

  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │d1│d2│d3│d4│d5│d6│p1│p2│p3│
  └──┴──┴──┴──┴──┴──┴──┴──┴──┘

  যেকোনো ৩টা হারালেও পুরোটা ফেরত পাওয়া যায়।

  Storage overhead: ৯/৬ = ১.৫×
  তুলনায় ৩ copy replication: ৩×
  আর সহনশীলতা প্রায় একই!

  ⚠ দাম: পুনর্গঠনে k টা খণ্ড পড়তে হয় (network এ),
        আর গণিতটা CPU খায়। তাই cold storage এ
        আদর্শ, hot path এ নয়।

ভুল ধারণা

"S3 এর ১১ nines durability মানে আমার data হারানো কার্যত অসম্ভব — তাই backup লাগবে না।"

১১ nines শুধু device ব্যর্থতার বিরুদ্ধে। যা এই সংখ্যার আওতায় নেই:

  • আপনার নিজের ভুল — একটা ভুল aws s3 rm --recursive। S3 বিশ্বস্তভাবে আপনার মুছে ফেলার নির্দেশ পালন করবে, ১১ nines নির্ভরযোগ্যতায়।
  • Application bug — ভুল data লেখা হলে সেটাও নিখুঁতভাবে সংরক্ষিত হবে।
  • Ransomware / compromised credential
  • Account সমস্যা — বিল না দেওয়া, বা policy ভুল।

তাই durability আর backup দুটো আলাদা জিনিস: durability device হারানো থেকে বাঁচায়, backup ভুল থেকে বাঁচায়। এই কারণেই versioning, object lock, আর আলাদা account এ cross-region replication — তিনটেই দরকার।

End-to-end নীতি

সবচেয়ে গুরুত্বপূর্ণ নীতিটা শেষে: checksum টা যেখানে data তৈরি হয় সেখানে বানাও, আর যেখানে ব্যবহৃত হয় সেখানে যাচাই করো। মাঝের কোনো স্তরের উপর ভরসা নয়। 

  ┌─────────────────────────────────────────────────┐
  │  application: checksum বানাও ─────────┐         │
  ├────────────────────────────────────────┼────────┤
  │  library / driver                      │        │
  ├────────────────────────────────────────┼────────┤
  │  file system                           │        │
  ├────────────────────────────────────────┼────────┤
  │  block layer / RAID                    │        │
  ├────────────────────────────────────────┼────────┤
  │  device (নিজের ECC আছে)                │        │
  ├────────────────────────────────────────┼────────┤
  │  ... ফেরার পথে ...                     │        │
  ├────────────────────────────────────────┼────────┤
  │  application: যাচাই করো ◀──────────────┘         │
  └─────────────────────────────────────────────────┘

  প্রতিটা স্তরের নিজের checksum থাকতে পারে, কিন্তু
  স্তরের সীমানায় data হাত বদলায় — আর সেখানেই
  RAM, bus, বা software bug ঢুকতে পারে।

  একমাত্র নির্ভরযোগ্য গ্যারান্টি হলো end-to-end।

এই কারণেই আধুনিক system গুলো content-addressed:

Systemকী করে
Git প্রতিটা object এর নামই তার SHA-1/SHA-256 hash। git fsck পুরো graph যাচাই করে। Corruption কার্যত অসম্ভব অলক্ষিত থাকা।
Docker / OCI Layer গুলো digest দিয়ে চিহ্নিত (sha256:...) — pull এর সময় যাচাই হয়।
S3 Content-MD5 বা x-amz-checksum-* header — upload এ যাচাই করা যায়।
ZFS Merkle tree — root থেকে block পর্যন্ত পুরো শৃঙ্খল।
ভুল ধারণা

"Checksum মানে checksum — CRC32 দিয়ে content identify আর dedup করা যায়।"

দুটো সম্পূর্ণ আলাদা কাজ, আর দুটোর জন্য আলাদা যন্ত্র:

  • Error detection — CRC32, xxHash, Fletcher। দ্রুত, আর দুর্ঘটনাজনিত পরিবর্তন ধরার জন্য যথেষ্ট। CRC32 এর মাত্র ৩২ bit, তাই ~৪ বিলিয়নে একটা collision — random error এর জন্য ঠিক আছে।
  • Content identity / dedup — SHA-256, BLAKE3। এখানে ইচ্ছাকৃত collision ঠেকাতে হবে। CRC32 দিয়ে dedup করলে একজন আক্রমণকারী সহজেই দুটো ভিন্ন file একই checksum এ বানিয়ে আপনার data প্রতিস্থাপন করতে পারে।

Git এর SHA-1 থেকে SHA-256 এ সরার কারণ ঠিক এটাই — SHA-1 এ ব্যবহারিক collision আক্রমণ (SHAttered, ২০১৭) প্রমাণিত হওয়ার পর।

আপনার কাজের সাথে যোগ

ব্যবহারিক তালিকা:

  • Backup যাচাই করুন — একটা restore-না-করা backup একটা অনুমান, backup নয়। নিয়মিত restore drill চালান।
  • Scrub সূচি রাখুন — ZFS/btrfs এ মাসিক, আর mismatch_cnt monitor করুন।
  • ECC RAM — একটা checksumming file system non-ECC RAM এ চললে corruption RAM থেকেই আসতে পারে, আর তখন checksum টাও ভুল data এর উপর হিসাব হবে।
  • Application স্তরে checksum — গুরুত্বপূর্ণ data হলে নিজের digest রাখুন আর পড়ার সময় যাচাই করুন। এটাই end-to-end নীতি।
  • Silent corruption monitor করুন — zpool status এর CKSUM, btrfs এর device stats, আর nvme smart-log এর media_errors।

প্রশ্ন

  1. Lost write একটা সাধারণ checksum দিয়ে ধরা যায় না। কেন? আর ZFS এর merkle tree ঠিক কোন তথ্যটা যোগ করে যা এটা ধরা সম্ভব করে?
  2. Checksum এর অবস্থান ঠিক করে সে কী ধরতে পারবে। Misdirected write ধরতে checksum টা কোথায় থাকতে হবে, আর কেন block এর সাথে রাখলে চলবে না?
  3. RAID-5 rebuild এ ১৬TB × ৭টা drive পড়তে হয়। UBER 10^-15 ধরে হিসাব করুন অন্তত একটা unrecoverable error পাওয়ার সম্ভাবনা কত, আর সেটা থেকে বলুন কেন RAID-6 আজ ন্যূনতম।
  4. Erasure coding (k=6, m=3) ১.৫× overhead এ প্রায় ৩× replication এর সহনশীলতা দেয়। তাহলে কেন সবাই সব জায়গায় EC ব্যবহার করে না? পুনর্গঠনের খরচটা কোথায় লাগে?
  5. S3 এর ১১ nines durability একটা ভুল rm --recursive থেকে বাঁচায় না। "Durability" আর "backup" এর পার্থক্য এক বাক্যে বলুন, আর প্রতিটার জন্য একটা S3 feature নাম করুন।
  6. CRC32 error detection এ যথেষ্ট কিন্তু dedup এ বিপজ্জনক। পার্থক্যটা "দুর্ঘটনা বনাম ইচ্ছাকৃত" দিয়ে ব্যাখ্যা করুন। Git কেন SHA-1 ছেড়ে SHA-256 এ যাচ্ছে?
