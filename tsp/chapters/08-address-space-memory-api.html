Address space আর memory API

প্রতিটা process ভাবে পুরো memory তার একলার, আর শূন্য থেকে শুরু। এই illusion টার গঠন, তার ভিতরে malloc() আসলে কী করে, আর কেন আপনার allocator একটা list ঘেঁটে জায়গা খোঁজে না — যদিও পাঠ্যবই সেটাই বলে।

Chapter 1 এ mem.c চালিয়ে দেখেছিলাম দুটো process একই address 0x200000 পায়, অথচ একজন অন্যজনের মান নষ্ট করে না। এখন সেই illusion টার নাম দিই: address space।

Address space হলো একটা process এর পুরো memory অবস্থা — তার instruction, তার data, তার stack, তার heap। Process এর দৃষ্টিতে এটা ০ থেকে শুরু হওয়া byte এর একটা নিরবচ্ছিন্ন array।

Crux

একটাই physical memory, অনেক process। OS কীভাবে প্রত্যেককে বিশ্বাস করাবে যে পুরো memory তার — আর তা করবে দ্রুত, আর একজনকে অন্যজনের থেকে সুরক্ষিত রেখে?

Address space এর গঠন

  0x7fff_ffff_ffff  ┌────────────────────────┐  উঁচু address
                    │  [stack]               │
                    │  argc, argv, env       │
                    │         ↓ নিচে বাড়ে    │
                    ├────────────────────────┤
                    │                        │
                    │      (বিশাল ফাঁকা)     │  ← এখানে কোনো
                    │                        │    physical page নেই
                    ├────────────────────────┤
                    │  mmap region           │  ← shared library,
                    │  libc.so, ...          │    বড় malloc
                    ├────────────────────────┤
                    │         ↑ উপরে বাড়ে    │
                    │  [heap]                │  ← malloc() এখান থেকে
                    ├────────────────────────┤
                    │  .bss   (শূন্য data)   │
                    │  .data  (init করা)     │
                    ├────────────────────────┤
                    │  .rodata (const)       │
                    │  .text  (code)         │  ← read-only, execute
  0x0000_0040_0000  └────────────────────────┘
  0x0             (প্রথম page ইচ্ছে করে unmapped —
                   তাই NULL pointer dereference
                   সাথে সাথে SIGSEGV দেয়)

x86-64 এ একটা সাধারণ address space। Stack আর heap বিপরীত দিকে বাড়ে, যাতে মাঝের ফাঁকা জায়গা দুজনেই ব্যবহার করতে পারে।

কয়েকটা সিদ্ধান্ত লক্ষ করুন, কারণ প্রতিটার পিছনে কারণ আছে:

  • Address 0 unmapped — এটা ইচ্ছাকৃত। তাই *(int*)NULL = 5 সাথে সাথে ধরা পড়ে, নীরবে কিছু নষ্ট না করে।
  • Code read-only — নিজের instruction বদলানো আটকায়, আর একই binary এর সব copy ওই page গুলো ভাগ করতে পারে (chapter 3 এর COW)।
  • Stack আর heap উল্টো দিকে — মাঝের ফাঁকা জায়গাটা যেকোনো একজন যত দরকার তত নিতে পারে, আগে থেকে ভাগ করে রাখতে হয় না।

আসলে দেখা যায়, chapter 2 এর মতোই: 

$ cat /proc/self/maps | awk '{print $1, $2, $6}'
5581c4c00000-5581c4c02000 r--p /usr/bin/cat      ← .text (read)
5581c4c02000-5581c4c06000 r-xp /usr/bin/cat      ← .text (execute)
5581c4c09000-5581c4c0a000 rw-p /usr/bin/cat      ← .data
5581c5f0a000-5581c5f2b000 rw-p [heap]
7f2a1c000000-7f2a1c028000 r--p /lib/libc.so.6
7ffd4a5c0000-7ffd4a5e1000 rw-p [stack]

ওই r--p / r-xp / rw-p অংশটা permission — read, write, execute, আর private। Hardware এই bit গুলো প্রতিটা access এ পরীক্ষা করে। Chapter 9 এ দেখব কোথায় রাখা থাকে।

তিনটা লক্ষ্য

লক্ষ্যমানেভাঙলে কী হয়
Transparency Process জানবেই না যে memory virtualized প্রতিটা program কে memory ভাগ করে নেওয়ার code লিখতে হতো
Efficiency সময়ে আর জায়গায় — দুদিকেই কম overhead প্রতিটা memory access ধীর হতো (chapter 10 এর TLB এর কারণ)
Protection একজন অন্যজনকে বা kernel কে ছুঁতে পারবে না যেকোনো bug বা attacker পুরো মেশিন নিতে পারত

Memory API — malloc আর free

C তে heap থেকে memory নেওয়ার interface টা ছোট:

c 
void *malloc(size_t size);   /* size byte দাও, বা NULL */
void  free(void *ptr);       /* ফেরত নাও */

/* একটা int এর জায়গা */
int *x = malloc(sizeof(int));        /* sizeof, 4 নয় — portable */
if (x == NULL) { /* handle it */ }
*x = 42;
free(x);

/* 100টা int এর array */
int *arr = malloc(100 * sizeof(int));

/* শূন্য দিয়ে ভরা */
int *zeroed = calloc(100, sizeof(int));

/* আকার বদলানো — পুরনো data রেখে */
arr = realloc(arr, 200 * sizeof(int));

sizeof ব্যবহার করা গুরুত্বপূর্ণ — এটা compile time এ হিসাব হয়, আর platform বদলালেও ঠিক থাকে। একটা সাধারণ ফাঁদ:

c 
int *x = malloc(10 * sizeof(int));
printf("%zu\n", sizeof(x));    /* 8 — pointer এর আকার, array এর নয়! */

/* string এ off-by-one */
char *src = "hello";
char *dst = malloc(strlen(src));       /* ভুল — '\0' এর জায়গা নেই */
char *ok  = malloc(strlen(src) + 1);   /* ঠিক */
strcpy(ok, src);

চারটা ক্লাসিক bug

  ১. Uninitialized read
     int *x = malloc(sizeof(int));
     printf("%d", *x);        ← আগের কারো ফেলে যাওয়া byte

  ২. Memory leak
     void f() { malloc(100); }   ← pointer হারিয়ে গেল,
     for(;;) f();                  memory ফেরত দেওয়ার উপায় নেই

  ৩. Dangling pointer (use after free)
     free(x);
     *x = 5;                  ← ওই জায়গা এখন অন্য কারো

  ৪. Double free
     free(x);
     free(x);                 ← allocator এর নিজের গঠন নষ্ট হয়

শেষ দুটো বিশেষভাবে বিপজ্জনক, কারণ এগুলো সাথে সাথে crash করে না। Use-after-free অনেক সময় কাজ করে যায় — যতক্ষণ ওই জায়গা কেউ পুনর্ব্যবহার করেনি। তারপর একদিন, অন্য কোথাও, অসংলগ্নভাবে ভাঙে। আর এটাই security exploit এর একটা প্রধান পথ।

এগুলো ধরার যন্ত্রপাতি আছে, আর সেগুলো ব্যবহার করা উচিত:

# ASan — দ্রুত, use-after-free আর overflow ধরে
$ gcc -fsanitize=address -g prog.c && ./a.out

# Valgrind — ধীর, কিন্তু leak এর পূর্ণ হিসাব দেয়
$ valgrind --leak-check=full ./prog

# শুধু leak খুঁজতে (ASan এর নিজের leak checker)
$ ASAN_OPTIONS=detect_leaks=1 ./a.out
ভুল ধারণা

"malloc() আর free() system call, তাই খরচি" — বা "free() করলে memory OS কে ফেরত যায়।"

দুটোই ভুল, আর দ্বিতীয়টা প্রায় সব "memory leak" তদন্তের মূলে।

malloc() একটা library function। সে kernel থেকে বড় বড় খণ্ডে memory নেয় (mmap() বা brk() দিয়ে), তারপর সেই খণ্ড নিজে কেটে কেটে আপনাকে দেয়। বেশিরভাগ malloc() কোনো syscall করেই না — ~১৫–২৫ ন্যানোসেকেন্ডে ফেরে।

free() শুধু allocator কে বলে "এই টুকরো আবার ব্যবহারযোগ্য"। Memory টা process এর কাছেই থাকে। তাই free() করার পরেও top এ RSS কমে না — আর এটা leak নয়।

এই কারণেই আপনার Node/Python/Java service এর RSS বাড়ে তারপর একটা মালভূমিতে স্থির হয়। Allocator টা চূড়ার চাহিদা ধরে রাখছে, পরের বার কাজে লাগানোর জন্য। Chapter 11 এ দেখব কখন এটা সত্যিই OS কে ফেরত যায় (আর MADV_FREE কেন RSS এর হিসাব আরও ঘোলা করে)।

Allocator এর ভিতরে

Allocator এর মূল সমস্যা: হাতে কিছু free জায়গা আছে, বিভিন্ন আকারের অনুরোধ আসছে। কোনটা কোথায় বসাব?

দুটো মৌলিক কাজ: 

  Splitting — বড় free খণ্ড কেটে ছোট অনুরোধ মেটানো

   আগে:  [ free 30 bytes                    ]
   10 byte চাওয়া হলো
   পরে:  [used 10][ free 20                 ]


  Coalescing — পাশাপাশি free খণ্ড জোড়া লাগানো

   আগে:  [ free 10 ][ free 10 ][ free 10 ]
         ← এখানে 25 byte চাইলে ব্যর্থ হতো!
   জোড়ার পর:  [ free 30                    ]
         ← এখন 25 byte দেওয়া যায়

Coalescing না করলে একটা বিশেষ সমস্যা হয়: মোট free জায়গা প্রচুর, কিন্তু কোনো একটা টুকরোই যথেষ্ট বড় নয়। এর নাম external fragmentation।

পাঠ্যবইয়ের placement নীতিগুলো — first fit, best fit, next fit — একটা free list ঘেঁটে জায়গা খোঁজে। ধারণাগতভাবে এগুলো জানা দরকার, কারণ trade-off টা চিরন্তন: দ্রুত খোঁজা বনাম কম অপচয়।

যেখানে source টা পুরনো

OSTEP এই অংশে বেশ সময় দেয় first/best/worst/next fit এর তুলনায়। কিন্তু ২০২৬ এ কোনো production allocator একটা list ঘেঁটে জায়গা খোঁজে না। "একটা list hunt করা" মানসিক ছবিটা আপনার performance intuition কে ভুল পথে নেয়।

আসল allocator (glibc malloc, jemalloc, tcmalloc, mimalloc) যা করে:

  • Size class — অনুরোধকে নির্দিষ্ট আকারের খোপে গোল করা (৮, ১৬, ৩২, ৪৮, ৬৪…)। প্রতিটা খোপের নিজের free list, তাই খোঁজার দরকার নেই — শুধু pop।
  • Per-thread cache — প্রতিটা thread এর নিজের ছোট ভাণ্ডার, তাই সাধারণ allocation এ কোনো lock লাগে না। এই কারণেই allocation ন্যানোসেকেন্ডে হয়।
  • বড় allocation সরাসরি mmap() — allocator মাঝখানে থাকে না।

আর একটা কথা: worst fit নিয়ে সময় নষ্ট করার দরকার নেই। কেউ এটা ship করে না; এটা একটা প্রতিতুলনামূলক উদাহরণ মাত্র।

একই ধারণা kernel এর ভিতরেও আছে, আর আপনি দেখতে পারেন: 

# buddy allocator — physical page এর জন্য
# প্রতিটা কলাম একটা আকার: 4K, 8K, 16K, ... (2^n)
$ cat /proc/buddyinfo
Node 0, zone   Normal  1024  512  256  128  64  32  16  8  4  2  1

# slab allocator — kernel এর নিজের object এর জন্য
$ sudo slabtop -o | head -8
# dentry, inode_cache ইত্যাদি — প্রতিটা একটা size class

buddyinfo এর সংখ্যাগুলো ডান দিকে গিয়ে শূন্য হলে সেটা fragmentation এর চিহ্ন: ছোট page আছে, কিন্তু বড় নিরবচ্ছিন্ন খণ্ড নেই। Huge page allocate করতে গিয়ে ব্যর্থ হওয়ার কারণ প্রায়ই এটাই — chapter 10 এ ফিরব।

আপনার কাজের সাথে যোগ

jemalloc কেন ব্যবহার করা হয় — Redis আর অনেক Rust/Go service এ — তার কারণ fragmentation এর আচরণ। glibc malloc এর arena গুলো thread সংখ্যার সাথে বাড়ে (default এ ৮ × core সংখ্যা), আর প্রতিটা arena আলাদাভাবে জায়গা ধরে রাখে। ৬৪ core এর মেশিনে এটা উল্লেখযোগ্য RSS। MALLOC_ARENA_MAX=2 দিয়ে সীমিত করা যায় — container এ এটা একটা সাধারণ tuning।

Postgres এর shared_buffers আসলে একটা নিজের allocator — সে OS কে বিশ্বাস না করে নিজেই একটা বড় shared memory অঞ্চল নিয়ে তার ভিতরে page ব্যবস্থাপনা করে। কারণ database জানে কোন page আবার লাগবে, OS জানে না।

V8 (Node) heap টা GC-চালিত, কিন্তু নিচে সেই একই mmap()। তাই --max-old-space-size V8 এর সীমা, আর cgroup এর memory.max kernel এর সীমা — দুটো আলাদা, আর প্রথমটা দ্বিতীয়টার চেয়ে বড় হলে OOM kill অনিবার্য।

সরাসরি kernel থেকে — mmap আর brk

Allocator নিজে kernel থেকে memory নেয় কীভাবে? দুটো উপায়:

c 
/* brk/sbrk — heap এর সীমানা সরানো (পুরনো পদ্ধতি) */
void *old_top = sbrk(0);          /* বর্তমান সীমা জানো */
sbrk(4096);                       /* 4KB বাড়াও */

/* mmap — একটা নতুন অঞ্চল চাওয়া (আধুনিক পদ্ধতি) */
void *p = mmap(NULL, 1 << 20,     /* 1 MB */
               PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS,
               -1, 0);
if (p == MAP_FAILED) { /* handle */ }
munmap(p, 1 << 20);

/* file কে সরাসরি memory তে map করা — chapter 24 এ ফিরব */
int fd = open("data.bin", O_RDONLY);
void *data = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
/* এখন data[i] পড়া মানে file এর i-তম byte পড়া,
   কোনো read() syscall ছাড়াই */

আপনি malloc() এর ভিতরে কোনটা হচ্ছে তা দেখতে পারেন: 

$ strace -e trace=mmap,munmap,brk ./your-program 2>&1 | head
# ছোট malloc → কোনো syscall নেই (cache থেকে)
# বড় malloc  → mmap দেখা যাবে
# glibc এ সীমাটা M_MMAP_THRESHOLD, default 128KB
ভুল ধারণা

mmap() সফল হয়েছে মানে memory টা আমার হয়ে গেছে।"

না। mmap() শুধু address space সংরক্ষণ করে — page table এ একটা এলাকা চিহ্নিত হয়, কিন্তু কোনো physical page বরাদ্দ হয় না। Physical page আসে যখন আপনি সত্যিই ওই address ছোঁন, একটা page fault এর মাধ্যমে। এর নাম demand paging, আর এটাই chapter 9 আর 11 এর বিষয়।

এই কারণেই একটা program ১TB mmap() করতে পারে ১৬GB মেশিনে, আর top এ VIRT ১TB দেখাবে কিন্তু RSS প্রায় শূন্য। Chapter 2 এ VmSize বনাম VmRSS এর পার্থক্য দেখেছিলাম — কারণটা এটাই।

আর তাই malloc() সফল হওয়া মানে আপনার memory আছে, এমন নয়। Linux ডিফল্টে overcommit করে — যত চাওয়া হয় তত প্রতিশ্রুতি দেয়, ধরে নিয়ে সবাই সবটা ব্যবহার করবে না। প্রতিশ্রুতি রাখতে না পারলে যা হয়, সেটা OOM killer — chapter 11।

Segmentation — যে পথটা হারিয়ে গেছে

Address space কে physical memory তে বসানোর একটা পুরনো পদ্ধতি ছিল segmentation: প্রতিটা logical অংশ (code, heap, stack) কে আলাদাভাবে একটা base + size দিয়ে বসানো।

এটা fixed base-and-bounds এর চেয়ে ভালো ছিল, কারণ মাঝের বিশাল ফাঁকা জায়গাটা physical memory নিত না। কিন্তু এর একটা মারাত্মক সমস্যা: segment গুলোর আকার আলাদা, তাই physical memory তে external fragmentation তৈরি হতো — উপরে allocator এ যে সমস্যাটা দেখলাম, কিন্তু এবার পুরো physical RAM এর মাপে।

এই একটা কারণেই fixed-size page জিতেছে: সব টুকরো একই আকার হলে external fragmentation তত্ত্বগতভাবেই অসম্ভব। যেকোনো free page যেকোনো চাহিদা মেটাতে পারে।

Segmentation এর অবস্থা — ২০২৬

Translation mechanism হিসেবে segmentation মৃত। x86-64 long mode এ CS, DS, ES, SS এর base জোর করে শূন্য করা — hardware সেগুলো উপেক্ষা করে। শুধু FS আর GS এর base টিকে আছে, আর সেটাও translation এর জন্য নয়: FS ব্যবহৃত হয় thread-local storage এ, GS kernel এর per-CPU data তে। ARM64 আর RISC-V এ segmentation নেই।

তাহলে এটা কেন জানা দরকার? দুটো কারণে:

  • SIGSEGV নামটা এখান থেকে — "segmentation violation"। প্রতিদিন যে error টা দেখেন, তার নাম একটা মৃত mechanism এর স্মৃতি।
  • External fragmentation এর যুক্তিটা — এটাই paging এর অস্তিত্বের কারণ। Chapter 9 এ fixed-size page দেখে "এত অপচয় কেন" মনে হলে, উত্তরটা এই অনুচ্ছেদে।

এর বেশি সময় দেওয়ার দরকার নেই — OSTEP এ এই বিষয়ে ৯ পাতা আছে, আমরা দুই অনুচ্ছেদে সারলাম, আর বাঁচানো জায়গাটা Part 2 এর memory model এ খরচ করব।

প্রশ্ন

  1. Address space এ প্রথম page টা ইচ্ছে করে unmapped রাখা হয়। যদি mapped রাখা হতো, তাহলে *(int*)NULL = 5 লেখা একটা bug কীভাবে প্রকাশ পেত? কেন "সাথে সাথে crash" "নীরবে কাজ করে যাওয়া" এর চেয়ে ভালো?
  2. আপনার service এ free() ঠিকভাবে ডাকা হচ্ছে, কোনো leak নেই (Valgrind পরিষ্কার), তবু RSS বেড়ে ২GB হয়ে স্থির হয়ে আছে। কেন memory OS কে ফেরত যাচ্ছে না? এটা কি সমস্যা — আর কোন পরিস্থিতিতে এটা সমস্যা হয়ে ওঠে?
  3. Coalescing না থাকলে মোট free memory প্রচুর থাকতেও allocation ব্যর্থ হতে পারে। একটা concrete ক্রম লিখুন (কয়েকটা malloc আর free) যার পরে ৩০ byte free আছে কিন্তু ২৫ byte এর অনুরোধ ব্যর্থ হবে।
  4. Production allocator size class আর per-thread cache ব্যবহার করে, list hunt করে না। এই পার্থক্যটা আপনার performance intuition এ কী বদলায়? বিশেষত: একটা multi-threaded program এ allocation কে "lock নেওয়ার মতো খরচি" ভাবা কেন ভুল, আর কখন সেটা সত্যি হয়ে যায়?
  5. একটা program ১TB mmap() করল ১৬GB মেশিনে, আর সফল হলো। তারপর সে ওই এলাকার প্রতি page এ একটা byte লিখতে শুরু করল। ঠিক কোন মুহূর্তে সমস্যা হবে, আর কী ঘটবে? আপনার উত্তরে "সংরক্ষণ" আর "বরাদ্দ" আলাদা করুন।
  6. Segmentation কে হত্যা করেছে external fragmentation, আর paging সেটা সমাধান করে সব টুকরো একই আকার করে। কিন্তু fixed-size page এর নিজের একটা অপচয় আছে — সেটা কী, আর কেন সেটা external fragmentation এর চেয়ে সহনীয়?
