Deadlock — আর যা সত্যিই আটকায়

Lock সমস্যা সমাধান করে, আর নতুন সমস্যা তৈরি করে। দুটো thread পরস্পরের অপেক্ষায় চিরকাল বসে থাকতে পারে। এর তত্ত্বটা সরল — চারটে শর্ত — কিন্তু আপনি এর সাথে প্রথম দেখা করবেন সম্ভবত একটা Postgres error message এ।

সবচেয়ে ছোট উদাহরণটা দিয়ে শুরু করি: 

  Thread 1                      Thread 2
  ─────────────────────         ─────────────────────
  lock(L1)     ✓                lock(L2)     ✓
       │                             │
  lock(L2)  ⏳ অপেক্ষা           lock(L1)  ⏳ অপেক্ষা
       │                             │
       └──── T2 এর জন্য ───┐  ┌── T1 এর জন্য ────┘
                          ▼  ▼
                    চিরকাল আটকে

  কেউ ছাড়বে না, কারণ কেউ এগোতে পারছে না।
c 
/* The classic. Both orders look reasonable in isolation. */
void *thread1(void *arg) {
    pthread_mutex_lock(&L1);
    pthread_mutex_lock(&L2);      /* ← waits for thread2 */
    /* ... */
    pthread_mutex_unlock(&L2);
    pthread_mutex_unlock(&L1);
    return NULL;
}

void *thread2(void *arg) {
    pthread_mutex_lock(&L2);      /* opposite order! */
    pthread_mutex_lock(&L1);      /* ← waits for thread1 */
    /* ... */
    pthread_mutex_unlock(&L1);
    pthread_mutex_unlock(&L2);
    return NULL;
}

লক্ষ করুন দুটো function আলাদাভাবে দেখলে কোনো ভুল নেই। Bug টা তাদের সম্পর্কে — আর এই কারণেই deadhead code review তে ধরা পড়া কঠিন: আপনাকে দুটো ফাইলের দুটো function একসাথে দেখতে হবে।

চারটে শর্ত

Deadlock হতে চারটে শর্তই একসাথে লাগে। যেকোনো একটা ভাঙলে deadlock অসম্ভব — আর এটাই সব প্রতিরোধ কৌশলের ভিত্তি:

শর্তমানেভাঙার উপায়
Mutual exclusion Resource একসাথে একজনই ধরতে পারে Lock-free structure (ch 16) — কঠিন
Hold-and-wait একটা ধরে রেখে আরেকটার অপেক্ষা সব lock একসাথে নাও, নয়তো কিছুই না
No preemption জোর করে কারো lock কেড়ে নেওয়া যায় না trylock() + ছেড়ে দিয়ে আবার চেষ্টা
Circular wait অপেক্ষার একটা বৃত্ত তৈরি হওয়া Lock ordering ← সবচেয়ে ব্যবহারিক

১. Lock ordering — বাস্তবে যেটা ব্যবহার করবেন

সবচেয়ে সরল আর কার্যকর: সব lock সবসময় একই ক্রমে নাও। তাহলে বৃত্ত তৈরি হতেই পারে না।

c 
/* Both threads now take L1 before L2, always. */
void *thread2_fixed(void *arg) {
    pthread_mutex_lock(&L1);      /* was L2 first */
    pthread_mutex_lock(&L2);
    /* ... */
    pthread_mutex_unlock(&L2);
    pthread_mutex_unlock(&L1);
    return NULL;
}

কিন্তু একটা সমস্যা: lock গুলো যদি runtime এ নির্ধারিত হয় (যেমন দুটো account এর মধ্যে টাকা সরানো), তখন "L1 আগে" বলার কোনো স্থির অর্থ নেই। সমাধান — একটা মোট ক্রম তৈরি করো, address দিয়ে:

c 
/* Transfer between two accounts, with a total order derived
   from the lock addresses themselves. Any pair of threads
   will agree on the order, whatever accounts they picked. */
void transfer(account_t *from, account_t *to, int amount) {
    account_t *first, *second;

    if (from < to) {              /* compare ADDRESSES */
        first = from; second = to;
    } else {
        first = to;   second = from;
    }

    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);

    from->balance -= amount;
    to->balance   += amount;

    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}

/* Bonus: also handles from == to safely if you add a check. */

এই কৌশলটা মনে রাখার মতো, কারণ database এও ঠিক একই সমাধান ব্যবহার করা হয় — নিচে দেখব।

২. trylock — preemption নকল করা

c 
/* If the second lock is busy, give up the first and retry.
   Breaks hold-and-wait. */
for (;;) {
    pthread_mutex_lock(&L1);
    if (pthread_mutex_trylock(&L2) == 0)
        break;                        /* got both */
    pthread_mutex_unlock(&L1);        /* back off */
    /* সামান্য random অপেক্ষা — নইলে livelock, নিচে দেখুন */
}
/* ... critical section ... */
pthread_mutex_unlock(&L2);
pthread_mutex_unlock(&L1);
ভুল ধারণা

"trylock + retry দিয়ে deadhead সম্পূর্ণ সমাধান হয়ে গেল।"

Deadlock গেল, কিন্তু livelock এল: দুটো thread একই সাথে চেষ্টা করছে, একই সাথে ব্যর্থ হচ্ছে, একই সাথে ছেড়ে দিচ্ছে, একই সাথে আবার চেষ্টা করছে — অনির্দিষ্টকাল। কেউ আটকে নেই (তাই deadlock নয়), কিন্তু কেউ এগোচ্ছেও না।

সমাধান: retry এর আগে একটা random অপেক্ষা (exponential backoff with jitter)। এটা ঠিক সেই কৌশল যা আপনি network retry তে ব্যবহার করেন — একই কারণে।

আরও একটা ফাঁদ: trylock loop এ যদি আপনি ইতিমধ্যে কিছু কাজ করে ফেলেছেন, তাহলে retry এর আগে সেটা undo করতে হবে। এই কারণেই lock ordering সাধারণত সহজ পথ।

৩. Avoidance — আর কেন এটা অপ্রাসঙ্গিক

যা আমরা সংক্ষেপে সারছি

OSTEP এ (আর প্রায় প্রতিটা OS পাঠ্যবইয়ে) Dijkstra এর Banker's Algorithm আছে — একটা scheduler যা আগে থেকে জানে কে কোন resource কতটা চাইবে, আর সেই জ্ঞান দিয়ে deadlock এড়িয়ে চলে।

এটা একটা ঐতিহাসিক টীকা হিসেবেই যথেষ্ট, কারণ শর্তটাই অবাস্তব: আপনাকে আগে থেকে সম্পূর্ণ resource চাহিদা জানতে হবে। একটা সাধারণ program এ সেটা অজানা। OSTEP নিজেই স্বীকার করে এটা কেবল embedded system এ কাজে লাগে, যেখানে workload আগে থেকে জানা।

তাই এই পাতাটা আমরা খরচ করছি সেই জিনিসে যা আপনি সত্যিই চালাবেন — TSan, lockdep, আর database deadlock detector।

Deadlock ধরা

প্রতিরোধ সবসময় সম্ভব নয়, তাই ধরার ব্যবস্থাও দরকার। কৌশলটা একটা wait-for graph: 

  কে কার অপেক্ষায় — একটা directed graph বানাও:

     T1 ──────▶ T2
     ▲           │
     │           ▼
     T4 ◀────── T3

  বৃত্ত আছে → deadlock আছে।

  এই graph টা খুঁজে বৃত্ত সনাক্ত করা একটা সাধারণ
  algorithm — আর database রা ঠিক এটাই করে।

আপনার code এ — TSan আর lockdep

$ gcc -fsanitize=thread -g -O1 prog.c -o prog -pthread
$ ./prog

  Cycle in lock order graph:
    M1 (0x5578...) => M2 (0x5578...) => M1

# গুরুত্বপূর্ণ: deadlock সত্যিই ঘটার দরকার নেই!
# TSan শুধু দেখে যে দুটো ক্রম পরস্পরবিরোধী।

এই শেষ কথাটাই TSan কে অমূল্য করে। Deadlock একটা timing-নির্ভর ঘটনা — হাজারবার চালিয়েও না ঘটতে পারে। TSan অপেক্ষা করে না; সে ক্রমের বিরোধ দেখে, আর একবার দুটো path দেখলেই সতর্ক করে।

Database deadlock — আপনি এটাই বেশি দেখবেন

একজন working engineer এর deadlock এর সাথে প্রথম দেখা প্রায় সবসময় একটা database error message এ, thread এ নয়: 

ERROR:  deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 678;
        blocked by process 12346.
        Process 12346 waits for ShareLock on transaction 679;
        blocked by process 12345.
HINT:   See server log for query details.
SQLSTATE: 40P01

কারণটা হুবহু উপরের সেই ছবি, শুধু lock এর বদলে row: 

  Transaction A                    Transaction B
  ──────────────────────           ──────────────────────
  UPDATE accounts                  UPDATE accounts
    SET bal = bal - 100              SET bal = bal - 50
    WHERE id = 1;    ✓ row 1 lock    WHERE id = 2;   ✓ row 2 lock
         │                                │
  UPDATE accounts                  UPDATE accounts
    SET bal = bal + 100              SET bal = bal + 50
    WHERE id = 2;   ⏳ অপেক্ষা        WHERE id = 1;  ⏳ অপেক্ষা
         │                                │
         └────── circular wait ───────────┘

  Postgres ~1 সেকেন্ড পর (deadlock_timeout) graph যাচাই করে,
  বৃত্ত পায়, আর একটা transaction কে "victim" বেছে abort করে।

সমাধানটা application এর দিকে, database এর নয় — আর সেটা ঠিক উপরের সেই lock ordering:

sql 
-- ভুল: ক্রম নির্ভর করে কে কোন account থেকে পাঠাচ্ছে
BEGIN;
UPDATE accounts SET bal = bal - 100 WHERE id = :from;
UPDATE accounts SET bal = bal + 100 WHERE id = :to;
COMMIT;

-- ঠিক: সবসময় id এর ক্রমে lock নাও
BEGIN;
SELECT id FROM accounts
  WHERE id IN (:from, :to)
  ORDER BY id                    -- ← deterministic order
  FOR UPDATE;                    -- ← lock both, in that order
UPDATE accounts SET bal = bal - 100 WHERE id = :from;
UPDATE accounts SET bal = bal + 100 WHERE id = :to;
COMMIT;

লক্ষ করুন এটা একই কৌশল যা C তে address তুলনা করে করেছিলাম — শুধু address এর বদলে primary key। ধারণাটা অপরিবর্তিত: একটা মোট ক্রম তৈরি করো যেটা সব participant স্বাধীনভাবে একইভাবে হিসাব করতে পারে।

আপনার কাজের সাথে যোগ

Deadlock কমানোর ব্যবহারিক তালিকা:

  • Deterministic key ordering — উপরের ORDER BY id FOR UPDATE। সবচেয়ে কার্যকর একক পরিবর্তন।
  • Transaction ছোট রাখা — lock ধরার সময় কমালে সংঘর্ষের সম্ভাবনা কমে। বিশেষত: transaction এর ভিতরে কখনো external API call করবেন না (আপনি একটা HTTP timeout এর সময় ধরে row lock ধরে রাখবেন)।
  • Retry করা — 40P01 একটা প্রত্যাশিত error, bug নয়। আপনার ORM layer এ এটা ধরে backoff দিয়ে retry করা উচিত। এটা optimistic concurrency এর স্বাভাবিক অংশ।
  • Isolation level বোঝা — SERIALIZABLE এ Postgres serialization failure (40001) দেয়, যা আরও ঘন ঘন হয় কিন্তু deadlock এর চেয়ে সস্তা। দুটোরই retry দরকার। 
-- আপনার deadlock গুলো কোথায় হচ্ছে
$ grep -i deadlock /var/log/postgresql/*.log
-- MySQL/InnoDB এ:
mysql> SHOW ENGINE INNODB STATUS\G    -- LATEST DETECTED DEADLOCK অংশ

অন্য ধরনের আটকে যাওয়া

Deadlock একটা শ্রেণী মাত্র। যে সমস্যাগুলো একইরকম দেখায় কিন্তু আলাদা:

সমস্যাকী ঘটেলক্ষণ
Deadlock বৃত্তাকার অপেক্ষা CPU ০%, কেউ এগোচ্ছে না
Livelock সবাই চেষ্টা করছে, সবাই ব্যর্থ CPU ১০০%, তবু কাজ এগোচ্ছে না
Starvation একজন বারবার হারছে একটা thread এর latency অস্বাভাবিক
Priority inversion নিম্ন-priority holder উচ্চ-priority waiter কে আটকাচ্ছে Real-time deadline মিস

Priority inversion টা বিশেষভাবে শিক্ষামূলক, কারণ এর একটা বিখ্যাত ঘটনা আছে: ১৯৯৭ সালে Mars Pathfinder rover মঙ্গলগ্রহে বারবার reset হতে শুরু করেছিল। কারণ ছিল একটা নিম্ন-priority thread একটা mutex ধরে রেখেছিল, যেটা একটা উচ্চ-priority thread এর দরকার ছিল, আর মাঝের একটা মাঝারি-priority thread নিম্ন টাকে চলতেই দিচ্ছিল না।

সমাধান priority inheritance — holder এর priority সাময়িকভাবে waiter এর সমান করে দেওয়া। Chapter 17 এ বলেছিলাম mutex এর মালিক থাকে আর semaphore এর থাকে না; এই feature টা সেই মালিকানার উপরই নির্ভর করে:

c 
/* Ask for priority inheritance — needs an owner, which is why
   this exists for mutexes and not for semaphores. */
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&m, &attr);

সবচেয়ে ভালো কৌশল — lock ই না রাখা

Chapter 14 আর 16 এর সেই একই উপদেশ, আর deadlock এর ক্ষেত্রে এটা সবচেয়ে জোরালো: যেখানে একটাই lock, সেখানে deadlock অসম্ভব। 

  deadlock প্রতিরোধের ক্রম, পছন্দ অনুসারে:

  ১. একটাই lock ব্যবহার করুন
       দুটো lock না থাকলে বৃত্ত তৈরি হতে পারে না।
       (দাম: কম concurrency — ch 16 এর trade-off)

  ২. lock একদম এড়িয়ে যান
       message passing (Go channel), immutable data,
       single-threaded event loop (ch 19)

  ৩. একটা মোট ক্রম মানুন
       address, id, বা যেকোনো স্থির tie-breaker
       → CI তে TSan দিয়ে যাচাই করুন

  ৪. trylock + backoff
       শুধু যখন ক্রম আরোপ করা অসম্ভব

  ৫. detect + recover
       database যেটা করে — abort করে retry
       (আপনার application এও এটা বৈধ কৌশল)
ভুল ধারণা

"আমাদের code এ deadlock নেই — আমরা কয়েক বছর ধরে চালাচ্ছি, কখনো হয়নি।"

Deadlock একটা timing-নির্ভর ঘটনা। দুটো পরস্পরবিরোধী lock ক্রম থাকা মানে সম্ভাবনাটা আছে; সেটা প্রকাশ পেতে দরকার শুধু ঠিক সেই interleaving।

আর সেই interleaving এর সম্ভাবনা বাড়ে যখন: load বাড়ে, core সংখ্যা বাড়ে, একটা নতুন code path যোগ হয়, বা একটা lock এর নিচে হঠাৎ ধীর কিছু চলে আসে (যেমন একটা query ধীর হয়ে গেল)। অর্থাৎ ঠিক সেই মুহূর্তে যখন আপনার system এর উপর সবচেয়ে বেশি চাপ।

তাই "কখনো হয়নি" প্রমাণ নয়। TSan এর সতর্কবার্তা প্রমাণ, কারণ সে ঘটনার অপেক্ষা না করে কারণ দেখে।

প্রশ্ন

  1. চারটে শর্তের যেকোনো একটা ভাঙলে deadlock অসম্ভব। প্রতিটা শর্তের জন্য একটা ভাঙার কৌশল আছে, কিন্তু বাস্তবে প্রায় সবাই একটাই বেছে নেয় (circular wait)। বাকি তিনটে কেন কম ব্যবহারিক — প্রতিটার জন্য একটা কারণ দিন।
  2. Address তুলনা করে lock ordering আর SQL এ ORDER BY id FOR UPDATE — দুটো একই কৌশল। সাধারণ নীতিটা কী? এখন একটা পরিস্থিতি ভাবুন যেখানে কোনো স্থির tie-breaker নেই — তখন কী করবেন?
  3. trylock + retry deadlock সারায় কিন্তু livelock আনতে পারে। দুটোর লক্ষণ কীভাবে আলাদা (বিশেষত CPU ব্যবহারে)? আর random backoff ঠিক কোন প্রক্রিয়াটা ভাঙে?
  4. TSan deadlock না ঘটলেও lock-order-inversion ধরে। এটা কীভাবে সম্ভব — সে কী তথ্য জমা করে? আর এই ক্ষমতাটা কেন একটা stress test এর চেয়ে বেশি নির্ভরযোগ্য?
  5. Postgres এর 40P01 একটা প্রত্যাশিত error, bug নয়। এই দৃষ্টিভঙ্গিটা মানলে আপনার application code এ কী থাকা উচিত? আর SERIALIZABLE isolation এ যে 40001 বেশি ঘন ঘন আসে, সেটা কি খারাপ খবর?
  6. Mars Pathfinder এ priority inversion ঘটেছিল একটা mutex এর কারণে। Chapter 17 এ শিখেছি semaphore এর মালিক নেই। তাহলে ওখানে semaphore ব্যবহার করলে সমস্যাটা এড়ানো যেত, নাকি আরও খারাপ হতো? কেন?
