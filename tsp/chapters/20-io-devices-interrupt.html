I/O device আর interrupt

Part 3 শুরু হচ্ছে সবচেয়ে নিচের স্তর থেকে: CPU কীভাবে একটা device এর সাথে কথা বলে। এখানে একটা ঐতিহাসিক মোচড় আছে — polling কে অদক্ষ বলে interrupt এসেছিল, আর NVMe এর যুগে polling ফিরে এসেছে।

Part 1 এ CPU আর memory virtualize করেছি। Part 2 এ একই memory ভাগ করার সমস্যা। এখন Part 3 — power চলে গেলেও যা থেকে যায়।

কিন্তু file system এ যাওয়ার আগে একটা স্তর নিচে নামতে হবে: CPU আসলে কীভাবে একটা disk কে বলে "এই block টা পড়ো"?

Crux

Device গুলো CPU এর চেয়ে হাজার থেকে লক্ষ গুণ ধীর। OS কীভাবে তাদের সাথে কথা বলবে, আর অপেক্ষার সময়টা নষ্ট না করে কীভাবে কাজে লাগাবে?

একটা আদর্শ device এর interface

প্রতিটা device এর দুটো অংশ: একটা interface (OS যা দেখে) আর একটা internal structure (ভিতরে যা আছে — সাধারণত নিজের firmware আর memory সহ একটা ছোট কম্পিউটার)। 

  OS এর দৃষ্টিতে একটা device = তিনটে register:

  ┌────────────────────────────────────────┐
  │  STATUS   — device এখন কী অবস্থায়      │
  │  COMMAND  — কী করতে হবে                │
  │  DATA     — data আনা-নেওয়ার জায়গা      │
  └────────────────────────────────────────┘

  একটা অনুরোধের protocol:

  while (STATUS == BUSY)          ← ১. অপেক্ষা
      ;                              (polling)
  write data to DATA register     ← ২. data দাও
  write command to COMMAND        ← ৩. কাজ শুরু করাও
  while (STATUS == BUSY)          ← ৪. শেষ হওয়ার অপেক্ষা
      ;                              (আবার polling)

এই protocol টা সঠিক কিন্তু নষ্ট করে দুটো জিনিস:

  1. Polling — ধাপ ১ আর ৪ এ CPU শুধু জিজ্ঞেস করতে করতে সময় নষ্ট করছে।
  2. PIO (Programmed I/O) — ধাপ ২ এ CPU নিজে প্রতিটা byte device এ লিখছে। ৪KB মানে হাজারো instruction।

Interrupt — CPU কে মুক্ত করা

প্রথম সমস্যার সমাধান interrupt (chapter 4 এ mechanism দেখেছি): অনুরোধ পাঠিয়ে process টাকে ঘুম পাড়িয়ে দাও, অন্য কাজ চালাও। Device শেষ করলে সে CPU কে ডাকবে। 

  Polling দিয়ে (CPU নষ্ট):

  CPU:  [P1 চলছে][p p p p p p p p][P1 আবার]
  Disk:          [████ কাজ করছে ███]
                  ↑ CPU শুধু জিজ্ঞেস করছে — অপচয়


  Interrupt দিয়ে (overlap):

  CPU:  [P1 চলছে][P2 চলছে ........][P1 আবার]
  Disk:          [████ কাজ করছে ███]⚡
                                    ↑ interrupt

  একই সময়ে disk আর CPU দুটোই ব্যস্ত।
ভুল ধারণা

"Interrupt সবসময় polling এর চেয়ে ভালো — তাই আধুনিক system এ polling ব্যবহার হয় না।"

OSTEP নিজেই সতর্ক করে যে interrupt সবসময় সেরা নয়, আর ২০২৬ এ সেই সতর্কবার্তাটা আরও প্রাসঙ্গিক হয়ে উঠেছে।

একটা interrupt এর খরচ আছে: context switch, handler চালানো, cache নষ্ট হওয়া — সব মিলিয়ে ~১–৫µs। এখন হিসাব করুন: 

HDD seek:        ~১০ ms   → interrupt এর খরচ তুচ্ছ (০.০৫%)
SATA SSD:        ~১০০ µs  → interrupt এর খরচ ~২%
NVMe SSD:        ~২০ µs   → interrupt এর খরচ ~১০–২৫%!
Optane/CXL:      ~১০ µs   → interrupt এর খরচ device এর সমান

Device যত দ্রুত, interrupt এর আপেক্ষিক খরচ তত বেশি। একটা NVMe read এ যদি ২০µs লাগে আর interrupt এ ৩µs, তাহলে ঘুমানো-জাগার পুরো চক্রটাই অপচয়।

তাই polling ফিরে এসেছে, নতুন রূপে: 

# Linux এর NVMe polling queue — অতি-কম latency এর জন্য
$ cat /sys/block/nvme0n1/queue/io_poll
1
# io_uring এ IORING_SETUP_IOPOLL দিয়ে polled I/O

# আর network এ NAPI — interrupt পেয়ে interrupt বন্ধ করে
# একগুচ্ছ packet poll করে নেওয়া (hybrid পদ্ধতি)
$ cat /proc/net/softnet_stat | head -2

এটাই সেই চক্র: polling → interrupt → hybrid → আবার polling। নীতিটা বদলায়নি, শুধু hardware এর গতি বদলেছে বলে সিদ্ধান্তটা উল্টে গেছে।

আরেকটা কারণ আছে interrupt এড়ানোর — livelock (chapter 18 এর সেই শব্দটা, ভিন্ন প্রসঙ্গে)। একটা network card যদি প্রতি packet এ interrupt দেয় আর packet আসে সেকেন্ডে লক্ষ লক্ষ, তাহলে CPU শুধু interrupt সামলাতেই পুরো সময় কাটাবে — আসল প্রক্রিয়াকরণ কখনো হবে না।

সমাধান interrupt coalescing: কয়েকটা ঘটনা জমিয়ে একটা interrupt দাও। দাম হলো সামান্য বাড়তি latency:

$ ethtool -c eth0
rx-usecs: 50          ← ৫০µs জমিয়ে তারপর interrupt
rx-frames: 32         ← বা ৩২টা frame হলেই

DMA — CPU কে data সরানোর কাজ থেকে মুক্তি

দ্বিতীয় সমস্যা — PIO। CPU নিজে byte সরালে ৪KB এর জন্য হাজারো instruction লাগে, আর সেই সময়টা সম্পূর্ণ অপচয়।

DMA (Direct Memory Access — একটা আলাদা engine যা CPU কে বাদ দিয়ে device আর memory এর মধ্যে সরাসরি data সরায়)। 

  PIO দিয়ে:

  CPU:  [P1][cccccccccc][P2 ...]
              ↑ CPU নিজে copy করছে — সম্পূর্ণ অপচয়
  Disk:                 [████]


  DMA দিয়ে:

  CPU:  [P1][P2 চলছে ..........][P1]
  DMA:      [cccc]
  Disk:          [████████]⚡

  CPU শুধু বলে "এই address এ ৪KB আনো", তারপর
  অন্য কাজে চলে যায়। DMA engine নিজে সরায়,
  শেষে interrupt দেয়।

DMA এর একটা গুরুত্বপূর্ণ পরিণতি আছে যা প্রায়ই ভুল বোঝা হয়: DMA engine physical address ব্যবহার করে, virtual নয়। সে page table জানে না।

এর ফলে দুটো জিনিস দরকার হয়:

  • Page pinning — DMA চলার সময় ওই page গুলো swap হয়ে যেতে পারবে না, নইলে DMA ভুল জায়গায় লিখবে। তাই kernel সেগুলো "pinned" করে রাখে। Chapter 11 এর reclaim ওই page ছুঁতে পারে না।
  • IOMMU — একটা device যদি যেকোনো physical address এ লিখতে পারে, তাহলে একটা দুষ্ট বা ত্রুটিপূর্ণ device পুরো kernel memory নষ্ট করতে পারে। IOMMU হলো device দের জন্য একটা page table — chapter 9 এর MMU এর সমতুল্য, কিন্তু device এর দিকে। 
# IOMMU চালু আছে কি (VM passthrough আর নিরাপত্তার জন্য দরকার)
$ dmesg | grep -i -E 'iommu|DMAR' | head -3
$ ls /sys/kernel/iommu_groups/ | wc -l

# কত memory pinned (DMA বা mlock এর কারণে)
$ grep -E 'Mlocked|Bounce' /proc/meminfo

Device এর সাথে কথা বলার দুটো উপায়

 Port I/OMMIO (Memory-Mapped I/O)
কীভাবে বিশেষ instruction (in/out) সাধারণ load/store, বিশেষ address এ
Address space আলাদা I/O space একই physical address space
আজকাল প্রায় অব্যবহৃত (legacy) সবকিছু

MMIO তেই সেই একটা জায়গা যেখানে chapter 14 এর volatile সত্যিই সঠিক হাতিয়ার:

c 
/* MMIO — the one legitimate use of volatile in this book.
   The device changes this memory; the compiler must not
   cache the value in a register or reorder the accesses. */
volatile uint32_t *status = (volatile uint32_t *) 0xfebf0000;

while (*status & BUSY_BIT)        /* must re-read every time */
    ;

/* In real kernel code you use accessors, which add the
   right barriers for the architecture: */
u32 v = readl(dev->regs + STATUS);
writel(CMD_READ, dev->regs + COMMAND);

Chapter 14 এ বলেছিলাম volatile এর বৈধ ব্যবহার আছে — এটাই সেটা। Device register এ volatile লাগে কারণ মানটা আপনার program এর বাইরে থেকে বদলায়। কিন্তু thread এর মধ্যে synchronization এ এটা কখনো নয়।

Device driver আর abstraction

প্রতিটা device এর নিজস্ব protocol আছে। OS কে প্রতিটার জন্য আলাদা code রাখতে হয় — device driver। আর উপরের স্তরগুলোকে একটা সাধারণ interface দিতে হয়: 

  ┌──────────────────────────────────────────────┐
  │  application:  read(fd, buf, 4096)           │
  ├──────────────────────────────────────────────┤
  │  POSIX file API                              │  ← সবার জন্য এক
  ├──────────────────────────────────────────────┤
  │  file system (ext4, xfs, btrfs)              │  ← ch 22-23
  ├──────────────────────────────────────────────┤
  │  generic block layer                         │  ← queue, merge,
  │  (bio, request queue, scheduler)             │    reorder
  ├──────────────────────────────────────────────┤
  │  device driver (nvme, ahci, virtio_blk)      │  ← device-নির্দিষ্ট
  ├──────────────────────────────────────────────┤
  │  hardware                                    │
  └──────────────────────────────────────────────┘

  এই স্তরবিন্যাসের দাম: একটা abstraction যা সব device
  কে একরকম দেখায়, সেটা প্রতিটা device এর বিশেষ ক্ষমতা
  লুকিয়ে ফেলে। NVMe এর ৬৪K queue একটা "block device"
  interface এ প্রকাশ করা কঠিন — তাই io_uring আর
  NVMe passthrough এর মতো নতুন পথ তৈরি হয়েছে।

Linux kernel এর একটা বড় অংশ — কিছু হিসাবে ৭০% এর বেশি code — driver। এই কারণেই kernel এত বড়, আর এই কারণেই একটা নতুন OS লেখা কঠিন: algorithm নয়, driver ই আসল কাজ।

NVMe — queue দিয়ে parallelism

পুরনো disk interface (SATA/AHCI) একটা queue নিয়ে ডিজাইন করা, কারণ একটা ঘুরন্ত disk এ একসাথে একটাই head। কিন্তু একটা SSD এর ভিতরে অনেকগুলো স্বাধীন channel আছে — একটা queue সেই parallelism ব্যবহার করতে পারে না। 

  AHCI (SATA):           একটা queue, ৩২ entry
  ┌─────────────────┐
  │ [][][][][][][]  │───▶ device
  └─────────────────┘
  সব core একই queue এর জন্য lock নেয় → ch 16 এর contention


  NVMe:                  ৬৪K queue, প্রতিটায় ৬৪K entry
  core 0 ──▶ ┌────────┐
             │ queue0 │───▶┐
  core 1 ──▶ ┌────────┐    │
             │ queue1 │───▶├──▶ SSD controller
  core 2 ──▶ ┌────────┐    │    (ভিতরে অনেক channel)
             │ queue2 │───▶┘
  core 3 ──▶ ┌────────┐
             │ queue3 │───▶

  প্রতি core এর নিজের queue → কোনো lock নেই
  → chapter 7 এর MQMS, শুধু I/O এর দিকে

আপনার কাজের সাথে যোগ

এই স্তরটা সাধারণত অদৃশ্য, কিন্তু যখন দেখা দেয় তখন এভাবে:

  • iostat এর %util — NVMe তে এই সংখ্যাটা বিভ্রান্তিকর। এটা মাপে "কত সময় অন্তত একটা request চলছিল", কিন্তু NVMe একসাথে শত শত request চালাতে পারে। তাই %util = 100% মানে saturated নয়। দেখুন avgqu-sz (queue depth) আর await (latency)।
  • Queue depth — একটা NVMe থেকে সর্বোচ্চ throughput পেতে একসাথে অনেক request দরকার। একটা single-threaded synchronous read loop NVMe এর ১০% ও ব্যবহার করতে পারবে না। এই কারণেই io_uring আর parallel read এত গুরুত্বপূর্ণ।
  • Postgres এর effective_io_concurrency ঠিক এই সংখ্যাটা — সে কতগুলো concurrent prefetch পাঠাবে। HDD এর জন্য ১-২, NVMe এর জন্য ২০০+ অর্থপূর্ণ।

শেষ সারিটা লক্ষ করুন: একই datacenter এ একটা network round-trip একটা local NVMe read এর সমান। এটা একটা তুলনামূলকভাবে নতুন সত্য, আর এর ফলে অনেক ঐতিহাসিক সিদ্ধান্ত উল্টে গেছে — "network এ যাওয়ার চেয়ে disk পড়া ভালো" আর সর্বজনীনভাবে সত্য নয়। Chapter 28 আর 30 এ এটা ফিরে আসবে।

প্রশ্ন

  1. Polling → interrupt → আবার polling। এই চক্রটা কোনো নীতি বদলানোর ফল নয়, বরং একটা অনুপাত বদলানোর ফল। কোন দুটো সংখ্যার অনুপাত, আর কোন device এর জন্য সেটা কত?
  2. DMA engine physical address ব্যবহার করে, virtual নয়। এই একটা তথ্য থেকে দুটো আবশ্যকতা বের করুন — একটা correctness এর জন্য (chapter 11 এর সাথে সম্পর্কিত), আরেকটা নিরাপত্তার জন্য।
  3. MMIO তে volatile সঠিক কিন্তু thread synchronization এ ভুল। Chapter 14 এর বিশ্লেষণ ব্যবহার করে বলুন কেন — volatile ঠিক কোন সমস্যাটা সমাধান করে যা MMIO তে দরকার, আর কোনটা করে না যা thread এ দরকার?
  4. NVMe তে iostat এর %util = 100% মানে saturated নয়। কেন এই মাপকাঠিটা NVMe এর জন্য ভেঙে যায়, আর কোন দুটো সংখ্যা দেখা উচিত? (সূত্র: একটা queue বনাম ৬৪K queue।)
  5. একটা single-threaded synchronous read loop একটা NVMe এর ১০% ও ব্যবহার করতে পারে না। কেন? Chapter 19 এর io_uring কীভাবে এই নির্দিষ্ট সমস্যাটা সমাধান করে?
  6. একই datacenter এ network RTT (~৭৫µs) এখন local NVMe read (~৫০µs) এর সমান মাপে। এই সমতা কোন ঐতিহাসিক design সিদ্ধান্তগুলোকে প্রশ্নবিদ্ধ করে? অন্তত দুটো উদাহরণ দিন যেখানে "local disk সবসময় দ্রুত" অনুমানটা এখন ভুল।
