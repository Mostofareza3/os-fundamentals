Runtime টা OS এর client — যেখানে সব leak করে

আপনি OS এর সাথে সরাসরি কথা বলেন না। V8, JVM, Go runtime বা CPython মাঝখানে থাকে, আর আপনার প্রায় প্রতিটা production বিস্ময় হলো OS এর একটা mechanism runtime এর আচরণে leak করা। এই শেষ chapter এ সেই leak গুলো শ্রেণীবদ্ধ করব — আর ২৯টা chapter এর সব সূত্র মিলবে।

Chapter 1 এ বলেছিলাম OS আপনার program কে "সুপরিকল্পিত মিথ্যা" বলে। এই বইটা ছিল সেই মিথ্যাগুলোর গঠন নিয়ে। এখন শেষ প্রশ্ন: মিথ্যাটা কোথায় ফাঁস হয়?

আর সেটা সবসময় একই জায়গায় ফাঁস হয় — আপনার runtime আর OS এর সীমানায়।

Crux

আপনার runtime OS সম্পর্কে কিছু অনুমান করে। সেই অনুমানগুলো যখন ভুল হয় — container এ, চাপে, বা ভিন্ন hardware এ — তখন লক্ষণটা runtime এ দেখা যায় কিন্তু কারণটা OS এ। এই দূরত্বটা কীভাবে পার হবেন?

শ্রেণী ১ — Container-limit blindness

সবচেয়ে সাধারণ শ্রেণী, আর chapter 2 এ এর বীজ বপন করেছিলাম: container এর ভিতরে /proc host এর সত্য দেখায়। 

  Host: 64 core, 256 GB        Container: 2 core, 1 GB

  runtime যা দেখে:              বাস্তবতা:
  ─────────────────             ──────────
  nproc → 64                    cpu.max = 2
  /proc/meminfo → 256 GB        memory.max = 1 GB

  ফলাফল:
    Go:     GOMAXPROCS = 64 → ৬৪টা OS thread, ২ core এর quota
            → throttling (ch 7) + অকারণ context switch (ch 4)
    JVM:    ForkJoinPool = 63, GC thread = 64
            → heap sizing ও ভুল হতে পারে
    Node:   cluster.fork() যদি os.cpus() ধরে → ৬৪টা process
    nginx:  worker_processes auto → ৬৪
    Python: multiprocessing.cpu_count() → 64
bash 
# The fix, per runtime. All of them do the same thing:
# read the cgroup, not /proc.

# Go — inject the limit, or use the library
GOMAXPROCS=2                          # or:
# import _ "go.uber.org/automaxprocs"
GOMEMLIMIT=900MiB                     # soft limit, pressures GC

# JVM — cgroup-aware since JDK 10, but verify
java -XX:MaxRAMPercentage=70 -jar app.jar
java -XX:+PrintFlagsFinal -version | grep -E 'ActiveProcessor|MaxHeap'

# Node
NODE_OPTIONS=--max-old-space-size=700
UV_THREADPOOL_SIZE=8                  # ch 19 — libuv's pool

# Kubernetes: let the platform tell the runtime
env:
  - name: GOMAXPROCS
    valueFrom:
      resourceFieldRef: { resource: limits.cpu }
  - name: GOMEMLIMIT
    valueFrom:
      resourceFieldRef: { resource: limits.memory }

একটা মূল নীতি: runtime এর সীমা cgroup এর সীমার চেয়ে ছোট রাখতে হবে। JVM heap = container limit মানে নিশ্চিত OOM kill, কারণ heap এর বাইরেও metaspace, thread stack, JIT code cache, direct buffer — সব লাগে।

শ্রেণী ২ — RSS রিপোর্টিং

"আমাদের memory leak আছে" — এই সিদ্ধান্তটা প্রায়ই RSS দেখে নেওয়া হয়, আর প্রায়ই ভুল। কারণ তিনটে chapter এ ছড়ানো: 

  RSS বাড়ছে কিন্তু leak নেই — চারটে সম্ভাবনা:

  ১. Allocator memory ধরে রেখেছে  (ch 8)
     free() OS কে ফেরত দেয় না — পরের বার কাজে লাগবে
     → RSS চূড়ায় ওঠে, তারপর মালভূমি

  ২. MADV_FREE এর অস্পষ্টতা  (ch 10, 11)
     jemalloc/Go runtime page টা "চাইলে নাও" বলে রাখে
     → kernel না নেওয়া পর্যন্ত RSS এ গোনা হয়
     → আপাত leak, আসলে নয়

  ৩. Page cache  (ch 24)
     cgroup এ file page ও memory.current এ গোনা হয়
     → আপনার heap ছোট, তবু limit এ ধাক্কা

  ৪. Fragmentation  (ch 8)
     ১০০ MB live object ২০০ MB arena জুড়ে ছড়ানো
     → RSS ২০০ MB, "ব্যবহৃত" ১০০ MB

$ cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file|slab|sock) '

# glibc এর arena কমানো (ch 8) — container এ সাধারণ tuning

শ্রেণী ৩ — GC আর paging এর সংঘর্ষ

একটা বিশেষভাবে বিভ্রান্তিকর শ্রেণী, কারণ দুটো স্বাধীন ব্যবস্থা একে অন্যের বিরুদ্ধে কাজ করে। 

  GC ধরে নেয়: memory access সব সমান দামি

  কিন্তু chapter 11 বলে: swap এ থাকা page ~১০০০ গুণ ধীর

  সংঘর্ষ:

  ১. Memory চাপ বাড়ল → kernel reclaim শুরু করল
  ২. GC heap এর কিছু পুরনো page swap এ গেল
  ৃ. GC চলল — সে পুরো heap হাঁটে (mark phase)
  ৪. প্রতিটা swapped page এ একটা MAJOR FAULT
  ৫. GC pause ২ms থেকে ২০০০ms হয়ে গেল
  ৬. Request জমতে থাকল, আরও memory লাগল
  ৭. আরও swap → আরও ধীর GC → মৃত্যুর সর্পিল

  এই কারণেই বড় heap এর service এ swap বিপজ্জনক,
  আর এই কারণেই Kubernetes ঐতিহাসিকভাবে swap বন্ধ
  করতে বলত (ch 11 এ দেখেছি সেই নিষেধাজ্ঞা এখন
  শিথিল হয়েছে, কিন্তু GC-ভিত্তিক runtime এ
  যুক্তিটা এখনো বৈধ)।

  আরেকটা রূপ — THP (ch 10):
    GC heap এ ছোট ছোট object বদলায়
    → THP এ প্রতিটা COW ২ MB copy
    → Redis এর THP বন্ধ করার পরামর্শ একই কারণে

শ্রেণী ৪ — Blocking যা runtime জানে না

Chapter 19 এ দেখেছি runtime গুলো event loop বা netpoller দিয়ে blocking লুকায়। কিন্তু সব blocking লুকানো যায় না — আর যেটা যায় না, সেটাই সমস্যা।

Runtimeলুকায়লুকায় না
Node Network I/O (epoll) CPU-ভারী JS, sync API — event loop আটকে যায়
Go Network (netpoller), channel, sleep File I/O, cgo call — একটা OS thread সত্যিই block হয়
JVM (virtual thread) Network, most blocking I/O synchronized block, native call — carrier thread pin হয়
Python asyncio Network যেকোনো sync call — পুরো loop আটকায়

শ্রেণী ৫ — Cloud storage যা local disk এর ভান করে

Chapter 20-25 এ ধরে নিয়েছি disk টা মেশিনের ভিতরে। Cloud এ সেটা মিথ্যা, আর এই মিথ্যাটার একটা নির্দিষ্ট আকার আছে। 

  আপনার application যা দেখে: একটা block device
  আসলে যা আছে: একটা network service

  ┌──────────────────────────────────────────────┐
  │  Local NVMe        EBS gp3         EFS/NFS   │
  ├──────────────────────────────────────────────┤
  │  ~২০–৮০ µs        ~০.৫–২ ms      ~২–১০ ms    │  latency
  │  ~১০ লক্ষ IOPS    provisioned     provisioned│
  │  স্থির            burst credit!   throughput │
  │                                    mode      │
  └──────────────────────────────────────────────┘

  তিনটে ফাঁদ:

  ১. fsync এখন একটা network round-trip
     chapter 25 এর ~২০µs হয়ে গেল ~১ms
     → একটা fsync-ভারী database ৫০ গুণ ধীর
     → etcd/Postgres এ এটা সরাসরি throughput

  ২. Burst credit শেষ হওয়ার cliff

ভুল ধারণা

"Runtime টা OS কে abstract করে দেয়, তাই আমার OS জানার দরকার নেই — runtime এর documentation যথেষ্ট।"

Abstraction যখন কাজ করে, কথাটা সত্য — আর বেশিরভাগ সময় সেটা কাজ করে। সমস্যা হলো abstraction ব্যর্থ হলে লক্ষণটা runtime এ দেখা যায় কিন্তু কারণটা নিচে থাকে, আর তখন runtime এর documentation আপনাকে ভুল দিকে পাঠায়। 

লক্ষণ (runtime এ)              আসল কারণ (OS এ)
────────────────────────       ──────────────────────────
"GC pause ২ সেকেন্ড"            swap + major fault (ch 11)
"event loop lag বেশি"          thread pool মাত্র ৪ (ch 19)
"memory leak আছে"              allocator arena (ch 8)
                               বা MADV_FREE (ch 11)
"CPU ২০% কিন্তু ধীর"            cgroup throttling (ch 7)
"database মাঝে মাঝে ধীর"        LSM compaction (ch 27)
                               বা EBS burst শেষ (ch 30)
"fsync ৫০ গুণ ধীর হলো"          network storage (ch 25)

প্রতিটা সারিতে runtime এর profiler আপনাকে "কোথায় সময় যাচ্ছে" বলবে, কিন্তু "কেন" বলবে না। বাঁ দিকটা খুঁজে ডান দিকে পৌঁছানোই এই বইয়ের আসল উদ্দেশ্য ছিল।

        অনুমান করবেন না — মাপুন।
bash 
# A first-pass triage script — one number per layer
#!/bin/bash
PID=${1:?usage: triage.sh PID}
CG=/sys/fs/cgroup

echo "── CPU ──"
awk '{printf "runqueue wait: %.1f ms\n", $2/1e6}' /proc/$PID/schedstat
grep -E 'nr_throttled|throttled_usec' $CG/cpu.stat 2>/dev/null

echo "── Memory ──"
grep -E '^(Rss|Pss|Private_Dirty)' /proc/$PID/smaps_rollup
grep -E '^(anon|file) ' $CG/memory.stat 2>/dev/null
cat $CG/memory.pressure 2>/dev/null | head -1
awk '/pgmajfault/ {print "major faults:", $2}' /proc/vmstat

echo "── I/O ──"
grep -E 'read_bytes|write_bytes' /proc/$PID/io
grep -E '^(Dirty|Writeback):' /proc/meminfo

echo "── Threads ──"
echo "os threads: $(ls /proc/$PID/task | wc -l)"
grep ctxt /proc/$PID/status

শেষ কথা

এই বইটা OSTEP এর ভিত্তিতে, কিন্তু OSTEP এর চেয়ে ভিন্ন লক্ষ্যে: আপনি kernel লিখবেন না, কিন্তু আপনার code kernel এর উপর চলবে — আর যখন কিছু অদ্ভুত ঘটবে, আপনাকে জানতে হবে কোথায় তাকাতে হবে।

যা মনে রাখার মতো তা তিনটে বাক্যে: OS একটা resource manager যে illusion বিক্রি করে; প্রতিটা illusion এর একটা দাম আছে; আর সেই দাম মাপা যায়। বাকিটা বিস্তারিত — আর বিস্তারিত অংশ বদলায়, কিন্তু এই তিনটে বদলায় না।

শেষ প্রশ্ন

  1. Container-limit blindness এর সমাধান হলো cgroup পড়া, /proc নয়। কিন্তু কেন kernel শুরুতেই /proc/cpuinfo কে namespace-সচেতন করেনি? (সূত্র: কোন কোন জিনিস ভেঙে যেত, আর lxcfs কী করে?)
  2. RSS বাড়ছে — চারটে সম্ভাব্য কারণের মধ্যে কোনটা সত্যিকারের leak তা smaps_rollup এর কোন একটা field দিয়ে আলাদা করবেন, আর কেন সেটাই সঠিক field?
  3. GC আর swap এর মৃত্যুর সর্পিলটা ধাপে ধাপে বর্ণনা করুন। এখন বলুন GOMEMLIMIT (soft) আর memory.max (hard) এর মধ্যে কোনটা এই সর্পিল আটকাতে বেশি কার্যকর, আর কেন।
  4. একটা Go service এ ১২,০০০ goroutine কিন্তু ৫১৭টা OS thread। এটা কী বলছে, আর কোন দুটো জিনিস এই অবস্থা তৈরি করতে পারে? Chapter 19 এর netpoller কেন এখানে সাহায্য করছে না?
  5. EBS এ burst credit শেষ হওয়াটা একটা cliff, ধীরে অবনতি নয়। আপনার database ঘণ্টার পর ঘণ্টা ঠিক চলার পর হঠাৎ ভেঙে পড়ল। Chapter 25 এর fsync আর chapter 20 এর queue depth ব্যবহার করে লক্ষণগুলো পূর্বানুমান করুন, আর বলুন কোন metric আগে থেকে সতর্ক করত।
  6. স্তর-চিহ্নিতকরণের তালিকাটা ব্যবহার করে একটা পরিস্থিতি সমাধান করুন: আপনার API এর p50 ৫ms, p99 ১২০০ms। Application profiler কিছু দেখাচ্ছে না। উপর থেকে নিচে নেমে প্রতিটা স্তরে একটা নির্দিষ্ট সংখ্যা বলুন যা আপনি দেখবেন, আর সেটা কী মান হলে আপনি ওই স্তরে থামবেন।
