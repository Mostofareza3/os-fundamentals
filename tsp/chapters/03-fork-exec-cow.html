fork, exec, wait — আর COW এর ফাঁদ

একটা function যা দুবার return করে। একটা যা কখনো return করে না। এই অদ্ভুত জোড়াটাই UNIX এর সবচেয়ে সফল design সিদ্ধান্ত — আর এর ভিতরের copy-on-write mechanism টা না বুঝলে Redis এর memory spike বা threaded process এ fork এর deadlock কোনোটাই ব্যাখ্যা করা যায় না।

Chapter 2 এ দেখেছি process কী। এখন প্রশ্ন: নতুন process কীভাবে বানানো হয়? বেশিরভাগ ভাষায় থাকত একটা createProcess(program, args)। UNIX সেটা করেনি। বরং কাজটা দুটো আলাদা system call এ ভেঙেছে, আর সেই ভাঙাটাই shell, pipe, redirection — সবকিছু সম্ভব করেছে।

Crux

Process তৈরি আর নিয়ন্ত্রণের জন্য OS কোন interface দেবে? এমনভাবে যাতে ব্যবহার করা সহজ হয়, আবার শক্তিশালীও হয়?

fork() — যে call দুবার ফেরে

fork() সম্ভবত আপনার দেখা সবচেয়ে অদ্ভুত system call। এটা কোনো argument নেয় না, আর এর return statement একবার লেখা থাকলেও দুটো process এ ফেরে।

c 
/* p1.c — the strangest call you will make */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());

    int rc = fork();
    if (rc < 0) {                 /* fork failed */
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {         /* child: fork() returned 0 */
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {                      /* parent: fork() returned child's pid */
        printf("hello, I am parent of %d (pid:%d)\n", rc, (int) getpid());
    }
    return 0;
}
$ ./p1
hello world (pid:29146)
hello, I am parent of 29147 (pid:29146)
hello, I am child (pid:29147)

লক্ষ করুন hello world একবারই ছাপা হয়েছে। Child main() থেকে শুরু করে না — সে জন্মায় ঠিক সেই জায়গায়, যেন সে নিজেই fork() ডেকেছিল। তার PC, register, stack, address space — সব parent এর মতো।

একটাই পার্থক্য: return value। Parent পায় child এর PID, child পায় 0। এই একটা সংখ্যার ভিত্তিতেই আপনি দুটো path লেখেন। 

              ./p1 চলছে (pid 29146)
                      │
                 printf("hello world")
                      │
                   fork()
                      │
          ┌───────────┴───────────┐
          │                       │
    parent (29146)          child (29147)
    rc = 29147              rc = 0
          │                       │
    else branch             if (rc==0) branch
          │                       │
   "I am parent of 29147"   "I am child"

একটা call, দুটো return। কোন branch চলবে তা rc এর মান ঠিক করে।

ভুল ধারণা

"fork() parent এর পুরো memory copy করে, তাই ২GB এর process fork করলে ২GB লাগবে।"

OSTEP নিজেই লেখে child পায় "its own copy of the address space"। Interface এর দিক থেকে কথাটা সত্য — child যা লেখে parent দেখে না। কিন্তু implementation হিসেবে এটা বিভ্রান্তিকর, আর এই ভুল ছবিটা তিন ধরনের production সমস্যার মূলে।

বাস্তবে kernel কিছুই copy করে না। সে দুটো process কেই একই physical page এ point করিয়ে দেয়, আর সব page কে read-only চিহ্নিত করে। এর নাম COW (Copy-on-Write — page গুলো ভাগ করে রাখা হয়, আর কেউ লিখতে গেলে তখনই সেই page টার copy বানানো হয়)। কেউ লিখতে গেলে hardware একটা protection fault তোলে, kernel তখন ওই একটা page copy করে, দুজনকে আলাদা করে দেয়।

মানে fork() এর খরচ address space এর আকারের সাথে বাড়ে না — বাড়ে page table এর আকারের সাথে (আর লেখার পরিমাণের সাথে)। ২GB process fork করা তাই সস্তা — যদি কেউ বেশি না লেখে।

COW — কীভাবে কাজ করে

  fork() এর ঠিক পরে — কোনো copy হয়নি:

    parent PTE            physical            child PTE
    ┌──────────┐          ┌────────┐          ┌──────────┐
    │ page A   │────────▶ │ frame  │ ◀────────│ page A   │
    │ RO, COW  │          │   7a   │          │ RO, COW  │
    └──────────┘          └────────┘          └──────────┘
                        refcount = 2

  child লিখল page A তে:

    1. CPU write করতে গেল → PTE read-only → protection fault
    2. kernel দেখল page টা COW-চিহ্নিত, refcount > 1
    3. নতুন frame allocate করল, বিষয়বস্তু copy করল
    4. child এর PTE কে নতুন frame এ, read-write করে দিল
    5. parent এর refcount 1 হলো → তার PTE ও read-write হলো

    parent PTE            physical            child PTE
    ┌──────────┐          ┌────────┐          ┌──────────┐
    │ page A   │────────▶ │ frame  │          │ page A   │
    │ RW       │          │   7a   │          │ RW       │
    └──────────┘          └────────┘          └──────┬───┘
                          ┌────────┐                 │
                          │ frame  │ ◀───────────────┘
                          │   c3   │  (copy)
                          └────────┘

COW: fault না হওয়া পর্যন্ত কোনো copy নেই। খরচটা লেখার সময়ে সরে গেছে।

এখানে একটা সূক্ষ্ম কিন্তু গুরুত্বপূর্ণ কথা: fault টা পড়ার সময় হয় না, লেখার সময় হয়। তাই যে page গুলো কেউ কখনো লেখে না (যেমন program এর code) সেগুলো চিরকাল ভাগ করা থাকে। এই কারণেই একই binary এর ১০০টা copy চললেও code এর জন্য RAM একবারই লাগে — chapter 1 এ যে ভুল ধারণাটা দেখেছিলাম ("প্রতিটা process এর আলাদা physical memory"), তার উত্তর এটাই।

আপনার কাজের সাথে যোগ

Redis BGSAVE — Redis যখন disk এ snapshot লেখে, সে fork() করে child কে লিখতে দেয়। ২GB dataset হলেও fork তাৎক্ষণিক, কারণ COW। কিন্তু snapshot চলার সময় যদি আপনার application প্রচুর key লিখতে থাকে, প্রতিটা লেখা একটা page কে আলাদা করে দেয় — আর memory ব্যবহার বাড়তে থাকে, সবচেয়ে খারাপ ক্ষেত্রে দ্বিগুণ। এই কারণেই Redis এর documentation বলে snapshot এর সময় memory headroom রাখতে, আর এই কারণেই vm.overcommit_memory=1 এর পরামর্শ দেওয়া হয়।

Postgres প্রতিটা client connection এর জন্য একটা নতুন backend process fork করে। COW না থাকলে এই model অচল হতো।

Git এর সাথেও ধারণাগত মিল আছে: Git ও content ভাগ করে রাখে আর পরিবর্তন হলে নতুন object লেখে। একই "যতক্ষণ না বদলাচ্ছে, ভাগ করে রাখো" নীতি।

wait() — অনিশ্চয়তা দূর করা

উপরের p1 এর output অনির্ধারিত — parent আগে ছাপতে পারে, child ও পারে। কে আগে চলবে তা scheduler ঠিক করে, আর সেটা আপনার নিয়ন্ত্রণে নেই: 

$ ./p1
hello world (pid:29146)
hello, I am child (pid:29147)          ←  এবার child আগে
hello, I am parent of 29147 (pid:29146)

wait() যোগ করলে ক্রম নিশ্চিত হয়:

c 
/* p2.c — parent waits for the child to finish */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());

    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {
        int wc = wait(NULL);      /* blocks until a child exits */
        printf("hello, I am parent of %d (wc:%d) (pid:%d)\n",
               rc, wc, (int) getpid());
    }
    return 0;
}
$ ./p2
hello world (pid:29266)
hello, I am child (pid:29267)
hello, I am parent of 29267 (wc:29267) (pid:29266)

এখন child সবসময় আগে ছাপবে। কেন? দুটো সম্ভাবনা, দুটোতেই একই ফল: child আগে চললে সে ছেপে বেরিয়ে যায়। Parent আগে চললে সে সাথে সাথে wait() এ গিয়ে BLOCKED হয় — chapter 2 এর state machine টা মনে করুন — আর child শেষ না হওয়া পর্যন্ত ফেরে না।

wait() শুধু ক্রম ঠিক করে না, সে child এর exit status সংগ্রহ করে আর zombie টা পরিষ্কার করে। Chapter 2 এ দেখেছি wait() না করলে zombie জমে। এখানে সেটাই API এর দিক থেকে।

c 
/* Reading what actually happened to the child */
int status;
pid_t p = waitpid(rc, &status, 0);

if (WIFEXITED(status)) {
    printf("exited normally, code %d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("killed by signal %d\n", WTERMSIG(status));
}

এই পার্থক্যটা কাজে লাগে: shell script এ exit code 137 দেখলে সেটা 128 + 9 — অর্থাৎ SIGKILL, সাধারণত OOM killer। আর 143 মানে 128 + 15, অর্থাৎ SIGTERM — Docker এর graceful shutdown। Container কেন মরল তা বোঝার প্রথম সূত্র এটাই।

exec() — যে call ফেরে না

fork() একই program এর copy বানায়। কিন্তু আপনি তো অন্য program চালাতে চান। সেটা exec() এর কাজ।

c 
/* p3.c — fork, then have the child become a different program */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());

    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {
        printf("hello, I am child (pid:%d)\n", (int) getpid());

        char *myargs[3];
        myargs[0] = strdup("wc");      /* program: word count */
        myargs[1] = strdup("p3.c");    /* argument: the file   */
        myargs[2] = NULL;              /* array terminator     */
        execvp(myargs[0], myargs);

        printf("this should never print\n");   /* exec does not return */
    } else {
        int wc = wait(NULL);
        printf("hello, I am parent of %d (wc:%d) (pid:%d)\n",
               rc, wc, (int) getpid());
    }
    return 0;
}
$ ./p3
hello world (pid:29383)
hello, I am child (pid:29384)
      29     107    1030 p3.c          ←  wc এর output
hello, I am parent of 29384 (wc:29384) (pid:29383)

exec() নতুন process বানায় না। সে চলমান process টাকেই অন্য program এ রূপান্তরিত করে: নতুন executable এর code আর static data এনে পুরনোটার উপর লিখে দেয়, heap আর stack নতুন করে সাজায়, তারপর সেখান থেকে চালাতে শুরু করে।

তাই exec() সফল হলে কখনো ফেরে না — ফেরার জায়গাটাই আর নেই, ওই code overwrite হয়ে গেছে। নিচের printf কখনো চলে না। exec() ফিরলে মানেই সে ব্যর্থ হয়েছে, আর তখন errno দেখা দরকার। 

  fork()                          exec()
  ──────                          ──────
  একটা process → দুটো process     একটা process → একটাই process
  code একই থাকে                   code বদলে যায়
  দুবার ফেরে                      ফেরেই না (সফল হলে)
  PID নতুন হয় (child এর)          PID একই থাকে
  fd খোলা থাকে                    fd খোলা থাকে (CLOEXEC ছাড়া)
ভুল ধারণা

"exec() এর পরে process টা নতুন, তাই খোলা file গুলো বন্ধ হয়ে যায়।"

না, আর এটাই redirection কাজ করার কারণ। exec() address space বদলায়, কিন্তু file descriptor table অটুট রাখে। Chapter 2 এ বলেছিলাম খোলা file process state এর অংশ — এখানে দেখা যাচ্ছে সেই অংশটা exec() পার হয়ে টিকে থাকে।

এটা কখনো অনিচ্ছাকৃত সমস্যাও করে: আপনার server একটা socket খুলে রেখে একটা child process spawn করল; child সেই socket টাও পেয়ে গেল। Child বেঁচে থাকলে port টা আটকে থাকবে, যদিও server মরে গেছে। সমাধান: open() এ O_CLOEXEC flag, বা fcntl(fd, F_SETFD, FD_CLOEXEC) — তাহলে exec() এর সময় fd টা নিজে বন্ধ হয়ে যায়। Node এ child process spawn করলে এটা default এ ঠিক করা থাকে।

কেন দুটো call? — shell এর উত্তর

এখন আসল প্রশ্ন: এত অদ্ভুত interface কেন? একটা spawn(program, args) তো সহজ হতো।

উত্তর: fork আর exec এর মাঝখানের ফাঁকটাই। ওই ফাঁকে child process টা বেঁচে আছে, কিন্তু নতুন program টা এখনো চালু হয়নি। ওই মুহূর্তে আপনি child এর পরিবেশ বদলে দিতে পারেন — আর নতুন program কিছুই জানবে না।

Shell পুরোপুরি এই ফাঁকের উপর দাঁড়িয়ে। Shell নিজে একটা সাধারণ user program: সে prompt দেখায়, আপনার লেখা পড়ে, executable খুঁজে বের করে, fork() করে, child এ exec() করে, আর wait() দিয়ে অপেক্ষা করে। তারপর আবার prompt।

Redirection ঠিক এভাবে কাজ করে:

$ wc p3.c > newfile.txt
c 
/* p4.c — how the shell implements "> newfile.txt" */
int rc = fork();
if (rc == 0) {
    /* We are in the child, BEFORE exec. Rewire stdout. */
    close(STDOUT_FILENO);
    open("./newfile.txt", O_CREAT | O_WRONLY | O_TRUNC, S_IRWXU);

    /* Now fd 1 points at the file, not the terminal. */
    char *myargs[3];
    myargs[0] = strdup("wc");
    myargs[1] = strdup("p3.c");
    myargs[2] = NULL;
    execvp(myargs[0], myargs);   /* wc has no idea anything changed */
}

কৌশলটা fd এর একটা নিয়মের উপর নির্ভর করে: UNIX সবসময় সবচেয়ে ছোট খালি fd নম্বর দেয়। তাই fd 1 বন্ধ করে সাথে সাথে open() করলে নতুন file টাই fd 1 পায়। wc যখন চালু হয়, সে fd 1 এ লেখে — যেমন সবসময় লেখে — কিন্তু সেটা এখন terminal নয়, file।

wc এর code এ redirection নিয়ে একটা লাইনও নেই। সে জানেই না। এটাই ভালো design এর চিহ্ন: shell একটা মেকানিজম পেয়েছে যা প্রতিটা program এ কাজ করে, কারো সহযোগিতা ছাড়াই। 

  সাধারণ অবস্থা:                redirection এর পর:

  fd 0 ──▶ terminal              fd 0 ──▶ terminal
  fd 1 ──▶ terminal              fd 1 ──▶ newfile.txt
  fd 2 ──▶ terminal              fd 2 ──▶ terminal

  pipe (wc p3.c | grep 29):

  ┌─────────┐ fd 1      fd 0 ┌─────────┐
  │   wc    │────▶ pipe ────▶│  grep   │
  └─────────┘                └─────────┘
  shell দুটো fork করে, pipe() দিয়ে জোড়া লাগায়,
  dup2() দিয়ে fd বসায়, তারপর দুটোতেই exec()

Pipe একই নীতির সম্প্রসারণ। pipe() দুটো fd দেয় — একটা পড়ার, একটা লেখার। Shell প্রথম program এর stdout কে pipe এর লেখার প্রান্তে আর দ্বিতীয়টার stdin কে পড়ার প্রান্তে বসায়। এভাবেই grep foo file.txt | wc -l কাজ করে, আর এভাবেই UNIX এর "ছোট ছোট program জোড়া লাগাও" দর্শনটা সম্ভব হয়েছে।

Design সিদ্ধান্ত

Lampson এর একটা কথা আছে: "Get it right. Neither abstraction nor simplicity is a substitute for getting it right." Process তৈরির API অনেকভাবে বানানো যেত — কিন্তু fork() আর exec() এর এই জোড়াটা সরল এবং অসম্ভব শক্তিশালী। UNIX এর নকশাকাররা এখানে ঠিক কাজটা করেছিলেন।

Threaded process এ fork — যেখানে সব ভাঙে

এখন সবচেয়ে বিপজ্জনক অংশ, যেটা OSTEP এ নেই কিন্তু production এ নিয়মিত মানুষকে কাটে।

fork() address space পুরোটা নিয়ে যায় — সব memory, সব lock এর অবস্থা সহ। কিন্তু শুধু যে thread টা fork() ডেকেছে সেটাই child এ বাঁচে। বাকি thread গুলো child এ অস্তিত্বহীন।

ফলাফল ভয়ংকর:

  Parent (multi-threaded):

    thread A ──── malloc() ডাকল, arena lock ধরল
    thread B ──── fork() ডাকল  ◀── ঠিক এই মুহূর্তে
    thread C ──── অন্য কাজ

  Child (fork এর পর):

    thread B ──── বেঁচে আছে
    thread A ──── নেই!  কিন্তু তার ধরা lock টা
                        memory তে "locked" অবস্থায় আছে
    thread C ──── নেই

  এখন child যদি malloc() ডাকে →
    lock টা locked দেখাচ্ছে →
    যে thread টা খুলবে সে অস্তিত্বহীন →
    চিরকালের deadlock

Lock টা ধরে আছে "কেউ না" — তাই কখনো খুলবে না।

এই কারণেই POSIX বলে: fork() এর পর child এ শুধু async-signal-safe function ডাকা যাবে, যতক্ষণ exec() না করছেন। malloc(), printf(), বেশিরভাগ library call — কোনোটাই সেই তালিকায় নেই।

glibc এর malloc arena deadlock এই শ্রেণীর সবচেয়ে পরিচিত উদাহরণ। আর এই কারণেই আধুনিক পরামর্শ হলো: threaded program এ fork() করলে সাথে সাথে exec() করুন, নইলে posix_spawn() ব্যবহার করুন — যেটা এই ফাঁদগুলো এড়িয়ে একই কাজ করে।

আপনার কাজের সাথে যোগ

Node.js এ আপনি কখনো সরাসরি fork() করেন না — child_process.spawn() ভিতরে posix_spawn() বা fork+exec করে, আর libuv এর নিজের thread pool থাকায় Node একটা multi-threaded process। তাই cluster.fork() নামটা বিভ্রান্তিকর: সেটা আসলে নতুন process spawn করে, POSIX fork() নয়।

Python এ এই সমস্যাটা এতই বাস্তব যে ৩.১৪ থেকে multiprocessing এর default start method Linux এ fork থেকে forkserver এ সরানো হয়েছে, আর threaded process এ os.fork() এখন DeprecationWarning দেয়।

JVM সহজাতভাবে multi-threaded, তাই Runtime.exec() ভিতরে vfork/ posix_spawn ব্যবহার করে — কখনো plain fork করে কাজ চালিয়ে যায় না।

বাকি নিয়ন্ত্রণ — signal

fork(), exec(), wait() এর বাইরে process নিয়ন্ত্রণের প্রধান উপায় signal। kill() system call দিয়ে একটা process কে signal পাঠানো হয়:

Signalকী করেধরা যায়?কোথায় দেখবেন
SIGTERM (15)ভদ্রভাবে থামতে বলাহ্যাঁDocker stop, k8s pod delete
SIGKILL (9)সাথে সাথে মেরে ফেলানাOOM killer, kill -9
SIGINT (2)Interruptহ্যাঁCtrl+C
SIGSTOP (19)থামিয়ে রাখানাCtrl+Z
SIGSEGV (11)অবৈধ memory accessহ্যাঁSegmentation fault

SIGKILL আর SIGSTOP ধরা যায় না — এটা ইচ্ছাকৃত। নইলে একটা দুষ্ট process সব signal উপেক্ষা করে অমর হয়ে যেত। Kernel নিজে এই দুটো কার্যকর করে, process এর সহযোগিতা ছাড়াই।

Container এর shutdown এই ক্রমেই হয়: Docker প্রথমে SIGTERM পাঠায়, ১০ সেকেন্ড (default) অপেক্ষা করে, তারপর SIGKILL। আপনার application যদি SIGTERM handle না করে — connection বন্ধ না করে, in-flight request শেষ না করে — তাহলে প্রতিবার deploy এ request হারাবেন। Chapter 29 এ এটা পুরো container lifecycle এর সাথে দেখব।

প্রশ্ন

  1. একটা process ১০GB heap ব্যবহার করছে। সে fork() করল, আর child সাথে সাথে exec() করল। কত memory copy হলো, আর কেন? এখন ধরুন child exec() না করে ১০ মিনিট ধরে heap এর অর্ধেক জুড়ে লিখল — তখন?
  2. Shell এ cat file.txt | grep foo > out.txt চালালে shell কতবার fork() করে, কতবার exec() করে, আর কোন fd গুলো কোথায় বসায়? fork আর exec এর মাঝখানের ফাঁক ছাড়া এটা করা যেত কি?
  3. exec() সফল হলে ফেরে না। তাহলে নিচের code টায় কী সমস্যা, আর ঠিক করতে কী লিখতেন? 
    execvp(prog, args);
printf("started %s\n", prog);
  4. আপনার Node server একটা log rotation script spawn করে। কিছুদিন পর দেখলেন server restart করলেও পুরনো port টা EADDRINUSE দিচ্ছে, যদিও server process মরে গেছে। কী ঘটেছে, আর কোন flag দিয়ে ঠেকাতেন?
  5. Redis BGSAVE চলার সময় আপনার monitoring এ RSS প্রায় দ্বিগুণ হয়ে গেল, তারপর নেমে এল। এটা memory leak, নাকি স্বাভাবিক? আপনার উত্তরে COW এর কোন ধাপটা ব্যবহার করবেন, আর কোন পরিস্থিতিতে এটা সত্যিই OOM ঘটাতে পারে?
  6. একটা multi-threaded program এ thread A প্রতি সেকেন্ডে malloc() করছে, আর thread B প্রতি মিনিটে fork() করে child এ একটা log লাইন printf() করছে। Program টা সপ্তাহে একবার আটকে যায়, কোনো নিয়ম ছাড়াই। কারণ ব্যাখ্যা করুন, আর বলুন কেন এটা test এ ধরা পড়ে না।
