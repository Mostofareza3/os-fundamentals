Event loop — epoll, io_uring, আর দুই স্তরের scheduler

Thread ছাড়াই concurrency — একটা thread, হাজারো connection। এটাই Node আর nginx এর স্থাপত্য। OSTEP এখানে select() শেখায়, যেটা ২০২৬ এ অচল; তাই এই chapter টা source এর চেয়ে অনেক দূর যায়।

Chapter 12 এ বলেছিলাম thread দুটো কারণে ব্যবহার হয় — parallelism আর latency hiding। দ্বিতীয়টার জন্য thread প্রায়ই ভুল হাতিয়ার, আর এই chapter এ কেন তা দেখব।

Crux

হাজারো connection একসাথে সামলাতে হবে, কিন্তু প্রতিটার জন্য একটা thread মানে অসহনীয় খরচ (chapter 12 এর stack, chapter 4 এর context switch)। Thread ছাড়া concurrency কীভাবে?

Event loop — মূল ধারণা

ধারণাটা নির্মমভাবে সরল: একটা thread, একটা loop। "কোন connection এ কাজ আছে?" জিজ্ঞেস করো, যেগুলোতে আছে সেগুলো সামলাও, আবার জিজ্ঞেস করো।

c 
/* The whole architecture, in five lines */
while (1) {
    events = wait_for_events();        /* blocks until something is ready */
    for (e in events) {
        process_event(e);              /* must NOT block */
    }
}

এর একটা চমকপ্রদ পরিণতি আছে: কোনো lock লাগে না। একটাই thread, তাই দুটো handler কখনো একসাথে চলে না — chapter 12–18 এর পুরো সমস্যাটা অদৃশ্য।

কিন্তু একটা কঠোর শর্ত আছে, আর সেটাই এই স্থাপত্যের দুর্বলতা: কোনো handler কখনো block করতে পারবে না। একটা handler যদি আটকে যায়, পুরো loop আটকে যায় — সব connection এর জন্য।

OSTEP এর উত্তর — select()

c 
/* select() — what OSTEP teaches. Correct, and obsolete
   for anything beyond a few dozen descriptors. */
#include <sys/select.h>

int main(void) {
    while (1) {
        fd_set readfds;
        FD_ZERO(&readfds);

        int max = 0;
        for (int fd = 0; fd < MAXFD; fd++) {
            if (is_active(fd)) {
                FD_SET(fd, &readfds);      /* rebuild the set every time */
                if (fd > max) max = fd;
            }
        }

        select(max + 1, &readfds, NULL, NULL, NULL);

        for (int fd = 0; fd <= max; fd++) {
            if (FD_ISSET(fd, &readfds))    /* scan all of them again */
                process(fd);
        }
    }
}

এটা কাজ করে, কিন্তু তিনটে মৌলিক সমস্যা আছে: 

  ১. প্রতিবার পুরো set আবার বানাতে হয়
     10,000 connection → প্রতি iteration এ 10,000 FD_SET

  ২. kernel প্রতিবার পুরো set scan করে
     O(n) — যদিও হয়তো মাত্র 3টা fd ready

  ৩. ফেরার পর আপনাকেও পুরোটা scan করতে হয়
     "কোনগুলো ready?" জানতে 10,000 বার FD_ISSET

  মোট: প্রতি iteration এ O(n), n = মোট connection
       কাজ হয়েছে হয়তো 3টায়, খরচ 10,000 এর।

  আর FD_SETSIZE সাধারণত 1024 — তার বেশি fd এ
  select() ব্যবহার করা অনিরাপদ (buffer overflow)।
যেখানে source টা পুরনো — সবচেয়ে বড় ব্যবহারিক ফাঁক

OSTEP এই chapter এ শুধু select() আর poll() শেখায়। আমি পুরো বইয়ের text এ গুনে দেখেছি: epoll শব্দটা একবারও নেই, io_uring ও নেই।

এটা শুধু একটা অনুপস্থিতি নয়, বরং বিভ্রান্তিকর — কারণ এই chapter টা ঠিক সেই স্থাপত্য শেখাচ্ছে যা Node.js আর nginx ব্যবহার করে, কিন্তু যে API দিয়ে শেখাচ্ছে সেটা ওরা কেউ ব্যবহার করে না।

libuv (Node এর ভিত) চলে epoll (Linux), kqueue (macOS/BSD), IOCP (Windows) এর উপর। আপনি প্রতিদিন যে event loop এর উপর code লেখেন, তার আসল mechanism টা source এ অনুপস্থিত।

epoll — O(1) এ পৌঁছানো

epoll এর মূল অন্তর্দৃষ্টি: আগ্রহের তালিকাটা kernel এ রাখো। প্রতিবার পাঠানোর দরকার নেই; একবার বলো, তারপর শুধু "কী ঘটেছে" জিজ্ঞেস করো। 

  select():                        epoll():

  প্রতি iteration এ:               একবার (setup):
    পুরো set kernel এ পাঠাও          epoll_ctl(ADD) প্রতি fd
    kernel পুরোটা scan করে
    পুরোটা ফেরত আসে                প্রতি iteration এ:
    আপনি পুরোটা scan করেন            epoll_wait() →
                                     শুধু READY গুলোর তালিকা
  O(n) per iteration               O(ready) per iteration

  10,000 connection, 3টা ready:
    select: ~10,000 একক কাজ          epoll: 3টা একক কাজ
c 
/* epoll — the actual mechanism behind every Linux event loop */
#include <sys/epoll.h>

int ep = epoll_create1(0);

/* Tell the kernel once, per fd */
struct epoll_event ev = {
    .events = EPOLLIN | EPOLLET,   /* readable, edge-triggered */
    .data.fd = conn_fd
};
epoll_ctl(ep, EPOLL_CTL_ADD, conn_fd, &ev);

/* Then loop, getting back only what is ready */
struct epoll_event events[MAX_EVENTS];
while (1) {
    int n = epoll_wait(ep, events, MAX_EVENTS, -1);
    for (int i = 0; i < n; i++) {          /* n = ready count, not total */
        int fd = events[i].data.fd;
        if (events[i].events & EPOLLIN)
            handle_readable(fd);
    }
}

একটা গুরুত্বপূর্ণ পছন্দ আছে — EPOLLET:

 Level-triggered (default)Edge-triggered (EPOLLET)
কখন জানায় যতক্ষণ data আছে, প্রতিবার শুধু অবস্থা বদলালে
আপনার দায়িত্ব একবারে কিছুটা পড়লেও চলবে EAGAIN পাওয়া পর্যন্ত পড়তে হবে
ভুল করলে অতিরিক্ত wake-up (অপচয়) connection আটকে যায় — বাকি data এর সংকেত আর আসবে না

Chapter 4 এ level বনাম edge triggered interrupt নিয়ে বলেছিলাম — এটা ঠিক সেই একই ধারণা, software স্তরে। আর একই ফাঁদ: edge-triggered এ সংকেত একবারই আসে, তাই না শুনলে হারিয়ে যায়।

ভুল ধারণা

"Edge-triggered দ্রুত, তাই সেটাই ব্যবহার করা উচিত।"

Edge-triggered কম wake-up দেয়, কিন্তু একটা কঠোর চুক্তি আরোপ করে: socket সম্পূর্ণ নিষ্কাশন করতে হবে। 

/* ভুল — edge-triggered এ এটা connection আটকে দেবে */
n = read(fd, buf, 1024);
process(buf, n);
/* 4KB এসেছিল, আপনি 1KB পড়লেন।
   বাকি 3KB এর জন্য নতুন event আসবে না — অবস্থা বদলায়নি! */

/* ঠিক — EAGAIN পর্যন্ত পড়ুন */
for (;;) {
    n = read(fd, buf, sizeof(buf));
    if (n > 0) { process(buf, n); continue; }
    if (n == -1 && errno == EAGAIN) break;   /* নিষ্কাশিত */
    if (n == 0) { close_conn(fd); break; }    /* peer বন্ধ করল */
    if (n == -1 && errno == EINTR) continue;
    /* real error */
    close_conn(fd); break;
}

এই কারণেই libuv আর অনেক production server level-triggered ব্যবহার করে — একটু বেশি wake-up এর দাম দিয়ে একটা গোটা শ্রেণীর bug এড়ানো যায়। Edge-triggered এর লাভটা বাস্তবে ছোট, আর ভুলের দাম বড়।

অ-blocking হওয়াটাই সব

Event loop এর চুক্তি: কোনো handler block করবে না। কিন্তু সব কাজ non-blocking করা যায় না — আর এখানেই আসল সমস্যা। 

  Non-blocking করা যায় (O_NONBLOCK + epoll):
    ✓ socket read/write
    ✓ pipe, timer, signal (signalfd, timerfd)
    ✓ eventfd (নিজের জাগানোর ব্যবস্থা)

  করা যায় NA (ঐতিহাসিকভাবে):
    ✗ regular FILE এর read/write  ← O_NONBLOCK উপেক্ষিত হয়!
    ✗ getaddrinfo() — DNS lookup
    ✗ stat(), open(), fsync()
    ✗ CPU-ভারী গণনা (স্বভাবতই)

  ওই দ্বিতীয় তালিকাটাই libuv কে একটা
  thread pool রাখতে বাধ্য করেছে।

এটা একটা গুরুত্বপূর্ণ আর কম-জানা সত্য: Linux এ regular file এ O_NONBLOCK কার্যত অর্থহীন। Disk read প্রস্তুত না থাকলে syscall টা ঘুমিয়ে পড়ে, আর epoll আপনাকে সাহায্য করতে পারে না। তাই file I/O এর জন্য একটা আলাদা ব্যবস্থা দরকার।

ওই "মাত্র ৪" টাই একটা বাস্তব bottleneck, আর এটা ব্যাখ্যা করে একটা প্রায়ই-বিভ্রান্তিকর আচরণ:

javascript 
// Five concurrent file reads. Four run; the fifth WAITS —
// not because of disk, but because the pool has 4 slots.
const fs = require('fs/promises');
await Promise.all([1,2,3,4,5].map(i => fs.readFile(`f${i}.dat`)));

// Same for DNS and crypto — they share the same pool:
const dns = require('dns/promises');
await dns.lookup('example.com');       // uses a pool thread
crypto.pbkdf2(...);                     // uses a pool thread too

// The fix, when file/DNS/crypto-heavy:
process.env.UV_THREADPOOL_SIZE = 16;   // MUST be set before any I/O
// (or export it in the environment — changing it later has no effect)
আপনার কাজের সাথে যোগ

Node এর event loop এ ধীর হওয়ার দুটো সম্পূর্ণ আলাদা কারণ আছে, আর দুটোর সমাধান আলাদা:

  • Event loop blocked — আপনার JS এ একটা synchronous কাজ (বড় JSON.parse, একটা tight loop, fs.readFileSync)। Chapter 5 এর convoy effect, শুধু event loop এ। সমাধান: worker_threads। 
    # event loop কতটা আটকাচ্ছে তা মাপুন
$ node --perf-basic-prof app.js
# বা code এ:
#   const { monitorEventLoopDelay } = require('perf_hooks');
#   const h = monitorEventLoopDelay(); h.enable();
#   later: h.mean, h.max  ← p99 latency এর সরাসরি কারণ
  • Thread pool saturated — event loop ঠিক আছে, কিন্তু file/DNS/crypto কাজ ৪টা slot এর জন্য লাইনে দাঁড়িয়ে। সমাধান: UV_THREADPOOL_SIZE।

দুটোর লক্ষণ একই ("API ধীর"), কিন্তু কারণ আর সমাধান সম্পূর্ণ আলাদা — আর monitorEventLoopDelay দিয়ে আপনি আলাদা করতে পারেন।

io_uring — syscall এর খরচটাই কমানো

epoll "কী ready" জানায়, কিন্তু আপনাকে তারপর read() করতে হয় — আরেকটা syscall। উচ্চ throughput এ syscall এর সংখ্যাটাই bottleneck হয়ে ওঠে, বিশেষত chapter 4 এ দেখা KPTI এর পর।

io_uring (Linux 5.1+, ২০১৯) এর সমাধান: kernel আর userspace এর মধ্যে দুটো shared ring buffer। 

  ┌─────────────── userspace ────────────────┐
  │                                          │
  │  SQ (Submission Queue)  ─── আপনি লেখেন   │
  │  ┌────┬────┬────┬────┐                   │
  │  │ op │ op │ op │ op │  "এই কাজগুলো করো" │
  │  └────┴────┴────┴────┘                   │
  │         │                                │
  │         │  mmap করা shared memory —      │
  │         │  কোনো copy নেই                 │
  │         ▼                                │
  │  CQ (Completion Queue) ─── kernel লেখে   │
  │  ┌────┬────┬────┬────┐                   │
  │  │ res│ res│ res│ res│  "এগুলো হয়ে গেছে" │
  │  └────┴────┴────┴────┘                   │
  └──────────────────────────────────────────┘

  লাভ:
  ১. একটা syscall এ শত শত operation জমা দেওয়া
  ২. SQPOLL mode এ kernel thread নিজেই ring দেখে
     → শূন্য syscall
  ৩. FILE I/O সত্যিকারের async — epoll যা পারে না
  ৪. অনেক operation একসাথে chain করা যায়
c 
/* io_uring with liburing — submit many, then reap many */
#include <liburing.h>

struct io_uring ring;
io_uring_queue_init(256, &ring, 0);

/* Queue up several reads — no syscall yet */
for (int i = 0; i < n; i++) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
    io_uring_prep_read(sqe, fds[i], bufs[i], SIZE, 0);
    io_uring_sqe_set_data(sqe, &ctx[i]);
}

/* ONE syscall submits all of them */
io_uring_submit(&ring);

/* Reap completions */
struct io_uring_cqe *cqe;
unsigned head;
int count = 0;
io_uring_for_each_cqe(&ring, head, cqe) {
    void *ctx = io_uring_cqe_get_data(cqe);
    handle_completion(ctx, cqe->res);
    count++;
}
io_uring_cq_advance(&ring, count);

দুই স্তরের scheduler — Go এর উত্তর

Event loop এর একটা অস্বস্তি আছে: আপনার code টা callback বা async/await এ ভেঙে যায়, আর OSTEP যেটাকে "manual stack management" বলে — প্রতিটা অপেক্ষার বিন্দুতে অবস্থা হাতে সংরক্ষণ করতে হয়।

Go একটা ভিন্ন পথ নিয়েছে: event loop টা লুকিয়ে ফেলো। আপনি blocking code লেখেন, runtime নিচে event loop চালায়। 

  Go এর GMP model:

  G (goroutine)  — আপনার হালকা "thread", ~2KB stack (বাড়ে)
  M (machine)    — একটা আসল OS thread
  P (processor)  — একটা scheduling context (= GOMAXPROCS)

  ┌─────────────────────────────────────────────────┐
  │  P0              P1              P2             │
  │  ┌──────────┐    ┌──────────┐    ┌──────────┐   │
  │  │ runqueue │    │ runqueue │    │ runqueue │   │  ← প্রতি-P
  │  │ G G G G  │    │ G G      │    │          │   │    queue
  │  └────┬─────┘    └────┬─────┘    └────┬─────┘   │   (ch 7 এর
  │       │               │        work stealing ───┘    MQMS!)
  │      M0              M1              M2             │
  └─────────────────────────────────────────────────┘
          │
          │  একটা goroutine network I/O করল
          ▼
  ┌─────────────────────────────────────────────────┐
  │  netpoller — ভিতরে epoll/kqueue                 │
  │  goroutine টা park করা হলো, M টা মুক্ত          │
  │  data এলে goroutine আবার runqueue এ             │
  └─────────────────────────────────────────────────┘

// This LOOKS blocking. It is not — the runtime parks the
// goroutine on the netpoller (epoll) and runs something else
// on that OS thread.
func handle(conn net.Conn) {
    buf := make([]byte, 1024)
    n, err := conn.Read(buf)      // parks here, no OS thread blocked
    if err != nil { return }
    conn.Write(buf[:n])           // parks here too
}

// So this is fine — 10,000 goroutines, not 10,000 OS threads
for {
    conn, _ := listener.Accept()
    go handle(conn)               // ~2KB each, not 8MB
}

অর্থাৎ Go আপনাকে thread-per-connection এর সরলতা দেয় আর event loop এর দক্ষতা দেয়। দাম: একটা জটিল runtime, আর কিছু সূক্ষ্ম ফাঁদ:

ভুল ধারণা

"Goroutine এ blocking call নিরাপদ, কারণ runtime সব সামলায়।"

Network I/O হ্যাঁ — netpoller সামলায়। কিন্তু:

  • Syscall যা netpoller এ যায় না (file read, cgo call) — সেই M টা সত্যিই block হয়। Runtime তখন একটা নতুন M বানায়, তাই goroutine গুলো চলে, কিন্তু OS thread সংখ্যা বেড়ে যায়।
  • CPU-ভারী loop — Go 1.14 থেকে asynchronous preemption আছে (signal দিয়ে), তাই এটা আর পুরো scheduler আটকায় না। তার আগে একটা tight loop অন্য goroutine কে অনাহারে রাখতে পারত।
  • GOMAXPROCS ভুল হলে — chapter 7 এ দেখেছি container এ Go host এর core সংখ্যা দেখে। ৬৪ P, ২ core এর quota → throttling।

Event loop এর সেই "সব আটকে যায়" সারিটাই কারণ যে nginx আর Node দুটোই multi-process চালায় — nginx এ worker_processes, Node এ cluster। প্রতিটা process এর নিজের event loop, তাই একটা core এর সীমাও কাটে আর একটা আটকে গেলেও বাকিরা চলে।

আপনার কাজের সাথে যোগ

Part 2 এর সারসংক্ষেপ হিসেবে: chapter 12–18 এ যে সব সমস্যা দেখেছি — race, memory model, lock, deadlock — event loop স্থাপত্য সেগুলোর সবগুলোই এড়িয়ে যায়, একটাই thread রেখে।

এটা কোনো কৌশল নয়, একটা বিনিময়: আপনি concurrency এর জটিলতা দিয়ে multicore ব্যবহারের ক্ষমতা কিনছেন, বা উল্টোটা। Node এর জনপ্রিয়তার একটা আসল কারণ হলো অনেক web workload এ ওই বিনিময়টা লাভজনক — I/O-bound কাজে একটা core যথেষ্ট, আর race condition ছাড়া development অনেক দ্রুত।

আর Postgres তৃতীয় পথ বেছেছে: process-per-connection (thread নয়, process — তাই একটা crash অন্যদের নেয় না)। দাম হলো connection তৈরি খরচি, তাই PgBouncer লাগে — chapter 4 এ এই যোগসূত্রটা শুরু করেছিলাম।

প্রশ্ন

  1. Event loop স্থাপত্যে কোনো lock লাগে না। Chapter 12–18 এর কোন কোন সমস্যা এতে অদৃশ্য হয়ে যায়, আর কোনটা তবু থাকে? (সূত্র: SharedArrayBuffer আর cluster।)
  2. select() প্রতি iteration এ O(n), epoll O(ready)। ১০,০০০ connection এ যদি সবসময় ৯,০০০ ready থাকে, তাহলে epoll এর লাভ কত? এই হিসাব থেকে বলুন epoll ঠিক কোন workload এ জেতে।
  3. Edge-triggered এ socket সম্পূর্ণ নিষ্কাশন না করলে connection আটকে যায়। Chapter 4 এর edge বনাম level-triggered interrupt এর সাথে এই ফাঁদের সাদৃশ্যটা কী? আর কেন libuv এর মতো library level-triggered বেছে নেয়?
  4. Linux এ regular file এ O_NONBLOCK কার্যত অর্থহীন। এই একটা তথ্য থেকে ব্যাখ্যা করুন কেন libuv কে একটা thread pool রাখতে হয়েছে, আর কেন io_uring একটা সত্যিকারের অগ্রগতি।
  5. Node এ "API ধীর" এর দুটো আলাদা কারণ — event loop blocked বনাম thread pool saturated। প্রতিটার জন্য একটা নির্দিষ্ট পরিমাপ বলুন যা দিয়ে আপনি দুটো আলাদা করবেন, আর প্রতিটার সমাধান কেন আলাদা।
  6. Go তে conn.Read() দেখতে blocking কিন্তু নয়, আর os.ReadFile() সত্যিই একটা OS thread block করে। এই অসামঞ্জস্যটা কোথা থেকে আসে? আপনার service এ /proc/<pid>/task এ thread সংখ্যা ৫০০ দেখলে আপনি কী সন্দেহ করবেন?
