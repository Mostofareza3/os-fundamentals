Condition variable আর semaphore

Lock বলে "একসাথে একজন"। কিন্তু প্রায়ই দরকার হয় "একটা শর্ত সত্যি হওয়া পর্যন্ত অপেক্ষা করো"। এই দুটো সম্পূর্ণ আলাদা সমস্যা, আর দ্বিতীয়টার জন্য একটা নিয়ম আছে যেটা ভাঙলে bug টা বছরে একবার প্রকাশ পায়।

Chapter 15-16 এ mutual exclusion পেয়েছি। কিন্তু একটা ভিন্ন ধরনের অপেক্ষা আছে: "queue তে কিছু আসা পর্যন্ত অপেক্ষা করো", "সব worker শেষ হওয়া পর্যন্ত অপেক্ষা করো", "connection পাওয়া পর্যন্ত অপেক্ষা করো"।

এটা lock দিয়ে করা যায় না — lock এর কাজ পালা ঠিক করা, শর্ত পাহারা দেওয়া নয়।

Crux

একটা thread কে একটা শর্তের অপেক্ষায় থাকতে হবে, আর শর্তটা অন্য thread পূরণ করবে। Spin না করে, CPU নষ্ট না করে — কীভাবে?

প্রথমে দেখি কেন spin চলবে না

c 
/* Parent waits for child. Correct, and wasteful. */
volatile int done = 0;

void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}

int main(void) {
    pthread_t c;
    pthread_create(&c, NULL, child, NULL);
    while (done == 0)
        ;                     /* spin — burns a whole core */
    printf("parent\n");
    return 0;
}

এটা কাজ করে (chapter 14 এর হিসাবে volatile এখানেও ভুল, কিন্তু সেটা আলাদা প্রসঙ্গ), কিন্তু একটা সম্পূর্ণ core পুড়িয়ে দেয়। Child যদি এক সেকেন্ড সময় নেয়, parent এক সেকেন্ড ধরে অর্থহীন loop চালাবে।

Chapter 7 এর container প্রসঙ্গে এটা আরও খারাপ: ওই spin আপনার cpu.max quota পোড়াচ্ছে, যা child এর কাজকেই ধীর করে দিচ্ছে।

Condition variable

Condition variable হলো একটা queue যেখানে thread ঘুমিয়ে অপেক্ষা করে, আর অন্য কেউ জাগিয়ে দেয়।

c 
/* The same wait, done properly. */
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;
int done = 0;

void thr_exit(void) {
    pthread_mutex_lock(&m);
    done = 1;
    pthread_cond_signal(&c);      /* wake one waiter */
    pthread_mutex_unlock(&m);
}

void thr_join(void) {
    pthread_mutex_lock(&m);
    while (done == 0)             /* WHILE, not if — see below */
        pthread_cond_wait(&c, &m);
    pthread_mutex_unlock(&m);
}

pthread_cond_wait() তিনটে কাজ atomically করে, আর এই তিনটেই বোঝা দরকার: 

  pthread_cond_wait(&c, &m) যা করে:

  ১. lock m ছেড়ে দেয়        ← নইলে signal দেওয়া অসম্ভব হতো
  ২. thread টাকে ঘুম পাড়ায়   ← CPU মুক্ত
  ৩. জাগার পর আবার m নেয়    ← ফেরার সময় lock ধরা অবস্থায়

  ১ আর ২ atomically হওয়া অপরিহার্য।
  যদি lock ছেড়ে দেওয়ার পর কিন্তু ঘুমানোর আগে
  signal চলে আসে → সেই signal হারিয়ে যাবে →
  চিরকাল ঘুম (lost wakeup)
ভুল ধারণা — Part 2 এর সবচেয়ে ব্যবহারিক নিয়ম

while এর বদলে if দিলেও চলবে — signal তো এসেছে, মানে শর্তটা সত্যি হয়ে গেছে।"

না, আর এটা তিনটে স্বাধীন কারণে:

  • Mesa semantics — কার্যত প্রতিটা বাস্তব system এই নিয়ম ব্যবহার করে: signal() মানে "শর্তটা হয়তো এখন সত্যি, গিয়ে দেখো", নয় "শর্তটা সত্যি, নিশ্চিত"। (বিকল্প ছিল Hoare semantics — শক্তিশালী গ্যারান্টি, কিন্তু বানানো কঠিন, তাই কেউ ব্যবহার করে না।)
  • অন্য কেউ আগে ঢুকে পড়তে পারে — আপনি জেগেছেন কিন্তু lock পাওয়ার আগে তৃতীয় একটা thread ঢুকে শর্তটা আবার মিথ্যা করে দিয়েছে।
  • Spurious wakeup — POSIX স্পষ্টভাবে অনুমতি দেয় যে cond_wait কোনো signal ছাড়াই ফিরে আসতে পারে। Linux এ এটা সত্যিই ঘটে (signal handler এর কারণে)।

তাই নিয়মটা নিঃশর্ত: শর্ত সবসময় একটা while loop এ পরীক্ষা করুন, আর lock ধরা অবস্থায় করুন। 

/* ভুল */
if (queue_empty) pthread_cond_wait(&c, &m);

/* ঠিক */
while (queue_empty) pthread_cond_wait(&c, &m);

আধুনিক API গুলো এই ভুলটা অসম্ভব করে দিয়েছে — C++ এর cv.wait(lock, predicate) আর Rust এর wait_while শর্তটাই argument হিসেবে নেয়।

Producer/consumer — আসল উদাহরণ

এটাই সবচেয়ে বেশি ব্যবহৃত pattern, আর ভুল করার সবচেয়ে বেশি সুযোগও এখানে:

c 
/* Bounded buffer with two condition variables.
   TWO is the important part — see below. */
#define MAX 10

int buffer[MAX];
int fill = 0, use = 0, count = 0;

pthread_mutex_t m    = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  full = PTHREAD_COND_INITIALIZER;   /* "buffer has room" */
pthread_cond_t  empty = PTHREAD_COND_INITIALIZER;  /* "buffer has data" */

static void put(int value) {
    buffer[fill] = value;
    fill = (fill + 1) % MAX;
    count++;
}

static int get(void) {
    int tmp = buffer[use];
    use = (use + 1) % MAX;
    count--;
    return tmp;
}

void *producer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&m);
        while (count == MAX)                 /* while! */
            pthread_cond_wait(&full, &m);    /* wait for room */
        put(i);
        pthread_cond_signal(&empty);         /* tell a consumer */
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&m);
        while (count == 0)                   /* while! */
            pthread_cond_wait(&empty, &m);   /* wait for data */
        int tmp = get();
        pthread_cond_signal(&full);          /* tell a producer */
        pthread_mutex_unlock(&m);
        printf("%d\n", tmp);
    }
    return NULL;
}

দুটো আলাদা condition variable কেন? এটাই এই code এর সবচেয়ে গুরুত্বপূর্ণ সিদ্ধান্ত। একটা দিয়ে চেষ্টা করলে যা হয়: 

  একটাই CV হলে (ভুল নকশা):

  buffer ভরা। দুটো producer অপেক্ষা করছে, একটা consumer।

  consumer একটা item নিল, signal() দিল
       │
       └─ কে জাগবে? CV তে অপেক্ষারত যেকেউ!
          → হয়তো আরেকটা PRODUCER জাগল
          → সে দেখল buffer এখনো... না, জায়গা আছে, ঠিক আছে

  কিন্তু উল্টো ক্ষেত্রে:
  buffer খালি। দুটো consumer অপেক্ষা করছে।
  একটা consumer signal পেল কিন্তু সে তো CONSUMER —
  সে অন্য consumer কে জাগাল, যে দেখল buffer খালি,
  আবার ঘুমিয়ে পড়ল।
       → প্রকৃত producer কখনো জাগল না
       → সবাই ঘুমিয়ে → DEADLOCK

  দুটো CV থাকলে: "জায়গা হলো" আর "data হলো"
  দুটো আলাদা সংকেত — ভুল পক্ষ কখনো জাগে না।

একটা বিকল্প আছে — pthread_cond_broadcast() দিয়ে সবাইকে জাগানো। এটা সঠিক হয়ে যায়, কিন্তু অপচয়: ১০০ জনকে জাগিয়ে ৯৯ জন আবার ঘুমাতে যাবে (thundering herd)। তাই নিয়মটা হলো: 

  signal()    → একজনকে জাগাও।
                ব্যবহার করুন যখন যেকোনো একজন waiter
                কাজটা সামলাতে পারে (একই শর্ত, একই CV)

  broadcast() → সবাইকে জাগাও।
                ব্যবহার করুন যখন শর্তটা একাধিক ধরনের
                waiter কে প্রভাবিত করে, বা যখন
                কতজন এগোতে পারবে তা অজানা
                (যেমন একটা barrier, বা shutdown signal)

Semaphore — একটাই primitive, দুটো কাজ

Semaphore হলো একটা integer সহ দুটো atomic operation। Dijkstra এর মূল নাম ছিল P আর V; POSIX এ sem_wait আর sem_post:

c 
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, X);     /* X = initial value; 0 = not process-shared */

/* sem_wait: মান ১ কমাও; নেগেটিভ হলে ঘুমাও */
sem_wait(&s);

/* sem_post: মান ১ বাড়াও; কেউ অপেক্ষা করলে একজনকে জাগাও */
sem_post(&s);

Initial value টাই ঠিক করে দেয় semaphore টা কী করবে — আর এটাই semaphore এর সৌন্দর্য আর বিভ্রান্তি দুটোরই কারণ:

Initialনামকী করে
1 Binary semaphore (mutex এর মতো) একসাথে একজন — mutual exclusion
0 Signalling (condition variable এর মতো) একটা ঘটনার অপেক্ষা
N Counting semaphore একসাথে সর্বোচ্চ N জন — resource pool
c 
/* Initial 1 — as a lock */
sem_t m;
sem_init(&m, 0, 1);
sem_wait(&m);   counter++;   sem_post(&m);

/* Initial 0 — as a completion signal (like thr_join) */
sem_t done;
sem_init(&done, 0, 0);
/* child: */  sem_post(&done);
/* parent: */ sem_wait(&done);     /* blocks until the child posts */

/* Initial N — as a connection pool limiter */
sem_t slots;
sem_init(&slots, 0, 10);           /* at most 10 concurrent */
sem_wait(&slots);
    do_database_query();
sem_post(&slots);

তৃতীয়টাই বাস্তবে সবচেয়ে কাজের, আর এটা condition variable দিয়ে করা বেশি ঝামেলার। একটা connection pool, একটা rate limiter, একটা "সর্বোচ্চ ৫টা concurrent upload" — সবই counting semaphore।

ভুল ধারণা

"Semaphore আর mutex একই জিনিস, শুধু নাম আলাদা।"

একটা binary semaphore দিয়ে mutual exclusion পাওয়া যায়, কিন্তু দুটো গুরুত্বপূর্ণ পার্থক্য আছে:

  • Mutex এর একজন মালিক আছে — যে lock করেছে, শুধু সেই unlock করতে পারে। এর ফলে kernel priority inheritance করতে পারে (একটা উচ্চ-priority thread যদি একটা নিম্ন-priority holder এর অপেক্ষায় থাকে, holder এর priority তুলে দেওয়া হয়)। Semaphore এর মালিক নেই — যেকেউ post করতে পারে।
  • Deadlock debug করা আলাদা — mutex এ "কে ধরে আছে" জানা যায়, তাই lockdep এর মতো tool কাজ করে। Semaphore এ সেটা জানা যায় না।

ব্যবহারিক নিয়ম: mutual exclusion এর জন্য mutex, সংকেতের জন্য condition variable, গণনার জন্য semaphore। তিনটেই থাকার কারণ আছে।

যা আমরা বাদ দিলাম

OSTEP এই দুটো chapter এ dining philosophers সমস্যাটায় উল্লেখযোগ্য জায়গা দেয়। আমরা সেটা বাদ দিয়েছি, আর কারণটা স্পষ্ট করে বলা ভালো।

Dining philosophers একটা সুন্দর তাত্ত্বিক ধাঁধা, আর deadlock এর চারটে শর্ত বোঝানোর একটা উপায়। কিন্তু একজন working engineer এর কাছে এর গঠনটা কখনো আসে না — আপনি পাঁচটা কাঁটা-চামচ নিয়ে symmetric resource acquisition সমস্যা সমাধান করেন না।

যেটা সত্যিই আসে সেটা হলো: দুটো transaction দুটো row কে বিপরীত ক্রমে lock করছে। ধারণাটা একই (circular wait), কিন্তু রূপটা সম্পূর্ণ আলাদা। তাই এই জায়গাটা chapter 18 এ খরচ করছি — ওখানে Postgres এর 40P01 deadlock detected, lock ordering, আর TSan/lockdep থাকবে।

আধুনিক বিকল্প

২০২৬ এ আপনি সম্ভবত এই primitive গুলো সরাসরি ব্যবহার করবেন না। উঁচু স্তরের abstraction গুলো একই কাজ করে, কম ভুলের সুযোগ দিয়ে:

c 
/* C++20 — the predicate form makes the while-loop bug impossible */
std::mutex m;
std::condition_variable cv;
std::queue<int> q;

/* consumer */
std::unique_lock lk(m);
cv.wait(lk, []{ return !q.empty(); });   /* loops internally */
int v = q.front(); q.pop();

/* C++20 also has real counting semaphores and latches */
std::counting_semaphore<10> slots(10);
std::latch done(n_workers);
go 
// Go — a buffered channel IS a bounded producer/consumer queue.
// No condition variable, no while loop, no lost wakeup.
ch := make(chan int, 10)          // capacity 10 = the bounded buffer

// producer
ch <- value                        // blocks if full

// consumer
v := <-ch                          // blocks if empty

// WaitGroup replaces the "wait for all workers" pattern
var wg sync.WaitGroup
wg.Add(n)
// each worker: defer wg.Done()
wg.Wait()

// A counting semaphore, idiomatically
sem := make(chan struct{}, 10)
sem <- struct{}{}                  // acquire
defer func() { <-sem }()           // release
javascript 
// Node — the event loop removes the problem entirely for I/O.
// For limiting concurrency you use a semaphore-shaped library:
import pLimit from 'p-limit';
const limit = pLimit(10);          // at most 10 concurrent
await Promise.all(urls.map(u => limit(() => fetch(u))));

// Backpressure in streams is the bounded-buffer idea:
readable.pipe(writable);           // pauses when the sink is full
আপনার কাজের সাথে যোগ

Bounded buffer টা আপনার architecture এ সর্বত্র, আর "bounded" শব্দটাই আসল বিষয়:

  • Connection pool (PgBouncer, HikariCP) একটা counting semaphore। Pool শেষ হলে আপনার request অপেক্ষা করে — সেটা ভালো, কারণ বিকল্প হলো database কে ডুবিয়ে দেওয়া।
  • Kafka consumer এর max.poll.records আর Node stream এর highWaterMark — দুটোই একই bounded buffer, আর দুটোই backpressure প্রয়োগ করে।
  • একটা unbounded queue একটা bug — producer যদি consumer এর চেয়ে দ্রুত হয়, unbounded queue মানে memory শেষ হওয়া পর্যন্ত বাড়তে থাকা, তারপর chapter 11 এর OOM kill। Bounded buffer চাপটা producer এর দিকে ফেরত পাঠায়, যেটাই সঠিক আচরণ।

Go তে make(chan int) (unbuffered) আর make(chan int, 1000000) এর মধ্যে সিদ্ধান্তটা ঠিক এই আলোচনা — আর উত্তরটা প্রায় সবসময় ছোট buffer।

ডান কলামটা লক্ষ করুন: আধুনিক ভাষায় প্রায় সব সারির উত্তর একটা channel। এটা কাকতালীয় নয় — channel হলো এই primitive গুলোর একটা সমন্বিত, কম-ভুল-প্রবণ রূপ। Chapter 14 এর সেই পরামর্শটাই: সবচেয়ে ভালো সমাধান হলো shared mutable state এড়ানো।

প্রশ্ন

  1. pthread_cond_wait() lock ছাড়া আর ঘুমানো — দুটো কাজ atomically করে। যদি atomic না হতো, তাহলে ঠিক কোন interleaving এ একটা thread চিরকাল ঘুমিয়ে থাকত? ক্রমটা লিখুন।
  2. while এর বদলে if দিলে তিনটে স্বাধীন কারণে ভাঙতে পারে। তিনটের মধ্যে কোনটা আপনার নিজের code এ কখনো ঘটবে না বলে আপনি যুক্তি দিতে পারেন, আর কোনটা আপনি কখনো নিয়ন্ত্রণ করতে পারবেন না?
  3. Producer/consumer এ একটা CV দিয়ে deadlock হতে পারে। broadcast() ব্যবহার করলে সেটা সারবে — কিন্তু কী দাম দিয়ে? ১০০ consumer আর ১টা item এর পরিস্থিতিতে হিসাব করুন কতগুলো অর্থহীন wake-up হবে।
  4. Mutex এর মালিক আছে, semaphore এর নেই। এই একটা পার্থক্য থেকে দুটো ব্যবহারিক পরিণতি বের করুন — একটা priority সংক্রান্ত, আরেকটা debugging সংক্রান্ত।
  5. একটা unbounded queue কেন একটা bug? Producer consumer এর চেয়ে ২০% দ্রুত হলে কী ঘটবে, আর chapter 11 এর কোন mechanism শেষে হস্তক্ষেপ করবে? Bounded buffer এই পরিস্থিতিতে কী আলাদা করে?
  6. Go তে প্রায় সব synchronization pattern এর উত্তর একটা channel। কিন্তু channel নিজেই ভিতরে mutex আর condition variable ব্যবহার করে। তাহলে channel কী যোগ করে যা primitive গুলো দেয় না — আর কোন পরিস্থিতিতে আপনি তবু সরাসরি sync.Mutex ব্যবহার করবেন?
