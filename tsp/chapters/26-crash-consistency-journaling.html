Crash consistency — fsck থেকে journaling

Chapter 25 এ শিখলাম কীভাবে একটা লেখা নিশ্চিত করা যায়। কিন্তু file system এর একটা কাজে একাধিক লেখা লাগে — আর মাঝখানে crash হলে disk একটা অসম্ভব অবস্থায় পড়ে থাকে। এর সমাধানটাই আপনার database এর WAL।

Chapter 23 এ দেখেছি একটা file এ ৪KB যোগ করতে তিনটে আলাদা জায়গায় লিখতে হয়: 

  একটা file এ একটা block যোগ করা:

  ১. data bitmap      — block টা "দখল" চিহ্নিত করো
  ২. inode            — size বাড়াও, block pointer বসাও
  ৩. data block       — আসল byte গুলো লেখো

  তিনটে লেখা, কিন্তু disk একসাথে একটাই atomically করে।
  মাঝখানে power গেলে?
Crux

একটা যুক্তিগত কাজে একাধিক disk write লাগে, কিন্তু crash যেকোনো মুহূর্তে হতে পারে। File system কীভাবে নিশ্চিত করবে যে reboot এর পর অবস্থাটা সঙ্গত থাকবে?

কী কী ভুল হতে পারে

তিনটে লেখার মধ্যে যেকোনো উপসেট সফল হতে পারে। প্রতিটা ক্ষেত্রের পরিণতি আলাদা, আর কয়েকটা অন্যদের চেয়ে অনেক খারাপ:

কী লেখা হলোফলাফলকতটা খারাপ
শুধু data block কেউ ওই block এর কথা জানে না — data হারাল সহনীয় (fs সঙ্গত)
শুধু inode inode একটা block এ point করছে যা bitmap এ মুক্ত।
পরে কেউ ওই block পাবে → দুজনে একই block		 মারাত্মক — data corruption
শুধু bitmap Block দখল দেখাচ্ছে কিন্তু কেউ ব্যবহার করছে না space leak (সহনীয়)
inode + bitmap, data নয় File এ আগের কারো আবর্জনা দেখা যাবে নিরাপত্তা সমস্যা!
inode + data, bitmap নয় অসঙ্গতি — block টা পরে আবার বিতরণ হতে পারে মারাত্মক

এর নাম crash-consistency problem। লক্ষ করুন চতুর্থ সারিটা — পুরনো data প্রকাশ হয়ে যাওয়া একটা নিরাপত্তা দুর্বলতা, শুধু bug নয়। এই কারণেই file system নতুন block কে শূন্য করে দেয় (demand zeroing)।

পুরনো সমাধান — fsck

প্রথম পদ্ধতি ছিল: crash হতে দাও, তারপর reboot এ পুরো file system পরীক্ষা করে সারাও। 

  fsck (file system check) যা করে:

  • superblock       — যুক্তিসঙ্গত দেখাচ্ছে কি?
  • free block       — সব inode স্ক্যান করে bitmap
                       আবার হিসাব করো
  • inode state      — প্রতিটা inode এর type বৈধ কি?
  • inode link       — পুরো directory tree হেঁটে
                       link count আবার গোনো
                       (এতিম inode → /lost+found এ)
  • duplicate        — দুটো inode একই block দাবি করছে?
  • directory        — "." আর ".." ঠিক আছে কি?

  সমস্যা: এটা পুরো disk স্ক্যান করে।
ভুল ধারণা

fsck crash এর পর আমার file গুলো সারিয়ে দেবে।"

fsck file system এর metadata সঙ্গত করে — আপনার data নয়। সে নিশ্চিত করে যে structure টা বৈধ, যাতে kernel crash না করে।

আপনার অর্ধেক-লেখা file টা অর্ধেকই থাকবে। আপনার হারানো data ফেরত আসবে না। /lost+found এ যা পাবেন সেটা নাম-হারানো inode — প্রায়ই অব্যবহার্য।

আর মূল সমস্যা: fsck এর সময় disk এর আকারের সাথে বাড়ে। ১০TB drive এ একটা পূর্ণ fsck ঘণ্টা লাগতে পারে — আর ঠিক সেই সময়ে আপনার service বন্ধ। এটাই journaling এর অস্তিত্বের কারণ।

Journaling — লেখার আগে লেখা

মূল ধারণা: কাজটা করার আগে লিখে রাখো কী করতে যাচ্ছ। Crash হলে ওই নোট পড়ে কাজটা শেষ করা যায়, বা বাতিল করা যায়।

এর আরেক নাম WAL (Write-Ahead Logging) — আর এই নামটাই আপনার database এ ব্যবহৃত হয়। 

  Disk এর layout এ একটা নতুন অংশ:

  ┌────────┬──────────────────┬──────────────────────────┐
  │ super  │     JOURNAL      │   বাকি file system       │
  └────────┴──────────────────┴──────────────────────────┘
              (একটা circular log)

  একটা transaction:

  ┌─────┬──────┬──────┬──────┬─────┐
  │ TxB │ I[v2]│ B[v2]│ D[v2]│ TxE │
  └─────┴──────┴──────┴──────┴─────┘
    ▲                              ▲
    │                              │
   শুরুর marker              শেষের marker
   (transaction ID)          (একই TID)

  TxE থাকা মানে: পুরো transaction টা journal এ আছে।
  TxE না থাকা মানে: অসম্পূর্ণ → পুরোটা বাতিল।

ক্রমটা গুরুত্বপূর্ণ, আর এখানে একটা সূক্ষ্ম কিন্তু অপরিহার্য বিস্তারিত আছে: 

  ধাপ ১: journal write
          TxB + সব metadata/data journal এ লেখো
          ═══ fsync ═══  (chapter 25!)

  ধাপ ২: journal commit
          TxE লেখো
          ═══ fsync ═══
          ← এই বিন্দুর পর transaction "committed"

  ধাপ ৩: checkpoint
          আসল জায়গায় (inode, bitmap, data) লেখো
          ═══ fsync ═══

  ধাপ ৪: journal এর ওই অংশ মুক্ত করো


  ⚠ কেন ধাপ ১ আর ২ আলাদা fsync?

  যদি একসাথে পাঠানো হয়, disk reorder করতে পারে
  (chapter 20 এর queue, chapter 21 এর FTL) —
  তাহলে TxE আগে লেখা হয়ে যেতে পারে যখন data
  এখনো যায়নি।

  ফল: crash এ journal বলছে "committed" কিন্তu
      ভিতরের data আবর্জনা → আমরা সেই আবর্জনা
      বিশ্বাস করে আসল file system এ লিখব!

  এই কারণেই TxE আলাদা করে, data লেখা নিশ্চিত
  হওয়ার পরে পাঠানো হয়।

Recovery টা তখন সরল আর দ্রুত: 

  Reboot এর পর — শুধু JOURNAL পড়ো, পুরো disk নয়:

  প্রতিটা transaction এর জন্য:
    TxE আছে?  ──▶ হ্যাঁ: আবার চালাও (redo)
                        → আসল জায়গায় লেখো
                        → নিরীহ, কারণ idempotent
              ──▶ না:   বাতিল করো (কিছুই হয়নি ধরে নাও)

  সময়: journal এর আকারের সমান (MB), disk এর নয় (TB)
  → কয়েক সেকেন্ড, ঘণ্টা নয়

  এই পদ্ধতির নাম redo logging।

ext4 এর তিনটে mode — একটা বাস্তব পছন্দ

সব কিছু journal এ লিখলে প্রতিটা byte দুবার লেখা হয় — chapter 21 এর ভাষায় WAF ২x। তাই একটা trade-off আছে, আর ext4 তিনটে বিকল্প দেয়:

ModeJournal এ যায়গ্যারান্টিখরচ
data=journal metadata + data সবচেয়ে শক্ত সব data দুবার লেখা
data=ordered
(default)		 শুধু metadata,
কিন্তু data আগে লেখা হয়		 metadata সঙ্গত,
আর কোনো আবর্জনা দেখা যাবে না		 মাঝারি
data=writeback শুধু metadata,
ক্রমের কোনো নিশ্চয়তা নেই		 metadata সঙ্গত,
কিন্তু পুরনো আবর্জনা দেখা যেতে পারে		 সবচেয়ে কম

data=ordered এর কৌশলটা সুন্দর: data টা journal এ লেখা হয় না (তাই দ্বিগুণ লেখা নেই), কিন্তু metadata commit করার আগে data লেখা নিশ্চিত করা হয়। তাই inode যখন একটা block এ point করে, ওই block এ সঠিক data আছেই — উপরের সেই "নিরাপত্তা সমস্যা" সারিটা এভাবে বন্ধ হয়। 

# আপনার mode কোনটা
$ mount | grep -o 'data=[a-z]*'
data=ordered

# journal এর আকার আর অবস্থা
$ sudo dumpe2fs -h /dev/nvme0n1p2 2>/dev/null | grep -i journal

Journal backup:           inode blocks
Journal features:         journal_64bit journal_checksum_v3
Journal size:             1024M

# XFS এ একই ধারণা, আলাদা নাম
$ sudo xfs_info /dev/nvme1n1 | grep log
যেখানে source টা পুরনো

OSTEP ext3 কে "a relatively modern journaling file system" বলে। ২০২৬ এ:

  • ext3 আর নেই — আলাদা driver হিসেবে Linux 4.3 (২০১৫) এ সরানো হয়েছে। ext4 driver ই ext3 filesystem mount করে।
  • Barrier BIO সরানো হয়েছে (kernel 2.6.37, ২০১০)। আজকের mechanism হলো প্রতিটা request এ REQ_PREFLUSH আর REQ_FUA flag। ধারণাটা একই — ক্রম আরোপ করা — কিন্তু নাম আর API বদলেছে, তাই পুরনো documentation বিভ্রান্তিকর।
  • Journal checksum যোগ হয়েছে (journal_checksum) — TxE এর সাথে একটা checksum রাখলে দুটো fsync এর বদলে একটায় কাজ চলে, কারণ checksum মিললেই বোঝা যায় পুরো transaction পৌঁছেছে। একটা সূক্ষ্ম কিন্তু উল্লেখযোগ্য optimization।
  • CoW file system (btrfs, ZFS) journaling ব্যবহার করেই না — তারা কখনো জায়গায় লেখে না, তাই crash এ পুরনো version অটুট থাকে। পুরো সমস্যাটাই এড়িয়ে যায়, আর তার বদলে অন্য খরচ নেয় (fragmentation, GC)।

এটাই আপনার database এর WAL

এখন সবচেয়ে কাজের যোগসূত্রটা: উপরের protocol টা আর Postgres এর WAL একই জিনিস, একই কারণে, একই ধাপে। 

  File system                    Postgres
  ─────────────────────────      ─────────────────────────
  journal                    ↔   WAL (pg_wal/)
  TxB / TxE                  ↔   transaction record + commit record
  checkpoint                 ↔   CHECKPOINT
  journal মুক্ত করা          ↔   WAL segment recycle
  redo recovery              ↔   crash recovery (startup এ)
  data=ordered এর ক্রম       ↔   full_page_writes

  একই ধাপ:
  ১. WAL এ লেখো + fsync       ← chapter 25 এর fdatasync
  ২. commit record + fsync    ← এখন transaction committed,
                                 client কে হ্যাঁ বলা যায়
  ৩. পরে: dirty page গুলো
     আসল data file এ লেখো     ← checkpoint
  ৪. পুরনো WAL মুক্ত করো
# Postgres এর WAL এই ধাপগুলোই দেখায়
$ psql -c "SELECT pg_current_wal_lsn(), pg_walfile_name(pg_current_wal_lsn());"

# checkpoint কত ঘন ঘন হচ্ছে — খুব ঘন মানে WAL ছোট
$ psql -c "SELECT * FROM pg_stat_bgwriter;" 
# checkpoints_timed vs checkpoints_req:
#   req বেশি মানে max_wal_size ছোট, checkpoint জোর করে হচ্ছে
#   → chapter 21 এর write amplification বাড়ছে

mysql> SHOW ENGINE INNODB STATUS\G   -- LOG অংশ দেখুন
ভুল ধারণা

"আমার file system journaled, তাই crash এ data হারাতে পারি না।"

Journaling file system এর metadata সঙ্গত রাখে। সে নিশ্চিত করে না যে আপনার application এর data সঠিক বা সম্পূর্ণ। 

/* journaled fs, তবু data হারাবে */
write(fd, "important", 9);
/* ⚡ power loss — fsync করা হয়নি */

/* Reboot: file system পুরোপুরি সঙ্গত।
   কোনো fsck লাগেনি। কোনো corruption নেই।
   আপনার "important" শব্দটা শুধু নেই। */

দুটো আলাদা গ্যারান্টি:

  • Journaling → file system ভাঙবে না (structural integrity)
  • fsync → আপনার data টিকবে (durability)

Chapter 25 এর পুরো বিষয়টা এই দ্বিতীয়টা নিয়ে, আর journaling সেটা দেয় না। একটা journaled file system এ fsync ছাড়া লেখা ঠিক ততটাই অস্থায়ী।

Torn write — একটা page ও atomic নয়

আরেকটা সমস্যা যা প্রায়ই অনুপস্থিত থাকে। আপনি ধরে নেন একটা ৪KB লেখা হয় সম্পূর্ণ হবে নয় একেবারেই হবে না। সেটা নিশ্চিত নয়। 

  Postgres এর page ৮KB, কিন্তু device এর sector ৫১২B বা ৪KB।

  ৮KB লেখা = একাধিক device write

  ⚡ মাঝখানে power loss:

  ┌────────┬────────┐
  │ নতুন   │ পুরনো  │   ← অর্ধেক-নতুন page
  │ ৪KB    │ ৪KB    │      কোনো checksum মিলবে না,
  └────────┴────────┘      আর কোনো version ও বৈধ নয়

  এর নাম TORN PAGE বা torn write।

  সমাধানগুলো:
  • Postgres: full_page_writes = on
      checkpoint এর পর প্রথম বদলে পুরো page টা
      WAL এ লেখা হয় → recovery তে সেটা দিয়ে
      page পুনর্গঠন করা যায়
      (দাম: WAL অনেক বড় হয়, WAF বাড়ে)
  • MySQL: doublewrite buffer
      একই ধারণা — আগে একটা আলাদা জায়গায় লেখো
  • btrfs/ZFS: CoW — কখনো জায়গায় লেখে না,
      তাই torn write সম্ভবই নয়
# Postgres এ এই সুরক্ষা চালু আছে কি
$ psql -c "SHOW full_page_writes;"

আপনার কাজের সাথে যোগ

এই chapter এর ধারণাগুলো storage এর বাইরেও সর্বত্র:

  • Git — .git/objects immutable, আর ref update হয় atomic rename দিয়ে। একটা .lock file দিয়ে concurrent writer আটকানো হয়। কার্যত একটা WAL-মুক্ত নকশা: কখনো জায়গায় লেখে না, তাই crash এ পুরনো অবস্থা অটুট — btrfs এর দর্শনের মতো।
  • Kafka — পুরো log টাই একটা WAL, আর সেটাই primary data। Journal আর data আলাদা নয়।
  • etcd / Raft — distributed consensus এ প্রতিটা node একটা WAL রাখে, আর একটা entry "committed" বলার আগে majority তে fsync হতে হয়। একই protocol, network জুড়ে।
  • SQLite এর দুটো mode: rollback journal (undo logging — পুরনো মান জমিয়ে রাখে) আর WAL mode (redo logging — উপরের পদ্ধতি)। WAL mode এ concurrent reader আর writer সম্ভব, তাই সেটাই সাধারণত পছন্দ।

সাধারণ নীতি: একাধিক জায়গায় লেখা লাগলে, আগে একটা জায়গায় নিয়তটা লিখে রাখো। এটা file system, database, distributed consensus — সব জায়গায় একই।

প্রশ্ন

  1. তিনটে লেখার (bitmap, inode, data) মধ্যে "শুধু inode লেখা হলো" সবচেয়ে খারাপ, আর "শুধু data লেখা হলো" সহনীয়। কেন এই অসমতা? আর "inode + bitmap কিন্তু data নয়" কেন একটা নিরাপত্তা সমস্যা?
  2. Journal এ TxE আলাদা করে দ্বিতীয় fsync দিয়ে পাঠানো হয়। যদি একসাথে পাঠানো হতো, ঠিক কী ভুল হতে পারত? Chapter 20 এর device queue আর chapter 21 এর FTL দুটোই কীভাবে এই সমস্যায় অবদান রাখে?
  3. data=ordered data কে journal এ না লিখেও নিরাপত্তা সমস্যাটা বন্ধ করে। কৌশলটা কী? আর data=writeback এ ঠিক কোন পরিস্থিতিতে আপনি অন্য কারো পুরনো data দেখতে পাবেন?
  4. একটা journaled file system এ fsync ছাড়া লেখা crash এ হারায় — যদিও fs সম্পূর্ণ সঙ্গত থাকে। "Structural integrity" আর "durability" এই দুটো গ্যারান্টি আলাদা করে ব্যাখ্যা করুন, আর বলুন কোনটা কে দেয়।
  5. Postgres এর checkpoints_req যদি checkpoints_timed এর চেয়ে অনেক বেশি হয়, সেটা কী বলছে? Chapter 21 এর write amplification এর সাথে এর সম্পর্ক কী, আর কোন setting বদলাবেন?
  6. Torn write সম্ভব কারণ একটা ৮KB লেখা একাধিক device write এ ভাঙে। btrfs/ZFS এর CoW নকশা এই সমস্যাটা সম্পূর্ণ এড়িয়ে যায় — কীভাবে? আর তার বদলে তারা কোন খরচ নেয়?
