Process — OS এর প্রধান abstraction

Disk এ পড়ে থাকা একটা file আর চলমান একটা program — দুটোর মধ্যে কী যোগ হলে প্রথমটা দ্বিতীয়টা হয়? উত্তরটা একটা kernel data structure, আর সেটা আপনি /proc দিয়ে নিজের চোখে দেখতে পারেন।

Process এর সংজ্ঞা সরল: একটা চলমান program। কিন্তু এই সরলতার নিচে একটা গুরুত্বপূর্ণ পার্থক্য আছে যেটা না ধরলে পরের কোনো chapter ঠিকভাবে বসবে না।

আপনার disk এ /usr/bin/node একটা file। সেটা নিষ্প্রাণ — কিছু instruction আর static data, পড়ে আছে। এর মধ্যে "চলা" বলে কিছু নেই। আপনি node লিখলে OS ওই byte গুলো নিয়ে তার সাথে আরও কিছু যোগ করে একটা চলমান সত্তা বানায়। সেই যোগ করা জিনিসটাই process।

Crux

Physical CPU মাত্র কয়েকটা। তাহলে OS কীভাবে প্রায়-অসীম সংখ্যক CPU এর illusion দেয়? উত্তর: time sharing — একটা process চালাও, থামাও, আরেকটা চালাও, এত দ্রুত যে সবগুলো একসাথে চলছে মনে হয়। দাম হলো performance: প্রত্যেকে ধীরে চলে।

Process = machine state

Process কী দিয়ে তৈরি, সেটা বোঝার সবচেয়ে কাজের উপায় হলো প্রশ্ন করা: একটা চলমান program কী কী পড়তে বা বদলাতে পারে? সেই তালিকাটাই তার machine state।

উপাদানকী থাকেকোথায় দেখবেন
Address space code, static data, heap, stack — যে memory টা process ছুঁতে পারে /proc/<pid>/maps
Register general purpose register, আর বিশেষ কয়েকটা (নিচে) /proc/<pid>/syscall, gdb
PC / IP Program Counter — এই মুহূর্তে কোন instruction চলছে /proc/<pid>/stat (field 30)
SP / FP Stack ও Frame Pointer — function এর parameter, local variable, return address /proc/<pid>/stat (field 29)
I/O information কোন কোন file খোলা আছে /proc/<pid>/fd/

শেষ সারিটা গুরুত্বপূর্ণ আর প্রায়ই ভুলে যাওয়া হয়: খোলা file গুলোও process এর state এর অংশ। এই কারণেই একটা process কে kill করলে তার সব file descriptor বন্ধ হয়ে যায়, আর এই কারণেই chapter 3 এ দেখব fork() করলে child ঠিক একই খোলা file গুলো পায় — একই file offset সহ।

Program থেকে process — কী কী ঘটে

OS কে কয়েকটা কাজ করতে হয় program টা চালু করার আগে: 

  DISK                          MEMORY (নতুন address space)
  ┌──────────────┐              ┌──────────────────────┐  উঁচু address
  │              │              │        stack         │  ↓ নিচের দিকে বাড়ে
  │ ELF file     │              │  argc, argv, env     │
  │ ┌──────────┐ │   load       ├──────────────────────┤
  │ │  code    │─┼───────────▶  │                      │
  │ ├──────────┤ │              │      (ফাঁকা)         │
  │ │ static   │─┼───────────▶  │                      │
  │ │ data     │ │              ├──────────────────────┤
  │ └──────────┘ │              │        heap          │  ↑ উপরের দিকে বাড়ে
  └──────────────┘              │   malloc() এখান থেকে │
                                ├──────────────────────┤
                    OS বানায়──▶ │    static data       │
                                ├──────────────────────┤
                                │       code           │  নিচু address
                                └──────────────────────┘

Program loading: file এর byte + OS এর বানানো stack ও heap = process।

  1. Code আর static data load করা — executable format (Linux এ ELF) থেকে memory তে।
  2. Stack বানানো — C তে local variable, function parameter আর return address এর জন্য। OS এখানেই main() এর argument বসিয়ে দেয়: argc আর argv।
  3. Heap এর প্রস্তুতি — malloc() যেখান থেকে নেবে। শুরুতে ছোট, দরকারে বাড়ে।
  4. I/O এর প্রাথমিক ব্যবস্থা — UNIX এ প্রতিটা process তিনটা file descriptor নিয়ে শুরু করে: 0 = stdin, 1 = stdout, 2 = stderr।
  5. Entry point এ লাফ দেওয়া — main() এ (আসলে তার আগে কিছু runtime setup), আর CPU টা process এর হাতে ছেড়ে দেওয়া।
যেখানে source টা পুরনো

OSTEP লেখে: OS কে "disk থেকে ওই byte গুলো পড়ে memory তে বসাতে হয়", আর যোগ করে যে পুরনো OS এটা eagerly করত, আধুনিক OS করে lazily। কথাটা সত্য কিন্তু এতটাই সংক্ষিপ্ত যে ভুল ছবি তৈরি হয় — আর বইয়ের পরের অংশের সাথে সাংঘর্ষিকও (paging chapter বলে loading lazy, আর এই chapter বলে OS byte পড়ে memory তে বসায়)।

আসল পথটা হলো: execve() ELF এর PT_LOAD segment গুলো mmap() করে — অর্থাৎ page table এ mapping বসায়, কিন্তু কোনো byte পড়ে না। তারপর dynamic linker (ld.so) shared library গুলো map করে। Page গুলো আসে চাহিদামতো, page fault এর মাধ্যমে, যখন সত্যিই ওই address টা ছোঁয়া হয়।

এর একটা মাপা ফল আছে যেটা আপনি রোজ দেখেন: একই binary দ্বিতীয়বার চালালে অনেক দ্রুত চালু হয় — কারণ page গুলো তখন page cache এ গরম, disk এ যেতে হয় না। Chapter 24 এ এটাই page cache। আর container এর cold start এর বড় অংশ এই একই কারণ: নতুন node এ image layer গুলো page-cache-cold, তাই প্রথম request ধীর — এই কারণেই image size আর layer এর ক্রম গুরুত্বপূর্ণ।

Process এর তিনটা অবস্থা

যেকোনো মুহূর্তে একটা process তিনটার একটায় থাকে: 

                    scheduled
              ┌─────────────────────┐
              │                     ▼
        ┌──────────┐          ┌──────────┐
        │  READY   │          │ RUNNING  │
        │          │◀─────────│          │
        └──────────┘descheduled└──────────┘
              ▲                     │
              │                     │ I/O শুরু
              │ I/O শেষ             ▼
              │               ┌──────────┐
              └───────────────│ BLOCKED  │
                              └──────────┘

  RUNNING  — এই মুহূর্তে CPU তে instruction চালাচ্ছে
  READY    — চালানোর জন্য প্রস্তুত, কিন্তু OS এখন চালাচ্ছে না
  BLOCKED  — কোনো ঘটনার অপেক্ষায় (I/O, lock, timer);
             CPU দিলেও কাজে লাগবে না

Process state machine। তীরগুলোর নাম মনে রাখা দরকার।

READY আর BLOCKED এর পার্থক্যটাই এই diagram এর আসল কথা। READY process কে CPU দিলে সে কাজ করবে — সে শুধু অপেক্ষা করছে তার পালার জন্য। BLOCKED process কে CPU দিলে সে কিছুই করতে পারবে না, কারণ সে অপেক্ষা করছে বাইরের কোনো ঘটনার। তাই scheduler BLOCKED process কে বিবেচনাই করে না।

দুটো process এর trace দেখলে পরিষ্কার হয়। প্রথমে দুটোই শুধু CPU ব্যবহার করছে, কোনো I/O নেই: 

  সময়   Process 0    Process 1    টীকা
  ────   ──────────   ──────────   ─────────────────────
   1     Running      Ready
   2     Running      Ready
   3     Running      Ready
   4     Running      Ready        Process 0 শেষ
   5     —            Running
   6     —            Running
   7     —            Running
   8     —            Running      Process 1 শেষ

Process 1 চারটা সময়-একক পুরো বসে থাকল। এখন Process 0 যদি মাঝপথে I/O শুরু করে: 

  সময়   Process 0    Process 1    টীকা
  ────   ──────────   ──────────   ──────────────────────────
   1     Running      Ready
   2     Running      Ready
   3     Running      Ready        Process 0 I/O শুরু করল
   4     Blocked      Running      P0 blocked, তাই P1 চলল
   5     Blocked      Running
   6     Blocked      Running
   7     Ready        Running      I/O শেষ → P0 এখন Ready
   8     Ready        Running      Process 1 শেষ
   9     Running      —
  10     Running      —            Process 0 শেষ

এখানে OS দুটো সিদ্ধান্ত নিয়েছে, আর দুটোই policy — mechanism নয়। প্রথমত, P0 blocked হওয়ার সাথে সাথে P1 চালিয়ে দিল, তাতে CPU খালি থাকল না। দ্বিতীয়ত, সময় ৭ এ I/O শেষ হওয়ার পরেও P0 তে ফেরত গেল না — P1 কে চলতে দিল। এটা ভালো সিদ্ধান্ত কি না, সেটা নির্ভর করে আপনি কী optimize করছেন, আর সেটাই chapter 5 আর 6 এর বিষয়।

ভুল ধারণা

"top এ load average ৮, মানে ৮টা process CPU খাচ্ছে।"

Linux এ load average হলো RUNNING + READY process এর সংখ্যা (আর একটা বিশেষ ব্যতিক্রম — নিচে)। অর্থাৎ যারা চলছে এবং যারা চলার জন্য লাইনে দাঁড়িয়ে আছে। ৮ core এ load ৮ মানে মোটামুটি পুরো ব্যবহার; ২ core এ load ৮ মানে প্রতিটা process তার সময়ের বড় অংশ লাইনে দাঁড়িয়ে কাটাচ্ছে।

ব্যতিক্রমটা বিভ্রান্তিকর: Linux (অন্য UNIX এর তুলনায় ব্যতিক্রমীভাবে) load average এ uninterruptible sleep — ps এ state D — ও গোনে। অর্থাৎ যে process disk I/O এর জন্য আটকে আছে, সে CPU চাইছে না, তবু load বাড়াচ্ছে। তাই ধীর disk বা আটকে যাওয়া NFS mount এর কারণে load ২০ দেখা যেতে পারে যখন CPU প্রায় খালি। Load average দিয়ে CPU saturation মাপা তাই ভুল — %util বা PSI (chapter 11) দেখা উচিত। 

# state কলাম দেখুন: R=running/ready, S=sleep, D=uninterruptible
$ ps -eo pid,stat,wchan:20,comm | head
# R  → RUNNING বা READY
# S  → BLOCKED (interruptible — signal এ জাগবে)
# D  → BLOCKED (uninterruptible — সাধারণত disk I/O)
# Z  → ZOMBIE (নিচে দেখুন)

PCB — যে structure টা process কে বাস্তব করে

OS নিজেও একটা program, আর যেকোনো program এর মতোই তার data structure আছে। প্রতিটা process সম্পর্কে যা জানা দরকার, তা একটা structure এ রাখা হয়। এর নাম PCB (Process Control Block — প্রতিটা process এর metadata রাখার kernel data structure); Linux এ এর নাম struct task_struct।

xv6 (একটা শিক্ষামূলক UNIX) এর structure টা ছোট বলে পড়া সহজ:

c 
/* xv6: the registers saved and restored to stop and
   restart a process — this IS the context switch */
struct context {
    int eip;     /* instruction pointer — কোথায় ছিল */
    int esp;     /* stack pointer */
    int ebx; int ecx; int edx;
    int esi; int edi; int ebp;
};

enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };

/* xv6: everything the kernel knows about one process */
struct proc {
    char *mem;                  /* start of process memory */
    uint sz;                    /* size of process memory */
    char *kstack;               /* bottom of kernel stack for this proc */
    enum proc_state state;      /* the state machine above */
    int pid;                    /* process ID */
    struct proc *parent;        /* who created it — needed for wait() */
    void *chan;                 /* if non-zero, sleeping on this channel */
    int killed;
    struct file *ofile[NOFILE]; /* open files — part of process state */
    struct inode *cwd;          /* current directory */
    struct context context;     /* switch here to run this process */
    struct trapframe *tf;       /* trap frame for current interrupt */
};

কয়েকটা field আলাদা করে দেখার মতো:

  • context — process থামলে তার register গুলো এখানে জমা হয়। আবার চালাতে হলে এখান থেকে ফিরিয়ে দিলেই সে ঠিক যেখানে ছিল সেখান থেকে চলতে শুরু করে। এটাই context switch, chapter 4 এ পুরোটা।
  • parent — কে এই process বানিয়েছে। wait() কাজ করার জন্য এটা দরকার, আর zombie আর orphan বোঝার জন্যও।
  • ofile[] — খোলা file। আবারও: I/O state process এর অংশ।
  • chan — BLOCKED হলে কীসের অপেক্ষায়। Linux এ এটাই /proc/<pid>/wchan — আটকে যাওয়া process debug করার সময় এটা প্রথম দেখার জিনিস।

লক্ষ করুন enum টায় তিনটার বেশি state আছে। আমাদের diagram এ ছিল RUNNING/READY/BLOCKED (xv6 এ RUNNING/RUNNABLE/SLEEPING), কিন্তু বাস্তবে শুরুর একটা state লাগে (EMBRYO) আর শেষেরও একটা — ZOMBIE।

Zombie — মরেও যায়নি

একটা process exit() করল। তার memory ছেড়ে দেওয়া যায়, file বন্ধ করা যায়। কিন্তু একটা জিনিস এখনো দরকার: তার exit code। Parent জানতে চায় কাজটা সফল হয়েছিল কি না (UNIX এ 0 মানে সফল, non-zero মানে না)।

তাই process টা মরার পরেও PCB টা রেখে দেওয়া হয়, শুধু exit status টুকু নিয়ে। এই অবস্থার নাম zombie। Parent wait() করলে status টা পায়, আর তখন kernel শেষ structure টাও মুছে ফেলে। 

  child: exit(0)
       │
       ▼
  ┌──────────┐   parent wait() করেনি
  │  ZOMBIE  │───────────────────────▶ PCB রয়ে গেল
  └──────────┘   (process table এ জায়গা দখল)
       │
       │ parent wait() করল → status পড়ল
       ▼
    সম্পূর্ণ মুছে গেল
ভুল ধারণা

"Zombie process CPU বা memory খাচ্ছে, তাই server ধীর।"

Zombie এর কোনো memory নেই, কোনো code চলছে না, CPU এর হিসাবে সে শূন্য। সে শুধু process table এর একটা entry আর একটা PID দখল করে আছে। একটা-দুটো zombie সম্পূর্ণ নিরীহ।

আসল বিপদ হলো জমতে থাকা zombie: PID এর একটা সীমা আছে (/proc/sys/kernel/pid_max), আর হাজারে হাজারে zombie জমলে নতুন process তৈরি করা যায় না — fork() ব্যর্থ হয় EAGAIN দিয়ে। এটা সবসময় parent এর bug: সে wait() করছে না।

Container এ এটা খুব সাধারণ। আপনি যদি Dockerfile এ সরাসরি CMD ["node", "server.js"] দেন, তাহলে node হয়ে যায় PID 1। কিন্তু PID 1 এর একটা বিশেষ দায়িত্ব আছে — যেসব process এর parent মরে গেছে (orphan), তারা PID 1 এর সন্তান হয়, আর PID 1 কেই তাদের wait() করতে হয়। Node সেটা করে না, তাই zombie জমে। সমাধান: docker run --init, বা tini/dumb-init কে PID 1 বানানো। Chapter 29 এ PID namespace এর সাথে এটা ফিরে আসবে। 

# zombie খুঁজুন
$ ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
# PPID কলামটাই দোষী parent

হাতে-কলমে — /proc দিয়ে abstraction দেখা

এই chapter এর সবকিছু কাল্পনিক শোনাতে পারে। শোনার দরকার নেই — Linux এ প্রতিটা process এর PCB এর বড় অংশ file হিসেবে পড়া যায়। একটা process চালিয়ে দেখুন: 

$ sleep 300 &
[1] 48231

$ ls /proc/48231/
cmdline   environ  fd/      maps     stat     status   wchan
cwd       exe      limits   mem      statm    syscall  task/

Address space টা দেখুন — উপরের diagram টা এখানে বাস্তব:

$ cat /proc/48231/maps
55d8c4e00000-55d8c4e02000 r--p ...  /usr/bin/sleep     ← code (read-only)
55d8c4e02000-55d8c4e06000 r-xp ...  /usr/bin/sleep     ← code (executable)
55d8c4e06000-55d8c4e08000 r--p ...  /usr/bin/sleep     ← static data
55d8c4e09000-55d8c4e0a000 rw-p ...  /usr/bin/sleep     ← writable data
55d8c5f0a000-55d8c5f2b000 rw-p ...  [heap]             ← heap
7f2a1c000000-7f2a1c028000 r--p ...  /lib/libc.so.6     ← shared library
7ffd4a5c0000-7ffd4a5e1000 rw-p ...  [stack]            ← stack
7ffd4a5f4000-7ffd4a5f8000 r--p ...  [vvar]

শেষ লাইনটা লক্ষ করুন — chapter 1 এ বলেছিলাম clock_gettime() syscall ছাড়াই ফেরে কারণ kernel একটা page map করে রাখে। ওই [vdso] টাই সেটা, প্রতিটা process এর address space এ।

State আর wait channel:

$ grep -E '^(State|Threads|VmRSS|VmSize)' /proc/48231/status
State:   S (sleeping)          ← BLOCKED
Threads: 1
VmSize:  2776 kB               ← virtual — বুক করা address space
VmRSS:   1024 kB               ← resident — সত্যিই RAM এ আছে

$ cat /proc/48231/wchan
hrtimer_nanosleep              ← ঠিক কীসের অপেক্ষায় আটকে আছে

VmSize আর VmRSS এর পার্থক্যটা মনে রাখুন — chapter 11 এ এটাই সবচেয়ে বেশি ভুল বোঝা মাপ। এখানে ২৭৭৬kB address space বুক করা, কিন্তু মাত্র ১০২৪kB সত্যিই RAM এ। বাকিটা lazy loading এর কারণে এখনো আসেইনি।

খোলা file গুলো:

$ ls -l /proc/48231/fd/
lrwx------ 0 -> /dev/pts/3      ← stdin
lrwx------ 1 -> /dev/pts/3      ← stdout
lrwx------ 2 -> /dev/pts/3      ← stderr

তিনটাই terminal এ যাচ্ছে। এটাই struct proc এর ofile[], শুধু file হিসেবে দেখানো।

আপনার কাজের সাথে যোগ

এই /proc টাই যেখান থেকে আপনার সব tool তথ্য নেয় — ps, top, htop সবাই /proc পড়ে। কোনো গোপন API নেই।

আর এই কারণেই container এ একটা বিখ্যাত সমস্যা হয়: Container এর ভিতরে /proc/cpuinfo আর /proc/meminfo সাধারণত host এর মান দেখায়, cgroup limit এর নয়। তাই JVM বা Go runtime যখন "কত core আছে?" জিজ্ঞেস করে, সে ৬৪ দেখে — যদিও আপনি ২ core এর quota দিয়েছেন। ফলাফল: ৬৪টা thread এর pool, অকারণ context switch, আর throttling। Chapter 7 আর 30 এ এটাই মূল আলোচনা। 

# container এর ভিতরে আসল limit কোথায়
$ cat /sys/fs/cgroup/cpu.max        # "200000 100000" = 2 core
$ cat /sys/fs/cgroup/memory.max     # byte এ
# অথচ:
$ nproc                             # host এর core সংখ্যা দেখাতে পারে

Process API — যা প্রতিটা OS এ থাকতে হয়

বিস্তারিত API পরের chapter এ, কিন্তু যেকোনো OS এ এই কাজগুলোর ব্যবস্থা থাকতেই হয়:

কাজকী করেPOSIX
Createনতুন process বানানোfork(), execve(), posix_spawn()
Destroyজোর করে থামানোkill() + signal
Waitশেষ হওয়া পর্যন্ত অপেক্ষাwait(), waitpid()
Controlথামানো/চালু করাSIGSTOP, SIGCONT
Statusতথ্য নেওয়া/proc, getrusage()

আপনি যখন terminal এ Ctrl+Z চাপেন, shell process টাকে SIGSTOP পাঠায় — সে RUNNING/READY থেকে একটা থেমে-থাকা অবস্থায় যায়। fg লিখলে SIGCONT যায়, আর সে আবার READY হয়। State machine টা আপনি প্রতিদিন হাতে চালান।

Time sharing আর space sharing

Resource ভাগ করার দুটো মৌলিক উপায়, আর দুটোই এই বইয়ে বারবার আসবে:

  • Time sharing — একজন কিছুক্ষণ ব্যবহার করে, তারপর আরেকজন। CPU এভাবেই ভাগ হয়। Network link ও।
  • Space sharing — resource টা ভাগ করে দেওয়া হয়। Disk এভাবে ভাগ হয়: একটা block একটা file কে দিলে, সেটা মুছে না ফেলা পর্যন্ত অন্য file পাবে না। Memory ও মূলত space-shared।

এই পার্থক্যটা কেন কাজের? কারণ দুটোর failure mode আলাদা। Time-shared resource শেষ হলে সবাই ধীর হয় (CPU contention)। Space-shared resource শেষ হলে কাজ ব্যর্থ হয় — ENOSPC, বা OOM kill। তাই capacity planning এ দুটোকে আলাদা করে ভাবতে হয়।

প্রশ্ন

  1. একটা process /proc/<pid>/maps এ দেখাচ্ছে VmSize: 4 GB কিন্তু VmRSS: 80 MB। আরেকটা দেখাচ্ছে VmSize: 200 MB, VmRSS: 190 MB। কোনটা OOM kill হওয়ার ঝুঁকিতে বেশি, আর কেন? আপনার উত্তরে "বুক করা" আর "সত্যিই পাওয়া" এর পার্থক্যটা ব্যবহার করুন।
  2. State machine এ BLOCKED থেকে সরাসরি RUNNING এ কোনো তীর নেই — I/O শেষ হলে process আগে READY তে যায়। এই বাড়তি ধাপটা কেন? সরাসরি RUNNING করে দিলে কী সমস্যা হতো?
  3. আপনার container এ node হলো PID 1, আর সে একটা shell script spawn করে যেটা নিজে আরও child বানিয়ে মরে যায়। কয়েক দিন পর fork() ব্যর্থ হতে শুরু করল EAGAIN দিয়ে। কী ঘটেছে, আর --init ঠিক কোন কাজটা করে যেটা node করছিল না?
  4. ps এ একটা process D state এ আটকে আছে, আর kill -9 দিয়েও মরছে না। কেন SIGKILL কাজ করছে না? /proc/<pid>/wchan পড়ে আপনি কী তথ্য পাবেন যা সিদ্ধান্ত নিতে সাহায্য করবে?
  5. Chapter 1 এ দেখেছেন OS "মিথ্যা বলে"। এই chapter এর /proc অংশ দেখে বলুন: container এর ভিতরে /proc/cpuinfo host এর core দেখানো — এটা কি abstraction নাকি leak? আপনার runtime কোন প্রশ্নটা জিজ্ঞেস করলে সঠিক উত্তর পেত?
  6. Time sharing আর space sharing এর পার্থক্য ব্যবহার করে বলুন: Kubernetes এ CPU limit ছাড়িয়ে গেলে pod throttled হয়, কিন্তু memory limit ছাড়ালে pod মারা যায়। এই অসমতা কেন — এটা Kubernetes এর নকশার খামখেয়াল, নাকি resource দুটোর প্রকৃতিগত পার্থক্য?
