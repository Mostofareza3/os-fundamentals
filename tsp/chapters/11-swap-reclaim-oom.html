Physical memory শেষ হলে — swap, reclaim, OOM

এখন পর্যন্ত ধরে নিয়েছি physical memory যথেষ্ট আছে। নেই। RAM ভরে গেলে কী বের করা হবে, কে সিদ্ধান্ত নেয়, আর কেন আপনার pod ঠিক ওই মুহূর্তে মারা যায় — এটাই Part 1 এর শেষ অংশ, আর production এ সবচেয়ে বেশি ভুল বোঝা অংশ।

Chapter 9-10 এ ধরে নিয়েছিলাম প্রতিটা page এর জন্য একটা frame আছে। বাস্তবে RAM সীমিত, আর সব process এর সব page একসাথে রাখার জায়গা নেই।

Crux

Physical memory এর চেয়ে বেশি page দরকার হলে OS কী করবে? কোন page বের করবে, কীভাবে সিদ্ধান্ত নেবে, আর ভুল সিদ্ধান্তের দাম কত?

Mechanism — present bit আর swap

পুরো ব্যবস্থাটা দাঁড়িয়ে আছে PTE এর একটা bit এর উপর, যেটা chapter 9 এ দেখেছি: P (present)। 

  P = 1 →  page টা RAM এ আছে, PFN বৈধ, সরাসরি ব্যবহার করো

  P = 0 →  page টা RAM এ নেই → page fault
           তখন PTE এর বাকি bit গুলো অন্য অর্থ বহন করে:
           সেখানে থাকে swap slot এর ঠিকানা

  ┌────────────────────────────────────────┐
  │  P=1:  [ PFN | flags | 1 ]             │  RAM এ
  │  P=0:  [ swap offset | type | 0 ]      │  disk এ
  └────────────────────────────────────────┘
     একই ৬৪ bit, দুটো সম্পূর্ণ আলাদা অর্থ

এটা একটা মিতব্যয়ী নকশা: page RAM এ না থাকলে PFN রাখার দরকার নেই, তাই ওই bit গুলোতেই disk এর ঠিকানা রাখা হয়।

Page fault এর পুরো পথটা chapter 9 এ দেখেছি। এখন যে শাখাটা গুরুত্বপূর্ণ: 

  access → P=0 → page fault → kernel

  kernel:
    ১. PTE থেকে swap offset পড়ো
    ২. একটা free frame দরকার
         │
         ├── free frame আছে? → ব্যবহার করো
         │
         └── নেই? → কাউকে বের করতে হবে (reclaim)
                    → dirty হলে আগে disk এ লেখো
                    → তারপর frame টা নাও
    ৩. disk থেকে page পড়ো  ← ধীর! process BLOCKED
    ৪. PTE হালনাগাদ করো: PFN বসাও, P=1
    ৫. process কে READY করো, instruction আবার চালাও

ধাপ ৩ টাই আসল দাম। এটা একটা major fault — chapter 10 এর table এ দেখেছি NVMe তে ~২০–১০০µs, HDD তে ~১০ms। CPU এর দৃষ্টিতে এটা অনন্তকাল।

কখন reclaim শুরু হয়

OS memory একেবারে শেষ হওয়া পর্যন্ত অপেক্ষা করে না — তাহলে প্রতিটা allocation একটা disk write এর জন্য আটকে থাকত। বরং দুটো সীমা রাখে: 

  free memory
      ▲
      │
  HW ─┼─────────────────  high watermark
      │    ╲              এখানে পৌঁছালে background reclaim
      │     ╲             থেমে যায়
      │      ╲
  LW ─┼───────╲─────────  low watermark
      │        ╲          এর নিচে নামলে kswapd জেগে ওঠে,
      │         ╲         background এ page বের করতে থাকে
  min ┼──────────╲──────  এর নিচে নামলে direct reclaim:
      │                   allocation করা thread নিজেই
      ▼                   reclaim করতে বাধ্য হয় → stall!

  background reclaim (kswapd)  → আপনার latency তে দেখা যায় না
  direct reclaim               → আপনার thread আটকে থাকে

এই পার্থক্যটা গুরুত্বপূর্ণ। kswapd নামের একটা kernel thread আগে থেকেই page বের করে রাখে, তাই allocation দ্রুত হয়। কিন্তু চাহিদা খুব দ্রুত বাড়লে direct reclaim হয় — যে thread memory চাইছে, সে নিজেই page বের করার কাজ করতে বাধ্য হয়। এটা সরাসরি latency spike। 

# direct reclaim হচ্ছে কি (এই সংখ্যা বাড়া মানে চাপ)
$ grep -E 'pgscan_direct|pgsteal_direct|pgscan_kswapd' /proc/vmstat

# watermark গুলো
$ grep -A3 'Node 0, zone   Normal' /proc/zoneinfo | head -6

Policy — কোন page বের করব

এখন আসল প্রশ্ন। লক্ষ্য: যেটা আর লাগবে না সেটা বের করো। কিন্তু ভবিষ্যৎ জানা যায় না।

আদর্শ — OPT

তত্ত্বগতভাবে সেরা নীতি: যে page সবচেয়ে দূর ভবিষ্যতে লাগবে, সেটা বের করো। এর নাম OPT বা Belady's algorithm।

এটা বাস্তবায়নযোগ্য নয় — ভবিষ্যৎ জানতে হয়। কিন্তু এটা একটা মাপকাঠি হিসেবে অমূল্য: আপনার আসল নীতি OPT এর কত কাছে, সেটাই বলে দেয় আর কতটা উন্নতি সম্ভব।

বাস্তব নীতিগুলোর তুলনা

একটা reference stream ধরে তুলনা করা যাক — cache এ ৩টা page রাখার জায়গা আছে: 

  access:  0  1  2  0  1  3  0  3  1  2  1  1

  FIFO (যে আগে এসেছে, সে আগে যাবে):
    hit rate ≈ 36%

  LRU (সবচেয়ে বেশিক্ষণ অব্যবহৃত):
    hit rate ≈ 54%

  OPT (আদর্শ):
    hit rate ≈ 63%

  Random:
    hit rate ≈ 40% (গড়ে)

LRU ভালো করে কারণ সে locality কে কাজে লাগায় — যা সাম্প্রতিক অতীতে ব্যবহৃত হয়েছে, তা শিগগিরই আবার লাগবে। Chapter 10 এর temporal locality, শুধু আলাদা মাপে।

একটা মজার বিষয়: FIFO তে Belady's anomaly ঘটতে পারে — cache বড় করলে hit rate কমে যায়। LRU তে এটা অসম্ভব, কারণ LRU এর একটা "stack property" আছে: N আকারের cache এ যা থাকে, N+1 আকারের cache এ তার সবটাই থাকে।

ভুল ধারণা

"LRU সেরা বাস্তব নীতি, kernel LRU ব্যবহার করে, তাই আমার application এও LRU cache বানানো উচিত।"

কোনো kernel সত্যিকারের LRU ব্যবহার করে না — করতে পারে না। সত্যিকারের LRU এর জন্য প্রতিটা memory access এ একটা list হালনাগাদ করতে হবে। প্রতিটা load/store এ। সেটা memory কে কয়েকগুণ ধীর করে দিত।

বাস্তবে যা হয়: hardware শুধু A (accessed) bit সেট করে (chapter 9), আর kernel সেটা দেখে একটা আনুমানিক LRU চালায় — clock algorithm বা দুই-list পদ্ধতি। "সবচেয়ে পুরনো" নয়, "সম্প্রতি ছোঁয়া হয়নি"।

আর application স্তরে LRU প্রায়ই ভুল পছন্দ: একবার-স্ক্যান করা বড় data (table scan, log প্রক্রিয়াকরণ) LRU cache সম্পূর্ণ ধুয়ে দেয় — যে page গুলো আর কখনো লাগবে না, সেগুলোই সব জায়গা নিয়ে নেয়। এই কারণেই Postgres clock-sweep ব্যবহার করে, আর আধুনিক cache LFU-ঘেঁষা (Redis এর allkeys-lfu, বা TinyLFU/W-TinyLFU)।

Linux এ আসলে কী হয়

Linux এর reclaim দুটো list এর উপর দাঁড়ানো: 

  ┌──────────────────────────────────────────────┐
  │  ACTIVE list    — সাম্প্রতিক ব্যবহৃত         │
  │  ┌────┬────┬────┬────┐                       │
  │  │ p1 │ p2 │ p3 │ p4 │                       │
  │  └────┴────┴────┴────┘                       │
  │         │ দুবার ছোঁয়া হলে উপরে ওঠে           │
  │         │ না ছোঁয়া হলে নিচে নামে ↓          │
  │  ┌──────▼───────────────┐                    │
  │  │  INACTIVE list       │  ← reclaim এখান    │
  │  │  ┌────┬────┬────┐    │    থেকে শুরু করে   │
  │  │  │ p5 │ p6 │ p7 │    │                    │
  │  │  └────┴────┴────┘    │                    │
  │  └──────────────────────┘                    │
  └──────────────────────────────────────────────┘

  আর প্রতিটা list দুই ধরনের page এর জন্য আলাদা:
    anon  — process এর নিজের memory (heap, stack) → swap এ যায়
    file  — file থেকে আসা page (page cache)      → শুধু ফেলে দেওয়া যায়
                                                    (dirty হলে আগে লেখা)

anon আর file page এর পার্থক্যটা গুরুত্বপূর্ণ: file page ফেলে দেওয়া সস্তা (disk এ কপি আছেই), কিন্তু anon page বের করতে swap এ লিখতে হয়। তাই kernel স্বাভাবিকভাবে file page আগে বের করে।

কতটা anon এর দিকে ঝুঁকবে, সেটা একটা knob: 

# 0 = anon page যতটা সম্ভব এড়াও, 100 = সমানভাবে দেখো
# আধুনিক default 60, কিন্তু cgroup এ আলাদা করে দেওয়া যায়
$ sysctl vm.swappiness
vm.swappiness = 60

# এই মুহূর্তে কোন list এ কত আছে
$ grep -E 'Active|Inactive' /proc/meminfo
Active(anon):    2451232 kB
Inactive(anon):   184020 kB
Active(file):    1203344 kB
Inactive(file):  4821092 kB
যেখানে source টা পুরনো

OSTEP এই chapter শেষ করে একটা পরামর্শ দিয়ে: thrashing এর সবচেয়ে ভালো সমাধান হলো "buy more memory"। ২০২৬ এ এটা সম্ভবত পুরো বইয়ের সবচেয়ে পুরনো বাক্য।

আপনি memory কিনতে পারেন না। আপনার সীমা একটা memory.max বা একটা instance SKU, আর দুটোই আপনার হাতের বাইরে। Memory এখন datacenter এর সবচেয়ে বড় খরচের খাত, তাই পুরো একটা প্রযুক্তি-শ্রেণী তৈরি হয়েছে ইচ্ছাকৃত overcommit এর জন্য:

  • zswap / zram — swap করার আগে page টা compress করে RAM এই রাখা। Disk এ যাওয়ার চেয়ে ১০০ গুণ দ্রুত।
  • KSM (Kernel Samepage Merging) — একই বিষয়বস্তুর page গুলো খুঁজে এক করে দেওয়া। একই container image থেকে চলা বহু pod এ কাজে লাগে।
  • MGLRU (Multi-Gen LRU) — Linux 6.1 থেকে পাওয়া, পুরনো দুই-list পদ্ধতির বদলে একাধিক প্রজন্ম। উল্লেখযোগ্যভাবে ভালো সিদ্ধান্ত নেয়, বিশেষত চাপে।
  • PSI (Pressure Stall Information) — নিচে দেখব, thrashing মাপার আধুনিক উপায়।

অর্থাৎ replacement policy এক দশক অপ্রাসঙ্গিক ছিল (RAM সস্তা ছিল), তারপর আগের চেয়ে বেশি প্রাসঙ্গিক হয়ে উঠেছে। 

# MGLRU চালু আছে কি
$ cat /sys/kernel/mm/lru_gen/enabled
0x0007                   ← শূন্য নয় মানে চালু

# zswap
$ cat /sys/module/zswap/parameters/enabled

Thrashing আর PSI

Thrashing হলো সেই অবস্থা যখন system তার বেশিরভাগ সময় page আনা-নেওয়ায় ব্যয় করে, আসল কাজে নয়। Working set RAM এর চেয়ে বড় হলে এটা হয়।

পুরনো লক্ষণ ছিল CPU কম কিন্তু disk ব্যস্ত। কিন্তু এটা মাপার একটা সরাসরি উপায় এখন আছে, আর এটা OSTEP এ নেই: 

$ cat /proc/pressure/memory
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0

# some = অন্তত একটা task memory এর জন্য আটকে আছে (% সময়)
# full = সব task আটকে — কেউ এগোচ্ছে না

# cgroup-ভিত্তিক (container এর নিজের চাপ)
$ cat /sys/fs/cgroup/memory.pressure

PSI হলো thrashing এর আধুনিক সংকেত। some ১০% এর উপরে মানে memory চাপ সত্যিকারের latency ঘটাচ্ছে; full শূন্যের উপরে মানে system কার্যত থেমে আছে। Kubernetes এর কিছু autoscaler এখন এটাই ব্যবহার করে, কারণ memory usage এর শতকরা হিসাবের চেয়ে এটা অনেক ভালো সংকেত।

Container এ — memory.max আর OOM

এবার সেই অংশ যা production এ সবচেয়ে বেশি কাটে। Chapter 7 এ CPU limit দেখেছি — ছাড়ালে throttle হয়, অর্থাৎ ধীর হয়। Memory সম্পূর্ণ আলাদা। 

  ┌─────────────────────────────────────────────────┐
  │  memory.high  = 900M   ← নরম সীমা               │
  │     ছাড়ালে: reclaim এর চাপ বাড়ে, allocation     │
  │     ধীর হয় (throttle), কিন্তু process বাঁচে     │
  ├─────────────────────────────────────────────────┤
  │  memory.max   = 1G     ← কঠিন সীমা              │
  │     ছাড়ালে: reclaim চেষ্টা, ব্যর্থ হলে          │
  │     ►► OOM kill ◄◄                              │
  └─────────────────────────────────────────────────┘

  CPU limit ছাড়ালে  →  ধীর হও (throttle)
  Memory limit ছাড়ালে →  মরে যাও (SIGKILL)

  কারণ: CPU time-shared — পরে পাওয়া যায়।
        Memory space-shared — এখনই লাগবে, নইলে কাজ অসম্ভব।
        (Chapter 2 এর time vs space sharing)

এই অসমতাটা Kubernetes এর খামখেয়াল নয় — এটা resource দুটোর প্রকৃতিগত পার্থক্য, আর chapter 2 এ time sharing বনাম space sharing হিসেবে এটা শুরু করেছিলাম। 

# container এ আসল সীমা আর বর্তমান ব্যবহার
$ cat /sys/fs/cgroup/memory.max
1073741824
$ cat /sys/fs/cgroup/memory.current
812334592

# OOM কতবার হয়েছে, আর reclaim এর চাপ
$ cat /sys/fs/cgroup/memory.events
low 0
high 4821          ← memory.high ছাড়িয়েছে 4821 বার
max 12             ← memory.max এ ধাক্কা খেয়েছে 12 বার
oom 3              ← OOM অবস্থা 3 বার
oom_kill 3         ← 3 বার kill হয়েছে

# বিস্তারিত হিসাব — anon, file, kernel আলাদা করে
$ cat /sys/fs/cgroup/memory.stat | head -12
ভুল ধারণা

"আমার container এ 1GB limit, heap 600MB, তাই 400MB headroom আছে।"

না। memory.max আপনার heap গোনে না — সে cgroup এর মোট charge গোনে, আর তাতে অনেক কিছু আছে যা আপনি হিসাবে রাখেন না:

  • Page cache — আপনার পড়া/লেখা file গুলো (এটাই প্রায়ই সবচেয়ে বড় অংশ)
  • Anonymous memory — heap, stack, সব thread এর stack
  • Kernel memory — socket buffer, dentry, inode cache, page table নিজে
  • tmpfs / shm — /dev/shm এ কিছু রাখলে সেটাও

তাই একটা service যেটা প্রচুর file পড়ে, তার page cache limit ভরিয়ে OOM ঘটাতে পারে — যদিও heap ছোট। সৌভাগ্যক্রমে page cache reclaimable, তাই kernel আগে সেটাই বের করে। কিন্তু হিসাবটা আপনার মাথায় থাকা দরকার। 

# আসলে কী charge হচ্ছে
$ cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file|slab|sock|kernel)'
anon 524288000        ← heap, stack
file 268435456        ← page cache!
slab 41943040         ← kernel structure
sock 8388608          ← network buffer
ভুল ধারণা

"Swap থাকা মানে system খারাপ — যেকোনো swap ব্যবহার সমস্যার চিহ্ন, তাই swapoff -a করে দেওয়া উচিত।"

Swap সম্পূর্ণ বন্ধ করা প্রায়ই পরিস্থিতি খারাপ করে। কারণ swap না থাকলে kernel এর reclaim করার একটাই উপায় থাকে: file page (page cache) ফেলে দেওয়া। ফলে আপনার কখনো-ব্যবহৃত-না-হওয়া anon page গুলো RAM দখল করে বসে থাকে, আর যে page cache টা সত্যিই কাজে লাগছিল সেটা বারবার বেরিয়ে যায় — অর্থাৎ বেশি disk I/O, বেশি major fault।

আরও: swap না থাকলে OOM kill আগে আসে, কারণ kernel এর হাতে বিকল্প কম।

আসল নিয়মটা হলো: swap এর পরিমাণ নয়, swap এর হার দেখুন। কিছু page swap এ পড়ে থাকা সুস্থ — সেগুলো লাগছে না। কিন্তু প্রতি সেকেন্ডে হাজার page আনা-নেওয়া হচ্ছে মানে thrashing। 

# si/so = swap in/out প্রতি সেকেন্ডে — এটাই আসল সংকেত
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io----
 r  b   swpd   free  buff  cache   si   so    bi    bo
 1  0 524288 102400 20480 819200    0    0     0     0   ← সুস্থ
 4  2 524288  40960  8192 204800  892 1024  4821  5102   ← thrashing!

Kubernetes ঐতিহাসিকভাবে swap বন্ধ করতে বলত (kubelet চলতই না), কিন্তু ১.২২ থেকে NodeSwap feature এসেছে আর ১.৩০+ এ এটা আরও পরিণত — কারণ সম্পূর্ণ নিষেধাজ্ঞা ভুল ছিল।

OOM killer — কাকে মারে, কেন

Reclaim ব্যর্থ হলে kernel কাউকে মারতে বাধ্য হয়। সিদ্ধান্তটা একটা score এর ভিত্তিতে: 

  oom_score ← মূলত process এর memory ব্যবহারের অনুপাত
              (cgroup এ: ওই cgroup এর মধ্যে সবচেয়ে বড়)

  সমন্বয় করা যায়:
    oom_score_adj = -1000  →  কখনো মারবে না (অনাক্রম্য)
    oom_score_adj =     0  →  স্বাভাবিক
    oom_score_adj = +1000  →  সবার আগে মারো

  ফল: সাধারণত সবচেয়ে বড় process টাই মরে —
       যেটা প্রায়ই আপনার মূল application,
       কোনো ছোট sidecar নয়।
# কে মরার সম্ভাবনায় এগিয়ে
$ for p in /proc/[0-9]*; do
    printf "%s %s %s\n" "$(cat $p/oom_score 2>/dev/null)" \
      "${p#/proc/}" "$(cat $p/comm 2>/dev/null)"
  done | sort -rn | head -5

# কেন মরল — dmesg এ পূর্ণ হিসাব থাকে
$ dmesg | grep -i -A5 'killed process'

# container এ exit code 137 = 128 + 9 (SIGKILL)
$ kubectl get pod mypod -o jsonpath='{.status.containerStatuses[0].lastState}'
# reason: OOMKilled

Chapter 3 এ exit code 137 এর কথা বলেছিলাম — এখানে তার উৎসটা সম্পূর্ণ হলো: 128 + 9, অর্থাৎ SIGKILL, আর container এ সেটা প্রায় সবসময় OOM killer।

আপনার কাজের সাথে যোগ

Runtime এর heap সীমা আর cgroup এর সীমা আলাদা, আর প্রথমটা দ্বিতীয়টার চেয়ে বড় হলে OOM kill অনিবার্য। এটাই container এ সবচেয়ে সাধারণ memory bug: 

# ভুল: JVM heap = limit, কিন্তু JVM এর heap-বহির্ভূত
# memory (metaspace, thread stack, JIT, direct buffer) ও লাগে
limits.memory: 1Gi
JAVA_OPTS: -Xmx1g          ← OOM kill নিশ্চিত

# ঠিক: heap কে limit এর একটা অংশ রাখো
limits.memory: 1Gi
JAVA_OPTS: -XX:MaxRAMPercentage=70   ← cgroup পড়ে হিসাব করে

# Node
limits.memory: 1Gi
NODE_OPTIONS: --max-old-space-size=700

# Go — GOMEMLIMIT (1.19+), soft limit, GC কে চাপ দেয়
env:
  - name: GOMEMLIMIT
    value: "900MiB"

Go এর GOMEMLIMIT বিশেষভাবে উল্লেখযোগ্য: এটা একটা soft limit — ছাড়ালে GC আরও আগ্রাসীভাবে চলে, মারা যায় না। এটা cgroup এর memory.high এর সমতুল্য দর্শন, আর অনেক সময় এটাই সঠিক হাতিয়ার।

আর RSS দেখে memory leak সিদ্ধান্ত নেওয়া বিপজ্জনক: chapter 8 এ দেখেছি free() করলে RSS কমে না। তার উপরে MADV_FREE ব্যবহার করা allocator (jemalloc, Go runtime) page টা kernel কে "চাইলে নিতে পারো" বলে রাখে — RSS তখনো গোনা হয়, যতক্ষণ kernel সত্যিই নেয়নি। তাই leak খুঁজতে smaps_rollup এর Pss আর Private_Dirty দেখা ভালো।

Part 1 শেষ — যা দাঁড়াল

এগারোটা chapter এ আমরা virtualization এর পুরো স্তম্ভটা দেখলাম। সবকিছু একটা শিকলে বাঁধা: 

  একটা program চালানো হলো
       │
       ├─ process তৈরি (ch 2)  — PCB, state machine
       ├─ fork/exec (ch 3)     — COW দিয়ে সস্তা copy
       ├─ trap ও LDE (ch 4)    — নিয়ন্ত্রণ না হারিয়ে চালানো
       │
       ├─ scheduling (ch 5-7)  — কে, কখন, কোথায়, কতটুকু
       │      MLFQ → EEVDF → cgroup
       │
       ├─ address space (ch 8) — illusion + allocator
       ├─ translation (ch 9)   — VPN→PFN, page table
       ├─ TLB (ch 10)          — নইলে ৫ গুণ ধীর
       └─ reclaim/OOM (ch 11)  — RAM শেষ হলে

  প্রতিটা স্তরে একই কাঠামো ফিরে এসেছে:
    mechanism (কীভাবে সম্ভব) বনাম policy (কোনটা উচিত)
    আর hardware এর সহযোগিতা ছাড়া কোনোটাই সম্ভব নয়।

Part 2 এ আমরা একটা ভিন্ন সমস্যায় যাব। এখন পর্যন্ত process গুলো আলাদা ছিল — আলাদা address space, আলাদা memory। কিন্তু একই memory ভাগ করে একাধিক execution চললে? সেখানে chapter 1 এর সেই counter++ ফিরে আসবে, আর এবার আমরা সম্পূর্ণ উত্তর দেব।

প্রশ্ন

  1. PTE তে P=0 হলে বাকি bit গুলো swap offset রাখে। এই পুনর্ব্যবহারটা মিতব্যয়ী, কিন্তু একটা নিরাপত্তা প্রশ্ন তোলে: ওই bit গুলোতে যদি এমন একটা physical address থাকে যা সত্যিই বিদ্যমান, আর CPU speculatively সেটা পড়ে ফেলে? (এটাই L1TF দুর্বলতার মূল। Linux এর সমাধান কী হতে পারে বলে আপনার মনে হয়?)
  2. Background reclaim (kswapd) আর direct reclaim এর পার্থক্য আপনার p99 latency তে কীভাবে দেখা যায়? /proc/vmstat এর কোন সংখ্যাগুলো দেখে আপনি বলতে পারবেন কোনটা ঘটছে?
  3. কোনো kernel সত্যিকারের LRU চালায় না। যদি চালাত, তাহলে প্রতিটা memory access এ কী অতিরিক্ত কাজ লাগত? সেই খরচটা hardware এ করা সম্ভব ছিল কি — আর A bit পদ্ধতিটা কী কী তথ্য হারায়?
  4. একটা container এ heap ৬০০MB, memory.max ১GB, তবু OOM kill হচ্ছে। memory.stat এ আপনি কোন চারটা খাত দেখবেন, আর প্রতিটার জন্য সমাধান কী আলাদা হবে?
  5. Swap বন্ধ করলে OOM kill আগে আসে — কেন? আপনার উত্তরে anon আর file page এর পার্থক্যটা ব্যবহার করুন, আর বলুন কেন "swap আছে মানে খারাপ" এর বদলে "swap এর হার" দেখা উচিত।
  6. CPU limit ছাড়ালে throttle, memory limit ছাড়ালে kill। Chapter 2 এর time sharing বনাম space sharing দিয়ে এই অসমতা ব্যাখ্যা করুন। এখন ভাবুন disk I/O — সেটা কোন শ্রেণীর, আর cgroup এ io.max ছাড়ালে কী হওয়া উচিত বলে আপনার মনে হয়?
