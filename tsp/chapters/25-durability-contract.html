Durability contract — write, fsync, আর যা হারায়

Chapter 1 এ প্রশ্নটা তুলেছিলাম: write() ফেরা মানে কি data নিরাপদ? উত্তর: না। এই chapter এ পুরো শৃঙ্খলটা — application থেকে NAND cell পর্যন্ত — আর প্রতিটা ধাপে ঠিক কী প্রতিশ্রুতি আছে। Data হারানো সবচেয়ে খারাপ ব্যর্থতা, আর এই API টা আপনি রোজ ডাকেন।

Chapter 24 এ দেখেছি write() শুধু page cache এ পৌঁছায়। এখন প্রশ্ন: তাহলে নিশ্চিত হব কীভাবে?

Crux

একটা লেখা যে সত্যিই টিকে থাকবে — power loss, kernel panic, বা container kill এর পরেও — সেটা নিশ্চিত করতে কী কী করতে হবে? আর প্রতিটা ধাপে কে কী প্রতিশ্রুতি দেয়?

পুরো শৃঙ্খল

  আপনার data কোথায় কোথায় থাকতে পারে:

  ┌──────────────────────────────────────────────────────┐
  │ ১. application buffer  (যেমন stdio এর FILE*)         │
  │    হারায়: process crash এ                            │  ← volatile
  ├──────────────────────────────────────────────────────┤
  │      ↓ fflush()  বা  বড় লেখা                        │
  ├──────────────────────────────────────────────────────┤
  │ ২. kernel page cache                                 │
  │    হারায়: power loss, kernel panic এ                 │  ← volatile
  │    টেকে:  process crash, container kill এ ✓          │
  ├──────────────────────────────────────────────────────┤
  │      ↓ fsync() / fdatasync()                         │
  ├──────────────────────────────────────────────────────┤
  │ ৩. device এর write cache (DRAM, drive এর ভিতরে)      │
  │    হারায়: power loss এ — যদি PLP না থাকে             │  ← ⚠ এখানেই
  ├──────────────────────────────────────────────────────┤     বেশিরভাগ
  │      ↓ FLUSH / FUA command (fsync এটাও পাঠায়)        │     ভুল হয়
  ├──────────────────────────────────────────────────────┤
  │ ৪. NAND cell / platter — সত্যিকারের stable storage   │  ← এখন নিরাপদ
  └──────────────────────────────────────────────────────┘

  মূল কথা: process crash আর power loss দুটো
           সম্পূর্ণ আলাদা failure mode।
           ২ নম্বর স্তর প্রথমটায় বাঁচে, দ্বিতীয়টায় নয়।

এই পার্থক্যটা কাজের: আপনার application যদি শুধু নিজের crash থেকে বাঁচতে চায়, page cache যথেষ্ট — kernel বেঁচে আছে, সে পরে লিখে দেবে। কিন্তু power loss বা kernel panic এর বিরুদ্ধে fsync() ছাড়া কিছুই নেই।

API — কোনটা কী করে

Callকী নিশ্চিত করেখরচ
write() data page cache এ ~১ µs
fdatasync(fd) file এর data + অপরিহার্য metadata (size) stable storage এ ~১০ µs – ১০ ms
fsync(fd) data + সব metadata (mtime সহ) ~২০ µs – ২০ ms
sync() সব file system এর সব dirty page (অন্ধভাবে) খুব বেশি
O_SYNC flag প্রতিটা write() নিজেই sync প্রতি লেখায় পূর্ণ খরচ

fsync আর fdatasync এর পার্থক্যটা ব্যবহারিক: fsync mtime ও লেখে, যেটা একটা বাড়তি metadata write। একটা database এর WAL file এ mtime কেউ দেখে না — তাই fdatasync যথেষ্ট, আর সেটা মাপা যায় দ্রুত। Postgres এর wal_sync_method ঠিক এই পছন্দটা।

সবচেয়ে বেশি ভুল হয় — parent directory

ভুল ধারণা

"File টা fsync করেছি, তাই নিরাপদ।"

একটা নতুন file এর ক্ষেত্রে এটা যথেষ্ট নয়। কারণ file এর নাম file এর ভিতরে নেই — chapter 22 এর সেই অন্তর্দৃষ্টি: নামটা parent directory তে থাকে। 

int fd = open("data.txt", O_CREAT | O_WRONLY, 0644);
write(fd, buf, len);
fsync(fd);          /* data নিরাপদ, inode নিরাপদ */
close(fd);
/* ⚡ power loss এখানে */

/* Reboot এর পর: data.txt টা হয়তো নেই!
   inode আর data block লেখা হয়েছে, কিন্তু
   directory তে "data.txt → inode" entry টা
   এখনো page cache এ ছিল। */

সঠিক রূপ — parent directory ও fsync করতে হবে: 

int fd = open("data.txt", O_CREAT | O_WRONLY, 0644);
write(fd, buf, len);
fsync(fd);
close(fd);

int dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);         /* ← এই লাইনটাই বাদ পড়ে */
close(dfd);

কখন লাগে: file তৈরি, মুছা, বা rename করলে — অর্থাৎ যখন directory entry বদলায়। শুধু বিদ্যমান file এ লিখলে লাগে না।

নিরাপদ update এর সম্পূর্ণ রূপ

Chapter 22 এ atomic rename দেখেছি। এখন তার সাথে durability যোগ করে পূর্ণ protocol:

c 
/* The complete safe-replace protocol.
   Every step exists because of a specific failure mode. */
int safe_replace(const char *path, const void *data, size_t len) {
    char tmp[PATH_MAX];
    snprintf(tmp, sizeof(tmp), "%s.tmp.%d", path, getpid());

    /* 1. Write to a temporary file */
    int fd = open(tmp, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return -1;

    if (write_all(fd, data, len) < 0) goto fail;

    /* 2. Data to stable storage BEFORE the rename.
          Without this: rename succeeds, then power loss, and
          config.txt exists but holds garbage — WORSE than
          keeping the old version. */
    if (fsync(fd) < 0) goto fail;

    /* 3. Check close() too — on some filesystems (NFS!)
          errors surface only here. */
    if (close(fd) < 0) { fd = -1; goto fail; }
    fd = -1;

    /* 4. The atomic swap (chapter 22) */
    if (rename(tmp, path) < 0) goto fail;

    /* 5. Persist the DIRECTORY ENTRY created by the rename */
    int dfd = open(dirname_of(path), O_RDONLY | O_DIRECTORY);
    if (dfd < 0) return -1;
    if (fsync(dfd) < 0) { close(dfd); return -1; }
    close(dfd);

    return 0;

fail:
    if (fd >= 0) close(fd);
    unlink(tmp);
    return -1;
}

পাঁচটা ধাপ, আর প্রতিটা একটা নির্দিষ্ট failure mode এর উত্তর। ধাপ ২ বাদ দিলে সবচেয়ে খারাপ ফল: আপনি পুরনো ভালো version হারিয়ে একটা corrupt নতুন version পাবেন।

fsyncgate — যখন fsync নিজেই মিথ্যা বলে

২০১৮ — একটা শিক্ষামূলক বিপর্যয়

Postgres এর developer রা একটা ভয়ানক জিনিস আবিষ্কার করলেন। প্রশ্নটা ছিল: fsync() যদি ব্যর্থ হয়, তখন কী হয়? 

write(fd, buf, len);      /* page cache এ, DIRTY */
fsync(fd);                /* → -1, EIO!  disk error */

/* এখন আপনি কী করবেন? স্বাভাবিক প্রতিক্রিয়া: retry */
fsync(fd);                /* → 0, সফল!  */

/* ⚠ কিন্তু এই "সফল" একটা মিথ্যা।
   Linux প্রথম ব্যর্থতায় page টাকে CLEAN চিহ্নিত
   করে দিয়েছিল (error টা রিপোর্ট করার পর সে ধরে
   নিয়েছিল কাজ শেষ)। তাই দ্বিতীয় fsync এর কাছে
   লেখার মতো কিছুই নেই — সে সফল হয়, কারণ
   করার কিছু নেই। আপনার data চিরতরে হারিয়ে গেছে। */

এই ঘটনার নাম fsyncgate, আর এর ফলাফল:

  • Postgres নিজের আচরণ বদলাল: fsync ব্যর্থ হলে সে এখন PANIC করে — পুরো server বন্ধ করে WAL থেকে recovery চালায়। কারণ একটাই নিরাপদ অনুমান: "আমি জানি না কী হারিয়েছে, তাই আবার শুরু করি।"
  • MySQL, MongoDB, WiredTiger — সবাই একই পথে গেল।
  • Linux kernel (4.13+) error reporting উন্নত করল, কিন্তু মূল নীতিটা বদলায়নি: একটা ব্যর্থ fsync retry করা নিরাপদ নয়।

শিক্ষা: fsync() ব্যর্থ হলে আপনার process এর আর কোনো নিরাপদ পথ নেই তাতে লেখা চালিয়ে যাওয়ার। Crash করুন আর recovery চালান — এটাই সঠিক আচরণ, আর এটা প্রতিস্বজ্ঞাত।

Device এর প্রতারণা — আর PLP

fsync() সফল হলো, kernel তার কাজ করেছে। কিন্তু drive কি সত্যিই লিখেছে? 

  প্রতিটা drive এর ভিতরে একটা DRAM write cache আছে
  (~২৫৬ MB – ১ GB সাধারণ SSD তে)।

  fsync() একটা FLUSH command পাঠায়:
    "তোমার cache খালি করে NAND এ লেখো"

  সৎ drive:     FLUSH পেয়ে সত্যিই লেখে, তারপর সাড়া দেয়
  অসৎ drive:    সাথে সাথে "হয়ে গেছে" বলে দেয় (দ্রুত দেখায়!)
                → power loss এ ওই data হারায়

  ঐতিহাসিকভাবে কিছু consumer drive এটা করত।
  আজকের বড় সমস্যা আলাদা:

  PLP (Power Loss Protection — drive এর ভিতরে capacitor,
  যা power গেলে cache টা NAND এ লেখার মতো যথেষ্ট
  বিদ্যুৎ জমা রাখে)

  Enterprise SSD  → PLP আছে → cache নিরাপদ, fsync দ্রুত
  Consumer SSD    → PLP নেই → FLUSH সত্যিই NAND পর্যন্ত
                                যেতে হয় → ধীর

  এই কারণেই একটা enterprise SSD এ fsync ~২০µs আর
  একটা consumer SSD এ ~২ms হতে পারে — ১০০ গুণ।
  Benchmark এ consumer drive দ্রুত দেখাতে পারে
  (cache এ লিখে সাড়া দেয়), কিন্তু fsync-ভারী
  workload এ enterprise drive জেতে।
# write cache চালু আছে কি
$ sudo hdparm -W /dev/sda

# NVMe তে volatile write cache
$ sudo nvme id-ctrl /dev/nvme0 | grep -i vwc
vwc  : 0x1        ← volatile write cache আছে

# drive টা কি FLUSH সমর্থন করে / PLP আছে কি
$ sudo nvme id-ctrl /dev/nvme0 | grep -i -E 'apsta|rtd3'
# PLP সাধারণত datasheet এ থাকে; "Enhanced Power Loss

খরচ আর trade-off

fsync() খরচি, তাই প্রতিটা system এ একটা knob থাকে — আর সেই knob টা আসলে "কতটুকু data হারাতে রাজি" এর একটা ঘোষণা:

SystemSettingহারানোর ঝুঁকি
Postgres synchronous_commit = on কিছুই না (committed transaction)
synchronous_commit = off শেষ wal_writer_delay (~২০০ms)
Redis appendfsync always কিছুই না (কিন্তু খুব ধীর)
appendfsync everysec (default) শেষ ১ সেকেন্ড
appendfsync no OS যা জমিয়েছে (~৩০ সেকেন্ড)
SQLite PRAGMA synchronous = FULL কিছুই না
synchronous = OFF database corrupt হতে পারে
MySQL innodb_flush_log_at_trx_commit = 1 / 2 / 0 কিছুই না / OS crash এ ১s / ১s
etcd সবসময় fsync কিছুই না — তাই ধীর disk এ cluster অস্থির

SQLite এর শেষ সারিটা লক্ষ করুন — অন্যদের চেয়ে গুরুতর। বেশিরভাগ system এ fsync কমালে আপনি সাম্প্রতিক data হারান, কিন্তু database টা সুস্থ থাকে। SQLite এ synchronous=OFF মানে লেখার ক্রম ও নিশ্চিত নয়, তাই পুরো file corrupt হতে পারে — একটা সম্পূর্ণ ভিন্ন মাপের ক্ষতি।

c 
/* Group commit — the standard way to make fsync affordable.
   Instead of one fsync per transaction, batch them. */

/* Naive: 1000 transactions = 1000 fsyncs = 1000 × 2ms = 2 s */
for (each txn) { write_wal(txn); fsync(wal_fd); }

/* Group commit: wait a moment, collect, then one fsync.
   1000 transactions = ~10 fsyncs = 20 ms */
for (;;) {
    collect_pending_txns(&batch, /* wait */ 1 /* ms */);
    for (t in batch) write_wal(t);
    fsync(wal_fd);                    /* ONE fsync for all */
    for (t in batch) reply_committed(t);
}

এটাই Postgres এর commit_delay, MySQL এর group commit, আর Kafka এর linger.ms — সবগুলো একই ধারণা: একটু latency যোগ করে throughput অনেক বাড়ানো।

আপনার ভাষায় এটা কোথায়

javascript 
// Node — fs.writeFile does NOT fsync. This is not durable:
await fs.writeFile('data.json', JSON.stringify(obj));

// Durable version:
const fh = await fs.open('data.json.tmp', 'w');
await fh.writeFile(JSON.stringify(obj));
await fh.sync();                      // ← fsync
await fh.close();
await fs.rename('data.json.tmp', 'data.json');

// And the parent directory:
const dh = await fs.open('.', 'r');
await dh.sync();
await dh.close();
go 
// Go — os.WriteFile does not sync either
f, _ := os.CreateTemp(dir, "tmp-*")
f.Write(data)
f.Sync()                              // fsync
f.Close()
os.Rename(f.Name(), target)

// Parent directory
d, _ := os.Open(dir)
d.Sync()
d.Close()
python 
# Python — two levels of buffering to flush!
with open('data.tmp', 'w') as f:
    f.write(data)
    f.flush()            # Python's buffer → kernel
    os.fsync(f.fileno()) # kernel → disk   ← both needed

os.replace('data.tmp', 'data.json')   # atomic rename

dfd = os.open('.', os.O_DIRECTORY)
os.fsync(dfd)
os.close(dfd)

Python এর উদাহরণটা শৃঙ্খলের প্রথম স্তরটা দেখায়: f.flush() শুধু Python এর নিজের buffer খালি করে kernel এ পাঠায় — সেটা fsync নয়। দুটোই লাগে। একই কথা C এর fflush() এর জন্য।

ভুল ধারণা

"আমার container এ data hostPath volume এ লিখছি আর fsync করছি, তাই নিরাপদ।"

Container আর cloud storage কয়েকটা নতুন স্তর যোগ করে, আর প্রতিটায় প্রশ্নটা আবার করতে হয়:

  • overlayfs — container এর writable layer। fsync কাজ করে, কিন্তু container মুছে ফেললে পুরো layer টাই যায়। "Durable" মানে "container এর জীবনকাল পর্যন্ত"।
  • Network storage (EBS, EFS, NFS) — fsync এখন একটা network round-trip। Latency ~১০০µs–কয়েক ms, আর NFS এ error শুধু close() তে আসতে পারে (তাই উপরের protocol এ close() ও check করেছি)।
  • Replication — একটা node এ fsync হওয়া মানে সেই node বাঁচলে data আছে। Node টাই হারালে? তাই distributed system এ durability মানে "N টা node এ লেখা হয়েছে", আর Postgres এর synchronous_standby_names বা Kafka এর acks=all সেটাই করে।

সাধারণ নিয়ম: durability একটা স্তরের ধর্ম নয়, পুরো শৃঙ্খলের। সবচেয়ে দুর্বল স্তরটাই আপনার আসল গ্যারান্টি।

আপনার কাজের সাথে যোগ

একটা ব্যবহারিক তালিকা, যেটা code review তে কাজে লাগে:

  • Config/state file লিখছেন? — write-tmp + fsync + rename + fsync(dir)। চারটে ধাপ, কম নয়।
  • একটা library ব্যবহার করছেন? — যাচাই করুন সে fsync করে কি না। বেশিরভাগ writeFile করে না।
  • fsync ব্যর্থ হলে? — retry করবেন না। Crash করুন, recovery চালান।
  • Durability বিক্রি করছেন? — করুন, কিন্তu সচেতনভাবে আর নথিবদ্ধ করে। "আমরা সবচেয়ে খারাপ ক্ষেত্রে ১ সেকেন্ডের data হারাতে পারি" একটা বৈধ সিদ্ধান্ত; "আমরা জানি না" নয়।
  • Test করছেন? — fsync এর সঠিকতা unit test এ ধরা পড়ে না। একমাত্র পরীক্ষা হলো power কাটা, বা একটা fault-injection layer (dm-flakey, CharybdeFS)।

প্রশ্ন

  1. Process crash আর power loss দুটো আলাদা failure mode। শৃঙ্খলের কোন স্তরটা প্রথমটায় বাঁচে কিন্তু দ্বিতীয়টায় নয়? এই তথ্য থেকে বলুন কেন একটা container-kill test আপনার durability প্রমাণ করে না।
  2. Parent directory fsync না করলে file টা "নেই" হয়ে যেতে পারে, যদিও data লেখা হয়েছে। Chapter 22 এর কোন তথ্যটা এটা ব্যাখ্যা করে? আর কোন তিনটে operation এর পর dir fsync লাগে?
  3. Safe-replace protocol এ ধাপ ২ (rename এর আগে fsync) বাদ দিলে সবচেয়ে খারাপ ফল কী? কেন সেটা "পুরনো version রেখে দেওয়া" এর চেয়ে খারাপ?
  4. fsyncgate এ একটা ব্যর্থ fsync retry করলে "সফল" হয় কিন্তু data হারায়। Kernel এর কোন সিদ্ধান্তটা এর কারণ, আর Postgres এর PANIC করার প্রতিক্রিয়াটা কেন প্রতিস্বজ্ঞাত হলেও সঠিক?
  5. একটা consumer SSD benchmark এ enterprise SSD এর চেয়ে দ্রুত দেখাচ্ছে, কিন্তু আপনার database workload এ ধীর। PLP দিয়ে এটা ব্যাখ্যা করুন, আর বলুন কোন benchmark টা এই পার্থক্যটা ধরতে পারবে।
  6. Redis এর appendfsync everysec মানে সর্বোচ্চ ১ সেকেন্ডের data হারানো। এখন ধরুন আপনার Redis তিনটে replica সহ চলছে। "১ সেকেন্ড" সংখ্যাটা কি বদলায়? Durability কে "শৃঙ্খলের ধর্ম" হিসেবে দেখে উত্তর দিন।
