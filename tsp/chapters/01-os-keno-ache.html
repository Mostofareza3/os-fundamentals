OS কেন আছে — তিনটি সমস্যা

একটা CPU, কিন্তু চল্লিশটা process চলছে। ১৬GB RAM, কিন্তু প্রতিটা process ভাবছে পুরো address space তার একলার। Power চলে গেল, তবু data রয়ে গেল। এই তিনটা illusion কীভাবে টিকে আছে — আর কোথায় ফাটল ধরে।

আপনি যখন node server.js চালান, আপনার ধারণা হয় program টা সরাসরি hardware এর উপর চলছে। চলছে না। মাঝখানে একটা layer আছে যেটা আপনার program কে মিথ্যা বলে — সুপরিকল্পিত, দরকারি মিথ্যা। সেই layer টার নাম operating system, আর এই বইটা মূলত সেই মিথ্যাগুলোর গঠন নিয়ে: কোনটা কীভাবে বানানো, কত খরচে, আর কোন পরিস্থিতিতে মিথ্যাটা ভেঙে গিয়ে আসল hardware বেরিয়ে পড়ে।

OSTEP বইটা পুরো বিষয়টাকে তিন ভাগে সাজিয়েছে, আর সেই ভাগটা এত ভালো যে আমরাও সেটাই রাখছি — virtualization, concurrency, persistence। এই chapter এ তিনটাকেই একবার দেখে নেব, কারণ বাকি ২৯টা chapter এই তিনটা সমস্যার বিস্তারিত উত্তর।

শুরুর জায়গা — একটা বোকা যন্ত্র

Processor যা করে তা হতাশাজনকভাবে সরল। একটা loop: memory থেকে instruction আনা (fetch), সেটা কী বলছে বোঝা (decode), সেটা করা (execute), তারপর পরেরটা। এটাই von Neumann model। একটা আধুনিক core সেকেন্ডে কয়েক বিলিয়ন বার এই চক্র ঘোরায়। 

   ┌──────────────── CPU core ────────────────┐
   │                                          │
   │   PC ──▶ fetch ──▶ decode ──▶ execute    │
   │   ▲                              │       │
   │   └──────────────────────────────┘       │
   │            (PC বাড়ে, আবার শুরু)          │
   └──────────────────────────────────────────┘
              │ load / store
              ▼
   ┌──────────────────────────────────────────┐
   │  Memory — byte এর একটা বিশাল array       │
   │  0                              2^48-1   │
   └──────────────────────────────────────────┘

fetch–decode–execute: এর বাইরে CPU কিছু জানে না।

আসল CPU এর চেয়ে এটা সরল করে বলা হলো। বাস্তবে একটা core একসাথে কয়েকটা instruction চালায় (superscalar), ক্রম ভেঙে চালায় (out-of-order), আর branch কোন দিকে যাবে তা আগেই অনুমান করে চালিয়ে ফেলে (speculative execution)। OSTEP এই জটিলতাগুলো সচেতনভাবে সরিয়ে রেখেছে, আমরাও আপাতত রাখছি — কারণ আপনার program যে model ধরে লেখা হয়, সেটা এই sequential model টাই।

তবে একটা কথা মনে রাখুন, কারণ chapter 13, 14 আর 30 এ এটা ফিরে আসবে: এই তিনটা optimization নিরীহ নয়। Out-of-order execution এর কারণেই memory model দরকার হয়। আর speculative execution এর কারণেই Meltdown আর Spectre সম্ভব হয়েছিল — যেখানে hardware এর একটা performance trick পুরো OS এর protection guarantee ভেঙে দিয়েছিল।

সংজ্ঞা

OS (Operating System — যে software টা hardware আর আপনার program এর মাঝখানে বসে resource ভাগ করে আর abstraction দেয়)। পুরনো নাম ছিল supervisor, আরও পুরনো নাম master control program — শেষেরটা একটু বেশি আত্মবিশ্বাসী শোনায় বলেই সম্ভবত টেকেনি।

OS কে তিনভাবে দেখা যায়

একটা OS কী, তার একটা উত্তর নেই — কোন দিক থেকে দেখছেন তার উপর নির্ভর করে। তিনটা দৃষ্টিভঙ্গি, তিনটাই সঠিক:

  1. Virtualizer — একটা physical resource নিয়ে তাকে আরও সাধারণ, শক্তিশালী, ব্যবহারযোগ্য একটা virtual রূপে বদলে দেয়। একটা CPU হয়ে যায় অসংখ্য virtual CPU। এই কারণেই OS কে মাঝে মাঝে virtual machine বলা হয়।
  2. Standard library — program চালানো, memory নেওয়া, file পড়া, packet পাঠানো — এসব করার জন্য OS কয়েকশো system call export করে। আপনার কাছে এগুলো function call এর মতোই দেখায়।
  3. Resource manager — যেহেতু অনেক program একসাথে CPU, memory আর disk ভাগ করছে, কাকে কখন কতটুকু দেওয়া হবে সেই সিদ্ধান্ত OS নেয় — কখনো efficiency এর কথা ভেবে, কখনো fairness এর।

এই তিনটার মধ্যে দ্বিতীয়টা নিয়ে সবচেয়ে বেশি ভুল হয়, তাই সেটা এখনই পরিষ্কার করে নেওয়া ভালো।

ভুল ধারণা

"malloc(), printf(), fopen() — এগুলো system call।" অথবা উল্টোটা: "library এর প্রতিটা function call kernel এ ঢোকে, তাই library call খরচি।"

দুটোই ভুল। এগুলো library function, আর তাদের বেশিরভাগ call কখনো kernel এ ঢোকেই না:

  • malloc() একটা userspace allocator। তার কাছে আগে থেকে নেওয়া memory থাকলে সে কোনো syscall ছাড়াই, ~১৫-২৫ nanosecond এ pointer ফেরত দেয়। শুধু pool শেষ হলে mmap() বা brk() দিয়ে kernel এ যায়।
  • printf() আপনার লেখা buffer এ জমায়। Buffer ভরলে বা newline পেলে (terminal এ) তখন একটা write() syscall হয়। দশটা printf() মানে দশটা syscall নয়।
  • clock_gettime() সাধারণত syscall ছাড়াই ফেরে — kernel একটা page (vDSO — virtual Dynamic Shared Object) প্রতিটা process এর address space এ map করে রাখে, যেখান থেকে সময় সরাসরি পড়া যায়।

পার্থক্যটা মাপা যায়: একটা syscall ~৫০-৪০০ns (Spectre mitigation চালু থাকলে আরও বেশি), আর একটা সাধারণ function call ~১-২ns। দুইশো গুণ ব্যবধান। কোনটা কোথায় যাচ্ছে তা strace দিয়ে দেখা যায় — chapter 4 এ করব।

সমস্যা ১ — একটা CPU, অনেক program

OSTEP একটা ছোট program দিয়ে শুরু করে। এটা কিছুই করে না — এক সেকেন্ড ঘোরে, একটা string ছাপে, আবার ঘোরে:

c 
/* cpu.c — spin for one second, print, repeat forever */
#include <stdio.h>
#include <stdlib.h>

/* Spin() busy-waits by repeatedly checking the clock
   until one second of wall time has passed. */
void Spin(int seconds);

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);
        printf("%s\n", str);
    }
    return 0;
}

একটা চালালে যা আশা করেন তাই হয়:

$ gcc -o cpu cpu.c -Wall
$ ./cpu A
A

A
^C

চারটা program একসাথে চলছে বলে মনে হচ্ছে, যদিও CPU একটা। এটাই CPU virtualization — একটা physical CPU কে আপাত-অসীম সংখ্যক virtual CPU তে রূপান্তর। Hardware সাহায্য করে (timer interrupt), OS সিদ্ধান্ত নেয় (scheduler), আর আপনি illusion টা পান।

লক্ষ করুন output এর ক্রম A B D C, তারপর A B D C, তারপর A C B D — বদলে যাচ্ছে। কেউ ঠিক করে দেয়নি কে আগে ছাপবে। এই non-determinism টা bug নয়, এটাই scheduler এর স্বভাব, আর chapter 12 এ দেখব এটাই race condition এর উৎস।

ভুল ধারণা

"Output interleaved মানে চারটা program একইসাথে চলছে।"

একটা CPU তে না। যেকোনো মুহূর্তে ঠিক একটা process ই চলছে। OS দ্রুত একটা থেকে আরেকটায় লাফাচ্ছে (context switch, chapter 4) — এত দ্রুত যে মানুষের চোখে একসাথে মনে হয়। এটা concurrency (কাজগুলো overlap করে এগোচ্ছে), কিন্তু parallelism নয় (একই মুহূর্তে একাধিক কাজ)।

২০২৬ এ উল্টো ভুলটাও সমান প্রচলিত: আপনার laptop এ ১০টা core আছে, তাই আপনি ধরে নেন সব সত্যিই parallel চলছে। কিন্তু container এ cpu.max দিয়ে আপনাকে ২ core এর সমান quota দেওয়া হলে, ১০টা thread চালালেও আপনি ২ core এর কাজই পাবেন — বাকি সময় thread গুলো throttled হয়ে বসে থাকবে। এটা production এ সবচেয়ে সাধারণ performance bug, chapter 7 এ পুরোটা আছে।

সমস্যা ২ — একই address, আলাদা memory

Physical memory একটা byte array, এর চেয়ে বেশি কিছু নয়। একটা program চলার সময় সারাক্ষণ এই array পড়ছে (load) আর লিখছে (store) — শুধু data নয়, প্রতিটা instruction fetch ও একটা memory access।

পরের program টা একটা int allocate করে, তার address ছাপে, তারপর সেটা বাড়াতে থাকে:

c 
/* mem.c — allocate one int, print its address, increment forever */
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <assert.h>

void Spin(int seconds);

int main(int argc, char *argv[]) {
    int *p = malloc(sizeof(int));       /* allocate 4 bytes */
    assert(p != NULL);
    printf("(pid:%d) addr of p: %p\n", (int) getpid(), p);
    *p = 0;
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(pid:%d) value of p: %d\n", getpid(), *p);
    }
    return 0;
}

দুটো instance একসাথে চালালে অদ্ভুত কিছু দেখা যায়:

$ ./mem & ./mem &

[2] 24114
(pid:24113) addr of p: 0x200000
(pid:24114) addr of p: 0x200000     ←  একই address!
(pid:24113) value of p: 1
(pid:24114) value of p: 1
(pid:24113) value of p: 2
(pid:24114) value of p: 2

দুটো process একই address 0x200000 পেয়েছে, অথচ একজন অন্যজনের counter নষ্ট করছে না। প্রত্যেকে নিজের মতো ১, ২, ৩ গুনছে।

কারণ ওই address টা physical নয়, virtual। প্রতিটা process একটা নিজস্ব address space পায় — byte এর একটা কাল্পনিক array, যার সূচনা শূন্য থেকে। OS (আর hardware এর MMU) এই virtual address গুলোকে আসল physical address এ অনুবাদ করে, প্রতিটা process এর জন্য আলাদা mapping দিয়ে। 

  Process 24113                      Process 24114
  virtual address space              virtual address space
  ┌────────────────┐                 ┌────────────────┐
  │                │                 │                │
  │  0x200000 ●────┼──┐         ┌────┼──● 0x200000    │

                      │         │
              page table         page table
                      │         │
                      ▼         ▼
       ┌──────────────────────────────────────────┐
       │  Physical RAM                            │
       │        ┌────┐            ┌────┐          │
       │        │0x7a│            │0x3c│          │
       │        └────┘            └────┘          │
       └──────────────────────────────────────────┘

Address space virtualization: একই সংখ্যা, ভিন্ন গন্তব্য।

এই উদাহরণটা কাজ করানোর জন্য আজকাল একটা জিনিস বন্ধ করতে হয় — ASLR (Address Space Layout Randomization — প্রতিবার চালালে stack, heap আর library গুলোকে এলোমেলো address এ বসানো, যাতে attacker আগে থেকে address অনুমান করতে না পারে)। ASLR চালু থাকলে দুটো process আলাদা address দেখাবে। বন্ধ করতে: 

# Linux: disable ASLR for one command
$ setarch $(uname -m) -R ./mem

# or globally (needs root, and don't leave it off)
$ sudo sysctl -w kernel.randomize_va_space=0
আপনার কাজের সাথে যোগ

এই isolation টাই কারণ যে docker run করলে দুটো container একই port এ bind করতে পারে (আলাদা network namespace), অথবা একই binary এর দুটো copy চললেও একজন আরেকজনের variable দেখে না। কিন্তু isolation টা সম্পূর্ণ নয় — chapter 29 এ দেখব container আসলে namespace + cgroup এর একটা সংকলন, আর কোন জায়গাগুলো ফাঁক থেকে যায়।

আরেকটা যোগসূত্র: Node এ একটা Buffer.alloc(1e9) করলে top এ VIRT লাফিয়ে বাড়ে কিন্তু RSS বাড়ে না। কারণ virtual address space বুক করা আর physical page পাওয়া দুটো আলাদা ঘটনা — chapter 11 এ এটাই মূল বিষয়।

সমস্যা ৩ — একসাথে চললে হিসাব মেলে না

এখন পর্যন্ত আলাদা process দেখেছি, যাদের memory আলাদা। কিন্তু একই memory ভাগ করে একাধিক execution চললে? সেটাই thread — একই address space এর ভিতরে চলা একাধিক execution path।

c 
/* threads.c — two threads increment a shared counter */
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

volatile int counter = 0;      /* NOTE: volatile is NOT the fix — see below */
int loops;

void *worker(void *arg) {
    for (int i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "usage: threads <loops>\n"); exit(1); }
    loops = atoi(argv[1]);

    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);
    pthread_create(&p1, NULL, worker, NULL);
    pthread_create(&p2, NULL, worker, NULL);
    pthread_join(p1, NULL);
    pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}

দুটো thread, প্রত্যেকে loops বার counter বাড়াচ্ছে। উত্তর হওয়া উচিত 2 × loops। ছোট সংখ্যায় মিলেও যায়: 

$ gcc -o threads threads.c -Wall -pthread
$ ./threads 1000
Initial value : 0
Final value   : 2000          ←  ঠিক আছে

সংখ্যা বাড়ান:

$ ./threads 100000
Initial value : 0
Final value   : 143012        ←  200000 হওয়া উচিত ছিল

$ ./threads 100000
Initial value : 0
Final value   : 137298        ←  আবার চালালে অন্য উত্তর!

প্রতিবার আলাদা উত্তর, আর কখনো কখনো ঠিক উত্তরও আসে — যেটা সবচেয়ে বিপজ্জনক, কারণ test এ ধরা পড়ে না।

কারণটা counter++ লাইনে। C তে এক লাইন, কিন্তু machine এ তিনটা ধাপ: 

  counter++  →   mov  eax, [counter]    ; 1. memory থেকে register এ আনো
                 add  eax, 1            ; 2. register এ ১ যোগ করো
                 mov  [counter], eax    ; 3. memory তে ফেরত লেখো

  দুটো thread, counter = 50 থেকে শুরু:

  Thread 1                    Thread 2               counter
  ─────────────────────────────────────────────────── ───────
  mov eax,[counter]  (50)                               50
  add eax,1          (51)
        ─── context switch ───▶
                              mov eax,[counter] (50)    50   ← পুরনো মান!
                              add eax,1         (51)
                              mov [counter],eax         51
        ◀── context switch ───
  mov [counter],eax                                     51   ← হারিয়ে গেল
  ─────────────────────────────────────────────────── ───────
  দুটো increment হলো, counter বাড়ল মাত্র ১।

Lost update: তিন ধাপের মাঝখানে switch হলেই হিসাব নষ্ট।

এই সমস্যাটার নাম race condition, আর যে অংশটা একসাথে একজনের বেশি চালানো নিরাপদ নয় তার নাম critical section। সমাধান দরকার এমন কিছু, যা ওই তিন ধাপকে একটা অবিভাজ্য (atomic) একক বানায় — সেটাই lock, chapter 15।

ভুল ধারণা

"উপরের code এ volatile আছে, তাই ওটাই সমস্যা সমাধান করার কথা ছিল।"

না। এটা এই বইয়ের source (OSTEP) থেকে পাওয়া সবচেয়ে ক্ষতিকর শিক্ষা, আর আমি ইচ্ছে করেই code টা হুবহু রেখেছি যাতে এখনই সংশোধন করা যায়।

volatile compiler কে বলে "এই variable এর access optimize করে সরিয়ে দিও না, প্রতিবার সত্যিই memory থেকে পড়ো।" এটা synchronization primitive নয়। এটা—

  • counter++ কে atomic বানায় না (তিন ধাপ তিন ধাপই থাকে);
  • CPU এর instruction reordering আটকায় না;
  • অন্য core এর cache এ আপনার লেখা কখন দেখা যাবে, তার কোনো নিশ্চয়তা দেয় না।

আর C11/C++11 এর ভাষায় এই code টা শুধু "ভুল উত্তর দেয়" এমন নয় — এটা undefined behavior, কারণ synchronization ছাড়া দুটো thread একই non-atomic object এ লিখছে। মানে compiler আইনত যা খুশি করতে পারে। ঠিক সমাধান _Atomic int বা atomic_fetch_add() বা একটা mutex — chapter 14 পুরোটাই এই নিয়ে, আর ওখানে দেখব কেন Apple Silicon এ কাজ করা code Graviton এ ভেঙে যেতে পারে।

সমস্যা ৩.৫ — power গেলে সব যায়

DRAM volatile — current বন্ধ হলে content শেষ। তাই যা রাখতে হবে, তা যেতে হবে এমন device এ যা power ছাড়াও মনে রাখে: HDD, বা আজকাল প্রায় সবসময় SSD। এই দায়িত্বটা OS এর যে অংশের, তার নাম file system।

c 
/* io.c — write a string to a file */
#include <stdio.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>

int main(int argc, char *argv[]) {
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 13);
    assert(rc == 13);
    close(fd);
    return 0;
}

এখানে তিনটা system call: open(), write(), close()। লক্ষণীয় যে OS এখানে virtualization এর নীতি থেকে সচেতনভাবে সরে এসেছে — CPU আর memory প্রতিটা process এর জন্য আলাদা করে virtualize করা হয়, কিন্তু disk করা হয় না। কারণ file এর উদ্দেশ্যই ভাগ করা: আপনি editor এ লিখবেন, compiler সেটা পড়বে, তারপর সেটা চালাবেন।

আর এখানেই এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ একটা ভুল ধারণা লুকিয়ে আছে।

ভুল ধারণা

"write() ১৩ ফেরত দিয়েছে, মানে ১৩ byte disk এ লেখা হয়ে গেছে।" সমগোত্রীয় ভুল: "close() করলে flush হয়ে যায়", "fflush() করেছি, তাই নিরাপদ"।

write() ফেরত আসা মানে শুধু এটুকু: আপনার data kernel এর page cache এ পৌঁছেছে। সেটা RAM। এই মুহূর্তে power গেলে data নেই। Kernel সাধারণত লেখাটা কিছুক্ষণ আটকে রাখে — কয়েক সেকেন্ড পর্যন্ত — যাতে ছোট লেখাগুলো একসাথে বড় করে পাঠানো যায়, আর একই block বারবার লেখা হলে বাড়তি I/O বাঁচে।

Disk এ সত্যিই পৌঁছেছে কিনা নিশ্চিত হতে fsync(fd) লাগে। আর তাতেও শেষ নয় — নতুন তৈরি করা file এর ক্ষেত্রে parent directory ও fsync করতে হয়, নইলে file এর নামটাই হারিয়ে যেতে পারে যদিও content লেখা হয়েছে। এই পুরো "durability contract" টা chapter 25 এর বিষয়, আর ওখানে fsyncgate ও দেখব — যেখানে Postgres আবিষ্কার করল fsync() fail করার পর Linux কীভাবে ভুলভাবে সফলতা রিপোর্ট করত, আর সেটা ঠিক করতে দুটো database কে নিজেদের recovery model বদলাতে হয়েছিল।

আপনার কাজের সাথে যোগ

এই কারণেই Postgres এ synchronous_commit নামে একটা setting আছে, আর সেটা off করলে TPS লাফিয়ে বাড়ে — আপনি durability বিক্রি করে throughput কিনছেন। একই কারণে Redis এ appendfsync everysec মানে "সবচেয়ে খারাপ ক্ষেত্রে এক সেকেন্ডের লেখা হারাবে", আর SQLite এর PRAGMA synchronous=OFF দিলে crash এ database corrupt হতে পারে। তিনটাই একই hardware সত্যের উপর দাঁড়িয়ে।

Mechanism আর policy — বইয়ের সবচেয়ে কাজের পার্থক্য

OS এর প্রতিটা অংশে এই দুটো আলাদা করে ভাবতে হয়:

 MechanismPolicy

OS এর design goal — আর সেগুলোর দাম

  • Abstraction — যাতে আপনি transistor এর কথা না ভেবে program লিখতে পারেন।
  • Performance — abstraction এর overhead যতটা সম্ভব কম, সময়ে (বাড়তি instruction) আর জায়গায় (kernel এর নিজের memory) দুদিকেই।
  • Protection আর isolation — একটা process আরেকটাকে, বা kernel কে, নষ্ট করতে না পারে।
  • Reliability — OS crash করলে তার উপরের সবকিছু যায়। Linux kernel এখন কয়েক কোটি লাইন code।
  • Energy efficiency, security, mobility — battery, attacker আর ছোট device এর যুগে এগুলো আর গৌণ নয়।
যেখানে source টা পুরনো

OSTEP (২০১৫) protection এর প্রতিশ্রুতিটা নিঃশর্তভাবে দেয়: page table এর privilege bit থাকার কারণে user process kernel memory পড়তে পারে না। ২০১৮ এর Meltdown দেখিয়ে দিল কথাটা সত্য নয় — speculative execution ব্যবহার করে ওই bit কে পাশ কাটিয়ে kernel memory পড়া যায়, কারণ hardware অনুমান করে আগেই data টা cache এ তুলে ফেলে, আর privilege check টা হয় পরে।

উত্তরে Linux এ এল KPTI (Kernel Page Table Isolation — প্রতিটা process এর address space থেকে kernel এর mapping সরিয়ে রাখা), যার দাম হলো প্রতিটা syscall এ বাড়তি খরচ। অর্থাৎ "kernel কে প্রতিটা address space এ map করে রাখা" — যে design টা কয়েক দশক ধরে নিঃসন্দেহে সঠিক ধরা হতো — তা আংশিকভাবে ফিরিয়ে নিতে হয়েছে। Chapter 9 আর 10 এ এই খরচটা মাপব।

এই বইয়ে যা নেই

OSTEP এর মতোই আমরা networking এর ভিতরের অংশ (TCP/IP stack এর implementation), graphics device আর GPU, আর security এর গভীর আলোচনা বাদ রাখছি — প্রতিটা নিজেই একটা বই। তবে যেখানে এগুলো OS এর সাথে সরাসরি লাগে, সেখানে ছোঁব: socket আর epoll (chapter 19), Meltdown/KPTI (chapter 9), seccomp আর namespace (chapter 29)।

প্রশ্ন

  1. একটা ৮-core মেশিনে আপনি ৮টা ./cpu process চালালেন আর output interleaved দেখলেন। এখন সেই একই ৮টা process কে --cpus=1 দেওয়া একটা container এ চালালেন — output দেখতে একই রকম লাগবে, কিন্তু কোন মাপে দুটো পরিস্থিতি সম্পূর্ণ আলাদা? কোন tool দিয়ে পার্থক্যটা প্রমাণ করবেন?
  2. mem.c এর দুটো instance একই address ছাপছিল। ধরুন আপনি ASLR বন্ধ রাখলেন, কিন্তু program টা fork() দিয়ে একটা child বানাল আর দুজনেই *p বাড়াতে থাকল। Address একই থাকবে, কিন্তু counter গুলো কি একসাথে বাড়বে, নাকি আলাদা? উত্তরটা কোন mechanism এর উপর নির্ভর করে?
  3. threads.c এ volatile সরিয়ে _Atomic int counter লিখলে উত্তর সবসময় ঠিক আসবে। এখন যদি দুটো thread এর কাজ হতো "counter পড়ে, সেটা দেখে সিদ্ধান্ত নিয়ে, তারপর লেখা" — তাহলে _Atomic দিয়ে কি সমস্যা মিটত? কেন, বা কেন নয়?
  4. একটা program write() করে সফল return পেল, তারপর close() করল, তারপর process টা exit() করল — সব ঠিকঠাক। এর ঠিক পরেই মেশিনের power cable খুলে ফেলা হলো। Data টা থাকবে কি? আপনার উত্তর যদি "নির্ভর করে" হয়, তাহলে কীসের উপর নির্ভর করে — অন্তত তিনটা জিনিস বলুন।
  5. Mechanism আর policy এর পার্থক্য ব্যবহার করে বলুন: Linux এ scheduler টা CFS থেকে EEVDF এ বদলানো হলো — এটা mechanism এর পরিবর্তন না policy এর? আর এই উত্তরটা থেকে বুঝুন কেন kernel upgrade করলে আপনার latency profile বদলে যেতে পারে যদিও আপনি কোনো code বদলাননি।
  6. File system কে library বানানো যায় না — protection এর কারণে। কিন্তু আজকাল কিছু database (যেমন embedded SQLite, বা io_uring ব্যবহার করে userspace driver) kernel কে অনেকটা পাশ কাটিয়ে সরাসরি device এ কাজ করে। তাহলে ১৯৬০ এর সেই যুক্তিটা কি ভুল হয়ে গেল, নাকি এখানে protection অন্য কোনো জায়গা থেকে আসছে?
