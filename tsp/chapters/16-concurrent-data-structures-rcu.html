Concurrent data structure আর lock granularity

একটা lock দিয়ে সবকিছু ঢেকে দিলে code সঠিক হয় কিন্তু scale করে না। এই chapter এ contention কমানোর তিনটে কৌশল, আর তারপর সেই প্রশ্ন যা lock-free programming কে আসলে কঠিন করে — memory কখন free করবেন?

Chapter 15 এ একটা কাজ করা lock পেয়েছি। এখন প্রশ্ন: সেটা কোথায় বসাব? একটা data structure এর কতটুকু একটা lock দিয়ে ঢাকব?

Crux

একটা data structure কে thread-safe করার সহজ উপায় হলো সবকিছু একটা lock দিয়ে ঢেকে দেওয়া। সেটা সঠিক, কিন্তু core সংখ্যা বাড়লে ভেঙে পড়ে। সঠিকতা না হারিয়ে contention কীভাবে কমাব?

Counter — সবচেয়ে সরল উদাহরণ, সবচেয়ে বড় শিক্ষা

একটা thread-safe counter। প্রথম প্রচেষ্টা সোজা:

c 
/* Correct, and it does not scale. */
typedef struct {
    int value;
    pthread_mutex_t lock;
} counter_t;

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

int get(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    int v = c->value;
    pthread_mutex_unlock(&c->lock);
    return v;
}

সঠিক। কিন্তু মেপে দেখলে: 

  চারটে thread, প্রত্যেকে ১ মিলিয়ন increment:

  1 thread  : 0.03 s
  2 threads : 0.42 s   ← ধীর হলো!
  4 threads : 1.85 s   ← আরও ধীর

  কাজ চারগুণ হলো, সময় ৬০ গুণ।
  এটা শুধু "scale করছে না" নয় — এটা নেতিবাচকভাবে scale করছে।

কারণ: প্রতিটা increment এ একই cache line এর exclusive ownership দরকার (chapter 13), আর একই lock এর জন্য সবাই লড়ছে (chapter 15)। Thread বাড়ালে শুধু coherence traffic বাড়ে।

Sloppy counter — নির্ভুলতা বিক্রি করে scalability কেনা

সমাধান: প্রতিটা CPU এর নিজের local counter দাও, আর মাঝে মাঝে global এ যোগ করো। 

  threshold S = 5

  CPU 0: local=4 ─┐
  CPU 1: local=2  │  local counter এ কোনো lock নেই
  CPU 2: local=3  │  (বা প্রতি-CPU আলাদা lock)
  CPU 3: local=1 ─┘
                    │
     local ≥ S হলে  │  global lock নাও, যোগ করো,
                    ▼  local শূন্য করো
             global = 47

  পড়ার সময়: global পড়ো (কিছু পিছিয়ে থাকতে পারে)

  S ছোট  → global বেশি নির্ভুল, কম scalable
  S বড়   → বেশি scalable, global বেশি পিছিয়ে
c 
/* Sloppy counter — per-CPU locals, periodic flush to global.
   Trades read accuracy for write scalability. */
typedef struct {
    int global;
    pthread_mutex_t glock;
    int local[NUMCPUS];
    pthread_mutex_t llock[NUMCPUS];
    int threshold;                    /* S */
} sloppy_t;

void sloppy_update(sloppy_t *c, int cpu, int amt) {
    pthread_mutex_lock(&c->llock[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        /* flush to global — the only contended step */
        pthread_mutex_lock(&c->glock);
        c->global += c->local[cpu];
        pthread_mutex_unlock(&c->glock);
        c->local[cpu] = 0;
    }
    pthread_mutex_unlock(&c->llock[cpu]);
}

/* NOTE: local[] and llock[] MUST be cache-line padded, or
   false sharing (chapter 13) undoes the whole optimisation. */

ওই শেষ comment টা গুরুত্বপূর্ণ আর OSTEP এ নেই: একটা int local[NUMCPUS] array এ চারটে int একই cache line এ পড়ে, তাই per-CPU করার পুরো লাভটাই false sharing খেয়ে ফেলবে। Chapter 13 এর padding এখানে আবশ্যক, optional নয়।

Threshold S = ১০২৪ দিয়ে ফল নাটকীয়ভাবে বদলায়: 

  4 threads, 1M increment প্রতিটা:

  একটা lock       : 1.85 s
  sloppy (S=1024) : 0.04 s     ← ৪৬ গুণ দ্রুত

  দাম: get() একটা কিছুটা পুরনো মান দেয়
       (সর্বোচ্চ NUMCPUS × S কম হতে পারে)
আপনার কাজের সাথে যোগ

এই নকশাটা আপনার চারপাশে আছে, প্রায়ই "approximate" নামে:

  • Linux kernel এর percpu_counter হুবহু এটাই — আর /proc/meminfo এর কিছু সংখ্যা তাই সামান্য পিছিয়ে থাকে।
  • Prometheus client library গুলো counter এ per-thread/per-goroutine জমা করে, scrape এর সময় যোগ করে।
  • Postgres এর statistics collector asynchronous — তাই pg_stat_user_tables এর সংখ্যা তাৎক্ষণিক নয়। একই trade-off।

সাধারণ শিক্ষাটা: metrics এ নির্ভুলতা প্রায়ই অপ্রয়োজনীয়, কিন্তু scalability অপরিহার্য। একটা request counter ১০০০ পিছিয়ে থাকলে কিছু যায় আসে না; কিন্তু সেটা hot path কে ধীর করলে অনেক কিছু যায় আসে।

Linked list — lock এর দানা ছোট করা

একটা list এ পুরোটা একটা lock দিয়ে ঢাকা সহজ। কিন্তু একটা লম্বা list এ দুটো thread যদি দুই প্রান্তে কাজ করে, তাদের পরস্পরের অপেক্ষা করার কোনো কারণ নেই। 

  ১. একটা lock পুরো list এ (coarse-grained)

     ┌──── একটাই lock ────────────────┐
     │  A ──▶ B ──▶ C ──▶ D ──▶ E     │
     └────────────────────────────────┘
     সরল, সঠিক, কোনো scalability নেই


  ২. প্রতি node এ একটা lock — hand-over-hand

     [A]🔒 ──▶ [B]🔒 ──▶ [C]🔒 ──▶ [D]🔒
      ↑         ↑
      │         └── thread 2 এখানে
      └── thread 1 এখানে

     চলার নিয়ম: পরের node এর lock নাও,
                তারপর এখনকার lock ছাড়ো
                (তাই "hand over hand")

     তত্ত্বে বেশি concurrency।
     বাস্তবে প্রায়ই ধীর! কারণ প্রতি node এ
     দুটো atomic operation — traversal এর খরচ
     concurrency এর লাভ খেয়ে ফেলে।


  ৩. Sharding / striping — ব্যবহারিক মধ্যপথ

     hash(key) % 16 → কোন bucket
     প্রতি bucket এর নিজের lock

     ┌──lock 0──┐ ┌──lock 1──┐ ... ┌──lock 15──┐
     │ A ──▶ Q  │ │ B ──▶ R  │     │ C ──▶ S   │
     └──────────┘ └──────────┘     └───────────┘

     ১৬ গুণ কম contention, traversal এর খরচ অপরিবর্তিত।
     এটাই বাস্তবে ব্যবহৃত হয়।

দ্বিতীয় পদ্ধতিটা একটা গুরুত্বপূর্ণ শিক্ষা দেয়: বেশি concurrency মানে বেশি performance নয়। Hand-over-hand তত্ত্বে সুন্দর কিন্তু প্রায়ই একটা lock এর চেয়ে ধীর, কারণ প্রতিটা lock/unlock এর নিজের খরচ আছে।

OSTEP এর নিজের পরামর্শটা এখানে ঠিক, আর সেটা মনে রাখার মতো: আগে সরল করে বানান, তারপর মেপে দেখুন সত্যিই bottleneck কি না। Knuth এর সেই কথাটা এখানে বিশেষভাবে প্রযোজ্য, কারণ concurrent code এ ভুল optimization শুধু জটিলতা নয়, bug ও আনে।

c 
/* Sharded hash map — the practical pattern.
   Each bucket has its own lock, padded to a cache line. */
#define NSHARDS 16

typedef struct {
    node_t *head;
    pthread_mutex_t lock;
    char pad[64 - (sizeof(node_t *) + sizeof(pthread_mutex_t)) % 64];
} shard_t;

typedef struct { shard_t shard[NSHARDS]; } map_t;

void map_insert(map_t *m, int key, int val) {
    shard_t *s = &m->shard[key % NSHARDS];
    pthread_mutex_lock(&s->lock);
    /* ... insert into s->head ... */
    pthread_mutex_unlock(&s->lock);
}
ভুল ধারণা

"Lock এর দানা যত ছোট, তত ভালো — প্রতিটা node এ lock দিলে সর্বোচ্চ concurrency পাব।"

Hand-over-hand এর benchmark প্রায়ই উল্টো ফল দেয়। প্রতিটা node এ একটা lock আর একটা unlock মানে দুটো atomic operation — একটা ১০০০-node list traversal এ ২০০০ টা atomic। একটা lock দিয়ে সেটা দুটো।

আর একটা লুকানো খরচ: প্রতিটা node এ একটা pthread_mutex_t (৪০ byte) যোগ করলে node এর আকার বাড়ে, তাই একই cache line এ কম node ধরে — অর্থাৎ traversal এ বেশি cache miss।

ব্যবহারিক নিয়ম: sharding প্রায় সবসময় সঠিক উত্তর। যথেষ্ট concurrency দেয়, আর per-operation খরচ বাড়ায় না।

Read-write lock — আর কেন প্রায়ই ফাঁদ

যদি পাঠক অনেক আর লেখক কম, তাহলে পাঠকদের একসাথে ঢুকতে দেওয়া যায়:

c 
pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

/* অনেক পাঠক একসাথে */
pthread_rwlock_rdlock(&rw);
int v = shared_data;
pthread_rwlock_unlock(&rw);

/* একজন লেখক, একা */
pthread_rwlock_wrlock(&rw);
shared_data = 42;
pthread_rwlock_unlock(&rw);

শোনাচ্ছে নিখুঁত। কিন্তু একটা সমস্যা আছে যা স্বজ্ঞাবিরোধী: 

  rdlock() নিজেই একটা লেখা!

  reader count বাড়াতে হয় → একটা atomic increment
  → cache line এর exclusive ownership দরকার
  → chapter 13 এর সেই ping-pong

  ফল: ১০টা thread শুধু পড়ছে, তবু তারা একটা
      cache line এর জন্য লড়ছে।

  পরিমাপ (৮ core, শুধু read):
    mutex    : 42 ns/op
    rwlock   : 61 ns/op     ← বেশি খরচি!
    RCU      :  1 ns/op     ← নিচে দেখুন

অর্থাৎ read-write lock শুধু তখনই লাভজনক যখন critical section দীর্ঘ — নইলে reader count এর accounting এর খরচই সব লাভ খেয়ে ফেলে। ছোট read এর জন্য এটা প্রায়ই একটা সাধারণ mutex এর চেয়ে খারাপ।

RCU — পাঠকদের জন্য শূন্য খরচ

এখন একটা সম্পূর্ণ ভিন্ন দৃষ্টিভঙ্গি, আর এটা OSTEP এ নেই যদিও Linux এর ভিতরে এটা সর্বত্র।

RCU (Read-Copy-Update — পাঠকরা কোনো synchronization ছাড়াই পড়ে, আর লেখক পুরনো copy টা ততক্ষণ রাখে যতক্ষণ সব পুরনো পাঠক শেষ না হয়)। 

  মূল ধারণা: data কখনো জায়গায় বদলাও না।
             নতুন copy বানাও, pointer টা atomically সরাও।

  শুরুতে:
     ptr ──▶ [ old config ]
              ↑ তিনজন পাঠক পড়ছে

  লেখক copy বানাল আর pointer সরাল:
     ptr ──▶ [ new config ]  ← নতুন পাঠকরা এটা পায়
              
             [ old config ]  ← পুরনো পাঠকরা এখনো এটায়
              ↑ এখনো তিনজন

  লেখক এখন অপেক্ষা করে: "grace period"
     = সব pre-existing reader তাদের read section শেষ করা
       পর্যন্ত অপেক্ষা

  grace period শেষ:
     ptr ──▶ [ new config ]
             free([ old config ])   ← এখন নিরাপদ
c 
/* Kernel-style RCU. The read side is the point:
   rcu_read_lock() compiles to NOTHING on a non-preemptible
   kernel — no atomic, no barrier, no cache line contention. */

/* --- reader --- */
rcu_read_lock();
struct config *c = rcu_dereference(global_config);
use(c->timeout);                  /* safe: c cannot be freed yet */
rcu_read_unlock();

/* --- writer --- */
struct config *new = kmalloc(sizeof(*new), GFP_KERNEL);
*new = *old;                      /* copy */
new->timeout = 60;                /* update the copy */

rcu_assign_pointer(global_config, new);   /* publish (release) */

synchronize_rcu();                /* wait for the grace period */
kfree(old);                       /* now nobody can be reading it */

দামটা অসমভাবে ভাগ করা, আর সেটাই RCU এর সৌন্দর্য:

 খরচ
Readerপ্রায় শূন্য — কোনো atomic, কোনো barrier, কোনো contention
Writerবেশি — copy বানানো + grace period এর অপেক্ষা

তাই RCU ঠিক সেই জায়গায় কাজ করে যেখানে read অনেক, write বিরল — routing table, configuration, kernel এর module list, network device list। Linux এ এটা এতটাই মৌলিক যে /proc/sys/kernel/ এ এর নিজের tuning আছে।

Userspace এ ব্যবহার করা যায় liburcu দিয়ে, কিন্তু সেখানে read side একেবারে বিনামূল্যে নয় (kernel এর preemption-সংক্রান্ত সুবিধাটা নেই)।

আসল কঠিন সমস্যা — কখন free করবেন

Chapter 14 এর publication pattern এ একটা ফাঁক রেখে এসেছিলাম: পুরনো object টা কখন free() করবেন? এখন সেটার উত্তর, কারণ এটাই lock-free programming কে কঠিন করে।

Algorithm লেখাটা সহজ অংশ। কঠিন অংশ হলো memory reclamation, আর তার কারণ ABA সমস্যা: 

  ABA problem:

  thread 1: stack এর top পড়ল → node A
            (CAS করার প্রস্তুতি নিচ্ছে)
       ⏸  preempt হলো

  thread 2: A কে pop করল, free করল
            B কে push করল
            আবার একটা নতুন node allocate করল —
            allocator ঠিক A এর জায়গাটাই ফেরত দিল!
            সেটাকে push করল → top আবার "A" এর ঠিকানায়

  thread 1: ▶ আবার চলল
            CAS(top, A, A->next) → সফল!
            কারণ ঠিকানা মিলে গেছে
            কিন্তু এটা সম্পূর্ণ অন্য একটা node,
            আর A->next এখন আবর্জনা
            → list corrupt

  pointer এর মান একই, কিন্তু অর্থ বদলে গেছে।

সমাধানগুলো সবই "পুরনো object টা এখনো কেউ দেখছে কি" — এই প্রশ্নের উত্তর দেওয়ার চেষ্টা:

পদ্ধতিকীভাবেব্যবহার
RCU Grace period — সব পুরনো reader শেষ হওয়ার অপেক্ষা Linux kernel
Hazard pointer প্রতিটা reader ঘোষণা করে সে কোন pointer দেখছে Folly, কিছু C++ library
Epoch-based Global epoch counter; পুরনো epoch এর object মুক্ত Rust এর crossbeam
GC Runtime নিজেই সামলায় Java, Go, C# — সমস্যাটাই নেই
Tagged pointer Pointer এর সাথে একটা version counter ABA এড়ানোর সরল কৌশল

শেষ সারিটা লক্ষ করুন: GC থাকলে এই পুরো সমস্যাটাই অদৃশ্য। এই কারণেই Java আর Go তে lock-free structure লেখা অনেক সহজ — reclamation টা runtime এর দায়িত্ব।

ভুল ধারণা

"Lock-free data structure lock-based এর চেয়ে দ্রুত, তাই আমার উচ্চ-চাপের path এ একটা লিখব।"

OSTEP এর সময়ে একটা উল্টো ভুলও প্রচলিত ছিল — যে lock-free "জটিল আর কেবল মাঝে মাঝে ব্যবহৃত"। ২০২৬ এ সেটা মিথ্যা: আপনি যে প্রতিটা runtime ব্যবহার করেন তার ভিতরে lock-free structure আছে (Linux এর RCU, Go এর runqueue, Java এর ConcurrentHashMap, jemalloc এর thread cache)।

কিন্তু ব্যবহার করা আর লেখা সম্পূর্ণ আলাদা। নিজে লেখার তিনটে বিপদ:

  • Algorithm এর অংশটা সহজ; reclamation এর অংশটা কঠিন, আর সেখানেই ABA এর মতো bug লুকায় যা মাসে একবার প্রকাশ পায়।
  • Lock-free মানে অপেক্ষা-মুক্ত নয়। উচ্চ contention এ একটা CAS loop বারবার retry করে — throughput একটা mutex এর চেয়ে খারাপ হতে পারে।
  • Chapter 14 এর memory ordering ভুল হলে code টা x86 এ কাজ করবে আর ARM64 এ ভাঙবে।

ব্যবহারিক পরামর্শ: library ব্যবহার করুন, নিজে লিখবেন না। আর যদি লিখতেই হয়, formal verification tool (CDSChecker, herd7) ব্যবহার করুন — test যথেষ্ট নয়।

ব্যবহারিক সিদ্ধান্তের ক্রম

  একটা shared data structure দরকার। ক্রমানুসারে চেষ্টা করুন:

  ১. ভাগ করা এড়ান
       thread-local + মাঝে মাঝে merge (sloppy counter)
       বা message passing (Go channel)
       → কোনো synchronization এর দরকারই নেই

  ২. আপনার standard library এর concurrent structure নিন
       Java: ConcurrentHashMap
       Go:   sync.Map (শুধু নির্দিষ্ট pattern এ), বা
             একটা sharded map
       C++:  TBB, folly
       → কেউ আগেই এটা ঠিক করে লিখেছে

  ৩. একটা mutex দিয়ে ঢাকুন, তারপর মাপুন
       ~২০ns uncontended — প্রায়ই যথেষ্ট

  ৪. Shard করুন
       hash(key) % N, প্রতি shard এ lock
       → সহজ, কার্যকর, নিরাপদ

  ৫. RCU বা lock-free
       শুধু যখন মেপে প্রমাণ হয়েছে এটাই bottleneck,
       আর read:write অনুপাত অত্যন্ত অসম
আপনার কাজের সাথে যোগ

Go এর sync.Map একটা শিক্ষামূলক উদাহরণ: এটা সাধারণ উদ্দেশ্যের map নয়। Documentation স্পষ্টভাবে বলে এটা দুটো নির্দিষ্ট pattern এর জন্য — (ক) key একবার লেখা হয় তারপর বহুবার পড়া হয়, (খ) একাধিক goroutine অসংলগ্ন key তে কাজ করে। অন্য ক্ষেত্রে একটা map + RWMutex ভালো। ভিতরে এটা একটা read-mostly কৌশল ব্যবহার করে যা RCU এর ধারণার কাছাকাছি।

Java এর ConcurrentHashMap ঠিক আমাদের তৃতীয় কৌশলটাই — bucket-স্তরের lock (আগে segment, এখন প্রতি-bin CAS)। অর্থাৎ sharding production-grade আকারে।

Postgres এর buffer pool partitioned (NUM_BUFFER_PARTITIONS) — একই কারণে। pg_stat_activity এ BufferMapping wait দেখলে সেটা এই partition গুলোর contention।

প্রশ্ন

  1. একটা lock দিয়ে counter এ ১ thread থেকে ৪ thread এ গেলে সময় ৬০ গুণ বাড়ল। কাজ বাড়ল ৪ গুণ। বাকি ১৫ গুণ কোথায় গেল? Chapter 13 আর 15 এর কোন দুটো প্রক্রিয়া মিলে এটা ঘটায়?
  2. Sloppy counter এ local[] array padding না করলে পুরো optimization ব্যর্থ হয়। কেন? আর threshold S বাড়ালে কী পাওয়া যায় আর কী হারানো যায় — একটা metrics counter আর একটা quota enforcement counter এর জন্য S আলাদা হবে কি?
  3. Hand-over-hand locking তত্ত্বে বেশি concurrency দেয় কিন্তু বাস্তবে প্রায়ই ধীর। দুটো আলাদা কারণ বলুন — একটা atomic operation সংক্রান্ত, আরেকটা cache সংক্রান্ত।
  4. rdlock() নিজেই একটা লেখা, তাই ছোট read এর জন্য rwlock একটা mutex এর চেয়ে খারাপ হতে পারে। তাহলে rwlock কখন সত্যিই লাভজনক? একটা concrete পরিস্থিতি দিন যেখানে এটা স্পষ্ট জয়।
  5. RCU তে reader এর খরচ প্রায় শূন্য কিন্তু writer কে grace period অপেক্ষা করতে হয়। এই অসম বিতরণটা কোন ধরনের workload এ আদর্শ, আর কোন ধরনের workload এ বিপর্যয়? আপনার উত্তরে একটা concrete counter-উদাহরণ দিন।
  6. ABA সমস্যায় pointer এর মান একই থাকে কিন্তু অর্থ বদলায়। Java বা Go তে lock-free stack লিখলে এই নির্দিষ্ট সমস্যাটা কেন হয় না? আর সেই তথ্যটা থেকে বলুন GC থাকা ভাষায় lock-free programming কতটা সহজ, আর কোন সমস্যাগুলো তবু থাকে।
