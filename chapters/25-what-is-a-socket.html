PART 7 · NETWORKING AND SOCKETS

Chapter 25 — What Is a Socket?

Network card শুধু packet চেনে; তুমি চাও "ওই server-এর সাথে একটা লাইন, যেখানে byte লিখব আর পড়ব"। মাঝের এই জিনিসটা kernel বানায় — socket। IP, port, চার-মানের পরিচয়, server-এর চার ধাপ, TCP বনাম UDP, আর একই machine-এর ভেতরের socket।

Chapter 2-এ দেখেছি network card (NIC) একটা device, যার driver kernel-এ। তারের ওপারে data যায় ছোট ছোট টুকরোয় — packet: কয়েকশো থেকে দেড় হাজারের মতো byte, মাথায় একটা ঠিকানার লেবেল। এখন ভাবো kernel তোমাকে শুধু এটুকুই দিত: "NIC থেকে যা packet আসে নাও, যা পাঠাবে packet বানিয়ে দাও।" তাহলে প্রতিটা app-কে নিজে packet বানাতে হতো, হারানো packet আবার পাঠাতে হতো, উল্টাপাল্টা ক্রমে আসা packet সাজাতে হতো — আর সবচেয়ে বড় সমস্যা, machine-এ চলা Chrome, Slack, তোমার Node server — কোন packet কার, সেটা ঠিক করত কে? File-এর বেলায় যেমন kernel disk-এর block লুকিয়ে "file" দেয় (Chapter 21), network-এর বেলায় সে packet লুকিয়ে দেয় socket।

ঠিকানা: IP, port আর চার-মানের পরিচয়

কয়েকটা শব্দ আগে ঠিক করে নিই:

  • IP address: network-এ একটা machine-এর (আসলে তার একটা network interface-এর) ঠিকানা, যেমন 93.184.215.14। 127.0.0.1 একটা বিশেষ ঠিকানা — loopback, মানে "এই machine নিজেই"; packet কোনো তারে যায় না, kernel-এর ভেতরেই ঘুরে আসে।
  • Port: একই machine-এর ভেতরে কোন program, সেটা বোঝানোর একটা ১৬-bit সংখ্যা (০ থেকে ৬৫,৫৩৫)। Server সাধারণত একটা চেনা port-এ বসে থাকে — HTTPS 443, Postgres 5432, তোমার dev server 3000।
  • TCP আর UDP: packet-এর উপর বসানো দুইটা নিয়ম (protocol)। TCP দেয় একটা নির্ভরযোগ্য, ক্রম-ঠিক-রাখা byte-এর স্রোত — Chapter 26-এ তার ভেতরটা। UDP দেয় আলাদা আলাদা বার্তা, কোনো নিশ্চয়তা ছাড়া।

একটা TCP connection-কে kernel চেনে চারটা মান দিয়ে: (client IP, client port, server IP, server port) — একে বলে four-tuple। Client-এর port তুমি সাধারণত বাছো না; connect()-এর সময় kernel একটা খালি নম্বর নিজেই দিয়ে দেয় — ephemeral port। কোন range থেকে দেবে, দেখা যায়:

sysctl net.inet.ip.portrange.first net.inet.ip.portrange.last   # macOS
cat /proc/sys/net/ipv4/ip_local_port_range                     # Linux

আমার Mac-এ ৪৯১৫২ থেকে ৬৫৫৩৫; Docker-এর Linux-এ ৩২৭৬৮ থেকে ৬০৯৯৯। চারটা মানের যেকোনো একটা আলাদা হলেই connection আলাদা — তাই একই server port 8080-এ হাজারো client একসাথে থাকতে পারে, কারণ প্রত্যেকের (client IP, client port) জোড়া আলাদা।

Socket: kernel-এর object, তোমার হাতে fd

Socket হলো kernel-এর ভেতরের একটা object — একটা connection-এর এক প্রান্ত। এর মধ্যে থাকে four-tuple, connection-এর অবস্থা, আর পাঠানো ও আসা data জমিয়ে রাখার buffer (Chapter 27)। তুমি এটা পাও একটা file descriptor হিসেবে — file-এর মতোই (Chapter 21)। একই fd table-এ বসে, read()/write() দিয়েই কাজ চলে। Unix-এর পুরনো দর্শন "everything is a file" এখানে সবচেয়ে কাজের: যে code একটা fd থেকে পড়তে জানে, সে file, pipe, socket — সবখান থেকে পড়তে পারে।

একটা server আর তিনটা client একই Node process-এ চালিয়ে kernel-এর চোখে কী কী আছে দেখি। ss হলো Linux-এর socket দেখার tool (iproute2 package-এ):

EXPERIMENT (Linux / Docker) — sockets.js
// sockets.js — একটা server, তিনটা client (সবাই এক process-এ, দেখার সুবিধার জন্য)
const net = require('net');
const fs = require('fs');
const { execSync } = require('child_process');

const server = net.createServer(() => {});
server.listen(8080, '127.0.0.1', () => {
  let n = 0;
  for (let i = 0; i < 3; i++)
    net.connect(8080, '127.0.0.1', () => { if (++n === 3) setTimeout(show, 100); });
});

function show() {
  console.log(execSync("ss -tan '( sport = :8080 or dport = :8080 )'").toString());
  for (const fd of fs.readdirSync('/proc/self/fd')) {        // এই process-এর খোলা fd গুলো
    let target = '';
    try { target = fs.readlinkSync(`/proc/self/fd/${fd}`); } catch {}
    if (target.startsWith('socket:')) console.log(`fd ${fd} -> ${target}`);
  }
  process.exit(0);
}

তিনটা connection, অথচ সাতটা socket। একটা LISTEN — server-এর "দরজা", যেটা কোনো নির্দিষ্ট client-এর সাথে যুক্ত না (peer *)। তারপর প্রতিটা connection-এর দুই প্রান্ত: client-এর দিকে local port ৩৬৬৬০/৩৬৬৬৬/৩৬৬৮০ (kernel-এর দেওয়া ephemeral port), আর server-এর দিকে local port 8080 — তিনটাই 8080, শুধু peer আলাদা। আর fd table-এ ঠিক সাতটা fd, প্রতিটা socket:[…] — বন্ধনীর সংখ্যাটা kernel-এর ভেতরে ওই socket-এর নিজের নম্বর। Socket সত্যিই fd-ই।

দুই পাশের app শুধু নিজের socket fd দেখে আর byte লেখে বা পড়ে। Byte-কে packet বানানো, হারালে আবার পাঠানো, ক্রম ঠিক রাখা, আর আসা packet কোন socket-এর তা four-tuple দেখে ঠিক করা — সবটা দুই kernel-এর কাজ, user/kernel সীমানার নিচে। নিচের four-tuple-এর সংখ্যা গুলো উদাহরণ।

Server-এর চার ধাপ

Client-এর কাজ সরল: socket বানাও, connect()। Server-এর ছন্দ আলাদা, চার ধাপে। Node-এর net.createServer().listen() ভেতরে ঠিক কী চায়, strace-এ দেখি:

EXPERIMENT (Linux / Docker) — একটা server-এর system call
docker run --rm -it --cap-add SYS_PTRACE node:22-bookworm-slim bash
apt-get update -qq && apt-get install -y -qq strace

cat > tiny.js <<'EOF'
const net = require('net');
const s = net.createServer(c => { c.end('hi\n'); s.close(); });
s.listen(8080, '127.0.0.1', () => net.connect(8080, '127.0.0.1').resume());
EOF
strace -f -e trace=socket,setsockopt,bind,listen,accept4 node tiny.js 2>&1 | grep -E "AF_INET|setsockopt|bind|listen|accept4"
[pid   131] socket(AF_INET, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, IPPROTO_IP) = 18
[pid   131] setsockopt(18, SOL_SOCKET, SO_REUSEADDR, [1], 4) = 0
[pid   131] bind(18, {sa_family=AF_INET, sin_port=htons(8080), sin_addr=inet_addr("127.0.0.1")}, 16) = 0
[pid   131] listen(18, 511)             = 0
[pid   131] socket(AF_INET, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, IPPROTO_IP) = 19
[pid   131] accept4(18, NULL, NULL, SOCK_CLOEXEC|SOCK_NONBLOCK) = 20
  1. socket(): kernel একটা খালি socket object বানায়, fd 18 দেয়। AF_INET মানে IPv4, SOCK_STREAM মানে TCP। SOCK_NONBLOCK — Node সব socket non-blocking করে রাখে, কারণ সে এদের epoll দিয়ে সামলায় (Chapter 28–29)।
  2. bind(): "127.0.0.1-এর port 8080 আমার।" অন্য কেউ আগে নিয়ে থাকলে এখানেই চেনা error EADDRINUSE। (আগের setsockopt(SO_REUSEADDR) একটা অনুমতি — server restart-এর পর আগের connection-এর শেষ চিহ্ন থাকলেও port আবার নেওয়া যাবে; Chapter 26।)
  3. listen(18, 511): socket-কে দরজা বানাও। এই মুহূর্ত থেকে kernel নিজে থেকে connection নিতে শুরু করে। ৫১১ হলো Node-এর default backlog — accept-এর অপেক্ষায় কতগুলো connection জমতে পারবে (Chapter 26); ওপরের ss-এর LISTEN লাইনের Send-Q 511 এটাই।
  4. accept4(): জমে থাকা একটা connection তুলে নাও — kernel তার জন্য নতুন একটা socket দেয়, fd 20। Data আদান-প্রদান চলে এই নতুন fd-তে; fd 18 দরজা হয়েই থাকে, পরের জনের জন্য। (মাঝের fd 19 আমাদের client-এর socket।)

একটা দরজা, অনেক ঘর। Listening socket কারো সাথে যুক্ত না; প্রতিটা accept() একজন client-এর জন্য নতুন একটা connected socket দেয়। সবার local port ৮০৮০, peer port আলাদা — ওপরের ss-এর আসল সংখ্যা।

TCP বনাম UDP

TCP-তে কথা বলার আগে একটা connection বানাতে হয় — দুই kernel আগে একমত হয় (Chapter 26)। UDP-তে কোনো connection নেই: প্রতিটা বার্তা (datagram) আলাদা packet হয়ে ঠিকানায় রওনা দেয়; পৌঁছাল কি না, কোন ক্রমে পৌঁছাল — UDP কিছুই দেখে না। পার্থক্যটা সবচেয়ে পরিষ্কার এমন একটা port-এ যেখানে কেউ শুনছে না:

EXPERIMENT — udp-vs-tcp.js
// udp-vs-tcp.js — port 9999-এ কেউ শুনছে না; দুই protocol কী বলে?
const dgram = require('dgram');
const net = require('net');

const u = dgram.createSocket('udp4');
u.send('hello', 9999, '127.0.0.1', err => {
  console.log('UDP send:', err ? err.code : 'no error (sent into the void)');
  u.close();
  net.connect(9999, '127.0.0.1')
     .on('error', e => console.log('TCP connect:', e.code));
});
UDP send: no error (sent into the void)
TCP connect: ECONNREFUSED

UDP-র send সফল — বার্তা বেরিয়ে গেছে, কেউ নিল কি না তার খবর রাখার কোনো ব্যবস্থাই নেই। TCP সাথে সাথে জানিয়ে দিয়েছে কেউ শুনছে না (ECONNREFUSED), কারণ connect-এর সময় অপর পাশের kernel-এর উত্তর লাগে। UDP সস্তা আর দেরিহীন, তাই সেখানে চলে যেখানে একটা হারানো বার্তা আবার পাঠানোর চেয়ে পরেরটা পাঠানোই ভালো, বা যেখানে app নিজের মতো করে নির্ভরযোগ্যতা বানাতে চায়: DNS lookup, video call, online game, আর HTTP/3 (যার নিচের QUIC protocol UDP-র উপর নিজস্ব নির্ভরযোগ্যতা বানায়)।

একই machine-এ: Unix domain socket

দুইটা process যদি একই machine-এ থাকে, তাহলে IP আর port-এর ঝামেলা কেন? Unix domain socket-এর ঠিকানা একটা file path; data কোনো network stack-এর ভেতর দিয়ে যায় না, kernel এক process-এর buffer থেকে আরেক process-এর buffer-এ সরাসরি দেয়। API হুবহু একই — Node-এ port-এর জায়গায় path দিলেই হলো:

EXPERIMENT — unixsock.js
// unixsock.js — একই machine-এর দুই process-এর জন্য socket: network না, একটা file path
const net = require('net');
const fs = require('fs');
const path = '/tmp/demo.sock';
try { fs.unlinkSync(path); } catch {}
const server = net.createServer(c => c.end('hello over a unix socket\n'));
server.listen(path, () => {
  console.log(fs.statSync(path).isSocket() ? 'file type: socket' : 'not a socket');
  net.connect(path).on('data', d => { process.stdout.write(d); server.close(); });
});
file type: socket
hello over a unix socket

তুমি এটা রোজ ব্যবহার করো, না জেনেই। docker command আসলে Docker daemon-এর সাথে HTTP-তে কথা বলে — কিন্তু TCP port-এ না, একটা Unix socket-এ:

ls -l /var/run/docker.sock
curl -s --unix-socket /var/run/docker.sock http://localhost/version | head -c 120

আমার Mac-এ প্রথমটা দেখায় /var/run/docker.sock -> /Users/mostofareza/.docker/run/docker.sock, আর দ্বিতীয়টা ফেরত দেয় {"Platform":{"Name":"Docker Desktop 4.46.0 (204649)"},"Components":[{"Name":"Engine","Version":"28.4.0",… — সাধারণ HTTP request আর JSON উত্তর, শুধু পথটা একটা file। Postgres-এর local connection (/var/run/postgresql/.s.PGSQL.5432) একই কৌশল।

COMMON MISCONCEPTION

"একটা port মানে একটা connection — তাই এক port-এ একসাথে একজনই কথা বলতে পারে।" Port শুধু four-tuple-এর একটা অংশ। sockets.js-এ port 8080-এ তিনটা connection একসাথে, তিনটা আলাদা socket আর fd নিয়ে; kernel আসা packet-কে চারটা মান মিলিয়ে ঠিক socket-এ পাঠায়। একটা server port-এ লাখো connection সম্ভব — সীমা আসে memory আর fd-র সংখ্যা থেকে (Chapter 30), port থেকে না।

MENTAL MODEL

Socket হলো kernel-এর ভেতরে একটা connection-এর এক প্রান্ত, তোমার হাতে একটা fd। তুমি byte লেখো আর পড়ো; packet বানানো, পাঠানো, সাজানো, আর কোন packet কোন socket-এর তা four-tuple মিলিয়ে ঠিক করা — kernel-এর কাজ। Server-এ একটা listening socket দরজা হয়ে দাঁড়িয়ে থাকে, আর প্রতিটা accept() একজন client-এর জন্য নতুন socket দেয়। TCP connection বানিয়ে নির্ভরযোগ্য স্রোত দেয়, UDP শুধু বার্তা ছুড়ে দেয়; একই machine-এ Unix socket network ছাড়াই একই API দেয়।

CAN I EXPLAIN THIS?
  • Kernel socket না দিয়ে শুধু raw packet দিলে প্রতিটা app-কে কী কী করতে হতো? কোন packet কোন process-এর, সেটা kernel কীভাবে ঠিক করে?
