PART 5 · PROCESS MANAGEMENT

Chapter 19 — Thread কখন ব্যবহার করবে?

Workload চেনো, তারপর tool বাছো — একটা practical decision framework।

প্রথম প্রশ্ন: তোমার workload কী-bound?

  • CPU-bound: সময় যাচ্ছে হিসাবে — image processing, encryption, বড় JSON parse, ML inference। CPU 100%-এ আটকে।
  • I/O-bound: সময় যাচ্ছে অপেক্ষায় — DB query, HTTP call, file read। CPU বেশিরভাগ সময় অলস; process টা Waiting state-এ (Chapter 15) পড়ে থাকে।

বেশিরভাগ web backend আসলে I/O-bound — request-এর জীবনের সিংহভাগ কাটে DB আর downstream service-এর অপেক্ষায়।

Framework

পরিস্থিতিভালো fitকেন
CPU-bound, কাজগুলো মোটামুটি স্বাধীন, data ভারী share করতে হয় নাMultiple processesসব core কাজে লাগে, isolation ফ্রি — একটার crash/leak অন্যদের ছোঁয় না। (PM2 cluster, worker process)
CPU-bound, কিন্তু বড় shared data structure-এর উপর সবাই কাজ করবেThreadsData copy না করে share করা যায়; process-এর মধ্যে বড় data পাঠানো দামি।
I/O-bound, অনেক concurrent connectionEvent loop / async I/Oঅপেক্ষার জন্য thread পোষা অপচয় — এক thread-ই non-blocking ভাবে হাজারটা সামলায় (Chapter 28-29)।
I/O-bound, কিন্তু blocking API/library ব্যবহার করতেই হবেThread poolBlocking call-গুলো pool-এর thread-এ ফেলে main flow মুক্ত রাখো। (Node-এর libuv নিজেই এটা করে।)

Thread-এর hidden bill

  • প্রতিটা thread-এর নিজস্ব stack (default প্রায়ই MB-স্কেলে reserve হয়) — দশ হাজার thread মানে memory-র বিশাল দাবি।
  • Thread যত বেশি, context switch তত বেশি (Chapter 17) — একটা সীমার পরে থread যোগ করলে throughput কমে।
  • Shared state এলেই lock, lock এলেই contention + deadlock-এর ঝুঁকি + মাথার ব্যথা (Chapter 18)।
RULE OF THUMB

CPU-bound হলে parallelism দরকার — core-সংখ্যার কাছাকাছি worker (process বা thread)। I/O-bound হলে parallelism না, দরকার অপেক্ষাটা সস্তায় করা — async I/O/event loop। আর isolation যত পাও নিয়ে নাও: shared state যত কম, রাতের ঘুম তত ভালো।

  • CPU-bound কাজে core-এর চেয়ে অনেক বেশি thread দিলে কী হয়?
