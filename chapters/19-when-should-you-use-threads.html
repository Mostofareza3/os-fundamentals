PART 5 · PROCESS MANAGEMENT

Chapter 19 — Thread কখন ব্যবহার করবে?

আগে workload চেনো — CPU-র কাজ নাকি অপেক্ষার কাজ — তারপর হাতিয়ার বাছো: event loop, libuv-এর thread pool, worker, নাকি আলাদা process। সাথে thread-এর লুকানো বিল।

Part 5-এর সব টুকরো এখানে একটা সিদ্ধান্তে জোড়া লাগবে। মনে করিয়ে দিই: thread সস্তা কিন্তু সব memory ভাগ করে (Chapter 16); প্রতিটা পালা বদলের সরাসরি আর লুকানো দাম আছে, core-এর চেয়ে বেশি CPU-র কাজের thread মানে লোকসান (Chapter 14, 17); ভাগাভাগি করা data মানে race আর lock-এর ঝামেলা (Chapter 18); আর যে thread কোনো কিছুর অপেক্ষায়, সে blocked — CPU চায় না (Chapter 15)।

প্রথম প্রশ্ন: সময় যাচ্ছে কোথায়?

"Thread দিলে দ্রুত হবে কি?" — উত্তর নির্ভর করে তোমার program-এর সময় কীসে যাচ্ছে তার উপর। দুই রকম কাজ আছে:

  • CPU-bound — সময় যাচ্ছে হিসাবে: image resize, encryption, বড় JSON parse, report বানানো। CPU পুরো সময় ব্যস্ত।
  • I/O-bound — সময় যাচ্ছে অপেক্ষায়: database query, HTTP call, disk। Process বেশিরভাগ সময় blocked, CPU অলস।

কোনটা, সেটা আন্দাজ না করে মাপো — Chapter 1-এর time দিয়েই। মোট সময় (real বা total) আর CPU-র সময়ের (user + system) তুলনা করো:

# ১) হিসাবের কাজ
time node -e "let s = 0; for (let i = 0; i < 2e9; i++) s += i % 7;"

# ২) অপেক্ষার কাজ — ৫০টা 'database query', প্রতিটা ৪০ ms (setTimeout দিয়ে নকল করা)
time node -e "
const sleep = ms => new Promise(r => setTimeout(r, ms));
(async () => { for (let i = 0; i < 50; i++) await sleep(40); })();"

আমার Mac-এ:

5.42s user 0.11s system 96% cpu 5.711 total
0.02s user 0.01s system 1% cpu 2.070 total

প্রথমটায় CPU-র সময় প্রায় মোট সময়ের সমান (96% cpu) — CPU-bound। দ্বিতীয়টায় দুই সেকেন্ডের মধ্যে CPU খেটেছে ৩০ ms (1% cpu) — বাকি পুরো সময় অপেক্ষা। বেশিরভাগ web backend দ্বিতীয় দলের: একটা request-এর জীবনের সিংহভাগ কাটে database আর অন্য service-এর উত্তরের অপেক্ষায়। Production-এ একই প্রশ্ন করো উল্টো দিক থেকে: server ধীর, কিন্তু top-এ তার CPU কত? ১০০%-এর কাছে হলে CPU-bound; ১০%-এ পড়ে থাকলে সমস্যা অপেক্ষায় — আরও thread সেটা সারাবে না।

অপেক্ষার কাজ: thread না, event loop

পুরনো ধাঁচের server-এর নকশা ছিল "প্রতিটা connection-এর জন্য একটা thread" — thread-টা query পাঠিয়ে blocked হয়ে বসে থাকে, উত্তর এলে জাগে। দশ হাজার connection মানে দশ হাজার thread, যাদের প্রায় সবাই ঘুমিয়ে, অথচ প্রত্যেকে নিজের stack-এর জায়গা আটকে রাখে, আর প্রত্যেকের জাগা-ঘুমানোয় context switch (Chapter 17)। Thread-এর স্ট্যাকের দামটা মাপো:

EXPERIMENT (Linux / Docker) — ১০০০টা ঘুমন্ত thread
docker run --rm debian:bookworm-slim bash -c 'apt-get update -qq >/dev/null 2>&1 && apt-get install -y -qq python3 >/dev/null 2>&1; python3 -c "
import threading, re
def vm():
    s = open(\"/proc/self/status\").read()
    return {k: int(re.search(k + r\":\s+(\d+)\", s).group(1)) // 1024 for k in (\"VmSize\", \"VmRSS\")}
print(\"before:\", vm(), \"MB\")
ev = threading.Event()
ts = [threading.Thread(target=ev.wait) for _ in range(1000)]   # ১০০০টা thread, সবাই অপেক্ষায়
for t in ts: t.start()
print(\"1000 idle threads:\", vm(), \"MB\")
ev.set()"; ulimit -s'

আমার output:

before: {'VmSize': 13, 'VmRSS': 7} MB
1000 idle threads: {'VmSize': 14174, 'VmRSS': 27} MB
8192

এক হাজার ঘুমন্ত thread-এ virtual memory ১৩ MB থেকে ১৪ GB! প্রতিটা thread-এর জন্য kernel ৮ MB (ulimit -s-এর 8192 KB) stack-এর জায়গা reserve করেছে, সাথে guard page। RSS বেড়েছে মাত্র ২০ MB — Chapter 9-এর lazy allocation: না ছোঁয়া পর্যন্ত frame নেই। তবু দশ হাজার thread মানে ১৪০ GB-র প্রতিশ্রুতি, আর Chapter 10-এর overcommit-এর নিয়ম কড়া হলে সেটা আটকে যায়।

Event loop-এর উত্তর: অপেক্ষার জন্য thread পোষার দরকারই নেই। একটা thread অনেকগুলো কাজ শুরু করে দেয়, তারপর OS-কে বলে "এদের কারও উত্তর এলে আমাকে জানিও" (কীভাবে — epoll, kqueue — Chapter 28–29)। Chapter 18-এর পরীক্ষাটা মনে করো: এক thread-এ এক হাজারটা ১০০ ms-এর অপেক্ষা শেষ হয়েছিল ১০৩ ms-এ। Node, nginx, Redis — সবাই এই নকশার উপর দাঁড়িয়ে।

CPU-র কাজ: main thread থেকে সরাও

Event loop-এর একটা দুর্বলতা আছে: সব JS এক thread-এ, তাই একটা ভারী হিসাব চলার সময় আর কিছুই চলে না — অন্য সব request-এর callback লাইনে দাঁড়িয়ে থাকে। নিচের server-এ দুইটা route: /hash একটা ভারী password hash বানায়, /ping সঙ্গে সঙ্গে উত্তর দেয়। Server আলাদা process-এ চলে (যাতে মাপার code-ও আটকে না যায়); /hash শুরু হওয়ার ৫০ ms পরে /ping পাঠিয়ে দেখি উত্তর আসতে কত লাগে:

EXPERIMENT — server.js
// একটা server: /hash ভারী CPU-র কাজ, /ping হালকা।
// প্রশ্ন: /hash চলার সময় /ping কত দ্রুত উত্তর পায়?
const http = require('http');
const crypto = require('crypto');
const { fork } = require('child_process');

if (process.argv[2] === 'serve') {                           // ---- server process ----
  const mode = process.argv[3];
  const server = http.createServer((req, res) => {
    if (req.url === '/hash') {
      if (mode === 'sync') {                                 // main thread-এই হিসাব
        crypto.pbkdf2Sync('secret', 'salt', 2_000_000, 64, 'sha512');
        res.end('done');
      } else {                                               // libuv-এর thread pool-এ পাঠাও
        crypto.pbkdf2('secret', 'salt', 2_000_000, 64, 'sha512', () => res.end('done'));
      }
    } else res.end('pong');
  });
  server.listen(0, () => process.send(server.address().port));
} else {                                                     // ---- client process ----
  const mode = process.argv[2];                              // 'sync' বা 'async'
  const child = fork(__filename, ['serve', mode]);
  child.on('message', async port => {
    const get = path => new Promise(r => http.get({ port, path }, res => { res.resume(); res.on('end', r); }));
    const hash = get('/hash');
    await new Promise(r => setTimeout(r, 50));               // /hash শুরু হতে দাও
    const t = performance.now();
    await get('/ping');
    console.log(`${mode.padEnd(5)}: /ping answered in ${(performance.now() - t).toFixed(0).padStart(4)} ms`);
    await hash;
    child.kill();
  });
}

node server.js sync আর node server.js async — আমার Mac-এ:

sync : /ping answered in  432 ms
async: /ping answered in    3 ms

একই কাজ, একই server। pbkdf2Sync main thread-এ চলায় ওই পুরো সময় server কানে তুলো দিয়ে বসে ছিল — সবচেয়ে হালকা request-ও ৪৩২ ms অপেক্ষা করল। pbkdf2-এর async version কাজটা Node-এর thread pool-এর একটা thread-এ পাঠিয়ে দেয়; main thread মুক্ত, /ping ৩ ms-এ। একশো user-এর server-এ প্রথমটার মানে: একজনের login বাকি নিরানব্বই জনকে আটকে দেয়।

তোমার নিজের CPU-ভারী JS (একটা বড় report, image-এর pixel ঘাঁটা) async API দিয়ে pool-এ পাঠানো যায় না — সেটার জন্য worker_threads। বাস্তবে একটা worker pool রাখো, আকার core-এর সংখ্যার কাছাকাছি (os.availableParallelism()) — Chapter 14-এর parallel.js-এ ১২টা worker পর্যন্ত লাভ, ২৪-এ উল্টো। (piscina-র মতো npm library এই pool সাজিয়ে দেয়।) আর যদি দরকার হয় একজনের crash বা memory leak যেন অন্যদের না ছোঁয় (Chapter 16-এর SIGSEGV), বা কাজ কয়েকটা machine-এ ছড়াতে হয় — তখন thread না, আলাদা process: Node-এর cluster, PM2, বা একটা queue-র পেছনে আলাদা worker service।

libuv-এর thread pool আর তার সীমা

Chapter 16-এ দেখেছিলে প্রথম fs.readFile-এর পরে চারটা libuv-worker thread হাজির হয়। Node-এর যেসব async কাজের পেছনে OS-এর কোনো "উত্তর এলে জানাও" ব্যবস্থা নেই — file system-এর কাজ, dns.lookup, crypto-র ভারী function, zlib — সেগুলো এই pool-এ blocking ভাবে চলে, আর শেষ হলে main thread-কে খবর দেয়। Pool-এর default মাপ ৪। পাঁচ নম্বর কাজকে তাহলে কী করতে হয়?

EXPERIMENT — pool.js
const crypto = require('crypto');
const t = performance.now();
for (let i = 1; i <= 8; i++) {                     // একসাথে ৮টা ভারী hash
  crypto.pbkdf2('secret', 'salt', 500_000, 64, 'sha512', () => {
    console.log(`task ${i} finished at ${(performance.now() - t).toFixed(0).padStart(4)} ms`);
  });
}

node pool.js — আমার Mac-এ চারটা করে দুই দফা: task ১–৪ শেষ হয়েছে 172–218 ms-এ, task ৫–৮ 330–391 ms-এ। এবার UV_THREADPOOL_SIZE=8 node pool.js: আটটাই 150–256 ms-এর মধ্যে।

Default-এ ৪টা thread, তাই পরের চারটা কাজ আগের চারটার শেষ হওয়ার জন্য লাইনে দাঁড়িয়েছিল — দ্বিগুণ সময়। বাস্তব বিপদটা আরও সূক্ষ্ম: তোমার server-এ চারটা ভারী crypto কাজ চললে ততক্ষণ একটা সাধারণ fs.readFile-ও pool-এ জায়গা পায় না — সম্পূর্ণ অসম্পর্কিত file পড়া হঠাৎ ধীর। Pool বড় করা যায় process চালুর আগে UV_THREADPOOL_SIZE environment variable দিয়ে (সর্বোচ্চ ১০২৪), কিন্তু CPU-ভারী কাজের জন্য core-এর বেশি দিয়ে লাভ নেই (Chapter 17)। আর মনে রেখো: network socket এই pool ব্যবহার করে না — সেগুলো OS-এর event ব্যবস্থায় চলে, তাই হাজার HTTP call-এ pool-এর চাপ পড়ে না।

সিদ্ধান্তের পথ। প্রথম ধাপ সবসময় মাপা। অপেক্ষার কাজে event loop-ই উত্তর, thread শুধু সেই library-র জন্য যেটা blocking ছাড়া কিছু পারে না। হিসাবের কাজে প্রথম লক্ষ্য main thread মুক্ত রাখা — Node-এর নিজের async API থাকলে সেটা, নিজের JS হলে worker pool; আর বিচ্ছিন্নতা বা একাধিক machine লাগলে process।

COMMON MISCONCEPTION

"Node single-threaded, তাই multi-core কাজে লাগাতে পারে না।" তোমার JS এক thread-এ চলে, কিন্তু process-এ এক ডজনের কাছাকাছি thread (Chapter 16); async crypto/zlib/fs থেকেই libuv pool-এর চারটা core কাজে লাগে; worker_threads আর cluster দিয়ে বাকি গুলোও। উল্টো ভুলটাও করো না: "আরও thread দিলে I/O দ্রুত হবে" — অপেক্ষার কাজে সীমা database বা network-এর, thread-এর সংখ্যার না।

RULE OF THUMB

আগে মাপো: real বনাম user + sys। অপেক্ষার কাজে parallelism না, দরকার অপেক্ষাটা সস্তায় করা — event loop। হিসাবের কাজে দরকার parallelism — core-এর সমান worker, আর main thread সবসময় মুক্ত। Thread-এর মধ্যে ভাগাভাগি যত কম, ঘুম তত ভালো; আর যেখানে বিচ্ছিন্নতা দামি, সেখানে thread না, process।
