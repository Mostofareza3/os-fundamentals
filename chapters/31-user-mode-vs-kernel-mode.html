PART 8 · USER SPACE AND KERNEL SPACE

Chapter 31 — User Mode vs Kernel Mode

Kernel-এ ঢোকার তিন দরজা, kernel থেকে process-এর দিকে ফেরার উল্টো দরজা (signal), kernel কেন তোমার দেওয়া প্রতিটা সংখ্যা সন্দেহ করে, root কেন আসলে সর্বশক্তিমান না, আর যে দুই পাহারাদার memory আগলে রাখে — তাদের একজন একবার কীভাবে ফাঁকি খেয়েছিল।

Chapter 1-এ মূল কথাটা দেখেছি: CPU সবসময় দুই mode-এর একটায় থাকে — user mode-এ তোমার app চলে সীমিত ক্ষমতা নিয়ে, kernel mode-এ kernel চলে সব ক্ষমতা নিয়ে — আর app kernel-এর কাছে কাজ চায় system call দিয়ে। এই chapter সেই ছবির ভেতরে ঢোকে। Syscall ছাড়া kernel আর কোন পথে CPU হাতে পায়? Kernel process-কে কোনো খবর দেবে কীভাবে? আর যে পাহারার উপর পুরো ব্যবস্থা দাঁড়িয়ে, সেটা ঠিক কোথায় বসানো?

ARM CPU-তে (Apple Silicon, আর Docker-এর Linux VM-ও এখানে ARM) এই দুই mode-এর নাম EL0 (user) আর EL1 (kernel) — EL মানে exception level। Intel/AMD-এ নাম ring 3 (user) আর ring 0 (kernel)। নাম আলাদা, ধারণা একই।

Kernel-এ ঢোকার তিন দরজা

ধরো syscall-ই kernel-এ ঢোকার একমাত্র পথ। তাহলে দুটো জিনিস ভেঙে পড়ে। এক: যে program কখনো syscall করে না — ধরো একটা while (true) loop — kernel তার কাছ থেকে CPU কোনোদিন ফেরত পাবে না। দুই: তোমার code এমন কিছু করল যেটা CPU চালাতেই পারে না, যেমন এমন memory ছুঁল যেটা নেই। তখন CPU যাবে কোথায়? Program তো kernel-কে ডাকেনি।

তাই CPU তিনটা আলাদা কারণে user mode থেকে kernel mode-এ যায়:

  • System call — program নিজে চায়। একটা বিশেষ instruction (ARM-এ svc, x86-এ syscall) দিয়ে kernel-কে ডাকে (Chapter 1)।
  • Interrupt — বাইরের hardware ডাকে: timer chip, SSD, network card (Chapter 2)। Program তখন কী করছে তাতে কিছু যায় আসে না; যেকোনো দুই instruction-এর মাঝে এটা ঘটতে পারে।
  • Exception — program-এর নিজের instruction CPU শেষ করতে পারল না। যেমন page table-এ ঠিকানাটা বসানো নেই (page fault, Chapter 9), বা user mode থেকে privileged instruction চালানো হয়েছে। এখানে program ডাকেনি, কিন্তু kernel-এ যাওয়ার কারণটা তার নিজের।

তিন দরজার একটা মিল সবচেয়ে জরুরি: CPU যেখানে খুশি লাফ দেয় না। Boot-এর সময় kernel CPU-র কয়েকটা বিশেষ register-এ নিজের entry point-গুলোর ঠিকানা লিখে রাখে। Entry point মানে kernel-এর যে code দিয়ে একটা দরজায় ঢোকা শুরু হয়। ARM-এ এই ঠিকানার তালিকার নাম exception vector table, x86-এ IDT (আর syscall-এর জন্য আলাদা একটা register)। ওই register-গুলো শুধু kernel mode থেকেই বদলানো যায়। ফলে user mode-এর code দরজা খোলাতে পারে, কিন্তু দরজার ওপাশে কোথায় নামবে, সেটা বদলাতে পারে না।

তিন দরজা, এক নিয়ম। Syscall-এ program নিজে ডাকে, exception-এ তার instruction আটকে যায়, interrupt আসে বাইরের hardware থেকে। তিনটাই নামে kernel-এর boot-এ ঠিক করা entry point-এ। কাজ শেষে kernel user mode-এ ফেরায় (বাঁয়ের নীল তীর); কোনো signal জমে থাকলে ফেরার আগে তার handler-এ পাঠায় (পরের section)।

Syscall দরজা Chapter 1 থেকে strace-এ বহুবার দেখেছি। বাকি দুটো নিজের চোখে দেখা যাক। প্রথমে interrupt: দুটো program নেব, যারা kernel-এর কাছে কিছুই চায় না — শুধু গোনে — আর দুটোকেই একটা মাত্র CPU core-এ বেঁধে দেব। তারপর দেখব kernel তাদের মাঝে CPU ভাগ করতে পারে কিনা।

EXPERIMENT (Linux / Docker) — interrupt দরজা
// spin.js — শুধু গোনা; kernel-এর কাছে কিছুই চায় না
let x = 0;
for (let i = 0; i < 3e9; i++) x += i;
const r = process.resourceUsage();
console.log(`pid ${process.pid}: user ${(r.userCPUTime / 1e3).toFixed(0)} ms, ` +
            `sys ${(r.systemCPUTime / 1e3).toFixed(0)} ms, ` +
            `involuntary switches ${r.involuntaryContextSwitches}`);
# twospin.sh
# CPU0-র timer interrupt কতবার এসেছে (ARM-এ লাইনের নাম arch_timer, Intel/AMD-এ LOC)
timer() { awk '/arch_timer|LOC:/ {print $2; exit}' /proc/interrupts; }
t0=$(timer)
time {
  taskset -c 0 node spin.js &     # দুইজনকেই একটা মাত্র core-এ (CPU0) বাঁধা
  taskset -c 0 node spin.js &
  wait
}
t1=$(timer)
echo "CPU0 timer interrupts: $((t1 - t0))"
docker run --rm --security-opt systempaths=unconfined -v "$PWD":/w:ro -w /w \
  node:22-bookworm-slim bash twospin.sh
pid 10: user 1930 ms, sys 7 ms, involuntary switches 541
pid 9: user 1934 ms, sys 6 ms, involuntary switches 538

real	0m3.887s
user	0m3.869s
sys	0m0.014s
CPU0 timer interrupts: 3887

দুটো নতুন জিনিস। taskset -c 0 process-কে শুধু CPU0-তে চলতে দেয়। আর Docker কিছু /proc file লুকিয়ে রাখে, /proc/interrupts-ও (Chapter 2-এ এটা পাইনি); --security-opt systempaths=unconfined সেগুলো খুলে দেয়।

এবার সংখ্যাগুলো পড়ো। মোট সময় ৩.৯ সেকেন্ড, আর প্রত্যেকে CPU পেয়েছে ১.৯ সেকেন্ড — অর্ধেক অর্ধেক। প্রত্যেককে kernel প্রায় ৫৪০ বার জোর করে নামিয়েছে। এর নাম involuntary switch: process চলতে চাইছিল, kernel তাকে সরিয়ে দিয়েছে (Chapter 17)। অথচ কেউ kernel-কে ডাকেনি। প্রমাণ চাইলে loop চলার সময় strace লাগিয়ে গুনে দেখো:

docker run --rm --cap-add SYS_PTRACE -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq strace >/dev/null
  node spin.js & sleep 0.5
  timeout 1 strace -q -c -f -p $!; wait'

  5.35    0.000047          11         4           getpid

এক সেকেন্ডে ২৬টা syscall। এগুলো V8-এর নিজের ঘরোয়া কাজ (background thread-এর futex, JIT-এর বানানো code-এর mprotect), loop-এর না। ওই এক সেকেন্ডে loop প্রায় ১৫০ কোটি বার ঘুরেছে, একবারও kernel-কে ডাকেনি। তাহলে kernel CPU কেড়ে নিল কীভাবে? উত্তর শেষ লাইনে: ৩.৮৮৭ সেকেন্ডে CPU0-তে ৩৮৮৭টা timer interrupt, মানে প্রতি millisecond-এ একটা। প্রতিটা tick-এ CPU loop-এর মাঝখানে থেমে interrupt দরজা দিয়ে kernel-এ ঢোকে। Kernel তখন ঠিক করে একই process চলবে নাকি অন্যজন। এখানে গড়ে ৩–৪ tick পরপর পালা বদলেছে।

এবার exception দরজা। এর দুই রকম পরিণতি আছে। Chapter 9-এর page fault মনে করো: process-এর চাওয়া memory kernel আগে থেকে বসায় না, প্রথম ছোঁয়ায় বসায়। প্রতিটা প্রথম ছোঁয়া আসলে একটা exception:

// fault.js — memory ছুঁলেই exception দরজা
const before = process.resourceUsage().minorPageFault;
const buf = Buffer.allocUnsafeSlow(100 * 1024 * 1024);   // ১০০ MB চাওয়া
const mid = process.resourceUsage().minorPageFault;
buf.fill(1);                                             // এবার প্রতিটা byte ছোঁয়া
const after = process.resourceUsage().minorPageFault;
console.log(`চাওয়ার সময় page fault: ${mid - before}, ছোঁয়ার সময়: ${after - mid}`);
চাওয়ার সময় page fault: 28, ছোঁয়ার সময়: 6412

আমার Mac-এ page-এর মাপ ১৬ KB, আর ১০০ MB ÷ ১৬ KB = ৬৪০০। প্রায় প্রতিটা page-এর প্রথম ছোঁয়ায় CPU থেমেছে, exception দরজা দিয়ে kernel-এ ঢুকেছে। Kernel একটা খালি frame বসিয়ে instruction-টা আবার চালিয়েছে, আর program কিছু টেরই পায়নি। (Docker-এর Linux-এ একই script-এ আসে মাত্র ৬০-এর মতো, কারণ সেখানে Transparent Huge Pages চালু, তাই এক fault-এ ২ MB বসে — Chapter 10।)

দ্বিতীয় পরিণতি মারাত্মক। Kernel দেখে ঠিকানাটা আসলেই অবৈধ, তখন আর বসানোর কিছু নেই। JS থেকে এটা ঘটানো কঠিন, কারণ V8 তোমাকে সাধারণত অবৈধ memory-র কাছেই যেতে দেয় না। তবে একটা ফাঁক আছে। V8 নিজের stack-এর মাপ নিজে হিসাব রাখে (default এক MB-র মতো); সীমা পেরোলে সে নিজেই RangeError দেয়, kernel জানতেই পারে না। --stack-size দিয়ে V8-কে যদি মিথ্যা বলি যে stack ৫০ MB, অথচ আসল stack মাত্র ৮ MB:

node -e "function f(){ f() } f()" 2>&1 | grep RangeError    # V8 নিজেই ধরে ফেলে
node --stack-size=50000 -e "function f(){ f() } f()"          # V8-কে বলা হলো stack ৫০ MB
echo "exit $?"
RangeError: Maximum call stack size exceeded
exit 139

দ্বিতীয়বার V8 থামেনি। Stack-এর শেষ সীমা পেরিয়ে সে এমন ঠিকানায় লিখতে গেছে যেটা map করাই নেই, সেখানে exception। Kernel দেখল ঠিকানাটা কোনো বৈধ এলাকার মধ্যে পড়ে না, তাই process-কে SIGSEGV পাঠিয়ে মেরে ফেলল। Exit code ১৩৯ = ১২৮ + ১১, আর ১১ হলো SIGSEGV-এর নম্বর (Chapter 16)। Linux-এ strace দিয়ে দেখলে kernel নিজেই কারণটা লিখে দেয়:

docker run --rm --cap-add SYS_PTRACE node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq strace >/dev/null
  strace -e trace=none node --stack-size=50000 -e "function f(){ f() } f()"'
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=0xffffe02caff0} ---
--- SIGSEGV {si_signo=SIGSEGV, si_code=SI_KERNEL, si_addr=NULL} ---
+++ killed by SIGSEGV +++

SEGV_MAPERR মানে "এই ঠিকানায় কিছু map করা নেই", আর si_addr সেই ঠিকানা — stack-এর ঠিক নিচে। দ্বিতীয় লাইনটা একটা খুঁটিনাটি: Node নিজের একটা SIGSEGV handler বসিয়ে রাখে। কিন্তু সেটা চালাতে stack-এ একটু জায়গা লাগে, আর stack তো ভরা। তাই kernel জোর করে default কাজটাই করেছে: মেরে ফেলা।

উল্টো দরজা: signal

এতক্ষণ সব দরজা ছিল user mode থেকে kernel-এর দিকে। কিন্তু kernel-কেও মাঝে মাঝে process-কে কিছু জানাতে হয়: "তুমি অবৈধ memory ছুঁয়েছ", "user Ctrl-C চেপেছে", "তোমাকে বন্ধ হতে বলা হচ্ছে", "তোমার child process শেষ"। সমস্যা হলো kernel process-এর কোনো function সরাসরি "call" করতে পারে না। Process নিজের গতিতে চলছে, আর kernel নিজে user mode-এর code চালায় না।

এর সমাধান signal: একটা নম্বরওয়ালা ছোট খবর, যেটা kernel process-কে পৌঁছে দেয়। কেউ kill দিয়ে পাঠাতে পারে, আবার kernel নিজেও পাঠায়। পৌঁছানোর পথটা এরকম:

  1. Kernel খবরটা process-এর PCB-তে (kernel-এর রাখা process-এর খাতা, Chapter 3) "pending" হিসেবে টুকে রাখে। Process অন্য core-এ চলতে থাকলে kernel সেই core-এ একটা interrupt পাঠায়, যাতে সে তাড়াতাড়ি থামে।
  2. Thread যখনই kernel mode থেকে user mode-এ ফিরতে যায় — syscall শেষে, interrupt শেষে, বা exception শেষে — kernel pending signal আছে কিনা দেখে। Timer interrupt ঘন ঘন আসে (উপরের experiment-এ প্রতি millisecond-এ), তাই একটা ব্যস্ত loop-ও signal-কে বেশিক্ষণ এড়িয়ে থাকতে পারে না।
  3. ওই signal-এর জন্য process কোনো handler (signal এলে চালানোর function) না বসালে kernel নিজেই default action করে। বেশিরভাগ signal-এর default হলো process মেরে ফেলা। এখানে process-এর একটা instruction-ও চলে না।
  4. Handler বসানো থাকলে kernel ফেরার ঠিকানা বদলে দেয়। Process যেখানে থেমেছিল সেখানে না ফিরে handler-এর শুরুতে যায়; আগের অবস্থা kernel user stack-এ সেভ করে রাখে। Handler শেষ হলে rt_sigreturn নামে একটা বিশেষ syscall করে। Kernel তখন সেভ করা অবস্থা ফিরিয়ে দেয়, আর process ঠিক আগের জায়গা থেকে চলতে থাকে।

দুটো signal-এর জন্য handler বসানোই যায় না: SIGKILL আর SIGSTOP। এটা kernel-এর তরফ থেকে admin-কে দেওয়া নিশ্চয়তা যে যেকোনো process-কে থামানো যাবে। সবচেয়ে বেশি যেগুলোর দেখা পাবে (নম্বরগুলো Linux-এর; macOS-এ কয়েকটা আলাদা):

Signal-এ মরলে shell exit code দেখায় ১২৮ + signal-এর নম্বর। মিলিয়ে দেখো (Mac-এ, bash দিয়ে):

# kills.sh
# ১) কোনো handler নেই: SIGTERM-এর default কাজ — মৃত্যু
node -e "setInterval(() => {}, 1000)" &
sleep 0.3; kill -TERM $!; wait $! 2>/dev/null; echo "no handler, SIGTERM -> exit $?"

# ২) SIGTERM-এর handler আছে (কিছুই করে না), তারপর SIGKILL
node -e "process.on('SIGTERM', () => {}); setInterval(() => {}, 1000)" &
sleep 0.3; kill -TERM $!; sleep 0.3
kill -0 $! && echo "SIGTERM caught, still alive"      # -0: শুধু জিজ্ঞেস, বেঁচে আছে?
kill -KILL $!; wait $! 2>/dev/null; echo "SIGKILL -> exit $?"

SIGTERM caught, still alive
SIGKILL -> exit 137

১৪৩ = ১২৮ + ১৫, আর ১৩৭ = ১২৮ + ৯। Container "137 দিয়ে বেরিয়েছে" দেখলে বুঝবে কেউ SIGKILL দিয়েছে: হয় OOM killer, নয়তো grace period শেষে Docker বা Kubernetes। দ্বিতীয় process-টা খেয়াল করো। Handler বসানো মানেই default কাজটা (মৃত্যু) বাতিল। Handler নিজে exit না করলে process দিব্যি বেঁচে থাকে, আর তখন একমাত্র উপায় SIGKILL। SIGKILL-এর handler বসাতে চাইলে kernel নিজেই মানা করে; প্রমাণ পরের section-এ।

এবার Node-এর একটা ব্যাপার, যেটা production-এ ঝামেলা বাধায়। নিচের script-এ SIGTERM handler আছে, কিন্তু main thread একটা ৩ সেকেন্ডের হিসাবে ব্যস্ত (যেমন একটা বড় JSON parse, বা একটা ভারী report):

// sigtrap.js — SIGTERM handler আছে, কিন্তু main thread ব্যস্ত
const t0 = Date.now();
const log = (m) => console.log(`${String(Date.now() - t0).padStart(5)} ms  ${m}`);

setInterval(() => {}, 1000);              // server-এর মতো: process চালু থাকে
process.on('SIGTERM', () => { log('JS SIGTERM handler: cleanup, exit'); process.exit(0); });

log(`pid ${process.pid}, ৩ সেকেন্ডের হিসাব শুরু`);
const end = Date.now() + 3000;
while (Date.now() < end);                 // event loop আটকে আছে
log('হিসাব শেষ');
# sig.sh

sleep 0.5; echo "  500 ms  shell: kill -TERM $pid"; kill -TERM $pid

  • --- SIGTERM ---: kernel ব্যস্ত loop-টাকে মাঝপথে থামিয়ে handler-এ পাঠাল। এটা JS handler না; libuv (Node-এর event loop library) শুরুতেই C-তে লেখা একটা ছোট handler বসিয়ে রেখেছিল, সেটা।
  • read(4)/write(5) "*": একটা ছোট pipe-কে lock হিসেবে নেওয়া আর ছাড়া।
  • write(15, ..., 16): আসল কাজ। Event loop-এর জন্য একটা pipe-এ ১৬ byte-এর একটা চিরকুট লেখা। \17 octal-এ ১৫, মানে SIGTERM-এর নম্বর।
  • rt_sigreturn: C handler শেষ, thread ফিরে গেল loop-এর ঠিক সেই জায়গায়।
  • তারপর ২.৩৩ সেকেন্ড কিছুই না। Loop চলছে, কেউ চিরকুট পড়ছে না।
  • Loop শেষ হলে event loop জাগে, read(14, ...) দিয়ে চিরকুট পড়ে (সেই একই ১৬ byte), আর তবেই তোমার JS handler চলে।

sigtrap.js-এর সময়রেখা, strace-এর মাপা সংখ্যায়। Kernel signal পৌঁছে দিয়েছে সাথে সাথেই, আর libuv-এর C handler এক millisecond-এরও কম সময়ে শুধু একটা চিরকুট লিখে ফিরে গেছে। JS handler-কে অপেক্ষা করতে হয়েছে main thread খালি হওয়া পর্যন্ত।

কেন এই ঘুরপথ? Signal handler যেকোনো instruction-এর মাঝে চলে আসতে পারে, এমনকি V8 যখন নিজের memory অর্ধেক গোছানো অবস্থায় রেখেছে তখনও। সেই মুহূর্তে JS চালানো নিরাপদ না। তাই C handler শুধু চিরকুট রাখে, আর JS চলে পরে, নিরাপদ মুহূর্তে। এর দাম হলো: event loop আটকে থাকলে তোমার SIGTERM handler-ও আটকে থাকে।

COMMON MISCONCEPTION

"process.on('SIGTERM', ...) লিখে দিয়েছি, graceful shutdown নিশ্চিত।" না, দুটো ফাঁক থাকে। এক: handler JS-এ, তাই event loop ফাঁকা না হলে সেটা চলে না। Kubernetes SIGTERM পাঠিয়ে grace period-এর (default ৩০ সেকেন্ড, Chapter 30) জন্য অপেক্ষা করে; তার মধ্যে loop মুক্ত না হলে আসে SIGKILL, exit 137, cleanup ছাড়াই। দুই: handler বসালে default মৃত্যু বাতিল হয়। Handler যদি শেষে process.exit না করে, বা এমন কিছুর অপেক্ষায় থাকে যেটা কখনো শেষ হয় না, process ঝুলে থাকে। এর সমাধান হলো ভারী sync কাজ worker-এ পাঠানো (Chapter 19), আর handler-এর ভেতরে নিজের একটা timeout রাখা।

Kernel কাউকে বিশ্বাস করে না

Syscall-এর প্রতিটা argument আসে user mode-এর code থেকে, আর সেই code buggy হতে পারে, এমনকি ইচ্ছে করে বিপজ্জনকও হতে পারে। read(fd, buffer, n) ধরো। এখানে buffer হলো একটা ঠিকানা (address): memory-র কোন ঘর থেকে data বসানো শুরু হবে তার নম্বর (Chapter 7)। Kernel mode-এ kernel সব memory ছুঁতে পারে। সে যদি যাচাই না করেই তোমার দেওয়া ঠিকানায় লিখে দিত, তাহলে read() দিয়ে একটা file-এর data kernel-এর নিজের memory-র উপর লেখানো যেত। তখন যেকোনো user পুরো machine দখল করতে পারত।

তাই kernel প্রতিটা argument যাচাই করে। Fd-টা কি বৈধ, আর এই process-এর? Permission আছে? ঠিকানাটা কি user-এর ভাগের memory-র মধ্যে পড়ে, আর সেখানে কিছু map করা আছে? User memory-তে লিখতে kernel বিশেষ copy function ব্যবহার করে (Linux-এ copy_to_user)। এই function আগে ঠিকানার সীমা দেখে, আর মাঝপথে fault হলেও crash করে না, error ফেরত দেয়।

JS থেকে এটা পরীক্ষা করা যায় না: Node-এর Buffer ঠিকানা লুকিয়ে রাখে, ভুল ঠিকানা দেওয়ার কোনো উপায়ই নেই। Python-এর ctypes দিয়ে পারা যায়। এটা C library-র read() সরাসরি ডাকতে দেয়, আর buffer-এর জায়গায় যেকোনো সংখ্যা বসাতে দেয়:

# badptr.py — kernel-কে আজেবাজে address দিলে কী হয়, আর নিজে ছুঁলে কী হয়
import ctypes, os
libc = ctypes.CDLL(None, use_errno=True)       # C library-র read() সরাসরি ডাকার উপায়
fd = os.open('badptr.py', os.O_RDONLY)

for name, addr in [('a real buffer', ctypes.addressof(ctypes.create_string_buffer(100))),
                   ('address 16', 16),
                   ('a kernel address', 0xffff800000001000)]:
    n = libc.read(fd, ctypes.c_void_p(addr), 100)
    err = os.strerror(ctypes.get_errno()) if n < 0 else 'ok'
    print(f'read() into {name:<16} -> {n:>4}  {err}')

print('এবার নিজেই address 16-এ লিখছি...', flush=True)
ctypes.memset(16, 0, 1)
print('এই লাইন কখনো print হবে না')

একই ঠিকানা ১৬, দুই রকম ফল। Kernel-কে দিলে সে যাচাই করে ভদ্রভাবে "Bad address" (EFAULT) ফেরত দিয়েছে, আর program চলতে থেকেছে। Kernel-এর ভাগের ঠিকানা দিলেও একই উত্তর: kernel তোমার হয়ে নিজের memory-তে লিখবে না। কিন্তু program নিজে ১৬-তে লিখতে গেলে CPU-র exception, তারপর SIGSEGV, exit ১৩৯। Linux-এ strace-এ kernel-এর উত্তর সরাসরি দেখা যায়: read(3, 0x10, 100) = -1 EFAULT (Bad address) আর read(3, 0xffff800000001000, 100) = -1 EFAULT (Bad address)। (0x10 হলো hex-এ ১৬।)

বাকি যাচাইগুলো Node থেকেই দেখা যায়। এবার একজন সাধারণ user হিসেবে চালাব (Node-এর Docker image-এ node নামে একটা user আছে, uid 1000):

root মানেও user mode

COMMON MISCONCEPTION

"sudo দিলে program kernel-এর ক্ষমতা পায়, kernel mode-এ চলে।" না। root মানে process-এর user id (uid) ০। এটা process-এর PCB-তে লেখা একটা সংখ্যা মাত্র, আর CPU-র mode এই সংখ্যার কথা জানেই না। root-এর process user mode-এই চলে, আর বাকি সবার মতোই syscall দিয়ে kernel-এর কাছে চায়। পার্থক্য শুধু একটা: kernel যখন যাচাই করে "এই process কি এটা করতে পারে?", তখন root বেশিরভাগ যাচাই পার হয়ে যায়। Privileged instruction root চালালেও একই exception, একই signal।

প্রমাণটা সহজ। Docker container-এ default user root, সেখানে spin.js চালাও:

docker run --rm -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash -c 'echo "uid: $(id -u)"; node spin.js'
uid: 0
pid 1: user 1938 ms, sys 8 ms, involuntary switches 27

root-এর loop-ও পুরোটাই user time, ঠিক আগের মতো। Kernel mode-এ code চলে শুধু ওই তিন দরজা দিয়ে ঢুকে, আর দরজার ওপাশে চলে kernel-এর নিজের code।

তবে "root সব যাচাই পার হয়" কথাটাও পুরো সত্যি না। পুরনো Unix-এ root ছিল all-or-nothing, আর তাতে একটা সমস্যা ছিল। যে web server-এর শুধু port 80 দরকার, root হতে গিয়ে সে kernel module load করার ক্ষমতাও পেয়ে যেত, আর তার একটা bug মানে পুরো machine হাতছাড়া। তাই Linux root-এর ক্ষমতাকে ৪১টা আলাদা টুকরোয় ভেঙেছে, নাম capabilities। যেমন CAP_NET_BIND_SERVICE (১০২৪-এর নিচের port), CAP_NET_ADMIN (network সাজানো), CAP_SYS_PTRACE (অন্যের process-এ ptrace লাগানো, strace যেটা ব্যবহার করে), CAP_SYS_ADMIN (hostname বদলানো সহ অনেক কিছু)। বেশিরভাগ কাজে kernel uid ০ দেখে না, দেখে নির্দিষ্ট capability-টা আছে কিনা। আর Docker container-এর root পায় মাত্র ১৪টা:

EXPERIMENT (Linux / Docker) — root.sh
# root.sh
apt-get update -qq && apt-get install -y -qq strace iproute2 > /dev/null
echo "uid: $(id -u)"                        # 0 মানে root
head -c 12 /etc/shadow; echo                # সাধারণ user পারে না, root পারে
hostname demo                               # machine-এর নাম বদলানো
ip link add dummy0 type dummy               # নতুন network interface বানানো
setpriv --reuid 1000 --regid 1000 --clear-groups sleep 5 &   # অন্য user-এর একটা process
sleep 0.2; timeout 1 strace -p $! 2>&1 | head -1             # তাতে strace লাগানো
docker run --rm -v "$PWD":/w:ro -w /w debian:bookworm-slim bash root.sh
docker run --rm --cap-add NET_ADMIN --cap-add SYS_PTRACE -v "$PWD":/w:ro -w /w debian:bookworm-slim bash root.sh

প্রথম container-এ uid ০, /etc/shadow-ও পড়া গেল। অথচ hostname বলছে "you must be root"! Tool-টা ধরে নিয়েছে যে "অনুমতি নেই" মানে "root না"। আসলে kernel EPERM দিয়েছে CAP_SYS_ADMIN না থাকায়। Network interface বানানো আর অন্য user-এর process-এ strace লাগানোও আটকে গেছে। দ্বিতীয় container-এ ঠিক দুটো capability যোগ করেছি, আর ঠিক ওই দুটো কাজই খুলে গেছে; hostname এখনো বন্ধ। একটা container-এর নিজের capability-র তালিকা দেখতে grep CapEff /proc/self/status চালাও। সেটা একটা hex সংখ্যা দেয়, আর capsh --decode=<সেই সংখ্যা> তাকে নামে বদলায়।

এবার বইয়ের একটা পুরনো ঋণ শোধ করি। Chapter 1 থেকে strace-এর আগে --cap-add SYS_PTRACE দিয়ে আসছি। strace ptrace নামের একটা syscall দিয়ে অন্য process-এর syscall দেখে। নতুন Docker-এ নিজের চালানো child-কে strace করতে এই flag আর লাগে না, কিন্তু পুরনো Docker-এ ptrace পুরোপুরি আটকানো থাকত। আর উপরে যেমন দেখলে, অন্য user-এর process-এ লাগাতে এখনো লাগে। তাই নিরাপদ থাকতে flag-টা সবসময় দিয়েছি। উল্টো দিকে --privileged দিলে container পায় ৪১টার সবগুলো, আর অনেক নিষেধও উঠে যায়। তখন container-এর root প্রায় host-এর root-এর সমান, তাই এটা হালকাভাবে দিও না।

JS developer-এর চেনা একটা উদাহরণ: আসল Linux server-এ সাধারণ user হিসেবে listen(80) করলে আসে EACCES। পুরো root না দিয়ে শুধু ওই একটা ক্ষমতা দেওয়া যায়:

node -e "require('net').createServer().listen(80).on('error', e => console.log(e.code))"
# EACCES
sudo setcap cap_net_bind_service=+ep "$(readlink -f "$(which node)")"
# এবার একই command চলে — root ছাড়াই

আমি এটা Docker-এ চালিয়ে দেখেছি: --sysctl net.ipv4.ip_unprivileged_port_start=1024 দিয়ে, node user হিসেবে। Flag-টা লাগে কারণ Docker নিজে container-এ এই সীমা ০ করে রাখে, তাই container-এ সাধারণত এই error দেখবে না। একটা সাবধানতা: এতে ওই node binary দিয়ে চলা সব script ক্ষমতাটা পায়। বাস্তবে সাধারণত app চলে ৩০০০-এর মতো port-এ, আর সামনে একটা reverse proxy বা load balancer ৮০ ধরে।

দুই পাহারাদার: CPU mode আর page table

এখন পর্যন্ত "পাহারা" বলতে একটা জিনিস বুঝিয়েছি, কিন্তু আসলে পাহারাদার দুইজন, আর তারা আলাদা জিনিস আগলায়। বুঝতে একটা জিনিস দরকার: প্রতিটা process-এর virtual address-এর নম্বর দুই ভাগে ভাগ করা। নিচের অর্ধেক user-এর: x86-64 Linux-এ 0x00007fff_ffffffff পর্যন্ত, ARM64-এ 0x0000ffff_ffffffff পর্যন্ত। উপরের অর্ধেক, 0xffff... দিয়ে শুরু হওয়া ঠিকানাগুলো, kernel-এর। Chapter 9-এর কথা মনে করো: প্রতিটা process-এর নিজের page table আছে, আর প্রতিটা memory access-এ MMU সেই table দেখে virtual ঠিকানাকে RAM-এর frame-এ বদলায়।

# guards.py — নিজের memory পড়া যায়; kernel-এর ভাগের address না
import ctypes
mine = ctypes.create_string_buffer(b'hello')          # আমার process-এর ৬ byte
addr = ctypes.addressof(mine)
print(f'{addr:#018x}  (user half)   ->', ctypes.string_at(addr, 5))

kernel = 0xffff800000001000                          # 64-bit ঠিকানার উপরের অর্ধেক
print(f'{kernel:#018x}  (kernel half) -> ...', flush=True)
ctypes.string_at(kernel, 1)
print('এই লাইন আসবে না')
docker run --rm -v "$PWD":/w:ro -w /w python:3.12-slim bash -c 'python3 guards.py; echo "exit $?"'
0x0000ffff98bf0320  (user half)   -> b'hello'
0xffff800000001000  (kernel half) -> ...
exit 139
bash: line 1:     7 Segmentation fault      python3 guards.py

নিজের ঠিকানা (নিচের অর্ধেকে) থেকে পড়া গেল। উপরের অর্ধেকে হাত দিতেই exception, তারপর SIGSEGV। (Mac-এও একই ফল, শুধু নিজের ঠিকানাটা 0x0000000104ca5598-এর মতো।) এবার দুই পাহারাদারকে আলাদা করে দেখো:

  • পাহারাদার ১ — CPU mode। এটা আটকায় privileged instruction (page table বদলানো, interrupt বন্ধ করা, device-এর register ছোঁয়া)। আর page table-এর যে entry-তে "kernel-only" চিহ্ন দেওয়া, user mode-এ সেটা ছোঁয়াও আটকায়। প্রতিটা access-এ MMU চিহ্নটা মিলিয়ে দেখে CPU এখন কোন mode-এ। guards.py-র SIGSEGV এই পাহারাদারের কাজ।
  • পাহারাদার ২ — page table। এটা ঠিক করে কোন RAM-এ পৌঁছানো আদৌ সম্ভব। Process B-র frame-গুলো A-র page table-এ নেই-ই। A যে ঠিকানাই বলুক, সেটা A-র নিজের table দিয়ে অনুবাদ হয়, তাই B-র data-র নাম নেওয়ারও উপায় নেই (Chapter 9-এর same-address demo)। এখানে mode কোনো কাজ করে না, শুধু table।

একটা প্রশ্ন থেকে যায়: kernel-এর অর্ধেক প্রতিটা process-এর page table-এ আছেই বা কেন? কারণ গতি। Syscall বা interrupt এলে CPU সোজা kernel-এর code-এ নামতে পারে, page table বদলাতে হয় না, কারণ kernel তো আগে থেকেই map করা। একে পাহারা দেয় শুধু ওই "kernel-only" চিহ্ন। এই কথাটা মনে রাখো, পরের section ঠিক এখানেই আঘাত করে।

দুই পাহারাদার, দুই আলাদা কাজ। Kernel-এর অর্ধেক (উপরে, amber) সব process-এর table-এ একই, শুধু "kernel-only" চিহ্ন দেওয়া; user mode-এ ছুঁলে CPU mode-এর পাহারাদার ধরে ফেলে। B-র memory A-র table-এ নেই-ই, তাই সেখানে পৌঁছানোর কোনো পথই নেই।

Meltdown: পাহারাদার যখন দেরিতে জাগল

দুটো পুরনো কথা এখানে লাগবে। Chapter 14: CPU অপেক্ষা না করে আন্দাজে সামনের instruction আগেই চালিয়ে ফেলে (speculative execution)। আন্দাজ ভুল হলে ফলগুলো ফেলে দেয়, কিন্তু cache-এ কী এল সেই চিহ্ন থেকে যায়। Chapter 13: cache-এ থাকা data পড়া আর RAM থেকে আনার মধ্যে সময়ের পার্থক্য এত বড় যে সেটা মাপা যায়। ২০১৮-র জানুয়ারিতে প্রকাশিত Meltdown এই দুটো জোড়া দিয়ে পাহারাদার ১-কে ফাঁকি দিয়েছিল। মূলত সেই সময়ের Intel CPU-তে এটা কাজ করত। কৌশলটা মোটা দাগে এরকম (code না, শুধু ধারণা):

  1. User mode-এর code kernel-এর অর্ধেক থেকে একটা byte পড়তে বলে। "Kernel-only" যাচাই ব্যর্থ হবে, exception আসবেই। কিন্তু আক্রান্ত CPU-তে byte-টা আগে চলে আসে, আর exception ঘোষণা হওয়ার আগেই পরের instruction-গুলো আন্দাজে চলে যায়।
  2. পরের instruction সেই byte-কে সূচক ধরে ২৫৬ ঘরের একটা বড় array-র একটা ঘর ছোঁয়। Byte-এর মান ৯৭ হলে ৯৭ নম্বর ঘর, আর সেই ঘর cache-এ চলে আসে।
  3. Exception আসে, CPU সব register-এর ফল ফেলে দেয়। Byte-টা আর কোথাও নেই, কিন্তু ৯৭ নম্বর ঘর cache-এ রয়ে গেছে।
  4. Program ২৫৬টা ঘরই পড়ে দেখে, কোনটা কত দ্রুত আসে। যেটা দ্রুত আসে (cache hit), সেটাই গোপন byte। তারপর পরের byte।

এটা ভয়াবহ ছিল, কারণ Linux kernel-এর অর্ধেকে গোটা physical RAM map করা থাকে। ফলে kernel memory পড়া মানে সব process-এর সব data পড়া: অন্যের password, key, সবকিছু। একটা hardware বাগ দুই পাহারাদারকেই এক সাথে ডিঙিয়ে গেল।

Hardware রাতারাতি বদলানো যায় না, তাই সমাধান এল software-এ: KPTI (Kernel Page-Table Isolation)। প্রতিটা process-এর জন্য এখন দুটো page table। User mode-এ যেটা চলে, তাতে kernel-এর অর্ধেক প্রায় পুরোটাই সরানো; আছে শুধু দরজার ছোট একটা entry stub, যেটা table বদলানোর কাজটা করে। কোনো দরজা দিয়ে ঢুকলেই (syscall, interrupt, exception) সেই stub পুরো table-এ বদলে নেয়, আর বেরোনোর সময় আবার ফেরত যায়। User mode-এ kernel memory map করাই না থাকলে আন্দাজে পড়ারও কিছু থাকে না।

তবে এর দাম আছে। প্রতিটা দরজা পেরোতে দুইবার table বদল। আর table বদলালে TLB-র (ঠিকানা অনুবাদের ছোট cache, Chapter 9) জমানো অনুবাদও কাজে লাগে না, যদি না CPU-তে PCID থাকে। PCID হলো TLB-র entry-তে কোন table-এর সেটা লিখে রাখার ব্যবস্থা। ২০১৮-তে যেসব কাজ অনেক syscall করে (ছোট ছোট database query, অনেক ছোট network write), সেগুলো চোখে পড়ার মতো ধীর হয়েছিল। একটা syscall-এর দাম আসলে কত, সেটা পরের chapter-এ মাপব।

বাঁয়ে পুরনো ব্যবস্থা: একটা table, kernel-এর অর্ধেক সবসময় map করা, পাহারা শুধু "kernel-only" চিহ্ন, আর Meltdown সেটাই আন্দাজে পড়েছিল। ডানে KPTI: user mode-এর table-এ kernel প্রায় নেই, আর kernel-এ ঢোকার সময় পুরো table-এ বদল হয়। নিরাপত্তা বাড়ল, প্রতিটা দরজা একটু দামি হলো।

তোমার machine-এর CPU আক্রান্ত কিনা, আর kernel কী ব্যবস্থা নিয়েছে, Linux সেটা একটা file-এ লিখে রাখে:

docker run --rm alpine sh -c 'cd /sys/devices/system/cpu/vulnerabilities; grep . meltdown spectre_v1 spectre_v2'
meltdown:Not affected
spectre_v1:Mitigation: __user pointer sanitization
spectre_v2:Not affected

Apple Silicon-এর উপর চলা এই VM-এর CPU-কে kernel Meltdown-এ আক্রান্ত মনে করে না, তাই KPTI বন্ধ রেখেছে। আক্রান্ত Intel server-এ লেখা থাকত Mitigation: PTI। দ্বিতীয় লাইনটা দেখো: __user pointer sanitization। Kernel শুধু তোমার দেওয়া ঠিকানা যাচাই করেই থামে না; যাচাই শেষ হওয়ার আগে CPU যেন আন্দাজেও সেই ঠিকানা ব্যবহার করতে না পারে, সেটাও নিশ্চিত করে। "Kernel কাউকে বিশ্বাস করে না" কথাটা এই পর্যন্ত যায়।

MENTAL MODEL

User mode থেকে kernel mode-এ ঢোকার দরজা তিনটা: syscall (program চায়), interrupt (hardware ডাকে, যেকোনো মুহূর্তে), exception (instruction আটকে যায়)। তিনটাই নামে boot-এ ঠিক করা entry point-এ, অন্য কোথাও না। ফেরার পথে kernel signal গুঁজে দিতে পারে। Handler না থাকলে kernel নিজেই default কাজ করে; SIGKILL-এ কোনো বিকল্প নেই। Kernel প্রতিটা argument যাচাই করে, আর ভুল হলে crash না করে error ফেরত দেয়। root শুধু kernel-এর permission যাচাইয়ে সুবিধা পায়, আর সেটাও capability ধরে ধরে; CPU mode বদলায় না। Memory আগলায় দুই পাহারাদার: CPU mode (privileged instruction আর kernel-only page) আর page table (কোন memory আদৌ আছে)। Meltdown দেখিয়েছে hardware-এর পাহারাও ফাঁকি খেতে পারে। KPTI সেটার দাম: প্রতিটা দরজা পেরোনো একটু বেশি খরচের।

CAN I EXPLAIN THIS?
  • twospin.sh-এ দুটো process প্রায় কোনো syscall না করেও প্রত্যেকে ~৫৪০ বার CPU হারাল। Kernel কোন দরজা দিয়ে ঢুকল? ৩.৯ সেকেন্ডে CPU0-তে ৩৮৮৭টা timer interrupt থেকে এই kernel-এর tick সম্পর্কে কী বোঝা যায়?
  • fault.js-এ ১০০ MB ছুঁতে ৬৪১২টা exception হলো, program টেরই পেল না। অথচ --stack-size=50000-এ exception-এর পরে program মরল (exit ১৩৯)। দুই ক্ষেত্রে kernel-এর সিদ্ধান্ত আলাদা হলো কেন?
  • sigtrap.js-এ kernel SIGTERM পৌঁছে দিয়েছে প্রায় সাথে সাথে, অথচ JS handler চলেছে ৩ সেকেন্ডে। মাঝের সময়টা signal কোথায় ছিল, আর Node কেন JS handler সরাসরি signal-এর মুহূর্তে চালায় না? Kubernetes-এ এর পরিণতি কী হতে পারে?
  • badptr.py-তে ঠিকানা ১৬ kernel-কে দিলে EFAULT, কিন্তু নিজে লিখলে SIGSEGV। পার্থক্য কেন? Kernel এই যাচাই না করলে read() দিয়ে কী করা যেত?
  • Container-এর root /etc/shadow পড়তে পারল কিন্তু hostname বদলাতে পারল না কেন? guards.py-র kernel-half read কোন পাহারাদার আটকাল? Meltdown সেই পাহারাদারকে কীভাবে ফাঁকি দিয়েছিল, আর KPTI তার জন্য কী দাম নিল?
