উপসংহার

The Operating Systems Mental Model

পুরো বই এক ছবিতে: তোমার JS থেকে silicon পর্যন্ত প্রতিটা স্তর, আর কোন chapter কোন স্তরের কথা বলে। তারপর পাঁচটা সুতো, যেগুলো চল্লিশটা chapter-কে একসাথে বেঁধে রাখে।

প্রতিটা chapter একটা জায়গায় zoom করেছে। এই পাতায় zoom-out: সব জায়গা একসাথে, কে কার উপর দাঁড়িয়ে, আর কোথায় সীমানা। কোনো স্তর ঝাপসা লাগলে পাশে লেখা chapter-এ ফিরে যাও।

পুরো stack, ওপর থেকে নিচে। নীল অংশ একটা process-এর ভেতরে, user mode-এ। Amber রেখা সেই সীমানা যেটা শুধু syscall, exception আর interrupt দিয়ে পার হওয়া যায়, আর signal উল্টো দিকে আসে। তার নিচে kernel-এর পাঁচ বিভাগ, আর সবার নিচে hardware। ডানে প্রতিটা স্তরের chapter।

পাঁচটা সুতো

  • সব রাস্তার একই আকার। File পড়া, socket-এ লেখা, একটা page প্রথমবার ছোঁয়া: প্রতিবার তোমার code একটা কিছু চায়, সীমানা পার হয় (syscall বা exception), kernel তার কোনো বিভাগে কাজটা এগোয়, দরকার হলে hardware-কে বলে, আর উত্তর নিয়ে user mode-এ ফেরে। Device-এর কাজ শেষ হলে interrupt এসে kernel-কে জানায়, আর kernel ঘুমন্ত thread-কে জাগায়। চরিত্র আলাদা, গল্প একটাই (Chapter 2, 21, 27, 31)। Chapter 37 আর 38 এই গল্প সত্যি সত্যি trace করে দেখিয়েছে।
  • প্রতিটা স্তর একটা মায়া দেয়, আর প্রতিটা মায়ার একটা দাম। Virtual memory বলে "পুরো memory তোমার একার", scheduler বলে "CPU তোমার একার", fd বলে "সবকিছু একটা file", TCP বলে "byte হারায় না, ক্রম বদলায় না", namespace বলে "machine-টা তোমার একার", hypervisor বলে "hardware তোমার একার"। এই মায়াগুলোর জন্যই আমরা সরল code লিখতে পারি। কিন্তু মায়া কোথাও না কোথাও ফাটে, আর সেখানেই performance-এর রহস্য লুকায়: প্রথম ছোঁয়ায় page fault, context switch-এর পরে ঠান্ডা cache, Nagle-এর ৪২ ms, os.cpus()-এর ১২ যখন cgroup দিয়েছে আধখানা CPU।
  • যেখানে গতির ফাঁক, সেখানে cache বা buffer। CPU আর RAM-এর মাঝে cache (Chapter 13), অনুবাদের জন্য TLB (Chapter 9), disk আর RAM-এর মাঝে page cache (Chapter 23), app আর network-এর মাঝে socket buffer (Chapter 27), আর তোমার নিজের application cache। একই কৌশলের পাঁচ তলা। প্রতিটার একই দুই প্রশ্ন: hit না হলে কত দাম, আর cache-এর copy আর আসলটা আলাদা হয়ে গেলে কী হয় (dirty page, false sharing, backpressure)।
  • বেশিরভাগ সময় যায় অপেক্ষায়। Chapter 38-এর server-এ তোমার JS ৮ ms-এর মধ্যে ০.২৪ ms; বাকিটা DB, kernel আর network। Chapter 37-এ এক লাইনের program ১৩ ms নিল, তোমার লাইন ২ ms-এর কম। অপেক্ষা CPU% দেখে ধরা যায় না, কিন্তু kernel প্রতিটা process-এর সময়ের পুরো হিসাব রাখে। সেই হিসাব (time, strace, vmstat, event loop delay) পড়তে পারাই এই বইয়ের সবচেয়ে কাজের দক্ষতা (Chapter 39)।
  • শেষ পর্যন্ত লাইন আর serial অংশই সীমা ঠিক করে। Resource-এর গতি না, তার সামনের লাইন latency ঠিক করে, আর utilization ১০০%-এর কাছে গেলে লাইন লাফিয়ে বাড়ে। যে অংশ ভাগ করা যায় না (একটা lock, একটা event loop, একটা DB row), core যতই বাড়াও সেটাই সিলিং (Chapter 18, 40)।

চলন্ত একটা program-এর দিকে তাকালে

বইয়ের শুরুতে লক্ষ্য ছিল একটা চোখ তৈরি করা। এখন node server.js-এর মতো একটা চলন্ত program-এর দিকে তাকালে তোমার দেখতে পাওয়া উচিত:

  • একটা process আর তার address space। সেখানে map করা আছে node binary-র ৯৯ MB, যার ৩০ MB আসলে RAM-এ, আর V8-এর heap-এ object জন্মাচ্ছে আর GC-তে মরছে।
  • সাতটা thread, আর file বা crypto-র কাজ হলে libuv-এর আরও চারটা। এর মধ্যে একটা তোমার JS চালায়, বাকিরা বেশিরভাগ সময় futex বা epoll-এ ঘুমিয়ে থাকে।
  • কয়েক ডজন fd: listening socket, প্রতিটা client-এর socket, DB-র connection, log file।
  • প্রতিটা request-এ কয়েকটা syscall, একেকটা একশো ns-এর ঘরে, আর তাদের ফাঁকে ফাঁকে CPU-র cache-এ hit আর miss।
  • Kernel-এর ভেতরে প্রতিটা connection-এর buffer আর queue, page cache-এ গরম file, আর disk-এ যাওয়ার অপেক্ষায় dirty page।
  • Scheduler, যে প্রতি millisecond-এ ঠিক করছে কে CPU পাবে, আর container হলে cgroup-এর কোটা, যেটা চুপচাপ তোমার request-কে থামিয়ে রাখতে পারে।

এগুলো যদি চোখে ভাসে, আর কোনটা ঝাপসা সেটা যদি জানো এবং মেপে দেখতে পারো, তাহলে বইটা কাজ করেছে। শেষ পাতায় প্রশ্নগুলো দিয়ে নিজেকে যাচাই করে নাও।
