PART 6 · STORAGE

Chapter 23 — Page Cache

Kernel কেন file-এর data RAM-এ ধরে রাখে, কতটা রাখে, dirty data কতক্ষণ RAM-এ বসে থাকে, কখন ছাড়ে — আর memory-সীমার container-এ এই cache কীভাবে তোমার process-কে OOMKilled করাতে পারে।

বইয়ে page cache নামটা বারবার এসেছে: Chapter 2-এ read-এর পথে, Chapter 7-এ free-এর "buff/cache" column-এ, Chapter 10-এ mmap-এর পেছনে, Chapter 21-এ স্তরের মাঝখানে। এক লাইনে: page cache হলো RAM-এর যে অংশে kernel file-এর data page ধরে ধরে (Chapter 9-এর page, 4 KB বা 16 KB) রেখে দেয়। এই chapter-এ দেখব এটা কী সমস্যা মেটায়, কীভাবে ভরে আর খালি হয়, আর কোথায় কামড় দেয়।

সমস্যা: disk ধীর, RAM অলস

Chapter 20-এর মাপ মনে করো: একটা random 4 KB read SSD থেকে ~৭৯ µs, আর RAM থেকে একটা cache line ~০.১২ µs। অথচ বাস্তবে একই file বারবার পড়া হয় — config, template, database-এর গরম অংশ, node_modules-এর file। আবার RAM-এর যে অংশ কোনো process নিচ্ছে না, সেটা ফাঁকা পড়ে থাকলে কারও কোনো লাভ নেই। Kernel-এর সমাধান: disk থেকে যা-ই পড়া বা লেখা হোক, সেটা RAM-এ রেখে দাও; পরে কেউ চাইলে disk-এ না গিয়ে এখান থেকে দাও; আর process-দের RAM লাগলে এই জায়গা ছেড়ে দাও।

Cache-টা কোনো process-এর না — kernel-এর। তাই এক process-এর পড়া অন্য process-এর কাজে লাগে। নিচের পরীক্ষায় প্রতিটা node আলাদা process (pid আলাদা দেখবে)। প্রথমে Chapter 20-এর কৌশলে (F_NOCACHE) একটা 1 GB file বানাব যেটা RAM-এ নেই:

EXPERIMENT (macOS) — ঠান্ডা আর গরম
# mkcold.py — 1 GB file লেখো, কিন্তু page cache-এ রেখো না (macOS F_NOCACHE)
import os, fcntl
fd = os.open('cold.bin', os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
fcntl.fcntl(fd, fcntl.F_NOCACHE, 1)
chunk = os.urandom(8 * 1024**2)
for _ in range(128):
    os.write(fd, chunk)
os.fsync(fd); os.close(fd)
// readall.js — পুরো file 1 MB করে পড়ো, সময় মাপো
const fs = require('fs');
const fd = fs.openSync(process.argv[2]);
const buf = Buffer.alloc(1024 * 1024);
const t = performance.now();
let total = 0, n;
while ((n = fs.readSync(fd, buf)) > 0) total += n;
const ms = performance.now() - t;
console.log(`pid ${process.pid}: ${total / 2 ** 20} MB in ${ms.toFixed(0)} ms (${(total / ms / 1e6).toFixed(1)} GB/s)`);
// randread.js — 20,000টা random 4 KB read, একটার পর একটা
const fs = require('fs');
const fd = fs.openSync(process.argv[2]);
const blocks = fs.fstatSync(fd).size / 4096;
const buf = Buffer.alloc(4096);
const t = performance.now();
for (let i = 0; i < 20000; i++)
  fs.readSync(fd, buf, 0, 4096, Math.floor(Math.random() * blocks) * 4096);
console.log(`${((performance.now() - t) * 1000 / 20000).toFixed(1)} µs per random 4 KB read`);

পুরো file একটানা পড়ায় ঠান্ডা (disk থেকে) ১৮২ ms, গরম (page cache থেকে) ৪৯ ms — প্রায় চার গুণ, আর দ্বিতীয়টা সম্পূর্ণ আলাদা একটা process। একটানা পড়ায় পার্থক্য কম, কারণ SSD বড় sequential read-এ খুব দ্রুত (Chapter 20)। আসল নাটক random read-এ: ঠান্ডা অবস্থায় প্রতিটা ~৭৬ µs, file-টা একবার পুরো পড়ে cache গরম করার পরে ~০.৯ µs — প্রায় পঁচাশি গুণ। ০.৯ µs-এর মধ্যেও disk নেই: শুধু system call আর page cache থেকে তোমার buffer-এ 4 KB copy।

এর দুইটা বাস্তব ফল। Benchmark-এ প্রথম run আর পরের run আলাদা জিনিস মাপে — "cold" আর "warm" আলাদা করে বলতে হয়, নইলে ভুল সিদ্ধান্ত। আর server restart বা নতুন machine-এ deploy-এর পর প্রথম কয়েক মিনিট সব ধীর লাগে, যতক্ষণ না cache আবার ভরে।

Page cache kernel-এর, কোনো process-এর না: A-র প্রথম read miss করে SSD থেকে page আনে, B একই page পরে পায় RAM থেকে। Write-এর page dirty (লাল) থাকে যতক্ষণ না writeback সেটা disk-এ নামায়। RAM লাগলে সবুজ (clean) page বিনা খরচে ফেলে দেওয়া যায়; লাল page আগে disk-এ লিখতে হয়।

কতটা রাখে: fincore আর read-ahead

Linux-এ একটা file-এর কতটা এই মুহূর্তে page cache-এ, সেটা fincore বলে দেয়। আর GNU dd-এর iflag=nocache দিয়ে একটা নির্দিষ্ট file-এর cache ফেলে দেওয়া যায় — root বা বিশেষ permission ছাড়াই। এবার পরপর একটু একটু পড়ে দেখি kernel কতটা তুলে আনে:

EXPERIMENT (Linux / Docker) — read-ahead
docker run --rm debian:bookworm-slim bash -c '
  cd /root; dd if=/dev/urandom of=big.bin bs=1M count=1024 status=none
  cat /sys/block/vda/queue/read_ahead_kb
  for n in 1 8 64 256; do
    dd if=big.bin iflag=nocache count=0 status=none        # এই file-এর cache ফেলে দাও
    dd if=big.bin of=/dev/null bs=4k count=$n status=none  # শুরু থেকে n × 4 KB পড়ো
    echo "read $n x 4K:"; fincore -n -o RES big.bin
  done'

৪ KB পড়তে চাইলে cache-এ এসেছে ১৬ KB; ৩২ KB পড়লে ১১২ KB; ১ MB পড়লে ১.২ MB। Kernel দেখছে তুমি পরপর পড়ছ, তাই যা চেয়েছ তার চেয়ে আগেভাগে কিছুটা বেশি এনে রাখছে — এর নাম read-ahead, আর পরপর পড়া যত চলে, আগাম আনার মাপ তত বাড়ে (এই disk-এর জন্য এক ধাপে সর্বোচ্চ read_ahead_kb = ১২৮ KB)। Chapter 8-এর CPU prefetcher-এর একই বুদ্ধি, এক স্তর নিচে: পরের অনুরোধ আসার আগেই data হাজির, আর ছোট ছোট অনুরোধ disk-এ বড় অনুরোধ হয়ে যায় (Chapter 20)। Random read-এ এটা উল্টো ক্ষতি করতে পারে — অকারণে বেশি আনা — তাই database-রা মাঝে মাঝে kernel-কে বলে দেয় "এই file-এ read-ahead কোরো না"।

Dirty page আর writeback: কতক্ষণ RAM-এ বসে থাকে

Chapter 21-এ দেখেছি write() শুধু page cache-এ লিখে page-কে dirty দাগায়। কিন্তু "পরে disk-এ যাবে" — পরে মানে কখন? Kernel-এর কয়েকটা setting এটা ঠিক করে, /proc/sys/vm/-এ পড়া যায়। এবার 500 MB লিখে /proc/meminfo-এর Dirty লাইনটা ২ সেকেন্ড পরপর দেখব:

EXPERIMENT (Linux / Docker) — dirty data-র আয়ু
docker run --rm debian:bookworm-slim bash -c '
  for f in dirty_background_ratio dirty_ratio dirty_expire_centisecs dirty_writeback_centisecs; do
    echo "$f = $(cat /proc/sys/vm/$f)"; done
  sync; cd /root
  dd if=/dev/zero of=w.bin bs=1M count=500 status=none      # sync ছাড়া 500 MB
  s=$(date +%s)
  for i in $(seq 0 20); do
    printf "%3ss " $(( $(date +%s) - s )); grep "^Dirty:" /proc/meminfo; sleep 2
  done'
dirty_background_ratio = 10
dirty_ratio = 20
dirty_expire_centisecs = 3000
dirty_writeback_centisecs = 1500

write() ফিরে আসার পর ৩০ সেকেন্ড ধরে প্রায় পুরো 500 MB শুধু RAM-এ। ১৬ সেকেন্ডে একটা ছোট অংশ (~৫০ MB) নামে; ৩০ সেকেন্ড পেরোনোর পরের পালায় (৩২ s) বাকি সব। এই পুরো সময়টা power বা VM মরলে data নেই। বিন্দুতে hover করলে মান।

Setting গুলোর মানে:

  • dirty_expire_centisecs = ৩০০০ (শতভাগের এক সেকেন্ড এককে, মানে ৩০ s): এর চেয়ে পুরনো dirty page পরের পালায় disk-এ যাবে। Chart-এ ঠিক এটাই দেখা গেল।
  • dirty_writeback_centisecs = ১৫০০ (১৫ s): kernel-এর writeback thread কতক্ষণ পরপর জেগে দেখে। (এই VM-এ ১৫ s; অনেক distro-তে ৫ s।)
  • dirty_background_ratio = ১০%: dirty data ব্যবহারযোগ্য memory-র এই অংশ ছাড়ালে বয়স না দেখেই background-এ লেখা শুরু। এই VM-এ ~৭.৩ GB available, তাই ~৭০০ MB — আলাদা করে 1000 MB আর 3000 MB লিখে দেখেছি, Dirty দুইবারই ~৭০০ MB-এর কাছে থেমেছে (৭,০৪,৫১২ আর ৭,২০,৮৯৬ kB)।
  • dirty_ratio = ২০%: এর বেশি dirty হলে kernel লেখক process-কেই write()-এর ভেতরে থামিয়ে রাখে, যতক্ষণ না writeback কিছুটা ধরে ফেলে। "write তো RAM-এ যায়, তাই সবসময় দ্রুত" — এই সীমায় এসে সেটা আর সত্যি থাকে না; বড় file লেখার মাঝপথে হঠাৎ ধীর হয়ে যাওয়ার কারণ এটাই।

অপেক্ষা না করে এখনই নামাতে চাইলে: পুরো machine-এর জন্য sync command, একটা file-এর জন্য fsync (Chapter 21)। এই VM-এ 500 MB dirty থাকা অবস্থায় time sync নিয়েছিল real 0m0.882s, তারপর Dirty: 4 kB।

Cache কখন ছাড়ে

Page cache যতটা পারে RAM ভরে রাখে — Chapter 7-এ free-এর "available" column-এ দেখেছ, cache সেখানে "ব্যবহারযোগ্য" হিসেবেই গোনা হয়। কোনো process-এর memory লাগলে kernel cache থেকে জায়গা ফেরত নেয় (eviction)। কোনটা আগে যাবে? Kernel সব page-এর উপর নজর রাখে না, মোটামুটি হিসাব রাখে: file page গুলো দুই তালিকায় — সম্প্রতি একাধিকবার ছোঁয়া (active) আর বাকি (inactive)। ফেলার সময় আগে inactive তালিকার পুরনোগুলো।

grep -E "^(Active|Inactive)\(file\)" /proc/meminfo   # Linux

আর ফেলার দাম page-এর অবস্থার উপর নির্ভর করে। Clean page-এর হুবহু কপি disk-এ আছে — ফেলে দেওয়া মানে শুধু হিসাব থেকে মোছা, প্রায় বিনা খরচে। Dirty page ফেলা যায় না; আগে disk-এ লিখতে হয়, আর সেটা ধীর। এই পার্থক্যটাই পরের অংশের পুরো গল্প।

Container-এর হিসাবে page cache

Docker-এর --memory (বা Kubernetes-এর memory limit) একটা cgroup-এর সীমা বসায় — kernel-এর একটা হিসাবের খাতা, যেখানে একদল process-এর memory একসাথে গোনা হয় (বিস্তারিত Chapter 36)। মজার কথা: সেই খাতায় process-এর নিজের memory (anon — heap, stack) ছাড়াও ওই process-দের পড়া-লেখা file-এর page cache-ও (file) গোনা হয়। 256 MB সীমার একটা container-এ আগে 600 MB পড়ব, তারপর লিখব:

EXPERIMENT (Linux / Docker) — ২৫৬ MB-এর খাঁচায় ৬০০ MB
docker volume create c23vol
# ১) 600 MB file বানাও (সীমাহীন container-এ), তারপর তার cache ফেলে দাও
docker run --rm -v c23vol:/data debian:bookworm-slim sh -c '
  dd if=/dev/urandom of=/data/big.bin bs=1M count=600 status=none; sync
  dd if=/data/big.bin iflag=nocache count=0 status=none'
# ২) 256 MB সীমার container-এ পুরোটা পড়ো
docker run --rm --memory 256m -v c23vol:/data debian:bookworm-slim bash -c '
  cat /data/big.bin > /dev/null
  echo current=$(( $(cat /sys/fs/cgroup/memory.current)/1048576 )) MB
  grep -E "^(anon|file) " /sys/fs/cgroup/memory.stat'
current=255 MB

এবার লেখা। bigwrite.js 600 MB লেখে; sync argument দিলে প্রতি 32 MB পরপর fdatasync (fsync-এর ছোট ভাই: data নামায়, দরকার না হলে metadata না — Chapter 24):

// bigwrite.js — 600 MB লেখো; "sync" দিলে প্রতি 32 MB পরপর fdatasync
const fs = require('fs');
const every = process.argv[2] === 'sync' ? 32 : Infinity;
const fd = fs.openSync('/data/new.bin', 'w');
const chunk = Buffer.alloc(1024 * 1024);
for (let mb = 1; mb <= 600; mb++) {
  fs.writeSync(fd, chunk);
  if (mb % every === 0) fs.fdatasyncSync(fd);   // dirty page গুলো এখনই disk-এ
}
fs.closeSync(fd);
console.log('done');
for m in plain sync; do
  docker run --name writer --memory 256m -v c23vol:/data -v "$PWD":/w:ro \
    node:22-bookworm-slim node /w/bigwrite.js $m
  echo "$m → $(docker inspect -f '{{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' writer)"
  docker rm writer
done
docker volume rm c23vol
plain → 137 OOMKilled=true
done
sync → 0 OOMKilled=false

পড়ার বেলায় container ঠিক তার সীমায় (২৫৫ MB) বসে আছে, যার প্রায় পুরোটাই (file ≈ ২৫৩ MB) page cache, আর process-এর নিজের memory (anon) মাত্র ১৩২ KB। কিন্তু কোনো সমস্যা হয়নি: সীমায় পৌঁছাতেই kernel পুরনো clean page ফেলে নতুনদের জায়গা দিয়েছে। লেখার বেলায় ঠিক উল্টো: Node process-এর নিজের memory সামান্য, তবু container OOMKilled (Chapter 10-এর সেই exit 137)। কারণ dirty page ফেলা যায় না, আর সেগুলো জমছিল container-এর খাতাতেই — writeback লেখকের সাথে তাল রাখতে পারেনি, খাতা সীমা ছাড়িয়েছে। প্রতি ৩২ MB পরপর fdatasync দিয়ে dirty data নিজে নামিয়ে দিতেই একই কাজ নির্বিঘ্নে শেষ। (Linux-এ cgroup-প্রতি লেখককে থামানোর ব্যবস্থা আছে, আর কোন kernel বা filesystem-এ কতটা কাজ করে তা ভিন্ন হয়; আমার Docker Desktop-এর VM-এ এটা ঠেকাতে পারেনি।)

Kubernetes-এ এই কারণেই memory-র দুইটা সংখ্যা দেখা যায়: মোট usage (page cache সহ) আর container_memory_working_set_bytes, যেখান থেকে inactive file cache বাদ দেওয়া হয় — dashboard-এ usage সীমার কাছে দেখে ভয় পাওয়ার আগে দেখো সেটা ফেলে দেওয়া যায় এমন cache কি না। আর বড় file লেখা হয় এমন container-এ (upload, export, SQLite, log) নিয়মিত fsync/fdatasync, বা Chapter 24-এর direct I/O।

COMMON MISCONCEPTION

"Page cache তো দরকার হলেই ফেলে দেওয়া যায়, তাই container-এর memory সীমায় এর কোনো ভূমিকা নেই।" Clean cache-এর বেলায় সত্যি — ২৫৬ MB-এর container ৬০০ MB file নির্বিঘ্নে পড়েছে। কিন্তু dirty cache ফেলা যায় না, আর সেটা container-এর হিসাবেই গোনা হয়: শুধু একটা বড় file লিখেই, heap প্রায় খালি রেখেও, container OOMKilled হয়েছে।

MENTAL MODEL

Page cache হলো kernel-এর file-data-র cache, অব্যবহৃত RAM দিয়ে বানানো, সব process-এর জন্য এক। পড়ায় সে সময় বাঁচায় (random read-এ ৮৫ গুণ), আর পরপর পড়া চিনে আগেভাগে আনে (read-ahead)। লেখায় সে "হয়ে গেছে" বলে আগেই, আসল লেখা করে ৩০ সেকেন্ড পর্যন্ত পরে বা চাপ বাড়লে। জায়গা লাগলে clean page বিনামূল্যে যায়, dirty page যায় disk-এ লেখার পরে — আর এই দ্বিতীয় দামটাই durability-র ঝুঁকি আর container-এর OOM, দুটোরই উৎস।
