PART 8 · USER SPACE AND KERNEL SPACE

Chapter 32 — System Call আর তার দাম

Kernel-এ একবার ঢুকে বেরোতে কত nanosecond লাগে, ছোট ছোট কাজে সেই দাম কীভাবে জমে পাহাড় হয়, কোন syscall kernel-এ না ঢুকেই উত্তর পায় (vDSO), আর দাম কমানোর আসল কৌশল — কম পারাপারে বেশি কাজ।

আগের chapter-এ দেখেছি syscall মানে একটা দরজা পেরোনো: CPU mode বদলায়, kernel প্রতিটা argument যাচাই করে, তারপর ফেরে। প্রশ্ন হলো এতে খরচ কত, আর সেটা কখন গুরুত্বপূর্ণ। উত্তরটা জানা থাকলে বুঝবে কেন console.log ভরা একটা loop এত ধীর, কেন file ১ byte করে পড়া বোকামি, আর কেন Date.now() চিন্তা ছাড়াই যত খুশি ডাকা যায়।

একটা syscall-এর দাম কোথা থেকে আসে

একটা সাধারণ JS function call-এ CPU শুধু একটা লাফ দেয় আর ফিরে আসে। Syscall-এ অনেক বেশি কাজ হয়:

  1. User দিকের প্রস্তুতি: JS থেকে Node-এর C++ অংশে যাওয়া, তারপর libc-র ছোট wrapper function। সেটা syscall-এর নম্বর আর argument register-এ বসায়।
  2. দরজা পেরোনো: বিশেষ instruction (svc/syscall) CPU-কে kernel mode-এ নিয়ে যায়। Kernel তোমার সব register কোথাও সেভ করে রাখে, যাতে পরে ঠিক আগের অবস্থায় ফেরানো যায়। CPU Meltdown-আক্রান্ত হলে KPTI page table-ও বদলায় (Chapter 31)।
  3. কাজ বাছাই আর যাচাই: Kernel একটা table-এ syscall-এর নম্বর দেখে ঠিক function-টা খুঁজে বের করে, argument যাচাই করে, তারপর কাজ করে।
  4. ফেরা: Register ফিরিয়ে দেওয়া, দরকার হলে page table আবার বদলানো, তারপর user mode।
  5. পরোক্ষ দাম: এতক্ষণ CPU-র cache, TLB (ঠিকানা অনুবাদের cache, Chapter 9) আর branch predictor (Chapter 14) kernel-এর code আর data-য় ভরেছে। ফেরার পরে তোমার code কিছুক্ষণ একটু ধীর চলে, যতক্ষণ না নিজের জিনিস আবার ফিরিয়ে আনে।

একটা syscall-এর পুরো পথ। উপরের নীল সারিতে user mode-এর প্রস্তুতি, নিচের amber সারিতে kernel-এর কাজ। দুইবার দরজা পেরোনো, register সেভ করা আর ফেরানো, আর KPTI থাকলে দুইবার page table বদল। ফেরার পরেও cache আর TLB-তে kernel-এর ছাপ থেকে যায়।

মাপা যাক। নিচের script-এ চারটা জিনিস বিশ লাখ বার করে ডাকা হয়েছে। process.uptime() আর process.ppid দুটোই JS থেকে Node-এর C++-এ যায়, কিন্তু দ্বিতীয়টা সেখান থেকে getppid syscall-ও করে (parent process-এর PID জানতে চায়; Node এটা মনে রাখে না, প্রতিবার kernel-কে জিজ্ঞেস করে)। তাই দুটোর পার্থক্যই মোটামুটি kernel-এ একবার ঢুকে বেরোনোর দাম।

// cost.js — kernel-এ একবার ঢুকে বেরোতে কত সময় লাগে?
const N = 2e6;

ছোট ছোট কাজে দাম জমে যায়

প্রতিটা syscall-এর একটা নির্দিষ্ট দাম আছে, যত byte-ই সে সরাক না কেন। তাই একটা syscall-এ কতটা কাজ হয়, সেটাই আসল প্রশ্ন। একই ৩২ MB file (page cache-এ, তাই disk-এর প্রশ্ন নেই — Chapter 23) পাঁচ রকম মাপের read() দিয়ে পড়া যাক:

// chunks.js — একই ৩২ MB file, আলাদা আলাদা মাপের read() দিয়ে পড়া
const fs = require('fs');
const FILE = '/tmp/chunks.bin', SIZE = 32 * 1024 * 1024;
fs.writeFileSync(FILE, Buffer.alloc(SIZE, 7));             // একবার লিখে রাখা, এখন page cache-এ

for (const chunk of [16, 256, 4096, 65536, 1048576]) {
  const buf = Buffer.alloc(chunk);
  const fd = fs.openSync(FILE, 'r');
  let calls = 0;
  const t0 = process.hrtime.bigint();
  while (fs.readSync(fd, buf, 0, chunk, null) > 0) calls++;
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  fs.closeSync(fd);
  console.log(`chunk ${String(chunk).padStart(7)} B: ${String(calls).padStart(7)} read() ` +
              `${ms.toFixed(1).padStart(6)} ms  ${(SIZE / 2 ** 20 / (ms / 1e3)).toFixed(0).padStart(5)} MB/s  ` +
              `${(ms * 1e6 / calls).toFixed(0).padStart(6)} ns/call`);
}
chunk      16 B: 2097152 read()  779.2 ms     41 MB/s     372 ns/call
chunk     256 B:  131072 read()   50.2 ms    638 MB/s     383 ns/call
chunk    4096 B:    8192 read()    4.1 ms   7756 MB/s     504 ns/call
chunk   65536 B:     512 read()    1.5 ms  20950 MB/s   2983 ns/call
chunk 1048576 B:      32 read()    1.4 ms  23235 MB/s  43038 ns/call

একই data, একই page cache, অথচ ১৬ byte করে পড়লে সেকেন্ডে ৪১ MB, আর ১ MB করে পড়লে ২৩ GB — প্রায় ৫৭০ গুণ। শেষ column-টা পুরো গল্প বলে দেয়। ছোট chunk-এ প্রতিটা call-এর দাম ~৩৮০ ns, সেটা ১৬ byte হোক বা ২৫৬ byte। এটা নির্দিষ্ট দাম: JS থেকে C++, syscall, যাচাই, ফেরা। বড় chunk-এ call প্রতি সময় বাড়ে, কারণ এবার আসল কাজ, মানে byte copy করা, প্রাধান্য পায়। তখন নির্দিষ্ট দামটা এত byte-এ ভাগ হয়ে যায় যে প্রায় চোখেই পড়ে না।

chunks.js-এর মাপ (Mac), দুই axis-ই log scale। ছোট chunk-এ রেখাটা dashed কর্ণ ধরে চলে: গতি ঠিক করে প্রতি call-এর নির্দিষ্ট দাম। ৬৪ KB-র পরে রেখা সমতল হয়ে যায়, কারণ তখন সীমা byte copy করার গতি। প্রতিটা বিন্দুর উপর mouse রাখলে সংখ্যা দেখাবে।

একই কথা dd দিয়েও দেখা যায়। dd হলো block ধরে ধরে copy করার পুরনো Unix tool; bs প্রতিটা read/write-এর মাপ ঠিক করে দেয়:

dd if=/dev/zero of=/dev/null bs=1 count=1048576      # ১ MB, এক byte করে
dd if=/dev/zero of=/dev/null bs=65536 count=16       # একই ১ MB, ৬৪ KB করে

(আমার Mac-এ, bash dd.sh; records in/out লাইন বাদ দিয়েছি।) ০.৬ সেকেন্ড বনাম ২৪ microsecond — পঁচিশ হাজার গুণ। Linux-এ strace দিয়ে গুনলে কারণটা সংখ্যায় পাওয়া যায়। এখানে ১ লাখ byte নিয়েছি, কারণ strace প্রতিটা syscall-এ program থামিয়ে দেখে, তাতে ১০ লাখ call-এ দেড় মিনিট লেগে যায়:

COMMON MISCONCEPTION

"Syscall ধীর, যত পারো এড়াও।" এভাবে ভাবলে ভুল জায়গায় খুঁজবে। Syscall-এর একটা নির্দিষ্ট দাম আছে, একশো ns-এর ঘরে। এক call-এ ১ MB পড়লে সেই দাম ধরাই যায় না। দশ লাখ call-এ ১৬ byte করে পড়লে সেই দামটাই পুরো সময়। সমস্যা syscall না; সমস্যা হলো খুব ছোট কাজের জন্য বারবার দরজা পেরোনো। তাই প্রশ্নটা হওয়া উচিত "প্রতিটা call-এ কতটা কাজ হচ্ছে?"।

vDSO: kernel-এ না ঢুকেই kernel-এর উত্তর

cost.js-এ Date.now() ২৩ ns, অথচ সময় তো kernel জানে। JS-এর Date.now(), performance.now(), আর Node-এর timer — সবাই শেষ পর্যন্ত kernel-এর কাছে সময় চায় (Linux-এ clock_gettime)। একটা ব্যস্ত server সেকেন্ডে লাখবার সময় দেখে: প্রতিটা log লাইনে, প্রতিটা request-এর সময় মাপতে। প্রতিবার ১০০ ns দিয়ে দরজা পেরোতে হলে সেটা ভালো খরচ। অথচ সময় জানা একটা নিরীহ কাজ: কিছু বদলায় না, শুধু পড়ে।

Kernel-এর সমাধান হলো vDSO (virtual dynamic shared object)। প্রতিটা process-এর address space-এ kernel নিজে দুটো ছোট page map করে দেয় (Chapter 5-এর /proc/self/maps-এ [vdso] আর [vvar] লাইন দুটো মনে করো):

  • [vvar] — একটা data page, শুধু পড়া যায়। প্রতিটা timer tick-এ kernel এখানে লিখে রাখে "শেষ tick-এর সময় কত ছিল" আর সময় গোনার হিসাব।
  • [vdso] — kernel-এর দেওয়া ছোট একটা code page, যেটা user mode-এ চলে। এটা [vvar] থেকে শেষ tick-এর সময় পড়ে, CPU-র নিজস্ব counter register (ARM-এ cntvct_el0, x86-এ TSC) পড়ে দেখে তারপর কতটা সময় গেছে, আর দুটো যোগ করে। কোনো দরজা পেরোতে হয় না।

libc clock_gettime ডাকলে আসলে এই vDSO function চলে। প্রমাণ — দশ লাখ Date.now() আর দশ লাখ process.ppid, একসাথে strace-এ:

getppid ঠিক দশ লাখ বার, আর clock_gettime একবারও না। দশ লাখ বার সময় জানা হয়েছে, কিন্তু kernel-এ একবারও ঢুকতে হয়নি।

vDSO-র কৌশল। Kernel প্রতিটা process-এ একটা code page ([vdso]) আর একটা data page ([vvar]) map করে দেয়, আর প্রতি tick-এ [vvar] হালনাগাদ করে (ডানের dashed পথ)। Date.now() user mode-এই সেগুলো পড়ে সময় বানায়। process.ppid-এর এমন শর্টকাট নেই, তাকে দরজা পেরোতেই হয়।

এই শর্টকাট শুধু নিরীহ, পড়া-মাত্র কাজে চলে: সময় জানা (clock_gettime, gettimeofday), x86-এ এখন কোন CPU-তে চলছি (getcpu)। File খোলা বা network-এ লেখা কখনো vDSO দিয়ে হয় না, কারণ সেখানে kernel-এর যাচাই আর আসল কাজ লাগে। আর vDSO-র ঘড়ি-পড়া নির্ভর করে machine-এর সময়ের উৎস (clocksource) কেমন তার উপর। কিছু virtual machine-এ clocksource vDSO-র উপযোগী না হলে শর্টকাটটা বন্ধ হয়ে যায়, আর প্রতিটা Date.now() আসল syscall হয়ে দাঁড়ায়। পুরনো কিছু cloud instance-এ এটা একটা পরিচিত ধীরতার কারণ ছিল। Linux-এ দেখো cat /sys/devices/system/clocksource/clocksource0/current_clocksource; Docker-এর VM-এ আমার উত্তর arch_sys_counter, মানে ARM-এর নিজস্ব counter, vDSO পুরোপুরি চলে।

Batching: কম পারাপারে বেশি কাজ

নির্দিষ্ট দাম কমানোর একটাই উপায়: একবার দরজা পেরিয়ে বেশি কাজ করা। JS developer-এর রোজকার সবচেয়ে বড় উদাহরণ হলো logging। দশ লাখ লাইন file-এ লেখা, তিনভাবে:

# logs.sh — ১০ লাখ লাইন file-এ লেখা, তিনভাবে
time node -e "for (let i = 0; i < 1e6; i++) console.log(i)" > /tmp/a.txt
time node -e "const out = []; for (let i = 0; i < 1e6; i++) out.push(i); console.log(out.join('\n'))" > /tmp/b.txt
time python3 -c "for i in range(10**6): print(i)" > /tmp/c.txt
bash logs.sh 2>&1 | grep real       # Mac
real	0m1.647s
real	0m0.079s
real	0m0.188s

একই output, অথচ প্রথমটা দ্বিতীয়টার চেয়ে কুড়ি গুণ ধীর। (Docker-এর Linux-এ ০.৯২, ০.১০ আর ০.১২ সেকেন্ড।) কারণ গুনে দেখো, এবার ১০ হাজার লাইনে:

EXPERIMENT (Linux / Docker) — writes.sh
# writes.sh — ১০ হাজার লাইন file-এ লিখতে কয়টা write syscall লাগে?
count() { strace -f -c -e trace=write,writev -o /tmp/s "$@" > /tmp/out.txt; awk '/total/ {print $4}' /tmp/s; }
echo "console.log per line : $(count node -e 'for (let i = 0; i < 1e4; i++) console.log(i)')"
echo "join, then one log   : $(count node -e 'const o = []; for (let i = 0; i < 1e4; i++) o.push(i); console.log(o.join("\n"))')"
echo "python print per line: $(count python3 -c 'for i in range(10**4): print(i)')"
docker run --rm --cap-add SYS_PTRACE -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq strace python3 >/dev/null
  bash writes.sh'
console.log per line : 10003
join, then one log   : 4
python print per line: 6

Node-এর console.log প্রতিটা লাইনের জন্য আলাদা একটা write করে। stdout file বা terminal হলে Node কিছু জমিয়ে রাখে না, সাথে সাথে লেখে। এর একটা লাভ আছে: process হঠাৎ মরলেও আগে লেখা লাইন হারায় না। Python-এর print উল্টো: stdout যখন terminal না, তখন সে ৮ KB-র একটা buffer ভরে তারপর এক write-এ পাঠায়, তাই দশ হাজার লাইনে মাত্র ৬টা syscall। এর দামও আছে: Python crash করলে buffer-এ আটকে থাকা শেষ লাইনগুলো হারায় (তাই Chapter 31-এ flush=True দিয়েছি)। Hot loop-এ প্রতি iteration-এ log করা তাই শুধু output-এর ঝামেলা না, সরাসরি syscall-এর দাম। Production logger-রা এজন্যই ইচ্ছেমতো লেখা জমিয়ে পাঠানোর option রাখে।

Socket-এও একই কৌশল। একটা HTTP response প্রায়ই কয়েক টুকরায় তৈরি হয়: status line, header, body। আলাদা আলাদা write() দিলে প্রতিটা আলাদা syscall, আর network-এ ছোট ছোট আলাদা packet হওয়ার সম্ভাবনা (Nagle-এর গল্প, Chapter 27)। cork() বলে "এখনই পাঠিও না, জমাও"; uncork() সব একসাথে এক writev-এ পাঠায়। writev হলো এমন একটা syscall, যেটা memory-র কয়েকটা আলাদা টুকরা এক call-এ লিখে দেয়:

// cork.js — একটা response-এর তিন টুকরা: আলাদা write বনাম cork করে একসাথে
const net = require('net');
const server = net.createServer((sock) => {
  sock.write('HTTP/1.1 200 OK\r\n');                 // ১) cork ছাড়া: তিনটা আলাদা write
  sock.write('Content-Length: 2\r\n\r\n');
  sock.write('hi');

  sock.cork();                                        // ২) cork: জমাও, এখনই পাঠিও না
  sock.write('HTTP/1.1 200 OK\r\n');
  sock.write('Content-Length: 2\r\n\r\n');
  sock.write('hi');
  process.nextTick(() => sock.uncork());              // এবার একসাথে
  sock.end();
});
server.listen(9100, '127.0.0.1', () => {
  net.connect(9100, '127.0.0.1').on('data', () => {}).on('end', () => server.close());
});
docker run --rm --cap-add SYS_PTRACE -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq strace >/dev/null
  strace -f -e trace=write,writev node cork.js 2>&1 | grep -E "HTTP|Content|hi\""'
[pid   129] write(20, "HTTP/1.1 200 OK\r\n", 17) = 17
[pid   129] write(20, "Content-Length: 2\r\n\r\n", 21) = 21
[pid   129] write(20, "hi", 2)          = 2
[pid   129] writev(20, [{iov_base="HTTP/1.1 200 OK\r\n", iov_len=17}, {iov_base="Content-Length: 2\r\n\r\n", iov_len=21}, {iov_base="hi", iov_len=2}], 3) = 40

তিনটা syscall থেকে একটা। Node-এর http module নিজেই header আর body এভাবে জুড়ে পাঠায়, তাই সাধারণ code-এ এটা নিয়ে ভাবতে হয় না। কিন্তু নিজে net দিয়ে protocol লিখলে এটা মনে রাখার মতো।

এই বইয়ে এর আগে দুটো বড় batching দেখেছ। একটা epoll_wait হাজার socket-এর খবর একসাথে ফেরত দেয় (Chapter 29)। আর io_uring memory-তে ভাগ করা ring-এ অনেকগুলো অনুরোধ জমা নেয়, তারপর এক syscall-এ সব পাঠায়; এমন mode-ও আছে যেখানে kernel-এর একটা thread নিজেই ring দেখতে থাকে, আর syscall প্রায় লাগেই না (Chapter 24)। সবগুলোই একই হিসাবের উত্তর: দরজা পেরোনোর নির্দিষ্ট দাম কমানো যায় না, কিন্তু প্রতিটা পারাপারে বেশি কাজ ভরে দেওয়া যায়।

MENTAL MODEL

প্রতিটা syscall-এর একটা নির্দিষ্ট দাম আছে: দরজা পেরোনো, register সেভ করা ও ফেরানো, যাচাই, আর পরে cache-এ kernel-এর ছাপ। এখানে সেটা ৬০–১১০ ns, একটা JS function call-এর ৫০–১০০ গুণ। Syscall-এ যত বেশি কাজ ভরবে, এই দাম তত অদৃশ্য হবে। ১৬ byte করে পড়লে সেকেন্ডে ৪১ MB, ১ MB করে পড়লে ২৩ GB। যে কাজ শুধু পড়ে আর নিরীহ (সময় জানা), kernel সেটার জন্য vDSO দিয়ে user mode-এই উত্তর রেখে দেয়। বাকি সবকিছুর দাওয়াই batching: জমিয়ে লেখো (buffer, cork/writev), বড় করে পড়ো, আর একবারে অনেকের খবর নাও (epoll, io_uring)।
