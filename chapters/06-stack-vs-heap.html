PART 2 · FROM PROGRAM TO PROCESS

Chapter 6 — Stack vs Heap

Memory পাওয়ার দুইটা আলাদা কৌশল — কেন দুটোই লাগে, JS-এর variable আর object আসলে কোথায় থাকে, আর memory ফেরত দেওয়ার দায়িত্ব কার।

Chapter 5 থেকে দুইটা জিনিস মনে করিয়ে দিই। Stack: process-এর memory-র যে region-এ প্রতিটা function call একটা frame পায় — local variable আর ফেরার ঠিকানা রাখার জায়গা; frame বানানো মানে stack pointer (SP) থেকে একটা বিয়োগ, ফেরত দেওয়া মানে একটা যোগ। Heap: আরেকটা region, যেটা চলার সময় উপরের দিকে বাড়ে। দুটোই একই RAM; পার্থক্য শুধু ব্যবহারের নিয়মে। এই chapter সেই নিয়ম নিয়ে।

সমস্যা: সব data-র জীবন function-এর সাথে বাঁধা না

Stack এত সস্তা যে সব কিছু সেখানে রাখতে ইচ্ছা করে। কিন্তু stack-এর একটা কঠিন নিয়ম আছে: function return করলেই তার frame মুক্ত, আর পরের call সেই জায়গা নিজের কাজে ব্যবহার করে। এখানে একটা শব্দ দরকার: কোনো data-র lifetime মানে কতক্ষণ তার memory বৈধ থাকে, মানে কতক্ষণ ধরে সেটা পড়া আর বিশ্বাস করা যায়। Stack-এর data-র lifetime ঠিক function call-এর সমান। তিনটা পরিস্থিতিতে সেটা যথেষ্ট না:

  • Data-কে function-এর পরেও বাঁচতে হবে। function createUser(name) { return { name, createdAt: Date.now() }; } — object-টা তৈরি হলো createUser-এর ভেতরে, কিন্তু ব্যবহার হবে function শেষ হওয়ার পরে। এটা যদি createUser-এর frame-এ থাকত, return-এর পরের call-ই তার উপর নিজের data লিখে দিত।
  • মাপ আগে থেকে জানা নেই। Chapter 5-এ দেখেছ main তার frame বানাল sub sp, sp, #0x20 দিয়ে — ওই 0x20 (৩২ byte) একটা স্থির সংখ্যা, compile-এর সময়েই ঠিক হয়ে গেছে। কিন্তু await db.query(...) ১০টা row দেবে নাকি ১০ লাখ, সেটা চলার আগে কেউ জানে না।
  • মাপ বড়। পুরো stack-ই মাত্র কয়েক MB (ulimit -s, Chapter 5), আর V8 তার ভেতরে মোটে ~১ MB ব্যবহার করে। ২০০ MB-র একটা file buffer সেখানে ধরবে না।

তাই দ্বিতীয় একটা জায়গা লাগে, যেখানে memory চলার সময় যেকোনো মাপে চেয়ে নেওয়া যায়, আর সেটা বেঁচে থাকে যতক্ষণ না কেউ স্পষ্টভাবে ছেড়ে দেয়। এটাই heap।

Stack allocation: কেন প্রায় বিনামূল্যে

আগে stack-এর দিকটা পাকা করে নিই, কারণ heap-এর দাম বুঝতে এটাই মাপকাঠি। Stack-এ জায়গা নেওয়াকে বলে stack allocation (allocation মানে কারও ব্যবহারের জন্য memory আলাদা করে দেওয়া)। Chapter 4-এর hello-র main-এ পুরো কাজটা দুইটা instruction:

sub  sp, sp, #0x20     ; ঢোকার সময়: 32 byte-এর frame
...
add  sp, sp, #0x20     ; বেরোনোর সময়: frame ফেরত

কোনো খোঁজাখুঁজি নেই, কোনো হিসাবের খাতা নেই, kernel-কে ডাকার প্রশ্নই নেই। ফেরত দেওয়াও স্বয়ংক্রিয় — function শেষ মানেই মুক্ত, ভুলে যাওয়ার উপায় নেই। বিনিময়ে তিনটা শর্ত মানতে হয়: মাপ compile-এর সময় জানা থাকতে হবে, lifetime function-এর চেয়ে বেশি হবে না, আর মোট জায়গা সীমিত।

Heap allocation: allocator কী করে

Heap-এ শর্ত নেই, কিন্তু তাতে নতুন সমস্যা আসে। হাজার হাজার অনুরোধ আসে, প্রতিটার মাপ আলাদা — ১০০ byte, ৩ KB, ১০ MB — আর ফেরতও আসে এলোমেলো ক্রমে, যে আগে নিয়েছে সে আগে ফেরত দেবে এমন কোনো নিয়ম নেই। একটা বিয়োগ দিয়ে আর চলে না। কাউকে হিসাব রাখতে হবে heap-এর কোন অংশ ব্যবহৃত, কোনটা খালি, আর নতুন অনুরোধে মানানসই খালি জায়গা খুঁজে দিতে হবে।

এই হিসাবরক্ষকের নাম allocator — process-এর ভেতরেই চলা একটা library code (C-তে libc-র malloc, Node-এ V8-এর নিজস্ব allocator)। মোটা দাগে:

  • চাওয়া (malloc(n)): allocator তার খালি block-এর তালিকা থেকে কমপক্ষে n byte-এর একটা খোঁজে, "ব্যবহৃত" চিহ্ন দেয়, block-এর মাপ পাশে লিখে রাখে, আর block-এর শুরুর address ফেরত দেয়।
  • ফেরত (free): block-কে আবার "খালি" চিহ্ন দেয়, পাশের খালি block থাকলে জুড়ে বড় করে।
  • ফুরিয়ে গেলে: হাতে মানানসই খালি জায়গা না থাকলে allocator kernel-এর কাছে আরও memory চায় — syscall দিয়ে। দুই রাস্তা: brk (Chapter 5-এর [heap] region-টাকেই উপরে বাড়াও), অথবা mmap (address space-এর অন্য কোথাও একদম নতুন একটা region দাও)।
EXPERIMENT (Linux / Docker) — allocator-কে kernel-এর কাছে যেতে দেখা

ছোট একটা C program, যেটা একবার ১০০ byte আর একবার ১০ MB চায় (malloc ফেরত দেয় address; %p সেটা hex-এ print করে):

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    char *small = malloc(100);               /* ছোট */
    char *big   = malloc(10 * 1024 * 1024);  /* 10 MB */
    printf("small at %p\nbig   at %p\n", (void *)small, (void *)big);
    free(big);
    free(small);
    return 0;
}

debian container-এ apt install gcc libc6-dev strace করে compile করো, তারপর strace -e trace=brk,mmap,munmap ./alloc। Program শুরুর library-loading-এর লাইন বাদ দিলে শেষটা:

brk(NULL)                          = 0xaaab00d40000
brk(0xaaab00d61000)                = 0xaaab00d61000
mmap(NULL, 10489856, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffffaa600000
munmap(0xffffaa600000, 10489856)   = 0
small at 0xaaab00d402a0
big   at 0xffffaa600010

পুরো গল্পটা output-এ আছে। ১০০ byte চাইতেই allocator brk দিয়ে heap region-কে 0x21000 byte (১৩২ KB) বাড়িয়ে নিল — এক কামড়ে বড় টুকরো, যাতে পরের ছোট অনুরোধ গুলোতে kernel-এর কাছে যেতে না হয়। small পেল সেই heap-এর ভেতরের একটা address (0xaaab00d4…)। ১০ MB-র বেলায় allocator আলাদা mmap নিল, তাই big-এর address একদম অন্য এলাকায় (0xffff…) — Chapter 5-এর ছবির memory-mapped region-এ। free(big)-এ allocator সেই region সঙ্গে সঙ্গে munmap দিয়ে kernel-কে ফেরত দিল; কিন্তু free(small)-এ কোনো syscall নেই — ছোট টুকরোটা সে পরের জন্য নিজের কাছে রেখে দিল।

মানে heap allocation-এর দাম: প্রতিবার খোঁজা আর হিসাব লেখা, আর মাঝে মাঝে পুরো একটা syscall। Stack-এর একটা বিয়োগের তুলনায় এটা অনেক ভারী।

Pointer আর reference: stack-এর variable, heap-এর object

Allocator ফেরত দেয় একটা address। Object-টা পড়ে থাকে heap-এ, কিন্তু যে code সেটা বানাল, তাকে তো মনে রাখতে হবে object-টা কোথায়। তাই সেই address-টা সে রেখে দেয় নিজের একটা variable-এ — সাধারণত নিজের stack frame-এ বা একটা register-এ। যে variable-এর মান আসলে একটা memory address, তাকে বলে pointer। ওপরের C code-এ char *small — এই * চিহ্নটাই বলছে small-এর ভেতরে একটা address থাকবে।

JS-এ তুমি কখনো address দেখো না, কিন্তু নিচে ঠিক এটাই হচ্ছে। const user = { name: 'Rahim' } লিখলে object-টা heap-এ তৈরি হয়, আর user variable-এ থাকে শুধু তার address। JS-এ একে বলে reference: এমন একটা pointer, যেটা দিয়ে address-এর গণিত করা যায় না, আর runtime নিজে সেটার উপর নজর রাখে। Chapter 2-এর %DebugPrint(user) যে 0x257501fa9999 দেখিয়েছিল, সেটাই ওই address। তোমার চেনা কয়েকটা JS আচরণের কারণ এখান থেকেই আসে:

const a = { count: 1 };
const b = a;             // object copy হলো না — address copy হলো
b.count = 99;
console.log(a.count);    // 99 — a আর b একই object-এর দিকে তাকিয়ে আছে

console.log({} === {});  // false — দুইটা আলাদা object, দুইটা আলাদা address
console.log(a === b);    // true  — একই address

Function-এ object পাঠালেও একই ঘটনা: callee পায় address-এর একটা copy, তাই সে object-টা বদলালে caller সেই বদল দেখে। === দুইটা object-এর ভেতরের মান তুলনা করে না, তুলনা করে address।

বাঁয়ে main-এর frame, ডানে heap। a আর b-এর ভেতরে একই address, তাই দুজনে একই object দেখে। ছোট integer 42 সরাসরি frame-এর ঘরেই বসে, কিন্তু 4.2 heap-এর একটা আলাদা object (নিচের misconception box দেখো)। সবচেয়ে নিচের object-এর দিকে কোনো তীর নেই — তাকে আর কেউ খুঁজে পাবে না।

Scope আর lifetime: closure-এর গোপন কথা

দুইটা শব্দ প্রায়ই গুলিয়ে যায়। Scope মানে code-এর কোন অংশ থেকে একটা নাম দেখা যায় — এটা code পড়েই বলা যায়। Lifetime মানে (ওপরে যেমন বলেছি) memory-টা কতক্ষণ বৈধ — এটা ঠিক হয় চলার সময়। Stack-এর variable-এর বেলায় দুটো মিলে যায়: function-এর বাইরে নামও দেখা যায় না, memory-ও থাকে না। কিন্তু JS-এ এটা ভাঙে:

function makeCounter() {
  let count = 0;             // makeCounter-এর local variable
  return () => ++count;
}
const next = makeCounter();  // makeCounter শেষ — তার frame মুক্ত
console.log(next(), next(), next());   // 1 2 3

count-এর scope শেষ হয়ে গেছে — makeCounter-এর বাইরে থেকে তুমি count লিখতে পারবে না। অথচ তার মান বেঁচে আছে, প্রতিবার বাড়ছে। এটা সম্ভব হলো কারণ V8 code দেখে বুঝে ফেলে যে ভেতরের arrow function-টা count ব্যবহার করে আর বাইরে চলে যাচ্ছে। তাই সে count-কে stack frame-এ না রেখে heap-এ একটা ছোট object-এ রাখে (V8 এর নাম দিয়েছে Context), আর arrow function-টা সেই object-এর reference ধরে রাখে। Function আর তার ধরে রাখা variable-দের এই জুটির নামই closure। মানে JS-এ "local variable মানেই stack" কথাটা সবসময় সত্যি না — lifetime যার বেশি, সে heap-এ যায়।

ফেরত দেবে কে: manual free বনাম garbage collection

Heap-এর memory ততক্ষণ দখলে থাকে যতক্ষণ না কেউ ফেরত দেয়। প্রশ্ন হলো, কে দেবে, আর কখন? C-তে উত্তর: programmer নিজে, free ডেকে। সেখানে তিন রকম ভুল হয়, আর প্রতিটা ভয়ংকর:

  • Memory leak — ফেরত দিতে ভুলে যাওয়া। Process-এর memory বাড়তেই থাকে, একসময় machine-এর RAM শেষ।
  • Dangling pointer — ফেরত দেওয়ার পরেও পুরনো address দিয়ে memory ব্যবহার করা। Allocator ততক্ষণে সেই জায়গা অন্য কাউকে দিয়ে দিতে পারে; তখন দুইজন একই memory-কে নিজের ভেবে লিখতে থাকে।
  • Double free — একই block দুইবার ফেরত দেওয়া, যাতে allocator-এর নিজের হিসাবের খাতাই এলোমেলো হয়ে যায়।

শেষ দুইটা শুধু crash না, security-র বড় ফুটো। Microsoft আর Chrome team দুই পক্ষই আলাদাভাবে জানিয়েছে, তাদের গুরুতর security bug-এর প্রায় ৭০% এই ধরনের memory-ভুল থেকে আসে।

JS, Java, Go, Python-এর মতো ভাষার উত্তর: runtime নিজেই ঠিক করবে। এর নাম garbage collection (GC), আর যে অংশ কাজটা করে সে garbage collector। নিয়মটা এরকম। কিছু জায়গাকে ধরা হয় root — এমন জায়গা যেখান থেকে program সরাসরি data-য় পৌঁছাতে পারে: stack-এ থাকা বর্তমান function গুলোর variable, global object ইত্যাদি। Root থেকে reference ধরে ধরে যত object-এ পৌঁছানো যায়, তারা জীবিত (reachable)। বাকি সব garbage — program আর কখনো তাদের খুঁজে পাবে না, তাই মুছে দেওয়া নিরাপদ। ওপরের ছবির { name: 'old' } ঠিক এমন। Collector চলার সময় তোমার JS কিছু মুহূর্ত থেমে থাকতে পারে; একেই বলে GC pause (V8 কাজের বড় অংশ অন্য thread-এ সারে, তবু কিছুটা থামা এড়ানো যায় না)।

EXPERIMENT — gc.js

--expose-gc flag দিলে global.gc() দিয়ে collector-কে হাতে ডাকা যায়; heapUsed হলো V8-এর heap-এ এই মুহূর্তে object-দের দখলে থাকা memory।

const mb = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1) + ' MB';

let big = new Array(5_000_000).fill(1);   // ~40 MB heap-এ
global.gc();
console.log('reference আছে     :', mb());

big = null;                                // শেষ reference-টা কেটে দিলাম
global.gc();
console.log('reference কাটার পর:', mb());

node --expose-gc gc.js চালালে আমার Mac-এ: 41.2 MB, তারপর 3.3 MB। big = null দেওয়ায় array-টা আর কোনো root থেকে reachable না, তাই collector পুরো ৩৮ MB ফেরত নিল।

তাহলে GC-ওয়ালা ভাষায় leak হয় কীভাবে? হয়, যখন একটা object আর তোমার কাজে লাগে না, কিন্তু কোথাও থেকে তার reference রয়ে গেছে — collector শুধু reachability দেখে, তোমার উদ্দেশ্য দেখে না। সবচেয়ে চেনা উদাহরণ: module-level একটা cache বা array যেটা শুধু বাড়ে, কখনো খালি হয় না; অথবা event listener যোগ করা হলো কিন্তু কখনো সরানো হলো না।

const cache = [];                 // module-level — সবসময় reachable
let tick = 0;
const timer = setInterval(() => {
  cache.push(new Array(100_000).fill(tick));   // প্রতি tick-এ ~800 KB, কখনো মোছা হয় না
  const mb = process.memoryUsage().heapUsed / 1024 / 1024;
  console.log(`tick ${++tick}: heapUsed = ${mb.toFixed(1)} MB`);
  if (tick === 6) clearInterval(timer);
}, 200);

Output: 4.0 MB, 4.9, 5.7, 6.5, 7.2, 8.0 MB — সিঁড়ির মতো উঠছে, GC কিছুই করতে পারছে না। Server-এ এটা দিনের পর দিন চললে শেষ দৃশ্য এরকম। V8-এর heap-এর যে অংশে দীর্ঘজীবী object থাকে তার নাম old space, আর তার সর্বোচ্চ মাপ একটা flag দিয়ে ছোট করে পরিণতিটা দ্রুত দেখা যায়:

node --max-old-space-size=50 -e "const a = []; while (true) a.push({ data: new Array(1000).fill(0) })"

কয়েক মুহূর্ত পরে: FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory। এটা JS error না যে catch করবে — পুরো process মারা যায়।

আসল দাম কোথায়: allocation, locality, fragmentation

"Stack fast, heap slow" — কথাটা শুনতে সুবিধার, কিন্তু আধা-সত্য। দামটা তিন জায়গায়, আলাদা করে দেখা দরকার।

১. Allocation-এর দাম

Stack-এ একটা বিয়োগ। C-র malloc-এ খোঁজাখুঁজি আর মাঝে মাঝে syscall, ওপরে দেখলে। V8 আবার এখানে চালাক: নতুন object গুলো সে বানায় একটা আলাদা এলাকায় (young generation), যেখানে allocation মানে stack-এর মতোই শুধু একটা pointer সামনে সরানো। দামটা সে পরে দেয় — garbage যত বেশি বানাবে, collector-কে তত বেশিবার চলতে হবে। তাই JS-এ প্রশ্নটা "heap-এ রাখলাম কি না" না, প্রশ্নটা "কত garbage বানাচ্ছি"।

২. Locality-র দাম

Stack বা heap — দুটোই একই RAM, পড়ার গতি একই। কিন্তু CPU সবসময় RAM পর্যন্ত যায় না। CPU-র ভেতরে ছোট কিন্তু অনেক দ্রুত একটা memory থাকে, cache — সম্প্রতি ছোঁয়া memory আর তার আশেপাশের byte গুলো সেখানে রাখা হয় (Chapter 13)। যে data পাশাপাশি থাকে আর ক্রমানুসারে পড়া হয়, সে cache-এ চমৎকার খাটে। একে বলে ভালো locality। Stack সবসময় ছোট, ঘন, আর সদ্য-ব্যবহৃত, তাই প্রায় সবসময় cache-এ থাকে। Heap-এর object গুলো ছড়ানো থাকলে প্রতিটা reference ধরে লাফ দিতে গিয়ে cache-এ পাওয়া যায় না, RAM পর্যন্ত যেতে হয় (Chapter 2-এর টেবিল: ~১০০ ns)।

EXPERIMENT — locality.js
const N = 5_000_000;
const flat = new Float64Array(N).fill(1);                  // সংখ্যা গুলো এক টানা memory-তে
const objs = Array.from({ length: N }, () => ({ v: 1 }));  // প্রতিটা সংখ্যা আলাদা heap object-এ
const shuffled = objs.slice();
for (let i = N - 1; i > 0; i--) {                          // reference গুলোর ক্রম এলোমেলো করো
  const j = Math.floor(Math.random() * (i + 1));
  [shuffled[i], shuffled[j]] = [shuffled[j], shuffled[i]];
}

function time(label, fn) {
  fn();                                                    // একবার চালিয়ে JIT-কে গরম করো
  const t = performance.now();
  fn();
  console.log(label.padEnd(28), (performance.now() - t).toFixed(1), 'ms');
}
time('Float64Array (contiguous)', () => { let s = 0; for (let i = 0; i < N; i++) s += flat[i]; return s; });
time('objects, in creation order', () => { let s = 0; for (let i = 0; i < N; i++) s += objs[i].v; return s; });
time('objects, shuffled order',    () => { let s = 0; for (let i = 0; i < N; i++) s += shuffled[i].v; return s; });

আমার Mac-এ: 2.8 ms, 4.0 ms, 30.4 ms। তিনটাই হুবহু একই হিসাব — পঞ্চাশ লাখটা ১ যোগ করা। পার্থক্য শুধু memory-তে data কীভাবে সাজানো। শেষেরটায় object গুলো একই, শুধু পড়ার ক্রম এলোমেলো, আর তাতেই ১০ গুণ ধীর।

৩. Fragmentation-এর দাম

Heap-এ অনেকক্ষণ ধরে নানা মাপের allocate আর free চললে খালি জায়গা গুলো ছোট ছোট টুকরো হয়ে ছড়িয়ে পড়ে, মাঝে মাঝে জীবিত block। তখন মোট খালি জায়গা অনেক থাকলেও একটা বড় অনুরোধ মেটানোর মতো একটানা খালি জায়গা না-ও থাকতে পারে। এর নাম fragmentation। ফল: allocator-কে kernel-এর কাছে নতুন memory চাইতে হয়, যদিও হাতে "খালি" memory পড়ে আছে।

উপরে: ৫৬ KB খালি, কিন্তু সবচেয়ে বড় একটানা ফাঁক ১৬ KB, তাই ৩২ KB-র অনুরোধ মেটে না। নিচে: V8-এর collector জীবিত object গুলো এক পাশে সরিয়ে আনলে (compaction) সব খালি জায়গা এক টুকরো হয়ে যায়।

V8 এটা কমাতে পারে একটা সুবিধার জোরে: collector জানে প্রতিটা reference কোথায় আছে, তাই সে জীবিত object গুলো সরিয়ে এক পাশে জড়ো করতে পারে আর সব reference-এ নতুন address বসিয়ে দিতে পারে — এর নাম compaction। C-র malloc এটা পারে না: program-এর কোন variable-এ কোন raw address লুকিয়ে আছে, allocator জানে না, তাই কিছু সরাতে গেলে সেই pointer গুলো ভুল জায়গা দেখাবে।

এর সাথে জড়ানো আরেকটা বাস্তবতা: free করা বা GC হওয়া মানেই memory OS-এর কাছে ফেরত যাওয়া না। Kernel memory দেয় আর ফেরত নেয় নির্দিষ্ট মাপের পুরো টুকরো ধরে — এর নাম page (সাধারণত ৪ KB, Apple Silicon-এ ১৬ KB; Chapter 9)। একটা page-এর ভেতরে একটাও জীবিত object থাকলে পুরো page আটকে থাকে। তার উপর allocator ভবিষ্যতের জন্য খালি জায়গা হাতে রাখতে পছন্দ করে। নিজে দেখো — RSS (resident set size) হলো process এই মুহূর্তে আসলে কতটা RAM দখল করে আছে, kernel-এর হিসাবে:

const mb = n => (n / 2 ** 20).toFixed(1) + ' MB';
const show = label => { global.gc(); const m = process.memoryUsage(); console.log(label.padEnd(18), 'heapUsed', mb(m.heapUsed).padStart(9), '| rss', mb(m.rss).padStart(9)); };
show('start');
globalThis.keep = [];                      // global — একটা root থেকে সরাসরি reachable
for (let i = 0; i < 2_000_000; i++) keep.push({ id: i, tag: 'x' + i });
show('2M objects alive');
globalThis.keep = null;                    // শেষ reference কেটে দিলাম
show('all released');

node --expose-gc দিয়ে চালালে আমার Mac-এ: শুরুতে heapUsed 3.1 MB, RSS 36.9 MB; ২০ লাখ object-এর পরে 147.7 MB আর 234.6 MB; সব ছেড়ে দেওয়ার পরে heapUsed আবার 3.3 MB — কিন্তু RSS তখনো 212.2 MB। JS-এর হিসাবে memory ফেরত গেছে; kernel-এর হিসাবে process এখনো প্রায় পুরোটা ধরে আছে। Production-এ container-এর memory graph কেন peak-এর পরে সহজে নামে না, এটাই তার একটা বড় কারণ।

COMMON MISCONCEPTION

"JS-এ primitive (number, string, boolean) stack-এ থাকে, object heap-এ।" V8-এ নিয়মটা আসলে অন্য। ছোট integer (V8-এর ভাষায় Smi, small integer) সরাসরি variable-এর ঘরের ভেতরেই বসে। কিন্তু দশমিক সংখ্যা, বড় সংখ্যা আর সব string heap-এর object। আর closure যে variable ধরে রাখে, সেটা primitive হলেও heap-এ যায় (ওপরের count)। দেখো:

node --allow-natives-syntax -e "%DebugPrint(42); %DebugPrint(4.2)"

প্রথমটা বলে Smi: 0x2a (42) — কোনো address নেই, মানটা নিজেই আছে। দ্বিতীয়টা বলে 0x20368725c921: [HeapNumber] in OldSpace — একটা heap address-এ রাখা আলাদা object। দুটোই JS-এর number, অথচ থাকার জায়গা আলাদা। মানে "primitive নাকি object" দিয়ে জায়গা ঠিক হয় না; ঠিক হয় V8 মানটাকে ভেতরে কীভাবে উপস্থাপন করে, তা দিয়ে।

MENTAL MODEL

Stack: মাপ আগে জানা, lifetime function-এর সমান, allocation একটা বিয়োগ, ফেরত স্বয়ংক্রিয়, সবসময় cache-এর কাছে। Heap: যেকোনো মাপ, যেকোনো lifetime, কিন্তু একজন allocator-কে হিসাব রাখতে হয়, আর কাউকে ফেরত দিতে হয় — C-তে তুমি, JS-এ garbage collector। দুইটাকে জোড়ে reference: stack-এ রাখা একটা address, যেটা heap-এর object দেখায়। JS-এ memory সমস্যা খুঁজতে হলে প্রশ্ন করো: "এই object-কে কে এখনো reach করছে?"
