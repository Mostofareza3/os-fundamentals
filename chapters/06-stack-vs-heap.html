Chapter 6 — Stack vs Heap

দুইটা আলাদা allocation strategy — কেন দুটোই লাগে, আর কার কী cost।

Stack কেন দরকার

Function-এর local variable-দের একটা সুন্দর property আছে — এদের lifetime একদম predictable। Function ঢুকলে জন্ম, function বের হলে মৃত্যু। এমন predictable lifetime-এর জন্য stack perfect: allocation মানে শুধু stack pointer-টা একটু সরানো, deallocation মানে ফেরত সরানো। কোনো bookkeeping লাগে না, কোনো খোঁজাখুঁজি লাগে না।

Heap কেন দরকার

কিন্তু সব data-র lifetime function-এর সাথে বাঁধা না। ধরো একটা function user object বানিয়ে return করলো — function শেষ, কিন্তু object টা বেঁচে থাকতে হবে। অথবা runtime-এ ঠিক হবে কত বড় array লাগবে। এই "যতদিন দরকার ততদিন বাঁচবে, size আগে থেকে জানা নেই" ধরনের data-র জন্য heap — malloc(size) দিয়ে চাও, free(ptr) দিয়ে ফেরত দাও।

SCOPE vs LIFETIME

Scope = code-এর কোথা থেকে variable-টা দেখা যায়। Lifetime = memory-টা কতক্ষণ বৈধ থাকে। Stack data-র বেলায় দুটো মিলে যায়। Heap data-র বেলায় না — pointer/reference টা scope-এর বাইরে চলে গেলেও heap-এর memory বেঁচে থাকতে পারে। C-তে এই ফাঁক থেকেই আসে dangling pointer আর memory leak; GC language-এ garbage collector এই lifetime tracking-টাই তোমার হয়ে করে।

Cost-এর আসল হিসাব

"Stack fast, heap slow" — এই oversimplification-টা এড়িয়ে যাই। আসল ছবিটা:

  • Stack allocation trivially simple — একটা pointer বাড়ানো/কমানো। প্রায় free।
  • Heap allocation-এ কাজ বেশি — allocator-কে free space খুঁজতে হয়, bookkeeping করতে হয়, মাঝে মাঝে kernel-এর কাছে আরো memory চাইতে হয় (system call!)। কতটা costly সেটা allocator, allocation pattern আর size-এর উপর নির্ভর করে।
  • Access speed-এ পার্থক্য allocation-এর না, locality-র — stack-এর data সাধারণত ছোট জায়গায় ঘেঁষাঘেঁষি করে থাকে বলে CPU cache-এ ভালো behave করে (Chapter 13)। Heap-এর data ছড়ানো-ছিটানো হলে cache miss বাড়ে। মানে পার্থক্যটা জায়গার "জাত"-এ না, access pattern-এ।

Heap-এর নিজস্ব রোগ

  • Fragmentation: বারবার ছোট-বড় allocate/free করতে করতে free memory টুকরা টুকরা হয়ে যায় — মোট জায়গা থাকলেও বড় এক টুকরা পাওয়া যায় না।
  • Memory leak: নেওয়া memory ফেরত না দেওয়া। GC language-এও হয় — যেমন global array-তে reference জমিয়ে রাখলে GC কিছুই করতে পারে না। Node.js app-এর memory ধীরে ধীরে বেড়ে যাওয়ার classic কারণ।
  • Stack overflow: Heap-এর রোগ না, stack-এর — infinite/গভীর recursion-এ frame জমে stack-এর সীমা পার হয়ে যাওয়া।
JS DEVELOPER-এর জন্য

V8-এ তোমার object/array/closure সব heap-এ থাকে, আর garbage collector সেই heap পরিষ্কার করে। "GC pause" মানে: collector heap ঘুরে ঘুরে মরা object খুঁজছে। Heap যত এলোমেলো আর বড়, GC-র কাজ তত বেশি। Chrome DevTools-এর Memory tab-এ যে heap snapshot নাও — সেটা আক্ষরিক অর্থেই এই chapter-এর heap region-এর ছবি।
