PART 1 · THE BIG PICTURE

Chapter 1 — Operating System কেন দরকার?

তোমার code আর hardware-এর মাঝখানে একটা বাড়তি layer বসানো আছে। এই chapter-এ দেখব সেটা না থাকলে কী কী ভেঙে পড়ত, আর সেই ভাঙন ঠেকাতে layer-টা ঠিক কী করে।

তুমি হয়তো বছরের পর বছর fs.readFile আর app.listen(3000) লিখেছ। কিন্তু কখনো ভাবতে হয়নি file টা SSD-র কোন কোণে পড়ে আছে, বা network card-কে কোন ভাষায় বলতে হয় "এই data টা পাঠাও"। এই যে "ভাবতে হয়নি" — এটা কোনো magic না। এর পেছনে একটা পুরো software layer দিনরাত কাজ করছে, যার নাম operating system (OS)। Definition দিয়ে শুরু না করে চলো আগে দেখি এটা না থাকলে জীবন কেমন হতো।

আগে জেনে নিই: machine-এর ভেতরে কী আছে

যেকোনো computer — তোমার laptop হোক বা AWS-এর server — মোটা দাগে চারটা জিনিস দিয়ে তৈরি:

  • CPU — আসল কাজ যে করে। CPU বোঝে শুধু instruction: খুব ছোট ছোট আদেশ, যেমন "এই দুইটা সংখ্যা যোগ করো", "memory থেকে একটা মান আনো", "শর্ত সত্যি হলে অন্য জায়গায় লাফ দাও"। তোমার পুরো Node.js app শেষ পর্যন্ত কোটি কোটি এমন instruction-এ ভেঙে চলে।
  • RAM (memory) — চলমান program-এর code আর data যেখানে থাকে। দ্রুত, কিন্তু power গেলে সব মুছে যায়।
  • Storage (SSD বা hard disk) — file যেখানে স্থায়ীভাবে থাকে। Power গেলেও থাকে, কিন্তু RAM-এর চেয়ে বহুগুণ ধীর।
  • Network card — অন্য machine-এর সাথে data আদান-প্রদান করে।

আর program বলতে এই বইয়ে বোঝাব instruction-ভরা একটা file — যেমন node, Chrome, বা ls।

একটা CPU chip-এর ভেতরে সাধারণত কয়েকটা স্বাধীন অংশ থাকে, যাদের প্রত্যেকে আলাদাভাবে instruction চালাতে পারে। প্রতিটা অংশের নাম core। ১২ core মানে একই মুহূর্তে সর্বোচ্চ ১২টা আলাদা কাজ সত্যিকার অর্থে পাশাপাশি চলতে পারে। তোমার machine-এ কী আছে, Node দিয়েই দেখে নাও:

node -e "const os = require('os'); console.log(os.cpus().length + ' cores,', Math.round(os.totalmem() / 2**30) + ' GB RAM')"

আমার Mac-এ output এল 12 cores, 24 GB RAM। প্রতিটা hardware-এর ভেতরটা Chapter 2-এ খুলে দেখব। এই chapter-এর জন্য এটুকুই যথেষ্ট।

OS না থাকলে কী হতো

ধরো এমন একটা computer যেখানে কোনো OS নেই — শুধু hardware আর তোমার program। তিনটা সমস্যা সঙ্গে সঙ্গে দেখা দেবে।

সমস্যা ১: প্রতিটা program-কে hardware-এর ভাষা শিখতে হতো

Storage device নিজে "file" বলে কিছু চেনে না। সে চেনে শুধু block — নির্দিষ্ট মাপের টুকরা (সাধারণত ৫১২ byte বা ৪ KB), প্রতিটার একটা নম্বর। তাকে বলতে হয় "block নম্বর ৮৮,২১০ পড়ো", আর সেই command-এর format এক কোম্পানির SSD থেকে আরেক কোম্পানির SSD-তে আলাদা। OS না থাকলে config file পড়ার জন্য তোমাকে নিজে হিসাব করতে হতো file কোন block-এ শুরু, কত block লম্বা, আর এই নির্দিষ্ট SSD model-কে কীভাবে command পাঠাতে হয়। Network card, USB, screen — সবার জন্য একই গল্প। আর দুনিয়ার প্রতিটা app-কে এই code আলাদা আলাদা করে লিখতে হতো।

সমস্যা ২: সবাই একই hardware চায়, একই সময়ে

এই মুহূর্তে তোমার machine-এ শুধু তোমার একটা program চলছে না। Browser, editor, Slack, background-এর অসংখ্য service — সবাই চলছে। ps command চলমান program-দের list দেখায়, আর wc -l সেই list-এর লাইন গোনে:

ps aux | wc -l

আমার Mac-এ এটা দেখাল ৭৫২ — মানে প্রায় সাড়ে সাতশো চলমান program, অথচ core মাত্র ১২টা। কে কখন CPU পাবে? RAM-এর কোন অংশ কার? দুইজন একসাথে disk-এ লিখতে চাইলে কার লেখা আগে যাবে? কেউ একজন সিদ্ধান্ত না নিলে পুরো বিশৃঙ্খলা।

সমস্যা ৩: একজনের bug আরেকজনকে মেরে ফেলত

RAM একটাই, সবার data একই RAM-এ। কোনো পাহারা না থাকলে তোমার Node server-এর একটা bug ভুল জায়গায় লিখে তোমার editor-এর unsaved file নষ্ট করে দিতে পারত। আরও খারাপ: একটা malicious program চুপচাপ তোমার password manager-এর memory পড়ে নিতে পারত।

OS হলো এই তিন সমস্যার সমাধান। এক বাক্যে: operating system হলো সেই software যেটা hardware-কে সহজ interface-এর পেছনে লুকায়, আর অনেক program-এর মধ্যে hardware নিরাপদে ভাগ করে দেয়। প্রথম কাজটার নাম abstraction, দ্বিতীয়টার নাম resource management। দুটো আলাদা করে দেখি।

প্রথম কাজ: abstraction

সমস্যা ১-এর মূল কথা ছিল: প্রতিটা device-এর নিজস্ব ভাষা, আর সেই ভাষা প্রতিটা app-কে শিখতে হচ্ছে। সমাধান হলো abstraction — জটিল জিনিসের ভেতরের details লুকিয়ে একটা সহজ, স্থির interface দেওয়া। JS-এ তুমি প্রতিদিন এটা করো: একটা class বা module বানিয়ে ভেতরের messy logic লুকিয়ে ফেলো, বাইরে থাকে শুধু কয়েকটা পরিষ্কার method। OS hardware-এর উপর ঠিক এটাই করে:

Hardware-এর আসল রূপOS যে abstraction দেয়তুমি যেভাবে দেখো
Storage-এর নম্বরওয়ালা blockFile আর folderfs.readFile('config.json')
Network card-এর কাঁচা data packetSocket — একটা network connection-এর এক প্রান্ত, যেখানে তুমি data লেখো আর পড়োnet.connect(), fetch()
CPU-র instruction চালানোর ক্ষমতাProcess — চলমান একটা program, নিজস্ব memory আর অবস্থা সহ (Chapter 3)node server.js
RAM-এর physical chipVirtual memory — প্রতিটা process মনে করে পুরো memory তার একার (Chapter 9)new Array(1e6)

File-এর উদাহরণটা নিজে পরীক্ষা করো। কোনো storage-কে folder tree-র একটা জায়গায় জুড়ে দেওয়াকে বলে mount করা — যেমন USB drive লাগালে macOS সেটাকে /Volumes/-এর নিচে mount করে। তোমার machine-এ কী কী mount করা আছে দেখো:

df -h

List-এ internal SSD থাকবে, USB drive লাগানো থাকলে সেটাও থাকবে, হয়তো কোনো network drive-ও। এদের hardware সম্পূর্ণ আলাদা, command-এর ভাষাও আলাদা। কিন্তু সবগুলোতে তুমি হুবহু একই code দিয়ে লিখবে: fs.writeFileSync(path, data)। কোন device-এ কীভাবে লিখতে হয়, সেই চিন্তা OS নিজের ঘাড়ে নিয়ে নিয়েছে। সমস্যা ১ সমাধান।

দ্বিতীয় কাজ: resource management

Resource বলতে এখানে বোঝাচ্ছি hardware-এর সেই জিনিসগুলো যাদের পরিমাণ সীমিত আর সবাই চায় — CPU-র সময়, RAM, disk, network। সমস্যা ২ আর ৩ দুটোই resource নিয়ে: একটা হলো ভাগাভাগি, আরেকটা হলো পাহারা।

Sharing: সবাইকে পালা করে দেওয়া

১২টা core দিয়ে সাড়ে সাতশো program চালানোর কৌশলের নাম time-sharing: OS একটা program-কে একটা core-এ কয়েক millisecond চালায়, তারপর থামিয়ে আরেকজনকে বসায়, তারপর আরেকজনকে। এত দ্রুত পালা বদলায় যে তোমার মনে হয় সবাই একসাথে চলছে। কাকে কখন, কতক্ষণ বসানো হবে — সেই সিদ্ধান্ত নেওয়ার কাজের নাম scheduling (Part 5-এ বিস্তারিত)।

নিজের চোখে দেখো। Core যতগুলো, তার দ্বিগুণ সংখ্যক infinite loop চালাও — প্রতিটা loop একাই একটা পুরো core খেয়ে ফেলতে চায়:

EXPERIMENT

শেষের busyloop শব্দটা শুধু একটা চিহ্ন, যাতে পরে এই process গুলোকেই খুঁজে বন্ধ করা যায়।

# কয়টা core আছে? (আমার Mac-এ 12)
node -p "require('os').availableParallelism()"

# core-এর দ্বিগুণ সংখ্যক infinite loop চালাও — এখানে 24
for i in $(seq 24); do node -e "while(true){}" busyloop & done

# CPU ব্যবহার দেখো (macOS; Linux-এ শুধু: top)। বের হতে q চাপো
top -o cpu

# দেখা শেষ হলে সবগুলো বন্ধ করো
pkill -f busyloop

top-এ দেখবে প্রতিটা node-এর CPU মোটামুটি ৫০%-এর কাছাকাছি — আমার চালানোয় ৪৬% থেকে ৫৩%-এর মধ্যে ছিল। ২৪ জন দাবিদার, ১২টা core: OS প্রত্যেককে প্রায় সমান ভাগে অর্ধেক সময় দিচ্ছে। আর এর মধ্যেও তোমার terminal, browser দিব্যি সাড়া দিচ্ছে, কারণ তারাও নিয়মিত পালা পাচ্ছে।

সমস্যা ২ সমাধান: কেউ CPU একা দখল করে রাখতে পারে না, কারণ কখন কাকে সরাতে হবে সেই সিদ্ধান্ত program-এর হাতে না, OS-এর হাতে।

Isolation: একজনকে আরেকজনের থেকে আলাদা রাখা

OS প্রতিটা process-কে আলাদা memory দেয়, আর একটা process অন্যটার memory ছুঁতে চাইলে সেখানেই আটকে দেয় (কীভাবে আটকায়, সেটা Chapter 9-এর virtual memory-র গল্প)। এই আলাদা রাখার নাম isolation। এর সবচেয়ে চেনা ফল তুমি Chrome-এ দেখেছ: Chrome প্রতিটা tab-কে আলাদা process-এ চালায়। Chrome-এ একটা নতুন tab খুলে address bar-এ লেখো:

chrome://crash

ওই tab-টা "Aw, Snap!" দেখিয়ে মারা যাবে, কিন্তু অন্য tab গুলোর কিছুই হবে না। মরা process-টা অন্যদের memory ছুঁতেই পারত না, তাই তার মৃত্যু অন্যদের টেনে নামাতে পারেনি। সমস্যা ৩ সমাধান।

MENTAL MODEL

OS = abstraction + resource management। Abstraction উত্তর দেয় "hardware ব্যবহার করব কীভাবে?" — file, socket, process-এর মতো সহজ interface দিয়ে। Resource management উত্তর দেয় "কে কতটুকু পাবে, আর কে কাকে ছুঁতে পারবে না?" — time-sharing আর isolation দিয়ে।

Kernel: OS-এর যে অংশের হাতে আসল ক্ষমতা

এখন একটা প্রশ্ন ওঠে: এই নিয়মগুলো enforce করবে কে? "তুমি অন্যের memory ছুঁতে পারবে না" — কথাটা যদি অন্য সবার মতোই একটা সাধারণ program বলে, তাহলে কেউ তার কথা শুনবে কেন? একটা buggy বা malicious program তো সেই নিয়ম-রক্ষক program-টাকেই overwrite করে দিতে পারে।

তাই OS-এর একটা বিশেষ অংশ আছে যেটা বাকি সবার চেয়ে বেশি ক্ষমতা নিয়ে চলে। এর নাম kernel। Kernel হলো একটা program যেটা:

  • machine চালু হওয়ার সময় (এই প্রক্রিয়াকে বলে boot) সবার আগে RAM-এ load হয়, আর বন্ধ হওয়া পর্যন্ত সেখানেই থাকে;
  • hardware-এ সরাসরি হাত দেওয়ার অনুমতি একমাত্র এরই আছে;
  • বাকি সব program-এর হয়ে সিদ্ধান্ত নেয় — কে কখন CPU পাবে, কে কোন memory পাবে, কে কোন file খুলতে পারবে।

তোমার machine-এর kernel-এর নাম আর version জিজ্ঞেস করো:

uname -a

আমার Mac-এ output-এর ভেতরে আছে Darwin Kernel Version 25.6.0 ... xnu-12377... — macOS-এর kernel-এর নাম XNU। Linux-এ দেখবে Linux আর একটা version নম্বর, যেমন 6.8.0। একটা মজার পরীক্ষা: docker run --rm alpine uname -r চালালে আমার Mac-এ এল 6.10.14-linuxkit — এটা Docker-এর নিজস্ব ছোট Linux VM-এর kernel। Container নিজের কোনো kernel আনে না, যে machine-এ চলে তারটাই ব্যবহার করে (Chapter 36)।

OS আর kernel কি একই জিনিস?

না। Kernel হলো core। "Operating system" বললে সাধারণত বোঝায় kernel এবং তার সাথে আসা দরকারি program আর library-র পুরো package — shell (zsh, bash), ls/cp-এর মতো command, system library, background service চালানোর manager, আর desktop থাকলে সেটাও। এরা সবাই সাধারণ program, kernel-এর বিশেষ ক্ষমতা এদের নেই।

ls /bin

এখানে যা দেখবে (ls, cp, zsh, ps…) সবই OS-এর অংশ, কিন্তু kernel-এর না — প্রতিটা disk-এ রাখা একটা সাধারণ program, তোমার node-এর মতোই।

COMMON MISCONCEPTION

"OS মানে desktop, window, icon।" না। Desktop environment আরেকটা program মাত্র। তুমি যে production server-এ deploy করো, সেখানে কোনো screen নেই, কোনো window নেই — অথচ kernel পুরোদমে কাজ করছে: process চালাচ্ছে, memory ভাগ করছে, network packet সামলাচ্ছে।

User mode আর kernel mode: পাহারাটা CPU নিজেই দেয়

Kernel-কে "বেশি ক্ষমতাবান" বললাম — কিন্তু ক্ষমতাটা আসে কোথা থেকে? শুধু software দিয়ে এটা হয় না। তোমার program-এর instruction গুলো CPU সরাসরি চালায়; kernel মাঝখানে বসে প্রতিটা instruction পরীক্ষা করে না। তোমার program যদি storage-কে সরাসরি command পাঠানোর instruction লিখে ফেলে, kernel জানতেই পারবে না।

তাই সমাধানটা বসানো হয়েছে hardware-এ, CPU-র ভেতরে। CPU সবসময় একটা নির্দিষ্ট mode-এ থাকে — CPU-র ভেতরের একটা অবস্থা, যেটা বলে এই মুহূর্তে যে code চলছে তাকে কতটা বিশ্বাস করা যায়। মূল mode দুইটা:

  • Kernel mode — সব instruction চালানো যায়, সব memory ছোঁয়া যায়। Kernel এই mode-এ চলে।
  • User mode — সীমিত। Hardware নিয়ন্ত্রণ করার instruction গুলো (এদের বলে privileged instruction) চালানো যায় না, আর শুধু সেই memory ছোঁয়া যায় যেটা kernel এই program-কে দিয়েছে। তোমার Node app, Chrome, VS Code — সবাই এই mode-এ চলে।

User mode-এ থাকা কোনো program privileged instruction চালাতে চাইলে, বা নিষিদ্ধ memory ছুঁতে চাইলে, CPU সেই instruction চালায়ই না। বরং সঙ্গে সঙ্গে থেমে kernel-কে ডেকে আনে, আর kernel সাধারণত ওই program-টাকে মেরে ফেলে। C বা C++ program-এ যে "segmentation fault" crash শোনা যায়, সেটা ঠিক এই ঘটনা।

এখান থেকে দুইটা শব্দ আসে যেগুলো পুরো বইয়ে বারবার পাবে: user space মানে user mode-এ চলা সব program আর তাদের memory; kernel space মানে kernel-এর code আর memory। (CPU কীভাবে এক mode থেকে আরেক mode-এ যায়, তার পুরো গল্প Chapter 31-এ।)

তোমার প্রতিটা program আসলে দুই mode-এর মধ্যে আসা-যাওয়া করে, আর OS হিসাব রাখে কোন mode-এ কতক্ষণ কাটল। time command সেই হিসাবটা দেখায়। নিচের দ্বিতীয় উদাহরণে fs.statSync একটা file-এর metadata (size, তারিখ ইত্যাদি) এনে দেয়:

# ১) শুধু হিসাব — kernel-এর কোনো সাহায্য লাগে না
time node -e "let s = 0; for (let i = 0; i < 1e9; i++) s += i;"

# ২) বিশ লাখ বার file-এর metadata চাওয়া
time node -e "const fs = require('fs'); for (let i = 0; i < 2e6; i++) fs.statSync('.');"

আমার Mac-এর zsh-এ output (bash-এ একই সংখ্যা user আর sys নামে আলাদা লাইনে আসে):

3.54s user 0.08s system 96% cpu 3.763 total
0.37s user 0.78s system 100% cpu 1.144 total

user হলো CPU user mode-এ তোমার program চালাতে কত সময় দিয়েছে। system হলো kernel mode-এ তোমার হয়ে কাজ করতে কত সময় দিয়েছে। প্রথমটায় প্রায় পুরোটাই user — loop-টা নিছক যোগ, kernel-এর কিছু করার নেই। দ্বিতীয়টায় system সময় user-এর দ্বিগুণ। কারণ file-এর metadata থাকে file system-এ, আর user mode থেকে সেখানে সরাসরি যাওয়ার কোনো উপায় নেই। তাহলে যায় কীভাবে? সেটাই পরের section।

System call: kernel-এর কাছে কাজ চাওয়ার একমাত্র দরজা

একটা ধাঁধা তৈরি হলো। তোমার app user mode-এ চলে, hardware ছুঁতে পারে না। অথচ fs.readFileSync দিব্যি file পড়ে ফেলে।

একটা সরল উপায় হতে পারত: program দরকার হলে নিজেই kernel mode-এ ঢুকে যাবে, কাজ সেরে বেরিয়ে আসবে। কিন্তু তাহলে যেকোনো program যখন খুশি kernel mode-এ ঢুকে যা খুশি করতে পারবে — পুরো পাহারাই অর্থহীন। দরকার এমন একটা দরজা যেটা দিয়ে ঢোকা যায়, কিন্তু ঢোকার পর নিয়ন্ত্রণ থাকে kernel-এর হাতে, program-এর হাতে না।

এই দরজার নাম system call, সংক্ষেপে syscall। একটা syscall এভাবে ঘটে:

  1. Program ঠিক করে সে kernel-এর কাছে কী চায়। Kernel-এর প্রতিটা সেবার একটা নম্বর আছে — "file খোলো", "file থেকে পড়ো", "network-এ পাঠাও"। Program সেই নম্বর আর দরকারি তথ্য (কোন file, কত byte) একটা নির্দিষ্ট জায়গায় রেখে দেয়।
  2. তারপর সে একটা বিশেষ CPU instruction চালায় — Intel/AMD-র x86-64 CPU-তে এর নাম syscall, ARM CPU-তে (যেমন Apple Silicon) svc। এই instruction CPU-কে kernel mode-এ নিয়ে যায়, এবং সোজা kernel-এর code-এর একটা নির্দিষ্ট শুরুর জায়গায় পাঠায় — যেটা kernel boot-এর সময় নিজে ঠিক করে রেখেছে। Program নিজে বাছতে পারে না kernel-এর কোন code-এ ঢুকবে।
  3. Kernel যাচাই করে: এই program-এর কি এই কাজের অনুমতি আছে? দেওয়া তথ্য কি বৈধ?
  4. সব ঠিক থাকলে kernel কাজটা করে। দরকার হলে hardware-এর সাথে কথা বলে driver-এর মাধ্যমে — driver হলো kernel-এর ভেতরের সেই code, যেটা একটা নির্দিষ্ট ধরনের hardware-এর ভাষা জানে (Chapter 2)।
  5. Result নিয়ে kernel CPU-কে আবার user mode-এ ফিরিয়ে দেয়, আর program ঠিক পরের instruction থেকে চলতে থাকে।

Node-এর fs.readFileSync, net.createServer, এমনকি console.log — সবাই শেষ পর্যন্ত ভেতরে এক বা একাধিক syscall করে। console.log-এর text terminal-এ পৌঁছায় write syscall দিয়ে।

EXPERIMENT (Linux / Docker)

strace হলো Linux-এর একটা tool, যেটা একটা program-এর প্রতিটা syscall ধরে ধরে print করে। macOS-এ এটা নেই, তাই Docker-এ একটা ছোট Linux container চালিয়ে দেখব। (Linux machine থাকলে Docker ছাড়াই সরাসরি চালাও; SYS_PTRACE অনুমতিটা container-এর ভেতরে strace চালাতে লাগে।)

docker run --rm -it --cap-add SYS_PTRACE node:22-alpine sh

# এখন তুমি container-এর ভেতরে (Linux)
apk add strace
echo '{"port":3000}' > config.json
strace -f -e trace=openat,statx,read,close node -e "require('fs').readFileSync('config.json')" 2>&1 | grep -A3 config.json

আমার output (লম্বা অংশ কেটে ছোট করা):

openat(AT_FDCWD, "config.json", O_RDONLY|O_LARGEFILE|O_CLOEXEC) = 17
statx(17, "", ..., {... stx_size=14, ...}) = 0
read(17, "{\"port\":3000}\n", 14) = 14
close(17)                               = 0

এক লাইনের readFileSync kernel-এর কাছে চারবার গেল। openat — "file-টা খোলো"; kernel একটা নম্বর ফেরত দিল, 17, আর এরপর থেকে এই নম্বর দিয়েই file-টাকে চেনা হলো (এই নম্বরের নাম file descriptor, Chapter 3-এ আসছে)। statx — "file কত বড়?" (১৪ byte)। read — "১৪ byte পড়ো"। close — "কাজ শেষ, বন্ধ করো"।

একই container-এ strace -c -f node -e "require('fs').readFileSync('config.json')" চালালে পুরো program-এর syscall গোনা হয়। আমার চালানোয় total এসেছিল ১,১৮৩টা — এক লাইনের script-এর জন্য! বেশিরভাগই Node নিজে চালু হওয়ার কাজ: memory চাওয়া, ভেতরের কাঠামো তৈরি করা। তোমার প্রতিটা "সাধারণ" কাজের নিচে kernel-এর সাথে এমন অবিরাম কথোপকথন চলছে।

Kernel যে সত্যিই যাচাই করে, সেটাও দেখে নাও। macOS-এ পুরো SSD-টা /dev/disk0 নামে একটা বিশেষ file হিসেবে দেখা যায়। সেটা সরাসরি খুলতে চাও:

node -e "require('fs').openSync('/dev/disk0', 'r')"

উত্তর আসবে Error: EPERM: operation not permitted, open '/dev/disk0'। Syscall-টা kernel পর্যন্ত পৌঁছেছিল, আর kernel অনুমতি যাচাই করে "না" বলে দিয়েছে। (Linux-এ একই পরীক্ষা /dev/sda বা /dev/nvme0n1 দিয়ে করো; সাধারণ user হিসেবে error আসবে EACCES।)

এতক্ষণ যা যা দেখলাম, এক ছবিতে:

নীল অংশটা user space: তোমার code আর Node.js runtime দুটোই user mode-এ চলে। Amber দাগটা system call boundary — এর নিচে নামার একমাত্র বৈধ পথ হলো system call, আর নিচে শুধু kernel-ই hardware-এর সাথে কথা বলে। ডানের লাল পথটা দেখাচ্ছে, user space থেকে সরাসরি hardware-এ যাওয়ার চেষ্টা CPU নিজেই আটকে দেয়।

MENTAL MODEL

User space-এর কোনো code hardware-এর দিকে নিজে এক পা-ও এগোতে পারে না। প্রতিটা file, প্রতিটা network packet, প্রতিটা নতুন memory — সব আসে system call দিয়ে, kernel-এর হাত ঘুরে। আর kernel প্রতিবার যাচাই করে তারপর কাজ করে।

একজন JS engineer হিসেবে এটা কেন জানা দরকার

কারণ তোমার app-এর অনেক রহস্যময় সমস্যার উত্তর এই boundary-তে লুকানো। কয়েকটা উদাহরণ, সামনে প্রতিটা বিস্তারিত আসবে:

  • একটা API slow, অথচ profiler-এ তোমার JS function গুলো দ্রুত দেখাচ্ছে। হয়তো সময় যাচ্ছে system time-এ — মানে অতিরিক্ত syscall-এ (Chapter 32)।
  • Server-এ হঠাৎ EMFILE: too many open files। Kernel প্রতিটা process-এর খোলা file-এর সংখ্যা সীমিত রাখে — এটা resource management-এর একটা সীমা, তোমার JS-এর bug না।
  • Container-এ app কোনো JS error ছাড়াই হঠাৎ মারা গেল। প্রায়ই দেখা যায় memory limit পার হয়েছিল আর kernel নিজে process-টাকে মেরেছে।

এসব সমস্যা তোমার JavaScript-এ দেখা যায় না, দেখা যায় OS layer-এ। এই বইয়ের বাকি অংশ সেই layer-টা খুলে দেখার গল্প।

CAN I EXPLAIN THIS?
  • OS না থাকলে যে তিনটা সমস্যা হতো, সেগুলো কী? OS-এর কোন কাজ (abstraction নাকি resource management) কোন সমস্যার সমাধান করে?
  • একই fs.writeFileSync code SSD আর USB drive দুটোতেই কীভাবে কাজ করে, যখন দুটো device-এর command-এর ভাষা আলাদা?
  • নিয়ম রক্ষার ক্ষমতা শুধু software-এ না রেখে CPU-র hardware-এ (user mode / kernel mode) রাখতে হলো কেন?
  • time-এর output-এ user আর system আলাদা করে দেখায় কেন? লুপে শুধু যোগ করা code আর বারবার fs.statSync করা code — কোনটায় system বেশি হবে, আর কেন?
  • System call-এর সময় program নিজে বাছতে পারে না kernel-এর কোন code-এ ঢুকবে। এই নিয়ম না থাকলে কী সমস্যা হতো?
