PART 1 · THE BIG PICTURE

Chapter 1 — Operating System কেন দরকার?

Hardware আর application-এর মাঝখানে একটা layer কেন লাগে, আর সেই layer-টা আসলে কী কী responsibility নেয়।

Problem-টা আগে বুঝি

Computer hardware মানে মূলত চারটা জিনিস — CPU (instruction execute করে), RAM (running data রাখে), storage (persistent data রাখে), আর network interface (বাইরের দুনিয়ার সাথে কথা বলে)। এগুলো ভয়ংকর রকমের "dumb"। CPU শুধু raw instruction চেনে, disk শুধু block number চেনে — "file" বলে কিছু চেনে না, network card শুধু raw packet পাঠাতে জানে।

অন্যদিকে application মানে তোমার লেখা code — যে চায় "এই file-টা পড়ো", "এই port-এ listen করো", "এই object-টা memory-তে রাখো"। এখন ভাবো, OS না থাকলে প্রতিটা application-কে নিজে নিজে disk-এর electronics-এর সাথে কথা বলতে হতো, নিজে RAM-এর কোন byte কার সেটা track করতে হতো, নিজে network card-এর driver লিখতে হতো।

তার উপর আরেকটা বড় সমস্যা — এক computer-এ একসাথে অনেকগুলো program চলে। Chrome, VS Code, node server, Spotify — সবাই একই CPU, একই RAM চায়। কে কখন CPU পাবে? কার data কোন RAM-এ থাকবে? একজন আরেকজনের memory-তে হাত দিলে কী হবে? এই ঝগড়া মেটানোর জন্য একজন referee লাগে।

MENTAL MODEL

Operating System = Resource Manager + Abstraction Layer। Resource manager হিসেবে ঠিক করে কে কখন CPU/RAM/disk/network পাবে। Abstraction layer হিসেবে dumb hardware-কে ঢেকে সুন্দর interface দেয় — raw disk block-এর বদলে file, raw packet-এর বদলে socket, raw physical memory-র বদলে virtual memory, raw CPU time-এর বদলে process।

Kernel, user space, kernel space

OS-এর core অংশটার নাম kernel। এটা একটা special program যেটা machine boot হওয়ার সময় load হয় এবং সবসময় memory-তে থাকে। Kernel-ই আসল resource manager — process schedule করা, memory ভাগ করা, filesystem চালানো, network stack চালানো, driver দিয়ে device-এর সাথে কথা বলা — সব kernel-এর কাজ।

CPU-তে hardware level-এ দুইটা privilege mode আছে (Chapter 31-এ deep dive করবো):

  • User mode / user space — তোমার application এখানে চলে। Restricted। Hardware-এ direct হাত দিতে পারে না, অন্য process-এর memory ছুঁতে পারে না।
  • Kernel mode / kernel space — kernel এখানে চলে। Full power। যেকোনো memory, যেকোনো device access করতে পারে।

তাহলে তোমার app file পড়ে কীভাবে? উত্তর: system call। Application kernel-কে অনুরোধ করে — "আমার হয়ে এই কাজটা করে দাও।" CPU controlled ভাবে kernel mode-এ ঢোকে, kernel কাজটা করে, তারপর result নিয়ে আবার user mode-এ ফেরত আসে। read(), write(), open(), socket() — এগুলো সব system call।

Application (তোমার code)
        ↓
Libraries / Runtime (libc, Node.js, JVM ...)
        ↓
━━━━━━ system call boundary ━━━━━━

পুরো বইয়ে এই ছবিটা বারবার ফিরে আসবে — নীল মানে user space, amber মানে kernel space।

একজন engineer-এর কেন এটা জানা দরকার

কারণ তোমার code-এর performance-এর বড় অংশ ঠিক হয় এই boundary-গুলোতে। একটা slow API-এর কারণ হতে পারে excessive system call, হতে পারে disk I/O, হতে পারে memory pressure — এগুলো তোমার JavaScript-এ দেখা যায় না, দেখা যায় OS layer-এ। Black box-টা খুললে debugging আর optimization দুটোই অন্য level-এ চলে যায়।

EXPERIMENT

Terminal-এ চালাও: uname -a — এটা তোমার kernel-এর নাম আর version দেখায় (macOS-এ Darwin, Linux-এ Linux)। তারপর ps aux | head -15 — এই মুহূর্তে চলা process-এর list। খেয়াল করো, তুমি কিছু run না করলেও কত process চলছে — এদের সবাইকে kernel-ই manage করছে।

  • Application hardware-এ direct হাত দিতে পারে না — তাহলে কাজ করায় কীভাবে?
  • System call এক কথায় কী?
