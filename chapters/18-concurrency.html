PART 5 · PROCESS MANAGEMENT

Chapter 18 — Concurrency

Shared state + একাধিক thread = software engineering-এর সবচেয়ে কুখ্যাত bug-দের জন্মভূমি।

Concurrency vs parallelism

দুটো আলাদা জিনিস, প্রায়ই গুলিয়ে যায়:

  • Concurrency: একাধিক কাজ overlapping সময়ে এগোচ্ছে — এক core-ও হতে পারে, context switch করে করে। Structure-এর ব্যাপার।
  • Parallelism: একাধিক কাজ আক্ষরিক একই মুহূর্তে চলছে — একাধিক core লাগবেই। Execution-এর ব্যাপার।

একজন waiter ১০টা টেবিল সামলাচ্ছে = concurrency। ১০ জন waiter = parallelism। Node.js event loop হলো এক waiter-এর master class; multi-core কাজে লাগানো মানে waiter বাড়ানো।

Race condition: কুখ্যাত counter++

দুই thread একই shared counter বাড়াচ্ছে। Source code-এ counter++ এক লাইন, কিন্তু CPU-র চোখে তিনটা আলাদা instruction:

1. LOAD   counter → register     (পড়ো)
2. ADD    register + 1           (বাড়াও)
3. STORE  register → counter     (লেখো)

এখন এই interleaving-টা দেখো (counter = 5 থেকে শুরু):

Thread A                    Thread B
LOAD  → 5
                            LOAD  → 5      ← A এখনো লেখেনি!
ADD   → 6
                            ADD   → 6
STORE → 6
                            STORE → 6      ← A-র কাজ মুছে গেল

দুইবার increment, কিন্তু ফলাফল 6 — 7 না।

এটাই race condition: ফলাফল নির্ভর করছে কে-কখন-চললো তার timing-এর উপর। ভয়ংকর দিকটা হলো — বেশিরভাগ সময় ঠিকঠাক চলে; হাজারে একবার ভুল হয়, সেটাও production-এ, load-এর সময়, আর reproduce করা প্রায় অসম্ভব।

রক্ষার অস্ত্র

যে code shared state ছোঁয়, সেই অংশটার নাম critical section। নিয়ম: এক সময়ে এক thread-ই সেখানে ঢুকবে (mutual exclusion)। Tools:

  • Mutex (lock): Critical section-এর দরজার তালা। ঢোকার আগে lock নাও, বেরিয়ে ছাড়ো; অন্যরা lock না পাওয়া পর্যন্ত block থাকে। সরল, সর্বাধিক ব্যবহৃত। বিপদ: দুই thread দুই lock ধরে পরস্পরেরটার জন্য বসে থাকলে deadlock — কেউই আর নড়ে না। (এর mathematical treatment-এ যাচ্ছি না; "lock নেওয়ার order সব জায়গায় এক রাখো" — এই practical নিয়মটাই বেশিরভাগ deadlock ঠেকায়।)
  • Semaphore: Counter-ওয়ালা তালা — "সর্বোচ্চ N জন একসাথে"। যেমন DB connection pool: ১০টা connection, ১১তম আবেদনকারী অপেক্ষা করবে।
  • Atomic operations: Hardware-এর দেওয়া বিশেষ instruction যা load-modify-store-কে একটা অবিভাজ্য ধাপে করে — ছোট কাজে (counter!) lock-এর চেয়ে সস্তা।
"JS-এ তো race condition নেই!" — সত্যি?

Memory-level race (উপরের counter++) single-threaded JS-এ হয় না, ঠিক। কিন্তু logical race দিব্যি হয়: দুইটা async request-ই আগে DB থেকে balance পড়লো, তারপর দুজনেই লিখলো — একই lost-update গল্প, শুধু interleaving-টা instruction level-এ না, await point-এ। Race-এর মূল কারণ thread না — shared mutable state + non-atomic read-modify-write। সেটা DB row-তেও হয়।
