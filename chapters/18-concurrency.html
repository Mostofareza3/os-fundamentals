PART 5 · PROCESS MANAGEMENT

Chapter 18 — Concurrency

একাধিক thread একই data ছুঁলে কী ভাঙে — race condition, atomic, lock, deadlock, semaphore — আর কেন single-threaded JS-ও এই রোগ থেকে মুক্ত না।

যা লাগবে: এক process-এর thread-রা একই memory ভাগ করে (Chapter 16); CPU memory ছোঁয় load আর store দিয়ে, আর হিসাব করে register-এ (Chapter 8); একাধিক core একই cache line-এ লিখলে hardware সেটাকে এক core থেকে আরেক core-এ চালাচালি করে (Chapter 13); আর Atomics.wait/notify দিয়ে thread ঘুমাতে-জাগাতে পারে (Chapter 17)। এই chapter-এর সব experiment Node-এর worker_threads আর SharedArrayBuffer দিয়ে — Chapter 16-এ দেখেছ, শুধু SharedArrayBuffer-এর memory-ই worker-রা সত্যিই ভাগ করে।

Concurrency বনাম parallelism

দুইটা শব্দ প্রায়ই গুলিয়ে যায়, অথচ সমস্যা আর সমাধান দুইটার আলাদা। Concurrency মানে একাধিক কাজ একই সময়-পরিসরে এগোচ্ছে — একটা core-এও সম্ভব, পালা করে (Chapter 15-এর scheduling timeline)। এটা কাজ সাজানোর ব্যাপার। Parallelism মানে একাধিক কাজ আক্ষরিক অর্থে একই মুহূর্তে চলছে — একাধিক core লাগবেই। এটা কাজ চালানোর ব্যাপার। একজন waiter দশটা টেবিল সামলাচ্ছে: concurrency। দশজন waiter: parallelism। এর বাস্তব রূপ তোমার Node-এই:

node -e "
const t = performance.now();
Promise.all(Array.from({ length: 1000 }, () => new Promise(r => setTimeout(r, 100))))
  .then(() => console.log('1000 waits of 100 ms each, one thread:', (performance.now() - t).toFixed(0), 'ms'));"

আমার Mac-এ: 103 ms। এক হাজারটা অপেক্ষা, প্রতিটা ১০০ ms, একটাই thread — তবু মোট ১০৩ ms, কারণ অপেক্ষা গুলো একসাথে চলছে (concurrency), কিন্তু কোনো মুহূর্তেই একাধিক JS instruction চলছে না (parallelism নেই)। উল্টো দিকে Chapter 14-এর parallel.js ছিল parallelism: বারোটা core-এ একই মুহূর্তে হিসাব।

Race condition: কুখ্যাত counter++

Source code-এ counter++ একটা লাইন। কিন্তু Chapter 8-এর ভাষায় CPU-র কাছে এটা তিন ধাপ: memory থেকে load করে register-এ আনো, register-এ ১ যোগ করো, register থেকে memory-তে store করো। দুইটা thread যদি একই counter-এ একসাথে এটা করে, আর এক thread-এর load আর store-এর মাঝখানে অন্যজনের load ঢুকে পড়ে, তাহলে একজনের কাজ মুছে যায়:

দুই thread-এর তিন ধাপ একে অন্যের ফাঁকে ঢুকে গেছে। B ধাপ ২-এ ৫ পড়েছে — A তখনো লেখেনি। দুজনেই ৬ হিসাব করল, দুজনেই ৬ লিখল। দুইবার বাড়ানো হলো, ফল একবারের।

এমন bug-এর নাম race condition: ফলাফল নির্ভর করছে কে কখন চলল তার উপর। শর্ত দুইটা — একাধিক thread-এর মধ্যে ভাগাভাগি করা, বদলানো যায় এমন data (shared mutable state), আর সেই data-র উপর পড়ো-বদলাও-লেখো ধরনের এমন কাজ যেটা মাঝপথে ভাঙা যায়। নিজে ঘটাও:

EXPERIMENT — race.js

চারটা worker, প্রত্যেকে একই shared counter ১০ লাখবার বাড়ায় — তিনভাবে: সাধারণ ++, Atomics.add, আর একটা নিজের বানানো lock দিয়ে (দুইটাই নিচের section-এ):

const { Worker, isMainThread, workerData } = require('worker_threads');
const WORKERS = 4, N = 1_000_000;

// একটা খুব সরল lock: 0 = খোলা, 1 = কেউ ধরে আছে
function lock(m)   { while (Atomics.compareExchange(m, 0, 0, 1) !== 0) Atomics.wait(m, 0, 1); }
function unlock(m) { Atomics.store(m, 0, 0); Atomics.notify(m, 0, 1); }

if (isMainThread) {
  const run = mode => new Promise(resolve => {
    const counter = new Int32Array(new SharedArrayBuffer(4));
    const mutex = new Int32Array(new SharedArrayBuffer(4));
    const t = performance.now();
    let done = 0;
    for (let w = 0; w < WORKERS; w++) {
      new Worker(__filename, { workerData: { counter, mutex, mode } }).on('exit', () => {
        if (++done === WORKERS) resolve([counter[0], performance.now() - t]);
      });
    }
  });
  (async () => {
    for (const mode of ['plain', 'atomic', 'lock']) {
      const [value, ms] = await run(mode);
      console.log(`${mode.padEnd(6)} counter = ${String(value).padStart(7)}  (expected ${WORKERS * N})  ${ms.toFixed(0)} ms`);
    }
  })();
} else {
  const { counter, mutex, mode } = workerData;
  for (let i = 0; i < N; i++) {
    if (mode === 'plain') counter[0]++;                         // পড়ো, বাড়াও, লেখো — তিন ধাপ
    else if (mode === 'atomic') Atomics.add(counter, 0, 1);     // এক অবিভাজ্য ধাপ
    else { lock(mutex); counter[0]++; unlock(mutex); }          // তালা দিয়ে একজন একজন করে
  }
}

plain  counter = 1103127  (expected 4000000)  19 ms
atomic counter = 4000000  (expected 4000000)  117 ms
lock   counter = 4000000  (expected 4000000)  426 ms

চল্লিশ লাখ বাড়ানোর মধ্যে প্রায় ত্রিশ লাখ হারিয়ে গেছে। (সন্দেহ হতে পারে V8-এর optimizer মানটা register-এ ধরে রাখছে কি না — node --jitless race.js দিয়ে শুধু interpreter-এ চালালেও আমার চালানোয় এসেছে 1254776। আর WORKERS = 1 করলে ঠিক 1000000 — একা থাকলে race নেই।) সবচেয়ে ভয়ংকর দিক হলো: কম চাপে, কম thread-এ, ছোট loop-এ এই bug প্রায়ই চোখেই পড়ে না। Test pass করে, production-এর চাপের দিনে হঠাৎ হিসাব গরমিল — আর আবার ঘটানো প্রায় অসম্ভব।

Atomic operation: ভাঙা যায় না এমন এক ধাপ

সমস্যার মূল ছিল তিন ধাপের মাঝের ফাঁক। Hardware এর জন্য বিশেষ instruction দেয়, যেটা পড়া-বদলানো-লেখা একসাথে এমনভাবে করে যে মাঝখানে কেউ ঢুকতে পারে না — atomic operation (ARM-এ যেমন LDADD, x86-এ LOCK XADD)। কাজটা হয় Chapter 13-এর cache coherence দিয়ে: core-টা cache line-এর একক মালিকানা নিয়ে তিন ধাপ শেষ না করা পর্যন্ত ছাড়ে না। JS-এ এটা Atomics.add, Atomics.compareExchange ইত্যাদি। ওপরে atomic ঠিক ৪০,০০,০০০ দিল।

দামটাও লক্ষ করো: ১৯ ms থেকে ১১৭ ms। প্রতিটা atomic-এ line-টা core থেকে core-এ ছোটে (Chapter 13-এর false sharing-এর মতোই, এবার সত্যিকারের sharing)। নির্ভুলতার দাম আছে — আর এক counter-এ হাজার thread ঠেলাঠেলি করলে সেই দাম বাড়ে। (Chapter 13-এর সমাধান এখানেও খাটে: প্রতিটা thread নিজের আলাদা counter বাড়াক, শেষে যোগ।)

Critical section আর mutex

Atomic instruction একটা সংখ্যার উপর এক ধাপের কাজ পারে। কিন্তু অনেক কাজ এর চেয়ে বড়: "balance দেখো, যথেষ্ট থাকলে কমাও আর log-এ লেখো" — কয়েকটা data, কয়েকটা ধাপ, মাঝে সিদ্ধান্ত। এমন কোনো একক instruction নেই। দরকার এমন ব্যবস্থা যাতে এই পুরো অংশে এক সময়ে একটাই thread থাকে। Shared data ছোঁয়া code-এর এই অংশের নাম critical section, আর "এক সময়ে একজন" নিয়মের নাম mutual exclusion। এটা নিশ্চিত করার হাতিয়ার mutex (lock): ঢোকার আগে lock নাও, বেরিয়ে ছাড়ো; অন্য কেউ ধরে থাকলে ছাড়া পর্যন্ত অপেক্ষা করো।

ওপরের race.js-এর lock-টা একটা আসল mutex-এর কঙ্কাল: Atomics.compareExchange(m, 0, 0, 1) — "মান যদি ০ (খোলা) হয়, তবে ১ (ধরা) বানাও", এক অবিভাজ্য ধাপে; না পারলে Atomics.wait দিয়ে ঘুম (Chapter 17-এর futex-এর মতো)। ছাড়ার সময় ০ লিখে একজন অপেক্ষমাণকে জাগাও। ফল নির্ভুল, কিন্তু ৪২৬ ms — atomic-এর চারগুণ, কারণ প্রতিবার lock-এর জন্য লড়াই, অনেক সময় ঘুম আর জাগা। শিক্ষা: critical section যত ছোট সম্ভব রাখো, আর একটা সংখ্যা বাড়ানোর মতো কাজে lock না, atomic।

Deadlock: সবাই সবার অপেক্ষায়

একাধিক lock এলে নতুন বিপদ। Thread 1 lock A ধরে আছে আর lock B চায়; ঠিক তখন Thread 2 lock B ধরে আছে আর lock A চায়। কেউ নিজেরটা ছাড়বে না যতক্ষণ না অন্যেরটা পায় — দুজনেই চিরকাল ঘুমিয়ে। এর নাম deadlock।

EXPERIMENT — deadlock.js
const { Worker, isMainThread, workerData } = require('worker_threads');

function lock(m)   { while (Atomics.compareExchange(m, 0, 0, 1) !== 0) Atomics.wait(m, 0, 1); }
function unlock(m) { Atomics.store(m, 0, 0); Atomics.notify(m, 0, 1); }
const pause = ms => Atomics.wait(new Int32Array(new SharedArrayBuffer(4)), 0, 0, ms);

if (isMainThread) {
  const sameOrder = process.argv[2] === 'same';
  const A = new Int32Array(new SharedArrayBuffer(4));   // lock A
  const B = new Int32Array(new SharedArrayBuffer(4));   // lock B
  let finished = 0, gaveUp = false;
  const workers = [
    new Worker(__filename, { workerData: { first: A, second: B, name: 'T1' } }),
    new Worker(__filename, { workerData: sameOrder ? { first: A, second: B, name: 'T2' } : { first: B, second: A, name: 'T2' } }),
  ];
  workers.forEach(w => w.on('exit', () => { if (++finished === 2 && !gaveUp) console.log('both finished'); }));
  setTimeout(() => {
    if (finished < 2) { gaveUp = true; console.log('DEADLOCK: after 2 s nobody has finished'); workers.forEach(w => w.terminate()); }
  }, 2000);
} else {
  const { first, second, name } = workerData;
  lock(first);  console.log(name, 'holds its first lock');
  pause(100);                                         // একটু দেরি — যাতে অন্যজনও নিজের প্রথম lock ধরে ফেলে
  lock(second); console.log(name, 'got its second lock');
  unlock(second); unlock(first);
}

node deadlock.js opposite (T1 নেয় A তারপর B, T2 নেয় B তারপর A):

T1 holds its first lock
T2 holds its first lock
DEADLOCK: after 2 s nobody has finished

node deadlock.js same (দুজনেই আগে A, তারপর B): চারটা "holds/got" লাইন, তারপর both finished।

নীল তীর: কে কোন lock ধরে আছে। লাল dashed তীর: কে কোনটার অপেক্ষায়। অপেক্ষার তীর গুলো একটা বৃত্ত বানিয়েছে — T1 দাঁড়িয়ে T2-র জন্য, T2 দাঁড়িয়ে T1-এর জন্য। সবাই একই ক্রমে lock নিলে এমন বৃত্ত তৈরিই হতে পারে না।

Deadlock-এর তত্ত্ব অনেক গভীর, কিন্তু বাস্তবে সবচেয়ে কাজের নিয়ম একটাই: সব জায়গায় lock নেওয়ার ক্রম এক রাখো। যদি প্রতিটা thread সবসময় আগে A, পরে B নেয়, তাহলে "B ধরে A-র অপেক্ষা" অবস্থা কখনো আসবেই না — same version যেমন দেখাল। Database-এ দুইটা transaction দুইটা row উল্টো ক্রমে update করলেও ঠিক এই জিনিস ঘটে; database তখন একটা transaction-কে বাতিল করে deadlock ভাঙে, আর তুমি error পাও।

Semaphore: সর্বোচ্চ N জন

কখনো "এক সময়ে একজন" না, দরকার "এক সময়ে সর্বোচ্চ N জন" — ধরো database-এর মাত্র ৩টা connection, অথচ একসাথে ১০টা request এসেছে। চতুর্থ request-কে কেউ একজন connection ফেরত না দেওয়া পর্যন্ত অপেক্ষা করতে হবে। এর হাতিয়ার semaphore: একটা counter-ওয়ালা lock — ঢোকার সময় counter এক কমাও (শূন্য হলে অপেক্ষা), বেরোনোর সময় এক বাড়াও। Mutex আসলে N = ১-এর semaphore। একই ধারণা async JS-এও কাজে লাগে — একসাথে কয়টা query বা HTTP call চলবে, সেটা বাঁধতে:

EXPERIMENT — semaphore.js
// Semaphore: একসাথে সর্বোচ্চ N জন ঢুকতে পারবে — যেমন DB connection pool
function semaphore(n) {
  const waiting = [];
  return {
    async acquire() { if (n > 0) { n--; return; } await new Promise(r => waiting.push(r)); },
    release()       { const next = waiting.shift(); if (next) next(); else n++; },
  };
}
const sem = semaphore(3);
const sleep = ms => new Promise(r => setTimeout(r, ms));
let inFlight = 0, maxInFlight = 0;

async function query(i) {
  await sem.acquire();
  inFlight++; maxInFlight = Math.max(maxInFlight, inFlight);
  try { await sleep(100); }                  // একটা ১০০ ms-এর query
  finally { inFlight--; sem.release(); }
}

(async () => {
  const t = performance.now();
  await Promise.all(Array.from({ length: 10 }, (_, i) => query(i)));
  console.log(`10 queries, max 3 at once → ${(performance.now() - t).toFixed(0)} ms, max in flight = ${maxInFlight}`);
})();

আমার Mac-এ: 10 queries, max 3 at once → 404 ms, max in flight = 3 — দশটা query তিন-তিন-তিন-একের চার দফায়, প্রতিটা ১০০ ms।

"JS-এ তো race condition নেই!" — সত্যি?

ওপরের counter++-এর মতো memory-র স্তরের race তোমার সাধারণ Node code-এ হয় না, কারণ তোমার সব JS একটা thread-এ চলে — এক function চলার মাঝখানে আরেকটা ঢুকতে পারে না। কিন্তু একটা জায়গায় ঢুকতে পারে: await। প্রতিটা await-এ তোমার function থেমে যায়, আর event loop তখন অন্য request-এর code চালায়। পড়া আর লেখার মাঝখানে যদি একটা await থাকে, সেটাই ঠিক ওপরের LOAD আর STORE-এর মাঝের ফাঁক:

EXPERIMENT — withdraw.js
// একটা নকল database: পড়া আর লেখায় কিছুটা সময় লাগে (network-এর মতো)
const db = { balance: 1000 };
const sleep = ms => new Promise(r => setTimeout(r, ms));
async function getBalance()     { await sleep(10); return db.balance; }
async function setBalance(v)    { await sleep(10); db.balance = v; }

async function withdraw(amount) {
  const balance = await getBalance();        // ১) পড়ো
  if (balance < amount) throw new Error('insufficient funds');
  await setBalance(balance - amount);        // ২) লেখো — মাঝখানে অন্য request ঢুকে পড়তে পারে
}

  await Promise.all([withdraw(700), withdraw(700)]);   // একই মুহূর্তে দুইটা request

  return run;

FOR UPDATE দিয়ে row-টা lock করে। মানে atomic operation আর lock — শুধু এক স্তর উপরে।

COMMON MISCONCEPTION

"Test-এ ঠিক ফল আসছে, মানে race নেই।" Race condition timing-নির্ভর: কম চাপে, কম thread-এ, ছোট loop-এ প্রায় কখনো দেখা দেয় না — race.js-এ একটা worker দিলে প্রতিবার নির্ভুল। Race খুঁজতে হয় code পড়ে: কোথায় ভাগাভাগি করা data, আর কোথায় তার উপর পড়া আর লেখার মাঝে একটা ফাঁক (আরেকটা thread, বা একটা await)?

MENTAL MODEL

Race = ভাগাভাগি করা data + মাঝপথে ভাঙা যায় এমন পড়ো-বদলাও-লেখো। প্রতিকারের সিঁড়ি: আগে ভাগাভাগিই কমাও (প্রতিটা thread নিজের data); একটা সংখ্যা হলে atomic; বড় কাজ হলে mutex দিয়ে ছোট্ট critical section; একাধিক lock হলে সবসময় একই ক্রম; সংখ্যা বাঁধতে semaphore। আর single-threaded JS-এ প্রতিটা await একটা সম্ভাব্য ফাঁক — একাধিক instance থাকলে atomic-তা database-কে দাও।
