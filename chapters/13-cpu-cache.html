PART 4 · CPU

Chapter 13 — CPU Cache

Memory wall-এর জবাব: cache-এর স্তরগুলো নিজের machine-এ মেপে দেখা, locality কেন সব ঠিক করে দেয়, data সাজানোর ধরন কীভাবে গতি বদলায়, আর একাধিক core একই line নিয়ে টানাটানি করলে কী হয়।

Chapter 8-এর কথা এক লাইনে: CPU-র গা ঘেঁষে থাকা ছোট দ্রুত memory — cache — সম্প্রতি ব্যবহৃত data রাখে; পাওয়া গেলে hit, না পেলে miss; আর data আসে-যায় পুরো cache line ধরে (Apple Silicon-এ ১২৮ byte, Intel/AMD-এ ৬৪)। সেই chapter একটা প্রশ্ন ঝুলিয়ে রেখেছিল: প্রতিটা core-এর নিজের cache-এ একই line-এর আলাদা copy থাকলে, একজন লিখলে অন্যজন জানবে কীভাবে? এই chapter-এ তার উত্তর, আর তার আগে cache-কে পুরো মাপজোখ করে দেখা।

এক স্তর না, কয়েক স্তর কেন

একটা বিশাল দ্রুত cache বানালেই তো হতো? হয় না, কারণ physics। SRAM যত বড়, তার ভেতরে খুঁজতে তত বেশি circuit পেরোতে হয়, তারও লম্বা হয় — আর signal-এর যাতায়াতে সময় লাগে। বড় cache তাই অনিবার্যভাবে ধীর, আর বেশি জায়গা ও বিদ্যুৎ খায়। সমাধান হলো সিঁড়ি: core-এর একদম পাশে খুব ছোট আর খুব দ্রুত স্তর, তার পেছনে একটু বড় আর একটু ধীর, তার পেছনে আরও বড়। প্রতিটা স্তর আগের স্তরের বেশিরভাগ miss ধরে ফেলে, তাই RAM পর্যন্ত যেতে হয় কম।

আমার M4 Pro-তে: প্রতিটা performance core-এর নিজস্ব L1 data cache ১২৮ KB (efficiency core-এর ৬৪ KB); আটটা performance core মিলে একটা ১৬ MB-র L2 ভাগ করে (চারটা efficiency core-এর নিজেদের ৪ MB)। তার পেছনে পুরো chip-এর একটা SLC (system level cache) — Apple যার মাপ প্রকাশ করে না — তারপর RAM। Intel/AMD-এ সাধারণত L1 আর L2 core-প্রতি, আর সবার ভাগের একটা বড় L3।

নিজের machine-এর সিঁড়ি মাপো

Chapter 7-এর pointer chase মনে করো — এলোমেলো একটা শিকল, যেখানে প্রতিটা ধাপ আগের ফলাফলের উপর নির্ভর করে, তাই প্রতিটা access-এর পুরো দেরি মাপা যায়। এবার শিকলের মাপ ছোট থেকে বড় করতে থাকো। যতক্ষণ পুরো শিকলটা কোনো একটা স্তরে আঁটে, access-এর দাম সেই স্তরের দাম; আঁটা বন্ধ হলেই দাম লাফিয়ে পরের স্তরে।

EXPERIMENT — staircase.js (কয়েক মিনিট লাগে)
function chase(bytes, steps) {
  const n = bytes / 4;
  const next = new Int32Array(n), order = new Int32Array(n);
  for (let i = 0; i < n; i++) order[i] = i;
  for (let i = n - 1; i > 0; i--) {                        // এলোমেলো ক্রম
    const j = Math.floor(Math.random() * (i + 1));
    const t = order[i]; order[i] = order[j]; order[j] = t;
  }
  for (let i = 0; i < n; i++) next[order[i]] = order[(i + 1) % n];
  let p = 0;
  for (let i = 0; i < 1_000_000; i++) p = next[p];          // গরম করো
  const t = process.hrtime.bigint();
  for (let i = 0; i < steps; i++) p = next[p];
  return Number(process.hrtime.bigint() - t) / steps;
}
const sizesKB = [8, 16, 32, 64, 96, 128, 192, 256, 512, 1024, 2048, 4096, 8192,
                 12288, 16384, 24576, 32768, 49152, 65536, 131072, 262144, 524288, 1048576];
for (const kb of sizesKB) console.log(kb, 'KB', chase(kb * 1024, 20_000_000).toFixed(2), 'ns');

আমার Mac-এ দুইবার চালিয়ে গড় করা ফল নিচের chart-এ।

দুই অক্ষই log scale। ১২৮ KB পর্যন্ত প্রতি access ~১.৩ ns (L1); ১৯২ KB-তেই লাফ — ঠিক L1-এর মাপ পেরোনোর জায়গায়। ১৬ MB পর্যন্ত ৩–১২ ns (L2); ২৪ MB-তে আবার লাফ, তারপর SLC আর TLB miss (Chapter 10) পেরিয়ে ১ GB-তে ~১২১ ns (RAM)। বিন্দুর উপর mouse রাখলে সংখ্যা দেখায়।

ছবিটা থেকে সবচেয়ে বড় শিক্ষা: hardware-এর মাপ গুলো software-এর সময়ের মধ্যে দেখা যায়। sysctl বলেছিল L1 ১২৮ KB — আর ঠিক ১২৮ KB থেকে ১৯২ KB-তে যাওয়ার সময় দাম আড়াই গুণ। L2 ১৬ MB — আর ১৬ MB থেকে ২৪ MB-তে গিয়ে দাম প্রায় দ্বিগুণ। তোমার data যদি এক সিঁড়ি নিচে নামিয়ে আনতে পারো (ছোট করে, বা ঘন করে), সেটা প্রায়ই কোনো algorithm বদলানোর চেয়ে বড় জয়।

Locality: cache কেন আদৌ কাজ করে

Cache শুধু অতীত মনে রাখে; ভবিষ্যৎ জানে না। তবু কাজ করে, কারণ বাস্তব program-দের আচরণে দুইটা অভ্যাস প্রায় সবসময় থাকে, যাদের একসাথে বলে locality:

  • Temporal locality — যা এইমাত্র ছুঁয়েছ, শিগগিরই আবার ছোঁবে। Loop-এর counter, বারবার ডাকা function-এর code, একটা hot object। ওপরের chart-এর বাঁ দিক এটাই: ছোট শিকল বারবার ঘোরা হচ্ছে, তাই সব সময় L1-এ।
  • Spatial locality — যা ছুঁয়েছ, তার পাশেরটাও ছোঁবে। Array-র পরের element, object-এর পরের field। Cache line এই অভ্যাসের পুরস্কার: একটা miss-এ ১২৮ byte আসে, পরের অনেকগুলো access ফ্রি।

একই data, একই হিসাব, শুধু পড়ার ক্রম বদলে দেখো locality কতটা গুরুত্বপূর্ণ। একটা বড় 2D grid memory-তে থাকে সারির পর সারি পাশাপাশি — [row][col] আসলে grid[row * N + col]:

EXPERIMENT — grid2d.js
const N = 4096;                                   // 4096 × 4096 টা সংখ্যা = 128 MB
const grid = new Float64Array(N * N).fill(1);     // সারির পর সারি, পাশাপাশি রাখা: [row][col] = grid[row * N + col]

function byRows() {                               // এক সারি শেষ করে পরের সারি
  let s = 0;
  for (let r = 0; r < N; r++) for (let c = 0; c < N; c++) s += grid[r * N + c];
  return s;
}
function byColumns() {                            // এক কলাম শেষ করে পরের কলাম
  let s = 0;
  for (let c = 0; c < N; c++) for (let r = 0; r < N; r++) s += grid[r * N + c];
  return s;
}
for (const [label, fn] of [['row by row      ', byRows], ['column by column', byColumns]]) {
  fn();
  const t = performance.now();
  const s = fn();
  console.log(label, (performance.now() - t).toFixed(0).padStart(5), 'ms   sum =', s);
}

আমার Mac-এ: row by row 11 ms, column by column 55 ms — একই যোগফল (16777216), পাঁচ গুণ পার্থক্য।

সারি ধরে পড়লে address গুলো পরপর — প্রতিটা ১২৮ byte-এর line থেকে ১৬টা সংখ্যা কাজে লাগে, আর prefetcher (Chapter 8) পরের line আগেই আনে। কলাম ধরে পড়লে প্রতিটা access আগেরটার চেয়ে ৪০৯৬ × ৮ = ৩২ KB দূরে: প্রতিবার নতুন line, প্রতি দুই access-এ নতুন page (TLB-র উপর চাপ), আর line থেকে মাত্র একটা সংখ্যা কাজে লাগে; পরের কলামে ফিরে আসার আগেই সেই line cache থেকে বেরিয়ে গেছে। পার্থক্য ১৬ গুণ না হয়ে পাঁচ গুণ, কারণ prefetcher নিয়মিত লাফের ধরনও কিছুটা ধরতে পারে।

Data layout: তোমার code-এর সাজসজ্জা

JS-এ আমরা data structure বাছি API দেখে — array নাকি Map, object নাকি class। কিন্তু cache-এর চোখে প্রশ্ন একটাই: যে byte গুলো একসাথে লাগবে, সেগুলো কি memory-তে একসাথে আছে?

Chapter 6-এর locality.js এখন cache line-এর ভাষায় পড়া যায়। একই পঞ্চাশ লাখ সংখ্যা যোগ: Float64Array-তে ২.৮ ms, সৃষ্টির ক্রমে রাখা { v: 1 } object-এ ৪.০ ms, এলোমেলো ক্রমের object-এ ৩০ ms। Float64Array-তে সংখ্যা গুলো ঠাসাঠাসি — ১২৮ byte-এর একটা line-এ ১৬টা। প্রতিটা object-এর নিজের একটা header থাকে (V8-এর বানানো, object-এর ধরন বোঝাতে) — ফলে একটা line-এ গোটা কয়েক object, আর যে ৮ byte দরকার তার পাশে অনেক byte অদরকারি। আর এলোমেলো ক্রমে প্রতিটা object আলাদা line-এ, আলাদা page-এ — কার্যত Chapter 7-এর pointer chase।

একই কারণে linked list প্রায় সবসময় array-র কাছে হারে, এমনকি যেখানে Big-O দুটোর সমান: list-এর পরের node কোথায় আছে সেটা আগের node পড়ার আগে জানা যায় না, আর node গুলো heap-এ ছড়ানো। Game engine আর database-এর মতো গতি-সচেতন software তাই প্রায়ই "array of objects" বাদ দিয়ে "প্রতিটা field-এর জন্য আলাদা typed array" সাজায় — যে field নিয়ে loop চলছে, শুধু সেটাই cache-এ আসে।

একাধিক core, একই line: coherence আর false sharing

এবার Chapter 8-এর ঝুলে থাকা প্রশ্ন। Core 0 একটা মান লিখল — write-back-এর কারণে নতুন মানটা আপাতত শুধু core 0-এর L1-এ। Core 1-এর L1-এ সেই line-এর একটা পুরনো copy আছে। Core 1 এখন পড়লে পুরনো মান পাবে, আর দুই thread দুই রকম বাস্তবতা দেখবে। কোনো multi-threaded program তাহলে নির্ভরযোগ্যভাবে চলতেই পারত না।

তাই hardware একটা নিয়ম মেনে চলে, যার নাম cache coherence। মোটা দাগে: একটা line একই সময়ে অনেক core-এর কাছে "শুধু পড়ার" copy হিসেবে থাকতে পারে, কিন্তু কেউ লিখতে চাইলে তাকে আগে line-টার একক মালিকানা নিতে হয় — বাকি সব core-এর copy বাতিল (invalidate) করে। অন্য কেউ পরে পড়তে চাইলে মালিকের কাছ থেকে নতুন মান আনিয়ে নেয়। (প্রচলিত protocol-এর নাম MESI — প্রতিটা line-এর চার অবস্থা: Modified, Exclusive, Shared, Invalid।) এটা নিখুঁতভাবে কাজ করে, কিন্তু দাম আছে: দুইটা core যদি পালাক্রমে একই line-এ লিখতে থাকে, line-টা core থেকে core-এ ছোটাছুটি করে, আর প্রতিবার কয়েক দশ ns।

ফাঁদটা হলো: coherence কাজ করে line ধরে, variable ধরে না। দুইটা thread যদি সম্পূর্ণ আলাদা দুইটা variable বদলায়, কিন্তু variable দুইটা ঘটনাক্রমে একই ১২৮ byte-এর line-এ পড়ে — hardware-এর চোখে তারা একই জিনিস নিয়ে কাড়াকাড়ি করছে। এর নাম false sharing।

EXPERIMENT — falseshare.js

Node-এর worker_threads আলাদা thread-এ JS চালায় (Chapter 16); SharedArrayBuffer এমন memory যেটা সব worker একসাথে দেখে; Atomics.add একটা মান নিরাপদে বাড়ায়, যাতে একসাথে দুইজন বাড়ালেও কিছু হারায় না (Chapter 18)। চারটা worker, প্রত্যেকে শুধু নিজের counter ২ কোটি বার বাড়ায়:

const { Worker, isMainThread, workerData } = require('worker_threads');
const THREADS = 4, N = 20_000_000;

if (isMainThread) {
  // প্রতিটা worker নিজের counter বাড়ায়; কেউ কারও counter ছোঁয় না।
  // শুধু বদলাচ্ছি counter গুলো memory-তে কত দূরে দূরে বসানো।
  const run = gapBytes => new Promise(resolve => {
    const shared = new SharedArrayBuffer(THREADS * gapBytes);
    const t = performance.now();
    let done = 0;
    for (let w = 0; w < THREADS; w++) {
      new Worker(__filename, { workerData: { shared, index: (w * gapBytes) / 4 } })
        .on('exit', () => { if (++done === THREADS) resolve(performance.now() - t); });
    }
  });
  (async () => {
    console.log('4 counters side by side  :', (await run(4)).toFixed(0), 'ms');    // সবাই একই cache line-এ
    console.log('4 counters 128 bytes apart:', (await run(128)).toFixed(0), 'ms'); // প্রত্যেকে নিজের line-এ
  })();
} else {
  const counters = new Int32Array(workerData.shared);
  const i = workerData.index;
  for (let k = 0; k < N; k++) Atomics.add(counters, i, 1);
}

আমার Mac-এ: side by side: 1772 ms, 128 bytes apart: 107 ms। (x86-এ ৬৪ byte দূরত্বই যথেষ্ট।)

বাঁয়ে চারটা counter একই line-এ: core 0 শুধু c0 লেখে, core 1 শুধু c1 — তবু প্রতিটা লেখার আগে পুরো line-টা অন্য core-এর কাছ থেকে কেড়ে আনতে হয়। ডানে প্রতিটা counter-এর পরে ফাঁকা জায়গা, তাই প্রত্যেকে নিজের line-এর মালিক হয়ে বসে থাকে। (সরল রাখতে দুইটা core দেখানো; পরীক্ষায় চারটা।)

চারটা worker, কেউ কারও data ছোঁয় না — তবু পাশাপাশি রাখায় ১৬ গুণ ধীর। সমাধান দুইটা: প্রতিটা thread-এর data-র মাঝে line-এর মাপের ফাঁকা রাখা (ওপরে যেমন করলাম), অথবা প্রতিটা thread নিজের local variable-এ হিসাব করে শেষে একবার shared জায়গায় যোগ করা। Java-র LongAdder আর Linux kernel-এর per-CPU counter ঠিক এই দ্বিতীয় কৌশল।

COMMON MISCONCEPTION

"Big-O ঠিক থাকলেই হলো; বাকিটা micro-optimization।" এই chapter-এর প্রতিটা experiment-এ দুইটা পক্ষ ছিল হুবহু একই Big-O-র — একই সংখ্যক যোগ, একই সংখ্যক access। পার্থক্য এসেছে ৫ গুণ (grid2d), ১০ গুণ (locality.js), ১৬ গুণ (falseshare), আর staircase-এ ৯০ গুণ। Big-O বলে কাজ কত দ্রুত বাড়ে; কাজের প্রতিটা ধাপ কত দামি, সেটা বলে memory-র কোন স্তরে তুমি আছ।

MENTAL MODEL

Cache হলো একটা সিঁড়ি — L1 (~১ ns) → L2 (কয়েক ns) → SLC/L3 → RAM (~১২০ ns) — আর তোমার data কোন ধাপে দাঁড়িয়ে, সেটা ঠিক করে তার মাপ আর তুমি কীভাবে ছোঁও। Locality (একই জিনিস বারবার, পাশের জিনিস পরপর) cache-কে কাজে লাগায়; ছড়ানো data আর এলোমেলো ক্রম তাকে অকেজো করে। আর একাধিক core-এ মনে রাখো: hardware মালিকানা দেয় line ধরে, variable ধরে না।

CAN I EXPLAIN THIS?
  • একটা বড় দ্রুত cache না বানিয়ে কয়েক স্তরের cache কেন? তোমার staircase-এ ১২৮ KB আর ১৬ MB-এর কাছে দাম লাফায় কেন?
  • Temporal আর spatial locality কী — নিজের code থেকে একটা করে উদাহরণ দাও। grid2d.js-এ কলাম ধরে পড়া পাঁচ গুণ ধীর কেন?
  • একই সংখ্যা Float64Array-তে আর { v } object-এর array-তে রাখলে cache line-এর হিসাবে পার্থক্য কী? Linked list কেন array-র কাছে হারে?
  • Cache coherence কেন লাগে? একটা core লিখতে চাইলে অন্য core-দের copy-র কী হয়?
  • falseshare.js-এ কোনো worker অন্যের counter ছোঁয় না, তবু ১৬ গুণ ধীর কেন? দুইটা সমাধান কী?
