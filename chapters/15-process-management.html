PART 5 · PROCESS MANAGEMENT

Chapter 15 — Process Management

Kernel প্রতিটা process-কে কোন অবস্থায় রাখে, কাকে কখন CPU দেয়, আর নতুন process কীভাবে জন্মায়, অন্য program হয়ে যায়, আর মারা যায় — fork, exec, wait।

যা লাগবে, এক লাইনে: process হলো চলমান program, যার জন্য kernel একটা PCB রাখে — PID, parent-এর PID, memory, খোলা file, CPU-র register-এর সেভ করা মান (Chapter 3)। Kernel কয়েক millisecond পরপর timer interrupt পেয়ে নিয়ন্ত্রণ ফিরে পায় (Chapter 2), আর execve একই process-এর ভেতরের program বদলে দেয়, PID না বদলে (Chapter 4)। এই chapter-এ এই টুকরোগুলো দিয়ে process-এর পুরো জীবনচক্র সাজাব।

Process-এর অবস্থা: কে CPU চায়, কে চায় না

তোমার Mac-এ এই মুহূর্তে সাড়ে সাতশোর বেশি process, অথচ core বারোটা। Kernel যদি পালা করে সবাইকে CPU দিত, বেশিরভাগ পালা নষ্ট হতো — কারণ বেশিরভাগ process-এর এই মুহূর্তে করার কিছুই নেই: কেউ keyboard-এর অপেক্ষায়, কেউ network-এর, কেউ timer-এর। গুনে দেখো:

ps -Ao stat | tail -n +2 | cut -c1 | sort | uniq -c

আমার Mac-এ: 755 S, 4 R, 3 U — প্রায় সবাই ঘুমিয়ে। তাই kernel প্রতিটা process-এর PCB-তে একটা state লিখে রাখে:

  • Running — এই মুহূর্তে কোনো একটা core-এ চলছে।
  • Ready (runnable) — চলতে চায়, কিন্তু core খালি নেই; kernel-এর একটা লাইনে (run queue) অপেক্ষা করছে।
  • Blocked (sleeping, waiting) — কোনো ঘটনার অপেক্ষায়: disk-এর data, network packet, timer, একটা lock, বা child-এর মৃত্যু। এখন CPU দিলেও কিছু করতে পারবে না, তাই CPU চাইছেও না। Chapter 2-এর readFileSync-এর "process sleeps" এই অবস্থা।
  • New আর Zombie — জন্মের মুহূর্ত আর মৃত্যুর পরের এক বিশেষ অবস্থা (নিচে আলাদা section)।
EXPERIMENT (Linux / Docker)

তিন রকম process চালিয়ে ps-এর STAT column দেখো — একটা ঘুমন্ত (sleep), একটা অবিরাম হিসাব করা, আর একটা যার child মারা গেছে কিন্তু parent খোঁজ নেয়নি:

docker run --rm debian:bookworm-slim bash -c '
  apt-get update -qq >/dev/null 2>&1 && apt-get install -y -qq procps python3 >/dev/null 2>&1
  sleep 300 &
  python3 -c "while True: pass" &
  python3 -c "import os,time; pid=os.fork(); os._exit(0) if pid==0 else time.sleep(300)" &
  sleep 1; ps -o pid,ppid,stat,command'

আমার output (দরকারি লাইন):

  PID  PPID STAT COMMAND
 3161     1 S    sleep 300
 3162     1 R    python3 -c while True: pass
 3163     1 S    python3 -c import os,time; pid=os.fork(); ...
 3165  3163 Z    [python3] <defunct>

S = blocked (Linux-এর ভাষায় sleeping), R = runnable, Z = zombie। একটা সূক্ষ্মতা: Linux ready আর running দুটোকেই R দেখায় — দুইজনেই "CPU চায়", ফারাক শুধু এই মুহূর্তে পেয়েছে কি না। আরেকটা অক্ষর দেখতে পারো D — এমন ঘুম যেটা ভাঙানো যায় না, সাধারণত disk I/O-র মাঝখানে; সেই সময় kill -9-ও অপেক্ষা করে। macOS-এর U প্রায় একই জিনিস, আর I মানে ২০ সেকেন্ডের বেশি ধরে ঘুমন্ত।

একটা process-এর জীবনের অবস্থা আর তাদের মাঝের রাস্তা। CPU পায় শুধু Running; Ready লাইনে দাঁড়িয়ে, Blocked লাইনেই নেই। Running থেকে বেরোনোর তিন পথ: সময় শেষ (Ready-তে ফেরা), কিছুর অপেক্ষা (Blocked), বা মৃত্যু (Zombie)।

Scheduler: কে কখন CPU পাবে

Run queue-তে কয়েকজন দাঁড়িয়ে থাকলে কাকে আগে দেবে, কতক্ষণের জন্য? এই সিদ্ধান্ত নেয় kernel-এর যে অংশ, তার নাম scheduler। সে চলে তিনটা মুহূর্তে: timer interrupt এলে (চলমান process-এর পালা শেষ হলো কি?), চলমান process নিজে block হলে (core খালি হলো), আর কেউ ঘুম থেকে জেগে ready হলে (তাকে এখনই বসানো উচিত কি?)।

প্রতিটা পালার একটা সর্বোচ্চ মাপ আছে — time slice, সাধারণত কয়েক millisecond। পালা শেষ হওয়ার আগে process নিজে ছেড়ে না দিলে timer interrupt তাকে জোর করে নামায় — এর নাম preemption। এজন্যই Chapter 1-এর while(true){} কখনো syscall না করেও পুরো machine আটকে রাখতে পারেনি। ভালো scheduler একসাথে কয়েকটা জিনিস মেলায়: সবাই ন্যায্য ভাগ পাক, যে process মানুষের সাথে কাজ করে (editor, browser) সে ডাক পেলেই দ্রুত জাগুক, আর পালা বদলের খরচ (Chapter 17) যেন বেশি না হয়।

Linux-এর scheduler (২০২৩ থেকে যার নাম EEVDF, আগে CFS) প্রতিটা process কতটা CPU সময় পেয়েছে তার হিসাব রাখে, আর মোটা দাগে যে কম পেয়েছে তাকে আগে বসায়। সেই হিসাবে ওজন দেওয়া যায় nice দিয়ে — -২০ (সবচেয়ে গুরুত্বপূর্ণ) থেকে ১৯ (সবচেয়ে ভদ্র); প্রতি ধাপে মোটামুটি সোয়া গুণ ওজনের পার্থক্য।

EXPERIMENT (Linux / Docker) — nice

taskset -c 0 একটা process-কে শুধু CPU 0-তে চলতে বাধ্য করে — তাই দুইটা অবিরাম loop-কে একই core-এর জন্য লড়তে হবে; একটার nice ০, আরেকটার ১০:

docker run --rm debian:bookworm-slim bash -c '
  apt-get update -qq >/dev/null 2>&1 && apt-get install -y -qq procps python3 >/dev/null 2>&1
  taskset -c 0 python3 -c "while True: pass" &             A=$!
  taskset -c 0 nice -n 10 python3 -c "while True: pass" &  B=$!
  sleep 5; ps -o pid,ni,pcpu,command -p $A,$B; kill $A $B'

আমার output:

  PID  NI %CPU COMMAND
 3168   0 89.8 python3 -c while True: pass
 3169  10  9.5 python3 -c while True: pass

একই কাজ, একই core — nice ১০ দেওয়ায় ভাগ হলো প্রায় ৯০:১০। Linux-এর ভেতরের ওজনের table-এ nice ০ মানে ১০২৪, nice ১০ মানে ১১০ — আর ১০২৪ : ১১০ ঠিক ৯০ : ১০। Background-এর ভারী কাজ (backup, report বানানো) nice দিয়ে চালালে সেটা CPU খালি থাকলে পুরোটাই পায়, কিন্তু জরুরি কাজ এলে সরে দাঁড়ায়। (macOS nice মানে, কিন্তু সেখানে বেশি কার্যকর Chapter 12-এর QoS — taskpolicy।)

একটা core-এ তিনটা process-এর ৪০ ms। প্রতিটা মুহূর্তে ঠিক একজন নীল (running)। A আর C পালা করে ৪ ms-এর time slice পায়; B অল্প চলেই disk-এর অপেক্ষায় block হয় — তখন তার কোনো পালাই লাগে না। Disk-এর interrupt আসার পরে B ready হয়, লাইনে দাঁড়ায়, আর ছোট্ট একটা পালা পায়। (ছক বোঝানোর জন্য বানানো, মাপা না।)

fork: process-এর জন্ম

Chapter 3-এ বলেছিলাম নতুন process বানাতে একটা চলমান process-কে kernel-এর কাছে চাইতে হয়। কিন্তু নতুন process-কে তো একগাদা জিনিস দিয়ে শুরু করতে হবে — memory, খোলা file, environment, working folder। প্রতিটা আলাদা করে বলে দেওয়ার বদলে Unix একটা চতুর পথ নিয়েছে: "আমার একটা হুবহু copy বানাও।" এই syscall-এর নাম fork।

fork-এর পরে দুইটা process: একই code, memory-র একই বিষয়বস্তু, একই খোলা file, একই জায়গায় থেমে — এমনকি দুজনেই fork call থেকে ফিরছে। পার্থক্য দুইটা: নতুনটার (child) আলাদা PID, আর fork-এর ফেরত মান — child পায় 0, parent পায় child-এর PID। এই একটা সংখ্যা দেখেই দুজন আলাদা পথে যায়। Node-এ সরাসরি fork নেই (Node-এর child_process.fork নামে এক হলেও আসলে একটা নতুন node process চালু করে), তাই এখানে Python — পড়তে JS-এর মতোই সহজ:

EXPERIMENT — fork.py
import os

x = 1
pid = os.fork()                 # এই লাইন থেকে দুইটা process — দুজনেই এখান থেকে এগোবে
if pid == 0:                    # child-এ fork() ফেরত দেয় 0
    x = 99
    print("child : my pid", os.getpid(), "| x =", x, flush=True)
    os._exit(7)                 # exit code 7
else:                           # parent-এ fork() ফেরত দেয় child-এর PID
    _, status = os.waitpid(pid, 0)
    print("parent: my pid", os.getpid(), "| child was", pid, "| exit code", os.waitstatus_to_exitcode(status), "| x =", x)

python3 fork.py — আমার Mac-এ:

child : my pid 97478 | x = 99
parent: my pid 97477 | child was 97478 | exit code 7 | x = 1

একটা fork() call, দুইটা ফেরত — দুইটা আলাদা process-এ। Child x-কে ৯৯ বানাল, parent-এর x তবু ১: copy মানে আলাদা memory (Chapter 9-এর দুই page table)। আর parent child-এর exit code ৭ হাতে পেল।

কিন্তু parent যদি কয়েক GB memory ধরে থাকে, সেটা copy করতে তো অনেক সময়? এখানেই Chapter 9-এর copy-on-write: kernel কিছুই copy করে না, শুধু child-এর page table-এ parent-এর frame গুলোই বসায়, আর দুইজনের জন্যই "লেখা নিষেধ" চিহ্ন দেয়। কেউ কোনো page-এ লিখতে গেলে page fault — তখন শুধু সেই page-টা copy।

python3 -c "
import os, time
big = bytearray(1024 * 1024 * 1024)            # ১ GB
for i in range(0, len(big), 16384): big[i] = 1 # সত্যিই ছুঁয়ে দিলাম — RSS ~১ GB
t = time.perf_counter()
pid = os.fork()
if pid == 0: os._exit(0)
ms = (time.perf_counter() - t) * 1000
os.waitpid(pid, 0)
print(f'fork of a process holding 1 GB took {ms:.1f} ms')"

আমার Mac-এ: fork of a process holding 1 GB took 2.4 ms। ১ GB copy করতে Chapter 7-এর ~৫৮ GB/s-এও ~১৭ ms লাগত; এখানে লাগল তার সাত ভাগের এক ভাগ, কারণ copy হয়ইনি — শুধু page table সাজানো হয়েছে।

exec আর fork + exec: shell কীভাবে command চালায়

fork শুধু নিজের copy বানায়। কিন্তু shell-এ ls লিখলে তো চাই ls চলুক, আরেকটা shell না। এর জন্য দ্বিতীয় ধাপ: child execve দিয়ে নিজের ভেতরের program বদলে ls হয়ে যায় (Chapter 4-এর loader)। আর parent — shell নিজে — wait syscall দিয়ে ঘুমিয়ে থাকে, যতক্ষণ না child শেষ হয়।

দুই ধাপ আলাদা কেন, এক syscall-এ "এই program চালাও" কেন না? কারণ fork আর exec-এর মাঝখানের মুহূর্তটা সোনার খনি: child তখনো shell-এর code চালাচ্ছে, কিন্তু আলাদা process — সে নিজের খোলা file, folder, environment ইচ্ছামতো সাজিয়ে নিতে পারে, তারপর নতুন program হয়। নতুন program সেই সাজানো অবস্থাই উত্তরাধিকার হিসেবে পায়, কিছু না জেনেই। ls / > out.txt ঠিক এভাবে কাজ করে:

EXPERIMENT (Linux / Docker) — shell-এর ভেতরে
docker run --rm --cap-add SYS_PTRACE debian:bookworm-slim bash -c '
  apt-get update -qq >/dev/null 2>&1 && apt-get install -y -qq strace >/dev/null 2>&1
  strace -f -e trace=clone,execve,openat,dup3,wait4 bash -c "ls / > /tmp/out.txt; true" 2>&1 | grep -E "clone|out.txt|dup3|execve|wait4"'

আমার output (একটু ছেঁটে; [pid 129] হলো child):

execve("/usr/bin/bash", ["bash", "-c", "ls / > /tmp/out.txt; true"], ...) = 0
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 129
[pid   128] wait4(-1,  <unfinished ...>
[pid   129] openat(AT_FDCWD, "/tmp/out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
[pid   129] dup3(3, 1, 0)               = 1
[pid   129] execve("/usr/bin/ls", ["ls", "/"], ...) = 0
<... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 129

Linux-এ fork-এর আধুনিক রূপের নাম clone। পড়ো: bash (128) clone করল, আর wait4-এ ঘুমিয়ে পড়ল। Child (129) তখনো bash — সে out.txt খুলে fd 3 পেল, তারপর dup3(3, 1) দিয়ে fd 1-কে (stdout, Chapter 3) সেই file-এর দিকে ঘুরিয়ে দিল, তারপর execve দিয়ে ls হয়ে গেল। ls জানেই না তার output কোথায় যাচ্ছে — সে শুধু fd ১-এ লেখে। শেষে parent-এর wait4 ফিরল child-এর exit code ০ নিয়ে।

Node-এর child_process.spawn-ও ভেতরে একই কাজ করে। strace -f -e trace=clone,execve node -e "require('child_process').spawnSync('ls', ['/'])" চালালে দেখবে clone(... flags=SIGCHLD), তারপর child একের পর এক execve("/usr/local/sbin/ls"), execve("/usr/local/bin/ls")… চেষ্টা করছে, সবগুলো ENOENT — যতক্ষণ না execve("/bin/ls") = 0। এটা PATH environment variable-এর folder গুলোয় ক্রমানুসারে খোঁজা।

উপরে parent, নিচে child, বাঁ থেকে ডানে সময়। Parent clone করেই wait4-এ ঘুমিয়ে পড়ে (Blocked)। Child প্রথমে bash-এর copy হিসেবে নিজের stdout-কে file-এর দিকে ঘোরায়, তারপর ls হয়ে যায়। Child শেষ হলে kernel parent-কে SIGCHLD signal দিয়ে জাগায়, সঙ্গে exit code।

wait, zombie আর অনাথ

Child শেষ হলে তার memory, খোলা file সব kernel ফেরত নেয়। কিন্তু Chapter 3-এর কথা মনে করো: parent-এর জানা দরকার child কীভাবে শেষ হলো — exit code। সেই সংখ্যা কোথায় থাকবে যতক্ষণ না parent খোঁজ নেয়? তাই kernel child-এর PCB-র একটা ছোট অংশ রেখে দেয় — শুধু PID আর exit status। এই অবস্থার নাম zombie: মৃত, কিন্তু কবর হয়নি। Parent wait (বা waitpid) ডাকলে kernel exit status দিয়ে zombie-টা মুছে ফেলে — একে বলে reap করা।

Parent যদি কখনো wait না ডাকে, zombie জমতে থাকে। একেকটা ছোট, কিন্তু প্রতিটা একটা PID আটকে রাখে, আর PID-এর সংখ্যা সীমিত। ওপরের state experiment-এ [python3] <defunct> ঠিক এমন একটা — parent ৩০০ সেকেন্ড ঘুমাচ্ছে, খোঁজ নিচ্ছে না।

উল্টো ঘটনাও ঘটে: parent আগে মারা গেলে child হয়ে যায় অনাথ (orphan)। তখন kernel তাকে PID 1-এর হাতে তুলে দেয় (Chapter 3-এর গাছের গোড়া), আর PID 1-এর দায়িত্ব এমন দত্তক child-দের মৃত্যুর পরে wait করা। systemd বা launchd এটা জানে। কিন্তু Docker container-এ PID 1 হয় container-এর প্রথম command — প্রায়ই node নিজে, যে এই দায়িত্বের কথা জানেই না:

EXPERIMENT (Docker) — pid1.js
const { spawn, execSync } = require('child_process');
console.log('my pid:', process.pid);
// sh একটা background sleep চালিয়েই শেষ হয়ে যায় → sleep অনাথ হয়ে PID 1-এর কাছে যায়
spawn('sh', ['-c', 'sleep 1 &']);
setTimeout(() => console.log(execSync('ps -o pid,ppid,stat,comm').toString()), 3000);
docker run --rm        -v "$PWD":/w node:22-alpine node /w/pid1.js
docker run --rm --init -v "$PWD":/w node:22-alpine node /w/pid1.js

আমার output — প্রথমটা:

my pid: 1
PID   PPID  STAT COMMAND
    1     0 S    node
   15     1 Z    sleep
   16     1 R    ps

দ্বিতীয়টা (--init):

my pid: 7
PID   PPID  STAT COMMAND
    1     0 S    docker-init
    7     1 S    node
   17     7 R    ps

প্রথম container-এ node-ই PID 1; অনাথ sleep তার কাছে এল, মরল, আর কেউ wait করল না — Z হয়ে পড়ে আছে। দীর্ঘ সময় চলা একটা server যদি বারবার child process চালায়, এমন zombie জমতেই থাকে। দ্বিতীয় container-এ --init একটা ছোট program (docker-init) কে PID 1 বানিয়েছে, যার একমাত্র কাজ অনাথদের wait করা আর signal ঠিকমতো পৌঁছে দেওয়া — zombie নেই। (Signal-এর কথা উঠল বলে: PID 1 হলে process-এর উপর kernel-এর default signal ব্যবস্থা খাটে না, তাই node PID 1 হলে docker stop-এর SIGTERM উপেক্ষা করে, আর Docker ১০ সেকেন্ড অপেক্ষা করে জোর করে মারে। --init সেটাও সারায়।)

COMMON MISCONCEPTION

"Zombie process memory খাচ্ছে, kill -9 দিয়ে মেরে দাও।" Zombie আগেই মৃত — তার memory, code, file সব ফেরত গেছে, আছে শুধু PCB-র একটা ছোট অংশ। মৃতকে আবার মারা যায় না; kill -9 কিছুই করবে না। সমাধান হলো parent-কে দিয়ে wait করানো, বা parent-কে থামানো — তাহলে zombie-রা PID 1-এর কাছে যায় আর সে তাদের reap করে।

MENTAL MODEL

প্রতিটা process সবসময় একটা অবস্থায় — running, ready (লাইনে), blocked (অপেক্ষায়), বা zombie। Scheduler শুধু ready-দের মধ্য থেকে বাছে, time slice শেষে বা কেউ block হলে। জীবনচক্র চারটা syscall-এ: fork (copy বানাও, copy-on-write দিয়ে সস্তায়) → মাঝখানে নিজেকে সাজাও → exec (অন্য program হয়ে যাও) → exit; আর parent-এর wait তার কবর দেয়।

CAN I EXPLAIN THIS?
  • Running, ready আর blocked-এর পার্থক্য কী — কে CPU চায়, কে চায় না? Linux-এর ps কেন ready আর running দুটোকেই R দেখায়?
  • Scheduler কোন তিন মুহূর্তে চলে? Nice ১০ দেওয়া loop একই core-এ মাত্র ~১০% CPU পেল কেন?
  • fork() "দুইবার ফেরে" — মানে কী? Child-এ x = 99 করলেও parent-এর x ১ কেন, আর ১ GB-র process fork করতে মাত্র ২.৪ ms কেন?
  • fork আর exec আলাদা দুই ধাপ হওয়ায় ls / > out.txt কীভাবে কাজ করে, অথচ ls redirect-এর কথা কিছুই জানে না?
  • Zombie কী, কেন থাকে, আর কীভাবে সরে? Docker-এ node PID 1 হলে কী দুইটা সমস্যা হয়, আর --init কী করে?
