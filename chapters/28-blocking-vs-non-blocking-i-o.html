PART 7 · NETWORKING AND SOCKETS

Chapter 28 — Blocking vs Non-blocking I/O

হাজারটা connection, যাদের বেশিরভাগ চুপচাপ বসে — তাদের জন্য কে অপেক্ষা করবে? প্রতি connection-এ একটা thread দিলে কী খরচ, non-blocking কী বদলায়, আর কেন non-blocking একা যথেষ্ট না।

একটা server-এর বাস্তব ছবি: হাজারো client connected, কিন্তু যেকোনো মুহূর্তে তাদের বেশিরভাগই কিছু পাঠাচ্ছে না — browser-এর keep-alive connection, websocket, মোবাইল app-এর খোলা লাইন। Server-এর আসল কাজ তাই মূলত অপেক্ষা: কে কখন কিছু পাঠাবে। প্রশ্ন হলো এই অপেক্ষাটা কে করবে, কীভাবে। Chapter 25-এ দেখেছি Node নিজের সব socket SOCK_NONBLOCK দিয়ে বানায়; এই chapter-এ দেখব কেন।

Blocking: প্রতি connection-এ একজন পাহারাদার

Default socket blocking: recv()/read() ডাকলে data না আসা পর্যন্ত thread ঘুমায় (Chapter 15-এর Waiting)। এক thread একসাথে একটা connection-এর জন্যই ঘুমাতে পারে, তাই সবচেয়ে সরল নকশা হলো thread-per-connection: প্রতিটা নতুন connection-এর জন্য একটা নতুন thread, যে সেই connection-এর recv()-এ বসে থাকে। Code পড়তে খুব সহজ — সবকিছু উপর থেকে নিচে, কোনো callback নেই। Node-এ এভাবে লেখা যায় না, তাই Python-এ:

# threaded_server.py — প্রতিটা connection-এর জন্য একটা thread, blocking recv
import socket, threading

def handle(conn):
    while True:
        data = conn.recv(4096)          # data না আসা পর্যন্ত এই thread ঘুমায়
        if not data:
            break
        conn.sendall(data)
    conn.close()

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(('127.0.0.1', 9000))
srv.listen(4096)
while True:
    conn, _ = srv.accept()
    threading.Thread(target=handle, args=(conn,), daemon=True).start()

পাশে একই কাজের Node version: require('net').createServer(c => c.pipe(c)).listen(9001, '127.0.0.1', 4096); (event_server.js)। দুইটাতেই ১০০০টা করে connection খুলে চুপচাপ বসিয়ে রাখব, তারপর /proc/<pid>/status থেকে thread-এর সংখ্যা আর memory পড়ব:

Python server-এ ১০০১টা thread — প্রতিটা connection-এর একজন পাহারাদার, প্রত্যেকে recv()-এ ঘুমিয়ে। Virtual memory (VmSize) ১৩ MB থেকে ১৪ GB: প্রতিটা thread-এর stack-এর জন্য ৮ MB জায়গা বরাদ্দ (Chapter 16, 19)। আসলে ব্যবহৃত RAM (VmRSS) বেড়েছে ~২৩.৫ MB, মানে thread-প্রতি ~২৪ KB। Node server-এ thread সংখ্যা ৭ থেকে নড়েইনি; তার RAM বেড়েছে ~১১.৫ MB — প্রতি connection-এ ~১২ KB, JS-এর socket object আর তার buffer-এর জন্য।

আসল খরচ আসে জাগার সময়

চুপচাপ বসে থাকা thread-এর দাম তুলনামূলক কম। দাম ওঠে যখন তারা জাগে: প্রতিটা আসা message মানে একটা thread-কে ঘুম থেকে তোলা আর CPU-তে বসানো — একটা context switch (Chapter 17)। একই ১০০০টা connection-এ এবার ১০ দফা করে সবাই একসাথে ১ byte পাঠাবে আর echo-র অপেক্ষা করবে; burst চলাকালীন server-এর সব thread-এর স্বেচ্ছায় context switch (voluntary_ctxt_switches, Chapter 17) যোগ করব:

EXPERIMENT (Linux / Docker) — burst আর context switch
// burst_clients.js — N টা connection; ১০ দফায় সবাই একসাথে 1 byte পাঠায় আর echo-র অপেক্ষা করে
const net = require('net');
const [port, n] = process.argv.slice(2).map(Number);
const socks = [];
let open = 0;
for (let i = 0; i < n; i++) {
  const s = net.connect(port, '127.0.0.1', async () => {
    if (++open < n) return;
    const t = performance.now();
    for (let round = 0; round < 10; round++)
      await Promise.all(socks.map(s => new Promise(r => { s.once('data', r); s.write('x'); })));
    console.log(`:${port} 10 rounds x ${n} echoes in ${(performance.now() - t).toFixed(0)} ms`);
    setTimeout(() => process.exit(0), 3000);   // connection গুলো আরও ৩ সেকেন্ড খোলা থাকুক
  });
  socks.push(s);
}
# switches.sh — burst-এর সময় server-এর সব thread-এর স্বেচ্ছায় context switch যোগ করো
cs() { cat /proc/$1/task/*/status | awk '/^voluntary_ctxt_switches/ {s += $2} END {print s}'; }
python3 threaded_server.py & PY=$!
node event_server.js & NJ=$!
sleep 1
for pair in "$PY 9000 python" "$NJ 9001 node"; do
  set -- $pair
  node burst_clients.js $2 1000 & C=$!
  sleep 2.5                                   # burst শেষ, connection গুলো তখনো খোলা
  echo "$3: $(cat /proc/$1/status | awk '/^Threads/ {print $2}') threads, $(cs $1) voluntary context switches"
  wait $C
done
kill $PY $NJ

python: 1001 threads, 62884 voluntary context switches
:9001 10 rounds x 1000 echoes in 48 ms
node: 7 threads, 123 voluntary context switches

একই ১০,০০০টা echo: thread-per-connection-এ ৬২ হাজারের বেশি context switch আর ৩৮২ ms; Node-এ ১২৩টা switch আর ৪৮ ms। ১০,০০০টা message-এ অন্তত ১০,০০০ বার কাউকে জাগাতেই হয়; বাকিটা Python-এর নিজস্ব একটা সীমা বাড়িয়েছে — GIL (global interpreter lock): এক process-এ একসাথে একটাই thread Python code চালাতে পারে, তাই জেগে ওঠা thread গুলো আবার GIL-এর লাইনে দাঁড়িয়ে ঘুমায়। Java বা C-তে এই অংশটা থাকত না, কিন্তু প্রথম ১০,০০০ switch, ১০০১টা stack আর scheduler-এর ঘাড়ে ১০০১টা thread-এর হিসাব থেকেই যেত। Node-এর একটা thread একবার জেগে একসাথে অনেকগুলো ready connection-এর কাজ সেরে আবার ঘুমায় — কীভাবে, পরের chapter-এ।

১৯৯৯ সালে এই সমস্যার একটা নাম দেওয়া হয়েছিল — C10K problem: একটা machine-এ দশ হাজার connection একসাথে কীভাবে সামলাবে। Thread-per-connection এখানে ভেঙে পড়ে মূলত তিনটা খরচে: প্রতিটা thread-এর stack আর kernel-এর হিসাব, প্রতিটা message-এ context switch আর তার cache দূষণ (Chapter 17), আর অনেক thread-এর মধ্যে CPU ভাগ করার scheduler-এর কাজ।

Non-blocking: "এখন নেই" বলে ফিরে আসা

বিকল্প: socket-কে non-blocking করে দাও (O_NONBLOCK)। তখন recv()-এর চুক্তি বদলে যায় — data থাকলে দাও, না থাকলে ঘুমিয়ো না, সাথে সাথে error দিয়ে ফেরো: EAGAIN ("আবার চেষ্টা করো", কিছু সিস্টেমে নাম EWOULDBLOCK)। Thread আর কোনো একটা connection-এ আটকে থাকে না — সে ঘুরে ঘুরে অনেকগুলোকে জিজ্ঞেস করতে পারে। কিন্তু "কখন জিজ্ঞেস করবে"? বারবার, loop-এ — একে বলে busy polling। দেখি তাতে কী দাম:

EXPERIMENT (Linux / Docker) — busypoll.py
# busypoll.py — data আসবে ২ সেকেন্ড পরে। অপেক্ষার দুই উপায়ের CPU খরচ
import socket, time, threading

def serve_once(port):
    srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind(('127.0.0.1', port)); srv.listen(1)
    conn, _ = srv.accept()
    time.sleep(2)                           # ধীর server: ২ সেকেন্ড পরে উত্তর
    conn.sendall(b'hello')

def measure(label, port, nonblocking):
    threading.Thread(target=serve_once, args=(port,), daemon=True).start()
    time.sleep(0.2)
    s = socket.create_connection(('127.0.0.1', port))
    s.setblocking(not nonblocking)
    tries, cpu0, wall0 = 0, time.process_time(), time.perf_counter()
    while True:
        tries += 1
        try:
            data = s.recv(100)              # blocking: এখানে ঘুমায়। non-blocking: সাথে সাথে ফেরে
            break
        except BlockingIOError as e:        # EAGAIN: "এখন কিছু নেই"
            if tries == 1: print(f'  first non-blocking recv: {e}')
    print(f'{label:12s} wall {time.perf_counter() - wall0:.2f} s, CPU {time.process_time() - cpu0:.2f} s, recv calls {tries:,}')

measure('blocking', 9100, False)
measure('busy-poll', 9101, True)
docker run --rm -v "$PWD":/w:ro python:3.12-slim python /w/busypoll.py
blocking     wall 2.00 s, CPU 0.00 s, recv calls 1
  first non-blocking recv: [Errno 11] Resource temporarily unavailable
busy-poll    wall 2.01 s, CPU 2.01 s, recv calls 4,398,095

দুইভাবেই ঠিক ২ সেকেন্ড অপেক্ষা। Blocking-এ একটাই recv, CPU খরচ শূন্য — thread kernel-এ ঘুমিয়ে ছিল, data আসতেই kernel তাকে জাগিয়েছে। Busy-poll-এ ৪৪ লাখ বার recv (Errno 11 = EAGAIN), আর পুরো ২ সেকেন্ড একটা core ১০০% ব্যস্ত — কোনো কাজ ছাড়াই, শুধু "এসেছে? এসেছে?" জিজ্ঞেস করে। প্রতিটা জিজ্ঞাসা একটা system call (Chapter 32-এ তার দাম)। হাজারটা socket-এ এটা করলে পুরো machine শুধু জিজ্ঞেস করেই শেষ।

তিনটা connection-এ data আসে তিনটা আলাদা মুহূর্তে। ওপরে: প্রতি connection-এ একটা thread, প্রত্যেকে আলাদা করে ঘুমায় আর জাগে। মাঝে: একটা non-blocking thread যে কখনো ঘুমায় না, শুধু জিজ্ঞেস করে। নিচে: একটা thread সবার জন্য একবার ঘুমায়, আর kernel তাকে ঠিক কাজের মুহূর্তে জাগায় — পরের chapter-এর বিষয়।

তৃতীয় জিনিসটা: kernel-কে বলা "কেউ ready হলে জাগিও"

তাহলে দুইটা পথই অসম্পূর্ণ। Blocking-এ অপেক্ষা সস্তা (ঘুমন্ত thread CPU খায় না), কিন্তু এক thread শুধু এক connection-এর জন্য অপেক্ষা করতে পারে। Non-blocking-এ এক thread অনেক connection সামলাতে পারে, কিন্তু কখন দেখবে জানে না, তাই CPU পোড়ায়। দরকার দুটোর ভালো অংশ: একটা thread ঘুমাবে (CPU শূন্য), কিন্তু ঘুমাবে সবগুলো socket-এর জন্য একসাথে, আর kernel তাকে জাগাবে ঠিক তখনই যখন কোনো একটায় data এসেছে — সাথে বলে দেবে কোনটায়। Kernel তো data আসার খবর এমনিই পায় (Chapter 27-এর আসার পথ, "অপেক্ষায় থাকা reader-কে জাগাও")। এই ব্যবস্থার নাম I/O multiplexing — Linux-এ epoll, Mac-এ kqueue — আর Node-এর event loop, nginx, Redis সবার ভিত এটাই। পরের chapter পুরোটা এটা নিয়ে।

COMMON MISCONCEPTION

"Non-blocking মানেই দ্রুত।" Non-blocking শুধু বলে thread আটকাবে না — কিন্তু তারপর thread কী করবে, সেটা বলে না। busypoll.py-তে non-blocking socket একটা পুরো core ২ সেকেন্ড পুড়িয়েছে ৪৪ লাখ অপ্রয়োজনীয় system call-এ, যেখানে blocking-এ খরচ ছিল শূন্য। Non-blocking কাজে লাগে কেবল একটা notification ব্যবস্থার সাথে জোড়া দিলে।

MENTAL MODEL

অপেক্ষার দুই মাত্রা: কে অপেক্ষা করে, আর অপেক্ষার সময় CPU কী করে। Thread-per-connection-এ প্রতিটা connection-এর জন্য একটা ঘুমন্ত thread — সরল, কিন্তু হাজারো stack আর প্রতি message-এ context switch। Busy polling-এ একটা জাগ্রত thread — কোনো stack-এর বোঝা নেই, কিন্তু CPU পোড়ে। Event notification-এ একটা ঘুমন্ত thread সবার জন্য, আর kernel ঠিক সময়ে জাগায় — এটাই C10K-এর উত্তর।

CAN I EXPLAIN THIS?
  • Blocking recv()-এ thread কী অবস্থায় থাকে, CPU খায় কি? Thread-per-connection নকশায় ১০০০টা connection-এ ১০০১টা thread কেন, আর VmSize ১৪ GB হলো কেন?
  • switches.sh-এ একই ১০,০০০ echo-তে Python server ৬২ হাজার context switch করল আর Node ১২৩টা — পার্থক্যের উৎস কী কী? GIL এখানে কী যোগ করেছে?
  • C10K problem কী, আর thread-per-connection কোন তিনটা খরচে ভেঙে পড়ে?
  • Non-blocking socket-এ data না থাকলে recv() কী করে? busypoll.py-তে busy-poll কেন ২ সেকেন্ড CPU খেল আর blocking খেল শূন্য?
