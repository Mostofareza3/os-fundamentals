PART 2 · FROM PROGRAM TO PROCESS

Chapter 3 — Program vs Process

Disk-এ পড়ে থাকা একটা file আর "চলছে" এমন একটা জিনিসের মধ্যে পার্থক্য কী — আর সেই পার্থক্য ধরে রাখতে kernel কী কী হিসাব রাখে।

আগের দুই chapter থেকে তিনটা জিনিস লাগবে, এক লাইনে মনে করিয়ে দিই। Kernel: OS-এর যে অংশ hardware-এর মালিক আর বাকি সবার হয়ে সিদ্ধান্ত নেয়। Register আর program counter (PC): CPU-র ভেতরের ছোট দ্রুত slot; PC মনে রাখে পরের instruction কোথায়। Memory address: RAM-এর প্রতিটা byte-এর নম্বর।

একটা ধাঁধা দিয়ে শুরু

দুইটা terminal খোলো, দুটোতেই এই এক লাইন চালাও:

node -e "let count = 0; setInterval(() => console.log(process.pid, ++count), 1000)"

দ্বিতীয়টা কয়েক সেকেন্ড পরে চালালে এরকম কিছু দেখবে:

# terminal 1            # terminal 2
4101 1                  4187 1
4101 2                  4187 2
4101 3                  4187 3
4101 4
4101 5

Disk-এ node নামের file একটাই, code-ও হুবহু এক। অথচ দুই জায়গায় দুইটা আলাদা count আলাদা গতিতে বাড়ছে, আর প্রতিটা আলাদা একটা নম্বর print করছে। এক file থেকে দুইটা স্বাধীন "চলমান জিনিস" এল কীভাবে? আর count-এর মান file-এ তো লেখা নেই — থাকছে কোথায়? এই প্রশ্নের উত্তরের জন্যই দুইটা আলাদা শব্দ লাগে: program আর process।

Program: disk-এ শুয়ে থাকা file

Program হলো একটা executable file — এমন file, যেটা OS চালাতে জানে। এর ভেতরে তিন রকম জিনিস থাকে:

  • Machine code — CPU-র instruction গুলো, সংখ্যা হিসেবে লেখা (Chapter 2-এর instruction set অনুযায়ী)। এগুলো মানুষের পড়ার জন্য না, এজন্য এমন file-কে চলতি ভাষায় binary বলে।
  • Initial data — program শুরুর সময় যে মানগুলো লাগবে, যেমন আগে থেকে লেখা string।
  • Header — file-এর একদম শুরুতে বসানো তথ্য: এটা কোন ধরনের file, কোন CPU-র জন্য, কোন instruction থেকে চালানো শুরু করতে হবে।

Program-এর সবচেয়ে গুরুত্বপূর্ণ বৈশিষ্ট্য: সে passive। কিছুই করে না, কিছুই বদলায় না। শুধু byte, disk-এ পড়ে থাকে। নিজে দেখো:

ls -lh $(which node)       # file-টা কত বড়
file $(which node)         # OS-এর চোখে এটা কী
xxd -l 16 $(which node)    # প্রথম ১৬ byte, hex-এ

আমার Mac-এ node ১০৪ MB-এর একটা file, file বলছে Mach-O 64-bit executable arm64, আর প্রথম চার byte cffa edfe। Linux-এ (Docker-এর node:22-alpine-এ) একই পরীক্ষায় প্রথম চার byte 7f 45 4c 46 — শেষের তিনটা ASCII-তে (অক্ষরকে সংখ্যা দিয়ে লেখার প্রচলিত তালিকা) E, L, F। এই শুরুর byte গুলোকে বলে magic number: kernel এগুলো দেখেই চেনে file-টা কোন format-এর executable। macOS-এর format-এর নাম Mach-O, Linux-এর ELF। দুটোর ভেতরে কী থাকে, Chapter 4-এ খুলব।

Process: program-এর একটা চলমান instance

এবার সমস্যাটা দেখো। Program চালু হলেই এমন সব তথ্য জন্মায় যা file-এ রাখা সম্ভব না:

  • এই মুহূর্তে কোন instruction চলছে (PC-র মান), আর register গুলোতে কী আছে;
  • variable-দের বর্তমান মান — ওপরের count;
  • কোন কোন file বা network connection খোলা আছে;
  • এটা কে চালিয়েছে, কোন user-এর অনুমতি নিয়ে।

File-এ রাখা যায় না, কারণ একই file থেকে একসাথে দশবার চালানো যায় — দশটার দশ রকম অবস্থা। তার উপর Chapter 1-এর time-sharing মনে করো: kernel কয়েক millisecond পরপর একটা program-কে CPU থেকে সরিয়ে আরেকটাকে বসায়। সরানোর আগে যদি ঠিক কোথায় থেমেছিল তা লিখে না রাখে, পরে আর ঠিক সেই জায়গা থেকে চালাতে পারবে না।

তাই program চালু করার সময় kernel একটা নতুন জিনিস তৈরি করে, যেটা এই সব চলমান অবস্থা ধরে রাখে। এর নাম process। একটা process-এর ভেতরে থাকে:

  • PID (process ID) — kernel-এর দেওয়া একটা নম্বর, যেটা দিয়ে এই process-কে চেনা যায়। ওপরের 4101 আর 4187।
  • Address space — এই process-এর নিজস্ব memory address-এর জগৎ। Program-এর code আর data এখানে বসানো হয়, আর count-এর মতো variable এখানেই থাকে। প্রতিটা process-এর address space আলাদা, একজনের address দিয়ে অন্যজনের memory-তে পৌঁছানো যায় না (কীভাবে, Chapter 9; ভেতরের গঠন Chapter 5)।
  • CPU context — register আর PC-র মান। Process CPU-তে চলার সময় এগুলো CPU-র ভেতরেই থাকে; kernel যখন process-টাকে সরায়, তখন এগুলো kernel-এর খাতায় সেভ করে রাখে, আবার বসানোর সময় ফিরিয়ে দেয়।
  • File descriptor table — এই process-এর খোলা file, socket ইত্যাদির তালিকা (নিচে আলাদা section)।
  • Credentials — কোন user-এর হয়ে চলছে। Chapter 1-এ /dev/disk0 খুলতে গিয়ে যে EPERM পেয়েছিলে, kernel সেটা ঠিক করেছিল এই তথ্য দেখে।
  • State — এখন CPU-তে চলছে, নাকি কিছুর অপেক্ষায় ঘুমিয়ে আছে (Chapter 2-এর readFileSync-এ দেখেছ)। সব state আর তাদের মধ্যে আসা-যাওয়ার পুরো ছবি Chapter 15-এ।
  • Parent — কোন process একে তৈরি করেছে (নিচে আলাদা section)।

Kernel প্রতিটা process-এর জন্য এই সব তথ্য এক জায়গায় একটা record-এ রাখে, যাকে সাধারণভাবে বলে PCB (Process Control Block)। Linux-এর source code-এ এর নাম task_struct, আর তাতে কয়েকশো field। Record-টা থাকে kernel space-এ — process নিজে এটা বদলাতে পারে না, শুধু syscall দিয়ে কিছু অংশ জানতে পারে।

বাঁয়ে একটাই program file; সেটা দুইবার চালানোয় ডানে দুইটা process — প্রত্যেকের নিজস্ব memory, আলাদা count, আলাদা state আর খোলা file-এর তালিকা। নিচে kernel space-এ প্রতিটা process-এর একটা করে PCB; যে process এই মুহূর্তে CPU-তে নেই (4187), তার PC আর register সেখানে সেভ করা।

Record-টার একটা অংশ নিজের চোখে দেখো। Linux kernel প্রতিটা process-এর তথ্য /proc/<PID>/ folder-এ file হিসেবে দেখায়, আর /proc/self মানে "যে process পড়ছে, সে নিজে":

EXPERIMENT (Linux / Docker)
docker run --rm node:22-alpine node -e "process.stdout.write(require('fs').readFileSync('/proc/self/status', 'utf8'))"

লম্বা output-এর ভেতর থেকে কয়েকটা লাইন (আমার চালানোয়):

Name:    node
State:   R (running)
Pid:     17
PPid:    1
Uid:     0  0  0  0
VmRSS:   52084 kB
Threads: 7

Name, State, Pid, PPid (parent-এর PID), Uid (কোন user — ০ মানে root, সব অনুমতিওয়ালা admin user), VmRSS (এই মুহূর্তে কতটা RAM ব্যবহার করছে) — সবই PCB থেকে আসছে। macOS-এ কাছাকাছি তথ্য পাবে ps -o pid,ppid,user,state,rss,command -p <PID> দিয়ে।

MENTAL MODEL

Program হলো রান্নার recipe — কাগজে লেখা, নিজে কিছু করে না। Process হলো চুলায় চলা একটা রান্না: কোন ধাপে আছে, হাঁড়িতে কী আছে, কোন চুলা জ্বলছে। এক recipe থেকে একসাথে দুই হাঁড়ি রান্না হতে পারে।

উপমাটা এখানেই থামাই, কারণ আসল জিনিসটা আরও নির্দিষ্ট: process মানে kernel-এর রাখা একটা PCB, একটা নিজস্ব address space যেখানে program-এর code আর data বসানো, আর CPU context (PC + register) — যেটা হয় CPU-তে আছে, নয়তো PCB-তে সেভ করা।

File descriptor: খোলা জিনিসের নম্বর

Process যখন একটা file খোলে, তারপর প্রতিটা read বা write-এ kernel-কে বলতে হয় কোন file-এর কথা বলছে। প্রতিবার পুরো path পাঠানো ধীর আর বিপজ্জনক — মাঝখানে কেউ file-টার নাম বদলে দিলে বা সরিয়ে দিলে কী হবে? আর kernel-কেও প্রতিবার path থেকে file খুঁজতে হবে।

তাই kernel খোলার সময় একবারই কাজটা করে, আর process-কে একটা ছোট integer ফেরত দেয়। এর নাম file descriptor (fd)। এরপর process শুধু সেই নম্বর দিয়ে কথা বলে: "fd 17 থেকে ১৪ byte পড়ো"। Chapter 1-এর strace output মনে করো: openat(...) = 17, তারপর read(17, ...), close(17)। নম্বরটা kernel-এর কাছে ওই process-এর file descriptor table-এর একটা index — table-এর প্রতিটা ঘরে লেখা থাকে কোন file, কোন mode-এ খোলা, এখন কত byte পর্যন্ত পড়া হয়েছে।

তিনটা নম্বর প্রায় সব process-এ আগে থেকেই খোলা থাকে: 0 = stdin (input আসে এখান দিয়ে), 1 = stdout (স্বাভাবিক output — console.log এখানে লেখে), 2 = stderr (error output — console.error)। Terminal থেকে চালালে তিনটাই terminal-এর দিকে যায়।

node -e "const fs = require('fs'); console.log(fs.openSync('/etc/hosts', 'r'), fs.openSync('/etc/hosts', 'r'))"

আমার Mac-এ output 14 15। নতুন খোলা file সবচেয়ে ছোট খালি নম্বর পায়; ৩ না পেয়ে ১৪ পেল কারণ Node নিজে চালু হওয়ার সময় ৩ থেকে ১৩ পর্যন্ত নম্বর নিজের কাজে খুলে রেখেছে। একটা চলমান process-এর সব fd দেখতে: macOS-এ lsof -p <PID> (FD column-এ 0r, 1w, 2w… — অক্ষরটা mode: read/write), Linux-এ ls -l /proc/<PID>/fd।

একই program, অনেক process — আর isolation

শুরুর ধাঁধার উত্তর এখন দেওয়া যায়। দুই terminal-এ node চালানোয় kernel দুইটা আলাদা process বানিয়েছে: আলাদা PID, আলাদা address space। count variable প্রতিটার নিজের address space-এ আছে, তাই একটার ++count অন্যটার কিছুই ছোঁয় না। আর এই আলাদা থাকা শুধু variable-এ সীমাবদ্ধ না — একটা মরে গেলেও অন্যটা বাঁচে। শুরুর দুই loop চলা অবস্থায় তৃতীয় terminal থেকে চালাও (kill command একটা PID-কে থামার সংকেত পাঠায়):

kill 4101      # তোমার terminal 1-এ যে PID print হচ্ছে, সেটা বসাও

Terminal 1-এর loop থেমে যাবে; terminal 2 নির্বিকারে গুনে চলবে। এটাই Chapter 1-এর isolation, এবার process-এর ভাষায়: kernel প্রতিটা process-কে আলাদা খাঁচায় রাখে।

COMMON MISCONCEPTION

"একটা app মানে একটা process।" প্রায়ই না। Chrome প্রতিটা tab, প্রতিটা extension আর GPU-র কাজের জন্য আলাদা process চালায় — ps aux | grep -c "Google Chrome Helper" চালিয়ে দেখো (আমার machine-এ এই মুহূর্তে ৫টা; tab যত বেশি, সংখ্যা তত বেশি)। VS Code-ও তাই। উল্টো দিকে, npm run dev চালালে প্রায়ই npm একটা process, আর সে আরও কয়েকটা child process জন্ম দেয়। "App" হলো তোমার দেখার একক; kernel-এর একক হলো process।

Process-এর বংশ: parent আর child

Process আকাশ থেকে পড়ে না। নতুন process তৈরি করতে হলে একটা আগে থেকে চলমান process-কে kernel-এর কাছে syscall দিয়ে অনুরোধ করতে হয়। যে অনুরোধ করে সে parent, নতুনটা child। Kernel child-এর PCB-তে parent-এর PID লিখে রাখে — একে বলে PPID।

এই সম্পর্ক রাখার কারণ আছে: child শেষ হলে সে সফল হলো কি না — একটা ছোট সংখ্যা, যার নাম exit code (০ মানে সফল, অন্য যেকোনো মান মানে কোনো সমস্যা) — সেটা কাউকে জানাতে হবে। Kernel সেটা parent-কে জানায়। তোমার shell ঠিক এভাবেই জানে একটা command fail করেছে কি না, আর CI pipeline এভাবেই জানে npm test fail করেছে।

echo $$                                               # shell-এর নিজের PID
node -e "console.log(process.pid, process.ppid)"      # node-এর PID আর তার parent
node -e "process.exit(3)"; echo "exit code: $?"      # child-এর exit code parent পেল

আমার চালানোয় shell-এর PID 85530, আর node print করল 85532 85530 — node-এর parent সেই shell-ই। শেষ লাইন print করল exit code: 3।

তোমার Node code-ও parent হতে পারে। child_process module ঠিক এই কাজ করে:

const { spawnSync } = require('child_process');
console.log('parent pid:', process.pid);
spawnSync('node', ['-e', 'console.log("child  pid:", process.pid, "| its parent:", process.ppid)'], { stdio: 'inherit' });

Output: parent pid: 87154, তারপর child pid: 87158 | its parent: 87154। প্রতিটা process-এর parent আছে, তার parent আছে — পুরো গাছের গোড়ায় PID 1, যেটা kernel নিজে boot-এর শেষে চালু করে। ps -p 1 -o comm চালালে macOS-এ দেখবে /sbin/launchd, Linux-এ সাধারণত systemd বা init (Docker container-এর ভেতরে PID 1 হয় container-এর প্রথম command নিজেই — ওপরের experiment-এ PPid: 1 ছিল সেজন্য)। Kernel ঠিক কোন syscall দিয়ে নতুন process বানায় (fork, exec), সেটা Chapter 15-এ।
