PART 7 · NETWORKING AND SOCKETS

Chapter 29 — I/O Multiplexing

"এই হাজারটা socket-এর যেকোনোটায় কিছু এলে আমাকে জাগিও" — select, poll থেকে epoll পর্যন্ত বিবর্তন, মেপে দেখা কেন epoll হাজারো connection-এও একই দামে চলে, ২০ লাইনের একটা আসল event loop, আর Node-এর ভেতরের ছবি।

Chapter 28 শেষ হয়েছিল একটা চাহিদায়: একটা thread ঘুমাবে, কিন্তু সবগুলো socket-এর জন্য একসাথে, আর kernel তাকে জাগাবে ঠিক তখনই যখন কোনো একটায় কিছু ঘটেছে — সাথে বলে দেবে কোনটায়। একটা thread দিয়ে অনেক I/O channel সামলানোর এই কৌশলের নাম I/O multiplexing। Kernel গত চল্লিশ বছরে এর তিনটা প্রজন্ম দিয়েছে; পার্থক্যটা হলো "কে কী মনে রাখে"।

প্রথম চেষ্টা: select আর poll

select() আর poll()-এ প্রতিবার ডাকার সময় তুমি পুরো তালিকা দাও: "এই fd গুলোর মধ্যে কেউ ready হলে জাগিও।" Kernel প্রতিটা fd আলাদা করে দেখে, কেউ ready না হলে সবার অপেক্ষার তালিকায় তোমাকে বসায়, জাগলে আবার সবাইকে দেখে কে ready, তারপর পুরো তালিকা ফেরত দেয় — আর তুমি নিজে পুরো তালিকা ঘুরে খুঁজে বের করো কারা ready। পরের বার? আবার শূন্য থেকে, পুরো তালিকা নিয়ে। মানে প্রতিটা call-এর খরচ মোট connection-এর সংখ্যার সমানুপাতিক — ১০,০০০ connection থাকলে, মাত্র একটায় data এলেও, ১০,০০০-এর হিসাব। select-এর আরেকটা পুরনো সীমা: fd গুলো একটা নির্দিষ্ট মাপের bit-এর সারিতে পাঠাতে হয়, যেটা ১০২৪-এ থামে — ১০২৩-এর চেয়ে বড় নম্বরের fd সে ধরতেই পারে না।

epoll: তালিকা kernel-এর কাছেই থাকে

Linux-এর epoll প্রশ্নটা উল্টে দেয়: তালিকাটা প্রতিবার পাঠিয়ো না, একবার kernel-কে দিয়ে দাও, সে মনে রাখবে। তিনটা call:

  1. epoll_create1(): kernel-এর ভেতরে একটা নজরদারি object বানাও (এটাও একটা fd)।
  2. epoll_ctl(ADD, fd): "এই fd-র উপর নজর রাখো" — প্রতিটা fd-র জন্য একবারই। Kernel এটা নিজের interest list-এ রাখে।
  3. epoll_wait(): ঘুমাও; জাগলে শুধু ready fd-দের তালিকা হাতে পাবে।

জাদুটা ঘটে Chapter 27-এর আসার পথে: TCP যখন একটা socket-এর receive buffer-এ data রাখে আর "অপেক্ষায় থাকা কাউকে জাগাও" ধাপে পৌঁছায়, তখন epoll-এর নজরে থাকা socket হলে kernel সেটাকে একটা ready list-এ টুকে রাখে, আর epoll_wait-এ ঘুমন্ত thread-কে জাগায়। epoll_wait শুধু ready list-টা ফেরত দেয়। ফলে খরচ মোট connection-এর সংখ্যার উপর না, যতগুলো ready হয়েছে তার উপর নির্ভর করে। মেপে দেখি — N-টা চুপচাপ socket, যার মধ্যে শুধু একটায় data আছে; প্রতিটা পদ্ধতিতে "কে ready?" জিজ্ঞেস করার দাম:

EXPERIMENT (Linux / Docker) — watchcost.py
# watchcost.py (Linux) — N টা চুপচাপ socket-এর উপর নজর: select, poll আর epoll-এর দাম
import select, socket, time

def cost(n):
    pairs = [socket.socketpair() for _ in range(n)]     # প্রতিটা জোড়া = দুই প্রান্তের একটা নল
    fds = [a.fileno() for a, b in pairs]
    p = select.poll()
    for fd in fds: p.register(fd, select.POLLIN)
    e = select.epoll()
    for fd in fds: e.register(fd, select.EPOLLIN)
    pairs[-1][1].send(b'x')                              # শুধু শেষেরটায় data আছে

    def per_call(f, reps=200):
        t = time.perf_counter()
        for _ in range(reps): f()
        return (time.perf_counter() - t) / reps * 1e6
    line = f'{n:6d} sockets:  poll {per_call(lambda: p.poll(0)):8.1f} µs   epoll {per_call(lambda: e.poll(0)):6.1f} µs'
    try:
        select.select(fds, [], [], 0)
        line += '   select ok'
    except ValueError as err:
        line += f'   select: {err}'
    print(line)
    for a, b in pairs: a.close(); b.close()

for n in (10, 100, 1000, 10000):
    cost(n)

দশ হাজার connection-এ poll-এর একটা "কে ready?" জিজ্ঞাসা প্রায় ১ ms — প্রতি সেকেন্ডে হাজারবার জিজ্ঞেস করলে পুরো একটা core শুধু এতেই শেষ। epoll-এর দাম connection ১০ হোক বা ১০,০০০, একই ০.৩ µs। আর select ১০০০ connection-এর পরীক্ষাতেই হার মেনেছে, কারণ socket-জোড়া বানাতে বানাতে fd নম্বর ১০২৩ পেরিয়ে গেছে। ঘুমন্ত connection epoll-এ কার্যত বিনামূল্যে — C10K-এর আসল উত্তর এটাই।

অন্য OS-এর আত্মীয়: Mac আর BSD-তে kqueue (একই দর্শন: kernel তালিকা মনে রাখে, শুধু ঘটনাগুলো ফেরত দেয়)। Windows-এর IOCP আর Linux-এর io_uring অন্য দর্শনের — "ready হলে জানাও" না, "কাজটা শেষ হলে জানাও" (Chapter 24)। এই পার্থক্যের কারণেই libuv নামের একটা আলাদা library লেগেছিল: Node-এর জন্য সব OS-এর ব্যবস্থাকে একই চেহারা দেওয়া।

একটা event loop, ২০ লাইনে

এবার নিজে একটা event loop বানাই। Python-এর selectors module OS দেখে সবচেয়ে ভালো ব্যবস্থা বেছে নেয় — Linux-এ epoll, Mac-এ kqueue (আমার Mac-এ KqueueSelector):

EXPERIMENT (Linux / Docker) — tiny_loop.py
# tiny_loop.py — এক thread, এক event loop, হাজারো connection (Linux-এ ভেতরে epoll, Mac-এ kqueue)
import selectors, socket

sel = selectors.DefaultSelector()
srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(('127.0.0.1', 9002)); srv.listen(4096)
srv.setblocking(False)
sel.register(srv, selectors.EVENT_READ, 'accept')      # "নতুন connection এলে জানিও"
print('selector:', type(sel).__name__, flush=True)

while True:
    for key, _ in sel.select():                        # ঘুমাও; কেউ ready হলে জাগো
        if key.data == 'accept':
            conn, _ = srv.accept()
            conn.setblocking(False)
            sel.register(conn, selectors.EVENT_READ, 'echo')
        else:
            data = key.fileobj.recv(4096)
            if data:
                key.fileobj.send(data)                 # echo (ছোট data, send buffer-এ জায়গা আছে ধরে নিচ্ছি)
            else:
                sel.unregister(key.fileobj); key.fileobj.close()

একটা thread, ৫২ ms — Chapter 28-এর ১০০১-thread-এর Python server-এর (৩৮২ ms) চেয়ে সাত গুণ দ্রুত, আর Node-এর (৪৮ ms) প্রায় সমান, একই ভাষা Python হওয়া সত্ত্বেও। পুরো loop-টার গঠন: listening socket আর প্রতিটা connection-এর socket নজরে দাও; ঘুমাও; জাগলে শুধু ready গুলোর কাজ করো — নতুন connection হলে accept করে নজরে যোগ করো, data হলে পড়ো আর উত্তর দাও; আবার ঘুমাও। nginx, Redis, Node — সবার হৃদপিণ্ড এই কয়েক লাইন। (একটা সরলীকরণ করেছি: বড় উত্তর হলে send buffer ভরে যেতে পারে, তখন "লেখার জায়গা হলে জানিও" — EVENT_WRITE — নজরেও দিতে হয়; Chapter 27-এর backpressure।)

Node-এর ভেতরে

Node-এর event loop (libuv) ঠিক এই কাঠামো, কয়েকটা বাড়তি ধাপ সহ। প্রতিটা পাক মোটামুটি এরকম: সময় হয়ে যাওয়া timer-এর callback চালাও → epoll-এ ঘুমাও, কিন্তু বড়জোর পরের timer পর্যন্ত (তাই setTimeout সময়মতো চলে) → জেগে ready fd-দের callback চালাও → setImmediate-এর callback → বন্ধ হওয়া জিনিসের callback → আবার। আর Chapter 24 থেকে মনে রাখো: file-এর কাজ epoll-এ যায় না, thread pool-এ যায়; pool শেষ হলে eventfd-তে লেখে, আর সেই eventfd-ও epoll-এর নজরে — তাই file-এর খবরও একই ঘুম ভাঙায়। Node server-এর উপর একই burst চালিয়ে system call গুনি:

Event loop-এর এক পাক। Loop epoll_wait-এ kernel-এ ঘুমায়; packet আসতেই kernel socket-টা ready list-এ টুকে loop-কে জাগায়; loop শুধু ready socket-গুলোর callback চালায় (নীল, JS), তারপর timer দেখে আবার ঘুমায়। এক callback দীর্ঘক্ষণ চললে loop আর epoll_wait-এ ফিরতে পারে না — বাকি সবার data kernel-এর buffer-এ পড়ে থাকে।

এবার Chapter 19-এর সেই পরীক্ষাটা (main thread-এ password hash, /ping-এর উত্তর ৪৩২ ms) kernel-এর চোখে দেখো: ওই সময় kernel নিজের কাজ ঠিকই করছিল — নতুন connection-এর handshake, আসা data receive buffer-এ, socket গুলো ready list-এ। শুধু যে thread-এর epoll_wait ডেকে ready list তোলার কথা, সে তখন hash করছে। তাই event loop-এ CPU-ভারী synchronous কাজ বিষ: সেই পুরো সময়টা server-এর প্রতিটা client-এর জন্য জমাট।

COMMON MISCONCEPTION

"Node single-threaded, তাই একসাথে একটাই request সামলাতে পারে।" একসাথে একটাই callback চালায় — কিন্তু request-এর জীবনের বেশিরভাগ সময় অপেক্ষা (network, database), আর সেই অপেক্ষা epoll-এ জমা থাকে, কোনো thread আটকে না রেখে। tiny_loop.py-র একটা thread ১০০০ connection একসাথে ধরে রেখে ১০,০০০ echo ৫২ ms-এ শেষ করেছে। সীমাটা আসে কেবল তখন, যখন একটা callback নিজেই CPU-তে দীর্ঘক্ষণ চলে (Chapter 19)।

MENTAL MODEL

select/poll: প্রতিবার পুরো তালিকা নিয়ে kernel-এর কাছে যাও, kernel সবাইকে দেখে — খরচ ∝ মোট connection। epoll/kqueue: তালিকা একবার kernel-কে দিয়ে দাও; data আসার মুহূর্তেই kernel ready list-এ টুকে রাখে; epoll_wait শুধু সেটুকু দেয় — খরচ ∝ ready connection, ঘুমন্ত connection বিনামূল্যে। Event loop = ঘুমাও → ready গুলোর ছোট ছোট কাজ সারো → আবার ঘুমাও। শর্ত একটাই: প্রতিটা কাজ ছোট হতে হবে।
