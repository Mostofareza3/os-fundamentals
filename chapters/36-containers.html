PART 10 · VIRTUALIZATION AND CONTAINERS

Chapter 36 — Containers

Docker-এর ভেতরের সত্য: container একটা সাধারণ process, যাকে kernel আলাদা করে দেখায় (namespace), সীমায় বাঁধে (cgroup), আর ক্ষমতা ছেঁটে দেয় (capabilities, seccomp)। সাথে Node-এর দুটো container-ফাঁদ, মেপে: ভুল CPU গোনা আর CPU limit-এর throttling।

আগের chapter-এর শেষে একটা প্রশ্ন রেখেছিলাম। প্রতিটা VM-এ আস্ত একটা OS চলে: নিজের kernel, নিজের boot, শত শত MB memory। অথচ এই বইয়ে আমরা এক সেকেন্ডের কম সময়ে ডজন ডজন container চালিয়েছি। কীভাবে? কারণ container কোনো VM না। Container-এর ভেতরে কোনো kernel নেই, নকল hardware নেই। এই chapter-এ সেটা নিজের চোখে দেখব, আর দেখব এই বইয়ের কোন কোন পুরনো জিনিস জোড়া দিয়ে container তৈরি।

Container মানে একটা সাধারণ process

একটা container চালাও, আর তাকে দুই দিক থেকে দেখো: container-এর ভেতর থেকে, আর যে Linux kernel তাকে চালাচ্ছে তার দিক থেকে। Mac-এ সেই kernel হলো Docker-এর VM (Chapter 35)। --pid=host দিয়ে চালানো একটা container VM-এর সব process দেখতে পায়:

# proc.sh — একটা container, দুই চোখে
docker run -d --name osbook-demo node:22-alpine node -e "setInterval(() => {}, 1000)" > /dev/null
sleep 1
echo "--- container-এর ভেতর থেকে"
docker exec osbook-demo ps -o pid,user,args
echo "--- VM-এর চোখে (host-এর PID namespace)"
docker run --rm --pid=host alpine ps -o pid,user,args | grep setInterval
echo "--- docker-এর হিসাবে: $(docker inspect -f '{{.State.Pid}}' osbook-demo)"
docker rm -f osbook-demo > /dev/null
--- container-এর ভেতর থেকে
PID   USER     COMMAND
    1 root     node -e setInterval(() => {}, 1000)
   14 root     ps -o pid,user,args
--- VM-এর চোখে (host-এর PID namespace)
88055 root     node -e setInterval(() => {}, 1000)
--- docker-এর হিসাবে: 88055

একই process, দুটো PID। Container-এর ভেতরে সে PID ১, আর তার সাথে আছে শুধু ps নিজে। VM-এর kernel-এর চোখে সে একটা সাধারণ process, PID ৮৮০৫৫, বাকি শত শত process-এর পাশেই। Container চালু করা মানে তাই কোনো OS boot করা না, একটা process চালু করা। এজন্যই সেটা এক সেকেন্ডের কম সময় নেয়। আসল Linux server-এ (Mac ছাড়া) ps aux চালালেই container-এর process-গুলো এভাবে দেখা যায়, আলাদা কিছু লাগে না।

(Test container-এর নাম দিয়েছি osbook-demo, a বা demo1-এর মতো ছোট নাম না। কারণ docker rm বা exec ওই নামের container না পেলে নামটাকে container ID-র শুরুর অংশ হিসেবে খোঁজে। ID-গুলো শুধু 0–9 আর a–f দিয়ে তৈরি, তাই a নামটা তোমার অন্য কোনো চালু container-এর ID-র সাথে মিলে যেতে পারে। নামে a–f-এর বাইরের একটা অক্ষর রাখলে সেই ভয় থাকে না।)

বাঁয়ে VM: প্রতিটার নিজের kernel, মাঝে hypervisor। ডানে container: সবাই একই kernel-এর উপর সাধারণ process; আলাদা থাকার ব্যবস্থা সেই kernel-এর ভেতরে। Amber dashed রেখা user/kernel সীমানা।

Namespace: কী দেখতে পাবে

একটা process "নিজেকে আলাদা machine-এ" ভাবে কীভাবে? Kernel-এর namespace দিয়ে। একটা namespace kernel-এর কোনো একটা বিশ্বব্যাপী তালিকার আলাদা একটা কপি। Chapter 9-এ প্রতিটা process-কে নিজের address space দিয়েছিলাম; namespace একই কাজ করে PID, network, file-এর গাছ আর hostname-এর জন্য। প্রতিটা process কোন কোন namespace-এ আছে, kernel সেটা /proc/self/ns/-এ দেখায়:

Namespaceযা আলাদা করেContainer-এ ফল
pidprocess নম্বরের তালিকানিজে PID ১, বাইরের কাউকে দেখে না
netnetwork interface, IP, port, routingনিজের localhost, নিজের port ৩০০০ (Chapter 25)
mntকোন filesystem কোথায় mount করাimage-এর file-গুলোই /
utshostnameনিজের নাম (container ID)
ipc, cgroup, usershared memory, cgroup-এর তালিকা, uid-এর মানেবাকি জিনিসগুলোও আলাদা
# ns.sh — দুটো container একসাথে চালু রেখে, প্রত্যেকের namespace-এর পরিচয় নম্বর
ids='for f in pid net mnt uts; do printf "%s  " "$(readlink /proc/self/ns/$f)"; done; echo'
docker run -d --name osbook-one alpine sleep 60 > /dev/null &&
docker run -d --name osbook-two alpine sleep 60 > /dev/null &&
echo "osbook-one: $(docker exec osbook-one sh -c "$ids")" &&
echo "osbook-two: $(docker exec osbook-two sh -c "$ids")" &&
echo "the VM:     $(docker run --rm --pid=host --net=host --uts=host alpine sh -c "$ids")"
docker rm -f osbook-one osbook-two > /dev/null
osbook-one: pid:[4026532561]  net:[4026532563]  mnt:[4026532558]  uts:[4026532559]
osbook-two: pid:[4026532696]  net:[4026532698]  mnt:[4026532693]  uts:[4026532694]
the VM:     pid:[4026531836]  net:[4026531840]  mnt:[4026532828]  uts:[4026531838]

প্রতিটা container-এর চার namespace-এর নম্বর আলাদা। তৃতীয় লাইনে --pid=host --net=host --uts=host বলেছে "এই তিনটায় আলাদা কপি দিও না", তাই সে VM-এর আসল namespace-এ বসেছে। Kernel boot-এর সময় যে প্রথম namespace-গুলো বানায়, তাদের নম্বর এমন ছোট 40265318xx। Mount namespace আলাদাই রয়ে গেছে, কারণ সেটা ভাগ করতে বলিনি।

Docker ছাড়াও namespace বানানো যায়। Linux-এর unshare command ঠিক এটাই করে: "নতুন namespace-এ এই command চালাও"। Docker-এর কাজের মূল অংশ হাতে করে দেখা যাক:

EXPERIMENT (Linux / Docker) — mini.sh
# mini.sh — Docker ছাড়া, শুধু namespace দিয়ে একটা "container"
apk add -q util-linux                               # unshare command-টা এখানে
echo "outside: hostname=$(hostname), processes: $(ps -o pid | tail -n +2 | wc -l)"
unshare --uts --pid --fork --mount-proc sh -c '
  hostname mini                                     # নিজের UTS namespace: নাম বদলানো যায়
  echo "inside:  hostname=$(hostname), my PID=$$"
  ps -o pid,args; true'
echo "outside: hostname=$(hostname)"
docker run --rm --cap-add SYS_ADMIN --security-opt seccomp=unconfined -v "$PWD":/w:ro -w /w alpine sh mini.sh
outside: hostname=1eebc2d1d698, processes: 5
inside:  hostname=mini, my PID=1
PID   COMMAND
    1 sh -c    hostname mini    ...
    4 ps -o pid,args
outside: hostname=1eebc2d1d698

(ps-এর লম্বা লাইনটা ছোট করেছি।) unshare-এর ভেতরের shell নিজেকে PID ১ দেখে। তার ps বাইরের পাঁচটা process-এর কাউকে দেখে না। Hostname বদলেছে, অথচ বাইরে বের হতেই আগের নাম। Container runtime-এর বাকি কাজ হলো এর সাথে image-এর file-গুলোকে / হিসেবে mount করা (নিচে), network জোড়া দেওয়া, আর সীমা বসানো। Chapter 31-এর কথা মনে করো: hostname বদলাতে CAP_SYS_ADMIN লাগে। এখানে তাই --cap-add SYS_ADMIN দিয়েছি, আর seccomp=unconfined, কারণ Docker-এর seccomp নিয়ম container-এর ভেতরে নতুন namespace বানানো আটকে রাখে। এই দুটো ছাড়া চালালে পাবে unshare failed: Operation not permitted।

PID namespace-এর বাসা। বাইরের (VM-এর) namespace সব process দেখে, container-এরটাও। Container-এর ভেতরের namespace শুধু নিজেদের দেখে। proc.sh-এর node একই process, বাইরে ৮৮০৫৫, ভেতরে ১।

cgroup: কতটা পাবে

Namespace ঠিক করে একটা process কী দেখবে, কিন্তু কতটা খাবে সেটা না। একটা container-এর memory leak পুরো machine-এর RAM খেয়ে ফেললে বাকি সবাই ভুগবে। cgroup (control group) হলো kernel-এর হিসাবের খাতা: একদল process-এর memory, CPU, I/O একসাথে গোনা আর সীমা বসানো। Chapter 23-এ দেখেছি page cache-ও এই খাতায় ওঠে। Docker-এর --memory আর --cpus, Kubernetes-এর resources.limits — সবাই শেষ পর্যন্ত /sys/fs/cgroup/-এর কয়েকটা file-এ সংখ্যা লেখে। প্রশ্ন হলো, Node এই সীমা কতটা বোঝে:

// limits.js — container-এর সীমা Node কতটা বোঝে?
const os = require('os'), fs = require('fs'), v8 = require('v8');
const read = (f) => { try { return fs.readFileSync('/sys/fs/cgroup/' + f, 'utf8').trim(); } catch { return '-'; } };
console.log(`cgroup memory.max: ${read('memory.max')}, cpu.max: ${read('cpu.max')}`);
console.log(`os.cpus().length: ${os.cpus().length}, os.availableParallelism(): ${os.availableParallelism()}`);
console.log(`os.totalmem(): ${(os.totalmem() / 2 ** 20).toFixed(0)} MB, ` +
            `V8 heap limit: ${(v8.getHeapStatistics().heap_size_limit / 2 ** 20).toFixed(0)} MB`);
# limits.sh — একই limits.js, তিন রকম সীমায়; তারপর availableParallelism() আলাদা --cpus-এ
for limit in "" "--memory 256m --cpus 0.5" "--cpus 2"; do
  echo "== ${limit:-no limit}"
  docker run --rm $limit -v "$PWD":/w:ro -w /w node:22-bookworm-slim node limits.js
done
for c in 0.5 1 1.5 2.5; do
  echo "--cpus $c → availableParallelism() = $(docker run --rm --cpus $c node:22-bookworm-slim node -p 'require("os").availableParallelism()')"
done

প্রথমে cgroup file-দুটো পড়ো। memory.max byte-এ সীমা (২৬৮৪৩৫৪৫৬ = ২৫৬ MB)। cpu.max-এ দুটো সংখ্যা: "প্রতি ১,০০,০০০ µs-এ (১০০ ms) সর্বোচ্চ ৫০,০০০ µs CPU"। মানে --cpus 0.5 কোনো core ভাগ করে দেয় না। সে সময়ের একটা কোটা দেয়, আর সেটা পরে গুরুত্বপূর্ণ হবে।

এবার Node-এর দিক। os.cpus() আর os.totalmem() সীমা একদমই দেখে না; তারা VM-এর ১২টা core আর ৭.৭ GB বলে। availableParallelism() কোটাকে নিচের দিকে গোল করে: ২.৫ হলে ২, ১.৫ হলে ১। কিন্তু ১-এর কম হলে (০.৫) সে হাল ছেড়ে সব core, মানে ১২ বলে। Kubernetes-এ cpu: 500m-এর মতো সীমা খুব সাধারণ। তাই availableParallelism() দিয়ে worker pool বানালে আধা CPU-র pod-এ ১২টা worker তৈরি হবে, আর সবাই মিলে একই আধা CPU নিয়ে কাড়াকাড়ি করবে (Chapter 17-এর oversubscription)। Container-এ pool-এর আকার তাই config থেকে দাও, অনুমানের উপর ছেড়ো না।

V8 উল্টো দিকে একটু বেশি চালাক: heap-এর সীমা memory cgroup দেখে ঠিক করে, ২০৯৬ MB থেকে নেমে ২৫৯ MB। কিন্তু ২৫৯ মানে পুরো container-এর সীমারও বেশি, অথচ node-এর heap-এর বাইরেও memory লাগে (code, Buffer, thread-এর stack)। swap ছাড়া (Kubernetes-এ সাধারণত যেমন থাকে) JS object দিয়ে memory ভরালে দেখো কী হয়:

// grow.js — JS object দিয়ে memory ভরাতে থাকো, আর দেখো কে আগে থামায়
const keep = [];
let mb = 0;
setInterval(() => {
  for (let i = 0; i < 10; i++) keep.push(new Array(128 * 1024).fill(mb));  // ~১০ MB JS heap
  mb += 10;
  if (mb % 50 === 0) console.log(`${mb} MB of JS objects so far`);
}, 5);
# oom.sh — ২৫৬ MB-এর container (swap ছাড়া), JS heap ভরানো: default আর ছোট heap limit
for heap in "" "--max-old-space-size=160"; do
  echo "== node ${heap:-(default heap limit)}"
  docker run --rm --memory 256m --memory-swap 256m -v "$PWD":/w:ro -w /w node:22-bookworm-slim sh -c "
    node $heap grow.js > /tmp/out 2>&1; code=\$?
    grep -E 'MB of|FATAL' /tmp/out | tail -2; echo \"exit \$code\""
done

Default-এ V8 ভেবেছে তার এখনো জায়গা আছে, কিন্তু cgroup-এর সীমা আগে এসে গেছে। Kernel-এর OOM killer (Chapter 10) SIGKILL পাঠিয়েছে: exit ১৩৭, কোনো error message নেই, log-এ কিছু নেই। Kubernetes শুধু বলবে "OOMKilled"। Heap-এর সীমা container-এর সীমার নিচে বেঁধে দিলে (এখানে ১৬০ MB, মোটামুটি ৬০–৭৫%) ব্যাপারটা বদলে যায়। V8 নিজেই থামে, পরিষ্কার "heap out of memory" message দেয় (exit ১৩৪ = ১২৮ + SIGABRT-এর ৬), আর তুমি জানো সমস্যাটা JS heap-এ।

এবার CPU-র কোটা। cpu.max = 50000 100000 মানে প্রতি ১০০ ms-এর পর্বে (period) এই দল মোট ৫০ ms CPU পাবে। কোটা শেষ হলে পর্ব শেষ হওয়া পর্যন্ত দলের সব thread-কে থামিয়ে রাখা হয়। এর নাম throttling। গড় হিসাবে এটা ন্যায্য, কিন্তু একটা একক request-এর জন্য কী মানে?

EXPERIMENT (Docker) — throttle.js
// throttle.js — ১০টা "request", প্রতিটায় ~১৫০ ms-এর CPU কাজ, মাঝে ৩০০ ms বিরতি
const fs = require('fs');
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
function handle() {                                    // request-এর কাজ: শুধু গোনা
  let s = 0;
  for (let i = 0; i < 190e6; i++) s += i;
  return s;
}
(async () => {
  const wall = [], cpu = [];
  for (let r = 0; r < 10; r++) {
    const t0 = performance.now(), c0 = process.cpuUsage().user;
    handle();
    wall.push(performance.now() - t0);
    cpu.push((process.cpuUsage().user - c0) / 1000);
    await sleep(300);                                  // পরের request আসার আগে বিরতি
  }
  const med = (a) => a.sort((x, y) => x - y)[a.length >> 1].toFixed(0);
  console.log(`per request: CPU time ${med(cpu)} ms, wall time ${med(wall)} ms (medians)`);
  const stat = fs.readFileSync('/sys/fs/cgroup/cpu.stat', 'utf8');
  console.log(stat.split('\n').filter((l) => /^(nr_periods|nr_throttled|throttled_usec)/.test(l)).join(', '));
})();
# throttle.sh
for limit in "" "--cpus 1" "--cpus 0.5"; do

প্রতিটা request-এর কাজ ~১৫০ ms CPU। সীমা না থাকলে বা ১ CPU হলে সেটা ১৫২ ms-এই শেষ। ০.৫ CPU-তে একই কাজ ২৯২ ms, প্রায় দ্বিগুণ। ১০টা request-এ ৩০ বার throttle, মোট ১.২৫ সেকেন্ড থামিয়ে রাখা। অথচ গড় হিসাবে এই process CPU চেয়েছে ১৫০ ms কাজ + ৩০০ ms বিরতি, মানে মাত্র ৩৩%, সীমার (৫০%) অনেক নিচে। গড় ঠিক আছে, কিন্তু প্রতিটা request-এর latency দ্বিগুণ। কারণ ১৫০ ms-এর একটানা কাজ ৫০ ms-এর টুকরোয় ভাগ হয়ে যায়, আর প্রতিটা টুকরোর পরে পর্বের বাকি অংশ অপেক্ষা।

একটা request, দুই অবস্থায়। সীমা না থাকলে ১৫০ ms-এর কাজ একটানা শেষ। --cpus 0.5-এ প্রতি ১০০ ms-এর পর্বে ৫০ ms চলার পরে পর্বের বাকিটা থামিয়ে রাখা (লাল), তাই একই কাজ শেষ হয় অনেক পরে। (ছবিটা ছকে আঁকা; মাপা সংখ্যা নিচে লেখা।)

Kubernetes-এ CPU limit দেওয়া Node service-এর P99 latency রহস্যজনকভাবে খারাপ হওয়ার একটা সাধারণ কারণ এটা। cpu.stat-এর nr_throttled দেখলেই ধরা পড়ে। সমাধান সাধারণত এই তিনের একটা: limit বাড়ানো, CPU request দিয়ে limit তুলে দেওয়া, বা ভারী কাজ ছোট টুকরোয় ভাগ করা (Chapter 19)।

Image আর overlayfs: file-গুলো কোথা থেকে আসে

Container-এর /-এ Debian বা Alpine-এর পুরো file-এর গাছ আছে। কিন্তু সেটা kernel না, শুধু file (Chapter 22)। Image হলো কয়েকটা layer-এর স্তূপ, প্রতিটা একটা file-এর সংকলন (base OS, তার উপর Node, তার উপর তোমার app)। Container চালু হলে overlayfs (Chapter 22) layer-গুলো read-only হিসেবে একটার উপর আরেকটা বসায়, আর সবার উপরে container-এর নিজের একটা খালি, লেখা-যোগ্য স্তর দেয়:

# layers.sh — image-এর স্তর, আর container যা বদলায় তা কোথায় যায়
docker image inspect node:22-bookworm-slim -f 'image layers: {{len .RootFS.Layers}}'
docker run --name osbook-diff node:22-bookworm-slim sh -c '
  echo hello > /tmp/new.txt                   # নতুন file
  rm /etc/debian_version                      # image-এর একটা file মোছা
  opts=$(grep " / " /proc/mounts | cut -d" " -f4)
  echo "root is: $(grep " / " /proc/mounts | cut -d" " -f3)"
  echo "read-only lower dirs: $(echo "$opts" | tr "," "\n" | grep ^lowerdir= | tr ":" "\n" | wc -l)"
  echo "$opts" | tr "," "\n" | grep ^upperdir= | cut -c1-70'
docker diff osbook-diff
docker rm osbook-diff > /dev/null
docker run --rm node:22-bookworm-slim cat /etc/debian_version   # নতুন container: image অক্ষত

Image-এর ৫টা layer, আর Docker-এর নিজের ছোট একটা (/etc/hosts-এর মতো file-এর জন্য), মোট ৬টা read-only স্তর। Container যা লেখে, সব যায় upperdir-এ। docker diff সেটাই দেখায়: A যোগ হয়েছে, D মোছা হয়েছে, C বদলেছে। "মোছা" আসলে উপরের স্তরে একটা চিহ্ন, যেটা নিচের file-টাকে লুকিয়ে রাখে। Image নিজে কখনো বদলায় না, তাই পরের container /etc/debian_version আবার পেয়েছে।

এর দুটো সুবিধা আছে। দশটা container একই image থেকে চালালে disk-এ image একবারই থাকে। আর যেহেতু নিচের file-গুলো একই, তাদের page cache-ও (Chapter 23) একবার থাকে: দশটা node container-এর node binary RAM-এ একটাই, Chapter 33-এর shared library-র মতো। Container যত file লেখে, সেগুলো container মুছলেই হারায়। আর image-এ আগে থেকে থাকা একটা বড় file-এ এক byte বদলালেও overlayfs পুরো file-টা আগে উপরের স্তরে copy করে নেয় (copy-up)। তাই database-এর data-র মতো জিনিস রাখা হয় volume-এ, মানে overlayfs এড়িয়ে সরাসরি host-এর একটা folder-এ।

নিরাপত্তা: এক kernel, অনেক ঘর

Container-এর সবচেয়ে বড় সুবিধা, মানে একটাই kernel, সেটাই তার সবচেয়ে বড় দুর্বলতা। প্রতিটা container একই kernel-এর কাছে syscall করে (docker run --rm alpine uname -r সবখানে 6.10.14-linuxkit)। Kernel-এর একটা bug মানে সব container-এর bug। VM-এ মাঝে hypervisor-এর দেয়াল ছিল; এখানে দেয়াল হলো kernel-এর নিজের নিয়ম। তাই Docker কয়েক স্তরের সুরক্ষা একসাথে বসায়:

  • Namespace — অন্যদের process, network, file দেখতেই দেয় না।
  • Capabilities (Chapter 31) — container-এর root uid=0, আর proc.sh-এ দেখলে VM-এর চোখেও সে root। কিন্তু ৪১টা capability-র মাত্র ১৪টা পায়।
  • Seccomp — kernel-এর একটা filter, যেটা একটা process-এর জন্য কিছু syscall দরজাতেই আটকে দেয় (কখনো পুরোপুরি, কখনো নির্দিষ্ট argument-এ), kernel-এর আসল কাজ শুরুর আগেই। Docker-এর default নিয়ম কয়েক ডজন বিপজ্জনক বা কম-দরকারি syscall আটকায়। grep Seccomp /proc/self/status container-এ দেখায় 2 (filter চালু), আর --security-opt seccomp=unconfined দিলে 0।
  • cgroup — একজন সবার resource খেয়ে ফেলতে পারে না।

এই বইয়ে experiment-এর জন্য এর কয়েকটা ইচ্ছে করে ঢিলা করেছি। কোনটা কী খুলেছে, একসাথে দেখে নাও:

Production-এ দিক উল্টো: --user দিয়ে root না হয়ে চালাও, অপ্রয়োজনীয় capability ফেলে দাও (--cap-drop ALL, তারপর যা লাগে শুধু সেটা যোগ), আর --privileged কখনো না। কারো অচেনা code চালাতে হলে (যেমন user-এর দেওয়া script) শুধু container-এর উপর ভরসা করা হয় না। তখন ব্যবহার হয় VM, বা মাঝামাঝি কিছু: প্রতিটা container-কে নিজের ছোট VM দেওয়া (Firecracker, Kata), বা syscall-গুলো একটা আলাদা user-space kernel-এ ধরা (gVisor)।

COMMON MISCONCEPTION

"Container হলো হালকা একটা VM।" না। VM-এ আলাদা kernel, নকল hardware, hypervisor-এর দেয়াল। Container-এ এর কোনোটাই নেই: সে একটা process (proc.sh-এর ৮৮০৫৫), যাকে kernel আলাদা করে দেখায় (namespace), সীমায় বাঁধে (cgroup) আর ক্ষমতা ছাঁটে (capability, seccomp)। এই পার্থক্য থেকেই সব আসে। Container এক সেকেন্ডে চালু হয়, কারণ OS boot নেই। Linux container-এর Linux kernel লাগে, তাই Mac-এ Docker-কে একটা VM চালাতে হয় (Chapter 35)। আর isolation VM-এর মতো শক্ত না, কারণ kernel সবার এক।

MENTAL MODEL

Container = একটা সাধারণ Linux process + চারটা kernel feature, যার সবগুলো এই বইয়ে আগেই দেখেছ। Namespace ঠিক করে সে কী দেখবে: নিজের PID ১, নিজের network, নিজের file-গাছ। cgroup ঠিক করে সে কতটা পাবে: memory.max পেরোলে OOM kill (১৩৭), আর cpu.max একটা সময়ের কোটা, যেটা লম্বা request-কে টুকরো করে থামিয়ে রাখে। Capability আর seccomp ঠিক করে সে kernel-এর কাছে কী চাইতে পারবে। File আসে image-এর read-only layer থেকে, overlayfs দিয়ে, উপরে container-এর নিজের পাতলা লেখার স্তর। Node-এর জন্য দুটো শিক্ষা: os.cpus() সীমা দেখে না, আর availableParallelism() ১-এর কম CPU-তে ভুল বলে; আর heap-এর সীমা container-এর সীমার নিচে বেঁধে দাও।

CAN I EXPLAIN THIS?
  • proc.sh-এ একই node process ভেতরে PID ১ আর বাইরে ৮৮০৫৫ কেন? Container চালু হতে VM-এর চেয়ে এত কম সময় লাগে কেন?
  • ns.sh-এ দুই container-এর namespace নম্বর আলাদা, কিন্তু --pid=host-ওয়ালা container-এর pid নম্বর VM-এর সাথে মেলে কেন? mini.sh কেন SYS_ADMIN আর seccomp=unconfined ছাড়া চলে না?
  • --memory 256m-এ V8-এর heap limit ২৫৯ MB হলো, আর grow.js exit ১৩৭ দিয়ে কোনো message ছাড়াই মরল। --max-old-space-size=160 দিলে কী বদলাল, আর কেন?
  • cpu.max = 50000 100000 মানে কী? throttle.js-এ গড় CPU ব্যবহার সীমার নিচে থেকেও প্রতিটা request প্রায় দ্বিগুণ সময় নিল কেন? --cpus 0.5-এ availableParallelism() ১২ বললে worker pool-এর কী হবে?
  • layers.sh-এ container /etc/debian_version মুছল, তবু পরের container সেটা পেল কেন? দশটা একই image-এর container-এ node binary RAM-এ কয়বার থাকে? আর এক kernel ভাগ করা নিরাপত্তার দিক থেকে কেন ঝুঁকি?
