PART 10 · VIRTUALIZATION AND CONTAINERS

Chapter 35 — Virtualization

এক hardware-এ কয়েকটা আস্ত OS কীভাবে চলে: hypervisor, guest kernel-কে ফাঁকি দেওয়া (trap-and-emulate), দুই ধাপের memory অনুবাদ, virtio device — আর মেপে দেখা কোথায় VM প্রায় বিনামূল্যে, কোথায় দাম দিতে হয় (steal time)।

এই বইয়ের প্রায় সব Linux experiment চলেছে Docker-এ, আমার Mac-এ। অথচ Mac-এর kernel Linux না, XNU (Chapter 1)। তাহলে uname "Linux" বলল কীভাবে? উত্তর এই chapter: Docker Desktop চুপচাপ একটা আস্ত Linux machine চালাচ্ছে, যেটা আসলে software দিয়ে বানানো। Cloud-এ তুমি যে "server" ভাড়া নাও, সেটাও প্রায় নিশ্চিতভাবে এমনই একটা machine।

এক machine-এ অনেক OS: বাধাটা কোথায়

একটা বড় server-এর CPU আর RAM একজন ছোট customer-এর কাজে বেশিরভাগ সময় অলস পড়ে থাকে। ভাগ করতে পারলে সস্তা হয়। কিন্তু প্রত্যেক customer চায় নিজের OS, নিজের kernel version, নিজের root। সমস্যা হলো, একটা kernel ধরেই নেয় machine-টা তার একার: সে kernel mode-এ চলে, page table নিজে লেখে, device-এর register সরাসরি ছোঁয়, interrupt বন্ধ করে (Chapter 31)। দুটো kernel একই disk controller-কে একসাথে নির্দেশ দিলে বা একই page table লিখলে দুজনেই ভেঙে পড়বে।

তাই Chapter 9-এর সেই কৌশল, এক ধাপ উপরে। OS যেমন প্রতিটা process-কে বলে "memory তোমার একার", তেমনি একটা নিচের স্তর প্রতিটা OS-কে বলে "machine তোমার একার"। শব্দগুলো:

  • Virtual machine (VM) — software দিয়ে বানানো একটা computer: virtual CPU (vCPU), virtual RAM, virtual disk, virtual network card।
  • Guest — VM-এর ভেতরে চলা OS, নিজের kernel সহ। Host — আসল machine, আর তার উপর চলা OS।
  • Hypervisor — যে software আসল hardware ভাগ করে VM-দের দেয়, আর guest-এর বিপজ্জনক কাজগুলো সামলায়। দুই রকম আছে। Type 1 সরাসরি hardware-এর উপর বসে (Xen, VMware ESXi; AWS-এর Nitro KVM-ভিত্তিক)। Type 2 একটা সাধারণ OS-এর উপর app-এর মতো চলে (VirtualBox, Parallels, UTM)। Linux-এর KVM আর macOS-এর Hypervisor.framework মাঝামাঝি: hypervisor host kernel-এর ভেতরেই একটা অংশ।

Docker Desktop macOS-এর hypervisor ব্যবস্থার উপর একটা ছোট Linux VM (LinuxKit) চালায়, আর সব container চলে সেই VM-এর Linux kernel-এর উপর। দুই দিক থেকে দেখো:

# Mac-এ
uname -srm
echo "CPUs: $(sysctl -n hw.ncpu), RAM: $(( $(sysctl -n hw.memsize) / 1048576 )) MB"
sysctl kern.hv_support                                     # CPU-তে virtualization support আছে?
# whereami.sh — Docker-এর Linux নিজের "machine"-কে কেমন দেখে
uname -srm
echo "CPUs: $(nproc), RAM: $(free -m | awk '/Mem:/ {print $2}') MB"
grep -m1 "CPU implementer" /proc/cpuinfo                  # 0x61 = Apple
for v in /sys/bus/virtio/devices/*; do basename "$(readlink -f "$v/driver")"; done | sort | uniq -c
echo "vda rotational: $(cat /sys/block/vda/queue/rotational)"
docker run --rm -v "$PWD":/w:ro -w /w alpine sh whereami.sh
# Mac

CPUs: 12, RAM: 24576 MB
kern.hv_support: 1
# Docker (whereami.sh)

একই physical machine, দুই রকম সত্য। Mac দেখছে XNU আর ২৪ GB RAM। VM-এর Linux দেখছে নিজের kernel (6.10.14-linuxkit) আর ৭.৭ GB RAM, কারণ hypervisor তাকে এতটুকুই দিয়েছে (Docker Desktop-এর settings-এ বদলানো যায়)। CPU-র পরিচয় আসলটাই (0x61 মানে Apple), কারণ guest-এর instruction আসল CPU-তেই চলে (পরের section)। আর device-এর তালিকায় একটাও "আসল" hardware নেই; সব virtio_*। সেগুলো সেকশন তিনে।

Trap-and-emulate: guest kernel-কে বিশ্বাস করিয়ে রাখা

সবচেয়ে সরল উপায় হতো guest-এর প্রতিটা instruction software দিয়ে নকল করা (emulation)। সেটা চলে, কিন্তু দশ-বিশ গুণ ধীর। আসল কৌশলটা উল্টো: guest-এর code যতটা সম্ভব সরাসরি আসল CPU-তে চালাও, আর শুধু বিপজ্জনক মুহূর্তগুলোতে থামাও।

এর জন্য CPU-তে user আর kernel mode-এর উপরে তৃতীয় আরেকটা স্তর আছে। ARM-এ EL2 (Chapter 31-এর EL0/EL1-এর উপরে), Intel/AMD-এ VT-x/AMD-V-এর "root mode"। Hypervisor চলে সেখানে। Guest-এর process চলে guest-এর EL0-তে, guest kernel চলে guest-এর EL1-এ, আর দুটোই আসল CPU-তে পূর্ণ গতিতে চলে। কিন্তু hypervisor CPU-কে বলে রাখে কোন কাজগুলো guest নিজে করতে পারবে না: আসল device-এর register ছোঁয়া, কিছু বিশেষ system register লেখা, CPU-কে ঘুম পাড়ানো। Guest kernel এমন কিছু করতে গেলেই CPU থেমে hypervisor-এ লাফ দেয়। এর নাম VM exit বা trap, Chapter 31-এর exception দরজারই আরেক ধাপ। Hypervisor কাজটার ফল নিজে তৈরি করে (emulate), তারপর guest-কে পরের instruction থেকে চালিয়ে দেয়। Guest kernel ভাবে কাজটা সে নিজেই করেছে।

২০০৫-০৬-এর আগে x86-এ কিছু বিপজ্জনক instruction trap না করে চুপচাপ অন্যরকম আচরণ করত। তখন VMware চলার সময় guest-এর code নিজেই বদলে লিখত, আর Xen guest kernel-কে বদলে নিতে বলত। Intel VT-x আর AMD-V এসে CPU-তে সরাসরি এই ব্যবস্থা যোগ করল, আর তখন থেকে সাধারণ কাজে VM প্রায় বিনামূল্যে। প্রমাণ, Chapter 31-এর spin.js (শুধু গোনা):

node spin.js                                                              # Mac-এ সরাসরি
docker run --rm -v "$PWD":/w:ro -w /w node:22-bookworm-slim node spin.js  # Linux VM-এর ভেতরে
pid 51776: user 1902 ms, sys 7 ms, involuntary switches 65
pid 1: user 1925 ms, sys 8 ms, involuntary switches 25

পার্থক্য ১%-এর মতো। Loop-এর একটা instruction-ও hypervisor-কে ডাকে না; ওগুলো একই M4 Pro core-এ একইভাবে চলে। VM-এর দাম আসে অন্য জায়গা থেকে: যখন ঘনঘন trap হয় (device, আর কিছু privileged কাজ), যখন memory অনুবাদ লম্বা হয় (পরের section), আর যখন অন্য কেউ তোমার CPU নিয়ে যায় (শেষ section)।

এই Mac-এর স্তরগুলো। Guest-এর process আর guest kernel দুটোই আসল CPU-তে চলে, শুধু guest-এর নিজের EL0/EL1-এ। Guest kernel device বা সুরক্ষিত register ছুঁতে গেলে CPU EL2-তে hypervisor-এর কাছে trap করে (লাল); hypervisor ফল বানিয়ে guest-কে আবার চালায় (amber dashed)।

Memory: দুই ধাপের অনুবাদ

Guest kernel নিজের process-দের জন্য page table বানায়, ঠিক Chapter 9-এর মতো: virtual ঠিকানা থেকে "physical" frame। কিন্তু guest যেটাকে physical ভাবছে, সেটা আসলে hypervisor-এর দেওয়া একটা কল্পিত জায়গা: guest physical address। আসল RAM-এর কোন frame সেটা, তা জানে শুধু hypervisor। তাই hypervisor প্রতিটা VM-এর জন্য দ্বিতীয় একটা table রাখে: guest physical থেকে host physical। ARM-এ এর নাম stage-2 translation, Intel-এ EPT, AMD-এ NPT।

আধুনিক MMU দুই table একসাথে hardware-এই হাঁটে, hypervisor-কে ডাকতে হয় না। দাম পড়ে TLB miss-এ (Chapter 9)। সাধারণ অবস্থায় একটা miss মানে table-এর ৪টা স্তর পড়া। VM-এ guest-এর table-এর প্রতিটা স্তরের ঠিকানা নিজেই একটা guest physical ঠিকানা, যেটাকে আবার stage-2 table দিয়ে অনুবাদ করতে হয়। ফলে সবচেয়ে খারাপ অবস্থায় একটা miss-এ ৪টার জায়গায় ২৪টা memory পড়া। TLB hit হলে কোনো বাড়তি দাম নেই, আর বেশিরভাগ access hit। তাই এই দাম শুধু সেই কাজে চোখে পড়ে যেটা বিশাল memory জুড়ে এলোমেলো ছোটে। VM-এ huge page (Chapter 10) এজন্য আরও বেশি কাজে লাগে: কম entry, কম হাঁটা।

VM-এ একটা ঠিকানার দুই ধাপের অনুবাদ। Guest kernel-এর table নিয়ে যায় একটা কল্পিত "physical" ঠিকানায়, hypervisor-এর stage-2 table সেখান থেকে আসল RAM-এ। TLB থাকায় বেশিরভাগ access-এ এই হাঁটাই লাগে না।

Guest-এর "৭.৭ GB RAM" তাই একটা প্রতিশ্রুতি, আগে থেকে আলাদা করে রাখা RAM না। Guest যে page এখনো ছোঁয়নি, সেটার জন্য host কোনো frame দেয়নি; Chapter 9-এর lazy allocation, এক স্তর উপরে। whereami.sh-এর তালিকার virtio_balloon এর উল্টো দিক সামলায়: guest-এর ভেতরে একটা driver, যেটা host চাইলে guest-এর কিছু অব্যবহৃত memory "ফুলিয়ে" দখল করে, যাতে host সেটা ফেরত পেয়ে অন্য কাউকে দিতে পারে।

Device: virtio, মানে guest জানে সে VM-এ

Guest-কে একটা নকল disk দিতে হবে। সবচেয়ে সরল উপায় হলো কোনো পরিচিত আসল disk controller হুবহু নকল করা, যাতে guest-এর পুরনো driver-ই কাজ করে। কিন্তু আসল controller-এর সাথে কথা মানে একটা একটা register-এ লেখা, আর VM-এ প্রতিটা register ছোঁয়া একটা trap। একটা read-এর জন্য কয়েক ডজন VM exit।

সমাধান হলো এমন device, যেটা VM-এর জন্যই বানানো, আর guest-এর driver জানে সে VM-এ আছে: virtio। কাজের অনুরোধ যায় guest আর host-এর মধ্যে ভাগ করা memory-র একটা ring-এ (Chapter 11-এর descriptor ring-এর মতো)। Guest ring-এ অনেকগুলো অনুরোধ জমা করে, আর একবার host-কে খবর দেয়, মানে একটা trap। Host কাজ সেরে ফলাফল ring-এ রাখে, আর একটা virtual interrupt দেয়। Chapter 32-এর batching, এবার VM-এর দরজায়।

whereami.sh-এর তালিকায় সবই virtio: network (virtio_net), disk (virtio_blk, VM-এর disk আসলে Mac-এর SSD-তে রাখা একটা বড় file), random number (virtio_rng), আর ছয়টা virtiofs। শেষেরটা Mac-এর folder সরাসরি guest-এ দেখায়। এই বইয়ে যতবার -v "$PWD":/w দিয়েছি, Mac-এর folder container-এ পৌঁছেছে এই পথে। আর vda rotational: 1 লাইনটা দেখো: virtual disk নিজেকে ঘোরানো HDD বলে পরিচয় দিচ্ছে (Chapter 20), অথচ নিচে আছে SSD। Guest জানে শুধু ততটুকু, যতটুকু hypervisor তাকে বলে।

COMMON MISCONCEPTION

"VM মানে emulation, তাই সবকিছু ধীর।" CPU-র কাজে VM প্রায় native: spin.js-এ ১%। দাম আসে তিনটা নির্দিষ্ট জায়গা থেকে। এক: trap, মানে device-এর সাথে কথা বা কিছু privileged কাজ, যেটা virtio অনেকটা কমিয়ে আনে। দুই: বিশাল memory জুড়ে এলোমেলো access-এ TLB miss, যেখানে দুই ধাপের অনুবাদ লাগে। তিন: steal, মানে তোমার vCPU চলতে চাইছে কিন্তু host অন্য কাউকে চালাচ্ছে। VM-এ কিছু ধীর লাগলে এই তিনটার কোনটা, সেটা আগে বের করো।

Steal time: তোমার CPU আসলে অন্য কারো

Hypervisor-এর কাছে প্রতিটা vCPU শুধু একটা thread, আর host-এর scheduler (Chapter 15) সেটা অন্য সব thread-এর সাথে চালায়। Cloud provider প্রায়ই যত core আছে তার চেয়ে বেশি vCPU বিক্রি করে (overcommit), কারণ সবাই একসাথে পুরো CPU চায় না। কিন্তু যখন চায়, তখন তোমার vCPU চলতে চাইলেও অপেক্ষা করে। Guest-এর দৃষ্টিতে সময় চলে যায়, অথচ তার কোনো instruction চলে না। এই হারানো সময়ের নাম steal time।

মেপে দেখা যাক। VM-এর ভেতরে ৮টা একই কাজ (spin.js) একসাথে চালাব: প্রথমে Mac চুপচাপ থাকা অবস্থায়, তারপর Mac-এর ১২টা core-কেই অন্য কাজে ব্যস্ত রেখে। /proc/stat-এর cpu লাইনের অষ্টম সংখ্যাটা হলো steal:

EXPERIMENT (Mac + Docker) — work.sh
# work.sh — VM-এর ভেতরে ৮টা একই কাজ (spin.js) একসাথে; প্রত্যেকের হিসাবে CPU time কত?
st() { awk '/^cpu / {print $9}' /proc/stat; }               # steal-এর ঘর
s0=$(st); t0=$(date +%s%N)
for i in $(seq 8); do node spin.js & done | awk '{gsub(",", ""); print $4}' | sort -n |
  awk '{a[NR] = $1} END {print "CPU time charged per job: " a[1] "–" a[NR] " ms"}'
echo "wall time: $(( ($(date +%s%N) - t0) / 1000000 )) ms, steal ticks: $(( $(st) - s0 ))"
# ১) Mac চুপচাপ
docker run --rm -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash work.sh
# ২) Mac-এর ১২টা core-এ ১২ সেকেন্ডের busy loop, তারপর একই কাজ

কাজ হুবহু এক, অথচ Mac ব্যস্ত থাকলে পুরো কাজ শেষ হতে ৩৫% বেশি সময় লেগেছে। আর guest kernel প্রতিটা process-এর নামে ২৫–৩৫% বেশি CPU time লিখেছে। অথচ steal শূন্য! কারণ এই hypervisor guest-কে জানায়ই না কখন তার vCPU থামিয়ে রাখা হয়েছিল। Guest-এর ঘড়ি চলতে থাকে, আর process যখন আবার চলে, মাঝের পুরো সময়টা kernel তার নামেই লিখে দেয়। ফলে VM-এর ভেতর থেকে মনে হয় program আরও বেশি CPU খাচ্ছে, অথচ আসলে সে অপেক্ষা করছিল।

Cloud-এর KVM-ভিত্তিক hypervisor সাধারণত guest-কে steal time জানায়। তখন top-এর st column বা vmstat-এর st-এ সেটা দেখা যায়। Production-এ হঠাৎ সবকিছু ধীর হলে আর CPU "ব্যস্ত" দেখালে, নিজের code-এর আগে st দেখো। বেশি হলে সমস্যা তোমার code-এ না, প্রতিবেশীতে বা instance-এর ধরনে (যেমন burstable instance-এর CPU credit ফুরিয়ে যাওয়া)।

একটা আসল core-এর সময়রেখা। উপরে core আসলে কাকে চালাচ্ছে: তোমার vCPU আর host-এর অন্য কাজ পালা করে। নিচে guest-এর চোখে: তার ঘড়ি থামে না, তাই মাঝের লাল ফাঁকগুলোও process-এর "চলার" সময় বলে গোনা হয়।

এই chapter-এ মূল হিসাবটা হলো: VM-এর isolation শক্ত। প্রতিটা guest-এর নিজের kernel, মাঝে hypervisor-এর দেয়াল, তাই অচেনা customer-দের এক machine-এ রাখতে cloud VM-এর উপরেই ভরসা করে। কিন্তু দামও আছে: প্রতিটা VM-এ আস্ত একটা OS-এর boot, memory আর kernel। Docker Desktop-এর এই একটা Linux VM-এর উপরে আমরা বইজুড়ে ডজন ডজন container চালিয়েছি, আর প্রতিটা চালু হয়েছে এক সেকেন্ডের কম সময়ে। কীভাবে, সেটা পরের chapter। (AWS Lambda-র মতো জায়গায় দুটোর মাঝামাঝি পথ আছে: Firecracker-এর মতো খুব হালকা VM, যেটা নিজের হিসাবে ~১২৫ ms-এ boot করে।)

MENTAL MODEL

Virtualization হলো Chapter 9-এর illusion, এক স্তর উপরে। Hypervisor প্রতিটা OS-কে বিশ্বাস করায় যে machine তার একার। Guest-এর code, এমনকি guest kernel-ও, আসল CPU-তে পূর্ণ গতিতে চলে। শুধু বিপজ্জনক মুহূর্তে CPU hypervisor-এ trap করে (VM exit), আর hypervisor ফল নকল করে ফেরায়। Memory-তে দুই ধাপের অনুবাদ হয়: guest-এর table, তারপর hypervisor-এর stage-2 table; দাম পড়ে শুধু TLB miss-এ। Device হলো virtio: guest জানে সে VM-এ, তাই ring-এ অনুরোধ জমিয়ে একবারে পাঠায়। আর vCPU host-এর একটা thread মাত্র, তাই host ব্যস্ত থাকলে তোমার সময় চুরি হয় (steal)। Hypervisor না জানালে সেই চুরি তোমার program-এর CPU time হিসেবেই দেখায়।
