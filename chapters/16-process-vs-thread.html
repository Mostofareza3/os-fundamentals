PART 5 · PROCESS MANAGEMENT

Chapter 16 — Process vs Thread

এক process-এর ভেতরে একাধিক execution-এর ধারা: কী আলাদা, কী ভাগাভাগি, kernel তাদের কীভাবে দেখে, Node-এর worker কোথায় আলাদা — আর এই মুহূর্তে তোমার "single-threaded" Node-এর ভেতরে আসলে কয়টা thread চলছে।

যা লাগবে: process মানে kernel-এর একটা PCB, নিজস্ব address space, আর CPU context — PC, SP, register (Chapter 3); প্রতিটা function call stack-এ একটা frame পায়, যেখানে ফেরার ঠিকানা থাকে (Chapter 5); আর fork দিয়ে process-এর copy বানানো যায় (Chapter 15)। Chapter 2-এ এক লাইনে thread-কে বলেছিলাম "process-এর ভেতরে instruction চালানোর একটা স্বাধীন ধারা"। এবার সেটা পুরো খুলি।

Thread কেন লাগে

ধরো একটা program একসাথে কয়েকটা কাজ করতে চায় — Chapter 14-এর মতো বারোটা core-এ হিসাব ভাগ করতে, বা একটা লম্বা হিসাব চলার সময়ও UI সাড়া দিক। একটা উপায়: কয়েকটা process চালাও। কিন্তু process-দের address space আলাদা (Chapter 9) — একজনের data আরেকজন সরাসরি দেখতে পারে না; ভাগ করতে হলে pipe বা socket দিয়ে kernel-এর মাধ্যমে copy করে পাঠাতে হয়। আর process বানানো নিজেই দামি: নতুন PCB, নতুন page table, খোলা file-এর নতুন table।

দ্বিতীয় উপায়: একই address space-এর ভেতরে একাধিক execution-এর ধারা চালাও — প্রত্যেকের নিজের PC, নিজের register, নিজের stack, আর kernel তাদের আলাদা আলাদা করে CPU-তে বসায়; কিন্তু memory, খোলা file, বাকি সব একই। এরই নাম thread। প্রতিটা process অন্তত একটা thread নিয়ে জন্মায় — main thread — আর চাইলে আরও বানাতে পারে। দামের পার্থক্য মাপো:

python3 -c "
import os, threading, time
N = 1000
t = time.perf_counter()
for _ in range(N):
    th = threading.Thread(target=lambda: None); th.start(); th.join()   # thread বানাও, শেষ হতে দাও
thr = (time.perf_counter() - t) / N * 1e6
t = time.perf_counter()
for _ in range(N):
    pid = os.fork()                                                     # process বানাও, শেষ হতে দাও
    if pid == 0: os._exit(0)
    os.waitpid(pid, 0)
prc = (time.perf_counter() - t) / N * 1e6
print(f'thread create+join: {thr:.0f} µs   |   process fork+wait: {prc:.0f} µs')"

আমার Mac-এ: thread create+join: 31 µs | process fork+wait: 844 µs — process বানানো ২৭ গুণ দামি, যদিও fork copy-on-write দিয়ে memory copy এড়িয়ে যায় (Chapter 15)। Thread-এর জন্য kernel-কে নতুন address space বানাতে হয় না, শুধু একটা নতুন stack আর register-এর একটা সেট।

কী নিজস্ব, কী ভাগাভাগি

প্রতিটা thread-এর নিজস্ব:

  • PC আর register — প্রত্যেকে code-এর আলাদা জায়গায় থাকতে পারে, আলাদা হিসাব করতে পারে।
  • Stack — কারণ প্রত্যেকে আলাদা আলাদা function ডাকে, আর প্রতিটা call-এর frame আর ফেরার ঠিকানা (Chapter 5) নিজের শিকলে রাখতে হয়। দুইটা thread একই stack ভাগ করলে একজনের return আরেকজনের frame মুছে দিত।
  • State — running, ready, blocked (Chapter 15) — thread ধরে। একটা thread disk-এর জন্য ঘুমালে একই process-এর অন্য thread চলতে থাকে।
  • নিজস্ব ID (TID), আর কিছু thread-local data — যেমন C-র errno, যাতে এক thread-এর error আরেকজনের ঘাড়ে না পড়ে।

সব thread মিলে ভাগাভাগি: পুরো address space — code, global data, heap, library — আর খোলা file-এর table, PID, working folder, user। এক thread malloc করে একটা pointer রাখলে অন্য thread সেটা দিয়ে সরাসরি একই memory পড়তে পারে; এক thread file খুললে অন্যজন সেই fd দিয়েই লিখতে পারে।

Chapter 5-এর memory layout, এবার তিনটা thread সহ। উপরের নীল অংশে প্রতিটা thread-এর নিজের stack, মাঝে ছোট নিষিদ্ধ guard page (একজনের stack overflow যাতে আরেকজনের stack-এ ঢুকে না পড়ে)। নিচের সবুজ অংশ — heap, globals, code, library — সবার এক। ডানে প্রতিটা thread-এর নিজের SP নিজের stack দেখায়।

Kernel-এর চোখে thread

Kernel thread আর process-কে কতটা আলাদা ভাবে? Linux-এ উত্তর চমকপ্রদ: প্রায় একই ভাবে। প্রতিটা thread kernel-এর কাছে একটা পূর্ণ "task" — নিজের PCB (task_struct), নিজের ID, scheduler-এর নিজের পালা। পার্থক্য শুধু একটা: একই process-এর task গুলো memory আর খোলা file-এর table ভাগ করে। আর দুটোই তৈরি হয় একই syscall দিয়ে — Chapter 15-এর clone — শুধু flag আলাদা। Node চালু হওয়ার সময় সে নিজের জন্য কয়েকটা thread বানায়; দেখো:

docker run --rm --cap-add SYS_PTRACE node:22-alpine sh -c 'apk add -q strace >/dev/null 2>&1; strace -f -e trace=clone node -e 1 2>&1 | grep clone | head -1'

আমার output (ছেঁটে): clone(child_stack=0xffff8e002950, flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|...)। Chapter 15-এ bash-এর fork ছিল clone(child_stack=NULL, flags=...|SIGCHLD)। তফাতটা পড়ো: thread-এর বেলায় CLONE_VM (address space ভাগ করো), CLONE_FILES (খোলা file-এর table ভাগ করো), CLONE_THREAD (একই process-এর সদস্য), আর একটা নতুন child_stack — নতুন thread-এর নিজের stack। Process-এর বেলায় এসবের কিছুই না — সব copy। একই যন্ত্র, কতটা ভাগ হবে সেটা flag ঠিক করে।

এবার দেখো তোমার "single-threaded" Node-এর ভেতরে আসলে কী চলছে। Linux প্রতিটা thread-কে /proc/<PID>/task/-এর নিচে একটা folder হিসেবে দেখায়, আর comm file-এ তার নাম:

EXPERIMENT (Linux / Docker) — Node-এর thread গুলো
docker run --rm node:22-alpine node -e "
const fs = require('fs');
const threads = () => fs.readdirSync('/proc/self/task')
  .map(t => t + ':' + fs.readFileSync('/proc/self/task/' + t + '/comm', 'utf8').trim());
console.log('at start         :', threads().join('  '));
fs.readFile('/etc/hostname', () => console.log('after fs.readFile:', threads().join('  ')));"

আমার output:

at start         : 1:node  10:node  11:node  12:node  13:node  8:DelayedTaskSche  9:node
after fs.readFile: 1:node  10:node  11:node  12:node  13:node  14:libuv-worker  15:libuv-worker  16:libuv-worker  17:libuv-worker  8:DelayedTaskSche  9:node

macOS-এ: ps -M <PID> — প্রতিটা thread একটা লাইন।

শুরুতেই সাতটা thread। 1 হলো main thread — তোমার সব JS আর event loop এখানে। 9–13 V8-এর helper thread: garbage collection-এর অনেকটা (Chapter 6) আর JIT compile (Chapter 4) এরা পেছনে চালায়। DelayedTaskSche V8-এর সময়-নির্ধারিত কাজ সামলায়। আর প্রথম fs.readFile-এর পরে হাজির চারটা libuv-worker — Node-এর thread pool, যেটা প্রথম দরকারের সময় তৈরি হয় আর file পড়া, DNS lookup, crypto, zlib-এর মতো blocking কাজ main thread-এর বাইরে সারে (Chapter 19)। "Node single-threaded" — কথাটা সত্যি শুধু তোমার JS-এর জন্য।

Node-এর worker: thread, কিন্তু আলাদা heap

C, Java বা Go-তে এক thread-এর বানানো object আরেক thread সরাসরি পড়তে-লিখতে পারে — ওপরের ছবির মতো heap সবার এক। Node-এর worker_threads আসল OS thread-ই (clone-এর ওই flag দিয়ে তৈরি), কিন্তু প্রতিটা worker পায় নিজের একটা পুরো V8 instance — নিজের JS heap, নিজের garbage collector, নিজের event loop। কারণ V8-এর heap আর GC এমনভাবে বানানো যে একাধিক thread একসাথে JS object বদলালে সেগুলো ভেঙে পড়ত। ফল: worker-কে সাধারণ object পাঠালে সেটা copy হয়ে যায়; শুধু SharedArrayBuffer-এর memory সত্যিই ভাগ হয়।

EXPERIMENT — share.js
const { Worker, isMainThread, workerData } = require('worker_threads');

if (isMainThread) {
  const plain = { count: 0 };                               // সাধারণ JS object
  const shared = new Int32Array(new SharedArrayBuffer(4));  // সবার দেখা memory

  const w = new Worker(__filename, { workerData: { plain, shared } });
  w.on('exit', () => {
    console.log('main sees plain.count =', plain.count);    // worker-এর বদল কি এখানে পৌঁছাল?
    console.log('main sees shared[0]   =', shared[0]);
  });
} else {
  workerData.plain.count = 42;                              // worker-এর নিজের copy বদলাল
  workerData.shared[0] = 42;                                // shared memory বদলাল
  console.log('worker set both to 42');
}

আমার output: worker set both to 42, তারপর main sees plain.count = 0, main sees shared[0] = 42।

Worker দুইটাকেই ৪২ বানাল, কিন্তু main দেখল শুধু shared-টার বদল। plain পৌঁছানোর সময় copy হয়েছিল (এই copy-র নাম structured clone), worker বদলেছে নিজের copy। শিক্ষা: worker-দের মধ্যে বড় data বারবার পাঠালে copy-র খরচ দিতে হয়। এড়ানোর দুই পথ — SharedArrayBuffer (ভাগ করো), অথবা postMessage(data, [data.buffer])-এর মতো transfer (copy না করে মালিকানা হস্তান্তর — পাঠানোর পরে পাঠানো thread আর ওটা ব্যবহার করতে পারে না)।

এক thread-এর ভুল, সবার বিপদ

ভাগাভাগির উল্টো পিঠ: একই address space মানে একটা thread-এর bug সবার memory নষ্ট করতে পারে, আর একটা thread crash করলে — ধরো ভুল address ছুঁয়ে segmentation fault — kernel-এর signal যায় পুরো process-এর কাছে, আর process-এর সব thread একসাথে মরে। Node-এর worker-এ JS স্তরের ভুল আলাদা ব্যাপার, কারণ প্রতিটা worker-এর V8 আলাদা:

EXPERIMENT — crash.js
const { Worker, isMainThread } = require('worker_threads');
if (isMainThread) {
  const mode = process.argv[2];
  new Worker(__filename, { argv: [mode] }).on('error', e => console.log('main: worker threw →', e.message));
  setTimeout(() => console.log('main: still alive after 500 ms'), 500);
} else if (process.argv[2] === 'throw') {
  throw new Error('JS error inside the worker');       // JS-এর error: শুধু worker-টা শেষ
} else {
  process.kill(process.pid, 'SIGSEGV');                // segfault-এর signal: পুরো process-এর জন্য
}
node crash.js throw; echo "exit code: $?"
node crash.js segv;  echo "exit code: $?"

আমার output: প্রথমটায় main: worker threw → JS error inside the worker, main: still alive after 500 ms, exit code: 0। দ্বিতীয়টায় শুধু exit code: 139 — main-এর একটা লাইনও না।

JS-এর exception worker-এর নিজের V8 ধরে ফেলে আর main-কে খবর দেয়। কিন্তু SIGSEGV (আসল একটা native crash যে signal তৈরি করে) process-এর — সবার — তাই main thread-ও শেষ, exit code ১৩৯ = ১২৮ + ১১ (SIGSEGV-এর নম্বর)। Chapter 1-এর chrome://crash মনে করো: Chrome প্রতিটা tab আলাদা process-এ রাখে ঠিক এই কারণে — thread হলে একটা tab-এর crash পুরো browser নামিয়ে দিত।

COMMON MISCONCEPTION

"Thread মানে হালকা process।" হালকা তো বটেই, কিন্তু আসল সংজ্ঞা ওজনে না — address space-এ: process-রা আলাদা জগতে থাকে, thread-রা এক জগৎ ভাগ করে। Linux-এর চোখে দুটোই task, শুধু clone-এর flag বলে কতটা ভাগ হবে। এই ভাগাভাগিই thread-এর সব সুবিধা (সস্তা, দ্রুত যোগাযোগ) আর সব বিপদের (একজনের ভুল সবার ঘাড়ে, race condition) উৎস।

MENTAL MODEL

Process হলো resource-এর ধারক — address space, খোলা file, PID; thread হলো execution-এর একক — PC, register, stack, আর scheduler-এর একটা পালা। একটা process-এর ভেতরে যত thread, সবাই একই memory দেখে কিন্তু প্রত্যেকে নিজের stack-এ নিজের পথে হাঁটে। Node-এ তোমার JS এক thread-এ, কিন্তু process-এ এক ডজনের কাছাকাছি; আর worker-রা আসল thread হলেও JS object ভাগ করে না — শুধু SharedArrayBuffer।
