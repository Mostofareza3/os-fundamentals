PART 9 · COMPILERS, LINKERS AND EXECUTABLES

Chapter 34 — Executable Load হওয়া

execve-এর মুহূর্তে kernel file-এর প্রথম কয়েকটা byte দেখে কী সিদ্ধান্ত নেয় (shebang, ELF, "not found"), node-এর ১১৭ MB-এর কতটা আসলে RAM-এ আসে, প্রতিবার ঠিকানা কেন বদলায় (ASLR), আর node চালু হতে সময়টা কোথায় যায়।

Chapter 4-এ loader-এর পাঁচ ধাপ দেখেছি। execve file যাচাই করে, পুরনো memory ফেলে দেয়, segment map করে, stack-এ argv আর env রাখে, আর PC বসায় dynamic linker (ld.so) বা program-এর entry point-এ। সেখানে ধরে নিয়েছিলাম সব ঠিকঠাক চলবে। এই chapter দেখে যখন ঠিকঠাক চলে না তখন কী হয়, আর "load" শব্দটার পেছনে আসলে কতটা কাজ হয়। JS developer-এর জন্য এর মানে: npx কীভাবে চলে, Alpine image-এ কেন "not found", আর serverless-এর cold start কোথা থেকে আসে।

প্রথম দুই byte: shebang

npx, tsc, eslint — এগুলো আসলে JS file। তবু terminal-এ সরাসরি নাম লিখে চালানো যায়, সামনে node লাগে না। কীভাবে? Kernel তো JS চেনে না।

উত্তর file-এর প্রথম লাইনে: head -1 $(which npx) চালালে দেখবে #!/usr/bin/env node। #! দিয়ে শুরু হওয়া এই লাইনের নাম shebang। execve file খুলে প্রথম দুই byte-এ #! পেলে kernel file-টা নিজে চালায় না। বরং লাইনের বাকিটা পড়ে সেই program চালায়, আর তোমার file-এর path argument হিসেবে দিয়ে দেয়। তিন রকম file দিয়ে দেখা যাক: ঠিক shebang, shebang নেই, আর Windows-এ লেখা file (লাইনের শেষে \r\n):

EXPERIMENT (Linux / Docker) — shebang.sh
# shebang.sh
printf '#!/usr/bin/env node\nconsole.log("hi from", process.argv.slice(0, 2));\n' > hi.js
printf 'console.log("no shebang here")\n' > plain.js
printf '#!/usr/bin/env node\r\nconsole.log("windows line endings")\r\n' > crlf.js
chmod +x hi.js plain.js crlf.js
echo "--- ./hi.js";    ./hi.js
echo "--- ./plain.js"; ./plain.js
echo "--- ./crlf.js";  ./crlf.js
echo "--- strace ./hi.js"
strace -f -e trace=execve ./hi.js 2>&1 | grep -E "execve|hi from"
echo "--- strace ./plain.js"
strace -e trace=execve ./plain.js 2>&1 | head -2

strace-এর লাইনগুলো গল্পটা বলে দেয়:

  • execve("./hi.js") সফল (= 0), অথচ চলল /usr/bin/env। Kernel shebang পড়ে নিজেই সেটা চালিয়েছে। env-এর কাজ একটাই: PATH-এর folder-গুলোতে একে একে node খোঁজা। প্রথমটায় পায়নি (ENOENT), দ্বিতীয়টায় পেয়েছে। সরাসরি #!/usr/local/bin/node না লিখে env দেওয়ার কারণ এটাই: node কোথায় বসানো, সেটা machine ভেদে আলাদা (nvm, Homebrew, Docker)।
  • plain.js-এ shebang নেই, ELF-ও না। Kernel বলেছে ENOEXEC: "এই format চিনি না"। তখন bash পুরনো একটা নিয়ম মেনে file-টাকে shell script হিসেবে চালিয়েছে, আর JS-কে shell ভেবে syntax error দিয়েছে।
  • crlf.js-এ লাইনের শেষে একটা অদৃশ্য \r। Kernel সেটাকে নামের অংশ ধরে env-কে বলেছে node\r খুঁজতে। Windows-এ লেখা CLI script Linux-এ চালাতে গিয়ে এই error খুব চেনা; সমাধান হলো file-টা \n line ending-এ save করা।

npm-এর package.json-এ "bin" দিলে npm install ঠিক এটাই করে: file-টা executable করে, আর node_modules/.bin-এ একটা link বানায়। Shebang-এর বাকি কাজ kernel-এর।

execve-এর প্রথম সিদ্ধান্ত। Kernel file-এর প্রথম byte দেখে পথ বাছে: #! হলে লাইনে লেখা interpreter, ELF হলে header-এ লেখা ld.so (না পেলে ENOENT, এর পরের section), আর কিছু না মিললে ENOEXEC। নীল তীরগুলো user mode-এ ফেরা।

Interpreter নেই: Alpine-এর "not found"

Chapter 4-এ দেখেছি dynamically linked ELF-এর header-এ একটা path লেখা থাকে: "আমাকে চালাতে এই dynamic linker লাগবে" (PT_INTERP, readelf-এ "program interpreter")। এই path-টা libc-র সাথে বাঁধা। Debian, Ubuntu, Fedora-র মতো বেশিরভাগ Linux ব্যবহার করে glibc (GNU-র C library), যার dynamic linker /lib/ld-linux-aarch64.so.1 (Intel/AMD-এ ld-linux-x86-64.so.2)। ছোট Docker image-এর জন্য জনপ্রিয় Alpine ব্যবহার করে musl, আরেকটা C library, যার dynamic linker অন্য নামের। Debian-এ build করা একটা program Alpine-এ নিয়ে যাও:

প্রথম লাইনে file-টা আছে, executable-ও (x)। অথচ চালাতে গেলে "not found"। Debugging-এ এটা সবচেয়ে বিভ্রান্তিকর error-গুলোর একটা, কারণ যে file "পাওয়া যাচ্ছে না" বলছে, সেটা তোমার file না। Header চায় /lib/ld-linux-aarch64.so.1, আর Alpine-এ আছে শুধু /lib/ld-musl-aarch64.so.1। Kernel interpreter খুলতে গিয়ে পায়নি, তাই পুরো execve ENOENT দিয়ে ফেরত এসেছে, আর shell সেটাকে "not found" বলে দেখিয়েছে।

Node-এর native addon-এ (Chapter 33) ব্যাপারটা আরও গোলমেলে হতে পারে। নিচের addon C-র snprintf দিয়ে একটা string বানায়। অনেক build-এ default থাকা একটা নিরাপত্তা option (_FORTIFY_SOURCE) glibc-তে snprintf-কে বদলে দেয় তার সীমা-যাচাই করা রূপ __snprintf_chk-এ, আর এই function musl-এ নেই:

// label.c — label(n) → "item-<n>" (C-র snprintf দিয়ে string বানানো)
#include <node_api.h>
#include <stdio.h>

static napi_value Label(napi_env env, napi_callback_info info) {
    size_t argc = 1;
    napi_value argv[1], out;
    int n;
    char buf[32];
    napi_get_cb_info(env, info, &argc, argv, NULL, NULL);
    napi_get_value_int32(env, argv[0], &n);
    snprintf(buf, sizeof buf, "item-%d", n);
    napi_create_string_utf8(env, buf, NAPI_AUTO_LENGTH, &out);
    return out;
}

NAPI_MODULE_INIT() {
    napi_value fn;
    napi_create_function(env, "label", NAPI_AUTO_LENGTH, Label, NULL, &fn);
    napi_set_named_property(env, exports, "label", fn);
    return exports;
}
# Debian-এ build আর চালানো
docker run --rm -v "$PWD":/w -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq gcc libc6-dev >/dev/null
  gcc -O2 -D_FORTIFY_SOURCE=2 -shared -fPIC -I/usr/local/include/node label.c -o label.node
  nm -D --undefined-only label.node | grep snprintf
  node -p "require(\"./label.node\").label(7)"'
# একই addon Alpine-এ

Debian-এ ঠিকঠাক চলল। Alpine-এ require দিব্যি সফল ("loaded fine"), কিন্তু প্রথম call-এই segfault। musl-এর dynamic linker __snprintf_chk খুঁজে পায়নি। Node addon load করে "lazy" ভাবে, মানে function-এর ঠিকানা খোঁজা হয় প্রথম ডাকের সময়, তাই load-এর সময় error আসেনি। ফাঁকটা ভরা হয়নি, আর প্রথম ডাকে CPU লাফ দিয়েছে একটা অর্থহীন ঠিকানায় (strace-এ si_addr=0x660)। Error message-এ addon-এর নামও নেই, শুধু exit ১৩৯। কারণ শুনে বোঝা যায়, কিন্তু আগে থেকে না জানলে খুঁজে বের করা কঠিন।

সমাধান তিনটা। Alpine-এর উপরেই build করো (npm install Alpine image-এর ভেতরে চালাও, Mac থেকে node_modules copy করো না)। অথবা package-এর musl-এর জন্য বানানো prebuilt binary নাও (নামে সাধারণত linuxmusl থাকে)। অথবা native addon-ওয়ালা app-এর জন্য Debian-ভিত্তিক image নাও (node:22-bookworm-slim)। Static binary-র এই সমস্যা নেই, কারণ তার কোনো interpreter-ই লাগে না।

Load মানে copy না: node-এর ১১৭ MB-এর কতটা RAM-এ আসে

Chapter 4-এ এক লাইনে বলেছিলাম: execve file-এর segment "map" করে, copy করে না। CPU যে page প্রথম ছোঁয়, page fault হয়ে সেটুকু আসে (Chapter 9)। এর নাম demand paging। এবার মেপে দেখা যাক, node binary-র কতটা শেষ পর্যন্ত আসে, আর page cache-এ (Chapter 23) না থাকলে কী হয়। /proc/self/smaps প্রতিটা mapping-এর Size (address space-এ কত বড়) আর Rss (এর মধ্যে কতটা এখন RAM-এ) দেয়:

// lazy.js — node binary-র কতটা আসলে RAM-এ এল?
const fs = require('fs');
const exe = fs.realpathSync(process.execPath);
let size = 0, rss = 0, mine = false;
for (const line of fs.readFileSync('/proc/self/smaps', 'utf8').split('\n')) {
  if (/^[0-9a-f]+-[0-9a-f]+ /.test(line)) mine = line.endsWith(exe);   // নতুন mapping শুরু
  else if (mine && line.startsWith('Size:')) size += parseInt(line.slice(5));
  else if (mine && line.startsWith('Rss:'))  rss  += parseInt(line.slice(4));
}
const ru = process.resourceUsage();
console.log(`node on disk: ${(fs.statSync(exe).size / 2 ** 20).toFixed(0)} MB, ` +
            `mapped: ${(size / 1024).toFixed(0)} MB, actually in RAM: ${(rss / 1024).toFixed(0)} MB`);
console.log(`page faults so far: ${ru.minorPageFault} minor, ${ru.majorPageFault} major; ` +
            `${performance.now().toFixed(0)} ms since start`);
# cold.sh — একই lazy.js: page cache-এ node থাকলে, আর না থাকলে
node lazy.js > /dev/null                                   # file-টা page cache-এ আনা
echo "warm:"; node lazy.js
dd if=/usr/local/bin/node iflag=nocache count=0 status=none  # node-এর page গুলো cache থেকে সরাও
echo "cold:"; node lazy.js
docker run --rm -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash cold.sh

node file ১১৭ MB, address space-এ map হয়েছে ৯৯ MB (বাকিটা symbol-এর মতো জিনিস, চলতে লাগে না)। অথচ তোমার code চলা পর্যন্ত RAM-এ এসেছে মাত্র ৩০ MB। বাকি ৭০ MB-র জায়গা ঠিক করা আছে, কিন্তু কেউ না ছুঁলে কখনো আসবে না।

দুই রকম page fault আছে। Minor fault-এ page আগে থেকেই RAM-এ, page cache-এ; kernel শুধু page table-এ বসায়, microsecond-এর কাজ। Major fault-এ page RAM-এ নেই, disk থেকে পড়তে হয়। Warm চালানোয় major fault শূন্য, আর node ১১ ms-এ তোমার code-এ পৌঁছেছে। dd ... iflag=nocache count=0 শুধু node file-টার page গুলো page cache থেকে সরিয়ে দেয়, আর তারপর ৩০৩টা major fault, সময় আড়াই গুণ। এখানে "disk" আসলে Mac-এর দ্রুত SSD-র উপর একটা virtual disk। Network-এ বসানো cloud disk-এ এই ফাঁক অনেক বড় হয়। Serverless-এর "cold start"-এর একটা অংশ ঠিক এটাই: নতুন machine-এ runtime-এর page গুলো তখনো page cache-এ নেই।

cold.sh-এর মাপ। উপরে node binary-র তিন মাপ: disk-এ, address space-এ, আর আসলে RAM-এ। নিচে একই program page cache-এ থাকলে আর না থাকলে: পার্থক্য শুধু major fault, মানে disk থেকে পড়া।

ASLR: প্রতিবার নতুন ঠিকানা

ধরো একটা program-এ bug আছে, আর আক্রমণকারী সেটা দিয়ে CPU-কে নিজের পছন্দের কোনো ঠিকানায় লাফ দেওয়াতে পারে। যেমন libc-র system() function-এ, যেটা যেকোনো shell command চালায়। এর জন্য তাকে জানতে হবে system() ঠিক কোন ঠিকানায় আছে। প্রতিবার সব একই ঠিকানায় বসলে এটা জানা সহজ: নিজের machine-এ একবার দেখে নিলেই হলো।

ASLR (Address Space Layout Randomization) এই অনুমান ভেঙে দেয়। প্রতিটা execve-তে kernel stack, heap, ld.so, আর libc-র মতো library-কে এলোমেলো ঠিকানায় বসায়। Program নিজেও PIE (position-independent executable) হিসেবে build করা থাকলে, যেমন Chapter 33-এর file-এ দেখা "pie executable", তার code-ও নড়ে। Chapter 4-এর 0x754-এর মতো ঠিকানাগুলো তাই আসলে file-এর শুরু থেকে দূরত্ব, চলার সময়ের আসল ঠিকানা না।

# aslr.sh — একই program তিনবার: libc-র code আর stack কোথায় বসল?
where() { grep -E "r-xp .*libc\.so|\[stack\]" /proc/self/maps | awk '{print substr($1, 1, 12), $6}' | tr '\n' ' '; echo; }

প্রতিটা লাইন আলাদা একটা grep process-এর নিজের memory-র ছবি। randomize_va_space = 2 মানে পুরো randomization চালু। তিনবারে libc আর stack তিন জায়গায় বসেছে। setarch -R randomization বন্ধ করে চালায়, আর তখন তিনবারই হুবহু এক ঠিকানা। Debugger কখনো কখনো এভাবে randomization বন্ধ রাখে, যাতে প্রতিবার একই ঠিকানা দেখা যায়।

একটা খুঁটিনাটি: --security-opt seccomp=unconfined ছাড়া setarch -R Docker-এ "Operation not permitted" দেয়। Docker-এর seccomp নিয়ম (Chapter 36) randomization বন্ধ করার অনুরোধটাই আটকে রাখে, কারণ সেটা আক্রমণকারীর কাজে লাগে। ASLR আক্রমণ অসম্ভব করে না; কোনো একটা ঠিকানা ফাঁস হলে পুরো library কোথায় আছে বের করা যায়। কিন্তু প্রতিটা আক্রমণে বাড়তি একটা ধাপ যোগ করে, আর অন্ধ অনুমানকে crash-এ পরিণত করে।

aslr.sh-এর তিনটা চালানো আর setarch -R। ASLR চালু থাকলে প্রতিটা process-এ libc আর stack নতুন জায়গায় বসে; বন্ধ করলে সব সময় একই ঠিকানা। (ঠিকানাগুলো আসল, অবস্থান মাপমতো না।)

(আমার Mac-এ।) V8 engine তৈরি হতে ৩ ms, তারপর Node-এর নিজের JS দিয়ে লেখা ভেতরের অংশ (require, process, stream…) দাঁড় করাতে আরও ৫ ms। এত কম লাগে কারণ Node এই অংশের একটা তৈরি-করা ছবি (V8-এর heap snapshot) binary-র ভেতরেই রেখে দেয়, আর প্রতিবার সেখান থেকে ফুটিয়ে তোলে; শূন্য থেকে বানায় না। তুলনার জন্য Linux container-এ ২০ বার চালু করে গড়:

(Node image-এ python3 নেই; apt দিয়ে বসিয়ে নিয়েছি।) একটা ছোট C program-এর পুরো execve + ld.so + exit এক millisecond-এরও কম। node-এর ১০ ms-এর বেশিরভাগ তাই engine আর runtime দাঁড় করানো, load করা না। তোমার app-এর নিজের require করা dependency-গুলো এর উপরে যোগ হয়। বড় app-এ সেটাই প্রায়ই সবচেয়ে বড় অংশ, তাই startup ধীর লাগলে সেখান থেকেই মাপা শুরু করো।

COMMON MISCONCEPTION

"not found মানে file-টা নেই।" execve-এর ENOENT তিনটা আলাদা file-এর যেকোনোটার জন্য আসতে পারে: তোমার program নিজে, shebang-এ লেখা interpreter (node\r), বা ELF header-এ লেখা dynamic linker (Alpine-এ ld-linux)। তাই "file তো আছে, তবু not found" দেখলে প্রথম প্রশ্ন: file-টা কে চালাতে বলছে? head -1 file (shebang) আর file prog (interpreter) দুই command-এ উত্তর মেলে।

MENTAL MODEL

execve file-এর প্রথম byte দেখে সিদ্ধান্ত নেয়। #! হলে লাইনে লেখা interpreter চালায়। ELF হলে header-এ লেখা ld.so map করে, সেটা না পেলে ENOENT। আর কিছু না মিললে ENOEXEC। Load মানে copy না, map: node-এর ১১৭ MB-এর মধ্যে তোমার code চলা পর্যন্ত আসে ৩০ MB, বাকিটা শুধু কেউ ছুঁলে আসে। Page cache-এ না থাকলে প্রতিটা ছোঁয়া disk থেকে পড়া (major fault), আর সেটাই cold start। প্রতিবার ঠিকানা এলোমেলো হয় (ASLR), যাতে আক্রমণকারী আগে থেকে জানতে না পারে কোথায় লাফ দিতে হবে। শেষে ld.so library খোঁজে, হাজার দুয়েক ফাঁক ভরে, init চালায়, তারপর main। Node-এর বাকি startup হলো V8 আর runtime দাঁড় করানো।
