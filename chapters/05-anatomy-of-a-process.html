PART 2 · FROM PROGRAM TO PROCESS

Chapter 5 — Anatomy of a Process

একটা process-এর memory-র ভেতরটা দেখতে কেমন, কোন অংশে কী থাকে আর কেন — আর function call-এর হিসাব রাখা stack আসলে কীভাবে কাজ করে।

যা যা লাগবে, এক লাইনে মনে করিয়ে দিই। Memory address: RAM-এর প্রতিটা byte-এর নম্বর (Chapter 2)। Address space: প্রতিটা process-এর নিজস্ব address-এর জগৎ, এক process-এর address দিয়ে অন্যজনের memory-তে পৌঁছানো যায় না (Chapter 3)। Loader: execve-র সময় kernel-এর যে অংশ executable-এর segment গুলো permission সহ address space-এ map করে (Chapter 4)। আর PC: CPU-র যে register পরের instruction-এর address ধরে রাখে।

Address space-কে ভাগ করতে হয় কেন

Loader-এর হাতে একটা ফাঁকা address space। ৬৪-bit machine-এ এটা বিশাল — Linux-এ একটা process-এর user space-এর ভাগেই প্রায় ১২৮ TB-র address, যদিও তার বেশিরভাগ কখনো ব্যবহার হয় না, কোনো RAM-এর সাথে যুক্তও থাকে না। প্রশ্ন হলো, এর ভেতরে কোথায় কী বসবে?

এলোমেলো বসালে দুইটা সমস্যা। এক, কিছু জিনিস চলার সময় বাড়ে — নতুন object তৈরি হয়, function-এর ভেতরে function ডাকা হয় — আর বাড়তে বাড়তে পাশের জিনিসের উপর উঠে যেতে পারে। দুই, সব memory একই নিয়মে চলা উচিত না: machine code কেউ বদলাতে পারবে না, অথচ variable বদলাতেই হবে; কিছু data program-এর পুরো জীবন বাঁচবে, কিছু এক function call-এর মধ্যেই শেষ।

তাই প্রতিটা process-এর address space একটা প্রচলিত নকশা মেনে কয়েকটা region-এ ভাগ করা হয় — প্রতিটা region-এ একই ধরনের জিনিস, একই জীবনকাল, একই permission। Linux-এ যেকোনো process-এর region গুলো দেখা যায় /proc/<PID>/maps file পড়ে। সবচেয়ে পরিষ্কার উদাহরণ ছোট একটা program — cat নিজের map নিজেই পড়ুক:

EXPERIMENT (Linux / Docker)
docker run --rm alpine cat /proc/self/maps

প্রতিটা লাইন একটা region। প্রথম column হলো address-এর range (hex-এ, শুরু–শেষ), দ্বিতীয়টা permission: r = পড়া যাবে, w = লেখা যাবে, x = instruction হিসেবে চালানো যাবে, - = যাবে না (শেষের p মানে region-টা এই process-এর নিজস্ব copy)। শেষ column বলে region-টা কোথা থেকে এসেছে। Alpine-এ cat আসলে busybox নামের একটা program, তাই সেই নাম দেখছ।

macOS-এ /proc নেই; একই তথ্য দেয় vmmap <PID> — output অনেক লম্বা, তাই vmmap <PID> | grep -E "__TEXT|Stack" দিয়ে ছেঁকে দেখো। একটা Node process-এ আমি পেয়েছি __TEXT 104054000-108f30000 r-x/r-x ... /bin/node — node-এর machine code, পড়া আর চালানো যায়, লেখা যায় না।

Region গুলো, নিচ থেকে উপরে

এবার ওপরের output-কে একটা ছবিতে সাজাই। নিচে ছোট address, উপরে বড়:

বাঁয়ের hex সংখ্যা গুলো ওপরের cat experiment থেকে নেওয়া, ডানে প্রতিটা region-এর কাজ আর permission। Heap উপরের দিকে আর stack নিচের দিকে বাড়ে, মাঝখানে বিশাল ফাঁকা জায়গা রেখে — যাতে দুজনেই বাড়ার জায়গা পায়। সবার উপরে kernel-এর অংশ, user mode থেকে ছোঁয়া নিষেধ।

প্রতিটা region, নিচ থেকে:

  • Text (code) — executable-এর machine code, Chapter 4-এর R E segment। Permission r-x: পড়া আর চালানো যায়, লেখা যায় না। ওপরের output-এর প্রথম লাইন। ঠিক পরের r--p লাইনটা শুধু-পড়া data — code-এ লেখা constant আর linker-এর কিছু table।
  • Data — যেসব global variable-এর শুরুর মান code-এ লেখা আছে। C-তে int count = 10; (function-এর বাইরে লেখা)। মানটা executable file-এ রাখা থাকে, loader সেখান থেকে map করে। ওপরে /bin/busybox-এর rw-p লাইন।
  • BSS — যেসব global-এর শুরুর মান দেওয়া নেই (int total;)। নিয়ম হলো এরা ০ দিয়ে শুরু হবে। তাই file-এ এদের জন্য হাজারটা শূন্য লিখে জায়গা নষ্ট করা হয় না, শুধু লেখা থাকে "এত byte লাগবে"। Loader সেই মাপের ০-ভরা memory দেয়। (নামটা ১৯৫০-এর দশকের একটা assembler থেকে আসা; মানে খুঁজে লাভ নেই।)
  • Heap — program চলার সময় যে memory চেয়ে নেওয়া হয়, আগে থেকে যার মাপ জানা ছিল না। বড় address-এর দিকে বাড়ে। কে কীভাবে এখান থেকে memory পায় আর ফেরত দেয়, সেটা পুরো Chapter 6।
  • Memory-mapped region — shared library (libc, dynamic linker নিজে) আর অন্য যেকোনো map করা জিনিস এখানে বসে। ওপরে /lib/ld-musl-aarch64.so.1-এর লাইনগুলো। ([vvar] আর [vdso] হলো kernel-এর দেওয়া একটা ছোট code আর data টুকরা, যাতে সময় জানার মতো কিছু syscall kernel-এ না ঢুকেই করা যায় — Chapter 32।)
  • Stack — function call-এর হিসাব। ছোট address-এর দিকে, মানে নিচের দিকে বাড়ে। পরের দুই section এর উপর।

Node process-এর map দেখলে ছবিটা আরও ভিড়ের — docker run --rm node:22-alpine node -e "console.log(require('fs').readFileSync('/proc/self/maps', 'utf8'))"। সেখানে দেখবে node binary-র নিজের r-xp আর rw-p লাইন, libstdc++-এর মতো আরও library, আর অনেকগুলো নামহীন rw-p region — ওগুলো V8-এর নিজের JS heap-এর টুকরো। V8 এগুলো [heap] region থেকে নেয় না, kernel-এর কাছে সরাসরি নতুন region map করে চেয়ে নেয় (Chapter 6)। মজার একটা লাইনও পাবে, rwxp — পড়া, লেখা, চালানো তিনটাই। Chapter 4-এর JIT মনে করো: V8 চলার মাঝখানে machine code লেখে, তারপর সেটা চালায়।

Permission: কোন region-এ কী করা যায়

প্রতিটা region-এ permission আলাদা রাখার কারণ দুইটা বিপদ। এক, একটা bug ভুল address-এ লিখে program-এর নিজের machine code নষ্ট করে ফেলতে পারে — তারপর CPU কী চালাবে কেউ জানে না। দুই, আক্রমণকারী যদি input হিসেবে machine code পাঠিয়ে সেটা stack বা heap-এ ঢুকিয়ে দিতে পারে, আর CPU যদি সেটা চালিয়ে দেয় — তাহলে তোমার server-এ সে যা খুশি চালাতে পারবে। পুরনো দিনের অনেক বড় hack ঠিক এভাবে হয়েছিল।

সমাধান: code region r-x (লেখা নিষেধ), আর data, heap, stack rw- (চালানো নিষেধ)। এই নিয়ম পাহারা দেয় CPU নিজে, প্রতিটা memory access-এ (কীভাবে, Chapter 9-এর page table-এর গল্প)। নিয়ম ভাঙলে ঠিক সেটাই ঘটে যা Chapter 1-এ বলেছিলাম: CPU থামে, kernel-কে ডাকে, kernel process-টাকে মেরে ফেলে। নিজে দেখতে চাইলে এই ছোট C program — Chapter 4-এর মতোই compile করো:

#include <stdio.h>

int main(void) {
    printf("main-এর code আছে এই address-এ: %p\n", (void *)main);
    *(char *)main = 0;            /* ওই address-এ একটা byte লেখার চেষ্টা */
    printf("এই লাইন কখনো print হবে না\n");
    return 0;
}

C না জানলে শুধু মাঝের লাইনটা বোঝো: (char *)main মানে "main function-এর machine code যে address-এ শুরু", আর *... = 0 মানে "সেই address-এ ০ লেখো"। (Address নিয়ে সরাসরি কাজ করার এই ক্ষমতার নাম pointer — Chapter 6।) cc writecode.c -o writecode && ./writecode চালালে:

# macOS
main-এর code আছে এই address-এ: 0x104158460
zsh: bus error  ./writecode

# Linux
main-এর code আছে এই address-এ: 0xaaaab45e07d4
Segmentation fault

দ্বিতীয় printf কখনো চলেনি। macOS এই ঘটনাকে "bus error" নামে দেখায়, Linux "segmentation fault" — নাম আলাদা, ঘটনা এক: r-x region-এ লেখার চেষ্টায় CPU থেমেছে, kernel process মেরেছে।

Code region-এ কেউ লিখতে পারে না বলে আরেকটা সুবিধা ফাউ পাওয়া যায়: একই program-এর দশটা process চললেও তাদের code-এর জন্য RAM-এ একটাই copy রাখলে চলে — সবাই সেটাই পড়ে, কেউ বদলায় না। Chapter 4-এর shared library (libc) এভাবেই শত শত process-এর মধ্যে ভাগ হয়।

COMMON MISCONCEPTION

"Stack আর heap হলো দুই রকম hardware memory, একটা দ্রুত আরেকটা ধীর।" না। দুটোই একই RAM, একই address space-এর দুইটা অংশ। পার্থক্য শুধু কীভাবে ব্যবহার করা হয় — কে জায়গা দেয়, কখন ফেরত নেয়, কোন দিকে বাড়ে। CPU-র কাছে stack-এর একটা byte আর heap-এর একটা byte পড়ার মধ্যে কোনো পার্থক্য নেই।

Stack: function call-এর হিসাবের খাতা

একটা সরল প্রশ্ন দিয়ে শুরু করি: function শেষ হলে CPU জানে কীভাবে কোথায় ফিরতে হবে? Chapter 4-এ দেখেছি bl instruction printf-এ লাফ দেওয়ার সময় ফেরার ঠিকানা একটা register-এ রেখে যায়। কিন্তু main ডাকল foo-কে, foo ডাকল bar-কে — তখন bar-এর ফেরার ঠিকানা সেই একই register-এ বসে foo-র ফেরার ঠিকানা মুছে ফেলবে। bar শেষে foo-তে ফেরা যাবে, কিন্তু foo শেষে main-এ ফেরার পথ হারিয়ে গেছে। একই সমস্যা local variable-এর বেলায়ও: foo-র y আর bar-এর z — দুইজনকেই কোথাও রাখতে হবে, আর recursive function হলে একই function-এর হাজারটা copy-র হাজারটা আলাদা variable।

লক্ষ করো, ফেরার ক্রম সবসময় উল্টো: যে সবার শেষে ঢুকেছে, সে সবার আগে বেরোয়। এমন শেষে-ঢোকা-আগে-বেরোনো (LIFO) হিসাবের জন্য সবচেয়ে সহজ কাঠামো হলো stack। তাই process-এর memory-তে একটা region রাখা হয় ঠিক এই কাজে:

  • CPU-র একটা register — stack pointer (SP) — সবসময় stack-এর বর্তমান মাথার address ধরে রাখে।
  • একটা function শুরু হলেই SP থেকে কিছু byte বিয়োগ করে নিজের জন্য জায়গা বানায় (stack নিচের দিকে বাড়ে, তাই বিয়োগ)। এই জায়গাটার নাম stack frame। Frame-এ থাকে: ফেরার ঠিকানা (return address), local variable, আর দরকার হলে কিছু argument।
  • Function শেষ হলে frame থেকে return address তুলে নেয়, SP-তে সেই byte গুলো আবার যোগ করে দেয় — frame মুক্ত — আর return address-এ লাফ দেয়।

এটা কোনো তত্ত্ব না — Chapter 4-এর hello-র main ঠিক এটাই করছিল। otool -tvj hello-এর output আবার দেখো, এবার শুরু আর শেষটা:

0000000100000460   d10083ff   sub  sp, sp, #0x20          ; frame বানাও: SP থেকে 32 byte বিয়োগ
0000000100000464   a9017bfd   stp  x29, x30, [sp, #0x10]  ; x30 (ফেরার ঠিকানা) frame-এ সেভ
...
0000000100000494   a9417bfd   ldp  x29, x30, [sp, #0x10]  ; ফেরার ঠিকানা frame থেকে তোলো
0000000100000498   910083ff   add  sp, sp, #0x20          ; frame মুক্ত: 32 byte ফেরত যোগ
000000010000049c   d65f03c0   ret                         ; x30-এর ঠিকানায় লাফ

ARM-এ x30 হলো সেই register যেখানে bl ফেরার ঠিকানা রাখে; main নিজেও printf-কে ডাকবে বলে x30-এর পুরনো মান আগে নিজের frame-এ সেভ করে রাখছে — ঠিক ওপরের সমস্যার সমাধান। (Intel/AMD-এর x86-64-এ call instruction ফেরার ঠিকানা নিজেই stack-এ push করে, আর ret সেখান থেকে তোলে — পথ আলাদা, ধারণা এক।) লক্ষ করো, stack-এ জায়গা নেওয়া মানে একটা বিয়োগ, ফেরত দেওয়া মানে একটা যোগ — কাউকে জিজ্ঞেস করতে হয় না, কিছু খুঁজতে হয় না। এই কথাটা Chapter 6-এ বড় ভূমিকা রাখবে।

JS-এ একই জিনিস দেখা যাক। V8 তোমার JS function গুলোর frame-ও এই একই process stack-এ রাখে:

function bar() { const z = 3; console.trace('এখানে stack কেমন?'); }
function foo() { const y = 2; bar(); }
function main() { const x = 1; foo(); }
main();

পাঁচটা মুহূর্তের stack, বাঁ থেকে ডানে সময়। নীল frame-টা এই মুহূর্তে যে function চলছে তার; SP সবসময় সবচেয়ে নিচের frame-এ। Return হলে frame-টা "freed" — ভেতরের byte গুলো মুছে ফেলা হয় না, শুধু SP উপরে উঠে যায়, আর পরের call সেই জায়গা আবার ব্যবহার করে।

Stack trace আর stack overflow

ওপরের script চালালে console.trace print করে (path ছোট করে দেখাচ্ছি):

Trace: এখানে stack কেমন?
    at bar (trace.js:1:26)
    at foo (trace.js:2:18)
    at main (trace.js:3:19)
    at Object.<anonymous> (trace.js:4:1)
    at Module._compile (node:internal/modules/cjs/loader:1730:14)
    ...

এটাই stack trace: stack-এ এই মুহূর্তে যত frame জমা আছে, তাদের তালিকা — সবচেয়ে নতুন (bar) উপরে, সবচেয়ে পুরনো নিচে। প্রতিটা frame-এর return address থেকে runtime বের করে কোন function-এর কোন লাইন থেকে ডাকা হয়েছিল। তুমি প্রতিদিন error-এর সাথে যে stack trace দেখো, সেটা ওপরের ছবির তৃতীয় column-এর লিখিত রূপ। (নিচের Module._compile ইত্যাদি Node-এর নিজের function, যারা তোমার file load করে চালিয়েছে।)

এবার সীমার কথা। Stack region-এর মাপ নির্দিষ্ট। Main thread-এর stack-এর সর্বোচ্চ মাপ দেখো:

ulimit -s     # KB-তে; আমার Mac-এ 8176, Linux-এ সাধারণত 8192 (প্রায় ৮ MB)

Stack-এর ঠিক নিচে kernel একটা নিষিদ্ধ অংশ (guard page) রেখে দেয়। Frame জমতে জমতে stack সেখানে পৌঁছালেই permission ভাঙে, আর process মারা যায় — এটাই stack overflow। সবচেয়ে সাধারণ কারণ: শেষ-না-হওয়া বা খুব গভীর recursion।

V8 এই মৃত্যুর আগেই নিজে থামে: সে নিজের জন্য প্রায় ১ MB-র একটা সীমা রাখে, আর সেখানে পৌঁছালে একটা সাধারণ JS error ছুড়ে দেয়, যেটা তুমি catch করতে পারো:

node -e "function f(n) { return f(n + 1) } f(0)"

Output: RangeError: Maximum call stack size exceeded। এখন একটা মজার পরীক্ষা, যেটা দেখায় frame-এর আসলেই একটা মাপ আছে:

EXPERIMENT — depth.js
let depth = 0;
function small() { depth++; small(); }
try { small(); } catch (e) { console.log('small frame depth:', depth); }

depth = 0;
function big() {
  depth++;
  let a = depth, b = a + 1, c = b + 1, d = c + 1, e = d + 1,
      f = e + 1, g = f + 1, h = g + 1, i = h + 1, j = i + 1;
  big();
  return a + b + c + d + e + f + g + h + i + j;
}
try { big(); } catch (e) { console.log('big frame depth:  ', depth); }

আমার Mac-এ: small frame depth: 9183, big frame depth: 5009। একই ~১ MB stack, কিন্তু big-এর প্রতিটা frame-এ দশটা local variable বেশি, তাই প্রতিটা frame বড়, তাই কম সংখ্যক frame ধরে। (সংখ্যা গুলো Node version আর machine ভেদে বদলাবে, অনুপাতটা মোটামুটি থাকবে।)

MENTAL MODEL

Process-এর address space হলো নিচ থেকে উপরে: code (r-x) → data → BSS → heap ↑ … shared libraries … ↓ stack, সবার উপরে kernel-এর নিষিদ্ধ অংশ। প্রতিটা region-এর নিজস্ব permission, যেটা CPU প্রতিটা access-এ যাচাই করে। আর stack হলো "এখন আমি কোথায়, আর কীভাবে ফিরব" — প্রতিটা call-এ একটা frame, SP-র একটা বিয়োগ; প্রতিটা return-এ একটা যোগ।

CAN I EXPLAIN THIS?
  • Process-এর address space-এ কোন কোন region থাকে, নিচ থেকে উপরে? কোন দুইটা region চলার সময় বাড়ে, কোন দিকে, আর মাঝখানে ফাঁকা জায়গা রাখা হয় কেন?
  • /proc/self/maps-এ code-এর লাইনে r-xp আর heap-এর লাইনে rw-p কেন? writecode program-টা মারা গেল কেন, আর code region read-only হওয়ার বাড়তি সুবিধা কী?
  • Return address কেবল একটা register-এ রাখলে main → foo → bar call-এ কী সমস্যা হতো? Stack frame কীভাবে সেটা সমাধান করে?
  • hello-র disassembly-তে sub sp, sp, #0x20 আর add sp, sp, #0x20 কী করছে? Stack-এ জায়গা নেওয়া এত সস্তা কেন?
  • depth.js-এ big-এর depth small-এর চেয়ে কম হলো কেন? V8 কেন OS-এর ৮ MB সীমায় পৌঁছানোর আগেই RangeError ছোড়ে?
