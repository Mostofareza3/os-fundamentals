PART 6 · STORAGE

Chapter 24 — File I/O Modes

Blocking, async, O_SYNC, O_DSYNC, fdatasync, O_DIRECT — নামের ভিড়ের পেছনে আসলে দুইটা আলাদা প্রশ্ন। কোনটার কী দাম, কোনটা আসলে কী নিশ্চয়তা দেয় না, আর Node-এ কখন কোনটা।

আগের তিন chapter-এ file I/O-র ভেতরটা দেখেছি: read-এর স্তর আর write()-এর মিথ্যা "হয়ে গেছে" (Chapter 21), page cache আর dirty page (Chapter 23)। File খোলার সময় বা লেখার পরে এই আচরণ বদলানোর অনেকগুলো উপায় আছে, আর নামগুলো গুলিয়ে যায়। সবগুলো আসলে দুইটা স্বাধীন প্রশ্নের কোনো একটার উত্তর:

  1. কে অপেক্ষা করবে? Disk-এর কাজ চলার সময় তোমার thread আটকে থাকবে, অন্য কেউ আটকাবে, নাকি কেউই না?
  2. Page cache-এর সাথে সম্পর্ক কী? Data RAM-এ রেখেই ফিরে আসবে, disk পর্যন্ত পৌঁছানোর অপেক্ষা করবে, নাকি page cache-কে পুরো এড়িয়ে যাবে?

প্রশ্ন ১: কে অপেক্ষা করবে

সাধারণ read() blocking: data না আসা পর্যন্ত call ফেরে না, thread ঘুমিয়ে থাকে (Chapter 15-এর Waiting অবস্থা)। Node-এর readFileSync ঠিক এটাই — আর যেহেতু সে main thread-এ চলে, অপেক্ষার পুরো সময়টা event loop বন্ধ।

Network socket-এর বেলায় এর একটা পরিচিত সমাধান আছে (Chapter 28–29-এ বিস্তারিত): fd-কে non-blocking করে দাও — data না থাকলে read() না ঘুমিয়ে সাথে সাথে EAGAIN ("এখন নেই, পরে এসো") error দিয়ে ফেরে। তারপর kernel-কে বলো "এই fd-তে data এলে আমাকে জাগিও" — Linux-এ এই ব্যবস্থার নাম epoll। Regular file-এ কি একই কৌশল চলে?

EXPERIMENT (Linux / Docker) — nonblock.py
# nonblock.py (Linux) — pipe বনাম regular file, দুইটাই non-blocking
import os, select

r, w = os.pipe()                       # pipe: এক পাশে লেখা, অন্য পাশে পড়া
os.set_blocking(r, False)
try:
    os.read(r, 100)
except BlockingIOError as e:
    print('pipe read :', e)

fd = os.open('/etc/hostname', os.O_RDONLY | os.O_NONBLOCK)
print('file read :', os.read(fd, 100))

ep = select.epoll()
ep.register(r, select.EPOLLIN)
print('epoll + pipe: registered')
try:
    ep.register(fd, select.EPOLLIN)
except PermissionError as e:
    print('epoll + file:', e)

Pipe (দুই process-এর মধ্যে একমুখী নল, kernel-এর বানানো) খালি থাকায় non-blocking read সাথে সাথে EAGAIN (Errno 11) দিয়ে ফিরেছে — ঠিক যেমন হওয়ার কথা। কিন্তু regular file-এ O_NONBLOCK-এর কোনো প্রভাবই নেই, আর epoll file নিতেই অস্বীকার করেছে (EPERM)। কারণটা ধারণাগত: socket বা pipe-এ "data এখনো আসেনি" একটা আসল অবস্থা — অন্য পাশে কেউ লিখলে তবে আসবে। File-এর data সবসময়ই "আছে", শুধু disk থেকে আনতে সময় লাগে, আর সেই আনা ঘটে read()-এর ভেতরেই। "Ready কি না" জিজ্ঞেস করার কিছু নেই, তাই epoll-এর মডেল এখানে খাটে না।

তাহলে file I/O-তে event loop না আটকানোর উপায় দুইটা। প্রথমটা Node-এর বহু পুরনো পথ: blocking কাজটা অন্য একটা thread-কে দাও। Chapter 21-এর strace-এ দেখেছ — readFile-এর openat, read, close চলেছিল libuv thread pool-এর আলাদা আলাদা thread-এ, আর main thread শুধু কাজ শেষের খবর পেয়েছিল। Socket-এর বেলায় কোনো pool লাগে না, main thread নিজেই epoll-এ অপেক্ষা করে — নিচের ছবিতে দুটো পাশাপাশি।

দ্বিতীয় পথ Linux-এর নতুন io_uring: process আর kernel-এর মধ্যে ভাগাভাগি করা memory-তে দুইটা ring (Chapter 11-এর descriptor ring-এর মতো) — একটায় process কাজের অনুরোধ লিখে রাখে ("এই fd-র এই জায়গা থেকে এত byte পড়ো"), kernel নিজে সেগুলো করে অন্যটায় ফলাফল রাখে। কেউ আটকায় না, আর অনেকগুলো অনুরোধের জন্য একটা system call-ই যথেষ্ট। এটা "ready হলে জানাও" না, "কাজ শেষ হলে জানাও" — তাই file-এও চলে। Node কি এটা ব্যবহার করে? আমার Node 22-এ (process.versions.uv = 1.51.0) Docker-এ strace করে দেখলাম (io_uring-এর system call Docker-এর default নিরাপত্তা নিয়মে বন্ধ, তাই --security-opt seccomp=unconfined লেগেছে): libuv একটা ring খোলে ঠিকই (io_uring_setup দেখা যায়), কিন্তু file-এর read তখনো pool thread-এর pread64 দিয়ে — UV_USE_IO_URING=1 দিলেও একই।

বাঁয়ে socket: main thread একবার epoll-এ ঘুমায়, হাজারটা fd-র যেকোনোটা ready হলে জাগে — কোনো বাড়তি thread লাগে না। ডানে file: epoll চলে না, তাই একটা pool thread pread64-এর ভেতরে kernel-এ ঘুমিয়ে disk-এর জন্য অপেক্ষা করে, আর main thread ততক্ষণ JS চালায়। Pool-এ ৪টা thread মানে একসাথে বড়জোর ৪টা file অপেক্ষা।

প্রশ্ন ২: page cache-এর সাথে সম্পর্ক

এবার দ্বিতীয় অক্ষ। লেখার সময় data কোথায় পৌঁছালে call ফিরবে, সেটা বদলানোর পাঁচটা হাতিয়ার:

  • Default (buffered): page cache-এ copy করেই ফেরে (Chapter 21)। দ্রুততম, কিন্তু crash-এ হারাতে পারে।
  • fsync(fd): এই file-এর সব dirty data আর metadata (size, সময় ইত্যাদি) disk-এ নামাও, তারপর ফেরো।
  • fdatasync(fd): একই, কিন্তু metadata-র শুধু সেটুকু যেটা ছাড়া data আবার পড়া যাবে না (যেমন file বড় হলে নতুন size); "শেষ কবে বদলেছে"-র মতো জিনিস বাদ। একটা disk write কম হতে পারে।
  • O_SYNC / O_DSYNC: file খোলার সময়ের flag। তারপর প্রতিটা write() নিজেই যেন শেষে একটা fsync / fdatasync করে ফেরে।
  • O_DIRECT: page cache-কে পুরো এড়িয়ে যাও — পরের অংশে।

প্রতিটার দাম মাপি। একই কাজ — ৫০০টা ১০০-byte-এর লাইন লেখা — ছয় রকমভাবে:

EXPERIMENT — durability.js (macOS আর Linux)
// durability.js — 500টা 100-byte লেখা, durability-র আলাদা আলাদা দামে
const fs = require('fs');
const { O_WRONLY, O_CREAT, O_TRUNC, O_SYNC, O_DSYNC } = fs.constants;
const line = 'x'.repeat(99) + '\n';
const N = 500;

function bench(label, flags, after) {
  const fd = fs.openSync('d.log', O_WRONLY | O_CREAT | O_TRUNC | flags);
  const t = performance.now();
  for (let i = 0; i < N; i++) { fs.writeSync(fd, line); after(fd, i); }
  const ms = performance.now() - t;
  fs.closeSync(fd);
  console.log(`${label.padEnd(26)} ${(ms * 1000 / N).toFixed(1).padStart(8)} µs per write`);
}
bench('plain write', 0, () => {});
bench('O_DSYNC', O_DSYNC, () => {});
bench('O_SYNC', O_SYNC, () => {});
bench('fdatasync every write', 0, fd => fs.fdatasyncSync(fd));
bench('fsync every write', 0, fd => fs.fsyncSync(fd));
bench('fsync every 100 writes', 0, (fd, i) => { if (i % 100 === 99) fs.fsyncSync(fd); });
fs.unlinkSync('d.log');

তিনটা শিক্ষা, প্রতিটা আলাদা করে মনে রাখার মতো:

  • Linux-এ চারটা sync পদ্ধতির দাম প্রায় এক (~২৭০ µs): O_SYNC, O_DSYNC, fsync, fdatasync সবাই device পর্যন্ত গিয়ে flush করে তবে ফেরে। এখানে শুধু file-এর শেষে জোড়া হচ্ছে বলে fdatasync-কেও size বদলানোর metadata লিখতে হচ্ছে, তাই সুবিধা চোখে পড়ে না; আগে থেকে বড় করে রাখা file-এর মাঝখানে লিখলে পার্থক্য দেখা যায়।
  • macOS-এ O_SYNC আসলে flash পর্যন্ত যায় না। ১৭–২০ µs মানে Chapter 21-এর সাধারণ macOS fsync-এর দাম — data SSD-র নিজের cache পর্যন্ত। Node-এর fsyncSync/fdatasyncSync macOS-এ F_FULLFSYNC ব্যবহার করে বলে সেগুলো ~৩.৮ ms। একই flag দুই OS-এ দুই রকম নিশ্চয়তা দেয় — "Linux-এ চলেছে" মানে "Mac-এও নিরাপদ" না।
  • Batching সব বদলে দেয়। প্রতি ১০০টা লেখায় একবার fsync করলে Mac-এ প্রতি লেখার দাম ৩,৭৫৪ µs থেকে ৫৬ µs — ৬৭ গুণ কম, কারণ একটা fsync-এর স্থির দাম ১০০টা লেখায় ভাগ হয়ে যায়। Database-রা এই কৌশলের নাম দিয়েছে group commit: একই মুহূর্তে commit হতে চাওয়া অনেকগুলো transaction-কে এক fsync-এ নামানো। দাম: শেষ fsync-এর পরের লেখাগুলো crash-এ হারাতে পারে।

O_DIRECT: page cache-কে পাশ কাটানো

O_DIRECT দিয়ে খোলা file-এ read আর write page cache-এ থামেই না: device DMA দিয়ে (Chapter 11) data সরাসরি তোমার buffer থেকে নেয় বা buffer-এ রাখে। কে চায় এটা? যে নিজের cache নিজে চালায় — যেমন একটা database engine, যার নিজের memory-তে data-র একটা সাজানো cache আছে। Kernel-এর page cache তখন শুধু একই data-র দ্বিতীয় কপি (RAM-এর অপচয়), আর kernel-এর সাধারণ নিয়মে কোনটা রাখা হবে তা database-এর নিজের জ্ঞানের চেয়ে খারাপ। MySQL-এর InnoDB-তে setting দিয়ে ঠিক এটাই বেছে নেওয়া যায়।

বিনিময়ে কড়া শর্ত: device block ধরে কাজ করে, আর মাঝে page cache নেই যে টুকরো জুড়ে দেবে। তাই লেখার মাপ, file-এর মধ্যে অবস্থান, এমনকি তোমার buffer RAM-এর যে ঠিকানায় শুরু হয় — সবকিছু block-এর মাপের গুণিতক হতে হয় (এই disk-এ ৫১২ byte)। Node-এ buffer কোন ঠিকানায় বসবে সেটা ঠিক করার উপায় নেই, তাই একটা বড় buffer-এর ভেতরে শুরুর জায়গা ১৬ byte করে সরিয়ে সরিয়ে চেষ্টা করি:

EXPERIMENT (Linux / Docker) — direct.js
// direct.js (Linux) — O_DIRECT-এর শর্ত: size আর memory-র ঠিকানা, দুটোই সাজানো
const fs = require('fs');
const { O_WRONLY, O_CREAT, O_TRUNC, O_DIRECT } = fs.constants;
const fd = fs.openSync('direct.bin', O_WRONLY | O_CREAT | O_TRUNC | O_DIRECT);
const big = Buffer.alloc(1 << 20);          // বড় একটা buffer; এর ভেতরে শুরুর জায়গা বদলে বদলে চেষ্টা
const tryWrite = buf => {
  try { fs.writeSync(fd, buf, 0, buf.length, 0); return 'ok'; } catch (e) { return e.code; }
};
console.log('100 bytes           :', tryWrite(big.subarray(0, 100)));
const ok = [];
for (let off = 0; off < 4096; off += 16)
  if (tryWrite(big.subarray(off, off + 4096)) === 'ok') ok.push(off);
console.log('4096 bytes, ok at   :', ok.join(', '));
fs.closeSync(fd);

 0B     0   4K direct.bin

১০০ byte সরাসরি EINVAL (অবৈধ argument)। 4096 byte-ও বেশিরভাগ জায়গা থেকে ব্যর্থ, সফল শুধু ঠিক ৫১২ byte পরপর — ৪৯৬, ১০০৮, ১৫২০…। মানে buffer-টা RAM-এর যে ঠিকানায় শুরু হয়েছে, তার থেকে ৪৯৬ byte সরলে ঠিকানাটা ৫১২-র গুণিতক হয়; ঠিক সেই জায়গাগুলো থেকেই লেখা গেছে। আর fincore দেখাচ্ছে file-এর 4 KB লেখা হলেও page cache-এ তার একটা page-ও নেই। dd ... oflag=direct নিজে থেকেই সাজানো buffer বানায় বলে সহজে চলে (Chapter 11); C, C++, Rust-এ লেখা database-ও তাই করে। Node-এ O_DIRECT কার্যত অবাস্তব।

আর একটা জরুরি কথা: O_DIRECT durability-র কোনো কথা দেয় না। Page cache এড়ায় ঠিকই, কিন্তু Chapter 21-এর device-এর নিজের volatile cache এখনো আছে। O_DIRECT দিয়ে লিখেও টেকসই চাইলে fsync বা O_DSYNC লাগবেই। O_DIRECT-এর প্রশ্নটা "cache-এর মালিক কে", "data কি নিরাপদ" না। macOS-এ O_DIRECT নেই; কাছাকাছি কাজ করে Chapter 20-এর F_NOCACHE।

তিনটা লেখার পথ। Buffered: CPU তোমার data page cache-এ copy করে আর ফিরে আসে, disk-এ যায় পরে। O_DSYNC/fsync: একই copy, কিন্তু device নিশ্চিত না করা পর্যন্ত অপেক্ষা। O_DIRECT: page cache বাদ, device সাজানো buffer থেকে সরাসরি নেয় — তবু device-এর নিজের cache-এর জন্য flush লাগে।

COMMON MISCONCEPTION

"O_SYNC দিয়ে খুললে বা O_DIRECT দিলে data নিরাপদ।" আমার Mac-এ O_SYNC-এর প্রতিটা লেখা ১৭ µs — data SSD-র volatile cache-এ পৌঁছেছে, flash-এ না; আসল flush (F_FULLFSYNC) লাগে ~৩.৮ ms। আর O_DIRECT durability-র কথাই বলে না, শুধু page cache এড়ায়। নিশ্চিত হতে হলে জানতে হয় তোমার OS-এ ঠিক কোন call device-কে flush করতে বলে — Node-এর fsyncSync দুই OS-এই সেটা করে।

MENTAL MODEL

প্রতিটা file I/O mode দুইটা নব-এর একটা অবস্থান। প্রথম নব: কে অপেক্ষা করে — তোমার thread (sync), অন্য thread (Node-এর pool), নাকি কেউ না (io_uring)। File-এ epoll-এর "ready হলে জানাও" চলে না, কারণ file-এর অপেক্ষা read()-এর ভেতরে। দ্বিতীয় নব: data কোথায় পৌঁছালে ফেরো — page cache (দ্রুত, ঝুঁকিপূর্ণ), device-এর flush পর্যন্ত (ধীর, নিরাপদ), নাকি page cache বাদ দিয়ে (O_DIRECT, নিজের cache যার আছে তার জন্য)। Durability-র দাম কমানোর একমাত্র আসল উপায় batching।
