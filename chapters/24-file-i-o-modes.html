Chapter 24 — File I/O-র Mode গুলো

Blocking, sync, async, O_SYNC, O_DIRECT — শব্দগুলোর পিছনের আসল প্রশ্ন দুটো মাত্র।

File I/O-র যাবতীয় mode আসলে দুইটা স্বাধীন প্রশ্নের উত্তর:

  1. আমার thread কি অপেক্ষা করবে? (blocking vs non-blocking/async)
  2. Page cache-এর সাথে সম্পর্ক কী হবে? (durability/caching)

প্রশ্ন ১: অপেক্ষা

  • Blocking (default): read() ডাকলে data না আসা পর্যন্ত thread টা Waiting-এ। সরল, বোঝা সহজ — আর এক thread-এ এক সময়ে একটাই I/O।
  • Asynchronous: "কাজটা শুরু করো, আমি অন্য কাজে যাচ্ছি — শেষ হলে জানিও।" Thread আটকায় না। Linux-এ আধুনিক উত্তর io_uring; Node.js তোমাকে যে async fs API দেয়, তার পিছনে (ঐতিহাসিকভাবে) থাকে thread pool — blocking read-গুলো অন্য thread-এ চালিয়ে তোমার thread-কে মুক্ত রাখা।

প্রশ্ন ২: cache-এর সাথে বোঝাপড়া

  • Default: সব page cache-এর মধ্য দিয়ে — write মানে cache-এ লেখা (fast, কিন্তু durable না যতক্ষণ না flush)।
  • O_SYNC: প্রতিটা write disk-এ পৌঁছানোর পরেই return করবে — যেন প্রতি write-এর সাথে ফাউ fsync। Durability সর্বোচ্চ, speed-এর দাম দিয়ে। (ছোট ভাই O_DSYNC — data আর শুধু ফেরত পড়ার জন্য দরকারি metadata sync করে, পুরো metadata না। WAL-ধরনের append path-এ সাধারণত এটাই যথেষ্ট আর সস্তা।)
  • O_DIRECT: Page cache-কে পুরোপুরি bypass — data সরাসরি disk ↔ তোমার buffer। কে চায় এটা? যে নিজে আরও ভালো cache চালায় — যেমন কিছু database engine: "kernel, তোমার generic cache লাগবে না, আমি আমার data আমি-ই ভালো বুঝি।" সাধারণ application-এর জন্য এটা প্রায় সবসময় ভুল choice — kernel-এর cache-টা আসলে চমৎকার।
    একটা ফাঁদ: O_DIRECT durability-র কথা বলে না। সে শুধু page cache এড়ায়; device-এর নিজের cache তো রয়েই গেল (Chapter 21)। তাই O_DIRECT দিয়ে লিখেও durability চাইলে fsync/O_DSYNC লাগবেই — database গুলো ঠিক তাই করে। O_DIRECT-এর প্রশ্নটা "cache-এর মালিক কে", "data কি নিরাপদ" না।
TRADE-OFF TRIANGLE

Speed, durability, simplicity — তিনটা একসাথে পুরোপুরি পাওয়া যায় না। Default mode: speed + simplicity। O_SYNC/fsync: durability কিনলে speed বেচতে হয়। O_DIRECT: control কিনলে simplicity বেচতে হয়। Database design-এর অর্ধেক আলোচনা এই ত্রিভুজের ভিতরে।
