PART 6 · STORAGE

Chapter 20 — Persistent Storage

Power চলে গেলেও data যেখানে টিকে থাকে — HDD আর SSD ভেতরে কীভাবে কাজ করে, "ধীর" মাপার তিনটা আলাদা উপায়, আর কেন একসাথে অনেক অনুরোধ পাঠালে SSD হঠাৎ দশ গুণ কাজ করে।

Chapter 7-এ দেখেছি RAM-এর প্রতিটা bit একটা ছোট্ট capacitor-এ জমা থাকা charge, যেটা নিজে থেকেই চুইয়ে পড়ে — তাই power গেলে RAM মুছে যায়। এমন memory-কে বলে volatile। তোমার code, database, photo টিকিয়ে রাখতে লাগে persistent (বা non-volatile) storage — যেখানে data power ছাড়াও থাকে। Chapter 2-এর টেবিলে দামটাও দেখেছিলাম: RAM ~১০০ ns, SSD ~২০–১০০ µs, hard disk ~৫–১০ ms। এই chapter-এ দেখব এই সংখ্যাগুলো কোথা থেকে আসে, আর নিজের machine-এর SSD মেপে দেখব।

HDD: ঘুরন্ত থালা আর নড়াচড়ার দাম

HDD (hard disk drive) হলো চুম্বকীয় আবরণ দেওয়া কয়েকটা গোল থালা (platter), যেগুলো একটা motor-এ অবিরাম ঘোরে। Data থাকে থালার উপর বৃত্তাকার পথে (track), আর প্রতিটা track ছোট ছোট টুকরোয় ভাগ করা (sector, সাধারণত 512 byte বা 4 KB)। পড়া-লেখা করে একটা head, যেটা একটা হাতলের (arm) মাথায় বসানো। একটা নির্দিষ্ট sector পড়তে দুইটা শারীরিক অপেক্ষা লাগে:

  1. Seek: হাতলটা সরিয়ে head-কে ঠিক track-এর উপর আনা। এটা যান্ত্রিক নড়াচড়া — গড়ে কয়েক millisecond।
  2. Rotational latency: head ঠিক track-এ এল, কিন্তু চাওয়া sector-টা হয়তো থালার উল্টো পাশে। সেটা ঘুরে head-এর নিচে আসা পর্যন্ত অপেক্ষা। থালা মিনিটে কতবার ঘোরে, তাকে বলে RPM।

হিসাবটা নিজেই করা যায়। সাধারণ desktop disk মিনিটে ৭২০০ বার ঘোরে: একবার ঘুরতে ৬০ ÷ ৭২০০ = ৮.৩ ms। গড়ে অর্ধেক পাক অপেক্ষা = ~৪.২ ms, তার সাথে seek ~৪ ms। মানে একটা এলোমেলো জায়গা পড়তে ~৮–১০ ms, সেকেন্ডে বড়জোর ~১০০টা। অথচ head একবার জায়গামতো বসে গেলে পরপর sector গুলো এমনিই তার নিচ দিয়ে ঘুরে যায় — তাই পরপর (sequential) পড়লে HDD সেকেন্ডে ~২০০ MB দিতে পারে। এলোমেলো (random) পড়ায় সে মরে, পরপর পড়ায় চলনসই — এই বৈষম্যই পুরনো database আর filesystem-এর অনেক নকশার পেছনের কারণ।

SSD: নড়াচড়া নেই, কিন্তু মোছার ঝামেলা

SSD (solid-state drive) data রাখে flash memory-র chip-এ: প্রতিটা cell-এর ভেতরে একটা অন্তরক দেয়ালে ঘেরা জায়গায় electron আটকে রাখা হয়, আর চারপাশ অন্তরক বলে power ছাড়াও electron পালাতে পারে না। কোনো নড়াচড়ার অংশ নেই, তাই seek বা ঘোরার অপেক্ষাও নেই। কিন্তু flash-এর দুইটা অদ্ভুত নিয়ম আছে, আর এখানে দুইটা শব্দ আগের chapter-এর অর্থ থেকে আলাদা — সাবধান:

  • Flash page (Chapter 9-এর memory page না): flash-এ পড়া-লেখার সবচেয়ে ছোট একক, সাধারণত কয়েক KB থেকে 16 KB।
  • Erase block: কয়েকশো flash page মিলে একটা block। Flash-এ একবার লেখা page-এর উপর আবার লেখা যায় না — আগে মুছতে হয়, আর মোছা যায় শুধু পুরো block একসাথে।

তাহলে তুমি file-এর একটা 4 KB জায়গা বদলালে কী হয়? পুরো block মুছে আবার লেখা ভয়ংকর ধীর হতো। তাই SSD-র ভেতরের controller-এ একটা ছোট software চলে — FTL (flash translation layer)। বাইরে থেকে SSD নিজেকে দেখায় নম্বর দেওয়া block-এর একটা লম্বা সারি হিসেবে — এই নম্বরকে বলে LBA (logical block address); OS শুধু বলে "LBA ৭ পড়ো/লেখো"। FTL-এর কাছে একটা table আছে: কোন LBA আসলে কোন chip-এর কোন flash page-এ। নতুন লেখা এলে FTL সেটা একটা খালি page-এ লেখে, table বদলে দেয়, আর পুরনো page-কে "বাতিল" (stale) দাগায়। Chapter 9-এর page table-এর সাথে মিলটা খেয়াল করো — এখানেও একটা নাম (LBA) আর আসল জায়গার মাঝে অনুবাদ, যাতে আসল জায়গা চুপচাপ বদলানো যায়।

বাতিল page জমতে থাকলে FTL পেছনে পরিষ্কারের কাজ চালায় (garbage collection): একটা block-এর যে কয়টা page এখনো কাজের, সেগুলো অন্য জায়গায় সরিয়ে পুরো block মুছে ফেলে। এই সরানোর জন্য তুমি যত byte লিখেছ, flash-এ আসলে তার চেয়ে বেশি লেখা হয় — একে বলে write amplification। আর প্রতিটা flash cell কয়েক হাজার বার মোছার পরে নষ্ট হয়ে যায়, তাই FTL লেখাগুলো সব block-এ সমানভাবে ছড়ায় (wear leveling)। OS-ও সাহায্য করে: file মুছলে TRIM command দিয়ে SSD-কে জানায় "এই LBA গুলো আর লাগবে না" — তাহলে garbage collection-এর সময় সেগুলো সরাতে হয় না।

আমার Mac-এ: Capacity: 500.28 GB, Model: APPLE SSD AP0512Z, TRIM Support: Yes, আর Device Block Size: 4096 Bytes — বাইরে থেকে SSD নিজেকে 4 KB-র LBA-র সারি হিসেবে দেখায়। ভেতরের flash page, erase block, FTL-এর table — সবই controller-এর গোপন ব্যাপার।

বাঁয়ে HDD: একটা random read মানে হাতল সরানো (①) আর sector ঘুরে আসার অপেক্ষা (②) — দুটোই যান্ত্রিক, তাই millisecond। ডানে SSD: controller-এর FTL প্রতিটা LBA-কে কোনো chip-এর কোনো flash page-এ বসায়; একই জায়গায় আবার লেখা যায় না, তাই নতুন data যায় খালি page-এ আর পুরনোটা stale হয়। আর chip গুলো আলাদা আলাদা কাজ একসাথে করতে পারে — এই chapter-এর শেষ অংশের চাবি এটাই।

তিনটা মাপ: latency, throughput, IOPS

"Disk ধীর" বললে তিনটা আলাদা জিনিস বোঝাতে পারে, আর তিনটা আলাদা অক্ষে মাপতে হয়:

  • Latency: একটা অনুরোধ পাঠানো থেকে উত্তর আসা পর্যন্ত সময়। Database-এর একটা ছোট lookup এখানে আটকায়।
  • Throughput (বা bandwidth): প্রতি সেকেন্ডে মোট কত byte সরানো যায়। বড় file copy বা backup এখানে আটকায়।
  • IOPS (I/O operations per second): প্রতি সেকেন্ডে কয়টা আলাদা অনুরোধ শেষ হয়, প্রতিটা যত ছোটই হোক। হাজার হাজার ছোট random read-এর কাজে এটাই আসল সীমা।

মাপতে একটা বাধা আছে। কোনো file একবার পড়লে kernel সেটা RAM-এ রেখে দেয় (Chapter 2-এর page cache, বিস্তারিত Chapter 23), তাই দ্বিতীয়বার পড়লে আসলে RAM মাপা হয়ে যায়। macOS-এ F_NOCACHE নামের একটা setting আছে যেটা একটা খোলা file-এর জন্য বলে "এর data RAM-এ জমিয়ো না" — তাহলে প্রতিটা read সত্যি SSD পর্যন্ত যায়। Node-এ এই setting দেওয়ার উপায় নেই, তাই script-টা Python-এ। os.pread(fd, n, offset) মানে "file-এর offset byte থেকে n byte পড়ো" — Node-এর fh.read(buf, 0, n, offset)-এর একই কাজ।

EXPERIMENT — storage.py (macOS, 2 GB জায়গা লাগবে)
# storage.py — cache এড়িয়ে (F_NOCACHE) Mac-এর SSD থেকে সরাসরি পড়া
import os, fcntl, random, time, threading

PATH = 'test.bin'
SIZE = 2 * 1024**3                      # 2 GB
BLK  = 4096

if not os.path.exists(PATH):
    fd = os.open(PATH, os.O_WRONLY | os.O_CREAT, 0o644)
    fcntl.fcntl(fd, fcntl.F_NOCACHE, 1)  # লেখার সময়ও RAM-এ জমিয়ো না
    chunk = os.urandom(8 * 1024**2)
    for _ in range(SIZE // len(chunk)):
        os.write(fd, chunk)
    os.fsync(fd); os.close(fd)

def open_nocache():
    fd = os.open(PATH, os.O_RDONLY)
    fcntl.fcntl(fd, fcntl.F_NOCACHE, 1)
    return fd

def run(label, bs, offsets):
    fd = open_nocache()
    t = time.perf_counter()
    for off in offsets:
        os.pread(fd, bs, off)
    dt = time.perf_counter() - t
    os.close(fd)
    n = len(offsets)
    print(f'{label:28s} {n*bs/dt/1e6:8.0f} MB/s  {n/dt:9.0f} IOPS  {dt/n*1e6:7.1f} µs/read')

N = 20000
seq = [i * BLK for i in range(N)]
rnd = [random.randrange(SIZE // BLK) * BLK for _ in range(N)]
run('sequential 4 KB', BLK, seq)
run('random     4 KB', BLK, rnd)
run('sequential 1 MB', 1024**2, [i * 1024**2 for i in range(1024)])

# একসাথে অনেক অনুরোধ: T টা thread, প্রত্যেকে random 4 KB পড়ে
for T in (1, 4, 16, 64):
    per = 40000 // T
    def work():
        fd = open_nocache()
        for _ in range(per):
            os.pread(fd, BLK, random.randrange(SIZE // BLK) * BLK)
        os.close(fd)
    ths = [threading.Thread(target=work) for _ in range(T)]
    t = time.perf_counter()
    for th in ths: th.start()
    for th in ths: th.join()
    dt = time.perf_counter() - t
    print(f'random 4 KB, {T:2d} at a time    {per*T/dt:9.0f} IOPS')

প্রথম তিন লাইন এখানে দেখো; শেষ চার লাইন পরের অংশে। কাজ শেষে rm test.bin।

প্রথম তিন লাইন থেকে তিনটা শিক্ষা:

  • SSD-র latency µs-এর ঘরে: একটা random 4 KB read ~৭৯ µs। Chapter 7-এ RAM থেকে একটা cache line আনতে লেগেছিল ~১২০ ns — SSD প্রায় ৬৫০ গুণ ধীর। আর HDD-র হিসাব করা ~৮ ms-এর চেয়ে প্রায় ১০০ গুণ দ্রুত।
  • SSD-তেও sequential জেতে: পরপর 4 KB পড়ায় ~২২ µs, এলোমেলোতে ~৭৯ µs — প্রায় সাড়ে তিন গুণ। SSD-র controller-ও পরপর চাওয়া চিনতে পারে, আর একটা flash page (4 KB-র কয়েক গুণ বড়) একবারে পড়ে পরের অংশগুলো হাতে রাখতে পারে। HDD-র মতো আকাশ-পাতাল না, কিন্তু উপেক্ষা করার মতোও না।
  • বড় অনুরোধে throughput: 1 MB করে পড়লে সেকেন্ডে ২.৬ GB, অথচ random 4 KB-তে মাত্র ৫২ MB — পঞ্চাশ গুণ পার্থক্য, একই disk-এ। প্রতিটা অনুরোধের একটা স্থির খরচ আছে (Chapter 11-এর descriptor, doorbell, interrupt), বড় অনুরোধে সেটা অনেক byte-এ ভাগ হয়ে যায়।
COMMON MISCONCEPTION

"SSD-তে তো seek নেই, তাই random আর sequential একই।" মাপে দেখলে না: আমার SSD-তে sequential 4 KB random-এর চেয়ে সাড়ে তিন গুণ দ্রুত, আর 1 MB-র টুকরোয় পড়লে throughput পঞ্চাশ গুণ। HDD-তে পার্থক্যটা শত গুণের, SSD-তে কম — কিন্তু আছে। এজন্যই database গুলো লেখার সময় আগে সবকিছু একটা file-এর শেষে পরপর জুড়ে দেয় — একে বলে append-only log বা WAL (write-ahead log) — তারপর সময় নিয়ে আসল জায়গায় সাজায়।

NVMe: একসাথে অনেক অনুরোধ

এবার শেষ চার লাইন। একটা thread একটা করে random read পাঠালে ~১২,৬০০ IOPS — মানে প্রতিটা ৭৯ µs, হিসাব মিলে যায় (১ সেকেন্ড ÷ ৭৯ µs ≈ ১২,৬০০)। কিন্তু ৪টা thread একসাথে পাঠালে ৪৫,০০০, ১৬টায় ১,১১,০০০ — প্রায় নয় গুণ, একই disk। কীভাবে?

উপরের ছবির ডান পাশটা মনে করো: একটা SSD-তে অনেকগুলো flash chip, প্রত্যেকে আলাদা কাজ একসাথে করতে পারে। একটা অনুরোধ একটা chip-এ গেলে বাকিরা বসে থাকে। একসাথে অনেক অনুরোধ হাতে পেলে controller সেগুলো আলাদা chip-এ ছড়িয়ে দেয়। কতগুলো অনুরোধ একই মুহূর্তে device-এর হাতে আছে, তাকে বলে queue depth। পুরনো SATA interface (HDD-র যুগে বানানো) একটা queue-তে বড়জোর ৩২টা অনুরোধ রাখতে পারত। NVMe হলো SSD-র জন্য নতুন করে বানানো নিয়ম: device বসে সরাসরি PCIe-তে (CPU-র সাথে device জোড়ার দ্রুততম bus, Chapter 2), আর standard অনুযায়ী ৬৫ হাজার পর্যন্ত queue রাখা যায়, প্রতিটায় ৬৫ হাজার পর্যন্ত অনুরোধ — সাধারণত প্রতিটা CPU core-এর জন্য নিজস্ব queue, যাতে core-দের মধ্যে lock-এর লড়াই না লাগে। Chapter 11-এর descriptor ring-ই এই queue।

একই SSD, একই random 4 KB read — শুধু একসাথে কতগুলো অনুরোধ পাঠানো হচ্ছে সেটা বদলেছে (x-অক্ষে ১, ৪, ১৬, ৬৪ সমান দূরত্বে, কারণ প্রতিটা আগেরটার ৪ গুণ)। ৪ পর্যন্ত প্রায় নিখুঁত বাড়ে (dashed রেখা), ১৬-তে ৯ গুণ, তারপর device-এর ভেতরের chip-রা সবাই ব্যস্ত — আর বাড়ে না। বিন্দুতে hover করলে ঠিক সংখ্যা।

এর মানে পরিষ্কার: SSD থেকে পুরো গতি পেতে হলে একসাথে অনেক অনুরোধ তার হাতে দিতে হয়। এক thread-এ একটার পর একটা readFileSync দিলে তুমি device-এর দশ ভাগের এক ভাগ ব্যবহার করছ। এবার Node-এর দিকে তাকাও। Chapter 19-এ দেখেছিলাম Node-এর async fs call গুলো libuv-এর thread pool-এ চলে, আর pool-এ default ৪টা thread। মানে তুমি যত await-ই একসাথে ছাড়ো, disk-এর হাতে একসাথে বড়জোর ৪টা অনুরোধ যায়:

EXPERIMENT — nodeqd.js (storage.py যে test.bin বানিয়েছে, সেটাই পড়ে)
// nodeqd.js — Node-এর fs দিয়ে 20,000টা random 4 KB read, একসাথে 64টা চাওয়া
const fs = require('fs/promises');
const [half] = process.argv.slice(2).map(Number);     // 0 বা 1: file-এর কোন অর্ধেক
(async () => {
  const fh = await fs.open('test.bin');
  const blocks = 1024 ** 3 / 4096;                    // এক অর্ধেকে (1 GB) কয়টা 4 KB block
  const buf = () => Buffer.alloc(4096);
  let left = 20000;
  const t = performance.now();
  async function worker() {
    while (left-- > 0) {
      const b = half * blocks + Math.floor(Math.random() * blocks);
      await fh.read(buf(), 0, 4096, b * 4096);
    }
  }
  await Promise.all(Array.from({ length: 64 }, worker));
  const ms = performance.now() - t;
  console.log(`pool=${process.env.UV_THREADPOOL_SIZE || 4}: ${Math.round(20000 / ms * 1000)} IOPS`);
  await fh.close();
})();
node nodeqd.js 0                          # প্রথম 1 GB, default pool
UV_THREADPOOL_SIZE=64 node nodeqd.js 1    # দ্বিতীয় 1 GB, 64টা thread

আমার output: pool=4: 52294 IOPS, pool=64: 129651 IOPS। দুইবার file-এর আলাদা অর্ধেক পড়া হয়েছে, যাতে প্রথম run-এর পড়া data RAM-এ থেকে গিয়ে দ্বিতীয়টাকে সাহায্য না করে (একই কারণে আবার চালালে সংখ্যা বাড়বে — Chapter 23)।

Script-এ ৬৪টা কাজ একসাথে await করছে, কিন্তু default pool-এ Python-এর "৪টা একসাথে"-র মতোই ~৫০ হাজার IOPS। Pool ৬৪ করতেই আড়াই গুণ। Random read-ভারী কাজে (যেমন নিজের বানানো key-value store, বা হাজারটা ছোট file পড়া) UV_THREADPOOL_SIZE বাড়ানোর যুক্তি এটাই — তবে Chapter 19-এর সতর্কতাও মনে রেখো: pool-টা crypto, zlib, dns.lookup-এর সাথে ভাগাভাগি।

এসব জেনে software কীভাবে বদলায়

এই মাপগুলো থেকে কয়েকটা সরাসরি নিয়ম বেরোয়, আর বড় system-গুলো ঠিক এভাবেই বানানো:

  • লেখাকে sequential বানাও: WAL, log file, Kafka-র মতো system — সবাই file-এর শেষে জুড়ে যায়, এলোমেলো জায়গায় বসায় না।
  • বড় টুকরোয় পড়ো-লেখো: ৪ KB-র হাজারটা অনুরোধের চেয়ে ১ MB-র চারটা অনেক সস্তা, কারণ অনুরোধ-প্রতি খরচ ভাগ হয়ে যায়।
  • একসাথে অনেক অনুরোধ হাতে দাও: SSD-র parallelism একা একটা sequential loop কখনো ব্যবহার করতে পারে না।
  • Cloud disk-এর সীমা জানো: cloud-এ ভাড়া করা disk-এর IOPS আর throughput দুটোই কেনা সীমা — যেমন AWS-এর gp3 volume-এর মূল সীমা ৩,০০০ IOPS আর ১২৫ MB/s, বেশি চাইলে আলাদা দাম। তোমার laptop-এর SSD এক thread-েই এর চার গুণ দেয়; তাই laptop-এ দ্রুত চলা কাজ server-এ হঠাৎ ধীর হতে পারে।
MENTAL MODEL

Storage-এর গতি একটা সংখ্যা না, তিনটা: একটা অনুরোধের latency, সেকেন্ডে কত অনুরোধ (IOPS), সেকেন্ডে কত byte (throughput)। HDD-র latency যান্ত্রিক (seek + ঘোরা), তাই random-এ মরে। SSD-র latency µs-এ, কিন্তু ভেতরে FTL অনুবাদ করে আর মুছে-লিখে সামলায়, আর তার আসল শক্তি অনেক chip-এর parallelism — যেটা পেতে হলে একসাথে অনেক অনুরোধ দিতে হয়। ছোট, একা, এলোমেলো অনুরোধ — storage-এর সবচেয়ে খারাপ ব্যবহার।

CAN I EXPLAIN THIS?
  • ৭২০০ RPM-এর HDD-তে একটা random read ~৮–১০ ms লাগে কেন — দুইটা যান্ত্রিক অপেক্ষা কী কী, আর হিসাবটা কীভাবে?
  • Flash-এ একটা page-এর উপর সরাসরি আবার লেখা যায় না — তাহলে SSD একটা 4 KB জায়গা বদলায় কীভাবে? FTL, stale page, garbage collection আর TRIM — কে কী করে?
  • Latency, throughput আর IOPS-এর পার্থক্য কী? storage.py-তে random 4 KB ৫২ MB/s কিন্তু 1 MB-র টুকরোয় ২.৬ GB/s কেন?
  • একই SSD এক thread-এ ~১২,৬০০ IOPS কিন্তু ১৬ thread-এ ~১,১১,০০০ দেয় কেন? Queue depth কী, আর NVMe এখানে SATA থেকে কীভাবে আলাদা?
  • nodeqd.js-এ ৬৪টা await একসাথে দিয়েও default Node-এ ~৫০ হাজার IOPS কেন? UV_THREADPOOL_SIZE=64 দিলে কী বদলায়?
