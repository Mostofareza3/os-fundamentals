PART 5 · PROCESS MANAGEMENT

Chapter 17 — Context Switching

একটা core-এ এক মুহূর্তে একটাই thread — তবু শত শত thread "একসাথে" চলে। পালা বদলের যন্ত্রটা কীভাবে কাজ করে, কখন ঘটে, আর তার দাম কোথায় লুকিয়ে থাকে।

যা লাগবে, এক লাইনে: scheduler ready থাকা thread-দের মধ্য থেকে কাউকে core-এ বসায়, time slice শেষে বা কেউ block হলে পালা বদলায় (Chapter 15); প্রতিটা thread-এর নিজের PC, SP আর register (Chapter 16); প্রতিটা process-এর নিজের page table, যেটা CPU-র একটা register দেখায় (Chapter 9); আর cache ও TLB সাম্প্রতিক data আর অনুবাদ ধরে রাখে (Chapter 13, 10)। এই chapter-এ দেখব scheduler-এর সিদ্ধান্ত বাস্তবে কার্যকর হয় কীভাবে, আর তাতে কী হারায়।

Context: থামানো thread-কে ঠিক সেখান থেকে চালানোর জন্য যা লাগে

Kernel thread A-কে core থেকে নামিয়ে পরে আবার বসাতে চায় — আর A যেন টেরই না পায়। তাহলে নামানোর মুহূর্তে CPU-র ভেতরে A-র যা যা আছে, সব কোথাও তুলে রাখতে হবে: কোন instruction-এ ছিল (PC), stack কোথায় (SP), প্রতিটা সাধারণ register-এর মান (হিসাবের মাঝপথের সংখ্যা), শেষ তুলনার ফলাফল (flags), আর floating-point/SIMD register গুলো — এগুলোই সবচেয়ে বড়। A অন্য process-এর হলে তার page table-ও। এই পুরো সংগ্রহের নাম context। Kernel এটা রাখে thread-এর নিজের kernel-record-এ (Linux-এ task_struct-এর সাথে)। কিছু না হারিয়ে ঠিক এটুকু ফিরিয়ে দিলেই A আবার সেই instruction থেকে চলবে, যেন মাঝে কিছুই ঘটেনি।

Switch কীভাবে ঘটে

একটা context switch শুরু হয় দুইভাবে: timer interrupt এল আর scheduler ঠিক করল A-র পালা শেষ (Chapter 2, 15), অথবা A নিজেই এমন syscall করল যেটায় অপেক্ষা করতে হবে — read, sleep, lock-এর অপেক্ষা। দুই ক্ষেত্রেই CPU আগে kernel mode-এ ঢোকে (Chapter 1), তারপর:

  1. A-র register গুলো (PC, SP, বাকি সব) A-র kernel-record-এ সেভ।
  2. Scheduler run queue থেকে পরের জনকে বাছে — ধরো B।
  3. B অন্য process-এর হলে page table-এর register-এ B-র page table বসানো (Chapter 9)। একই process-এর দুই thread হলে এই ধাপ লাগে না।
  4. B-র সেভ করা register গুলো CPU-তে ফেরত — SP এখন B-র stack দেখায়, PC B-র পরের instruction।
  5. User mode-এ ফেরা। B ঠিক সেখান থেকে চলতে শুরু করে যেখানে সে শেষবার থেমেছিল।

উপরে user mode-এ A চলছিল; timer interrupt বা একটা blocking syscall তাকে kernel-এ নিয়ে আসে। নিচে kernel-এর চার ধাপ — সেভ, বাছাই, (দরকার হলে) page table বদল, লোড — তারপর user mode-এ ফিরে B চলে। A-র কাছে পুরো ব্যাপারটা অদৃশ্য: পরেরবার ④-এ তার context লোড হলে সে ঠিক আগের instruction থেকে চলবে।

দুই রকম switch: স্বেচ্ছায় আর বাধ্য হয়ে

ওপরের দুই শুরুর পথের দুইটা নাম আছে। Voluntary switch — thread নিজেই CPU ছেড়ে দিল, কারণ তার অপেক্ষা করার কিছু আছে (I/O, sleep, lock)। Involuntary switch — thread চলতে চাইছিল, কিন্তু kernel জোর করে নামিয়ে দিল (time slice শেষ, বা বেশি গুরুত্বপূর্ণ কেউ জেগেছে)। Linux দুইটাই গোনে, আর Node process.resourceUsage() দিয়ে দেখায়:

EXPERIMENT (Linux / Docker) — switches.js
const ru = () => { const r = process.resourceUsage(); return [r.voluntaryContextSwitches, r.involuntaryContextSwitches]; };
const mode = process.argv[2];
const [v0, i0] = ru();
if (mode === 'sleepy') {
  // বারবার ঘুমাও — প্রতিবার নিজে CPU ছেড়ে দিচ্ছে
  let n = 0;
  const tick = () => (++n < 200 ? setTimeout(tick, 1) : report());
  tick();
} else {
  // অবিরাম হিসাব — কখনো নিজে ছাড়ে না
  const end = Date.now() + 2000;
  let x = 0;
  while (Date.now() < end) x++;
  report();
}
function report() {
  const [v1, i1] = ru();
  console.log(`${mode.padEnd(6)} voluntary: ${v1 - v0}   involuntary: ${i1 - i0}`);
}

তিনভাবে চালাও — ঘুমপ্রিয়টা, একা busy-টা, আর একটা core-এ আরেকটা loop-এর সাথে ভাগাভাগি করে busy-টা (taskset -c 0 দুজনকেই CPU 0-তে আটকায়, Chapter 15):

docker run --rm -v "$PWD":/w node:22-bookworm-slim bash -c '
  node /w/switches.js sleepy
  node /w/switches.js busy
  taskset -c 0 node -e "while(true){}" & C=$!; sleep 0.5
  taskset -c 0 node /w/switches.js busy; kill $C'

আমার output:

sleepy voluntary: 199   involuntary: 0
busy   voluntary: 7   involuntary: 14
busy   voluntary: 8   involuntary: 275

ঘুমপ্রিয় process-এ প্রায় প্রতিটা setTimeout-এ একটা voluntary switch — সে নিজে block হয়ে CPU ছেড়েছে, কেউ তাকে সরায়নি। একা busy loop-এ switch প্রায় নেই: অন্য core খালি, কাউকে তার জায়গা লাগেনি। কিন্তু একই core আরেকটা loop-এর সাথে ভাগ করতেই দুই সেকেন্ডে ২৭৫টা involuntary switch — প্রায় প্রতি ৭ ms-এ scheduler জোর করে পালা বদলাচ্ছে। (macOS এই দুই সংখ্যা নির্ভরযোগ্যভাবে দেয় না, তাই Linux।)

Production-এ এই দুই সংখ্যা রোগ চেনায়: involuntary বেশি মানে CPU-র জন্য কাড়াকাড়ি — core-এর তুলনায় বেশি runnable thread; voluntary বেশি মানে প্রচুর blocking I/O বা lock-এর অপেক্ষা। পুরো system-এর হিসাব Linux রাখে /proc/stat-এর ctxt লাইনে (আসল machine-এ vmstat 1-এর cs column একই জিনিস):

docker run --rm alpine sh -c "awk '/^ctxt/{print \$2}' /proc/stat; sleep 1; awk '/^ctxt/{print \$2}' /proc/stat"

আমার চালানোয় 58931623 থেকে 58934114 — প্রায় চুপচাপ একটা VM-এও সেকেন্ডে ~২,৫০০ switch।

দামটা কোথায়

প্রথম দাম সরাসরি: kernel-এ ঢোকা-বেরোনো, register সেভ আর লোড, scheduler-এর সিদ্ধান্ত, আর ঘুমন্ত thread-কে জাগানো (অন্য core-এ হলে সেই core-কে interrupt পাঠিয়ে ডাকা)। কত? দুইটা thread-এর মধ্যে একটা বল চালাচালি করে মাপো — একবার অপেক্ষার সময় kernel-এর কাছে ঘুমিয়ে পড়ে (Atomics.wait), আরেকবার না ঘুমিয়ে অবিরাম দেখতে থেকে:

EXPERIMENT — pingpong.js

Atomics.wait kernel-এর কাছে বলে "এই memory-র মান না বদলানো পর্যন্ত আমাকে ঘুম পাড়াও"; Atomics.notify বলে "ওখানে যে ঘুমাচ্ছে তাকে জাগাও":

const { Worker, isMainThread, workerData } = require('worker_threads');
const ROUNDS = 100_000;

if (isMainThread) {
  for (const mode of ['sleep', 'spin']) {
    const flag = new Int32Array(new SharedArrayBuffer(4));   // 0 = main-এর পালা, 1 = worker-এর পালা
    const w = new Worker(__filename, { workerData: { flag, mode } });
    const t = performance.now();
    for (let i = 0; i < ROUNDS; i++) {
      Atomics.store(flag, 0, 1); Atomics.notify(flag, 0);      // বল worker-এর দিকে
      if (mode === 'sleep') while (Atomics.load(flag, 0) === 1) Atomics.wait(flag, 0, 1);  // ঘুমিয়ে অপেক্ষা
      else while (Atomics.load(flag, 0) === 1);                                              // না ঘুমিয়ে বারবার দেখা
    }
    const us = (performance.now() - t) * 1000 / ROUNDS;
    console.log(`${mode.padEnd(5)}: ${us.toFixed(2)} µs per round trip`);
    w.terminate();
  }
} else {
  const { flag, mode } = workerData;
  for (;;) {
    if (mode === 'sleep') while (Atomics.load(flag, 0) === 0) Atomics.wait(flag, 0, 0);
    else while (Atomics.load(flag, 0) === 0);
    Atomics.store(flag, 0, 0); Atomics.notify(flag, 0);        // বল main-এর দিকে
  }
}

আমার Mac-এ: sleep: 5.36 µs, spin: 0.22 µs প্রতি round trip। Docker-এর Linux-এ: 2.36 µs আর 0.30 µs।

ঘুমিয়ে-জাগিয়ে পালা দিলে প্রতি চালাচালিতে কয়েক microsecond — kernel-এ দুইবার ঢোকা, ঘুম পাড়ানো, জাগানো, scheduler। না ঘুমিয়ে অবিরাম দেখলে (spin) kernel ছোঁয়াই হয় না — শুধু Chapter 13-এর মতো একটা cache line দুই core-এর মধ্যে চালাচালি — ২০ গুণেরও বেশি সস্তা। তাহলে সবসময় spin না কেন? কারণ spin করা thread অপেক্ষার পুরো সময় একটা core ১০০% জ্বালিয়ে রাখে, যেটা অন্য কেউ কাজে লাগাতে পারত। বাস্তব lock গুলো তাই মাঝামাঝি পথ নেয়: অল্প কিছুক্ষণ spin, তারপরও না পেলে kernel-এর কাছে ঘুম (Linux-এ এই ঘুম-জাগানোর syscall-এর নাম futex)।

দ্বিতীয় দাম লুকানো, আর প্রায়ই বড়টা: B core-এ বসে দেখে cache ভরা A-র data-য় (Chapter 13) — তার নিজের data আনতে একের পর এক miss। TLB-তেও A-র অনুবাদ (Chapter 10)। আধুনিক CPU প্রতিটা TLB entry-র সাথে address space-এর একটা ছোট tag রাখে (x86-এ PCID, ARM-এ ASID), তাই switch-এ TLB পুরো মুছতে হয় না — কিন্তু জায়গা সীমিত, সবাই ঠেলাঠেলি করে। Branch predictor-এর শেখা অভ্যাসও (Chapter 14) অন্যের। A ফিরে এসে দেখে তার গরম cache ততক্ষণে ঠান্ডা। Register সেভ-লোড nanosecond-এর কাজ; এই "গরম হতে লাগা" সময়টা কয়েক দশ microsecond পর্যন্ত যেতে পারে, working set যত বড় তত বেশি। একই process-এর দুই thread-এর মধ্যে switch একটু সস্তা — page table বদলায় না, আর ভাগ করা data হয়তো cache-এ থেকেই যায়।

Oversubscription: বেশি thread, কম কাজ

CPU-র কাজ করা thread যদি core-এর চেয়ে বেশি হয়, scheduler-কে ক্রমাগত জোর করে পালা বদলাতে হয় — প্রতিবার সরাসরি দাম আর cache ঠান্ডা হওয়ার দাম। মোট কাজ একটুও বাড়ে না, শুধু বদলাবদলির খরচ যোগ হয়। Chapter 14-এর parallel.js এর প্রমাণ: ১২টা worker-এ ১৬৯ ms, ২৪টায় ১৮০ ms — দ্বিগুণ thread, বেশি সময়। এই অবস্থার নাম oversubscription। (এটাকে "thrashing" বলো না — ওই শব্দ Chapter 10-এর রোগের, যেখানে working set RAM-এ আঁটে না বলে system অবিরাম page আনা-নেওয়া করে।)

ব্যবহারিক নিয়ম: CPU-র কাজের জন্য thread বা worker রাখো core-এর সংখ্যার কাছাকাছি — Node-এ require('os').availableParallelism() সংখ্যাটা দেয়। যে কাজ বেশিরভাগ সময় অপেক্ষা করে, তার জন্য হিসাব আলাদা — সেটা Chapter 19।

COMMON MISCONCEPTION

"Context switch-এর খরচ হলো register সেভ আর লোড করা।" ওটা সবচেয়ে সস্তা অংশ — কয়েকশো byte, nanosecond-এর কাজ। আসল দাম kernel-এ ঢোকা-বেরোনো, ঘুমন্ত thread জাগানো (pingpong.js-এর কয়েক µs), আর তার চেয়েও বড় — switch-এর পরে ঠান্ডা cache, ভাগাভাগি করা TLB, আর অন্যের শেখা branch predictor। এজন্যই "সস্তা" thread হাজারটা বানালে machine ধীর হয়ে পড়ে।

MENTAL MODEL

Context switch = kernel mode-এ ঢুকে একজনের context সেভ, scheduler-এর বাছাই, দরকার হলে page table বদল, আরেকজনের context লোড, ফেরা। শুরু হয় দুইভাবে — thread নিজে block হলে (voluntary) বা timer তাকে নামালে (involuntary)। দাম দুই স্তরে: সরাসরি কয়েক µs, আর cache/TLB ঠান্ডা হওয়ার লুকানো দাম। তাই CPU-র কাজে core-এর চেয়ে বেশি thread মানে লোকসান।

CAN I EXPLAIN THIS?
  • একটা thread-এর context-এ কী কী থাকে, আর switch-এর সময় সেটা কোথায় রাখা হয়?
  • Switch-এর ধাপ গুলো কী কী? কোন ধাপটা শুধু দুই আলাদা process-এর মধ্যে switch-এ লাগে?
  • Voluntary আর involuntary switch-এর পার্থক্য কী? switches.js-এর তিনটা ফল (১৯৯/০, ৭/১৪, ৮/২৭৫) ব্যাখ্যা করো।
  • pingpong.js-এ ঘুমিয়ে পালা দেওয়া spin-এর চেয়ে ২০ গুণেরও বেশি দামি কেন? তবু সবসময় spin করা খারাপ কেন?
  • Context switch-এর লুকানো দাম কী? CPU-র কাজে core-এর চেয়ে বেশি thread দিলে কী হয়, আর এটাকে thrashing বলা ভুল কেন?
