PART 6 · STORAGE

Chapter 22 — File Systems

Disk চেনে শুধু নম্বর দেওয়া block; "file", "folder", "নাম" — এসব বানায় filesystem। Inode, directory, link, মুছে ফেলার আসল মানে, ছোট file-এর লুকানো দাম, আর crash-এর পরেও গোছানো থাকার কৌশল।

Chapter 20-এ দেখেছি SSD নিজেকে দেখায় 4 KB-র নম্বর দেওয়া block-এর একটা লম্বা সারি হিসেবে (LBA)। Device শুধু বোঝে "block ২০৬৬ পড়ো"। অথচ তুমি বলো fs.readFile('/home/reza/notes.md')। নাম, folder-এর ভেতরে folder, কে পড়তে পারবে, কবে বদলেছে, file কত বড় — এর কিছুই disk জানে না। এই সব হিসাব disk-এরই কিছু block-এ একটা নির্দিষ্ট নকশায় সাজিয়ে রাখার নিয়মের নাম filesystem। Chapter 21-এর স্তরে এটা VFS-এর ঠিক নিচে: "এই file-এর byte ০–১৪" কথাটাকে "disk-এর block অমুক"-এ অনুবাদ করে।

Inode: file-এর সব তথ্য, নাম ছাড়া

Linux-এর ext4 (আর বেশিরভাগ Unix filesystem) প্রতিটা file-এর জন্য একটা ছোট record রাখে — inode (index node)। প্রতিটা inode-এর একটা নম্বর আছে, আর তাতে থাকে: file-এর ধরন (সাধারণ file, folder, link), size, মালিক আর permission, সময়ের হিসাব, কয়টা নাম এটাকে দেখায় (link count), আর সবচেয়ে জরুরি — file-এর data disk-এর কোন কোন block-এ আছে তার মানচিত্র। যেটা নেই: file-এর নাম। সেটা কোথায়, একটু পরে।

ext4-এর ভেতরে সরাসরি উঁকি দেওয়া যায়। Docker-এ একটা ছোট ext4 disk image বানাব (একটা সাধারণ file, যার ভেতরে একটা পুরো filesystem), তারপর ext4-এর নিজস্ব debugger debugfs দিয়ে পড়ব — mount না করেই:

EXPERIMENT (Linux / Docker) — ext4-এর ভেতরে
docker run --rm -it debian:bookworm-slim bash

# দুইটা file: একটা ২৪ byte-এর note, একটা ৩ লাখ byte-এর "photo"
mkdir /tmp/src
printf "# notes\nhello from ext4\n" > /tmp/src/notes.md
head -c 300000 /dev/urandom > /tmp/src/photo.jpg

# 64 MB-র একটা ext4 image, 4 KB block, ভেতরে ওই দুইটা file
mkfs.ext4 -q -b 4096 -d /tmp/src /tmp/disk.img 64M

debugfs -R "stat /photo.jpg" /tmp/disk.img 2>/dev/null | grep -E "Inode:|Size:|Links|EXTENTS|^\("
debugfs -R "stat /notes.md"  /tmp/disk.img 2>/dev/null | grep -A1 EXTENTS
Inode: 13   Type: regular    Mode:  0644   Flags: 0x80000
User:     0   Group:     0   Project:     0   Size: 300000
Links: 1   Blockcount: 592
EXTENTS:
(0-73):2066-2139
EXTENTS:
(0):2065

photo.jpg হলো inode ১৩। Size ৩,০০,০০০ byte। আর মানচিত্রটা: (0-73):2066-2139 — file-এর block ০ থেকে ৭৩ disk-এর block ২০৬৬ থেকে ২১৩৯-এ, পরপর। ext4 প্রতিটা block আলাদা করে না লিখে এভাবে টানা অংশ লেখে: "শুরু এখানে, এতগুলো" — একে বলে extent। File যত টানা জায়গায় বসে, মানচিত্র তত ছোট, আর পড়াও sequential (Chapter 20-এর শিক্ষা)। আর notes.md: মাত্র ২৪ byte, কিন্তু সে পুরো একটা block (২০৬৫) দখল করেছে — block-ই সবচেয়ে ছোট একক। এই কথাটা একটু পরে বড় হয়ে ফিরবে।

তোমার Mac-এও inode নম্বর দেখা যায় (APFS-এর ভেতরের নকশা আলাদা, কিন্তু প্রতিটা file-এর একটা স্থায়ী নম্বর সেও দেয়): ls -li-এর প্রথম column, বা stat।

Directory: নাম থেকে inode number-এর তালিকা

নাম তাহলে কোথায়? Directory (folder) নিজেও একটা file, যার data হলো একটা তালিকা: "নাম → inode নম্বর"। একই image-এর root folder:

debugfs -R "ls -l /" /tmp/disk.img 2>/dev/null
      2   40755 (2)      0      0    4096 24-Sep-2026 14:01 .
      2   40755 (2)      0      0    4096 24-Sep-2026 14:01 ..
     11   40700 (2)      0      0   16384 24-Sep-2026 14:01 lost+found
     12  100644 (1)      0      0      24 24-Sep-2026 14:01 notes.md
     13  100644 (1)      0      0   300000 24-Sep-2026 14:01 photo.jpg

প্রথম column inode নম্বর, শেষ column নাম। Root folder নিজে inode ২ (. মানে "আমি নিজে", .. মানে "আমার parent" — root-এর parent সে নিজেই)। "photo.jpg" নামটা আছে root folder-এর data-য়, আর সেটা শুধু বলে "inode ১৩"।

তাহলে /home/reza/notes.md খুলতে kernel কী করে? এক ধাপ এক ধাপ করে হাঁটে — একে বলে path resolution: root-এর inode (সবসময় জানা, ২) → তার তালিকায় "home" খোঁজো → সেই inode → তার তালিকায় "reza" → সেই inode → তালিকায় "notes.md" → অবশেষে file-এর inode। প্রতিটা ধাপে permission দেখা হয়। Folder-এর বেলায় "x" permission-এর মানে "এর ভেতর দিয়ে হেঁটে যাওয়া যাবে" — এটা না থাকলে ভেতরের file নিজে সবার জন্য খোলা হলেও পৌঁছানো যায় না:

EXPERIMENT (Linux / Docker) — হাঁটার অনুমতি
docker run --rm --user 1000 node:22-bookworm-slim sh -c '
  cd /tmp && mkdir secret && echo "top secret" > secret/plan.txt
  chmod 644 secret/plan.txt; ls -l secret/plan.txt
  chmod u-x secret;          ls -ld secret
  cat secret/plan.txt
  chmod u+x secret;          cat secret/plan.txt'
-rw-r--r-- 1 node node 11 Sep 24 14:02 secret/plan.txt
drw------- 2 node node 4096 Sep 24 14:02 secret
cat: secret/plan.txt: Permission denied
top secret

--user 1000 দিয়েছি যাতে সাধারণ user হিসেবে চলে (root permission-এর বাধা মানে না)। plan.txt নিজে সবার পড়ার জন্য খোলা (rw-r--r--), তবু folder থেকে x সরাতেই Permission denied — kernel path-এ হাঁটতে গিয়ে secret-এর ধাপেই থেমে গেছে। x ফেরত দিতেই পড়া গেল।

/photo.jpg খোলার পুরো পথ, ওপরের debugfs-এর আসল সংখ্যা দিয়ে। নাম থাকে folder-এর তালিকায় (①), file-এর সব তথ্য থাকে inode-এ (②), আর inode-এর extent বলে data disk-এর কোথায় (③)। লম্বা path মানে ① ধাপটা প্রতিটা folder-এর জন্য আবার।

Hard link, symlink, আর মুছে ফেলা আসলে কী

নাম যেহেতু শুধু একটা তালিকার লাইন, একই inode-এর জন্য দুইটা লাইন থাকলে কী? কোনো সমস্যা নেই — এটাই hard link: একই file, দুইটা নাম। আর symbolic link (symlink) সম্পূর্ণ আলাদা জিনিস: নিজের inode-ওয়ালা একটা ছোট্ট file, যার ভেতরে শুধু আরেকটা path লেখা থাকে। Kernel symlink পেলে সেই path ধরে আবার হাঁটে।

EXPERIMENT — hard link আর symlink (macOS বা Linux)
echo "hello" > notes.md
ln notes.md hard.md          # hard link: একই inode-এ দ্বিতীয় নাম
ln -s notes.md soft.md       # symlink: "notes.md" লেখা একটা নতুন file
ls -li notes.md hard.md soft.md
rm notes.md
cat hard.md; cat soft.md
120356818 -rw-r--r--@ 2 mostofareza  wheel  6 Sep 24 20:00 hard.md
120356818 -rw-r--r--@ 2 mostofareza  wheel  6 Sep 24 20:00 notes.md
120356821 lrwxr-xr-x@ 1 mostofareza  wheel  8 Sep 24 20:00 soft.md -> notes.md
hello
cat: soft.md: No such file or directory

hard.md আর notes.md-এর inode নম্বর হুবহু এক (১২০৩৫৬৮১৮), আর তৃতীয় column-এর 2 হলো link count — দুইটা নাম এই inode-কে দেখায়। soft.md-এর inode আলাদা, size ৮ byte — "notes.md" লেখাটার দৈর্ঘ্য। তারপর rm notes.md: hard.md দিয়ে file দিব্যি পড়া গেল, কিন্তু symlink ভেঙে গেল, কারণ সে যে নাম ধরে হাঁটে সেটা আর নেই।

এর মানে rm file মোছে না — একটা নাম মোছে। System call-টার নামও তাই unlink। Kernel inode আর তার block গুলো আসলে তখনই ছাড়ে যখন দুইটা শর্তই পূরণ হয়: link count শূন্য, এবং কোনো process-এর কাছে file-টা আর খোলা নেই। দ্বিতীয় শর্তটা production-এর একটা ক্লাসিক ধাঁধার জন্ম দেয় — disk ভরা, অথচ কোনো বড় file খুঁজে পাওয়া যাচ্ছে না:

EXPERIMENT (Linux / Docker) — deleted.js
// deleted.js — file মুছে ফেলা হয়েছে, কিন্তু fd এখনো খোলা
const fs = require('fs');
const { execSync } = require('child_process');
const df = () => execSync("df -m / | tail -1 | awk '{print $3}'").toString().trim() + ' MB used';

console.log('start        :', df());
const fd = fs.openSync('big.log', 'w');
fs.writeSync(fd, Buffer.alloc(500 * 1024 * 1024, 1));   // 500 MB-র একটা "log"
fs.fsyncSync(fd);
console.log('after write  :', df());
fs.unlinkSync('big.log');                                // rm big.log
console.log('after unlink :', df(), '| file exists?', fs.existsSync('big.log'));
console.log(execSync(`ls -l /proc/${process.pid}/fd | grep deleted`).toString().trim());
fs.closeSync(fd);
console.log('after close  :', df());
docker run --rm -v "$PWD":/w:ro -w /root node:22-bookworm-slim node /w/deleted.js
start        : 22585 MB used
after write  : 23085 MB used
after unlink : 23085 MB used | file exists? false
l-wx------ 1 root root 64 Sep 24 14:01 18 -> /root/big.log (deleted)
after close  : 22585 MB used

File মুছে ফেলার পরেও disk-এর ৫০০ MB দখলে, কারণ fd 18 এখনো খোলা; /proc/<pid>/fd-এ সেটা (deleted) চিহ্ন নিয়ে দেখা যায়। fd বন্ধ করতেই জায়গা ফেরত। বাস্তবে এটা ঘটে যখন কেউ disk খালি করতে একটা চলমান server-এর বিশাল log file rm করে দেয় — server তখনো সেই fd-তে লিখছে, du (যে নাম ধরে ধরে গোনে) কিছু পায় না, df (যে filesystem-এর মোট হিসাব দেখে) বলে ভরা। সমাধান: process restart, বা file মোছার বদলে খালি করা (: > app.log, যেটা নাম রেখে size শূন্য করে)।

Hard link মানে একই inode-এ দ্বিতীয় নাম — তাই link count ২, আর একটা নাম মুছলেও অন্যটা দিয়ে file পাওয়া যায়। Symlink-এর নিজের inode, আর তার data একটা path; kernel সেই নাম ধরে আবার খোঁজে (dashed তীর) — নামটা মুছলে symlink ভেঙে যায়।

ছোট file-এর দাম: block আর inode

notes.md-এর ২৪ byte একটা পুরো 4 KB block নিয়েছিল। এক-দুইটা file-এ কিছু যায় আসে না, কিন্তু node_modules-এর কথা ভাবো — লাখখানেক ছোট file খুব সাধারণ ঘটনা:

EXPERIMENT (Linux / Docker) — smallfiles.js
// smallfiles.js — ১,০০,০০০টা ১০ byte-এর file
const fs = require('fs');
fs.mkdirSync('many', { recursive: true });
for (let i = 0; i < 100000; i++) fs.writeFileSync(`many/f${i}.txt`, '0123456789');
docker run --rm -v "$PWD":/w:ro -w /root node:22-bookworm-slim sh -c '
  df -i / | tail -1
  node /w/smallfiles.js
  df -i / | tail -1
  du -sh many; du -sh --apparent-size many
  stat -c "%s bytes, %b blocks of %B" many/f1.txt'
overlay        67108864 865607 66243257    2% /
overlay        67108864 965607 66143257    2% /
394M	many
3.8M	many
10 bytes, 8 blocks of 512

Data মোট ~১ MB (folder-এর নিজের তালিকা সহ ৩.৮ MB — --apparent-size মানে file-গুলোর আসল দৈর্ঘ্যের যোগফল), কিন্তু disk-এ খরচ ৩৯৪ MB — একশো গুণ। প্রতিটা ১০ byte-এর file ৮টা ৫১২-byte-এর একক, মানে 4 KB নিয়েছে। আর df -i-এর তৃতীয় column (ব্যবহৃত inode) ঠিক ১,০০,০০০ বেড়েছে। ext4 filesystem বানানোর সময়ই ঠিক করে ফেলে মোট কয়টা inode থাকবে (এখানে ৬.৭ কোটি); অসংখ্য ছোট file-এ inode আগে ফুরিয়ে যেতে পারে — তখন df -h বলে জায়গা আছে, অথচ নতুন file বানাতে গেলে No space left on device। একই script আমার Mac-এর APFS-এও du-তে ৩৯১ MB দেখিয়েছে। (কাজ শেষে rm -rf many।)

Crash-এর পরে: journaling

একটা নতুন file বানাতে filesystem-কে disk-এর কয়েকটা আলাদা জায়গায় লিখতে হয়: কোন inode খালি তার হিসাব, inode নিজে, folder-এর তালিকায় নতুন লাইন, কোন block খালি তার হিসাব, আর data block। এগুলো একসাথে হয় না — একটার পর একটা। মাঝখানে power গেলে? হয়তো inode "ব্যবহৃত" দাগানো হয়েছে কিন্তু কোনো folder-এ তার নাম নেই (জায়গা চিরতরে হারানো), বা নাম আছে কিন্তু inode-টা আবর্জনা। Filesystem-এর নিজের হিসাব অসঙ্গত হয়ে যায়। পুরনো সমাধান ছিল boot-এর সময় পুরো disk স্ক্যান করে গরমিল খোঁজা (fsck) — বড় disk-এ ঘণ্টার পর ঘণ্টা।

ext4-এর সমাধান journal: disk-এর একটা আলাদা জায়গা, একটা ডায়েরির মতো। কোনো পরিবর্তন আসল জায়গায় লেখার আগে filesystem পুরো পরিকল্পনাটা journal-এ লেখে, শেষে একটা "commit" দাগ দেয়, তারপর আসল জায়গাগুলোয় লেখে। Crash-এর পরে শুধু journal পড়লেই চলে: commit দাগ আছে এমন পরিকল্পনা আবার চালাও, দাগ নেই এমনগুলো ফেলে দাও। পুরো disk স্ক্যান লাগে না। আমাদের image-এও journal আছে:

dumpe2fs -h /tmp/disk.img 2>/dev/null | grep -E "features|Total journal size"
Filesystem features:      has_journal ext_attr resize_inode dir_index filetype extent 64bit flex_bg ...
Total journal size:       4096k

একটা জরুরি সীমা: ext4-এর default mode-এ journal শুধু filesystem-এর নিজের হিসাব (metadata — inode, folder, খালি-block-এর তালিকা) রক্ষা করে, তোমার file-এর ভেতরের data না। Crash-এর পরে filesystem গোছানো থাকবে, কিন্তু তোমার শেষ কয়েকটা write হারাতে পারে — তার জন্য Chapter 21-এর fsync আর temp file + rename এখনো লাগবে।

Mac-এর APFS অন্য পথ নেয়: copy-on-write — কোনো block কখনো জায়গায় বসে বদলায় না; বদলানো অংশ নতুন জায়গায় লেখা হয়, তারপর এক ধাপে পুরনোর বদলে নতুনটাকে দেখানো হয়। এর একটা মজার ফাউ হলো clone: file copy করার সময় data copy না করে দুইটা file-কে একই block দেখাও; পরে কেউ বদলালে শুধু বদলানো block-এর নতুন কপি হয়।

EXPERIMENT (macOS) — clone বনাম copy
# Chapter 20-এর 2 GB test.bin (বা যেকোনো বড় file)
df -m . | tail -1 | awk '{print $3}'
/usr/bin/time -p cp -c test.bin clone.bin    # -c = clone
df -m . | tail -1 | awk '{print $3}'
/usr/bin/time -p cp test.bin copy.bin
df -m . | tail -1 | awk '{print $3}'
rm clone.bin copy.bin

আমার output: শুরুতে ৩,৩৫,৪০৬ MB ব্যবহৃত; clone-এ real 0.00, ব্যবহৃত জায়গা এক MB-ও বাড়েনি; সাধারণ copy-তে real 0.72 (আরেকবার ১.৯৪), আর ব্যবহার বেড়েছে ঠিক ২,০৪৮ MB। (Node-এর fs.copyFileSync আমার Mac-এ clone করেনি — COPYFILE_FICLONE_FORCE দিলে ENOSYS দেয়।)

VFS: একই read(), অনেক রকম filesystem

Chapter 21-এর সবচেয়ে উপরের kernel স্তর ছিল VFS। এখন বোঝা যায় কেন লাগে: একটা Linux machine-এ একসাথে অনেক রকম filesystem চলে, আর কিছু কিছু কোনো disk-এই থাকে না:

docker run --rm debian:bookworm-slim sh -c '
  stat -f -c "%-10n %T" / /proc /dev/shm /sys
  ls -l /proc/uptime; cat /proc/uptime'
/          overlayfs
/proc      proc
/dev/shm   tmpfs
/sys       sysfs
-r--r--r-- 1 root root 0 Sep 24 14:02 /proc/uptime
84450.59 1010619.05

/proc/uptime-এর size শূন্য, অথচ পড়লে লেখা আসে। কারণ proc একটা নকল filesystem: কেউ read করলে kernel সেই মুহূর্তে উত্তর বানিয়ে দেয় (এখানে VM কত সেকেন্ড ধরে চলছে)। বইয়ে এতদিন যত /proc/<pid>/maps, /proc/meminfo পড়েছ — সব এভাবেই। tmpfs পুরোটাই RAM-এ থাকে; overlayfs কয়েকটা folder-কে স্তরে স্তরে জুড়ে একটা দেখায় — Docker image-এর স্তর এভাবেই কাজ করে (Chapter 36)।

VFS এদের সবার জন্য একটা সাধারণ চুক্তি ঠিক করে দেয় — open, read, write, lookup-এর মতো কাজের একটা তালিকা — আর প্রতিটা filesystem নিজের মতো করে সেগুলো বানায়। TypeScript-এর একটা interface আর তার কয়েকটা আলাদা class implementation-এর মতো: তোমার code শুধু interface চেনে, পেছনে ext4 না proc না tmpfs, জানার দরকার নেই।

COMMON MISCONCEPTION

"rm করলেই disk-এর জায়গা খালি।" rm শুধু folder-এর তালিকা থেকে একটা নাম সরায়। জায়গা ফেরত আসে যখন inode-এর আর কোনো নাম নেই এবং কোনো process সেটা খুলে রাখেনি — deleted.js-এ fd বন্ধ না হওয়া পর্যন্ত ৫০০ MB আটকে ছিল। Hard link থাকলেও একই কথা: শেষ নামটা না যাওয়া পর্যন্ত file বেঁচে থাকে।

MENTAL MODEL

Filesystem হলো block-এর সমুদ্রের উপর বসানো একটা database। Inode = একটা file-এর record (নাম ছাড়া সবকিছু, আর data কোথায় তার extent)। Directory = নাম → inode নম্বরের একটা তালিকা, আর path খোলা মানে এই তালিকা ধরে ধাপে ধাপে হাঁটা। নাম, inode আর block তিনটা আলাদা জিনিস বলেই hard link, "মুছেও জায়গা ফেরত না আসা", আর এক ধাপের rename সম্ভব। Journal (বা copy-on-write) নিশ্চিত করে যে crash-এর পরেও এই database-এর নিজের হিসাব ঠিক থাকে — তোমার data-র দায়িত্ব তবু তোমার।
