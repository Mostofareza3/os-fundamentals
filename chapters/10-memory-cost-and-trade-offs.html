PART 3 · MEMORY

Chapter 10 — Memory-র Cost আর Trade-off

Virtual memory বিনামূল্যে না। কোথায় কত দাম — TLB miss, page fault, swap, OOM kill — আর page-এর মাপ বদলে বা file map করে কীভাবে সেই দাম কমানো যায়।

Chapter 9-এর সারকথা: memory ভাগ হয় page-এ (macOS-এ ১৬ KB, বেশিরভাগ Linux-এ ৪ KB); প্রতিটা process-এর page table বলে কোন page কোন physical frame-এ; CPU-র MMU প্রতিটা access-এ অনুবাদ করে, সাম্প্রতিক অনুবাদ রাখে TLB-তে; আর frame না থাকা page ছুঁলে page fault — kernel frame বসিয়ে দেয়। এই প্রতিটা ধাপের একটা দাম আছে। এই chapter সেই দামের হিসাব।

Page-এর মাপ: ছোট বনাম বড়

Page ৪ KB কেন, ৪০ byte বা ৪০ MB কেন না? দুই দিকেই খরচ:

  • ছোট page — একই memory ঢাকতে বেশি page, মানে page table-এ বেশি entry (table নিজেই memory খায়), আর TLB-তে প্রতিটা entry কম জায়গা ঢাকে।
  • বড় page — ৫ KB data-র জন্য ২ MB-র page দিলে বাকিটা অকেজো পড়ে থাকে। Page-এর ভেতরের এই অপচয়কে বলে internal fragmentation (Chapter 6-এর heap-এর টুকরো টুকরো খালি জায়গা ছিল তার উল্টো — external fragmentation)। তার উপর permission আর lazy loading-এর সূক্ষ্মতাও কমে যায়।

৪ KB হলো কয়েক দশকের পুরনো একটা আপস; Apple Silicon ১৬ KB বেছেছে, কারণ আজকের RAM অনেক বড়। আর বড় memory-র কাজের জন্য প্রায় সব CPU আরও বড় page-ও সমর্থন করে — huge page (সাধারণত ২ MB, কোথাও ১ GB)। Linux-এ একটা feature আছে, Transparent Huge Pages (THP): বড় একটানা memory চাইলে kernel নিজে থেকেই সম্ভব হলে ২ MB-র page ব্যবহার করে। Chapter 9-এর lazy.js-এর Linux version-এ fault কম আসার রহস্য এটাই:

EXPERIMENT (Linux / Docker)
docker run --rm node:22-alpine sh -c 'cat /sys/kernel/mm/transparent_hugepage/enabled; node -e "
const f = () => process.resourceUsage().minorPageFault;
const f0 = f();
const buf = new Uint8Array(1024 * 2 ** 20);                 // ১ GB
for (let i = 0; i < buf.length; i += 4096) buf[i] = 1;     // প্রতি ৪ KB-তে ১ byte
const huge = require(\"fs\").readFileSync(\"/proc/self/smaps_rollup\", \"utf8\").match(/AnonHugePages:.*/)[0];
console.log(\"faults:\", f() - f0, \"|\", huge);"'

আমার output: প্রথম লাইন [always] madvise never (THP চালু), তারপর faults: 872 | AnonHugePages: 1050624 kB।

৪ KB page হলে ১ GB ছুঁতে ২,৬২,১৪৪টা fault লাগত; এসেছে মাত্র ৮৭২টা, আর AnonHugePages বলছে প্রায় পুরো ১ GB-ই ২ MB-র page-এ বসেছে (১ GB ÷ ২ MB = ৫১২; বাকিগুলো Node-এর নিজের কাজের — কিছু না ছুঁয়ে শুধু ১ GB চাইলেই ~১১০টা fault আসে)। প্রতিটা fault-এ kernel ৪ KB-র বদলে ২ MB-র frame বসিয়েছে।

TLB reach: অনুবাদের cache কত দূর ঢাকে

TLB ছোট — কয়েকশো থেকে কয়েক হাজার entry। প্রতিটা entry একটা page-এর অনুবাদ। তাই TLB মোট যতটা memory ঢাকতে পারে (TLB reach) = entry-র সংখ্যা × page-এর মাপ। ধরো ২০০০ entry: ৪ KB page-এ reach মাত্র ৮ MB, ১৬ KB-তে ৩২ MB, আর ২ MB-র huge page-এ ৪ GB। তোমার program যদি এর চেয়ে বেশি page জুড়ে ছড়ানো data ঘাঁটে, প্রায় প্রতিটা access-এ TLB miss — আর প্রতিটা miss মানে MMU-র page table-এর গাছ ধরে হাঁটা।

এটা মাপার কৌশল: data-র পরিমাণ একই রাখো আর এত ছোট রাখো যে পুরোটা cache-এ আঁটে (যাতে cache miss মাপে না ঢোকে), শুধু বদলাও কতগুলো আলাদা page-এ ছড়ানো।

EXPERIMENT — tlb.js
// একই পরিমাণ data (৪০৯৬টা cache line = 512 KB, পুরোটা L2-তে আঁটে),
// একবার ঘেঁষাঘেঁষি করে রাখা, একবার ৪০৯৬টা আলাদা page-এ ছড়ানো।
const PAGE = 16384, LINE = 128, N = 4096;          // Linux/x86-এ PAGE = 4096, LINE = 64 দাও
const a = new Int32Array((N * PAGE) / 4);          // 64 MB জায়গা, কিন্তু ব্যবহার হবে সামান্য

function build(spread) {
  // i-তম line কোথায়: ঘন হলে পরপর; ছড়ানো হলে প্রতিটা আলাদা page-এ
  const where = i => spread ? (i * PAGE + (i * LINE) % PAGE) / 4 : (i * LINE) / 4;
  const order = Array.from({ length: N }, (_, i) => i).sort(() => Math.random() - 0.5);
  for (let k = 0; k < N; k++) a[where(order[k])] = where(order[(k + 1) % N]);
  return where(order[0]);
}
function chase(start, steps) { let p = start; for (let i = 0; i < steps; i++) p = a[p]; return p; }

for (const [label, spread] of [['dense  (32 pages)  ', false], ['spread (4096 pages)', true]]) {
  const start = build(spread);
  chase(start, 1e6);
  const t = process.hrtime.bigint();
  chase(start, 2e7);
  console.log(label, (Number(process.hrtime.bigint() - t) / 2e7).toFixed(1), 'ns per access');
}

আমার Mac-এ: dense (32 pages) 6.5 ns, spread (4096 pages) 15.1 ns।

একই ৫১২ KB data, একই সংখ্যক access, দুই ক্ষেত্রেই পুরোটা L2 cache-এ বসে। তবু ছড়ানো version দ্বিগুণের বেশি ধীর — বাড়তি প্রতিটা nanosecond খরচ হয়েছে ঠিকানা অনুবাদ করতে। এজন্যই বিশাল memory নিয়ে কাজ করা software — PostgreSQL (huge_pages setting), JVM (-XX:+UseLargePages), বড় in-memory cache — প্রায়ই huge page চালু করে।

Page fault-এর দুই জাত: minor আর major

Chapter 9-এ যে fault দেখেছ, সেখানে kernel-কে disk ছুঁতে হয়নি — একটা খালি frame নিয়ে শূন্য দিয়ে ভরে বসিয়ে দিয়েছে। এর নাম minor page fault, দাম মোটামুটি এক microsecond-এর ঘরে (Chapter 9-এর Mac-এ ৬৫ হাজার fault সহ পুরো loop লেগেছিল ৬২ ms)। কিন্তু কখনো কখনো page-এর data শুধু disk-এ আছে — তখন kernel-কে disk থেকে পড়তে হয়, আর process ততক্ষণ ঘুমায়। এর নাম major page fault, দাম কয়েকশো microsecond থেকে কয়েক millisecond — minor-এর চেয়ে শত-হাজার গুণ।

Major fault-এর সবচেয়ে চেনা উৎস swap: RAM কম পড়লে kernel কম-ব্যবহৃত page গুলোর data disk-এর একটা বিশেষ জায়গায় (swap area) লিখে রাখে, frame ছেড়ে দেয়, আর page table entry-তে "present না" লিখে দেয়। সেই page আবার ছুঁলে major fault — disk থেকে ফিরিয়ে আনো। নিজে ঘটাও: container-কে ২০০ MB RAM দাও (swap সহ মোট ১ GB পর্যন্ত), আর ৬০০ MB ছোঁয়াও:

EXPERIMENT (Docker) — swap
docker run --rm --memory=200m --memory-swap=1g node:22-alpine node -e "
const ru = () => process.resourceUsage();
const buf = new Uint8Array(600 * 2 ** 20);          // 600 MB — container-এর RAM সীমা 200 MB
let t = performance.now();
for (let i = 0; i < buf.length; i += 4096) buf[i] = 1;
console.log('first touch :', (performance.now() - t).toFixed(0), 'ms | major faults so far:', ru().majorPageFault);
t = performance.now();
for (let i = 0; i < buf.length; i += 4096) buf[i] += 1;   // আবার পুরোটা ছোঁয়া
console.log('second pass :', (performance.now() - t).toFixed(0), 'ms | major faults so far:', ru().majorPageFault);"

আমার output:

first touch : 123 ms | major faults so far: 204
second pass : 1562 ms | major faults so far: 39228

প্রথমবার ছোঁয়ার সময় kernel শুধু নতুন frame দিচ্ছিল, আর RAM ফুরালে পুরনো page swap-এ ঠেলে দিচ্ছিল। দ্বিতীয়বার ঘুরতে গিয়ে প্রায় সব page-ই ততক্ষণে swap-এ — ৩৯ হাজার major fault, আর একই loop ১২ গুণের বেশি ধীর। এখন কল্পনা করো তোমার server-এর যে data সারাক্ষণ লাগে (তার working set) সেটাই RAM-এর চেয়ে বড়: system তখন আসল কাজের চেয়ে বেশি সময় কাটায় page disk-এ পাঠাতে আর ফিরিয়ে আনতে। এই অবস্থার নাম thrashing, আর তখন কোনো code optimization কাজে আসে না — হয় RAM বাড়াও, নয় working set ছোট করো।

একটা memory access-এর সম্ভাব্য পরিণতি, সস্তা থেকে দামি। বাঁয়ের দুই ধাপ hardware-এর ভেতরেই মেটে; মাঝখান থেকে kernel-কে ডাকতে হয়; major fault-এ disk পর্যন্ত যেতে হয়; আর শেষ ধাপে কোনো frame-ই দেওয়ার নেই।

Overcommit: প্রতিশ্রুতি বেশি, RAM কম

Chapter 9-এ দেখেছ Node-এর VmSize ৪২১ MB, অথচ VmRSS ৫০ MB — program-রা যা চায়, তার অল্পই আসলে ছোঁয়। Kernel যদি প্রতিটা চাওয়ার বিপরীতে তখনই আসল RAM আলাদা করে রাখত (বা চাওয়ার যোগফল RAM ছাড়ালেই "না" বলত), অনেক program চালুই হতো না, আর বেশিরভাগ RAM পড়ে থাকত সংরক্ষিত কিন্তু অব্যবহৃত।

তাই kernel ব্যাংকের মতো আচরণ করে: যত RAM আছে তার চেয়ে বেশি প্রতিশ্রুতি দেয়, এই ভরসায় যে সবাই একসাথে পুরোটা তুলতে আসবে না। এর নাম overcommit।

node -e "
const buf = new ArrayBuffer(64 * 2 ** 30);    // ৬৪ GB চাও
console.log('got', buf.byteLength / 2 ** 30, 'GB on a', require('os').totalmem() / 2 ** 30, 'GB machine; rss =', Math.round(process.memoryUsage().rss / 2 ** 20), 'MB');"

আমার Mac-এ: got 64 GB on a 24 GB machine; rss = 37 MB। ২৪ GB RAM-এর machine ৬৪ GB-র প্রতিশ্রুতি দিয়ে দিল, কারণ এখনো একটা byte-ও ছোঁয়া হয়নি। Linux-এ নিয়মটা বদলানো যায় /proc/sys/vm/overcommit_memory দিয়ে: 0 = অনুমান করে সিদ্ধান্ত (default), 1 = সবসময় হ্যাঁ, 2 = কড়া হিসাব। Docker Desktop-এর VM-এ এটা 1 — সেখানেও একই পরীক্ষায় ৬৪ GB পাওয়া যায়।

RAM সত্যিই ফুরালে: OOM killer

প্রতিশ্রুতির খেলায় একদিন সবাই টাকা তুলতে আসে। Process গুলো সত্যি সত্যি page ছুঁতে থাকে, RAM শেষ, swap-ও শেষ (বা নেই), অথচ একটা page fault মেটাতে একটা frame লাগবেই। Kernel তখন কী করবে? Fault মেটাতে না পারলে যে process fault করেছে সে এক পা-ও এগোতে পারবে না।

Linux-এর উত্তর নির্মম: OOM killer (out of memory)। Kernel প্রতিটা process-কে একটা নম্বর দেয় (মূলত কে কত memory দখল করে আছে), সবচেয়ে বড়টাকে বেছে নেয়, আর SIGKILL পাঠায় — এমন একটা signal যেটা process ধরতেও পারে না, আটকাতেও পারে না। Container-এ একই ঘটনা ঘটে container-এর নিজের memory সীমায় (Chapter 36-এ cgroup)।

EXPERIMENT (Docker) — OOM kill
docker run --name oomdemo --memory=100m --memory-swap=100m node:22-alpine node -e "
const chunks = [];
for (let i = 1; i <= 10; i++) {
  chunks.push(Buffer.alloc(50 * 2 ** 20, 1));   // 50 MB, সত্যি সত্যি লেখা
  console.log('holding', i * 50, 'MB');
}"
echo "exit code: $?"
docker inspect -f 'OOMKilled={{.State.OOMKilled}}' oomdemo
docker rm oomdemo

আমার output: holding 50 MB — তারপর কিছুই না — exit code: 137, OOMKilled=true (শেষ command container-টা মুছে দেয়)।

কোনো JS error নেই, কোনো stack trace নেই, process.on('exit')-ও চলেনি — process-টা স্রেফ হাওয়া। Exit code ১৩৭ মানে ১২৮ + ৯, আর ৯ হলো SIGKILL-এর নম্বর। Chapter 1-এ যে রহস্যের কথা বলেছিলাম — "container-এ app কোনো JS error ছাড়াই হঠাৎ মারা গেল" — এটাই তার চেহারা। Chapter 6-এর মৃত্যুর সাথে গুলিয়ো না: সেখানে V8 নিজের JS heap-এর সীমায় পৌঁছে নিজেই FATAL ERROR: ... JavaScript heap out of memory লিখে থেমেছিল। এখানে ব্যবহার করেছি Buffer, যার memory V8-এর JS heap-এর বাইরে — সীমাটা kernel-এর, মৃত্যুদণ্ডও kernel-এর। (macOS-এ Linux-এর মতো OOM killer নেই; সে আগে memory compress করে আর swap করে, শেষে "Your system has run out of application memory" dialog দেখায়।)

mmap: file-কে memory বানিয়ে ফেলা

Chapter 2-এর readFileSync-এর যাত্রা মনে করো: data disk থেকে page cache-এ আসে, তারপর kernel সেটা তোমার process-এর buffer-এ copy করে। ছোট file-এ ঠিক আছে। কিন্তু ৫০ GB-র একটা database file, যার এখানে-ওখানে একটু একটু পড়তে হবে? প্রতিবার read syscall আর copy — এবং একই data RAM-এ দুইবার (page cache-এ আর তোমার buffer-এ)।

Page fault-এর কৌশল এখানে আরেকবার কাজে লাগে। mmap syscall দিয়ে একটা file-কে সরাসরি address space-এর একটা range-এ map করা যায়। শুরুতে কিছুই পড়া হয় না। তুমি সেই range-এর কোনো address ছুঁলে page fault; kernel file-এর ঠিক সেই অংশ page cache-এ আনে, আর page cache-এর সেই frame-টাই তোমার page table-এ বসিয়ে দেয়। কোনো copy নেই, কোনো read নেই — file পড়া মানে memory পড়া। একাধিক process একই file map করলে সবাই একই frame দেখে।

তুমি প্রতিদিন এটা ব্যবহার করছ না জেনেই। Chapter 4-এর dynamic linker libc-কে ঠিক এভাবে load করে:

docker run --rm --cap-add SYS_PTRACE debian:bookworm-slim sh -c 'apt-get update -qq && apt-get install -y -qq strace >/dev/null 2>&1; strace -e trace=openat,mmap cat /dev/null 2>&1 | grep -A2 "libc.so.6\""'

আমার output (একটু ছেঁটে):

openat(AT_FDCWD, "/lib/aarch64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
mmap(NULL, 1826912, PROT_NONE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffff9d383000
mmap(0xffff9d390000, 1761376, PROT_READ|PROT_EXEC, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0) = 0xffff9d390000

libc খোলা হলো (fd 3), তারপর mmap-এর শেষ দুই argument 3, 0 মানে "fd 3-এর file, শুরু থেকে" — ১.৭ MB-র code অংশটা PROT_READ|PROT_EXEC (Chapter 5-এর r-x) permission নিয়ে address space-এ বসে গেল, একটা byte-ও copy না করে। SQLite, LMDB, Elasticsearch-এর মতো database আর search engine বড় file-এর জন্য একই কৌশল ব্যবহার করে। (Node-এ built-in mmap নেই; npm package আছে।)

MENTAL MODEL

Memory নিয়ে দুইটা প্রশ্ন করো। (১) আমার working set কি RAM-এ আঁটে? না আঁটলে major fault, thrashing, শেষে OOM kill — তখন code-এর কোনো কারসাজি বাঁচাবে না। (২) আমার data কতগুলো page জুড়ে ছড়ানো? ছড়ানো হলে cache আর TLB দুইটাই ভুগবে; ঘন রাখো, দরকারে huge page চালু করো। আর মনে রেখো: kernel যা প্রতিশ্রুতি দেয় (VSZ) আর যা আসলে দেয় (RSS) — দুইটা আলাদা সংখ্যা।

CAN I EXPLAIN THIS?
  • Page ছোট হলে কী দাম, বড় হলে কী দাম? Linux-এ ১ GB ছুঁয়ে লাখ লাখের বদলে মাত্র কয়েকশো fault এল কেন?
  • TLB reach কী? tlb.js-এ একই ৫১২ KB data ৪০৯৬টা page-এ ছড়ালে দ্বিগুণের বেশি ধীর কেন, যখন data পুরোটাই cache-এ?
  • Minor আর major page fault-এর পার্থক্য কী? Swap demo-তে দ্বিতীয়বার ঘোরা ১২ গুণ ধীর কেন? Thrashing কী?
  • Overcommit কী, kernel এটা কেন করে, আর এর শেষ পরিণতি কী হতে পারে?
  • Exit code ১৩৭ আর V8-এর "JavaScript heap out of memory" — দুই মৃত্যুর পার্থক্য কী? আর mmap কীভাবে read-এর copy বাঁচায়?
