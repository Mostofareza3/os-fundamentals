PART 3 · MEMORY

Chapter 10 — Memory-র Cost আর Trade-off

Virtual memory ফ্রি না — কোথায় কী দাম দিতে হয়, সেটার engineering হিসাব।

Page size-এর টানাটানি

Page 4KB কেন — 1 byte বা 1GB না কেন? দুই দিকেই খরচ আছে:

  • Page ছোট হলে → page table-এ entry বেশি → table-এর নিজেরই memory খরচ বাড়ে, TLB-তে কম range ধরে।
  • Page বড় হলে → internal fragmentation: 5KB data-র জন্য 2MB page দিলে বাকিটা অপচয়। (তুলনায়, heap allocator-এর free space টুকরা টুকরা হয়ে যাওয়াটা external fragmentation — Chapter 6-এ দেখেছিলে।)

4KB একটা historical sweet spot। Database/বড়-memory workload-এর জন্য Linux-এ "huge pages" (2MB) option-ও আছে — TLB-র উপর চাপ কমাতে।

কোন operation-এর কী দাম

ঘটনাCost-এর ধরন

Minor page faultKernel-এ যেতে হয়, কিন্তু disk লাগে না (যেমন প্রথমবার ছোঁয়া lazy page)। মাঝারি দাম।
Major page faultDisk থেকে page আনতে হয় (swap বা file)। দাম কয়েক মাত্রা (orders of magnitude) বেশি। এগুলো ঘনঘন হলে performance ধসে যায়।

Memory mapping: file-কে memory বানিয়ে ফেলা

Virtual memory-র আরেকটা elegant ব্যবহার — mmap। একটা file-কে process-এর address space-এ map করে দাও; এরপর file পড়া মানে স্রেফ memory পড়া। প্রথম access-এ page fault হবে, kernel disk থেকে page আনবে, তারপর থেকে direct। Database engine, dynamic linker (shared library load), বড় file processing — সবখানে এই কৌশল। এখানে দেখো কীভাবে concepts জোড়া লাগছে: page fault যেটা Chapter 9-এ "error handling" মনে হচ্ছিল, সেটাই এখানে একটা loading mechanism।

ENGINEERING INTUITION

Memory নিয়ে চিন্তা করার সময় দুইটা প্রশ্ন করো: (১) আমার working set (একই সময়ে দরকারি data) RAM-এ ধরে তো? না ধরলে major fault/swap শুরু হবে — তখন কোনো code optimization বাঁচাবে না। (২) আমার access pattern কি ঘেঁষাঘেঁষি (dense) নাকি ছড়ানো (sparse)? ছড়ানো হলে TLB আর cache দুটোই কাঁদবে।
