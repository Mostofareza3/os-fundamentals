Chapter 39 — Software ধীর হয় কেন

"Slow" কোনো রোগের নাম না, একটা উপসর্গ। এই chapter-এ রোগগুলো নিজেরাই ঘটাব, আর প্রতিটাকে ঠিক tool দিয়ে ধরব: প্রথমে time-এর তিনটা সংখ্যা, তারপর profiler আর strace, পুরো machine-এর জন্য vmstat আর USE method, আর Node-এর জন্য event loop delay।

ধীর program সামনে এলে প্রথম ইচ্ছা হয় code পড়ে অনুমান করা: "এই loop-টা মনে হয় ভারী", "DB query-টা নিশ্চয়ই"। অনুমান প্রায়ই ভুল জায়গায় নিয়ে যায়, কারণ সময় যেখানে যায় সেটা code পড়ে বোঝা যায় না। বোঝা যায় OS-এর হিসাব দেখে। Kernel প্রতিটা process-এর প্রতিটা millisecond-এর খাতা রাখে (Chapter 37-এর watch.js), আর সেই খাতা পড়াই রোগ নির্ণয়ের প্রথম ধাপ। নিয়ম একটাই: আগে মাপো, তারপর ভাবো, সবার শেষে বদলাও।

প্রথম প্রশ্ন: CPU-তে, নাকি অপেক্ষায়?

time command যেকোনো program-কে তিনটা সংখ্যা দেয়:

  • real — ঘড়ির সময়, শুরু থেকে শেষ। User এটাই টের পায়।
  • user — CPU user mode-এ এই process-এর code চালিয়েছে কতক্ষণ: তোমার JS, V8, library (Chapter 31)।
  • sys — CPU kernel mode-এ এই process-এর হয়ে কাজ করেছে কতক্ষণ: syscall, page fault।

তিনটা মিলিয়েই প্রথম রোগ নির্ণয়। যদি user + sys প্রায় real-এর সমান হয়, তাহলে পুরো সময়টা CPU ব্যস্ত ছিল এই program নিয়ে। আর real যদি অনেক বড় হয়, তাহলে বাকিটা সময় program CPU-তে ছিলই না, কিছুর অপেক্ষায় ঘুমিয়ে ছিল। তিনটা ইচ্ছাকৃত ধীর program দিয়ে দেখা যাক:

// sick.js — তিনটা ধীর program; কোনটার রোগ কী, time বলে দেবে
const fs = require('fs');
const mode = process.argv[2];
if (mode === 'cpu') {                          // হিসাবের কাজ: প্রতিবার পুরো list-এর deep copy
  const users = Array.from({ length: 2e4 }, (_, i) => ({ id: i, name: `user${i}`, tags: ['a', 'b'] }));
  const clone = x => JSON.parse(JSON.stringify(x));
  for (let i = 0; i < 150; i++) clone(users);
}
if (mode === 'syscalls') {                     // log লেখা, প্রতিবার এক byte, সরাসরি file-এ (Chapter 32)
  const fd = fs.openSync('/tmp/app.log', 'w');
  for (let i = 0; i < 1e6; i++) fs.writeSync(fd, 'x');
}
if (mode === 'wait') {                         // প্রতিটা order লিখে disk পর্যন্ত নিশ্চিত হওয়া (Chapter 21)
  const fd = fs.openSync('/tmp/orders.log', 'w');
  for (let i = 0; i < 2000; i++) { fs.writeSync(fd, `order ${i}\n`); fs.fsyncSync(fd); }
}
# triad.sh — তিন রোগ, প্রতিটার time
for mode in cpu syscalls wait; do
  echo "--- $mode"
  { time node sick.js $mode; } 2>&1 | grep -E 'real|user|sys'
done

তিনটা আলাদা ছবি। cpu-তে user প্রায় পুরো real: সময়টা গেছে আমাদের নিজের code-এ। (user + sys এখানে real-এর চেয়ে সামান্য বেশি, কারণ garbage collector-এর thread পাশাপাশি অন্য core-এ চলেছে; সব thread-এর CPU time যোগ হয়।) syscalls-এ sys প্রায় অর্ধেক। একটা সুস্থ program-এ sys সাধারণত কয়েক শতাংশ, তাই এত বড় sys মানে kernel-কে দিয়ে অনেক কাজ করানো হচ্ছে। wait-এ user আর sys মিলিয়ে ৩১ ms, অথচ real ৫৮৬ ms। বাকি ৯৫% সময় program CPU-তে ছিলই না, disk-এর উত্তরের অপেক্ষায় ঘুমিয়ে ছিল।

অপেক্ষা মানে সবসময় disk বা network না। CPU-র জন্যও অপেক্ষা হয়। প্রথম program-টাই আবার চালাই, এবার container-কে আধখানা CPU দিয়ে (Chapter 36):

docker run --rm --cpus 0.5 -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash -c '{ time node sick.js cpu; } 2>&1 | grep -E "real|user|sys"'
real	0m1.893s
user	0m0.914s

কাজ একই, user একই (০.৯ s), কিন্তু real দ্বিগুণ। বাকি ০.৯৫ s program runnable ছিল, মানে চলতে তৈরি, কিন্তু CPU পায়নি: cgroup-এর কোটা শেষ হয়ে গিয়েছিল। ভিড় করা machine-এ, অন্য process-এর সাথে কাড়াকাড়িতেও (Chapter 17) বা cloud-এ অন্য VM-এর কারণে (steal, Chapter 35) একই ছবি আসে। তাই "real ≫ user + sys" মানে "অপেক্ষা", কিন্তু কিসের অপেক্ষা, সেটা পরের প্রশ্ন।

চার চালানোর real, user আর sys। প্রতিটা দণ্ডের পুরো দৈর্ঘ্য real। নীল আর amber অংশে CPU এই program-এর কাজ করছিল। Dashed অংশে program CPU-তে ছিলই না: disk-এর জন্য, বা CPU-র কোটার জন্য অপেক্ষা।

প্রতিটা উত্তরের পরের প্রশ্ন

time বলে দেয় কোন দিকে খুঁজতে হবে। প্রতিটা দিকের জন্য আলাদা tool:

user বেশি: কোন function? CPU কোন function-এ সময় কাটাচ্ছে, সেটা বলে profiler। Node-এর নিজের একটা আছে: --cpu-prof চালু থাকলে প্রতি ~১ ms-এ V8 দেখে নেয় এই মুহূর্তে কোন function চলছে, আর শেষে একটা .cpuprofile file লেখে। File-টা Chrome DevTools-এর Performance tab-এ খোলা যায়। এখানে ছোট একটা script দিয়ে গুনে নিচ্ছি:

// top.js — node --cpu-prof-এর file থেকে: কোন function নিজে কত % CPU নিল
const prof = JSON.parse(require('fs').readFileSync(process.argv[2]));
const nodes = new Map(prof.nodes.map(n => [n.id, n.callFrame]));
const count = new Map();
for (const id of prof.samples) {                       // প্রতি ~১ ms-এ একটা নমুনা: CPU তখন কোন function-এ
  const f = nodes.get(id);
  const name = `${f.functionName || '(anonymous)'} ${f.url ? f.url.split('/').pop() + ':' + (f.lineNumber + 1) : ''}`;
  count.set(name, (count.get(name) || 0) + 1);
}
for (const [name, n] of [...count].sort((a, b) => b[1] - a[1]).slice(0, 5))
  console.log(`${(100 * n / prof.samples.length).toFixed(1).padStart(5)}%  ${name}`);

sys বেশি: কোন syscall, কতবার? এর উত্তর দেয় strace -c (Chapter 1, 32)। অপেক্ষা: কিসে আটকে আছে? এর উত্তর strace -c -w। -w মানে প্রতিটা syscall-এর ভেতরে ঘড়ির যে সময় কেটেছে তার হিসাব, ঘুমানো সময়সহ। -f দিইনি, তাই শুধু main thread গোনা হচ্ছে; নইলে V8-এর ঘুমন্ত helper thread-দের futex পুরো হিসাব দখল করত। দুটো একসাথে:

একটা ধীর program-এর সামনে প্রশ্নের ক্রম। প্রথমে সময়টা কোন ঘরে গেছে, তারপর সেই ঘরের tool দিয়ে আসল জায়গাটা খোঁজা। কোনো ধাপেই অনুমান লাগে না।

পুরো machine: USE method আর vmstat

time আর strace একটা process দেখে। কিন্তু কখনো সমস্যা process-এ না, machine-এ: CPU-র জন্য লাইন, memory ফুরিয়ে যাওয়া, disk-এর জট। এর জন্য Brendan Gregg-এর একটা সহজ checklist আছে, USE method। Machine-এর প্রতিটা resource-কে (CPU, memory, disk, network) তিনটা প্রশ্ন:

  • Utilization — resource-টা কতটা সময় ব্যস্ত ছিল?
  • Saturation — এর জন্য কাজ কি লাইনে দাঁড়িয়ে আছে? কত লম্বা লাইন?
  • Errors — কিছু কি ব্যর্থ হচ্ছে?

শুধু utilization দেখলে ভুল হয়। ১০০% ব্যস্ত CPU ঠিক আছে, যদি কেউ লাইনে না দাঁড়ায়; সমস্যা শুরু হয় লাইন থেকে। "Memory ৯০% used" প্রায়ই কোনো সমস্যাই না, কারণ তার বড় অংশ page cache (Chapter 23)। আসল বিপদ হলো swap-এ page যাওয়া-আসা, মানে saturation। তাই প্রথম প্রশ্নটা সবসময় saturation নিয়ে।

Linux-এ তিনটার প্রাথমিক উত্তর একটা command-এ: vmstat 1, প্রতি সেকেন্ডে পুরো machine-এর এক লাইন। নিচের script vmstat চালু রেখে তিনটা ঝামেলা ঘটায়, প্রতিটা ৩ সেকেন্ড করে। প্রথমটা ১২টা CPU-র জন্য ২৪টা busy loop। দ্বিতীয়টা দুই thread-এর মধ্যে একটা বল চালাচালি, যেখানে প্রতিবার ঘুম আর জাগা (Chapter 17-এর pingpong)। তৃতীয়টা ২০০ MB-র সীমার container-এ ৩০০ MB-র ওপর বারবার ঘোরা (Chapter 10-এর swap):

// storm.js — দুই thread একটা বল চালাচালি করে, প্রতিবার kernel-এ ঘুমিয়ে আর জেগে (Chapter 17)
const { Worker, isMainThread, workerData } = require('worker_threads');
if (isMainThread) {
  const s = new Int32Array(new SharedArrayBuffer(4));
  new Worker(__filename, { workerData: s });
  const end = Date.now() + 3000;
  let n = 0;
  while (Date.now() < end) { Atomics.store(s, 0, 1); Atomics.notify(s, 0); Atomics.wait(s, 0, 1); n++; }
  console.error(`storm: ${n} round trips in 3 s`);
  process.exit();
} else {
  const s = workerData;
  for (;;) { Atomics.wait(s, 0, 0); Atomics.store(s, 0, 0); Atomics.notify(s, 0); }
}
// swap.js — 300 MB-এর working set: প্রতিটা page বারবার ছোঁয়া, ৩ সেকেন্ড ধরে (Chapter 10)
const b = Buffer.alloc(300 * 2 ** 20);
const end = Date.now() + 3000;
let passes = 0;
while (Date.now() < end) { for (let i = 0; i < b.length; i += 4096) b[i]++; passes++; }
console.error(`swap: ${passes} passes over 300 MB in 3 s`);

এবার তিন ঝামেলা, তিন রকম সংকেত:

  • CPU (লাইন ৩–৫) — us ১০০, id ০: utilization পুরো। কিন্তু আসল খবর r = ২৪: CPU ১২টা, চাইছে ২৪ জন। অর্ধেক সবসময় লাইনে, প্রত্যেকে অর্ধেক গতিতে। এটাই saturation। r যদি CPU-র সংখ্যার চেয়ে বেশি থাকে লম্বা সময় ধরে, তাহলে latency বাড়বে, CPU যতই "মাত্র ১০০%" দেখাক।
  • Context switch (লাইন ৭–৮) — CPU প্রায় অলস (id ৯৭), অথচ cs সেকেন্ডে ১,৬৪,০০০, আর in ৮৩,০০০: অন্য core-এর ঘুমন্ত thread-কে জাগাতে interrupt পাঠাতে হয়। দুই thread তিন সেকেন্ডে ১,২০,০০০ বার বল চালাচালি করেছে, প্রতিবার গড়ে ২৫ µs, যার প্রায় পুরোটা ঘুম আর জাগার খরচ (Chapter 17)। Production-এ হঠাৎ cs লাফিয়ে উঠলে সন্দেহ করো: lock নিয়ে কাড়াকাড়ি, বা core-এর চেয়ে অনেক বেশি thread।
  • Memory (লাইন ৯–১২) — si আর so প্রতি সেকেন্ডে প্রায় ৪ লাখ ৯০ হাজার KB করে, মানে প্রায় আধা GB, swpd প্রায় ৩১০ MB পর্যন্ত, b ১, wa ৪। প্রতিটা ছোঁয়া page আগে swap থেকে আনতে হয়, আর আনতে গিয়ে অন্যটা বের করে দিতে হয়। ফল দেখো শেষ লাইনে: তিন সেকেন্ডে ৩০০ MB-র ওপর মাত্র ৬ বার ঘোরা গেছে। একই swap.js সীমা ছাড়া চালালে (docker run --rm -v "$PWD":/w:ro -w /w node:22-alpine node swap.js) আমার এখানে ৪১২০ বার। প্রায় সাতশো গুণ ধীর। অথচ CPU ৯৩% অলস।

শেষ উদাহরণটা মনে রাখো: machine "অলস" দেখাচ্ছে, অথচ program প্রায় থেমে আছে। শুধু CPU% দেখলে এই রোগ কোনোদিন ধরা পড়ত না। পুরো checklist, এই বইয়ের tool দিয়ে:

Node-এর নিজস্ব resource: event loop

শেষ সারিটা Node-এর জন্য আলাদা করে। Event loop একটাই thread (Chapter 29)। সে কোনো sync কাজে ১ ms আটকে থাকলে, সেই ১ ms-এ আসা প্রতিটা request অপেক্ষা করে। Machine-এর হিসাবে এটা কোথাও saturation হিসেবে দেখা যায় না: ১২ core-এর machine-এ একটা thread পুরো ব্যস্ত মানে machine-এর CPU মাত্র ৮%। তাই Node নিজেই এই saturation মাপার ব্যবস্থা রাখে: monitorEventLoopDelay। একটা timer বারবার বসিয়ে দেখে, সেটা সময়মতো ফুটল কি না; দেরির পরিমাণই event loop-এর লাইনে কাজ আটকে থাকার মাপ।

একটা চেনা ঘটনা দিয়ে দেখি। একটা server-এর /login password hash করে, যেটা ইচ্ছে করেই ধীর একটা কাজ (এখানে ~৫০ ms), আর /ping সাথে সাথে উত্তর দেয়। একবার hash হবে main thread-এ, pbkdf2Sync দিয়ে; আরেকবার libuv-এর thread pool-এ (Chapter 19):

// app.js — দুটো endpoint: /ping সাথে সাথে উত্তর দেয়; /login password hash করে (~৫০ ms CPU)
const http = require('http'), crypto = require('crypto');
const { monitorEventLoopDelay } = require('perf_hooks');
const lag = monitorEventLoopDelay({ resolution: 1 });    // event loop কতটা দেরিতে ঘুরছে, ms-এর ঘরে মাপা
lag.enable();
const hash = (pw, done) => process.env.SYNC
  ? done(crypto.pbkdf2Sync(pw, 'salt', 5e5, 32, 'sha256'))              // main thread-এই
  : crypto.pbkdf2(pw, 'salt', 5e5, 32, 'sha256', (err, key) => done(key)); // libuv-এর thread pool-এ (Chapter 19)
http.createServer((req, res) => {
  if (req.url === '/login') hash('secret', key => res.end(key.toString('hex')));
  else res.end('pong');
}).listen(3000, '127.0.0.1');
process.on('SIGTERM', () => {
  const ms = ns => (ns / 1e6).toFixed(1);
  console.log(`event loop delay: p50 ${ms(lag.percentile(50))} ms, p99 ${ms(lag.percentile(99))} ms, max ${ms(lag.max)} ms`);
  process.exit();
});
// load.js — ৩ সেকেন্ড ধরে: প্রতি ১০ ms-এ একটা /ping, প্রতি ১০০ ms-এ একটা /login; /ping-এর latency মাপা
const http = require('http');
const pings = [];
const get = (path, done) => {
  const t = performance.now();
  http.get(`http://127.0.0.1:3000${path}`, r => r.resume().on('end', () => done && done(performance.now() - t)));
};
const a = setInterval(() => get('/ping', ms => pings.push(ms)), 10);
const b = setInterval(() => get('/login'), 100);
setTimeout(() => {
  clearInterval(a); clearInterval(b);
  pings.sort((x, y) => x - y);
  const p = q => pings[Math.floor(q * (pings.length - 1))].toFixed(1);
  console.log(`/ping: ${pings.length} requests, p50 ${p(0.5)} ms, p99 ${p(0.99)} ms, max ${p(1)} ms`);
}, 3000);
# lag.sh — একই load, দুইবার: hash main thread-এ (SYNC=1), আর thread pool-এ
for sync in 1 ""; do
  echo "--- SYNC=${sync:-no}"
  SYNC=$sync node app.js & sleep 0.5
  node load.js; sleep 0.2
  kill $!; wait
done

লক্ষ্য করো, server-এর ভেতরের event loop delay-এর P99 (৫৪.৬ ms) বাইরে থেকে মাপা ping-এর P99-এর (৫৬ ms) প্রায় সমান। তাই load test ছাড়াই, production-এ চলন্ত server থেকেই এই saturation মাপা যায়: event loop delay-এর P99 একটা metric হিসেবে পাঠাও। (অলস অবস্থাতেও P50 ২ ms আসে, কারণ এই মাপে ১ ms-এর timer-এর নিজের ঘোরাটাও ধরা হয়। তুলনা করো পার্থক্যটা।)

COMMON MISCONCEPTION

"CPU মাত্র ১০%, তাই সমস্যা CPU-তে না।" machine-এর CPU% পুরো machine-এর গড়। lag.sh-এর Node server-এর event loop hash চলার সময় পুরো ব্যস্ত, কিন্তু ১২ core-এর machine-এ সেটা ৮%-এর বেশি দেখাবে না। swap.js-এর সময় machine ৯৩% অলস, অথচ program সাতশো গুণ ধীর। আবার উল্টোটাও সত্যি: ১০০% CPU নিজে কোনো সমস্যা না, যদি কেউ লাইনে না দাঁড়ায়। Utilization-এর সংখ্যা একা কিছু বলে না। জিজ্ঞেস করো কে অপেক্ষা করছে, কিসের জন্য, আর কত লম্বা লাইনে।

MENTAL MODEL

ধীর মানে সময় কোথাও যাচ্ছে, আর kernel সেই সময়ের হিসাব রাখে। প্রথমে time: real = user + sys + অপেক্ষা। user বেশি হলে profiler (--cpu-prof) বলে কোন function। sys বেশি হলে strace -c বলে কোন syscall, কতবার। অপেক্ষা বেশি হলে খুঁজতে হয় কিসের অপেক্ষা: CPU-র লাইন (vmstat r, throttling), disk (strace -c -w, wa), memory (si/so), নাকি আটকে থাকা event loop (event loop delay)। পুরো machine-এর জন্য প্রতিটা resource-কে USE-এর তিন প্রশ্ন, আর সবচেয়ে গুরুত্ব দাও saturation-কে: লাইন যেখানে, latency সেখানে। অনুমান দিয়ে শুরু কোরো না; সংখ্যা যেখানে নিয়ে যায়, code সেখানে খোলো।
