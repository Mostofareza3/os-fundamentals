PART 11 · PUTTING EVERYTHING TOGETHER

Chapter 37 — একটা Program চালালে কী কী ঘটে?

Shell-এ node hello.js লিখে Enter। এক লাইনের program, অথচ এর পেছনে দুটো process, আটটা task, প্রায় ৭০০টা system call আর আড়াই হাজার page fault। পুরো বইটা এই এক trace-এ, সময় ধরে ধরে।

এতদিন একেকটা জিনিস আলাদা করে দেখেছি: fork আর wait (Chapter 15), virtual memory আর page fault (Chapter 9), thread (Chapter 16), file (Chapter 21), epoll (Chapter 29), kernel-এর দরজা (Chapter 31), loader (Chapter 34), cgroup (Chapter 36)। কিন্তু একটা program চালালে এরা সবাই কাজ করে, একটার পর একটা, কয়েক millisecond-এর মধ্যে। এই chapter-এ নতুন কোনো ধারণা নেই, আছে জোড়া দেওয়া। দুটো প্রশ্ন আলাদা রাখব। কী ঘটে, সেটা বলবে strace (Chapter 1): প্রতিটা system call, কোন task-এর, কখন। কতক্ষণ লাগে, সেটা মাপব strace ছাড়া, কারণ strace প্রতিটা syscall-এ program থামিয়ে দেখে, আর তাতে সবকিছু কয়েক গুণ ধীর হয়ে যায়।

পুরো trace, এক file-এ

Program-টা যত ছোট হতে পারে, hello.js নামে, এক লাইনের (২২ byte):

console.log('hello');

আর trace করার script। bash -c দিয়ে চালাচ্ছি, যাতে terminal-এর মতোই একটা shell node-কে চালায়। শেষে ; echo রেখেছি Chapter 15-এর মতো একই কারণে: node শেষ command হলে bash fork না করে নিজেই node হয়ে যেত। -f মানে child process আর thread-দেরও ধরো, -ttt মানে প্রতিটা লাইনে সময়। awk সেই সময়কে বদলে দেয় "shell-এর fork-এর পর কত ms"-এ:

# timeline.sh — shell থেকে node hello.js, পুরোটা strace-এ; সময় ms-এ, shell-এর fork-এর মুহূর্ত = 0
strace -f -ttt -o trace.txt bash -c 'node hello.js; echo "exit=$?"'
awk 'NR == FNR { if (!t0 && /clone\(/) t0 = $2; next }
     { printf "%-3s %7.2f  %s\n", $1, ($2 - t0) * 1000, substr($0, index($0, $3)) }' trace.txt trace.txt > timeline.txt
echo "$(wc -l < timeline.txt) lines, $(cut -d' ' -f1 timeline.txt | sort -u | wc -l) tasks"
docker run --rm --cap-add SYS_PTRACE -v "$PWD":/w -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq strace >/dev/null 2>&1
  bash timeline.sh'
hello
exit=0
970 lines, 8 tasks

timeline.txt তোমার folder-এই তৈরি হয়েছে, কারণ container-এর /w আসলে তোমার $PWD। তাই এই chapter-এর বাকি grep-গুলো Mac-এর terminal-এই চালাতে পারো। প্রতিটা লাইনে তিনটা জিনিস: task-এর নম্বর (Linux-এর চোখে process আর thread দুটোই task, Chapter 16), fork থেকে কত ms, আর syscall। Negative সময় মানে fork-এর আগের অংশ: bash নিজে চালু হচ্ছে। ৯৭০ লাইনে ৮৪৮টা system call, তার ৬৯৬টা node-এর। আটটা task হলো bash, node, আর node-এর ছয়টা বাড়তি thread।

strace-এর নিচে পুরো কাজে লেগেছে ৭৪ ms। আসল সময় মাপতে strace বাদ দিয়ে দুটো ঘড়ি মেলাব। একটা shell-এর ঘড়ি, fork-এর ঠিক আগে। অন্যটা node-এর নিজের: performance.timeOrigin (node-এর ঘড়ি চালু হওয়ার মুহূর্ত) আর performance.nodeTiming (Chapter 34):

// clock.js — hello.js-ই, সাথে ঘড়ি: shell-এর fork-এর মুহূর্ত (T0) থেকে কখন কোন ধাপ, ms-এ
const code = performance.now();               // node-এর ঘড়ি: process-এর জন্ম থেকে ms
console.log('hello');
const logged = performance.now();
process.on('exit', () => {
  const born = performance.timeOrigin - process.env.T0 / 1000;   // fork থেকে node-এর ঘড়ি চালু হওয়া
  const t = performance.nodeTiming;
  const rows = [['node clock starts', 0], ['V8 ready', t.v8Start], ['Node env ready', t.environment],
                ['bootstrap done', t.bootstrapComplete], ['your first line', code],
                ['hello written', logged], ['exit event', performance.now()]];
  for (const [what, ms] of rows) console.error(`${what.padEnd(18)} ${(born + ms).toFixed(1).padStart(5)} ms`);
});
# when.sh — strace ছাড়া: shell-এর fork-এর মুহূর্ত = 0, তারপর কোন ধাপ কখন
node clock.js > /dev/null 2>&1                # warm-up: প্রথমবারের বাড়তি খরচ বাদ দিতে
t0=${EPOCHREALTIME/./}                        # bash-এর নিজের ঘড়ি, µs-এ (নতুন process লাগে না)
T0=$t0 node clock.js > /dev/null
t1=${EPOCHREALTIME/./}
awk -v d=$((t1 - t0)) 'BEGIN { printf "back in the shell  %5.1f ms\n", d / 1000 }'
docker run --rm -v "$PWD":/w:ro -w /w node:22-bookworm-slim bash when.sh

$EPOCHREALTIME bash-এর নিজের variable। এটা পড়তে নতুন process লাগে না, তাই মাপে কিছু যোগ হয় না। T0 environment variable দিয়ে fork-এর মুহূর্তটা node-কে জানিয়ে দিয়েছি; সেটা আর node-এর ঘড়ি চালু হওয়ার পার্থক্যই fork থেকে node জন্মানো পর্যন্ত সময়। strace-এর নিচে যা ৭৪ ms, আসলে তা ১৩ ms: strace কাজটা প্রায় ছয় গুণ ধীর করেছিল। তাই strace-এর সময় থেকে শুধু ক্রমটা নাও (কোনটা আগে, কোনটা পরে), আর সময়টা মাপো আলাদাভাবে। কয়েকবার চালালে সংখ্যা ১–২ ms এদিক-ওদিক হয়।

when.sh-এর মাপ, strace ছাড়া। নীল অংশে node-এর নিজের কাজ। Amber অংশে kernel process বানায় (১) আর ভাঙে (৭)। পুরো সময়টা bash ঘুমিয়ে থাকে wait4-এ। তোমার লেখা লাইন (৫ আর ৬) ১৩ ms-এর মধ্যে ২ ms-এরও কম।

ছবির সবচেয়ে বড় কথা: তোমার লেখা এক লাইন চলেছে ২ ms-এরও কম সময়। বাকি ১১ ms গেছে process-এর জন্ম আর বিদায়ে। এবার trace ধরে ধাপগুলো একে একে দেখা যাক।

fork-এর আগে bash node খুঁজছে। PATH-এর প্রথম folder /usr/local/sbin-এ নেই (ENOENT), দ্বিতীয়টায় আছে। Chapter 34-এ env ঠিক এই কাজটাই করত, এখানে shell নিজে করছে। তারপর ০ ms-এ clone। Flag-এ SIGCHLD আছে, CLONE_VM নেই, অর্থাৎ এটা fork: নতুন একটা process, bash-এর copy, copy-on-write-এর কারণে প্রায় বিনা খরচে (Chapter 15, 9)।

Parent bash (task ১২৭) সঙ্গে সঙ্গে wait4-এ ঢোকে আর Blocked হয়ে যায়। তার পরের লাইন আসবে ৭৩ ms-এ, যখন child শেষ হবে। Child (১২৮) তখনো bash। ০.৮৪ ms-এ execve দিয়ে সে node হয়ে যায়: kernel পুরনো address space ফেলে দিয়ে node-এর ELF map করে, আর চালায় ld.so-কে (Chapter 34)। ld.so ১ থেকে ৫ ms-এর মধ্যে node-এর ছয়টা library খুঁজে map করে (awk '$2 > 0 && /openat.*\.so/' timeline.txt দিয়ে দেখতে পারো)। Relocation সেরে ৮.৬ ms-এ node-এর main শুরু হয়।

main-এর প্রথম কাজগুলো সাবধানতার। capget দিয়ে দেখে তার কী কী capability আছে (Chapter 31)। fstat দিয়ে দেখে fd ০, ১, ২ খোলা আছে কি না। তারপর প্রতিটা signal-এর handler একবার করে পরীক্ষা করে: parent কোনোটা ignore করিয়ে রেখে গেলে সেটাকে default-এ ফেরায়। আর দুটো signal নিজে ইচ্ছে করে ignore করে, যার একটা SIGPIPE (নিচের grep-এর প্রথম লাইন)। Chapter 31-এর table-এ বলেছিলাম Node শুরুতেই এটা করে; এই সেই প্রমাণ। ফলে যে socket-এর ওপাশ বন্ধ, তাতে লিখলে process মরে না, শুধু EPIPE error আসে (Chapter 30)।

(শেষ লাইনটা বিদায়ের সময়ের, সেটা পরে।) Chapter 29-এর event loop এখানে জন্মায়: epoll_create1। Main thread দুটো epoll বানায়, fd ৩ আর ১৩। তোমার JS-এর event loop ১৩ নম্বরটা; কীভাবে চিনলাম, পরের অংশে দেখবে। প্রতিটার পরপরই io_uring_setup: libuv io_uring চালু করার চেষ্টা করে (Chapter 24)। Docker-এর seccomp নিয়ম সেটা আটকায় (EPERM, Chapter 36), আর libuv চুপচাপ epoll দিয়েই কাজ চালায়। তোমাকে কোনো error দেখায় না।

তারপর ছয়টা clone, এবার flag-এ CLONE_VM|CLONE_THREAD। মানে নতুন process না, একই address space-এ নতুন thread (Chapter 16)। কে কী:

  • ১২৯ — সবার আগে তৈরি, আর নিজের একটা epoll বানায় (fd ৯)। এর নাম DelayedTaskScheduler: V8-এর "এই কাজটা একটু পরে করো" ধরনের কাজের সময় রাখে।
  • ১৩০–১৩৩ — V8-এর চারটা worker thread। Garbage collection-এর অনেকটা (Chapter 6) আর JIT compile (Chapter 4) এরা পেছনে চালায়, যাতে main thread না আটকায়।
  • ১৩৪ — সবার শেষে, ৫২ ms-এ। এই thread সারাজীবন একটা SIGUSR1-এর অপেক্ষায় ঘুমায়। Signal handler-এর ভেতরে প্রায় কিছুই নিরাপদে করা যায় না (Chapter 31), তাই handler শুধু এই thread-কে জাগায়, আর সে debugger চালু করে। চেষ্টা করে দেখো:

  node -e "setTimeout(() => {}, 1000)" & sleep 0.3
  kill -USR1 $!; wait'

Chapter 16-এর libuv-worker-দের এখানে দেখা যাচ্ছে না। hello.js কোনো file, DNS বা crypto-র কাজ চায়নি, তাই thread pool তৈরিই হয়নি; সেটা তৈরি হয় প্রথম দরকারের সময়।

৩২ ms-এ /sys/fs/cgroup/memory.max পড়া: Chapter 36-এর সেই ঘটনা। Node এখান থেকে দেখে কতটা memory পাওয়া যাবে, আর সেই হিসাবে V8-এর heap-এর সীমা ঠিক করে। তাই --memory 256m-এ heap-এর সীমা হয়েছিল ২৫৯ MB। এখানে container-এ কোনো সীমা দিইনি, তাই file-টায় লেখা max, আর Node পরের লাইনে /proc/meminfo থেকে পুরো RAM-এর হিসাবও নেয়।

trace-এর আটটা task, আর কাজ না থাকলে প্রত্যেকে kernel-এর কোথায় ঘুমায়। Dashed বাক্সটা একটা process: ভেতরের সাত thread একই memory ভাগ করে। কাজ এলে kernel ঠিক যাকে দরকার তাকেই জাগায়, বাকিরা S (sleeping) অবস্থায় থাকে, CPU খায় না (Chapter 15, 17)।

এরপর ছবির চার নম্বর ধাপ: Node-এর নিজের JS (require, process, stream…) দাঁড় করানো, V8-এর snapshot থেকে (Chapter 34)। এই অংশের syscall-গুলো প্রায় সবই memory-র: V8-এর heap-এর জন্য mmap, mprotect, madvise। বাকি কাজটা CPU-র, strace-এ তার কোনো লাইন নেই।

৫৬ ms-এ, strace-এর হিসাবে জন্মের প্রায় শেষে, Node প্রথমবার তোমার file খোঁজে। প্রথম statx দেখে hello.js আছে কি না, আর সেটা file না folder। দ্বিতীয়টা (AT_SYMLINK_NOFOLLOW) দেখে সেটা symlink কি না, যাতে আসল path জানা যায় (Chapter 22: path থেকে inode)। তারপর Node খোঁজে package.json: প্রথমে /w-এ, তারপর উপরের /-এ। এই grep-এ শুধু /w-এরটা এসেছে। খোঁজার কারণ, সবচেয়ে কাছের package.json-এর "type" দেখে Node ঠিক করে .js file-টা CommonJS না ES module। তারপর openat, ২২ byte read, close (Chapter 21)। Compile-এ কোনো syscall নেই: V8 পুরোটা user mode-এ করে (Chapter 4)।

console.log-এর আগে Node দেখে নেয় fd ১ আসলে কী। ioctl(1, TCGETS) (grep-এ নেই) উত্তর দেয় ENOTTY, মানে এটা terminal না। -t ছাড়া Docker stdout-কে একটা pipe দিয়ে নিজের কাছে নেয়। Terminal, file আর pipe-এ লেখার নিয়ম আলাদা বলে Node এটা আগে জেনে নেয়। তারপর fd-টাকে non-blocking করে (FIONBIO, Chapter 28), আর একটাই write(1, "hello\n", 6) (Chapter 32)। node জানে না লেখাটা শেষে কোথায় যাবে, সে শুধু fd ১-এ লেখে (Chapter 15-এর dup3)।

তারপর দুটো epoll_pwait(13, [], 1024, 0)। তোমার script শেষ, এবার event loop ঘোরে। শেষ argument 0 হলো timeout: "একটুও অপেক্ষা কোরো না"। কারণ অপেক্ষা করার মতো কিছু বাকি নেই: কোনো timer নেই, socket নেই, চলমান file-এর কাজ নেই। Loop তাই শেষ, আর process-ও শেষ। Node কখন exit করে, তার নিয়ম এটাই: যখন আর কিছুর অপেক্ষা বাকি থাকে না। একটা timer যোগ করলে একই লাইন বদলে যায়:

Node আগে নিজে গোছায়। V8 worker-দের futex দিয়ে জাগিয়ে বলে থামতে (grep-এ নেই; Chapter 17–18-এর ঘুম-জাগানো)। DelayedTaskScheduler ঘুমিয়ে আছে তার epoll-এ, তাই তাকে জাগাতে fd ১২-তে ৮ byte লেখে। fd ১২ একটা eventfd, যেটা সেই epoll-এ বসানো ছিল (Chapter 29)। একে একে পাঁচটা thread শেষ হয়। তারপর exit_group(0), আর বাকি কাজ kernel-এর:

  • যে thread-কে কেউ থামতে বলেনি, তাকে মেরে ফেলে। এখানে ১৩৪, সেই signal watcher।
  • পুরো address space ফেরত নেয়: ৪৭৩ MB-এর mapping, যার ৪১ MB RAM-এ ছিল (নিচে মাপা)।
  • সব খোলা fd বন্ধ করে।
  • Exit code রেখে দেয়। Parent সেটা তুলে না নেওয়া পর্যন্ত process-টা zombie হয়ে থাকে (Chapter 15)।

৭৩.২৪ ms-এ bash-এর সেই wait4 অবশেষে ফেরে, WEXITSTATUS == 0 নিয়ে, সাথে SIGCHLD। bash কোডটা রাখে $?-এ, আর echo লেখে exit=0। Terminal-এ হলে এখানেই prompt ফিরে আসত।

strace যা দেখে না

strace শুধু system call দেখে। অথচ ওই ১৩ ms-এ আরও অনেক কিছু ঘটে যা syscall না। Page fault একটা exception, kernel-এর তৃতীয় দরজা (Chapter 31)। Context switch ঘটায় scheduler (Chapter 17)। Timer interrupt আসে hardware থেকে। কোনোটাই strace-এর লাইনে আসে না। তবে kernel প্রতিটা process-এর জন্য এগুলোর হিসাব রাখে, আর getrusage() syscall সেটা দেয়; Node-এ process.resourceUsage()। -r (require) দিয়ে যেকোনো script-এর আগে load করা যায় এমন একটা ছোট file:

// watch.js — যেকোনো script-এর আগে load করো (node -r ./watch.js app.js); শেষে kernel-এর খাতা দেখায়
process.on('exit', () => {
  const r = process.resourceUsage();                        // getrusage(): পুরো process, সব thread মিলিয়ে
  const vm = require('fs').readFileSync('/proc/self/status', 'utf8');
  const mb = key => Math.round(vm.match(new RegExp(key + ':\\s+(\\d+)'))[1] / 1024);
  console.error(`CPU time         user ${(r.userCPUTime / 1000).toFixed(1)} ms, kernel ${(r.systemCPUTime / 1000).toFixed(1)} ms`);
  console.error(`page faults      ${r.minorPageFault} minor, ${r.majorPageFault} major`);
  console.error(`context switches ${r.voluntaryContextSwitches} voluntary, ${r.involuntaryContextSwitches} involuntary`);
  console.error(`memory           ${mb('VmSize')} MB mapped, ${mb('VmRSS')} MB in RAM, ${vm.match(/Threads:\s+(\d+)/)[1]} threads`);
});

  • CPU time — ১২ ms user mode-এ, ২ ms kernel mode-এ (Chapter 31-এর দুই mode)। দুটো মিলিয়ে প্রায় পুরো ১৩ ms, কারণ বেশিরভাগ সময় একটা thread-ই ব্যস্ত ছিল। User আর kernel-এর ভাগটা এক চালানো থেকে আরেক চালানোয় বেশ নড়ে। এই তিন সংখ্যা (real, user, kernel) দিয়ে ধীর program-এর রোগ ধরা Chapter 39-এর বিষয়।
  • ২৪৩৪টা minor page fault — প্রতিটা একটা page-এ প্রথম ছোঁয়া: node-এর code (Chapter 34-এর সেই ৩০ MB), V8-এর heap, thread-দের stack। Major শূন্য, কারণ node file-টা page cache-এ ছিল; ঠান্ডা অবস্থায় Chapter 34-এ পেয়েছিলাম ৩০৩টা। এই আড়াই হাজার ঘটনার একটাও strace-এ নেই।
  • ২৪টা voluntary context switch — প্রতিবার কোনো thread নিজে থেকে ঘুমাতে গেছে (ওপরের ছবির futex আর epoll_pwait)। Involuntary মাত্র ১: scheduler প্রায় কাউকেই জোর করে সরায়নি (Chapter 17)।
  • ৪৭৩ MB mapped, ৪১ MB RAM-এ — V8 বড় বড় জায়গা আগে থেকে দাবি করে রাখে, ব্যবহার করে সামান্যই। Virtual আর physical memory-র সেই পার্থক্য (Chapter 9)।

(Command-টা bash -c-এর ভেতরে চালিয়েছি। node নিজেই container-এর PID ১ হলে, মানে docker run … node -r ./watch.js hello.js, আমার এখানে সংখ্যাগুলো বেশি আসে: প্রায় ৩২০০ fault আর ৮০টা switch। কারণটা আমি খুঁজে বের করিনি।)

COMMON MISCONCEPTION

"time node script.js মানে আমার code-এর সময়।" hello.js-এ ১৩ ms-এর মধ্যে তোমার code ২ ms-ও না; বাকিটা process-এর জন্ম আর বিদায়, যা প্রতিবার একই দামে দিতে হয়। ছোট script, CLI tool, প্রতি test-এ নতুন process চালানো test runner, serverless-এর cold start (Chapter 34): এসব ক্ষেত্রে এই স্থির খরচটাই প্রায়ই মূল খরচ। নিজের code মাপতে চাইলে ভেতর থেকে মাপো (performance.now()), নয়তো এত বেশিবার চালাও যে স্থির খরচ হিসাবে আর চোখে না পড়ে। আর strace-এর সময় বিশ্বাস কোরো না: এখানে সে সবকিছু ছয় গুণ ধীর করেছিল।

MENTAL MODEL

Enter চাপার পর: shell PATH ধরে file খোঁজে, fork করে (copy-on-write copy), আর wait4-এ ঘুমিয়ে পড়ে। Child execve দিয়ে node হয়ে যায়। Kernel ELF map করে, ld.so library জোড়ে। node-এর main signal গোছায়, event loop-এর epoll বানায়, ছয়টা helper thread তৈরি করে, cgroup দেখে heap-এর সীমা ঠিক করে, snapshot থেকে নিজের JS দাঁড় করায়। তারপর, ১০ ms পরে, তোমার file: খোঁজা, পড়া, compile, আর একটা write(1)। Event loop-এ অপেক্ষার কিছু না থাকলে (timeout 0) node গুছিয়ে exit_group করে। Kernel memory আর fd ফেরত নেয়, আর parent-কে exit code পৌঁছে দেয়। পুরো পথে strace-এর চোখের আড়ালে থাকে আড়াই হাজার page fault, কয়েক ডজন ঘুম-জাগা আর timer interrupt। এই গল্পটা বই না খুলে বলতে পারলে, আর যেখানে আটকাও সেই chapter-এ ফিরে গেলে, বইয়ের বেশিরভাগটাই তোমার।
