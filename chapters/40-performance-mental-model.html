এই বইয়ে আমরা অনেক কিছু মেপেছি, এই Mac-এ আর তার Docker VM-এ। সেগুলো এক জায়গায়, ছোট থেকে বড়:

এই বইয়ে মাপা সংখ্যা, log scale-এ: ডানে প্রতিটা দাগ আগেরটার দশ গুণ। বাঁ থেকে ডানে সাড়ে সাত ঘর, মানে সবচেয়ে সস্তা আর সবচেয়ে দামি কাজের মধ্যে প্রায় সাড়ে তিন কোটি গুণ তফাত। Machine: M4 Pro Mac আর তার Docker VM।

সংখ্যাগুলো মুখস্থ করার দরকার নেই, তোমার machine-এ অন্য রকম হবে। মনে রাখার জিনিস হলো মাত্রা আর ধাপ। CPU আর cache থাকে nanosecond-এর ঘরে। Kernel-এ একবার ঢোকা, page cache থেকে পড়া বা একটা thread জাগানো microsecond-এর নিচের দিকে। Disk আর network-এর এক round trip microsecond-এর উপরের দিকে। আর durability (fsync) বা একটা ভুল TCP setting millisecond-এ। প্রতিটা বড় ধাপে দশ থেকে হাজার গুণ। মানুষের মাপে ভাবলে ধাক্কাটা বোঝা যায়: L1-এর একটা ছোঁয়া যদি ১ সেকেন্ড হতো, তাহলে RAM দেড় মিনিট, NVMe থেকে একটা read ১৭ ঘণ্টা, একটা fsync আড়াই দিন, আর delayed ACK-এর একটা আটকে থাকা প্রায় এক বছর। সংখ্যায় বললে, একটা fsync-এর সময়ে CPU প্রায় আড়াই হাজার বার RAM থেকে পড়ে আসতে পারত।

এখান থেকে design-এর প্রথম দুটো নিয়ম আসে। এক: যে data বারবার লাগে, সেটা সিঁড়ির উপরের দিকে রাখো। এই কারণেই CPU cache (Chapter 13), page cache (Chapter 23), আর তোমার application-এর নিজের cache আছে। দুই: নিচের ধাপে নামতে হলে কম বার নামো, প্রতিবার বেশি কাজ নিয়ে। এক byte করে লেখার বদলে batching (Chapter 32), প্রতি order-এ fsync-এর বদলে group commit (Chapter 24), N+1 query-র বদলে একটা query।

Latency আর throughput: Little's law

দুটো আলাদা প্রশ্ন প্রায়ই গুলিয়ে যায়। Latency মানে একটা কাজ কতক্ষণ নেয়। Throughput মানে প্রতি সেকেন্ডে কয়টা কাজ শেষ হয়। দুটোকে জোড়ে একটা সরল নিয়ম, Little's law:

L = λ × W
L = গড়ে একসাথে কয়টা কাজ চলছে (in flight)
λ = প্রতি সেকেন্ডে কয়টা কাজ আসে (আর স্থির অবস্থায়, শেষ হয়)
W = প্রতিটা কাজ গড়ে কতক্ষণ system-এর ভেতরে থাকে

নিয়মটা যেকোনো স্থির system-এ খাটে, কাজ কীভাবে আসে বা কীভাবে সারা হয় তাতে কিছু যায় আসে না। Chapter 20-এর NVMe মনে করো। একটা করে read পাঠালে (L = ১) প্রতিটা ৭৯ µs, তাই λ = ১ ÷ ৭৯ µs ≈ ১২,৬০০ IOPS। ১৬টা একসাথে পাঠালে পাওয়া গিয়েছিল ১,১১,৬১০ IOPS। Little's law দিয়ে প্রতিটার latency: W = ১৬ ÷ ১,১১,৬১০ ≈ ১৪৩ µs। প্রতিটা read প্রায় দ্বিগুণ ধীর, অথচ throughput নয় গুণ। বেশি কাজ একসাথে চালালে throughput বাড়ে, latency কিছুটা বাড়ে, আর কতটা বাড়ে সেটা দেখায় কতগুলো কাজ একসাথে চলছে।

রোজকার কাজে এর সবচেয়ে বড় ব্যবহার হলো আকার ঠিক করা। Chapter 38-এর server-এ প্রতিটা DB query ৫ ms। সেকেন্ডে ২০০০ request সামলাতে হলে গড়ে L = ২০০০ × ০.০০৫ = ১০টা query একসাথে চলবে। একটা connection-এ query একটার পর একটা চললে সেকেন্ডে ২০০টার বেশি হবে না; তাই connection pool-এ অন্তত ১০টা connection লাগবে, আর ওঠানামা সামলাতে কিছু বেশি। Accept queue-এর আকার (Chapter 26), thread pool-এর আকার (Chapter 19), সবখানে একই হিসাব।

লাইন: utilization বাড়লে latency লাফায়

Chapter 39-এ বলেছিলাম saturation, মানে লাইন, utilization-এর চেয়ে গুরুত্বপূর্ণ। কেন? একটা resource ১০০% ব্যস্ত না হলেও লাইন তৈরি হয়, কারণ কাজ সমান তালে আসে না। কখনো তিনটা একসাথে আসে, তারপর কিছুক্ষণ কেউ না। একসাথে আসা তিনজনের দুজনকে দাঁড়াতে হয়, আর পরের ফাঁকা সময়টা ফেরত আসে না। এর দাম কত, সেটা সূত্র দিয়ে না, একটা simulation দিয়ে দেখি। একটা server, প্রতিটা request-এর কাজ গড়ে ১ ms, request আসে এলোমেলো সময়ে; শুধু আসার হার বাড়াব:

// queue.js — একটা server, একটা লাইন: প্রতিটা request-এর কাজ গড়ে ১ ms, আর request আসে এলোমেলো সময়ে।
// Utilization বাড়ালে latency কী করে? Simulation: ঘড়িটা নিজেরা চালাই, আসল অপেক্ষা লাগে না।
let seed = 42;                                                  // নির্দিষ্ট seed: তোমার output আমার সাথে হুবহু মিলবে
const uniform = () => ((seed = (seed * 16807) % 2147483647) - 1) / 2147483646;
const random = mean => -mean * Math.log(1 - uniform());          // এলোমেলো সময়, কিন্তু গড় = mean
function run(util, n = 1e6) {
  const work = 1;                                   // ms, প্রতিটা request-এর গড় কাজ
  const rate = util / work;                         // প্রতি ms-এ গড়ে কয়টা request আসে
  let now = 0, freeAt = 0, inSystemSum = 0;
  const done = [], latency = new Float64Array(n);
  for (let i = 0, head = 0; i < n; i++) {
    now += random(1 / rate);                        // পরের request এল
    while (head < done.length && done[head] <= now) head++;
    inSystemSum += done.length - head;              // সে এসে কতজনকে ভেতরে দেখল
    const start = Math.max(now, freeAt);            // server ব্যস্ত থাকলে লাইনে দাঁড়াও
    freeAt = start + random(work);
    done.push(freeAt);
    latency[i] = freeAt - now;                      // লাইনে অপেক্ষা + নিজের কাজ
  }
  latency.sort();
  const mean = latency.reduce((a, b) => a + b) / n;
  return { mean, p50: latency[n * 0.5 | 0], p99: latency[n * 0.99 | 0], L: inSystemSum / n, rate };
}
console.log('util   mean    p50     p99    | in system  λ×W');
for (const u of [0.1, 0.3, 0.5, 0.7, 0.8, 0.9, 0.95]) {
  const r = run(u), f = x => x.toFixed(1).padStart(5);
  console.log(`${String(u * 100).padStart(3)}%  ${f(r.mean)}  ${f(r.p50)}  ${f(r.p99)} ms |  ${r.L.toFixed(2).padStart(6)}  ${(r.rate * r.mean).toFixed(2).padStart(6)}`);
}

queue.js-এর ফল। কাজ একই, ১ ms; শুধু utilization বাড়ছে। ৫০% পর্যন্ত প্রায় সমতল, তারপর বাঁক নিয়ে খাড়া। গড় (নিচের রেখা) ৯৫%-এ বিশ গুণ, আর P99 (dashed) ৮৬ গুণ।

৫০% utilization-এ latency দ্বিগুণ: গড়ে যতক্ষণ নিজের কাজ, ততক্ষণই লাইনে। ৮০%-এ পাঁচ গুণ, ৯০%-এ দশ গুণ, ৯৫%-এ বিশ গুণ। এই ধরনের একটা লাইনের জন্য নিয়মটা সরল: গড় latency = কাজের সময় ÷ (১ − utilization)। Utilization যত ১০০%-এর কাছে যায়, হর তত শূন্যের দিকে, আর latency অসীমের দিকে। এটাই "hockey stick"। Server হঠাৎ "পড়ে যায়" এভাবেই: traffic ৮০% থেকে ৯০%-এ উঠল, মানে মাত্র ১২% বেশি, অথচ latency দ্বিগুণ। শেষ দুই কলামে Little's law নিজে থেকেই মিলে গেছে: আসা request-রা ভেতরে গড়ে যতজনকে দেখেছে, সেটা λ × W-এর সমান।

বাস্তবে এর মানে: latency যেখানে জরুরি, সেখানে কোনো resource-কে ৭০–৮০%-এর বেশি ব্যস্ত রাখার পরিকল্পনা কোরো না। বাকিটা অপচয় না, সেটাই লাইন শোষণ করার জায়গা। CPU, DB connection pool, একটা Node process-এর event loop (Chapter 39), disk, সবার জন্য একই কথা।

গড় কেন মিথ্যা বলে: P50, P99

ওপরের table-এ ৯০% utilization-এ গড় ১০ ms, কিন্তু P50 ৭ ms আর P99 ৪৭ ms। Percentile মানে: সব মাপ ছোট থেকে বড় সাজালে P50 হলো ঠিক মাঝেরটা, আর P99 হলো সেই মান, যার চেয়ে ধীর মাত্র ১%। গড় দুটোর কোনোটাই না। অল্প কয়েকটা খুব ধীর request গড়কে টেনে তোলে, অথচ বেশিরভাগ user সেই গড় কখনো দেখে না। আর সবচেয়ে খারাপ অভিজ্ঞতাটা গড়ে লুকিয়ে যায়।

Chapter 39-এর lag.sh এর আরেকটা উদাহরণ: /ping-এর P50 ০.৭ ms, P99 ৫৬ ms। Dashboard-এ শুধু গড় বা P50 দেখলে মনে হতো server ঠিক আছে। অথচ প্রতি একশো request-এর একটা ৫০ ms আটকে ছিল, আর সেটাই event loop আটকে যাওয়ার একমাত্র চিহ্ন।

P99 কেন "প্রায় কেউ না"-র সংখ্যা না, সেটা বোঝা যায় যখন একটা page বা API অনেকগুলো backend call করে। প্রতিটা call ১% সম্ভাবনায় ধীর হলে, ১০টা call-এর মধ্যে অন্তত একটা ধীর হওয়ার সম্ভাবনা কত?

node -p "(1 - 0.99 ** 10).toFixed(3) + '  ' + (1 - 0.99 ** 100).toFixed(3)"
0.096  0.634

১০টা call-এ প্রায় ১০%, ১০০টায় ৬৩%। Page-টা সবচেয়ে ধীর call-এর জন্য অপেক্ষা করে, তাই backend-এর P99 হয়ে যায় page-এর P90। বড় system-এ tail, মানে সবচেয়ে ধীর কয়েক শতাংশ, অনেক user-এর রোজকার অভিজ্ঞতা। তাই latency-র লক্ষ্য লেখো percentile-এ ("P99 < ১০০ ms"), গড়ে না।

Amdahl's law: parallel-এর সিলিং

Chapter 14-এর parallel.js মনে করো: ১২টা worker-এ ৮ গুণ দ্রুত, ১২ গুণ না; ২৪টায় আরও ধীর। কারণের একটা অংশ হার্ডওয়্যার: এই Mac-এর ১২ core-এর ৪টা ছোট efficiency core। আরেকটা অংশ আরও মৌলিক: প্রতিটা কাজের কিছু অংশ ভাগ করা যায় না। Worker চালু করা, কাজ ভাগ করে দেওয়া, ফল জোড়া দেওয়া, একটা shared lock বা একটা DB row-এর জন্য লাইন। এর নাম Amdahl's law: কাজের যে অংশ parallel করা যায় না, core যতই বাড়াও সেটা একই সময় নেয়:

// amdahl.js — কাজের ৯৫% ভাগ করা যায়, ৫% যায় না: core বাড়ালে কত গুণ দ্রুত?
const speedup = (parallel, cores) => 1 / ((1 - parallel) + parallel / cores);
for (const n of [1, 2, 4, 8, 12, 100, Infinity])
  console.log(`${String(n).padStart(8)} cores: ${speedup(0.95, n).toFixed(1).padStart(4)}×`);

     100 cores: 16.8×
Infinity cores: 20.0×

মাত্র ৫% ভাগ-না-করা অংশ থাকলে ১২ core-এ ৭.৭ গুণ, ১০০ core-এ ১৬.৮, আর অসীম core-এও ২০ গুণের বেশি না। সিলিং ঠিক করে দেয় serial অংশটা: ১ ÷ ০.০৫। তাই কোনো system-কে scale করতে চাইলে আগে খোঁজো কোন অংশ serial। Node-এ সবচেয়ে বড় serial অংশ প্রায়ই event loop নিজে: একটা process-এর সব JS একটা thread-এ। এই কারণেই CPU-ভারী Node service একাধিক process-এ চালাতে হয় (cluster, একাধিক container), আর ভারী কাজ worker-এ পাঠাতে হয় (Chapter 19)।

COMMON MISCONCEPTION

"Server ৬০% CPU-তে চলছে, তাই এখনো ৪০% জায়গা আছে। Traffic দেড় গুণ হলেও চলবে।" Queue.js বলছে উল্টো। ৬০% থেকে ৯০%-এ গেলে গড় latency ২.৫ ms থেকে ১০ ms, চার গুণ; P99 আরও বেশি। আর traffic কখনো সমান তালে আসে না: এক মিনিটের গড় ৬০% মানে কিছু সেকেন্ডে ৯০%-এর বেশি। Capacity-র হিসাব utilization দিয়ে না, latency-র লক্ষ্য দিয়ে করো: "P99 ১০০ ms-এর নিচে রেখে কত traffic নেওয়া যায়?", আর সেটা load test করে মাপো।

শেষ কথা — চারটা প্রশ্নের অভ্যাস

যেকোনো system, feature বা bug-এর সামনে দাঁড়িয়ে চারটা প্রশ্ন। (১) Data সিঁড়ির কোন ধাপে? প্রতিটা request কত নিচে নামছে: cache, RAM, kernel, disk, network? উপরে রাখা যায় কি? (২) সীমানা কতবার পার হচ্ছি? Syscall, process, network-এর প্রতিটা পারাপারের একটা স্থির দাম আছে। কম বার, বড় টুকরোয় পার হওয়া যায় কি? (৩) লাইন কোথায়? কোন resource ৭০%-এর বেশি ব্যস্ত, কে কার অপেক্ষায়, কত লম্বা লাইনে? আর আমি গড় দেখছি, নাকি P99? (৪) কোন অংশ serial বা shared? একটা lock, একটা event loop, একটা DB row, একটা connection: সেটাই শেষে সিলিং। এই চার প্রশ্নের প্রতিটার উত্তর দিতে এই বইয়ের কোনো না কোনো chapter লাগে। আর উত্তরগুলো অনুমানে না, মেপে দাও।

CAN I EXPLAIN THIS?
  • সিঁড়ির সংখ্যাগুলো থেকে: একটা request-এ ১০০০টা ছোট syscall আর একটা fsync থাকলে কোনটা বেশি সময় নেবে? L1 থেকে delayed ACK পর্যন্ত মোটামুটি কত গুণ তফাত?
  • Little's law কী বলে? NVMe-তে ১৬টা read একসাথে পাঠালে প্রতিটা ধীর হলো অথচ throughput নয় গুণ বাড়ল, কীভাবে? ৫ ms-এর query দিয়ে সেকেন্ডে ২০০০ request সামলাতে কয়টা DB connection লাগবে?
  • queue.js-এ কাজ একই রেখেও ৯৫% utilization-এ গড় latency বিশ গুণ কেন? ১০০% ব্যস্ত না হয়েও লাইন তৈরি হয় কেন? Latency-জরুরি resource-কে কেন ৭০–৮০%-এর নিচে রাখা ভালো?
  • P50, P99 আর গড়ের পার্থক্য কী? ১০টা backend call-এর page-এ backend-এর P99 কেন page-এর প্রায় P90 হয়ে যায়?
  • ৫% serial অংশ থাকলে অসীম core-এও ২০ গুণের বেশি দ্রুত হয় না কেন? Node service-এ সবচেয়ে সাধারণ serial অংশ কোনটা, আর তার সমাধান কী?
