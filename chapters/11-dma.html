PART 3 · MEMORY

Chapter 11 — DMA

Device আর RAM-এর মধ্যে বিশাল data আনা-নেওয়ায় CPU-কে মুক্তি দেওয়ার কৌশল — কীভাবে কাজ করে, প্রতিটা অনুরোধের কী দাম, কী পাহারা লাগে, আর কোথায় তার সীমা।

Chapter 2-এর readFileSync-এর যাত্রায় এক লাইনে বলেছিলাম: SSD controller data সরাসরি RAM-এ লিখে দেয়, CPU-কে byte byte copy করতে হয় না — এর নাম DMA (Direct Memory Access)। সেই chapter থেকে আরও দুইটা জিনিস লাগবে: device-এর নিজস্ব controller, যার register-এ CPU command লেখে (Chapter 7-এর /proc/iomem-এ দেখেছ এই register গুলোও physical address-এর জায়গা নিয়ে থাকে); আর interrupt, যেটা দিয়ে device কাজ শেষে CPU-কে ডাকে। এই chapter-এ DMA-কে খুলে দেখব।

DMA না থাকলে: CPU যখন কুলি

DMA ছাড়া device-এর data RAM-এ আনার উপায় একটাই: CPU নিজে controller-এর data register থেকে একটা একটা করে word পড়বে, আর প্রতিটা RAM-এ store করবে। এর নাম programmed I/O (PIO)। সমস্যা দুইটা। এক, device register পড়া সাধারণ memory পড়ার মতো না — এগুলো cache-এ রাখা যায় না (device-এর মান যেকোনো মুহূর্তে বদলাতে পারে), প্রতিবার bus পেরিয়ে device পর্যন্ত যেতে হয়, একেকটায় কয়েকশো ns। দুই, আজকের NVMe SSD সেকেন্ডে ৭ GB পর্যন্ত data দিতে পারে; PIO-তে সেটা আনতে একাধিক core-কে সারাক্ষণ শুধু এই কুলিগিরিতে লাগিয়ে রাখতে হতো, আর সেই সময় তারা আর কোনো process চালাতে পারত না।

"CPU নিজে copy করছে" দেখতে কেমন, তার একটা নমুনা Linux-এ দেখা যায় — file যখন আগে থেকেই page cache-এ আছে (Chapter 2), তখন read মানে kernel page cache থেকে তোমার buffer-এ CPU দিয়ে copy করে:

EXPERIMENT (Linux / Docker) — CPU-র copy

dd হলো block ধরে ধরে data পড়া-লেখার একটা পুরনো Unix tool; time দেখায় মোট সময় (real) আর তার মধ্যে CPU কতটা user mode আর kernel mode-এ খেটেছে (Chapter 1)। Container-টা খোলা রাখো, পরের experiment-ও এখানেই:

docker run --rm -it debian:bookworm-slim bash

# container-এর ভেতরে: ১ GB-র একটা file বানাও (লেখার পরে এটা page cache-এও থাকবে)
dd if=/dev/urandom of=/root/big.bin bs=1M count=1024 status=none

# file-টা পড়ো — data আসবে page cache থেকে, CPU-র copy দিয়ে
time dd if=/root/big.bin of=/dev/null bs=1M status=none

আমার output: real 0m0.033s, user 0m0.000s, sys 0m0.033s। পুরো সময়টাই (sys = real) CPU kernel mode-এ ব্যস্ত ছিল — ১ GB সরাতে একটা core ৩৩ ms পুরোপুরি আটকে। আর এটা RAM থেকে RAM-এ copy; device register থেকে PIO এর চেয়ে বহু গুণ ধীর হতো।

DMA: device নিজেই RAM-এ লেখে

সমাধান হলো কাজটা device-কেই দিয়ে দেওয়া। আধুনিক device গুলো bus master — মানে CPU-কে জিজ্ঞেস না করেই নিজে bus-এ memory read/write চালাতে পারে। CPU-র কাজ তখন শুধু বলে দেওয়া কী করতে হবে, আর শেষে খবর নেওয়া। ধাপগুলো:

  1. Buffer আর descriptor: driver RAM-এ data রাখার জন্য একটা buffer ঠিক করে, তারপর RAM-এর একটা নির্দিষ্ট জায়গায় একটা ছোট নির্দেশ-পত্র লেখে — descriptor: "disk-এর এই block থেকে, এত byte, RAM-এর এই physical address-এ"। Descriptor গুলো সাজানো থাকে একটা চক্রাকার তালিকায় (ring), যাতে একসাথে অনেক কাজ লাইনে রাখা যায়।
  2. Doorbell: driver controller-এর একটা বিশেষ register-এ লিখে জানায় "ring-এ নতুন কাজ আছে"। এটাই CPU আর device-এর মধ্যে একমাত্র সরাসরি কথা।
  3. Device নিজে কাজ করে: controller DMA দিয়ে ring থেকে descriptor পড়ে, disk থেকে data আনে, আর DMA দিয়ে সেটা buffer-এ লিখে দেয়। এই পুরো সময় CPU অন্য process চালাচ্ছে।
  4. Completion + interrupt: কাজ শেষে controller RAM-এ একটা "শেষ হয়েছে" entry লেখে আর interrupt পাঠায়। Driver দেখে কোন কাজ শেষ, আর অপেক্ষায় থাকা process-কে জাগায়।

CPU-র কাজ শুধু ① আর ② — RAM-এ একটা descriptor লেখা আর device-এর একটা register-এ টোকা দেওয়া। ③ আর ④ device নিজে করে, bus master হিসেবে। ⑤-এ interrupt এলে CPU আবার ফেরে। মাঝের পুরো সময় CPU অন্য কাজে।

এবার মাপো। Linux-এ O_DIRECT নামের একটা flag আছে যেটা page cache এড়িয়ে যায় (বিস্তারিত Chapter 24): device DMA দিয়ে data সরাসরি process-এর নিজের buffer-এ লেখে। তাই CPU-র copy মাপে ঢোকে না — দেখা যায় DMA-র সময় CPU আসলে কতটা খাটে:

EXPERIMENT (Linux / Docker) — DMA-র সময় CPU
# আগের container-এই
time dd if=/root/big.bin of=/dev/null bs=1M iflag=direct status=none

আমার output: real 0m0.234s, user 0m0.002s, sys 0m0.030s।

১ GB এল ০.২৩৪ সেকেন্ডে, কিন্তু CPU খেটেছে মোট ০.০৩২ সেকেন্ড — সময়ের সাত ভাগের এক ভাগ। বাকি ~২০০ ms CPU-র হাতে কোনো কাজ ছিল না; data সরাচ্ছিল device, DMA দিয়ে। (এখানে "disk" আসলে Docker VM-এর একটা virtual disk, কিন্তু VM-এর kernel আর driver-এর চোখে ঠিক এই descriptor-doorbell-interrupt-এর খেলাই চলছে।) Queue কত গভীর হতে পারে, সেটাও দেখা যায়: cat /sys/block/vda/queue/nr_requests আমার VM-এ 256 — একসাথে ২৫৬টা পর্যন্ত অনুরোধ লাইনে থাকতে পারে, আর NVMe standard প্রতিটা device-এ হাজার হাজার ring রাখার সুযোগ দেয়।

একই transfer, দুই পদ্ধতি। PIO-তে CPU পুরো সময় কুলিগিরিতে আটকে। DMA-তে CPU-র ভাগ শুধু শুরু আর শেষের দুইটা ছোট টুকরো — dd-এর user + sys এই দুই টুকরোই মাপছিল; মাঝের সবুজ অংশটা real-এর বাকি সময়।

প্রতিটা অনুরোধের নিজস্ব দাম

DMA data-র প্রতি byte-এর খরচ মুছে দেয়, কিন্তু প্রতিটা অনুরোধ-এর খরচ থেকেই যায়: syscall, descriptor লেখা, doorbell, device-এর নিজের প্রস্তুতি, interrupt, completion দেখা, process জাগানো। অনুরোধ যত ছোট, এই স্থির খরচ তত বড় ভাগ খায়:

EXPERIMENT (Linux / Docker) — block-এর মাপ
# একই প্রথম 256 MB, একবার 4 KB টুকরোয় (65536টা অনুরোধ), একবার 1 MB টুকরোয় (256টা)
time dd if=/root/big.bin of=/dev/null bs=4k count=65536 iflag=direct status=none
time dd if=/root/big.bin of=/dev/null bs=1M count=256   iflag=direct status=none

আমার output: 4 KB-তে real 0m2.217s (sys 0m0.395s), 1 MB-তে real 0m0.027s।

একই ২৫৬ MB, একই disk — তবু ছোট টুকরোয় ৮০ গুণেরও বেশি সময়। কারণ ৬৫,৫৩৬টা অনুরোধের প্রতিটায় পুরো আনুষ্ঠানিকতা লেগেছে, আর CPU-কেও শুধু সেই আনুষ্ঠানিকতায় ০.৪ সেকেন্ড খাটতে হয়েছে। (১ MB-র সংখ্যাটা আগের ১ GB-র চেয়েও দ্রুত, কারণ এই VM-এর virtual disk-এর পেছনে Mac-এর নিজের cache আছে — কিন্তু অনুপাতের শিক্ষাটা বদলায় না।)

Network card-এ এই সমস্যা আরও তীব্র: সেকেন্ডে দশ লাখ packet এলে প্রতি packet-এ একটা interrupt মানে CPU শুধু interrupt সামলাতে সামলাতেই শেষ। দুইটা কৌশল আছে। Interrupt coalescing — device কয়েকটা completion জমিয়ে একটা interrupt পাঠায়। আর Linux-এর NAPI — চাপ বাড়লে driver interrupt বন্ধ করে দিয়ে নিজেই ring-টা বারবার দেখতে থাকে। Chapter 2-এ polling-কে অপচয় বলেছিলাম; কিন্তু কাজ যখন প্রতি মুহূর্তে আসছে, তখন বারবার ডাক শোনার চেয়ে নিজে দেখে নেওয়াই সস্তা। Interrupt আর polling — দুটোই হাতিয়ার, কোনটা ভালো তা নির্ভর করে কাজের ঘনত্বের উপর।

IOMMU: device-কে পাহারা

DMA-র একটা ভয়ংকর দিক আছে। Device physical address-এ সরাসরি লিখতে পারে — Chapter 9-এর MMU আর page table-এর কোনো পাহারা তার উপর নেই, কারণ ওগুলো CPU-র জন্য। তাহলে একটা buggy driver ভুল address দিলে, বা একটা দূষিত Thunderbolt device laptop-এ লাগালে, সে kernel-এর memory পড়ে ফেলতে বা বদলে দিতে পারে। এটা কল্পনা না — "DMA attack" নামে বাস্তবে দেখানো হয়েছে।

সমাধান: device-দের জন্য আলাদা একটা MMU — IOMMU। Device যে address ব্যবহার করে, IOMMU সেটাকে kernel-এর বানানো একটা page table দিয়ে অনুবাদ করে; kernel শুধু সেই buffer গুলোই map করে দেয় যেগুলো device-কে দেওয়া হয়েছে। Table-এর বাইরের যেকোনো address-এ device-এর লেখা আটকে যায়। Apple এর নাম দিয়েছে DART:

ioreg -l | grep -o '"IOClass" = "Apple[A-Z0-9]*DART"' | sort | uniq -c   # macOS
ls /sys/kernel/iommu_groups                                             # Linux (আসল machine-এ)

আমার Mac-এ 30 "IOClass" = "AppleT8110DART" — ৩০টা IOMMU, একেকটা একেক গোষ্ঠীর device পাহারা দিচ্ছে। Linux-এ IOMMU চালু থাকলে /sys/kernel/iommu_groups-এ প্রতিটা গোষ্ঠীর জন্য একটা folder থাকে (Docker Desktop-এর VM-এ এটা খালি — সেখানে IOMMU নেই)। Virtual machine-কে একটা আসল device সরাসরি দিতে চাইলেও (Chapter 35) IOMMU লাগে।

DMA-র পরেও একটা copy বাকি

সাধারণ fs.readFile-এ DMA data আনে kernel-এর page cache পর্যন্ত; সেখান থেকে তোমার buffer-এ আনে CPU-র copy (প্রথম experiment-এর sys = real)। একটা file server-এর কথা ভাবো যে disk থেকে পড়ে network-এ পাঠায়: disk → (DMA) → page cache → (CPU copy) → Node-এর buffer → (CPU copy) → socket-এর buffer → (DMA) → network card। মাঝের দুইটা copy সম্পূর্ণ অপ্রয়োজনীয় — data তো Node কখনো দেখছেই না।

এজন্য "zero-copy" কৌশল গুলো আছে: O_DIRECT (DMA সরাসরি process-এর buffer-এ, database-রা ব্যবহার করে), mmap (Chapter 10 — page cache-এর frame-ই process-এর page), আর sendfile (kernel-কে বলো "এই file-টা ওই socket-এ পাঠাও" — data user space-এ ঢোকেই না; nginx এভাবে static file পাঠায়)। বিস্তারিত Chapter 24 আর 27-এ।

COMMON MISCONCEPTION

"DMA মানে I/O-তে CPU-র কোনো খরচ নেই।" Data সরানোর খরচ নেই, ঠিক। কিন্তু প্রতিটা অনুরোধের setup, interrupt, completion আর process জাগানোর খরচ আছে — ৪ KB-র experiment-এ সেটাই ০.৪ সেকেন্ড CPU খেয়েছে। আর page cache থেকে user buffer-এ copy DMA করে না, CPU করে। "I/O-bound" কাজেও তাই বেশি ছোট ছোট অনুরোধ CPU-কে ব্যস্ত রাখতে পারে।

MENTAL MODEL

DMA-তে CPU হলো ম্যানেজার, device হলো কুলি: CPU একটা নির্দেশ-পত্র (descriptor) রাখে, একবার ঘণ্টা বাজায় (doorbell), তারপর অন্য কাজে চলে যায়; device নিজে RAM-এ data রেখে interrupt দিয়ে জানায়। খরচ গোনা হয় অনুরোধ ধরে, byte ধরে না — তাই বড় টুকরো, batching, coalescing। আর device-এর হাতে RAM-এর চাবি দেওয়ার আগে IOMMU দিয়ে ঠিক করে দিতে হয় সে কোন ঘরে ঢুকতে পারবে।

CAN I EXPLAIN THIS?
  • DMA না থাকলে (programmed I/O) সেকেন্ডে ৭ GB দেওয়া একটা SSD-র data আনতে CPU-র কী দশা হতো? Device register পড়া সাধারণ memory পড়ার চেয়ে ধীর কেন?
  • DMA-র পাঁচ ধাপে driver, device আর CPU — কে কোনটা করে? Descriptor, ring আর doorbell কী?
  • O_DIRECT-এর dd-তে real ০.২৩৪ s কিন্তু user + sys ০.০৩২ s — বাকি সময় কী হচ্ছিল? Page cache থেকে পড়ায় sys ≈ real কেন?
  • একই ২৫৬ MB ৪ KB block-এ পড়লে ৮০ গুণ ধীর কেন? Interrupt coalescing আর NAPI কোন সমস্যার সমাধান?
  • IOMMU না থাকলে একটা দূষিত Thunderbolt device কী করতে পারত? IOMMU সেটা কীভাবে আটকায়?
