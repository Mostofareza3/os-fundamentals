PART 4 · CPU

Chapter 14 — Pipelining আর Parallelism

CPU কেন একটা instruction শেষ করে তবে পরেরটা ধরে না: pipeline, একসাথে কয়েকটা instruction, আগাম অনুমান — আর core-এর বাইরে গিয়ে একাধিক core-এ কাজ ভাগ করা।

Chapter 12-এর দুইটা জিনিস লাগবে: CPU চলে clock-এর তালে, এক টিকের নাম cycle; আর একটা core-এর ভেতরে আলাদা আলাদা execution unit — কয়েকটা ALU, floating-point, load/store, branch। সেই chapter-এর clock.js-এর একটা অদ্ভুত দিক তখন এড়িয়ে গিয়েছিলাম: loop-এর প্রতিটা ধাপে অন্তত চারটা instruction (যোগ, i বাড়ানো, তুলনা, পেছনে লাফ), অথচ প্রতিটা ধাপ শেষ হয়েছে প্রায় এক cycle-এ। এক cycle-এ চারটা instruction? এই chapter সেই রহস্যের ব্যাখ্যা।

Pipeline: একটার পেছনে আরেকটা

একটা instruction-এর জীবনে কয়েকটা ধাপ: আনা (fetch), ভাঙা (decode), চালানো (execute), দরকার হলে memory ছোঁয়া, আর ফলাফল register-এ লেখা (write back)। প্রতিটা ধাপ core-এর আলাদা অংশে হয়। CPU যদি একটা instruction-এর পাঁচটা ধাপই শেষ করে তবে পরেরটা ধরত, তাহলে যে কোনো মুহূর্তে পাঁচটা অংশের চারটা বসে থাকত — decoder কাজ করছে তো fetch unit অলস।

সমাধান কারখানার assembly line-এর মতো: একটা instruction যখন decode হচ্ছে, পরেরটা তখন fetch হচ্ছে; প্রথমটা execute-এ গেলে দ্বিতীয়টা decode-এ আর তৃতীয়টা fetch-এ। এর নাম pipeline। কারখানার উপমাটা এখানেই থামাই, আসল ব্যাপারটা সংখ্যায় বলি: প্রতিটা instruction-এর নিজের সময় একটুও কমে না — সে এখনো পাঁচ cycle ধরে pipeline পেরোয়। কিন্তু প্রতি cycle-এ একটা করে instruction শেষ হয়ে বেরিয়ে আসে। Chapter 7-এর ভাষায়: latency একই, throughput পাঁচ গুণ।

একই ১১টা cycle। উপরে প্রতিটা instruction পাঁচ ধাপ শেষ করে তবে পরেরটা শুরু — মাত্র দুইটা শেষ। নিচে ধাপগুলো তির্যকভাবে একে অন্যের উপর বসে — pipeline ভরে যাওয়ার পর প্রতি cycle-এ একটা করে instruction শেষ (সবুজ W)। প্রতিটা instruction-এর নিজের পাঁচ cycle বদলায়নি।

একসাথে কয়েকটা: superscalar আর out-of-order

Pipeline দিয়ে বড়জোর প্রতি cycle-এ একটা। কিন্তু Chapter 12-এ দেখেছি একটা core-এ কয়েকটা ALU পাশাপাশি থাকে। তাই আধুনিক core প্রতি cycle-এ কয়েকটা instruction একসাথে pipeline-এ ঢোকায় — এর নাম superscalar। প্রতি cycle-এ গড়ে কতগুলো instruction শেষ হচ্ছে, সেই সংখ্যার নাম IPC (instructions per cycle); আধুনিক core-এ ভালো code-এ এটা ৩–৬ পর্যন্ত যায়। clock.js-এর রহস্যের উত্তর এটাই: loop-এর চারটা instruction একই cycle-এ আলাদা আলাদা unit-এ চলছিল।

কিন্তু একসাথে চালাতে হলে instruction গুলো একে অন্যের উপর নির্ভরশীল হলে চলবে না। b = a + 1 আর c = b * 2 — দ্বিতীয়টা প্রথমটার ফলাফল ছাড়া শুরুই হতে পারে না। তাই core আরও এক ধাপ চালাক: সামনের কয়েকশো instruction-এ চোখ বুলিয়ে যেগুলোর input তৈরি সেগুলো আগেভাগে চালিয়ে দেয়, লেখা ক্রম না মেনে — এর নাম out-of-order execution। (ফলাফল গুলো অবশ্য শেষে লেখা ক্রমেই "পাকা" করা হয়, যাতে বাইরে থেকে সব ঠিকঠাক দেখায়।) তবু একটা সীমা থেকেই যায়: শিকলের মতো পরপর নির্ভরশীল কাজ কোনো কৌশলেই একসাথে চলে না।

EXPERIMENT — ilp.js

একই দুই কোটি গুণ, একবার একটা শিকলে (প্রতিটা গুণ আগেরটার ফলাফলের জন্য অপেক্ষা করে), একবার চারটা স্বাধীন শিকলে ভাগ করে:

const N = 20_000_000;
const a = new Float64Array(N).fill(1.0000001);
function one(a) {                                   // একটা শিকল
  let s = 1;
  for (let i = 0; i < a.length; i++) s = s * a[i];
  return s;
}
function four(a) {                                  // চারটা স্বাধীন শিকল, শেষে জোড়া
  let s0 = 1, s1 = 1, s2 = 1, s3 = 1;
  for (let i = 0; i < a.length; i += 4) { s0 *= a[i]; s1 *= a[i + 1]; s2 *= a[i + 2]; s3 *= a[i + 3]; }
  return s0 * s1 * s2 * s3;
}
for (const [label, f] of [['1 chain ', one], ['4 chains', four]]) {
  f(a);
  const t = performance.now();
  for (let k = 0; k < 5; k++) f(a);
  console.log(label, ((performance.now() - t) / 5).toFixed(1), 'ms');
}

আমার Mac-এ: 1 chain 15.7 ms, 4 chains 4.4 ms।

গুণের সংখ্যা একই, তবু সাড়ে তিন গুণ দ্রুত। একটা শিকলে প্রতিটা গুণকে আগের গুণ শেষ হওয়ার জন্য floating-point unit-এর কয়েক cycle অপেক্ষা করতে হয় (Chapter 12-এর units.js); চারটা শিকলে সেই অপেক্ষার ফাঁকে বাকি তিনটা শিকলের গুণ চলে যায়। Memory-র বেলাতেও হুবহু এক গল্প: Chapter 7-এর pointer chase-এ প্রতিটা address আগের load-এর ফলাফল, তাই প্রতি access ১১৯ ns; Chapter 8-এর এলোমেলো যোগে address গুলো আগে থেকে জানা, তাই core একসাথে অনেকগুলো RAM অনুরোধ পাঠিয়ে দেয় — প্রতি access মাত্র ~৫ ns।

Branch prediction: আগাম অনুমান

Pipeline-এর একটা বড় শত্রু আছে: শর্তসাপেক্ষ লাফ (Chapter 12)। if-এর শর্তের উত্তর জানা যায় execute ধাপে, কিন্তু pipeline-কে পরের instruction আনতে হয় তার অনেক আগে, fetch ধাপে। উত্তরের জন্য অপেক্ষা করলে প্রতিটা branch-এ pipeline খালি পড়ে থাকবে — আর সাধারণ code-এ প্রতি পাঁচ-ছয়টা instruction-এ একটা branch।

তাই core অপেক্ষা করে না, অনুমান করে। Chapter 12-এর front-end-এর branch predictor প্রতিটা branch-এর অতীত আচরণ মনে রাখে — "এই loop-এর লাফ প্রায় সবসময় নেওয়া হয়", "এই if পাঁচবারে একবার সত্যি" — আর সেই অনুমানে পরের instruction গুলো আনা আর চালানো শুরু করে দেয়। অনুমান ঠিক হলে কোনো দেরি নেই। ভুল হলে আধা-চালানো সব কাজ ফেলে দিয়ে সঠিক পথ থেকে নতুন করে শুরু — কয়েক ডজন cycle-এর লোকসান।

EXPERIMENT — branch.js
const N = 10_000_000;
const data = new Int32Array(N);
for (let i = 0; i < N; i++) data[i] = Math.floor(Math.random() * 256);   // ০–২৫৫ এলোমেলো

function sumBig(arr) {                     // শুধু ১২৮ বা বড় সংখ্যা যোগ করো
  let s = 0;
  for (let i = 0; i < arr.length; i++) { if (arr[i] >= 128) s += arr[i]; }
  return s;
}
function run(label, arr) {
  sumBig(arr);
  const t = performance.now();
  for (let k = 0; k < 5; k++) sumBig(arr);
  console.log(label, ((performance.now() - t) / 5).toFixed(1), 'ms');
}
run('unsorted:', data);
run('sorted:  ', data.slice().sort());     // একই সংখ্যা, সাজানো

আমার Mac-এ: unsorted: 28.2 ms, sorted: 6.5 ms।

একই সংখ্যা, একই যোগফল, একই code — সাজানো data-য় চার গুণ দ্রুত। সাজানো array-তে প্রথম অর্ধেক পুরোটা "না", তারপর পুরোটা "হ্যাঁ" — predictor কয়েকবার দেখেই শিখে ফেলে। এলোমেলো array-তে প্রতিটা if একটা coin toss — অর্ধেক অনুমান ভুল, আর প্রতিটা ভুলে pipeline খালি। (Speculation-এর একটা অন্ধকার দিকও আছে: ২০১৮-এর Spectre আক্রমণ দেখিয়েছিল, ভুল পথে আগাম চালানো কাজের চিহ্ন cache-এ থেকে যায়, আর সেখান থেকে গোপন data চুরি করা যায়। আজকের browser আর OS-এ তার বিরুদ্ধে অনেক পাহারা বসানো।)

Core-এর বাইরে: একাধিক core-এ কাজ ভাগ

এতক্ষণের সব কৌশল একটা core-এর ভেতরে, একটা instruction-প্রবাহের জন্য। কিন্তু clock আর বাড়ানো যাচ্ছে না — বেশি clock মানে বেশি তাপ, আর ২০০০-এর দশকের মাঝামাঝি থেকে সেই দেয়ালে ধাক্কা লেগে আছে। তাই chip-নির্মাতারা বাড়াচ্ছে core-এর সংখ্যা। সমস্যা: তোমার Node-এর JS চলে একটা thread-এ, মানে একটা core-এ; বাকি এগারোটা বসে থাকে। বাড়তি core কাজে লাগাতে হলে কাজটাকে ভাগ করে একাধিক thread বা process-এ দিতে হয় (Part 5)।

EXPERIMENT — parallel.js

একই মোট কাজ (২৪০ কোটিবার বর্গমূল যোগ), ১, ২, ৪, ৮, ১২ আর ২৪টা worker_threads-এ সমান ভাগ করে:

const { Worker, isMainThread, workerData, parentPort } = require('worker_threads');
const TOTAL = 2_400_000_000;                     // মোট কাজ: ২৪০ কোটি ধাপ

function work(from, to) {                        // শুধু CPU-র কাজ, memory প্রায় ছোঁয় না
  let s = 0;
  for (let i = from; i < to; i++) s += Math.sqrt(i);
  return s;
}

if (isMainThread) {
  const run = n => new Promise(resolve => {
    const t = performance.now();
    const chunk = TOTAL / n;
    let done = 0;
    for (let w = 0; w < n; w++) {
      new Worker(__filename, { workerData: { from: w * chunk, to: (w + 1) * chunk } })
        .on('message', () => { if (++done === n) resolve(performance.now() - t); });
    }
  });
  (async () => {
    let base;
    for (const n of [1, 2, 4, 8, 12, 24]) {
      const ms = await run(n);
      base ??= ms;
      console.log(`${String(n).padStart(2)} workers: ${ms.toFixed(0).padStart(5)} ms   speedup ×${(base / ms).toFixed(1)}`);
    }
  })();
} else {
  parentPort.postMessage(work(workerData.from, workerData.to));
}

আমার Mac-এ (৮টা P-core, ৪টা E-core):

 1 workers:  1344 ms   speedup ×1.0
 2 workers:   672 ms   speedup ×2.0
 4 workers:   374 ms   speedup ×3.6
 8 workers:   201 ms   speedup ×6.7
12 workers:   169 ms   speedup ×8.0
24 workers:   180 ms   speedup ×7.5

আটটা worker পর্যন্ত প্রায় সরল হারে বাড়ে — প্রত্যেকে একটা P-core পায়। ১২-তে বাকি চারটা worker যায় E-core-এ, যারা ধীর (Chapter 12), তাই লাভ কম। আর ২৪-এ core-এর চেয়ে worker বেশি: OS তাদের পালা করে চালায় (time-sharing, Chapter 1), কাজ বাড়ে না কিন্তু পালা বদলের খরচ বাড়ে — উল্টো ধীর (Chapter 17)। প্রতিটা worker চালু হতে যে সময় লাগে, সেটাও সব ক্ষেত্রে বসে থাকে, তাই আট গুণের জায়গায় ৬.৭ গুণ।

Intel আর AMD-এর বেশিরভাগ core আরও একটা কৌশল করে: SMT (Intel-এর নাম Hyper-Threading) — একটা physical core নিজেকে দুইটা "hardware thread" হিসেবে দেখায়, যাতে একটা thread memory-র জন্য আটকে থাকলে core-এর অলস unit গুলো অন্যটা চালাতে পারে। দুইটা আসল core-এর সমান না, কিন্তু ব্যবহার বাড়ে। Apple Silicon-এ SMT নেই — sysctl hw.physicalcpu hw.logicalcpu দুটোই 12। Linux-এ lscpu | grep "Thread(s) per core" দেখায় সংখ্যাটা।

Instruction set নিয়ে দুই টুকরো কথা

RISC বনাম CISC: instruction set নকশার দুই দর্শন — ছোট, সরল, সমান মাপের instruction (RISC — ARM, তোমার Mac; সব instruction ৪ byte, Chapter 4-এ দেখেছ), বনাম বড়, জটিল, নানা মাপের instruction (CISC — Intel/AMD-এর x86)। আজ ভেতরে দুই ধারাই জটিল instruction ভেঙে ছোট ছোট অংশে চালায়, তাই পার্থক্য আগের চেয়ে কম। App developer-এর জন্য আসল কথা: আলাদা instruction set মানে আলাদা machine code।

file /bin/ls

macOS-এ output: Mach-O universal binary with 2 architectures: [x86_64 ...] [arm64e ...] — একটা file-এর ভেতরে দুইটা পুরো program, দুই instruction set-এর জন্য; loader চালানোর সময় machine-এর সাথে মেলে এমনটা বেছে নেয়। যে program-এ শুধু x86 code আছে, Apple Silicon-এ সেটা চালায় Rosetta — x86-এর machine code-কে ARM-এর machine code-এ অনুবাদ করে।

৩২-bit বনাম ৬৪-bit: মূলত register আর address কত চওড়া। ৩২-bit-এ একটা address দিয়ে সর্বোচ্চ ৪ GB বোঝানো যায় — আজকের জন্য হাস্যকর ছোট। getconf LONG_BIT তোমার machine-এ 64 দেখাবে। তবে আজকের CPU পুরো ৬৪ bit address ব্যবহার করে না, সাধারণত নিচের ৪৮ bit — এজন্যই Chapter 5-এর /proc/self/maps-এর address গুলো ১২ hex digit লম্বা (ffffffee8000): ১২ × ৪ = ৪৮ bit।

COMMON MISCONCEPTION

"Thread বা worker যত বেশি, তত দ্রুত।" CPU-র কাজে worker-এর সংখ্যা core-এর সংখ্যা পেরোলে আর কোনো লাভ নেই — parallel.js-এ ২৪টা worker ১২টার চেয়ে ধীর। আর নির্ভরশীল কাজে (একটা ধাপের ফলাফল পরের ধাপে লাগে) বাড়তি core বা unit কিছুই করতে পারে না — ilp.js-এর এক শিকল যেমন। Parallelism পেতে কাজের ভেতরে স্বাধীনতা থাকতে হয়; hardware শুধু সেটা কাজে লাগায়।

MENTAL MODEL

একটা core ভেতরে প্রচণ্ড parallel: pipeline-এ ধাপ গুলো একে অন্যের উপর বসে, superscalar unit গুলো একই cycle-এ কয়েকটা instruction চালায়, out-of-order যন্ত্র স্বাধীন কাজ আগে সেরে ফেলে, আর branch predictor আন্দাজে সামনে দৌড়ায়। এর সবকিছু থেমে যায় দুই জায়গায় — নির্ভরশীল শিকল আর ভুল অনুমান। আর core-এর বাইরে বাড়তি core গুলো ব্যবহার করতে হলে কাজ তোমাকেই ভাগ করে দিতে হয়।

CAN I EXPLAIN THIS?
  • Pipeline কীভাবে throughput বাড়ায় অথচ একটা instruction-এর নিজের সময় কমায় না? clock.js-এর loop প্রতি ধাপে ~১ cycle নেয় — এর মানে কী?
  • ilp.js-এ চারটা স্বাধীন শিকল সাড়ে তিন গুণ দ্রুত কেন? একই যুক্তিতে Chapter 7-এর pointer chase আর Chapter 8-এর এলোমেলো যোগের পার্থক্য ব্যাখ্যা করো।
  • Branch prediction কেন লাগে, আর ভুল অনুমানের দাম কী? branch.js-এ এলোমেলো data চার গুণ ধীর কেন?
  • parallel.js-এ ৮টা worker পর্যন্ত প্রায় সরল speedup, ১২-তে কম লাভ, ২৪-এ উল্টো ফল — তিনটারই কারণ কী?
  • /bin/ls-এ দুইটা architecture কেন? ৬৪-bit machine-এ address গুলো ১২ hex digit লম্বা কেন?
