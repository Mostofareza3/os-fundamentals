PART 11 · PUTTING EVERYTHING TOGETHER

Chapter 38 — একটা Web Server-এ Request এলে কী ঘটে?

তোমার প্রতিদিনের কাজের সবচেয়ে কাছের গল্প: একটা request আসে, handler database-কে জিজ্ঞেস করে, JSON ফেরত যায়। দুই process-এর system call আর network-এর প্রতিটা packet এক সময়রেখায়, তারপর মাপ: তোমার code আসলে কতটুকু সময় নেয়। শেষে ২০টা request একসাথে পাঠিয়ে Chapter 27-এর একটা ফাঁদ নিজে থেকে বেরিয়ে আসে।

Chapter 37-এ একটা process জন্ম থেকে মৃত্যু পর্যন্ত দেখেছি। Server-এর গল্প আলাদা: process আগে থেকেই চালু, বেশিরভাগ সময় ঘুমিয়ে থাকে, আর প্রতিটা request-এ অল্প কিছুক্ষণ জাগে। এই জেগে ওঠা থেকে আবার ঘুমানো পর্যন্ত কী ঘটে, আর সময় কোথায় যায়, সেটাই এই chapter। আয়োজনটা ছোট, কিন্তু আসল জিনিসের মতো। তিনটা process থাকবে: client হিসেবে curl, একটা Node HTTP server, আর database-এর জায়গায় আলাদা process-এ একটা নকল DB, যে প্রতিটা query-র উত্তর দেয় ৫ ms পরে। Packet ধরবে tcpdump (Chapter 26), syscall ধরবে strace। তিনটা tool-ই একই kernel-এর ঘড়ি দেখে সময় লেখে, তাই সব লাইন সময় ধরে সাজালে একটাই সময়রেখা পাওয়া যায়।

তিনটা process, একটা request

// db.js — নকল database: আলাদা process, port 5432; প্রতিটা query-র উত্তর দেয় ৫ ms পরে
const net = require('net'), readline = require('readline');
net.createServer(sock => {
  if (process.env.NODELAY) sock.setNoDelay(true);        // এখন না; কেন লাগে, chapter-এর শেষে
  readline.createInterface({ input: sock }).on('line', q => {      // "user 42", লাইন ধরে ধরে (Chapter 27)
    const id = Number(q.split(' ')[1]);
    setTimeout(() => sock.write(JSON.stringify({ id, name: 'Rahim' }) + '\n'), 5);   // disk আর query-র ভান
  });
}).listen(5432, '127.0.0.1');
// server.js — HTTP server; প্রতিটা request-এ db.js-কে একটা query, তারপর JSON উত্তর
const http = require('http'), net = require('net'), readline = require('readline');
const db = net.connect(5432, '127.0.0.1');               // একটাই connection, আগে থেকে খোলা (pool-এর মতো)
if (process.env.NODELAY) db.setNoDelay(true);            // এখন না; কেন লাগে, chapter-এর শেষে
const waiting = [];                                      // উত্তরের অপেক্ষায় থাকা query-রা, পাঠানোর ক্রমে
readline.createInterface({ input: db }).on('line', l => waiting.shift()(JSON.parse(l)));
const query = q => new Promise(resolve => { waiting.push(resolve); db.write(q + '\n'); });

http.createServer(async (req, res) => {
  const t0 = performance.now();
  const pending = query('user 42');                      // query পাঠানো পর্যন্ত: আমাদের JS
  const t1 = performance.now();
  const user = await pending;                            // এখানে handler থামে; event loop অন্য কাজে যায়
  const t2 = performance.now();
  res.setHeader('content-type', 'application/json');
  res.end(JSON.stringify({ user, path: req.url }));      // উত্তর বানানো আর পাঠানো: আবার আমাদের JS
  const t3 = performance.now();
  console.error(`handler JS ${(t1 - t0 + t3 - t2).toFixed(2)} ms, waiting for db ${(t2 - t1).toFixed(2)} ms`);
}).listen(3000, '127.0.0.1');

DB-র সাথে যোগাযোগ একটা সাধারণ TCP connection-এ, প্রতি লাইনে একটা query, প্রতি লাইনে একটা উত্তর। আসল database driver-ও মূলত এটাই করে, শুধু protocol-টা আরও জটিল। TCP message-এর সীমানা রাখে না (Chapter 27), তাই দুই দিকেই readline byte-এর স্রোত থেকে লাইন কেটে দেয়। Handler নিজের JS-এ কতটা সময় নিল আর DB-র জন্য কতক্ষণ অপেক্ষা করল, সেটা আলাদা করে লিখে রাখে। এবার trace:

এবার strace -p-কে একটা আগে থেকে চালু process-এ জুড়ে দিয়েছি (-p = attach), আর -f দিইনি, তাই শুধু main thread-এর syscall এসেছে। -e trace= দিয়ে শুধু দরকারি syscall-গুলো বেছেছি। শেষের pipeline-এ সেই লাইনগুলো বাদ দিয়েছি, যেগুলো কাজ শেষে strace থামানোর সময় মাঝপথে কাটা পড়ে (EINTR)। Mac-এর terminal-এ cut -c1-100 together.txt চালিয়ে পুরো সময়রেখা দেখো; নিচে সেটা তিন ভাগে ভেঙে পড়ছি, আগে পুরো ছবিটা:

একটা request, সময় ওপর থেকে নিচে। নীল তীর একটা syscall: user mode থেকে kernel-এ কিছু দেওয়া। Amber তীর kernel কাউকে জাগিয়ে data দিচ্ছে। দুই "kernel" কলাম এখানে আসলে একই kernel, কারণ তিনটা process এক container-এ, loopback-এ। আলাদা machine হলে প্রতিটা পাশে নিজের kernel থাকত, মাঝে network।

প্রথম পাঁচটা লাইনের একটাও Node-এর না। Handshake-এর তিন packet (Chapter 26), তারপর curl-এর ৮৫ byte-এর GET আর তার ACK, সবই ০.১২ ms-এর মধ্যে। পুরো কাজটা kernel একা করেছে: connection তৈরি করে accept queue-তে রেখেছে, আর request-এর byte-গুলো সেই connection-এর receive buffer-এ (Chapter 27)। Node তখনো ঘুমিয়ে ছিল।

তারপর Node জাগে। তার ঘুমের epoll_pwait লাইনটা trace-এ নেই, কারণ সেটা strace জোড়ার আগেই শুরু হয়েছিল। Listening socket (fd ১৯) ready হওয়ায় সে জেগে accept4 করে। Queue থেকে connection-টা বের হয়ে একটা নতুন fd পায়, ২০, যেটা শুরু থেকেই non-blocking (SOCK_NONBLOCK, Chapter 28)। epoll_ctl(…ADD, 20…) দিয়ে সেটাকে event loop-এর তালিকায় যোগ করে (Chapter 29)। পরের epoll_pwait-এর timeout ০, আর উত্তর সাথে সাথে এসে যায়: fd ২০ ready, কারণ data আগে থেকেই বসে আছে। তারপর এক read-এ পুরো request। HTTP parse হয় user mode-এ, কোনো syscall ছাড়া, আর তারপর প্রথমবারের মতো তোমার handler চলে।

fd ১৬-এ ৮ byte-এর লেখা আর পড়া Node-এর নিজের ভেতরের ডাকাডাকি। এটা একটা eventfd, Chapter 37-এর বিদায়ের অংশে যেমন দেখেছিলে। এগুলো বাদ দিয়ে পড়ো। বাকি গল্প:

  • ৫.৮৫ — handler query() ডাকল: DB-র socket-এ (fd ১৮) একটা write। ১৬০ µs পরে packet-টা port ৫৪৩২-এ, আর তার ACK।
  • ৬.৩৩ — অন্য process, db.js, জেগে read করল। একই kernel, একই মুহূর্তে দুই process-এর কাজ।
  • ৭.৮০ — db.js-এর epoll_pwait-এর timeout ৪: তার setTimeout(…, 5)-এর বাকি সময়টা সে kernel-এর ভেতরে ঘুমায়।
  • ১০.৯৯ — Node-এর main thread-এরও কিছু করার নেই। Handler await-এ থেমে আছে, অন্য কোনো request নেই, তাই event loop ঘুমাতে যায়। Timeout ২৮৪৯৪ ms, মানে সবচেয়ে কাছের timer পর্যন্ত: http server প্রতি ৩০ সেকেন্ডে একবার পুরনো connection-গুলোর সময়সীমা পরীক্ষা করে, আর server চালু হয়েছে দেড় সেকেন্ড আগে। strace লাইনের সময়টা call শুরুর, আর ফলাফলটা এসেছে পরে: fd ১৮ ready।
  • ১৩.৭১ — db.js উত্তর লিখল। Packet গেল, আর kernel Node-কে জাগাল। read(18)-এ ২৫ byte, await-এর পরের লাইন চলতে শুরু করে।

এই chapter-এর সবচেয়ে জরুরি কথা এই অংশে। await মানে thread আটকে থাকা না (Chapter 19)। Handler থেমে আছে, কিন্তু main thread kernel-কে বলে দিয়েছে "এই fd-গুলোর যেকোনোটায় কিছু এলে জাগিও" (Chapter 29), তারপর ঘুমিয়েছে। এই ফাঁকে অন্য কোনো request এলে সে সেটা ধরত। Thread-per-request server-এ (Chapter 28) এই পুরো সময়টা একটা thread শুধু বসে থাকত।

তারপর একটাই writev: status line, header আর body মিলিয়ে ২০৬ byte, একটা syscall, একটা packet (Chapter 32-এর batching)। curl উত্তর পেয়ে connection বন্ধ করে ([F.])। Node-এর কাছে সেটা আসে read = ০ হিসেবে, মানে "ওপাশ আর কিছু পাঠাবে না"। Node তখন নিজের দিক থেকেও FIN পাঠায়, epoll_ctl(…DEL…) দিয়ে fd ২০-কে তালিকা থেকে সরায়, আর close করে। যে আগে বন্ধ করেছে, সেই curl-এর দিকের socket এখন TIME-WAIT-এ (Chapter 26)।

সময় কোথায় যায়

এবার strace আর tcpdump ছাড়া মাপা যাক। পাঁচটা request, একটার পর একটা। curl মাপে মোট সময়, আর server-এর নিজের লাইন বলে তার JS কতক্ষণ চলল:

# timing.sh — strace আর tcpdump ছাড়া: পাঁচটা request, একটার পর একটা
node db.js & sleep 0.3
node server.js 2> handler.txt & sleep 0.5
for i in 1 2 3 4 5; do

done

timing.sh-এর প্রথম দুই request, strace ছাড়া। দ্বিতীয়টায় ৭.৯ ms-এর মধ্যে তোমার handler-এর JS মাত্র ০.২৪ ms, মানে ৩%। বাকিটা DB-র অপেক্ষা আর সবার কাজ: kernel, HTTP parsing, curl। প্রথম request-এ মোট সময় প্রায় দ্বিগুণ, JS আট গুণ।

গরম অবস্থায় (দ্বিতীয় request থেকে) একটা request ৮ ms-এর মতো। তার মধ্যে DB-র অপেক্ষা ৭ ms: DB-র নিজের ৫ ms, সাথে দুই দিকের পথ আর দুই process-এর ঘুম থেকে জাগা। তোমার handler-এর JS ০.২–০.৫ ms। বাকি প্রায় ১ ms-এ সব মিলিয়ে: kernel-এর TCP/IP, Node-এর HTTP parse, curl নিজে। তাই এই endpoint দ্রুত করতে JS optimize করলে লাভ প্রায় নেই। লাভ আছে DB-র কাজ কমালে, বা DB-তে যাওয়াই এড়ালে, যেমন cache দিয়ে।

প্রথম request দ্বিগুণ সময় নেয়। JS ২ ms, কারণ handler আর http module-এর উত্তর পাঠানোর code এই প্রথম চলছে: V8-কে এগুলো তখনই parse করে bytecode বানাতে হয়, আর এরা interpreter-এ চলে, JIT-এর machine code-এ না (Chapter 4)। সাথে /etc/localtime পড়া। একেই বলে cold request। Deploy-এর পর প্রথম কিছু request, বা autoscaling-এ নতুন চালু হওয়া instance-এর প্রথম request ধীর হয় এই কারণে। তাই অনেকে traffic পাঠানোর আগে কয়েকটা warm-up request দিয়ে নেয়।

২০টা একসাথে: Chapter 27-এর ফাঁদ, নিজে থেকেই

Event loop DB-র অপেক্ষার সময় মুক্ত থাকে। তাহলে ২০টা request একসাথে এলে সবার অপেক্ষা একসাথে চলার কথা, আর মোট সময় একটা request-এর কাছাকাছি হওয়ার কথা। মেপে দেখি:

// burst.js — একই request ২০টা, একসাথে; আগে একটা একা, তুলনার জন্য
const http = require('http');
const get = () => new Promise(done => http.get('http://127.0.0.1:3000/user/42', r => r.resume().on('end', done)));
(async () => {
  await get();                                           // warm-up: প্রথম request-এর বাড়তি খরচ বাদ
  let t = performance.now();
  await get();
  console.log(`1 request:            ${(performance.now() - t).toFixed(1)} ms`);
  t = performance.now();
  await Promise.all(Array.from({ length: 20 }, get));
  console.log(`20 requests at once:  ${(performance.now() - t).toFixed(1)} ms`);
})();

একটা request ৭ ms, অথচ ২০টা একসাথে ৬১ ms। Event loop কি তাহলে কাজ করছে না? Packet-গুলো উত্তর দেয়। প্রথম দুই জোড়া (০ আর ১১.৯০ ms) হলো warm-up আর একা request: ৮ byte-এর query, ২৫ byte-এর উত্তর। Burst শুরু ২১.৮৩-এ:

  • ২১.৮৩ — ২০টা query-র প্রথমটা একা যায়, ৮ byte।
  • ২৮.৭৪ — বাকি ১৯টা যায় একসাথে, একটা packet-এ: ১৯ × ৮ = ১৫২ byte। মাঝের ৭ ms kernel এদের আটকে রেখেছিল, যতক্ষণ না প্রথম query-র ACK এল। ACK এসেছে db-র প্রথম উত্তরের সাথে, ২৮.৭৩-এ।
  • ৩৪.৫৯ — db-র দিকে একই ঘটনা। প্রথম উত্তর যায়, বাকি ১৮টা আটকে থাকে।
  • ৭৬.৭০ — ৪২ ms পরে, server-এর kernel-এর একটা খালি ACK। সাথে সাথে বাকি ১৮টা উত্তর একসাথে আসে, ১৮ × ২৫ = ৪৫০ byte।

এটা Chapter 27-এর Nagle আর delayed ACK। প্রেরকের kernel ছোট টুকরো আটকে রাখে, যতক্ষণ আগেরটার ACK না আসে (Nagle)। গ্রাহকের kernel ACK পাঠাতে দেরি করে, এই আশায় যে app উত্তর লিখলে ACK সেটার সাথে যাবে (delayed ACK, Linux-এ ~৪০ ms)। একজন ACK-এর অপেক্ষায়, অন্যজন ACK দিতে দেরি করছে, আর মাঝে ৪২ ms নষ্ট। Chapter 27-এ দেখেছিলাম http server নিজেই প্রতিটা connection-এ Nagle বন্ধ করে দেয় (TCP_NODELAY)। কিন্তু DB-র connection-টা আমাদের নিজের বানানো net connection, আর net-এ Nagle চালু থাকে। একা request-এ ধরা পড়ে না, কারণ তখন আটকে থাকা পরের টুকরো থাকেই না। একসাথে অনেকগুলো query গেলেই ফাঁদটা খোলে। সমাধান দুই দিকে এক লাইন, যেটা আগে থেকেই code-এ বসানো আছে, শুধু চালু করা বাকি:

docker run --rm -e NODELAY=1 -v "$PWD":/w -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq tcpdump >/dev/null 2>&1
  bash burst.sh | head -2'
1 request:            7.8 ms
20 requests at once:  13.1 ms

৬১ ms থেকে ১৩ ms। এবার ২০টা request-এর অপেক্ষা সত্যিই একসাথে চলেছে। একই test আমার Mac-এ, Docker ছাড়া, NODELAY ছাড়াই ১০–১৪ ms এসেছে: macOS-এর delayed ACK-এর নিয়ম আলাদা (Chapter 27)। মানে এই bug developer-এর Mac-এ লুকিয়ে থাকে, আর বেরোয় production-এর Linux-এ, load আসার পর। নিজে TCP-র উপর কিছু বানালে, বা কোনো database বা cache-এর client library ব্যবহার করলে, দেখে নিও সেটা noDelay চালু করে কি না।

COMMON MISCONCEPTION

"API ধীর, মানে আমার code ধীর।" এই server-এ গরম অবস্থায় handler-এর JS ৭.৯ ms-এর মধ্যে ০.২৪ ms। Profiler দিয়ে JS-কে দশ গুণ দ্রুত করলেও request দ্রুত হবে ৩%-এরও কম। আর burst-এর ৬১ ms-এ তোমার JS-এর কোনো দোষই ছিল না, ছিল দুই kernel-এর TCP-র নিয়মে। Latency-র বেশিরভাগ থাকে অপেক্ষায়: DB, network, kernel-এর buffer আর timer। তাই ধীর request-এর প্রথম প্রশ্ন "কোন লাইনটা ধীর" না, প্রশ্ন হলো "সময়টা কোথায় যাচ্ছে": CPU-তে, নাকি কারো অপেক্ষায়। কীভাবে ধরতে হয়, সেটা পরের chapter।

MENTAL MODEL

Request আসার আগে server epoll_pwait-এ ঘুমিয়ে থাকে। Handshake, request-এর byte, ACK — সব kernel একা সামলায়, accept queue আর receive buffer-এ রাখে। তারপর kernel Node-কে জাগায়। Node accept4 করে নতুন fd নেয়, epoll-এ যোগ করে, read করে, user mode-এ HTTP parse করে, আর handler চালায়। Handler DB-তে write করে await-এ থামে। Thread তখন আটকায় না, আবার ঘুমায়, আর অন্য request এলে ধরে। DB-র উত্তর এলে kernel জাগায়, read, JSON, একটা writev, আর FIN-এ read = ০ পেয়ে close। সময়ের হিসাবে তোমার JS সামান্য অংশ; বাকিটা অপেক্ষা আর kernel-এর কাজ। আর একসাথে অনেক request এলে যে জিনিস একা request-এ অদৃশ্য ছিল, যেমন Nagle, সেটাই সময়ের বড় অংশ হয়ে উঠতে পারে।
