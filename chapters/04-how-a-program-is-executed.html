PART 2 · FROM PROGRAM TO PROCESS

Chapter 4 — Program কীভাবে execute হয়

মানুষের লেখা source code থেকে CPU-তে চলা instruction পর্যন্ত পুরো পথ: compile, link, load, আর CPU-র নিজের loop।

আগের chapter-এর সারকথা: program হলো disk-এ রাখা একটা executable file — ভেতরে header, machine code আর initial data; process হলো সেই program-এর চলমান রূপ, যার জন্য kernel একটা PCB, নিজস্ব address space আর CPU context (register + program counter) রাখে। এই chapter-এ দুইটা ফাঁক ভরাট করব: ওই executable file-টা তৈরি হলো কীভাবে, আর file থেকে process-এ রূপান্তরটা ঠিক কীভাবে ঘটে।

CPU সংখ্যা বোঝে, মানুষ বোঝে শব্দ

Chapter 2-এ দেখেছি CPU শুধু তার instruction set-এর সংখ্যা বোঝে। হাতে লিখতে হলে তোমাকে d10083ff-এর মতো সংখ্যা মুখস্থ করতে হতো, আর ARM-এর জন্য লেখা জিনিস Intel-এ চালাতে পুরোটা আবার লিখতে হতো। কেউ এভাবে software লেখে না। মানুষ লেখে পড়ার উপযোগী ভাষায়, আর একটা program সেটাকে machine code-এ অনুবাদ করে। এই অনুবাদক program-এর নাম compiler।

উদাহরণ হিসেবে C ভাষার একটা ছোট program নেব — C এখানে শুধু একটা tool, কারণ এটা hardware-এর সবচেয়ে কাছের জনপ্রিয় ভাষা, আর node নিজেও মূলত C/C++-এ লেখা। C জানতে হবে না, প্রতিটা লাইন বলে দিচ্ছি:

#include <stdio.h>

int main(void) {
    printf("hello %d\n", 42);
    return 0;
}
  • #include <stdio.h> — JS-এর import-এর কাছাকাছি: compiler-কে জানায় printf নামে একটা function আছে। কিন্তু printf-এর আসল code এখানে আসে না, শুধু তার নাম আর কী কী argument নেয় সেটা আসে।
  • int main(void) { — main নামের function, C program-এর কাজ এখান থেকে শুরু। int মানে function-টা একটা integer ফেরত দেয়।
  • printf("hello %d\n", 42); — console.log-এর মতো। %d-এর জায়গায় সংখ্যাটা বসে, ঠিক template literal-এর ${42}-এর মতো; \n মানে নতুন লাইন।
  • return 0; — main থেকে ০ ফেরত দেওয়া মানে process-এর exit code ০, মানে সফল (Chapter 3)।

File-টা hello.c নামে save করো। macOS-এ cc command আগে থেকেই থাকে (না থাকলে xcode-select --install); Linux-এ gcc। নিচের সব command দুই জায়গাতেই চলে, শুধু output-এ ছোটখাটো পার্থক্য থাকবে — সেগুলো আলাদা করে দেখাব।

Compiler আর object file

প্রথমে শুধু compile করো, link না (-c flag):

cc -c hello.c -o hello.o
nm hello.o

hello.o হলো একটা object file: তোমার লেখা function গুলো machine code-এ অনুবাদ করা, কিন্তু এখনো চালানো যায় না। কেন যায় না, nm বলে দিচ্ছে। nm একটা file-এর symbol দেখায় — symbol মানে file-এর ভেতরে লিখে রাখা function বা variable-এর নাম, আর সেটা কোথায় আছে। Output:

0000000000000000 T _main
                 U _printf

(Linux-এ নামের সামনে _ থাকে না: main, printf।) T মানে "এই file-এর code অংশে আছে" — main আমরা লিখেছি, তাই আছে। U মানে undefined: এই file printf ব্যবহার করে, কিন্তু তার code এখানে নেই। Machine code-এর যেখানে printf-কে ডাকা হয়েছে, সেখানে আসলে একটা ফাঁকা জায়গা রয়ে গেছে — "printf-এর ঠিকানা পরে এখানে বসবে"।

Compiler নিজে printf-এর code ঢুকিয়ে দেয় না কেন? কারণ বড় project-এ হাজারটা source file থাকে; প্রতিটা আলাদা করে object file-এ compile করলে একটা file বদলালে শুধু সেটাই আবার compile করতে হয়। জোড়া লাগানোর কাজটা আলাদা একটা ধাপ।

Library আর linker

printf-এর code আছে একটা library-তে — library হলো আগে থেকে compile করা function-এর সংকলন, যাতে সবাই বারবার একই code না লেখে। C-র standard function গুলো থাকে libc-তে; Linux-এ file-টার নাম libc.so.6, macOS-এ এটা libSystem.B.dylib-এর অংশ।

Object file আর library জোড়া দিয়ে চালানোর উপযোগী executable বানানোর কাজ করে linker। cc-কে -c ছাড়া ডাকলে সে ভেতরে linker চালায়:

cc hello.o -o hello
./hello              # hello 42
nm hello | grep " U "
otool -L hello       # macOS: কোন library লাগবে
ldd hello            # Linux: একই প্রশ্ন

চমকপ্রদ ব্যাপার: executable hello-তেও nm এখনো দেখাচ্ছে U _printf! মানে linker printf-এর code copy করে ঢোকায়নি। সে শুধু লিখে রেখেছে "এই program চলতে libSystem.B.dylib লাগবে, printf সেখান থেকে নিও" — otool -L ঠিক সেটাই দেখাচ্ছে। Linux-এ ldd hello দেখায় libc.so.6 => /lib/aarch64-linux-gnu/libc.so.6। এর নাম dynamic linking: library-র code জোড়া লাগে program চালু হওয়ার মুহূর্তে। উল্টোটা, static linking-এ library-র দরকারি code executable-এর ভেতরেই copy হয়ে যায়। আজকের বেশিরভাগ program dynamic; কোনটা কখন ভালো, সেটা Chapter 33-এ।

JS দুনিয়ায় এর কাছাকাছি জিনিস হলো bundler: webpack বা esbuild তোমার import গুলো resolve করে একটা file বানায়। কোনো dependency bundle-এর ভেতরে ঢুকিয়ে দেওয়া হলো static linking-এর মতো, আর CDN থেকে runtime-এ load করা dynamic-এর মতো। তবে পার্থক্যটা মনে রেখো: linker কাজ করে machine code আর memory address নিয়ে — "printf-কে ডাকার instruction-এ আসল address বসাও" — module বা text file নিয়ে না।

node নিজেও এভাবে তৈরি: otool -L $(which node) চালালে আমার Mac-এ দেখায় সে libc++, libSystem, CoreFoundation, Security — এই চারটা library-র উপর নির্ভরশীল।

Compiler তোমার code-কে machine code-এ অনুবাদ করে, কিন্তু printf-এর জায়গাটা ফাঁকা রাখে। Linker ফাঁকটার হিসাব মেলায় — dynamic linking-এ সে library-র code copy করে না, শুধু লিখে রাখে কোন library লাগবে। আসল জোড়া লাগে program চালু হওয়ার সময়।

Executable-এর ভেতরে: header, segment, entry point

এবার kernel-এর দিক থেকে ভাবো। তাকে একটা file দিয়ে বলা হলো "চালাও"। সে জানবে কীভাবে কোন byte গুলো code (যেগুলো চালানো যাবে কিন্তু বদলানো যাবে না), কোনগুলো data (যেগুলো বদলানো যাবে), কোথা থেকে চালানো শুরু করতে হবে, আর কোন library লাগবে? File-টা যদি এলোমেলো byte হতো, kernel-এর আন্দাজ করা ছাড়া উপায় থাকত না।

তাই executable একটা নির্দিষ্ট format মেনে লেখা হয় — Linux-এ ELF (Executable and Linkable Format), macOS-এ Mach-O। নাম আলাদা, মূল জিনিস এক:

  • Header — magic number (Chapter 3-এর 7f 45 4c 46), কোন CPU-র জন্য, আর entry point: program-এর প্রথম instruction-টা কোথায়।
  • Segment — file-এর এক একটা টুকরা, যেটা memory-তে একসাথে বসানো হবে, নিজস্ব permission সহ: code-এর segment "পড়া + চালানো যাবে" (R E), data-র segment "পড়া + লেখা যাবে" (RW)।
  • Dynamic linker-এর path — library জোড়া লাগানোর দায়িত্ব কোন program নেবে (নিচে আলাদা section)।
EXPERIMENT — header আর segment পড়া

Linux-এ (বা debian Docker image-এ apt install gcc binutils করে):

readelf -h hello | grep Entry
readelf -lW hello | grep -E "LOAD|interpreter"

আমার output:

  Entry point address:               0x640
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD  0x000000 0x0000000000000000 ... 0x000884 0x000884 R E 0x10000
  LOAD  0x00fdc8 0x000000000001fdc8 ... 0x000270 0x000278 RW  0x10000

macOS-এ একই তথ্য: otool -l hello | grep -A3 LC_MAIN দেখায় entryoff 1120, আর otool -l hello | grep -A2 LC_LOAD_DYLINKER দেখায় /usr/lib/dyld।

দুইটা LOAD লাইন হলো দুইটা segment — প্রথমটা code (R E), দ্বিতীয়টা data (RW)। Entry point-এ একটা সূক্ষ্মতা আছে। Linux-এ 0x640 ঠিকানায় আছে _start নামের একটা ছোট function (nm hello | grep _start দিয়ে দেখো), যেটা C library নিজে যোগ করে; সে কিছু প্রস্তুতি সেরে তারপর main ডাকে। macOS-এ entry সরাসরি main: entryoff 1120-কে hex-এ লিখলে 0x460, আর nm hello বলছে _main আছে 0x100000460-এ — file-এর শুরুর ঠিকানা 0x100000000-এর সাথে 0x460 যোগ করলেই সেটা।

exec: kernel কীভাবে file থেকে process বানায়

Terminal-এ ./hello লিখে Enter চাপলে কী হয়? Chapter 3-এ দেখেছি shell একটা child process তৈরি করে। কিন্তু সেই নতুন child শুরুতে shell-এরই একটা copy, hello না। তাকে hello-তে রূপান্তর করতে child একটা syscall করে: execve — "আমার ভেতরের পুরনো program ফেলে দাও, এই file-টা চালাও"। সঙ্গে দেয় argument-এর তালিকা আর environment variable-এর তালিকা।

Kernel-এর যে অংশ এই কাজ করে তাকে বলে loader। ধাপগুলো:

  1. যাচাই: file-টা আছে কি না, magic number চেনা কি না, আর file-এ execute permission আছে কি না। chmod -x hello; ./hello চালিয়ে দেখো — উত্তর আসবে permission denied: ./hello; kernel execve-তেই আটকে দিয়েছে। (chmod +x hello দিয়ে ফেরত দাও।)
  2. পুরনো memory ফেলে দেওয়া: এই process-এর আগের program-এর (shell-এর copy) সব memory বাদ, নতুন ফাঁকা address space।
  3. Segment map করা: header দেখে code segment আর data segment-কে address space-এর নির্দিষ্ট জায়গায় বসায়, নিজ নিজ permission সহ। "বসায়" বলতে map করে — মানে ঠিক করে দেয় "address-এর এই range-এ file-এর ওই অংশ থাকবে"। পুরো file তখনই RAM-এ copy হয় না; CPU যখন কোনো অংশ প্রথমবার ছোঁয়, kernel তখন সেটুকু disk থেকে আনে (Chapter 9)। এজন্যই ১০৪ MB-এর node চালু হয়ে node -e "console.log(process.memoryUsage().rss / 2**20)"-এ দেখায় মাত্র ~৩৭ MB RAM ব্যবহার করছে।
  4. Stack তৈরি: নতুন process-এর জন্য একটা stack-এর জায়গা (কী জিনিস, Chapter 5-এ), আর তার মাথায় রেখে দেয় argument আর environment-এর তালিকা। argv মানে তুমি command-এ যা যা শব্দ লিখেছ; environment variable মানে PATH, HOME-এর মতো নাম=মান জোড়া।
  5. PC বসানো: program dynamically linked হলে kernel dynamic linker-কেও map করে, আর PC বসায় তার entry point-এ; না হলে সরাসরি program-এর entry point-এ। তারপর user mode-এ ফিরে যায় — CPU সেখান থেকে চালাতে শুরু করে।

ধাপ ৪ তোমার চেনা: Node-এর process.argv আর process.env ঠিক সেই তালিকাই পড়ে, যেটা kernel stack-এ রেখে গিয়েছিল।

node -e "console.log(process.argv)" hello world

Output: [ '/Users/you/.nvm/versions/node/v22.15.1/bin/node', 'hello', 'world' ]। আর একটা জিনিস লক্ষ করো: execve নতুন process বানায় না, একই process-এর ভেতরের program বদলায়। PID একই থাকে:

sh -c 'echo "shell pid: $$"; exec node -e "console.log(\"node pid: \" + process.pid)"'

আমার চালানোয়: shell pid: 87520, তারপর node pid: 87520। Shell-এর exec command সরাসরি execve ডাকে — তাই shell-টা নিজেই node-এ রূপান্তরিত হলো, নম্বর বদলাল না।

উপরে child process execve দিয়ে kernel-এ ঢোকে; মাঝের amber সারি loader-এর পাঁচ ধাপ। নিচে একই PID-এ user mode-এ ফেরা — কিন্তু এবার ডান থেকে বাঁয়ে পড়ো: প্রথমে dynamic linker চলে, তারপর main, আর শেষে printf আবার syscall করে terminal-এ লেখে।

Dynamic linker: প্রথম instruction আসলে তোমার না

Dynamic linking-এর ফাঁকটা মনে করো: hello-এর ভেতরে printf-এর ঠিকানা এখনো ফাঁকা। main চালু হওয়ার আগে কাউকে libc খুঁজে map করতে হবে আর ফাঁকটা ভরাট করতে হবে, না হলে printf ডাকার মুহূর্তে CPU অর্থহীন ঠিকানায় লাফ দেবে।

Kernel এই কাজ নিজে করে না — library খোঁজার নিয়ম (কোন folder-এ, কোন version) কাজের নীতির ব্যাপার, আর kernel-কে যত ছোট রাখা যায় তত নিরাপদ। তাই এই দায়িত্ব দেওয়া হয় একটা user-space program-কে: dynamic linker (Linux-এ ld.so, যেমন /lib/ld-linux-aarch64.so.1; macOS-এ dyld)। ওপরের ধাপ ৫-এ kernel PC বসিয়েছিল এরই entry point-এ। Dynamic linker তারপর দরকারি library গুলো একই process-এর address space-এ map করে, ফাঁকা ঠিকানা গুলো ভরাট করে, আর শেষে program-এর entry point-এ লাফ দেয়। মানে তোমার process-এর প্রথম user-space instruction গুলো তোমার না — dynamic linker-এর।

macOS-এ dyld-কে কাজ করতে দেখা যায়:

DYLD_PRINT_LIBRARIES=1 ./hello

Output-এর প্রথম দিকের লাইন:

dyld[87515]: <39E396B6-...> /private/tmp/.../hello
dyld[87515]: <4FED5EE2-...> /usr/lib/libSystem.B.dylib
dyld[87515]: <9CD7B1E1-...> /usr/lib/system/libcache.dylib
...
hello 42

hello 42 আসার আগে dyld একের পর এক library load করেছে। আর এটা শুধু ছোট C program-এর ব্যাপার না: একটা চলমান Node process-এর খোলা file-এর তালিকায় (lsof -p <PID>) আমি পেয়েছি txt REG /usr/lib/dyld — dyld সেই process-এর address space-এ map করা আছে।

এত ঝামেলা কেন? কারণ libc-র code একটাই কপি হয়ে RAM-এ থাকে আর শত শত process সেটা ভাগ করে ব্যবহার করে (code-এর অংশ কেউ বদলাতে পারে না বলে ভাগ করা নিরাপদ — Chapter 5)। আর libc-তে security fix এলে একটা file বদলালেই সব program ঠিক হয়ে যায়।

Fetch–decode–execute: "চলছে" মানে আসলে কী

Loader PC বসিয়ে দিল, dynamic linker main-এ লাফ দিল। এখন "program চলছে" — কিন্তু CPU-র ভেতরে এর মানে কী? উত্তরটা আশ্চর্যরকম সরল: CPU একটা loop চালায়, আর থামে না।

  1. Fetch: PC যে address দেখাচ্ছে, memory থেকে সেখানকার instruction পড়ো।
  2. Decode: সংখ্যাটা ভেঙে বোঝো — কোন কাজ (যোগ? memory থেকে আনা? লাফ?), কোন register নিয়ে।
  3. Execute: কাজটা করো।
  4. PC update: সাধারণত পরের instruction-এ সরাও; আর instruction-টা যদি লাফ হয়, তাহলে লাফের গন্তব্যে বসাও। তারপর আবার ১ নম্বর।

আধুনিক CPU সেকেন্ডে কয়েকশো কোটিবার এটা করে (আসলে অনেকগুলো instruction একসাথে ধাপে ধাপে এগিয়ে নেয় — Chapter 14), কিন্তু ধারণাটা এটাই। নিজের program-এর instruction গুলো দেখো:

otool -tvj hello              # macOS
objdump -d --disassemble=main hello    # Linux

macOS-এ main-এর মাঝখানের অংশ:

000000010000047c   d2800548   mov  x8, #0x2a
0000000100000480   f9000128   str  x8, [x9]
0000000100000484   90000000   adrp x0, 0
0000000100000488   9112b000   add  x0, x0, #0x4ac ; literal pool for: "hello %d\n"
000000010000048c   94000005   bl   0x1000004a0    ; symbol stub for: _printf
0000000100000490   b9400be0   ldr  w0, [sp, #0x8]

প্রথম column address, দ্বিতীয় column instruction-টা আসলে যে ৪ byte-এর সংখ্যা, তৃতীয়টা মানুষের পড়ার জন্য তার নাম (এই নামে লেখা রূপকে বলে assembly)। কয়েকটা জিনিস লক্ষ করো। mov x8, #0x2a — 0x2a মানে ৪২, তোমার সংখ্যাটা একটা register-এ রাখা হচ্ছে। Address গুলো ৪ করে বাড়ছে (47c, 480, 484…), কারণ arm64-এ প্রতিটা instruction ঠিক ৪ byte, তাই "পরের instruction" মানে PC + ৪। আর bl হলো লাফ: PC-কে printf-এর দিকে পাঠায়, আর ফেরার ঠিকানা (0x100000490) একটা register-এ রেখে যায়, যাতে printf শেষে ঠিক পরের লাইনে ফেরা যায়। (ফেরার ঠিকানা কোথায় জমা থাকে, সেটা Chapter 5-এর বড় বিষয়।)

বাঁয়ে memory-তে রাখা hello-র কয়েকটা instruction; PC এই মুহূর্তে bl _printf-এর দিকে তাকিয়ে আছে। ডানে CPU-র loop: fetch, decode, execute, তারপর PC সরাও। সাধারণ instruction-এর পরে PC ৪ বাড়ে; bl-এর পরে সে সোজা printf-এর ঠিকানায় চলে যায়।

তাহলে node server.js-এর বেলায়?

JavaScript-এ তো compile বা link-এর ধাপ দেখো না। তাহলে এই পুরো গল্প কোথায় খাটে? খাটে, শুধু অন্য জায়গায়। node server.js চালালে kernel যে executable load করে সেটা হলো node — ওপরের সব ধাপ (execve, segment map, dyld/ld.so, main) ঘটে node binary-র জন্য। Kernel-এর কাছে server.js নিছক একটা argument, argv[1]।

node -e "setTimeout(() => {}, 60000)" server-demo &
ps -o pid,comm,args -p $!

($! মানে shell-এর শেষ background process-এর PID।) Output-এ COMM column বলছে node — kernel-এর চোখে process-টার program হলো node, তোমার script না।

তোমার JS-এর machine code তাহলে আসে কোথা থেকে? node-এর ভেতরের V8 engine চালু হয়ে server.js-কে সাধারণ file হিসেবে পড়ে (read syscall দিয়ে), parse করে, প্রথমে নিজের একটা interpreter দিয়ে চালায় — interpreter মানে এমন code, যেটা তোমার program-কে machine code-এ না বদলে নিজে এক এক ধাপ পড়ে পড়ে কাজটা করে দেয়। যে function বারবার চলে, V8 সেটাকে চলার মাঝখানেই machine code-এ compile করে ফেলে — এর নাম JIT (just-in-time) compilation। মানে compiler আর linker-এর কাজটা JS-এর বেলায় ঘটে program চলাকালীন, process-এর নিজের memory-র ভেতরে। দেখো:

node --trace-opt -e "function add(a, b) { return a + b } let s = 0; for (let i = 0; i < 1e7; i++) s = add(s, i)" | grep add

Output-এ আসবে marking ... <JSFunction add ...> for optimization to TURBOFAN ... reason: hot and stable, তারপর completed optimizing ... add। TurboFan হলো V8-এর optimizing compiler — add গরম হয়ে উঠতেই সে সেটাকে arm64 বা x86-64-এর machine code বানিয়ে ফেলেছে, এবং এরপর থেকে CPU সরাসরি সেই instruction গুলো fetch-decode-execute করছে।

MENTAL MODEL

Source → compiler (অনুবাদ, ফাঁক রেখে) → linker (ফাঁকের হিসাব) → executable file → execve (kernel-এর loader: যাচাই, map, stack, PC) → dynamic linker (library জোড়া) → main → CPU-র অন্তহীন fetch-decode-execute। Node-এর বেলায় পুরো শিকলটা চলে node binary-র জন্য; তোমার JS-এর জন্য compile হয় পরে, চলার মাঝখানে, JIT দিয়ে।

CAN I EXPLAIN THIS?
  • nm hello.o-তে printf-এর পাশে U দেখায় কেন? Executable hello-তেও U থেকে যায় কেন — static linking হলে কী দেখাত?
  • execve-র সময় kernel-এর loader ধাপে ধাপে কী করে? Node-এর process.argv শেষ পর্যন্ত কোথা থেকে আসে?
  • exec node ... চালানোর আগে আর পরে PID একই থাকে কেন? execve আসলে কী বদলায়?
  • Dynamically linked program-এ process-এর প্রথম user-space instruction গুলো কার, আর এই দায়িত্ব kernel নিজে নেয় না কেন?
  • otool -tvj বা objdump -d-এর output-এ address গুলো ৪ করে বাড়ে কেন? bl instruction PC-র সাথে কী করে? আর node server.js-এ তোমার JS কখন machine code হয়?
