PART 4 · CPU

Chapter 12 — CPU-র ভিতরে

Fetch–decode–execute loop-এর পেছনের যন্ত্রপাতি: সবাইকে এক তালে রাখা ঘড়ি, একটা core-এর ভেতরে কে কী করে, তোমার if কীভাবে তুলনা আর লাফে বদলায়, আর এক chip-এ দুই রকম core কেন।

এতদূর CPU-কে আমরা দেখেছি বাইরে থেকে। Chapter 2: CPU চালায় instruction, কাজ করে ছোট দ্রুত register নিয়ে। Chapter 4: program counter (PC) দেখায় পরের instruction কোথায়, আর CPU অবিরাম fetch → decode → execute করে। Chapter 8: memory ছোঁয়া হয় load/store দিয়ে, cache হয়ে। এবার ঢাকনা খুলি — কোন যন্ত্র এই loop চালায়, আর কোন তালে।

Clock আর cycle: সবাই একই তালে

একটা CPU-তে কয়েকশো কোটি transistor। একটা যোগ করতে signal কিছু circuit-এর ভেতর দিয়ে যায়, আর প্রতিটা পথের দৈর্ঘ্য আলাদা, সময়ও আলাদা। প্রতিটা অংশ যদি নিজের সুবিধামতো ফলাফল পরের অংশে ঠেলে দিত, তাহলে কোনো অংশ অর্ধেক-তৈরি ফলাফল পড়ে ফেলত — কখন একটা মান "প্রস্তুত", কেউ জানত না।

সমাধান হলো একটা কেন্দ্রীয় ছন্দ: clock — একটা signal যেটা নির্দিষ্ট হারে ওঠানামা করে। প্রতিটা টিকে CPU-র সব অংশ একসাথে এক ধাপ এগোয়: আগের ধাপের ফলাফল ধরে রাখে, পরের কাজ শুরু করে। এক টিকের নাম cycle। সেকেন্ডে কতগুলো cycle, সেটাই clock-এর গতি — ৪ GHz মানে সেকেন্ডে ৪০০ কোটি cycle, এক cycle ০.২৫ ns। কোনো circuit-এর কাজ এক cycle-এর মধ্যে শেষ না হলে সেটা একাধিক cycle নেয়।

তোমার CPU-র clock মোটামুটি মাপা যায় JS দিয়েই। কৌশলটা: এমন একটা শিকল বানাও যেখানে প্রতিটা যোগ আগের যোগের ফলাফলের জন্য অপেক্ষা করে। একটা integer যোগ কমপক্ষে এক cycle নেয়, আর শিকলের যোগ গুলো পাশাপাশি চালানো যায় না — তাই প্রতি ধাপ কমপক্ষে এক cycle।

EXPERIMENT — clock.js
// প্রতিটা যোগ আগের যোগের ফলাফলের উপর নির্ভর করে,
// তাই CPU এগুলো একসাথে চালাতে পারে না — প্রতি ধাপে কমপক্ষে এক cycle।
function chain(n) { let x = 0; for (let i = 0; i < n; i++) x = (x + i) | 0; return x; }
chain(1e7);                                  // JIT গরম করো
const N = 1e9;
const t = process.hrtime.bigint();
chain(N);
const ns = Number(process.hrtime.bigint() - t);
console.log(`${(ns / N).toFixed(3)} ns per step  →  clock is at least ~${(N / ns).toFixed(1)} GHz`);

আমার Mac-এ কয়েকবার চালিয়ে এসেছে 0.225 থেকে 0.28 ns per step — সবচেয়ে ভালো run-এ clock is at least ~4.5 GHz।

প্রতি ধাপ যেহেতু কমপক্ষে এক cycle, আসল clock এই সংখ্যার সমান বা বেশি। M4 Pro-র performance core-এর ঘোষিত সর্বোচ্চ গতি প্রায় ৪.৫ GHz — সবচেয়ে ভালো run-এর সাথে হুবহু মিলে যায়, মানে সেই run-এ প্রতি ধাপ ঠিক এক cycle নিয়েছে। (node -p "require('os').cpus()[0].speed" আমার Mac-এ দেখায় 2400 — Apple Silicon-এ এই সংখ্যা বিশ্বাসযোগ্য না। Linux-এ lscpu | grep MHz ভালো উৎস।) আর run-ভেদে পার্থক্য কেন? আধুনিক CPU চাপ, তাপমাত্রা আর বিদ্যুতের হিসাব দেখে clock নিজেই বাড়ায়-কমায় — তাই একই মাপ দুইবার চালালে সংখ্যা একটু আলাদা আসে।

Core-এর ভেতরে: কে কী করে

Fetch-decode-execute একটা যন্ত্রের কাজ না — প্রতিটা ধাপের জন্য আলাদা বিশেষজ্ঞ circuit, আর execute ধাপে কাজের ধরন অনুযায়ী আলাদা আলাদা unit। একটা core-এর ভেতরে মোটা দাগে:

  • Front-end — PC দেখে L1 instruction cache থেকে instruction আনে (fetch), সংখ্যাটা ভেঙে বোঝে কী করতে হবে (decode), আর সামনে কোন দিকে লাফ আসতে পারে তা আন্দাজ করে (branch predictor — Chapter 14)।
  • Register file — সব register একসাথে। সাধারণ register (ARM-এ x0–x30), PC, SP, আর কিছু বিশেষ register: শেষ তুলনার ফলাফল (flags), আর CPU এখন user mode নাকি kernel mode (Chapter 1) — সেটাও এখানেই লেখা।
  • ALU (Arithmetic Logic Unit) — integer যোগ, বিয়োগ, তুলনা, bit-এর কাজ। একটা core-এ কয়েকটা ALU পাশাপাশি থাকে।
  • FPU / SIMD unit — দশমিক সংখ্যার হিসাব (floating point), আর একসাথে অনেকগুলো সংখ্যায় একই কাজ (vector)।
  • Load/store unit — memory-র সাথে লেনদেন: MMU আর TLB দিয়ে address অনুবাদ (Chapter 9), তারপর L1 data cache (Chapter 8)।
  • Branch unit — লাফের instruction চালায়: শর্ত মিললে PC-তে নতুন address বসায়।

Chapter 4-এর hello-র instruction গুলো মনে করো: mov x8, #0x2a আর add x0, x0, #0x4ac যায় ALU-তে; str x8, [x9] আর ldr w0, [sp, #0x8] যায় load/store unit-এ; bl _printf যায় branch unit-এ। আর আলাদা unit মানে আলাদা গতি — নিজে মাপো:

EXPERIMENT — units.js
// দুইটা শিকল: একটায় integer যোগ (ALU), আরেকটায় দশমিক যোগ (floating-point unit)
function intChain(n)   { let x = 0;   for (let i = 0; i < n; i++) x = (x + i) | 0; return x; }
function floatChain(n) { let x = 0.5; for (let i = 0; i < n; i++) x = x + 0.25;    return x; }
const N = 1e9;
for (const [label, fn] of [['integer add', intChain], ['float add  ', floatChain]]) {
  fn(1e7);
  const t = process.hrtime.bigint();
  fn(N);
  console.log(label, (Number(process.hrtime.bigint() - t) / N).toFixed(3), 'ns per step');
}

আমার Mac-এ: integer add 0.262 ns, float add 0.552 ns।

দুইটাই "একটা যোগ", কিন্তু দশমিক যোগের শিকল দ্বিগুণ ধীর। কারণ কাজটা করে আলাদা একটা unit — floating-point unit — যার একটা যোগ শেষ করতে কয়েক cycle লাগে, integer ALU-র লাগে এক। (V8 ছোট integer-এর জন্য integer instruction ব্যবহার করে আর দশমিকের জন্য floating-point — Chapter 6-এর Smi আর HeapNumber-এর ভাগ এখানেও কাজে লাগে।)

একটা performance core-এর ভেতরের মোটা দাগের নকশা (মাপ গুলো sysctl থেকে)। উপরের সারি PC ধরে instruction আনে আর ভাঙে; নিচে বিশেষজ্ঞ unit গুলো আসল কাজ করে, সবাই register file থেকে পড়ে আর সেখানেই লেখে। Load/store unit একাই memory-র দিকে যায়।

তোমার if কীভাবে তুলনা আর লাফ হয়

CPU instruction চালায় একটার পর একটা, PC + ৪ করে। তাহলে "যদি এটা হয় তবে ওটা করো" — এই সিদ্ধান্ত সে নেয় কীভাবে? উত্তরটা দুই ধাপে:

  1. একটা compare instruction দুইটা মান তুলনা করে, আর ফলাফল (বড়? ছোট? সমান?) register file-এর flags-এ লিখে রাখে।
  2. একটা conditional branch instruction flags দেখে: শর্ত মিললে branch unit PC-তে লাফের গন্তব্য বসায়; না মিললে PC স্বাভাবিকভাবে পরের instruction-এ যায়।

if, else, for, while, switch, && — সব শেষে এই দুই ধাপে নামে। Loop মানে শুধু একটা পেছনের দিকে লাফ, যতক্ষণ শর্ত মেলে। তোমার JS-এ এটা দেখা যায় V8-এর bytecode-এ — V8-এর নিজের বানানো একটা instruction set, যেটা তার interpreter চালায় (Chapter 4), দেখতে অনেকটা CPU-র instruction-এর মতো:

node --print-bytecode --print-bytecode-filter=check -e "function check(x) { if (x > 5) return 'big'; return 'small'; } check(7)"

লম্বা output-এর মাঝখানে check-এর পুরো দেহ (address গুলো ছেঁটে):

@ 0 : LdaSmi [5]                 ; 5 নাও
@ 2 : TestGreaterThan a0, [0]    ; argument x কি 5-এর চেয়ে বড়? ফলাফল রাখো
@ 5 : JumpIfFalse [5] (@ 10)     ; না হলে @10-এ লাফ দাও
@ 7 : LdaConstant [0]            ; 'big'
@ 9 : Return
@10 : LdaConstant [1]            ; 'small'
@12 : Return

ঠিক ওপরের দুই ধাপ: TestGreaterThan তুলনা করে, JumpIfFalse ফলাফল দেখে লাফ দেয় বা দেয় না। check গরম হয়ে উঠলে (Chapter 4-এর JIT) TurboFan এটাকে ARM-এর আসল cmp আর শর্তসাপেক্ষ b.-জাতীয় instruction-এ বদলে দেয় — তখন কাজটা করে core-এর ALU (তুলনা) আর branch unit (লাফ)।

এক chip-এ দুই রকম core

দ্রুত core বানাতে বড় circuit, উঁচু clock, আর প্রচুর বিদ্যুৎ লাগে। অথচ laptop বা phone-এর বেশিরভাগ কাজ — mail sync, backup, index বানানো — তাড়ার কিছু না। সব কাজ বড় core-এ চালালে battery অকারণে শেষ হয়।

তাই আজকের অনেক chip-এ দুই রকম core থাকে: performance core (P-core — বড়, দ্রুত, বেশি বিদ্যুৎ খায়) আর efficiency core (E-core — ছোট, ধীর, খুব কম বিদ্যুৎ)। Apple Silicon, Intel-এর নতুন chip, আর phone-এর ARM chip — সবাই এই পথে। কোন কাজ কোন core-এ যাবে, সেটা ঠিক করে OS-এর scheduler (Chapter 15)।

sysctl hw.perflevel0.name hw.perflevel0.physicalcpu hw.perflevel1.name hw.perflevel1.physicalcpu

আমার Mac-এ: Performance 8, Efficiency 4। দুই দলের cache-ও আলাদা মাপের: P-core-এর L1 data cache ১২৮ KB, E-core-এর ৬৪ KB; P-core-দের ভাগ করা L2 ১৬ MB, E-core-দের ৪ MB। macOS-এ একটা command দিয়ে কোনো process-কে "background" চিহ্ন দেওয়া যায় — তখন সে E-core-এ চলে। একই clock.js দুইভাবে চালাও:

time node clock.js                  # সাধারণ — P-core-এ
time taskpolicy -b node clock.js    # background — E-core-এ

আমার Mac-এ প্রথমটা 0.225 ns per step, মোট 0.245 total; দ্বিতীয়টা 2.046 ns per step, মোট 2.166 total। একই code, একই machine — প্রায় নয় গুণ ধীর, কারণ কাজটা ছোট core-এ গেছে, যে কম clock-এ আর কম শক্তিতে চলে। (Linux-এ hybrid Intel chip থাকলে lscpu -e-তে দেখবে বিভিন্ন CPU-র MAXMHZ আলাদা।) Benchmark চালানোর সময় এটা মনে রেখো: তোমার কাজ কোন core-এ পড়ল, তার উপর ফল বদলে যেতে পারে।

COMMON MISCONCEPTION

"যার GHz বেশি, সে দ্রুত।" GHz শুধু বলে সেকেন্ডে কতগুলো cycle; প্রতিটা cycle-এ কতটা কাজ হয় — সেটা বলে না। একটা core এক cycle-এ কয়েকটা instruction শেষ করতে পারে (কীভাবে, Chapter 14), আরেকটা হয়তো একটাই। ওপরের E-core-এর নয় গুণ ধীরতার একটা অংশ কম clock, বাকিটা ছোট core — প্রতি cycle-এ কম কাজ। দুইটা CPU-র তুলনা করতে হয় আসল কাজ চালিয়ে, সংখ্যার লেবেল দেখে না।

MENTAL MODEL

একটা core হলো ঘড়ির তালে চলা একটা কারখানা: front-end PC ধরে instruction আনে আর ভাঙে; বিশেষজ্ঞ unit গুলো (ALU, floating point, load/store, branch) আসল কাজ করে, register file-এ পড়ে-লেখে। প্রতিটা if হলো একটা তুলনা আর একটা শর্তসাপেক্ষ লাফ। আর একই chip-এ বড় আর ছোট core থাকতে পারে — তোমার কাজ কোনটায় পড়ল, তা ঠিক করে OS।
