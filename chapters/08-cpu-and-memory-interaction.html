PART 3 · MEMORY

Chapter 8 — CPU আর Memory-র কথাবার্তা

CPU একটা মান চাইলে ভেতরে ঠিক কী ঘটে: load আর store, cache-এ পাওয়া-না-পাওয়া, memory কেন টুকরো ধরে আসে, আর CPU কীভাবে আগেভাগে আনিয়ে রাখে।

Chapter 7-এর শেষ সংখ্যাগুলো মনে করো: RAM থেকে একটা মান আনতে এই Mac-এ ~১১৯ ns, মানে CPU-র প্রায় ৫০০ cycle। অথচ একই chase.js ১৬ KB-র array-তে দিল ~১.৪ ns। মাঝখানে কী আছে যেটা ৮০ গুণ তফাত গড়ে দিল? এই chapter সেই মাঝখানের গল্প। আর Chapter 4 থেকে একটা জিনিস লাগবে: CPU-র ভেতরে কয়েক ডজন register থাকে — সবচেয়ে দ্রুত, সবচেয়ে ছোট storage।

Load আর store: CPU memory ছোঁয় কীভাবে

CPU-র যে অংশ আসলে যোগ-বিয়োগ-তুলনা করে (Chapter 12-এ এর নাম পাবে: ALU), সে কাজ করে শুধু register-এর মান নিয়ে। কিন্তু তোমার data থাকে memory-তে — লাখ লাখ মান, register মাত্র কয়েক ডজন। তাই দুই জগতের মাঝে মান আনা-নেওয়ার জন্য আলাদা instruction লাগে:

  • Load — memory-র একটা address থেকে মান পড়ে register-এ আনো।
  • Store — register-এর মান memory-র একটা address-এ লেখো।

Chapter 4-এর hello-র disassembly-তে এরা ছিল:

str  x8, [x9]           ; store: register x8-এর মান লেখো x9-এ রাখা address-এ
ldr  w0, [sp, #0x8]     ; load:  (SP + 8) address থেকে ৪ byte পড়ে w0-তে আনো

ARM-এ (Apple Silicon) নিয়মটা কড়া: হিসাব শুধু register-এ, memory ছোঁয়া শুধু load/store দিয়ে। Intel/AMD-এর x86-এ একটা instruction-এর ভেতরেই memory থেকে পড়ে যোগ করা যায়, কিন্তু CPU ভেতরে সেটাকেও load আর যোগ — দুই ধাপে ভাঙে। মানে JS-এর s += a[i] CPU-র চোখে: a[i]-এর address হিসাব, load, যোগ। প্রতিটা a[i] একটা load; প্রশ্ন শুধু সেই load কত দূর পর্যন্ত যেতে হয়।

Cache: কাছে রাখা ছোট, দ্রুত copy

প্রতিটা load যদি RAM পর্যন্ত যেত, CPU-র জীবনের সিংহভাগ কাটত অপেক্ষায় — ৫০০ cycle বসে থেকে এক cycle কাজ। অথচ program-রা একটা জিনিস প্রায়ই করে: যা এইমাত্র ছুঁয়েছে, সেটাই আবার ছোঁয় — loop-এর counter, একই object-এর field, একই function-এর instruction।

তাই CPU-র গা ঘেঁষে রাখা হয় ছোট কিন্তু অনেক দ্রুত memory (Chapter 7-এর SRAM), যেখানে সম্প্রতি ব্যবহৃত memory-র copy থাকে। এর নাম cache। Load এলে CPU আগে cache-এ খোঁজে। পাওয়া গেলে cache hit — কয়েক cycle-এ কাজ শেষ। না পেলে cache miss — পরের, বড় কিন্তু ধীর স্তরে যেতে হয়। স্তরগুলো:

  • L1 — প্রতিটা core-এর নিজস্ব, সবচেয়ে ছোট আর দ্রুত।
  • L2 — বড়, একটু ধীর; কোনো CPU-তে core-প্রতি, কোনোটায় কয়েকটা core মিলে ভাগ করা।
  • L3 বা Apple-এর SLC (system level cache) — আরও বড়, সব core-এর জন্য এক।
  • তারপর RAM।

গুরুত্বপূর্ণ কথা: এটা পুরোপুরি hardware-এর কাজ। "এটা cache-এ রাখো" বলার কোনো সাধারণ instruction নেই, kernel-ও প্রতিটা load-এ মাথা ঘামায় না। তোমার হাতে একমাত্র লাগাম হলো access pattern — কোন ক্রমে, কতটা ছড়িয়ে memory ছুঁচ্ছ। তোমার machine-এর cache-এর মাপ দেখো:

sysctl hw.perflevel0.l1dcachesize hw.perflevel0.l2cachesize   # macOS (Apple Silicon)
lscpu --caches                                                 # Linux

আমার Mac-এ performance core-প্রতি L1 data cache 131072 byte (১২৮ KB), আর performance core-দের ভাগ করা L2 16777216 byte (১৬ MB)। Chapter 7-এর chase.js দিয়ে তিনটা মাপে চালালে ছবিটা পরিষ্কার: ১৬ KB-তে 1.4 ns (পুরোটা L1-এ আঁটে), ২৫৬ KB-তে 4.0 ns (L1-এ আঁটে না, L2-তে আঁটে), ৫১২ MB-তে 118 ns (কোথাও আঁটে না — প্রতিবার RAM)। প্রতিটা স্তরের পুরো মাপজোখ Chapter 13-এ।

একটা load বাঁ থেকে ডানে যায়, যতক্ষণ না কোনো স্তরে data পাওয়া যায়। RAM পর্যন্ত যেতে হলে ফেরার পথে পুরো একটা cache line আসে আর প্রতিটা স্তরে তার copy থেকে যায়। সময়গুলো এই Mac-এ chase.js দিয়ে মাপা।

Cache line: memory আসে টুকরো ধরে

Cache যদি প্রতিটা byte আলাদা করে রাখত, তাহলে প্রতিটা byte-এর পাশে লিখে রাখতে হতো "এটা কোন address-এর copy" — সেই হিসাবের খাতাই data-র চেয়ে বড় হয়ে যেত। তার উপর, program একটা byte ছুঁলে প্রায়ই পাশেরগুলোও ছোঁয় — array-র পরের element, object-এর পরের field।

তাই cache আর RAM-এর মধ্যে লেনদেন হয় নির্দিষ্ট মাপের টুকরো ধরে, যার নাম cache line। তুমি ৪ byte চাইলেও RAM থেকে আসে পুরো line; তার পরে সেই line-এর যেকোনো byte ছোঁয়া মানে hit। মাপটা CPU-ভেদে আলাদা:

sysctl -n hw.cachelinesize            # macOS — Apple Silicon-এ 128
getconf LEVEL1_DCACHE_LINESIZE        # Linux — Intel/AMD-এ সাধারণত 64

এবার প্রমাণ। নিচের script ১২৮ MB জুড়ে ছড়ানো ১০ লাখ line-এ একটা এলোমেলো শিকল বানায়: প্রতিটা line-এর প্রথম ঘরে লেখা থাকে পরের কোন line-এ যেতে হবে (Chapter 7-এর pointer chase, শুধু এবার line ধরে)। তারপর দুইবার শিকল ধরে হাঁটে — একবার প্রতি line থেকে শুধু ওই একটা মান পড়ে, আরেকবার প্রতি line-এর ৩২টা মানই পড়ে যোগ করে।

EXPERIMENT — cacheline.js
const LINE = 128;                          // Apple Silicon-এ 128 byte; Intel/AMD-এ 64 দাও
const PER_LINE = LINE / 4;                 // এক line-এ কতগুলো Int32
const LINES = 2 ** 20;                     // ~১০ লাখ line × 128 B = 128 MB, cache-এ আঁটবে না
const a = new Int32Array(LINES * PER_LINE).fill(1);

// প্রতিটা line-এর প্রথম ঘরে লেখা থাকবে "পরের line কোনটা" — এলোমেলো একটা চক্র
const order = new Int32Array(LINES);
for (let i = 0; i < LINES; i++) order[i] = i;
for (let i = LINES - 1; i > 0; i--) {
  const j = Math.floor(Math.random() * (i + 1));
  const t = order[i]; order[i] = order[j]; order[j] = t;
}
for (let i = 0; i < LINES; i++) a[order[i] * PER_LINE] = order[(i + 1) % LINES];

function firstOnly() {                     // প্রতি line থেকে শুধু "পরের ঠিকানা"
  let line = 0;
  for (let k = 0; k < LINES; k++) line = a[line * PER_LINE];
  return line;
}
function wholeLine() {                     // একই পথ, কিন্তু প্রতি line-এর বাকি ৩১টা মানও যোগ করো
  let line = 0, s = 0;
  for (let k = 0; k < LINES; k++) {
    const base = line * PER_LINE;
    for (let j = 1; j < PER_LINE; j++) s += a[base + j];
    line = a[base];
  }
  return line + s;
}
for (const [label, fn] of [['1 value per line   ', firstOnly], ['all 32 values/line ', wholeLine]]) {
  fn();
  const t = performance.now();
  fn();
  const ms = performance.now() - t;
  console.log(label, ms.toFixed(0).padStart(4), 'ms  =', (ms * 1e6 / LINES).toFixed(0), 'ns per line');
}

আমার Mac-এ:

1 value per line     124 ms  = 118 ns per line
all 32 values/line   128 ms  = 122 ns per line

৩২ গুণ বেশি মান পড়া হলো, সময় বাড়ল মাত্র ৩%। প্রতিটা line-এর দাম ~১১৮ ns — সেটা দেওয়া হয় প্রথম byte ছোঁয়ার সময়ই; তারপর বাকি ৩১টা মান এসে বসে আছে L1-এ, প্রায় বিনামূল্যে। উল্টো দিক থেকে ভাবলে: প্রতি line থেকে মাত্র একটা মান নিলে তুমি ১২৮ byte আনার দাম দিচ্ছ ৪ byte কাজে লাগাতে — বাকি ৯৭% bandwidth নষ্ট।

Store-ও line ধরেই কাজ করে। CPU একটা মান লিখলে সেটা প্রথমে লেখা হয় cache-এর line-এ, আর line-টা "বদলানো হয়েছে" (dirty) চিহ্ন পায়; RAM-এ ফেরত লেখা হয় পরে, যখন cache-এ জায়গা খালি করতে line-টাকে সরাতে হয়। এর নাম write-back। নাহলে একটা loop-এর counter-এর প্রতিটা ++ ১০০ ns-এর RAM যাত্রা হতো। দাম হলো একটা নতুন প্রশ্ন: একাধিক core-এর প্রত্যেকের নিজের L1-এ যদি একই line-এর আলাদা copy থাকে, আর একজন সেটা বদলায় — অন্যজন জানবে কীভাবে? উত্তর Chapter 13-এ।

Prefetcher: CPU যখন আগেভাগে আনে

একটা array শুরু থেকে শেষ পর্যন্ত পড়লেও প্রতি ৩২টা Int32-এ একবার নতুন line লাগে। CPU যদি প্রতিবার line-এর জন্য ~১০০ ns বসে থাকত, একটানা পড়াও ধীর হতো। অথচ Chapter 7-এ copy করার সময় ~৫৮ GB/s পেয়েছিলাম।

কারণ CPU-র ভেতরে একটা circuit আছে যে memory access-এর ধরন খেয়াল করে — "এ তো পরপর line পড়ছে" বা "এ প্রতি ৬৪ byte পরপর লাফাচ্ছে" — আর অনুমান করে পরের line গুলো চাওয়ার আগেই RAM থেকে আনিয়ে রাখে। এর নাম prefetcher। অনুমান মিললে load এসে দেখে data আগে থেকেই cache-এ। কিন্তু pattern না থাকলে সে কিছুই অনুমান করতে পারে না।

EXPERIMENT — prefetch.js
const N = 32 * 2 ** 20;                    // ৩ কোটির বেশি Int32 = 128 MB
const a = new Int32Array(N).fill(1);
const inOrder = new Int32Array(N);         // 0, 1, 2, 3, ...
const shuffled = new Int32Array(N);        // একই index গুলো, এলোমেলো ক্রমে
for (let i = 0; i < N; i++) inOrder[i] = shuffled[i] = i;
for (let i = N - 1; i > 0; i--) {
  const j = Math.floor(Math.random() * (i + 1));
  const t = shuffled[i]; shuffled[i] = shuffled[j]; shuffled[j] = t;
}
function sum(idx) { let s = 0; for (let k = 0; k < N; k++) s += a[idx[k]]; return s; }
for (const [label, idx] of [['in order', inOrder], ['shuffled', shuffled]]) {
  sum(idx);
  const t = performance.now();
  const s = sum(idx);
  console.log(label, (performance.now() - t).toFixed(0).padStart(5), 'ms  sum =', s);
}

আমার Mac-এ in order 17 ms, shuffled 168 ms — একই যোগফল (33554432), একই সংখ্যক load, ১০ গুণ পার্থক্য।

ক্রমানুসারে পড়লে দুইটা সুবিধা একসাথে: প্রতিটা line-এর ৩২টা মানই কাজে লাগে, আর prefetcher পরের line আগেই এনে রাখে। এলোমেলো ক্রমে প্রায় প্রতিটা load নতুন একটা line চায়, আর prefetcher কোনো pattern খুঁজে পায় না। (এলোমেলো হয়েও এটা Chapter 7-এর pointer chase-এর মতো ১১৮ ns প্রতি access না, কারণ এখানে পরের address আগের load-এর উপর নির্ভর করে না — CPU একসাথে অনেকগুলো miss চালিয়ে দিতে পারে। ওই কৌশল Chapter 14-এ।)

COMMON MISCONCEPTION

"Cache OS বা runtime manage করে; দরকার হলে কিছু একটা cache-এ 'রেখে' দেওয়া যায়।" CPU cache-এর বেলায় না। কোন line থাকবে, কোনটা বাদ যাবে — সব সিদ্ধান্ত hardware প্রতি nanosecond-এ নিজে নেয়। (Redis বা HTTP cache সম্পূর্ণ আলাদা জিনিস, শুধু নামটা এক।) তোমার লাগাম দুইটা: data কীভাবে সাজাচ্ছ (পাশাপাশি নাকি ছড়ানো), আর কোন ক্রমে ছুঁচ্ছ।

MENTAL MODEL

প্রতিটা load একটাই প্রশ্ন করে: "এই address-এর line এখন কোথায় আছে?" L1-এ হলে ~১ ns, L2-তে কয়েক ns, RAM-এ ~১২০ ns। Line আসে পুরোটা একসাথে (৬৪ বা ১২৮ byte), আর pattern বোঝা গেলে prefetcher আগেভাগে আনে। দ্রুত code মানে প্রায়ই কম instruction না — কম নতুন line।

CAN I EXPLAIN THIS?
  • Load আর store কী? JS-এর s += a[i] CPU-র ভাষায় কী কী ধাপে ভাঙে, আর তার কোন ধাপটার দাম অনিশ্চিত?
  • Cache hit আর miss কী? একটা load L1 থেকে RAM পর্যন্ত কোন ক্রমে খোঁজে, আর chase.js-এর ১৬ KB / ২৫৬ KB / ৫১২ MB-এর তিনটা সংখ্যা কোন স্তরের কথা বলে?
  • Cache line কী? cacheline.js-এ ৩২ গুণ বেশি মান পড়েও সময় প্রায় একই থাকল কেন?
  • prefetch.js-এ একই যোগফল এলোমেলো ক্রমে ১০ গুণ ধীর কেন? Prefetcher কখন সাহায্য করতে পারে না?
  • Write-back না থাকলে একটা loop-এর counter বাড়ানো কেন ভয়ংকর ধীর হতো? আর write-back কোন নতুন সমস্যা তৈরি করে?
