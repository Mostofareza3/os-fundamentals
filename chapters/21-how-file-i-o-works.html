PART 6 · STORAGE

Chapter 21 — File I/O ভিতরে কীভাবে কাজ করে

fs.readFile() লেখা থেকে disk-এর data হাতে পাওয়া পর্যন্ত — পুরো stack-টা এবার সিরিয়াসলি।

Stack-টা

Application        — read(fd, buf, 4096)
      ↓ system call
VFS                — "file" ধারণাটা সামলায়, fd → আসল file
File System (ext4) — file-এর byte → disk-এর কোন block, হিসাব রাখে
Page Cache         — data RAM-এ আছে? থাকলে এখানেই শেষ ✓
Block Layer        — disk request-দের queue, merge, schedule
Driver             — device-এর ভাষায় command
      ↓
Storage Device     — data পড়ে DMA-তে RAM-এ দেয়

একটা read-এর গল্প, step by step

  1. open("config.json") — kernel file-টা খুঁজে বের করে, process-এর file descriptor table-এ একটা entry বসায়, তোমাকে দেয় একটা ছোট number — fd (ধরো 3)। এরপরের সব কথাবার্তা এই fd দিয়েই।
  2. read(3, buf, 4096) — system call। Kernel-এ ঢুকলো।
  3. Filesystem হিসাব করে: এই file-এর প্রথম 4096 bytes মানে disk-এর অমুক block গুলো।
  4. Page cache check — block গুলোর data কি আগে থেকেই RAM-এ? থাকলে সরাসরি copy করে দাও — disk ছোঁয়াই লাগলো না। বাস্তবের বেশিরভাগ read এখানেই মিটে যায়।
  5. Cache miss হলে: block layer-এ request → driver → device। ততক্ষণ তোমার process Waiting state-এ; CPU অন্য কাউকে চালায় (Chapter 15, 17 জোড়া লাগছে দেখো)।
  6. Device DMA-তে data page cache-এ দেয়, interrupt দেয় (Chapter 11)। Kernel process-কে জাগায়, data user buffer-এ copy করে, read() return করে।

Write-এর গল্প: একটা মোচড় আছে

write(fd, data, len) return করলো মানে data disk-এ পৌঁছে গেছে? না। Default behavior: kernel data-টা page cache-এ লিখে page-টাকে dirty mark করে সাথে সাথেই return করে দেয়। Disk-এ আসল লেখা হয় পরে, background-এ (writeback)। ফলে write অবিশ্বাস্য fast লাগে — কারণ তুমি আসলে RAM-এ লিখেছ।

Trade-off পরিষ্কার: মাঝখানে power গেলে সেই dirty data হারিয়ে যায়। এজন্যই "সত্যি সত্যি disk-এ নামাও" বলার আলাদা system call আছে — fsync(fd)। Database-রা transaction commit-এ এটাই করে; এজন্যই durable write ধীর, আর এজন্যই Postgres-এর WAL config-এ fsync নিয়ে এত কথা।

কিন্তু শিকলটা দুই ধাপের না, তিন ধাপের — আর এটা না জানলেই "fsync করেছি তো, তাহলে গেল কীভাবে?" প্রশ্নটা জন্মায়:

write()
   ↓
page cache (dirty)
   ↓  fsync এখানে ঠেলে দেয়
device
   ↓  fsync flush command-ও পাঠায়
device-এর নিজের cache
   ↓  ← এই ধাপটাই বইয়ে সাধারণত থাকে না
media (power গেলেও টেকে)

fsync দুটো কাজ করে: dirty page গুলো device-এ পাঠায়, এবং device-কে "তোমার নিজের cache খালি করো" command দেয়। দ্বিতীয় কাজটা device না মানলে (consumer SSD-র volatile cache, barrier ছাড়া hdparm -W1, hypervisor-এ cache=unsafe) fsync সফল return করবে, কিন্তু data তখনো volatile cache-এ — power গেলে গেল। মানে fsync দরকারি, কিন্তু একা যথেষ্ট না — নিচের স্তরটাকেও সৎ হতে হয়।

আর একটা ফাঁদ, যেটা আসল data-loss bug-এর জন্ম দেয়: fsync fail করতে পারে, আর Linux-এ writeback fail হলে kernel dirty bit মুছে দিয়ে error টা একজন caller-কেই জানাতে পারে। ফলে একই fd-তে আবার fsync ডাকলে সে success return করবে যদিও data কখনো লেখা হয়নি। নিয়মটা তাই: fsync fail মানে "আবার চেষ্টা করি" না — মানে "এই data সম্ভবত চিরতরে গেছে"। (Postgres-এর ২০১৮-র "fsyncgate" এই নিয়েই।)

COMMON MISCONCEPTION

"write() সফল return করেছে মানে data নিরাপদ।" না — মানে data kernel-এর হাতে পৌঁছেছে। Durability চাইলে fsync (এবং তার দাম) লাগবে, আর fsync-এর return value দেখতেই হবে। এই এক ভুল বোঝাবুঝি থেকে বহু "power গেল, data গেল" ঘটনা জন্মেছে।

EXPERIMENT (Linux)

strace -e trace=openat,read,write,close cat /etc/hostname চালাও। নিজের চোখে দেখো cat-এর মতো সামান্য command-ও ঠিক এই system call গুলোই করে: open → fd পেলো → read → write (stdout-এ) → close। এই x-ray মেশিনটা (strace) মনে রেখো — Chapter 32-এ আবার আসবে।
