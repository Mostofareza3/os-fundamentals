PART 6 · STORAGE

Chapter 21 — How File I/O Works

fs.readFile() থেকে SSD পর্যন্ত প্রতিটা স্তর, fd-র পেছনের তিন স্তরের হিসাব, আর লেখার পথের সবচেয়ে বড় ফাঁদ — write() ফিরে আসা মানে data নিরাপদ না।

Chapter 2-এ একটা readFileSync-কে disk পর্যন্ত অনুসরণ করেছিলাম, আর Chapter 3-এ দেখেছিলাম kernel খোলা file-এর জন্য process-কে একটা ছোট সংখ্যা দেয় — file descriptor (fd)। এই chapter-এ সেই যাত্রার প্রতিটা স্তর খুলব, fd-র পেছনে আসলে কী আছে দেখব, তারপর উল্টো দিকের যাত্রা — লেখা — যেখানে production-এ data হারানোর বেশিরভাগ গল্পের জন্ম।

স্তরগুলো: কেন এত ভাগ

ভাবো kernel-এ কোনো ভাগ নেই। তাহলে read()-এর code-কে একসাথে জানতে হতো: file-টা ext4-এ নাকি APFS-এ নাকি USB drive-এর FAT-এ, disk-টা NVMe নাকি SATA নাকি network-এর ওপারে, data আগে পড়া হয়েছে কি না। প্রতিটা নতুন filesystem বা নতুন device এলে সব আবার লিখতে হতো। তাই kernel কাজটা স্তরে ভাগ করে, প্রতিটা স্তর শুধু তার ঠিক নিচেরটার সাথে কথা বলে:

  • VFS (virtual file system): সব filesystem-এর উপরে একটা সাধারণ স্তর। fd থেকে খোলা file খুঁজে বের করে, permission দেখে, তারপর নিচের আসল filesystem-কে ডাকে। এজন্যই একই read() সব ধরনের file-এ চলে।
  • Filesystem (Linux-এ সাধারণত ext4, Mac-এ APFS): "এই file-এর byte ০ থেকে ১৪" কথাটাকে অনুবাদ করে "disk-এর অমুক block"-এ (Chapter 22)।
  • Page cache: RAM-এ রাখা file data-র কপি। Data এখানে পাওয়া গেলে নিচে আর যেতেই হয় না (Chapter 23)।
  • Block layer: disk-এর জন্য অনুরোধের লাইন। পাশাপাশি block-এর আলাদা অনুরোধ জুড়ে একটা বানায় (merge), আর ক্রম সাজায় — এই সাজানোর নিয়মকে বলে I/O scheduler।
  • Driver: device-এর নিজের ভাষায় command বানায় — NVMe-র বেলায় Chapter 11-এর descriptor আর doorbell।

একটা read নীল user space থেকে system call দিয়ে kernel-এ নামে, তারপর স্তরে স্তরে নিচে। Page cache-এ data পেলে (সবুজ) সেখান থেকেই ফেরত — disk ছোঁয়াই লাগে না। না পেলে block layer আর driver হয়ে SSD পর্যন্ত যায়, data DMA দিয়ে page cache-এ ফেরে, তারপর তোমার buffer-এ copy হয়।

Block layer-এর merge কতটা কাজ করে, Linux-এ দেখা যায়। /proc/diskstats-এ প্রতিটা disk-এর জন্য হিসাব রাখা থাকে; নিচের awk শুধু দরকারি column গুলো বাছে:

docker run --rm debian:bookworm-slim sh -c '
  cat /sys/block/vda/queue/scheduler
  awk "\$3==\"vda\"{print \"reads\", \$4, \"merged\", \$5, \"| writes\", \$8, \"merged\", \$9}" /proc/diskstats'

আমার Docker VM-এ: none [mq-deadline] kyber — তিনটা scheduler আছে, বন্ধনীরটা চালু। আর reads 129537 merged 130847 | writes 279244 merged 430191 — লেখার অনুরোধের মধ্যে ৪ লাখেরও বেশি আলাদা অনুরোধ হিসেবে device-এ যায়ইনি, পাশের অনুরোধের সাথে জুড়ে গেছে। Chapter 20-এর শিক্ষাটাই kernel নিজে থেকে প্রয়োগ করছে: অনেক ছোট অনুরোধের চেয়ে কম বড় অনুরোধ সস্তা।

একটা read, system call ধরে ধরে

এবার Node আসলে কী চায়, দেখি। strace (Chapter 1) দিয়ে শুধু file-সংক্রান্ত system call গুলো ধরছি:

EXPERIMENT (Linux / Docker) — readFile-এর system call
docker run --rm -it --cap-add SYS_PTRACE node:22-bookworm-slim bash
apt-get update -qq && apt-get install -y -qq strace
echo '{"port": 8080}' > config.json

strace -f -e trace=openat,statx,read,close \
  node -e "require('fs').readFileSync('config.json')" 2>&1 | grep -A3 config.json
openat(AT_FDCWD, "config.json", O_RDONLY|O_CLOEXEC) = 17
statx(17, "", AT_STATX_SYNC_AS_STAT|AT_EMPTY_PATH, STATX_ALL, {... stx_size=15, ...}) = 0
read(17, "{\"port\": 8080}\n", 15) = 15
close(17)                   = 0

চারটা call, চারটা কাজ:

  1. openat: path থেকে file খুঁজে (Chapter 22) একটা fd দেয় — এখানে 17 (০ থেকে ১৬ Node নিজেই আগে খুলে রেখেছে)। O_RDONLY মানে শুধু পড়ব; O_CLOEXEC মানে এই process পরে অন্য program exec করলে (Chapter 4) সেই নতুন program এই fd পাবে না — ভুল করে fd ফাঁস হওয়া ঠেকাতে Node সব file-এ এটা দেয়।
  2. statx: file-এর তথ্য (metadata) — এখানে দরকার size, stx_size=15, যাতে ঠিক ১৫ byte-এর buffer বানানো যায়।
  3. read: ১৫ byte চাইল, ১৫ byte পেল।
  4. close: fd ফেরত দিল, kernel তার হিসাব মুছে ফেলল।

Async fs.promises.readFile-এ একই চারটা call, কিন্তু একটা মজার পার্থক্য। একই command-এ readFileSync-এর জায়গায় require('fs').promises.readFile('config.json') দিলে আমার output-এ (ছাঁটা):

[pid   147] openat(AT_FDCWD, "config.json", O_RDONLY|O_CLOEXEC) = 17
[pid   140] read(16, "\1\0\0\0\0\0\0\0", 1024) = 8
[pid   148] statx(17, "", ...) = 0
[pid   140] read(16, "\1\0\0\0\0\0\0\0", 1024) = 8
[pid   149] read(17, "{\"port\": 8080}\n", 15) = 15
[pid   140] read(16, "\1\0\0\0\0\0\0\0", 1024) = 8
[pid   150] close(17)                   = 0

চারটা কাজ চারটা আলাদা thread-এ (pid 147, 148, 149, 150) — Chapter 19-এর libuv thread pool। আর প্রতিটার পরে main thread (pid 140) fd 16 থেকে ৮ byte পড়ছে। Fd 16 একটা eventfd: kernel-এর ভেতরের একটা ছোট counter, যেটা fd হিসেবে পাওয়া যায়। Pool-এর thread কাজ শেষে এতে লেখে, আর main thread-এর event loop সেটা দেখে জেগে ওঠে: "একটা কাজ শেষ, তার callback চালাও।" একটা ছোট file পড়তে তাই চারবার thread বদল আর চারবার ঘুম ভাঙানো — এজন্যই অনেক ছোট file-এর বেলায় async readFile sync-এর চেয়ে ধীর হতে পারে, যদিও event loop আটকায় না।

fd, open file, inode: তিন স্তরের হিসাব

একটা প্রশ্ন: file-এর কোথা থেকে পড়ছি, সেই অবস্থান (offset) কে মনে রাখে? read(17, buf, 15)-এ তো কোনো অবস্থান দেওয়া নেই। Kernel আসলে তিন স্তরে হিসাব রাখে:

  • fd table: প্রতিটা process-এর নিজের তালিকা — fd নম্বর থেকে একটা "খোলা file"-এর দিকে ইশারা।
  • Open file description: প্রতিটা open() call-এ kernel একটা নতুন বানায়। এখানে থাকে offset আর খোলার সময়ের flag (পড়া না লেখা, append কি না)।
  • Inode: file-টা নিজে — size, permission, data কোথায় (Chapter 22)। একটা file-এর একটাই inode, যতবারই খোলা হোক।

তাহলে একই file দুইবার খুললে দুইটা আলাদা offset — আর দুজনেই শুরু থেকে লিখলে একে অন্যের উপর লিখবে:

EXPERIMENT — offsets.js
// offsets.js — একই file দুইবার খোলা: প্রতিটা open-এর নিজস্ব offset
const fs = require('fs');

fs.writeFileSync('log.txt', '');
const a = fs.openSync('log.txt', 'r+');   // দুইটা আলাদা open
const b = fs.openSync('log.txt', 'r+');
for (let i = 0; i < 3; i++) {
  fs.writeSync(a, `A${i}\n`);              // position না দিলে: "আমার offset থেকে লেখো"
  fs.writeSync(b, `B${i}\n`);
}
console.log('r+ :', JSON.stringify(fs.readFileSync('log.txt', 'utf8')));

fs.writeFileSync('log.txt', '');
const c = fs.openSync('log.txt', 'a');    // 'a' = O_APPEND: প্রতিটা write file-এর শেষে
const d = fs.openSync('log.txt', 'a');
for (let i = 0; i < 3; i++) {
  fs.writeSync(c, `A${i}\n`);
  fs.writeSync(d, `B${i}\n`);
}
console.log('a  :', JSON.stringify(fs.readFileSync('log.txt', 'utf8')));
r+ : "B0\nB1\nB2\n"
a  : "A0\nB0\nA1\nB1\nA2\nB2\n"

r+-এ A-র তিনটা লাইনই হারিয়ে গেছে: a আর b-এর offset আলাদা, দুজনেই ০ থেকে শুরু করেছে, আর B প্রতিবার A-র লেখার উপর লিখেছে। 'a' flag (O_APPEND) দিলে kernel প্রতিটা write-এর ঠিক আগে offset-কে file-এর শেষে সরায়, আর সরানো আর লেখা এক ধাপে করে — মাঝে কেউ ঢুকতে পারে না (Chapter 18-এর atomic)। একাধিক process একই log file-এ লিখলে (যেমন cluster mode-এ চলা কয়েকটা Node process) 'a' ছাড়া লেখা মানে log হারানো।

উল্টো ঘটনাও আছে: দুইটা fd একই open file description দেখাতে পারে — তখন offset ভাগাভাগি। Child process-কে নিজের একটা fd দিলে ঠিক এটাই হয় (Chapter 15-এ দেখেছ, fork-এ child parent-এর fd table-এর কপি পায়):

EXPERIMENT — inherit.js
// inherit.js — child process একই fd পেলে offset-ও ভাগাভাগি
const fs = require('fs');
const { spawnSync } = require('child_process');

const fd = fs.openSync('log.txt', 'w');           // O_APPEND ছাড়া
fs.writeSync(fd, 'P0\n');
spawnSync('node', ['-e', 'for (let i = 0; i < 3; i++) process.stdout.write(`C${i}\\n`)'],
          { stdio: ['ignore', fd, 'inherit'] });  // child-এর stdout = আমাদের fd
fs.writeSync(fd, 'P1\n');
console.log(JSON.stringify(fs.readFileSync('log.txt', 'utf8')));
"P0\nC0\nC1\nC2\nP1\n"

Parent-এর P1 child-এর লেখার পরে বসেছে, উপরে না — কারণ child-এর fd 1 আর parent-এর fd একই open file description দেখায়, তাই child লিখে offset যতদূর সরিয়েছে, parent সেখান থেকেই শুরু করেছে। Shell-এ node app.js > out.log চালালে app আর তার সব child একই file-এ গুছিয়ে লিখতে পারে এই কারণেই।

তিন স্তর: fd নম্বর process-এর নিজের; offset থাকে মাঝের open file description-এ; file নিজে (inode) একটাই। offsets.js-এর a আর b হলো open #1 আর #2 — আলাদা offset, তাই একে অন্যের উপর লেখে। inherit.js-এ parent-এর fd আর child-এর stdout দুটোই open #3 দেখায় — একটাই offset।

Write: ফিরে আসা মানেই disk-এ পৌঁছানো না

write() ফিরে এলে data কোথায়? সাধারণ অবস্থায় kernel data-টা শুধু page cache-এ copy করে, সেই page-কে dirty (RAM-এর কপি disk-এর চেয়ে নতুন) বলে দাগায়, আর সাথে সাথে ফিরে আসে। Disk-এ আসল লেখা হয় পরে, kernel-এর নিজের সময়ে — একে বলে writeback। এতে write খুব দ্রুত হয় আর কাছাকাছি অনেক write একসাথে disk-এ যেতে পারে। দাম: writeback-এর আগে power গেলে সেই dirty data হারায়।

"এখনই disk-এ নামাও" বলার system call হলো fsync (Node-এ fs.fsyncSync(fd))। কিন্তু Chapter 20-এর SSD-র ভেতরেও একটা ছোট volatile RAM আছে, যেখানে device নিজে লেখা জমায়। তাই শিকলটা তিন ধাপের: page cache → device-এর নিজের cache → flash। Power গেলে শুধু শেষ ধাপটা টেকে। Linux-এ fsync দুটো কাজ করে: dirty page গুলো device-এ পাঠায়, তারপর device-কে একটা flush command দেয় — "তোমার cache-ও খালি করো"। macOS-এ সাধারণ fsync প্রথম কাজটুকুই করে; পুরো পথ যেতে আলাদা একটা command লাগে — F_FULLFSYNC। মেপে দেখো:

EXPERIMENT — fsync.py আর fsync.js (macOS)
# fsync.py — macOS: সাধারণ fsync বনাম F_FULLFSYNC, প্রতিবার 100 byte লিখে
import os, fcntl, time
line = b'x' * 99 + b'\n'
def bench(label, sync):
    fd = os.open('t.txt', os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    t = time.perf_counter()
    for _ in range(200):
        os.write(fd, line)
        sync(fd)
    ms = (time.perf_counter() - t) * 1000
    os.close(fd)
    print(f'{label:18s} {ms/200:7.3f} ms per write')
bench('no sync', lambda fd: None)
bench('fsync', os.fsync)
bench('F_FULLFSYNC', lambda fd: fcntl.fcntl(fd, fcntl.F_FULLFSYNC))
os.remove('t.txt')
// fsync.js — Node-এর fsyncSync কত সময় নেয়
const fs = require('fs');
const fd = fs.openSync('t.txt', 'w');
const line = 'x'.repeat(99) + '\n';
const t = performance.now();
for (let i = 0; i < 200; i++) { fs.writeSync(fd, line); fs.fsyncSync(fd); }
console.log('node fsyncSync', ((performance.now() - t) / 200).toFixed(3), 'ms per write');
fs.closeSync(fd); fs.unlinkSync('t.txt');
no sync              0.001 ms per write
fsync                0.023 ms per write
F_FULLFSYNC          3.592 ms per write
node fsyncSync 3.766 ms per write

তিনটা আলাদা জগৎ। Sync ছাড়া write ১ µs — শুধু RAM-এ copy। সাধারণ fsync ২৩ µs — data device-এর হাতে পৌঁছেছে, কিন্তু device-এর cache-এ। F_FULLFSYNC ৩.৬ ms — device flash-এ লেখা শেষ করে তবে জবাব দিয়েছে; প্রায় দেড়শো গুণ ধীর, কারণ এটাই আসল কাজ। আর Node-এর fsyncSync পড়েছে তৃতীয় সারিতে: libuv macOS-এ নিজে থেকেই F_FULLFSYNC ব্যবহার করে। Chapter 2-এর disk.js-এ Mac-এ ২০০টা fsync-এ ৭২৫ ms লেগেছিল কেন, এখন বোঝা গেল — প্রতিবার ~৩.৬ ms।

একটা write-এর তিন ঠিকানা। লাল দুইটা RAM — power গেলে মুছে যায়; শুধু সবুজ flash টেকে। কোন call কোথায় পৌঁছে তবে ফেরে, আর আমার Mac-এ তার দাম কত, নিচে লেখা। (Linux-এর fsync নিজেই device-কে flush করতে বলে — তাই সেটা ডান প্রান্তে।)

দুইটা সতর্কতা, দুটোই বাস্তব data-হারানোর গল্প থেকে। এক, device নিজে মিথ্যা বলতে পারে: কিছু সস্তা SSD, বা virtual machine-এর disk যার setting-এ flush উপেক্ষা করা আছে, flush command পেয়েও সাথে সাথে "হয়ে গেছে" বলে। তখন fsync সফল, কিন্তু data তখনো volatile cache-এ। দুই, fsync নিজে fail করতে পারে (disk ভরা, device error)। Linux-এ writeback fail করলে kernel সেই page গুলোর dirty দাগ মুছে দিতে পারে, আর error-টা একবারই জানায় — তারপর একই fd-তে আবার fsync ডাকলে সফল ফেরে, যদিও data কখনো disk-এ পৌঁছায়নি। PostgreSQL ২০১৮-তে ঠিক এই ফাঁদে পড়েছিল ("fsyncgate"), আর তার পর থেকে fsync fail করলে Postgres আবার চেষ্টা না করে নিজেকে বন্ধ করে দেয়। নিয়মটা তাই: fsync-এর error মানে "আবার চেষ্টা করো" না, মানে "এই data হয়তো গেছে"।

Crash-safe লেখা: temp file আর rename

এবার একটা রোজকার কাজ: app-এর config বা state একটা JSON file-এ save করা। fs.writeFileSync('config.json', data) ভেতরে 'w' দিয়ে খোলে — আর 'w' প্রথমেই পুরনো file খালি করে দেয় (truncate), তারপর নতুনটা লেখে। মাঝপথে process মারা গেলে (crash, deploy-এর সময় kill -9, OOM killer) কী থাকে?

EXPERIMENT — torn.js
// torn.js — config লেখার মাঝপথে process মারা গেলে file-এ কী থাকে
const fs = require('fs');
const { spawnSync } = require('child_process');
const [role, how] = process.argv.slice(2);

function save(file, text, crash) {                  // সরাসরি file-এর উপর লেখা
  const fd = fs.openSync(file, 'w');                // 'w' আগে file-টা খালি করে দেয়
  fs.writeSync(fd, text.slice(0, text.length / 2));
  if (crash) process.kill(process.pid, 'SIGKILL');  // ঠিক এখানে crash
  fs.writeSync(fd, text.slice(text.length / 2));
  fs.fsyncSync(fd);
  fs.closeSync(fd);
}
function safeSave(file, text, crash) {              // আগে পাশের একটা file-এ, তারপর rename
  save(file + '.tmp', text, crash);
  fs.renameSync(file + '.tmp', file);
  const dir = fs.openSync('.', 'r');                // নতুন নামটাও disk-এ পাকা করো
  fs.fsyncSync(dir);
  fs.closeSync(dir);
}

if (role === 'child') {
  const text = JSON.stringify({ version: 2, items: Array.from({ length: 1e5 }, (_, i) => i) });
  (how === 'safe' ? safeSave : save)('config.json', text, true);
} else {
  for (const how of ['direct', 'safe']) {
    fs.writeFileSync('config.json', JSON.stringify({ version: 1 }));   // পুরনো, ঠিকঠাক config
    spawnSync(process.execPath, [__filename, 'child', how]);
    const text = fs.readFileSync('config.json', 'utf8');
    let verdict;
    try { verdict = 'valid, version ' + JSON.parse(text).version; } catch { verdict = 'BROKEN JSON'; }
    console.log(`${how.padEnd(6)} → ${text.length} bytes, ${verdict}`);
  }
}
direct → 294456 bytes, BROKEN JSON
safe   → 13 bytes, valid, version 1

Mac আর Docker-এর Linux — দুই জায়গাতেই হুবহু একই output।

সরাসরি লেখায় পুরনো config গেছে, নতুনটার অর্ধেক এসেছে — app পরের বার চালু হতেই JSON.parse-এ মরবে। Safe পদ্ধতিতে crash-এর পরেও config.json পুরনো, অক্ষত version 1; শুধু পাশে একটা আধা-লেখা config.json.tmp পড়ে আছে, যেটা পরের চালুতে মুছে দিলেই হয়। কৌশলটা rename-এ: একই folder-এর মধ্যে rename মানে folder-এর নামের তালিকায় "config.json" নামটাকে পুরনো file থেকে সরিয়ে নতুন file-এ বসানো (Chapter 22) — kernel এটা এক ধাপে করে। যে-ই file-টা খুলুক, হয় পুরো পুরনোটা পাবে, নয় পুরো নতুনটা; মাঝামাঝি কিছু কখনো না।

Power cut-এর বিরুদ্ধে দুইটা fsync-ও লাগে, আর দুইটাই কোডে আছে। Rename-এর আগে tmp file-এর fsync: না দিলে power cut-এর পরে এমন হতে পারে যে নতুন নাম disk-এ পৌঁছে গেছে কিন্তু ভেতরের data পৌঁছায়নি — ফলে একটা খালি বা ভাঙা config.json (ext4-এ ২০০৯ সালে ঠিক এই অভিযোগে বহু খালি file-এর ঘটনা ঘটেছিল)। আর rename-এর পরে folder-এর fsync: নামের তালিকাও তো disk-এর data, সেটার বদলও পাকা করতে হয়। npm-এর write-file-atomic package ঠিক এই কাজটাই করে।

COMMON MISCONCEPTION

"writeFileSync একটা call, তাই পুরো file একসাথে বদলায়।" না — সে আগে file খালি করে, তারপর লেখে, আর মাঝের যেকোনো মুহূর্তে process মারা যেতে পারে। আর write() বা writeFileSync সফল ফিরলেও data তখনো RAM-এ। পুরনো-বা-নতুন নিশ্চয়তা চাইলে temp file + rename; power cut-এর পরেও টেকার নিশ্চয়তা চাইলে তার সাথে fsync — আর fsync-এর error মানে data হয়তো গেছে।

MENTAL MODEL

File I/O হলো স্তরের সিঁড়ি: VFS → filesystem → page cache → block layer → driver → device। পড়া নামে যতক্ষণ না কোথাও data পাওয়া যায় — বেশিরভাগ সময় page cache-এই। লেখা উল্টো: সবচেয়ে উপরের সুবিধাজনক জায়গায় (RAM) রেখেই "হয়ে গেছে" বলে, আর নিচে নামে পরে। Durability মানে নিজে ধাক্কা দিয়ে নামানো (fsync), নামার দাম দেওয়া (ms), আর নামতে না পারলে সেটা শোনা। আর fd একটা নম্বর মাত্র — offset থাকে মাঝের open file description-এ, file থাকে inode-এ।

CAN I EXPLAIN THIS?
  • একটা read কোন কোন স্তর পেরোয়, আর page cache-এ data পেলে কোথায় থেমে যায়? Block layer-এর "merge" কী, আর /proc/diskstats-এ সেটা কীভাবে দেখা গেল?
  • readFileSync-এর strace-এ চারটা system call কী কী, প্রত্যেকে কী করে? Async readFile-এ সেগুলো কোন thread-এ চলে, আর main thread কীভাবে খবর পায়?
  • offsets.js-এ 'r+'-এ A-র লাইন হারাল কেন, আর 'a'-তে হারাল না কেন? inherit.js-এ P1 child-এর লেখার উপরে না বসে পরে বসল কেন?
  • write() ফিরে আসার পর data কোথায়? macOS-এ fsync ০.০২৩ ms কিন্তু F_FULLFSYNC ৩.৬ ms কেন — আর Node-এর fsyncSync কোনটা ব্যবহার করে?
  • torn.js-এ সরাসরি লেখায় JSON ভাঙল কেন, আর temp file + rename-এ ভাঙল না কেন? Rename-এর আগে আর পরে fsync লাগে কেন?
