PART 1 · THE BIG PICTURE

Chapter 2 — The System Architecture

Hardware-এর ভেতরে ঢুকব: CPU, RAM, storage কীভাবে জোড়া লাগানো, device কীভাবে CPU-কে ডাকে, আর একটা readFileSync পুরো পথটা কীভাবে পাড়ি দেয়।

Chapter 1-এর সারকথা এক লাইনে: তোমার code user mode-এ চলে আর hardware ছুঁতে পারে না; hardware ছোঁয় শুধু kernel, আর দুইয়ের মাঝখানের দরজা হলো system call। সেই chapter-এ hardware-কে চারটা বাক্সে সেরে দিয়েছিলাম। এবার বাক্সগুলো খুলব, কারণ সামনের প্রায় প্রতিটা chapter — memory, process, file, network — এই বাক্সগুলোর আচরণের উপর দাঁড়িয়ে।

CPU: এক hardware, অসংখ্য কাজ

একদম প্রথম দিকের computer গুলো একটা নির্দিষ্ট কাজের জন্য তৈরি হতো। অন্য কাজ করাতে চাইলে তার পাল্টে নতুন করে wiring করতে হতো — দিনের পর দিন লাগত। তুমি যদি প্রতিবার নতুন app install করতে গিয়ে laptop-এর ভেতরের তার বদলাতে, তাহলে software industry বলে কিছু থাকত না।

CPU এই সমস্যার সমাধান। CPU-র hardware স্থির, কখনো বদলায় না। সে শুধু একটা কাজ জানে: memory থেকে একটা instruction পড়ো, চালাও, তারপর পরেরটা পড়ো। Instruction আসলে একটা সংখ্যা, যার ভেতরে লেখা থাকে কী করতে হবে — যোগ, তুলনা, memory থেকে আনা, অন্য জায়গায় লাফ দেওয়া। কাজ বদলাতে চাইলে hardware না, শুধু memory-তে রাখা instruction-এর তালিকা বদলাও। এই তালিকাটাই program।

Instruction গুলো কাজ করে CPU-র ভেতরের কয়েকটা ছোট storage slot নিয়ে, যাদের বলে register। একটা core-এ মাত্র কয়েক ডজন register থাকে, প্রতিটায় একটা সংখ্যা রাখা যায় (৬৪-bit CPU-তে ৮ byte), আর এগুলো পুরো machine-এর সবচেয়ে দ্রুত storage। একটা বিশেষ register-এর নাম program counter (PC): এটা মনে রাখে পরের instruction টা memory-র কোথায় আছে। CPU প্রতিটা instruction শেষ করে PC সামনে সরায় — "program চলছে" বলতে আসলে এটুকুই বোঝায় (Chapter 4-এ বিস্তারিত)।

একটা শর্ত আছে: CPU কোন কোন instruction বোঝে, আর সেগুলো কোন সংখ্যা দিয়ে লেখা হয় — এই তালিকার নাম instruction set। Intel/AMD-র CPU বোঝে x86-64, Apple Silicon আর বেশিরভাগ phone বোঝে arm64। একটার জন্য বানানো program আরেকটায় সরাসরি চলে না। তোমার machine কোনটা?

node -p "process.arch"
file $(which node)

আমার Mac-এ দুটোই বলছে arm64 — node program-টা ARM-এর instruction দিয়ে লেখা। Intel Mac-এ এই একই file চলবে না, তার জন্য x86_64 version লাগবে।

RAM আর memory address

Register মাত্র কয়েক ডজন। অথচ তোমার Node server একসাথে লাখ লাখ মান নিয়ে কাজ করে — প্রতিটা request, প্রতিটা object, প্রতিটা string। এত data রাখার জন্য একটা বড় কাজের জায়গা লাগে, আর সেখানে প্রতিটা মানকে আলাদা করে চেনার উপায়ও লাগে। না হলে CPU বলবে কীভাবে "ওই মানটা আনো"?

RAM হলো সেই বড় কাজের জায়গা। RAM-কে ভাবো byte-এর একটা বিশাল array হিসেবে — এটা উপমা না, hardware আসলেই এভাবে আচরণ করে। প্রতিটা byte-এর একটা index আছে: ০, ১, ২, … এই index-এর নাম memory address। CPU যখন RAM থেকে কিছু পড়ে, সে বলে "address এত থেকে ৮ byte দাও"; লেখার সময় বলে "address এত-তে এই মান রাখো"। ২৪ GB RAM মানে মোটামুটি ২,৫৭০ কোটি আলাদা address।

Address গুলো সাধারণত hexadecimal-এ লেখা হয় — ১৬-ভিত্তিক সংখ্যা, যেখানে ০–৯-এর পরে a–f আসে (a=১০ … f=১৫), আর সামনে 0x বসিয়ে বোঝানো হয় এটা hex। Node-এ চেষ্টা করো:

node -p "[0xff, (255).toString(16), Buffer.from('Hi!')]"

Output: [ 255, 'ff', <Buffer 48 69 21> ]। শেষেরটা দেখো — "Hi!" string-টা memory-তে তিনটা পাশাপাশি byte: 0x48 (H), 0x69 (i), 0x21 (!)। প্রথম byte যে address-এ, পরেরটা তার ঠিক পরের address-এ।

তোমার JS object-এরও একটা address আছে, V8 শুধু সেটা তোমাকে দেখায় না। একটা debug flag দিয়ে দেখানো যায়:

node --allow-natives-syntax -e "const user = { name: 'Rahim' }; %DebugPrint(user)"

প্রথম লাইনে আসবে এরকম কিছু: DebugPrint: 0x257501fa9999: [JS_OBJECT_TYPE]। ওই 0x257501fa9999 হলো user object-টা memory-র কোন address-এ বসে আছে। (এটা আসলে "virtual" address — প্রতিটা process-কে OS যে নিজস্ব address-এর জগৎ দেয় তার ভেতরের ঠিকানা, Chapter 9-এ খুলে বলব। আপাতত ধরে নাও এটা RAM-এর একটা জায়গা।)

RAM-এর দুইটা সীমাবদ্ধতা মনে রাখো: volatile — power গেলে সব মুছে যায়; আর দামি — প্রতি GB-র দাম storage-এর চেয়ে অনেক বেশি।

Storage: ধীর, কিন্তু স্থায়ী

RAM volatile হলে তোমার code, তোমার database, তোমার photo — laptop বন্ধ করলেই সব হারাবে। এমন একটা জায়গা লাগবে যেখানে data power ছাড়াও টিকে থাকে, আর সস্তায় অনেক বেশি জায়গা পাওয়া যায়। সেটাই storage: SSD (flash chip-এ data রাখে, কোনো নড়াচড়ার অংশ নেই) বা পুরনো ধরনের hard disk (ঘুরন্ত চৌম্বক plate)।

দামটা দিতে হয় গতিতে। সময়ের একক আগে ঠিক করে নিই: ms (millisecond) = সেকেন্ডের হাজার ভাগের এক, µs (microsecond) = ms-এর হাজার ভাগের এক, ns (nanosecond) = µs-এর হাজার ভাগের এক। মোটা দাগের হিসাব (hardware ভেদে কম-বেশি হয়):

Data কোথা থেকে আসছেমোটামুটি সময়RAM-এর সময়টা ১ সেকেন্ড ধরলে
CPU register< ১ nsএক পলকেরও কম
RAM~১০০ ns১ সেকেন্ড
SSD~২০–১০০ µs৩–১৭ মিনিট
Hard disk~৫–১০ ms১৪–২৮ ঘণ্টা
একই data center-এর অন্য server~০.৫ msপ্রায় দেড় ঘণ্টা
অন্য মহাদেশের server~১৫০ msপ্রায় ১৭ দিন

এই টেবিলটা মাথায় গেঁথে রাখো — "software কেন slow" প্রশ্নের অর্ধেক উত্তর এখানেই। নিজের machine-এ পার্থক্যটা মাপো। নিচের script একই ২০০ লাইন একবার শুধু RAM-এ (array-তে) রাখে, আরেকবার disk-এ লেখে। Disk-এর বেলায় প্রতিটা লেখার পর fsyncSync ডাকা হয়েছে। কারণ সাধারণ write-এ kernel data আগে RAM-এ জমিয়ে রাখে আর পরে সুবিধামতো storage-এ পাঠায় (কেন, সেটা Chapter 23-এ)। আর fsync বললে kernel storage-এ লেখা শেষ হওয়া পর্যন্ত অপেক্ষা করে তারপর ফেরে — মানে আসল storage-এর গতি মাপা হয়।

EXPERIMENT — disk.js
const fs = require('fs');
const N = 200;
const line = 'x'.repeat(100) + '\n';

// ১) শুধু RAM-এ: একটা array-তে N বার রাখা
let t = performance.now();
const arr = [];
for (let i = 0; i < N; i++) arr.push(line);
console.log('RAM (array push)     :', (performance.now() - t).toFixed(3), 'ms');

// ২) storage-এ: প্রতিবার লিখে fsync — "সত্যি সত্যি storage-এ লেখো"
const fd = fs.openSync('test.txt', 'w');
t = performance.now();
for (let i = 0; i < N; i++) { fs.writeSync(fd, line); fs.fsyncSync(fd); }
console.log('Disk (write + fsync) :', (performance.now() - t).toFixed(3), 'ms');
fs.closeSync(fd);
fs.unlinkSync('test.txt');

আমার Mac-এ: RAM 0.013 ms, disk 725.560 ms — প্রায় ৫০,০০০ গুণ পার্থক্য। Docker-এর Linux-এ disk-এর অংশটা এসেছিল ~১০ ms। তোমার সংখ্যা আলাদা হবে, কিন্তু পার্থক্যটা শত বা হাজার গুণের ঘরেই থাকবে।

সবাইকে জোড়া লাগানো: bus, controller আর driver

CPU-কে RAM-এর সাথে কথা বলতে হয়, SSD-র সাথে, network card-এর সাথে, USB-র সাথে। প্রতিটা জোড়ার জন্য আলাদা তার টানলে তারের জঙ্গল হবে। তার উপর এই device গুলো CPU-র তুলনায় ভয়ংকর ধীর আর প্রত্যেকের কাজের নিয়ম জটিল — CPU যদি নিজে flash chip-এর প্রতিটা voltage সামলাতে বসে, অন্য কিছু করার সময় পাবে না।

প্রথম সমস্যার সমাধান bus: একটা ভাগ করা যোগাযোগের পথ, যেটা দিয়ে একাধিক component data আর command আদান-প্রদান করে। CPU আর RAM-এর মাঝে একটা আলাদা দ্রুত memory bus থাকে। SSD, network card, GPU-র মতো device গুলো বসে একটা I/O bus-এ — আজকের machine-এ সাধারণত PCIe।

দ্বিতীয় সমস্যার সমাধান device controller: প্রতিটা device-এর নিজস্ব একটা ছোট chip, যেটা ওই device-এর খুঁটিনাটি নিজেই সামলায়। CPU-কে flash-এর voltage বুঝতে হয় না। Controller-এর কয়েকটা নিজস্ব register থাকে, আর CPU সেখানে একটা সরল command লিখে দেয় — "block ৮৮,২১০ থেকে ৪টা block পড়ো, RAM-এর এই address-এ রাখো"। বাকিটা controller নিজে করে।

কিন্তু কোন controller কোন command বোঝে, সেটা model ভেদে আলাদা। এই জ্ঞানটা রাখে driver — kernel-এর ভেতরের সেই code, যেটা একটা নির্দিষ্ট ধরনের controller-এর ভাষা জানে। Chapter 1-এ যে abstraction-এর কথা বলেছিলাম, তার নিচের তলাটা এরাই: file system বলে "এই block গুলো পড়ো", driver সেটাকে ওই নির্দিষ্ট controller-এর command-এ অনুবাদ করে।

তোমার kernel-এ কোন কোন driver load করা আছে, দেখো:

# macOS
kmutil showloaded | grep -iE "nvme|wlan|apfs"

# Linux
lsmod | head

আমার Mac-এ এসেছে com.apple.iokit.IONVMeFamily (SSD-র driver; NVMe হলো আধুনিক SSD-র সাথে কথা বলার একটা standard), com.apple.driver.AppleBCMWLANCore (Wi-Fi chip-এর driver), আর com.apple.filesystems.apfs (macOS-এর file system)। সব মিলিয়ে kmutil showloaded | wc -l গুনলে ২৬০-এর বেশি।

CPU আর RAM একটা দ্রুত memory bus দিয়ে জোড়া; RAM-এর প্রতিটা byte-এর একটা address। বাকি device গুলো নিজ নিজ controller সহ I/O bus-এ বসে। Amber দাগটা interrupt-এর পথ (পরের section) — আঁকা হয়েছে শুধু SSD-রটা, কিন্তু প্রতিটা controller-এরই এমন পথ আছে।

Interrupt: device কীভাবে CPU-কে ডাকে

ধরো kernel SSD controller-কে command দিল "এই block গুলো পড়ো"। টেবিল অনুযায়ী এতে প্রায় ১০০ µs লাগবে — এই সময়ে একটা আধুনিক core কয়েক লাখ instruction চালিয়ে ফেলতে পারে। Kernel জানবে কীভাবে কখন কাজ শেষ হলো?

সরল উপায়: CPU বারবার controller-কে জিজ্ঞেস করবে "হয়েছে? হয়েছে?" — এর নাম polling। JS-এ এটা হলো setInterval দিয়ে প্রতি মুহূর্তে একটা flag চেক করা। সমস্যা হলো, ওই কয়েক লাখ instruction-এর সময়টা পুরো নষ্ট হয় প্রশ্ন করতে করতে। আর device যদি হাজারটা হয়, CPU-র সারাদিন কাটবে শুধু খোঁজ নিতে।

সমাধান হলো interrupt: device-এর কাজ শেষ হলে controller নিজেই একটা নির্দিষ্ট তার দিয়ে CPU-কে একটা hardware signal পাঠায়। তারপর:

  1. CPU হাতের instruction-টা শেষ করে, আর মনে রাখে সে কোথায় ছিল (PC আর দরকারি register গুলো সেভ করে)।
  2. CPU kernel mode-এ ঢোকে, আর kernel-এর interrupt handler-এ লাফ দেয় — boot-এর সময় kernel প্রতিটা ধরনের interrupt-এর জন্য যে code ঠিক করে রেখেছিল।
  3. Handler দেখে কী হয়েছে (যেমন "block পড়া শেষ"), যে program এই data-র জন্য অপেক্ষা করছিল তাকে জাগিয়ে দেয়।
  4. CPU আগের জায়গায় ফিরে যায় — যেন কিছুই হয়নি।

মাঝের পুরো সময়টা CPU অন্য কাজ করতে পারল। এটা JS-এর event listener-এর মতো শোনালেও পার্থক্য আছে: এটা কোনো software callback না, CPU chip-এর একটা physical input, যেটা চলমান যেকোনো code-কে মাঝপথে থামিয়ে দিতে পারে।

এখান থেকে Chapter 1-এর একটা রহস্যের উত্তরও আসে। while(true){} loop কোনো syscall করে না, kernel-কে কখনো ডাকে না — তাহলে OS তাকে CPU থেকে সরাল কীভাবে? উত্তর: timer interrupt। CPU-র পাশে একটা timer chip থাকে, যেটা kernel-এর বেঁধে দেওয়া নিয়মিত ব্যবধানে (Linux-এ সাধারণত প্রতি ১–৪ ms-এ) interrupt পাঠায়। প্রতিটা tick-এ kernel নিয়ন্ত্রণ ফিরে পায় আর সিদ্ধান্ত নেয় এই program-কে চলতে দেবে নাকি অন্য কাউকে বসাবে। Program নিজে না চাইলেও kernel-এর হাতে নিয়ন্ত্রণ ফেরার এটাই নিশ্চিত পথ।

EXPERIMENT (Linux / Docker)

Linux kernel শুরু থেকে এ পর্যন্ত কতগুলো interrupt সামলেছে, সেই মোট হিসাব রাখে /proc/stat file-এর intr লাইনে। এক সেকেন্ডের ব্যবধানে দুইবার পড়ো:

docker run --rm alpine sh -c "awk '/^intr/{print \$2}' /proc/stat; sleep 1; awk '/^intr/{print \$2}' /proc/stat"

আমার চালানোয় এসেছে 38638665 আর 38640797 — প্রায় চুপচাপ বসে থাকা একটা VM-এও এক সেকেন্ডে ২,১০০-এর বেশি interrupt। আসল Linux machine-এ cat /proc/interrupts চালালে device ধরে ধরে আলাদা হিসাব দেখবে (Docker Desktop এই file-টা লুকিয়ে রাখে)।

Kernel-এর ভেতরের ভাগগুলো

Kernel-এর কাজের তালিকা এখন লম্বা: program-দের পালা ঠিক করা, memory ভাগ করা, file-এর নাম থেকে block খোঁজা, network packet সামলানো, শত শত ধরনের device-এর সাথে কথা বলা। সব এক জায়গায় জট পাকালে কেউ এই code maintain করতে পারত না। তাই kernel কয়েকটা ভাগে (subsystem) সাজানো, প্রত্যেকের দায়িত্ব আলাদা:

Subsystemকী সামলায়Linux-এ উঁকি দাও
Process managementকোন program চলছে, কে কখন CPU পাবেcat /proc/self/status
Memory managementকোন process কোন memory পাবে, কারটা কে ছুঁতে পারবে নাhead -3 /proc/meminfo
File systemFile-এর নাম আর folder-কে storage-এর block-এ রূপান্তরcat /proc/filesystems
Network stackSocket থেকে packet বানানো, packet থেকে socket-এ data পৌঁছানোcat /proc/net/tcp
Device driversপ্রতিটা controller-এর ভাষায় কথা বলাcat /proc/modules

ডানের command গুলো সবই /proc-এর file পড়ে। /proc আসলে disk-এ রাখা কোনো folder না — Linux kernel তার ভেতরের অবস্থা এখানে file-এর চেহারায় সাজিয়ে রাখে, আর তুমি পড়লে তখনই তৈরি করে দেয়। Docker-এ চালিয়ে দেখো: docker run --rm alpine cat /proc/meminfo। (macOS-এ /proc নেই; সেখানে একই তথ্য আসে vm_stat, ps, kmutil-এর মতো আলাদা আলাদা command থেকে।)

পুরো যাত্রা: একটা readFileSync

এবার সব টুকরো জোড়া দিই। তোমার code-এ এক লাইন:

const config = fs.readFileSync('config.json');

ধরে নিচ্ছি file-টা আগে কখনো পড়া হয়নি। যা যা ঘটে:

  1. User space: Node file খোলার আর পড়ার জন্য syscall করে — Chapter 1-এর strace-এ দেখা openat আর read। CPU kernel mode-এ ঢোকে।
  2. File system: config.json নামটা থেকে বের করে storage-এর কোন কোন block-এ file-টা আছে।
  3. RAM-এ আগে থেকে আছে কি? Kernel সম্প্রতি পড়া file-এর data RAM-এ রেখে দেয়, যাতে পরেরবার storage-এ যেতে না হয় — এই জায়গার নাম page cache (Chapter 23)। থাকলে সোজা ধাপ ৭-এ। এবার নেই।
  4. Driver: SSD controller-এর register-এ command লেখে: "এই block গুলো পড়ো, RAM-এর এই address-এ রাখো"।
  5. অপেক্ষা: তোমার process-কে kernel ঘুম পাড়িয়ে দেয়, আর CPU-তে অন্য কাউকে বসায়। CPU বসে থাকে না।
  6. SSD: controller flash থেকে data পড়ে সরাসরি RAM-এ লিখে দেয় — CPU-কে byte byte copy করতে হয় না; device-এর এই নিজে নিজে RAM-এ লেখার ক্ষমতার নাম DMA (Direct Memory Access, Chapter 11)। তারপর interrupt পাঠায়।
  7. Interrupt handler: kernel দেখে data এসেছে, সেটা Node-এর নিজের memory-তে (যেটা Node user mode থেকে ছুঁতে পারে) copy করে, আর তোমার process-কে জাগায়।
  8. ফেরা: read syscall result নিয়ে ফেরে, CPU আবার user mode-এ, readFileSync তোমাকে Buffer দেয়।

উপর থেকে নিচে সময় এগোচ্ছে। Amber খাড়া দাগের বাঁয়ে user space, ডানে kernel আর hardware। বাঁয়ের ধূসর বারটা লক্ষ করো: SSD যতক্ষণ কাজ করছে, তোমার process ততক্ষণ ঘুমিয়ে — কিন্তু CPU তখন অন্য process চালাচ্ছে।

COMMON MISCONCEPTION

"readFileSync মানে CPU বসে বসে disk-এর জন্য অপেক্ষা করে।" না — অপেক্ষা করে তোমার process, CPU না। Kernel তোমার process-কে ঘুম পাড়িয়ে CPU অন্য কাউকে দিয়ে দেয়। তাহলে Sync version খারাপ কেন? কারণ Node-এ তোমার সব JS চলে একটাই thread-এ — thread হলো একটা process-এর ভেতরে instruction চালানোর একটা স্বাধীন ধারা, kernel যাকে আলাদাভাবে ঘুম পাড়াতে বা জাগাতে পারে। সেই একমাত্র thread ঘুমালে ওই সময় তোমার server আর কোনো request ধরতে পারে না। CPU ফাঁকা থাকলেও তোমার app আটকে আছে। (Thread নিয়ে বিস্তারিত Part 5-এ, আর async I/O কীভাবে এই আটকে যাওয়া এড়ায় — Part 7-এ।)

MENTAL MODEL

যেকোনো I/O-এর গল্প একই ছাঁচে: user space-এর request → system call → kernel-এর subsystem → driver → controller → (অপেক্ষা) → interrupt → kernel → user space। File হোক বা network — ছাঁচ এক, শুধু মাঝের subsystem আর controller বদলায়।

CAN I EXPLAIN THIS?
  • CPU-র hardware কখনো বদলায় না, তবু একই CPU browser আর database দুটোই চালায় কীভাবে? Program counter এখানে কী ভূমিকা রাখে?
  • Memory address কী? Buffer.from('Hi!')-এর তিনটা byte-এর address গুলোর মধ্যে সম্পর্ক কী?
  • RAM থাকতে storage লাগে কেন, আর storage থাকতে RAM লাগে কেন? উত্তরে গতি আর স্থায়িত্ব দুটোই আনো।
  • Interrupt না থাকলে kernel-কে কীভাবে জানতে হতো যে SSD-র কাজ শেষ? আর কোনো syscall না করা while(true){} loop-কে kernel CPU থেকে সরায় কীভাবে?
  • readFileSync চলার সময় SSD যখন data আনছে, তখন CPU কী করছে, আর তোমার Node process কী করছে?
