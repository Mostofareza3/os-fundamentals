PART 3 · MEMORY

Chapter 9 — Virtual Memory

এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ ধারণাগুলোর একটা: প্রতিটা process কীভাবে নিজের একটা পুরো memory-জগৎ পায়, আর CPU প্রতিটা access-এ কীভাবে সেটাকে আসল RAM-এ অনুবাদ করে। ধীরে পড়ো।

এই chapter আগের অনেকগুলো ঝুলে থাকা সুতো একসাথে বাঁধবে, তাই আগে সেগুলো এক জায়গায় রাখি। Physical address: RAM-এর আসল ঠিকানা, যেটা শুধু kernel দেখে (Chapter 7)। Address space: প্রতিটা process-এর নিজস্ব address-এর জগৎ (Chapter 3), যার ভেতরে code, data, heap, stack নিজ নিজ permission (r-x, rw-) নিয়ে সাজানো (Chapter 5)। আর কয়েকটা প্রতিশ্রুতি: "লেখার চেষ্টায় CPU থামে" (Chapter 5-এর writecode), "১০৪ MB-র node চালু হয়ে মাত্র ৩৭ MB RAM নেয়" (Chapter 4), "kernel memory দেয় page ধরে" (Chapter 6)। এই chapter-এ সবগুলোর ব্যাখ্যা একটাই।

Physical address সরাসরি দিলে কী হতো

ধরো process গুলো RAM-এর physical address সরাসরি ব্যবহার করত — pointer মানে RAM-এর আসল ঠিকানা। তিনটা সমস্যা সঙ্গে সঙ্গে ধরা পড়ে:

  • পাহারা নেই। যেকোনো process যেকোনো address-এ পড়তে-লিখতে পারত। তোমার password manager-এর secret কোন address-এ আছে জানলেই Chrome-এর একটা buggy extension সেটা পড়ে ফেলত।
  • কে কোথায় বসবে? Chapter 4-এ দেখেছ linker main-কে বসিয়েছে 0x100000460-এ, আর সেই সংখ্যা machine code-এর ভেতরে লেখা। দুইটা program যদি একই address চায়? প্রতিবার load-এর সময় program-এর ভেতরের সব address নতুন খালি জায়গা অনুযায়ী বদলাতে হতো; আর RAM-এ program আসা-যাওয়ায় খালি জায়গা টুকরো টুকরো হয়ে যেত — Chapter 6-এর fragmentation, এবার পুরো machine-এর মাপে।
  • যা চাইবে, এখনই দিতে হবে। ১ GB-র একটা buffer বানালে ১ GB RAM এখনই আলাদা করে রাখতে হতো, তুমি সেটা ব্যবহার করো বা না করো। সব process-এর মোট চাহিদা RAM-এর মাপ ছাড়ালেই শেষ।

Idea: প্রতিটা process-কে নিজস্ব address-এর জগৎ

সমাধান: process যত address দেখে ও ব্যবহার করে — প্রতিটা pointer, PC, SP — সবই virtual address। প্রতিটা process-এর জন্য kernel একটা আলাদা অনুবাদ-তালিকা রাখে: "এই process-এর এই virtual address আসলে RAM-এর ওই physical address"। আর CPU প্রতিটা load, store আর instruction fetch-এর সময় hardware দিয়ে অনুবাদটা করে। Process কখনো জানে না তার data RAM-এর আসল কোথায় আছে।

এটা এখনই নিজের চোখে দেখা যায়। V8 সাধারণত নিজের heap এলোমেলো একটা জায়গায় বসায়, কিন্তু --random-seed দিয়ে এলোমেলোর বীজ বেঁধে দিলে দুইটা আলাদা process ঠিক একই virtual address বেছে নেয়। তখন দুইটা process একসাথে চালাও, আলাদা মান দিয়ে:

EXPERIMENT — same-address.js
// চালাও: node --allow-natives-syntax --random-seed=42 same-address.js 111
const box = { value: Number(process.argv[2]) };
%DebugPrint(box);                       // box কোন address-এ আছে
setTimeout(() => {
  console.log(`pid ${process.pid}: 2 সেকেন্ড পরেও box.value = ${box.value}`);
}, 2000);

দুইটা terminal-এ প্রায় একসাথে চালাও — একটায় শেষে 111, আরেকটায় 222। আমার Mac-এ (লম্বা output থেকে দরকারি লাইন):

# terminal 1
DebugPrint: 0x23143ad24b49: [JS_OBJECT_TYPE]
pid 93215: 2 সেকেন্ড পরেও box.value = 111

# terminal 2
DebugPrint: 0x23143ad24b49: [JS_OBJECT_TYPE]
pid 93223: 2 সেকেন্ড পরেও box.value = 222

দুইটা process একই মুহূর্তে জীবিত, দুইটার box হুবহু একই address-এ — 0x23143ad24b49। অথচ একটায় ১১১, আরেকটায় ২২২, কেউ কারও মান মুছে দেয়নি। একই address দুই জায়গায় দুই রকম মান রাখতে পারে শুধু তখনই, যখন address-টা আসল জায়গা না — প্রত্যেকের নিজের অনুবাদ-তালিকা একই সংখ্যাকে RAM-এর আলাদা জায়গায় পাঠাচ্ছে। Chapter 3-এর দুই terminal-এর দুই count-এর রহস্যের সমাধানও এটাই।

Page, frame, page table

অনুবাদ-তালিকা byte ধরে রাখা অসম্ভব — প্রতি byte-এর জন্য একটা ৮-byte-এর entry লাগলে তালিকাটাই memory-র চেয়ে আটগুণ বড় হতো। তাই অনুবাদ হয় বড় টুকরো ধরে:

  • Page — virtual address space-এর নির্দিষ্ট মাপের একটা টুকরো।
  • Frame (বা page frame) — physical RAM-এর একই মাপের একটা টুকরো।
  • Page table — প্রতিটা process-এর নিজস্ব তালিকা: কোন page কোন frame-এ বসানো, আর সেই page-এর permission কী (পড়া, লেখা, চালানো যাবে কি না; user mode থেকে ছোঁয়া যাবে কি না)। Kernel এটা বানায় আর বদলায়; process নিজে এটা ছুঁতে পারে না।
getconf PAGESIZE

আমার Mac-এ 16384 (১৬ KB — Apple Silicon-এর মাপ), Docker-এর Linux-এ 4096 (৪ KB — বেশিরভাগ Linux machine-এর মাপ)। এখন একটা address-কে দুই ভাগে ভাঙা যায়। ১৬ KB = ২১৪ byte, তাই address-এর নিচের ১৪টা bit হলো page-এর ভেতরে কত দূরে (offset), আর বাকি উপরের bit গুলো হলো page number। ওপরের box-এর address দিয়ে Node-এই হিসাব করো:

node -e "
const addr = 0x23143ad24b49n;
console.log('page number:', '0x' + (addr >> 14n).toString(16));
console.log('offset     :', '0x' + (addr & 0x3fffn).toString(16));"

Output: page number: 0x8c50eb49, offset: 0xb49। অনুবাদের সময় শুধু page number বদলায় — page table থেকে frame number আনা হয় — আর offset হুবহু থাকে। দুই process-এর page number একই (0x8c50eb49), কিন্তু দুইজনের page table সেটাকে আলাদা frame-এ পাঠায়।

একটা বাস্তব সূক্ষ্মতা: ৬৪-bit address space বিশাল আর প্রায় পুরোটা ফাঁকা, তাই page table একটা সমতল তালিকা না — কয়েক স্তরের একটা গাছ (সাধারণত ৪ স্তর), যাতে ফাঁকা অংশের জন্য কোনো entry-ই রাখতে না হয়। আর CPU-র একটা বিশেষ register জানে এই মুহূর্তে কোন process-এর গাছ ব্যবহার করতে হবে; kernel এক process থেকে আরেক process-এ গেলে সেই register বদলে দেয় (Chapter 17)।

দুই process-এর box একই virtual page-এ, কিন্তু দুইজনের page table তাকে আলাদা frame-এ (৮৭ আর ৪১২) পাঠায় — তাই মান আলাদা। Libc আর node-এর code কেউ বদলাতে পারে না, তাই দুজনের page table একই frame দেখায় — RAM-এ একটাই copy। B-এর একটা page কখনো ছোঁয়া হয়নি, তার পেছনে এখনো কোনো frame নেই। (Frame নম্বরগুলো বোঝানোর জন্য বানানো।)

MMU আর TLB: প্রতিটা access-এ অনুবাদ

অনুবাদ হয় প্রতিটা memory access-এ — প্রতি সেকেন্ডে শত কোটিবার। Software দিয়ে এটা করলে প্রতিটা load-এর আগে আরও কয়েকটা instruction লাগত; সব program কয়েক গুণ ধীর হয়ে যেত। তাই কাজটা করে CPU-র ভেতরের একটা hardware অংশ: MMU (Memory Management Unit)। প্রতিটা access-এ MMU:

  1. Virtual address থেকে page number আলাদা করে;
  2. page table-এ সেই page-এর entry খোঁজে, frame number আনে;
  3. permission মেলায় — এটা লেখা, অথচ page-টা r-x? এটা user mode, অথচ page-টা kernel-এর?
  4. frame number আর অপরিবর্তিত offset জুড়ে physical address বানিয়ে Chapter 8-এর cache/RAM-এর পথে পাঠায়।

ধাপ ২-এ একটা সমস্যা আছে: page table নিজেই RAM-এ থাকে, আর চার স্তরের গাছ মানে একটা অনুবাদের জন্য চারটা memory পড়া। প্রতিটা load-এর আগে চারটা বাড়তি load — অসহনীয়। তাই MMU-র ভেতরে একটা ছোট বিশেষ cache থাকে যেখানে সম্প্রতি ব্যবহৃত অনুবাদগুলো জমা থাকে: TLB (Translation Lookaside Buffer)। বেশিরভাগ access-এর অনুবাদ TLB-তেই মিলে যায়, প্রায় বিনামূল্যে; না মিললে MMU গাছ ধরে হেঁটে (page table walk) অনুবাদ বের করে আর TLB-তে রেখে দেয়। TLB-র দাম কত আর কখন সেটা সমস্যা হয় — Chapter 10।

Chapter 5-এর writecode এখন পুরোপুরি ব্যাখ্যা করা যায়: main-এর code যে page-এ, তার page table entry-তে "লেখা নিষেধ"। Store instruction এল, MMU ধাপ ৩-এ permission ভাঙা পেল, আর অনুবাদ না করে CPU-কে থামিয়ে kernel-কে ডাকল।

Page number যায় MMU-তে — আগে TLB, না পেলে RAM-এ রাখা page table-এর গাছ ধরে হাঁটা। Offset (dashed দাগ) অনুবাদ ছাড়াই সোজা নিচে নামে। Entry না থাকলে বা permission না মিললে অনুবাদ হয় না — kernel-কে ডাকা হয়, যেটা পরের section।

Page fault: illusion-এর সবচেয়ে চালাক অংশ

Process যত memory চায়, সব যদি সঙ্গে সঙ্গে RAM-এ বসাতে হতো, তাহলে ১ GB-র buffer বানালে ১ GB RAM তখনই আটকে যেত, আর ১০৪ MB-র node binary চালু হওয়ার আগেই পুরোটা disk থেকে পড়তে হতো — এমনকি যে অংশ কখনো চলবে না সেটাও।

Kernel এখানে চালাকি করে। Process memory চাইলে kernel শুধু লিখে রাখে "এই virtual range বৈধ, এই permission-এ", কিন্তু page table-এ কোনো frame বসায় না — entry-তে লেখা থাকে "present না"। Process প্রথমবার সেই page ছুঁলে MMU entry খালি পায় আর CPU-কে থামিয়ে kernel-কে ডাকে। এর নাম page fault। Kernel-এর handler তখন দেখে:

  • Address বৈধ, শুধু এখনো বসানো হয়নি — একটা খালি frame নাও, শূন্য দিয়ে ভরো (বা file থেকে দরকারি অংশ পড়ো), page table-এ বসাও, আর যে instruction থেমেছিল সেটা আবার চালাও। Process টেরই পায় না। Disk ছাড়াই মেটানো এমন fault-কে বলে minor page fault।
  • Address অবৈধ, বা permission ভাঙা — process-কে signal পাঠিয়ে মেরে ফেলো। Chapter 5-এর Segmentation fault।
EXPERIMENT — lazy.js

process.resourceUsage().minorPageFault বলে এই process-এ এ পর্যন্ত কতগুলো minor fault হয়েছে; RSS (Chapter 6) বলে কতটা RAM আসলে দখলে।

const mb = n => (n / 2 ** 20).toFixed(0).padStart(5) + ' MB';
const faults = () => process.resourceUsage().minorPageFault;
const PAGE = 16384;                                  // macOS-এ 16 KB; Linux-এ 4096 দাও

console.log('start          rss', mb(process.memoryUsage().rss), '| minor faults', faults());
const buf = new Uint8Array(1024 * 2 ** 20);          // ১ GB চাইলাম
console.log('after alloc    rss', mb(process.memoryUsage().rss), '| minor faults', faults());
for (let i = 0; i < buf.length; i += PAGE) buf[i] = 1; // প্রতিটা page-এ মাত্র ১ byte লিখলাম
console.log('after touching rss', mb(process.memoryUsage().rss), '| minor faults', faults());

আমার Mac-এ:

start          rss    36 MB | minor faults 2655
after alloc    rss    38 MB | minor faults 2754
after touching rss  1066 MB | minor faults 68586

১ GB চাওয়ার পরেও RSS বাড়ল মাত্র ২ MB — kernel শুধু প্রতিশ্রুতি লিখেছে। তারপর প্রতিটা page-এ একটা করে byte লেখায় RSS লাফিয়ে ১ GB, আর minor fault বাড়ল ৬৫,৮৩২টা। হিসাব মেলাও: ১ GB ÷ ১৬ KB = ৬৫,৫৩৬ page — প্রায় প্রতিটা page-এর প্রথম ছোঁয়ায় একটা করে fault, kernel-এর একটা করে frame বসানো। (Linux-এ একই পরীক্ষায় fault অনেক কম আসে — কারণটা Chapter 10-এর huge page।)

একই কারণে প্রায় প্রতিটা process-এর "চাওয়া" memory তার "পাওয়া" memory-র চেয়ে অনেক বড়। Linux-এ দুটো পাশাপাশি দেখা যায়:

docker run --rm node:22-alpine node -e "console.log(require('fs').readFileSync('/proc/self/status','utf8').match(/^Vm(Size|RSS).*$/gm).join('\n'))"

আমার output: VmSize: 421312 kB (virtual address space-এ মোট বৈধ করা range) আর VmRSS: 49816 kB (আসলে frame পাওয়া অংশ) — আটগুণের বেশি পার্থক্য। ps-এর VSZ আর RSS column-ও এই দুই জিনিস।

এই design থেকে ফাউ পাওয়া সুবিধা

একবার page table হাতে এলে kernel অনেক কৌশল করতে পারে শুধু table-এর entry সাজিয়ে:

  • Shared memory — কয়েকটা process-এর page table-এ একই frame বসিয়ে দাও। ওপরের ছবির libc আর node-এর code এভাবেই RAM-এ একবার থাকে।
  • Copy-on-write — process-এর copy বানানোর সময় memory copy না করে দুজনের page table-এ একই frame বসাও, কিন্তু "লেখা নিষেধ" চিহ্ন দিয়ে; কেউ লিখতে গেলে page fault হবে, তখন শুধু সেই page-টা copy করো। নতুন process বানানোর fork এভাবে প্রায় তাৎক্ষণিক (Chapter 15)।
  • File-কে memory হিসেবে map করা আর swap (RAM ভরে গেলে কম-ব্যবহৃত page disk-এ সরানো) — দুটোই page fault-এর উপর দাঁড়ানো; Chapter 10।
EXPERIMENT (Linux / Docker) — shared frame-এর প্রমাণ

Linux প্রতিটা mapping-এর জন্য /proc/<PID>/smaps-এ দুইটা সংখ্যা দেয়: Rss (এই mapping-এর কতটা RAM-এ আছে) আর Pss (proportional set size — shared page-এর দাম যতজন share করছে তাদের মধ্যে ভাগ করে দেখানো)। একটা sleep-এর libc code দেখো, তারপর আরও তিনটা sleep চালিয়ে আবার দেখো:

docker run --rm debian:bookworm-slim sh -c '
  sleep 100 & P=$!; sleep 0.3
  awk "/libc.so.6/ && /r-xp/ {f=1} f && /^(Rss|Pss):/ {print} f && /^Pss/ {exit}" /proc/$P/smaps
  for i in 1 2 3; do sleep 100 & done; sleep 0.3
  awk "/libc.so.6/ && /r-xp/ {f=1} f && /^(Rss|Pss):/ {print} f && /^Pss/ {exit}" /proc/$P/smaps'

আমার output: প্রথমে Rss: 816 kB, Pss: 271 kB; তিনটা বাড়তি process-এর পরে Rss: 816 kB, Pss: 136 kB। প্রথম sleep-এর libc-র জন্য RAM-এ পড়ে থাকা অংশ একই রইল, কিন্তু তার "ভাগের দাম" অর্ধেক হয়ে গেল — কারণ নতুন process গুলো নতুন copy আনেনি, একই frame-এর দিকে নিজেদের page table বসিয়েছে।

COMMON MISCONCEPTION

"Virtual memory মানে disk-কে RAM হিসেবে ব্যবহার করা।" না — সেটা swap, virtual memory-র অনেকগুলো ব্যবহারের একটা মাত্র। Virtual memory-র আসল কাজ তিনটা: প্রতিটা process-কে আলাদা, সুরক্ষিত address-এর জগৎ দেওয়া; page ধরে permission বসানো; আর memory আসলে ছোঁয়ার আগে পর্যন্ত RAM আটকে না রাখা। Swap পুরো বন্ধ রাখা server-এও (অনেক production server-এ তাই থাকে) virtual memory প্রতি nanosecond-এ কাজ করছে।

MENTAL MODEL

প্রতিটা address যা তোমার code কখনো দেখেছে — প্রতিটা pointer, প্রতিটা %DebugPrint — virtual। প্রতিটা access-এ MMU page number-কে (TLB থেকে, না পেলে page table থেকে) frame number-এ বদলায়, offset রেখে দেয়, আর permission যাচাই করে। Frame না থাকলে বা নিয়ম ভাঙলে page fault — kernel হয় চুপচাপ frame বসিয়ে দেয়, নয়তো process মেরে ফেলে। Isolation, lazy allocation, shared library, copy-on-write — সব এই এক কৌশলের ফল।

CAN I EXPLAIN THIS?
  • Process গুলো সরাসরি physical address ব্যবহার করলে কোন তিনটা সমস্যা হতো?
  • same-address.js-এ দুইটা জীবিত process-এর box একই address-এ, অথচ মান আলাদা — এটা কী প্রমাণ করে, আর কীভাবে সম্ভব?
  • Page, frame আর page table-এর সম্পর্ক কী? ১৬ KB page-এ 0x23143ad24b49 ভাঙলে কোন অংশ অনুবাদ হয় আর কোনটা হুবহু থাকে?
  • MMU প্রতিটা access-এ কী কী করে? TLB না থাকলে কী সমস্যা হতো?
  • lazy.js-এ ১ GB চেয়েও RSS বাড়ল না কেন, আর ছোঁয়ার পরে ৬৫ হাজারের বেশি minor fault এল কেন? Page fault-এর দুই রকম পরিণতি কী?
