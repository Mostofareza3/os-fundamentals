PART 3 · MEMORY

Chapter 9 — Virtual Memory

এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ chapter-গুলোর একটা। ধীরে পড়ো — এটা clear হলে OS-এর অর্ধেক রহস্য খুলে যায়।

Problem: সবাই একই RAM চায়

ধরো process-রা সরাসরি physical address ব্যবহার করতো। তাহলে তিনটা মারাত্মক সমস্যা:

  1. Isolation নেই: Chrome ভুল করে (বা malware ইচ্ছা করে) তোমার password manager-এর memory পড়ে ফেলতে পারতো — শুধু address জানলেই হলো।
  2. Coordination নightmare: Compiler code বানানোর সময় জানেই না program-টা RAM-এর কোথায় বসবে, আর কোন address অন্য কেউ ব্যবহার করছে।
  3. RAM-এর সীমা = hard limit: 8GB RAM-এ সব process মিলে 8GB-র বেশি কিছুতেই না।

Idea: প্রত্যেককে নিজের একটা "নকল" memory জগৎ দাও

OS + hardware মিলে প্রতিটা process-কে একটা illusion দেয়: "পুরো memory তোমার একার।" প্রতিটা process পায় নিজস্ব virtual address space — address 0 থেকে শুরু করে বিশাল একটা range, যেখানে Chapter 5-এর সেই layout (code, data, heap, stack) সাজানো থাকে। Process-এর সব pointer, সব address — এগুলো virtual address। Physical RAM-এর সাথে এদের direct মিল নেই।

তাহলে আসল RAM-এ পৌঁছায় কীভাবে? Translation-এর মাধ্যমে। প্রতিটা memory access-এ virtual address → physical address-এ convert হয়।

Page, page frame, page table

Byte-by-byte translation রাখা অসম্ভব (mapping table-ই RAM খেয়ে ফেলতো)। তাই memory-কে ভাগ করা হয় fixed-size টুকরায়:

  • Page: Virtual address space-এর টুকরা — সাধারণত 4KB।
  • Page frame: Physical RAM-এর একই size-এর টুকরা।
  • Page table: প্রতিটা process-এর নিজস্ব "dictionary" — কোন virtual page কোন physical frame-এ বসেছে। Kernel এটা maintain করে।
Process A                                Process B
virtual addr 0x1000                       virtual addr 0x1000  ← একই address!
      ↓                                         ↓
A-এর Page Table                           B-এর Page Table
      ↓                                         ↓
Physical frame #87                        Physical frame #412  ← আলাদা RAM!

              Physical RAM
   [ frame 87: A-র data ] ... [ frame 412: B-র data ]

দুই process-এর virtual address এক হলেও page table আলাদা — তাই physical memory আলাদা। এটাই isolation-এর মূলমন্ত্র।

Translation-টা করে CPU-র ভিতরের একটা hardware unit — MMU (Memory Management Unit)। প্রতিটা memory access-এ MMU page table দেখে address translate করে। আর যেহেতু প্রতিবার page table (যেটা নিজেই RAM-এ থাকে) পড়া দামি, MMU-র ভিতরে থাকে TLB (Translation Lookaside Buffer) — সাম্প্রতিক translation-গুলোর একটা ছোট cache। বেশিরভাগ access TLB-তেই মিটে যায়।

Page fault: illusion-এর সবচেয়ে চালাক অংশ

Page table-এ একটা entry-র "এই page-এর পিছনে এখন কোনো physical frame নেই" অবস্থাও থাকতে পারে। Process সেই address ছুঁলেই MMU হাত তুলে দেয় — CPU একটা page fault তোলে, control চলে যায় kernel-এর কাছে। তখন kernel সিদ্ধান্ত নেয়:

  • Address টা বৈধ, কিন্তু data এখনো আনা হয়নি (যেমন executable-এর যে অংশ এখনো পড়া হয়নি, বা swap-এ পাঠানো page)? → RAM-এ frame জোগাড় করো, data আনো, page table update করো, process-কে আবার চালাও। Process টেরও পায় না।
  • Address টা আসলেই অবৈধ? → process-কে segmentation fault দিয়ে মেরে ফেলো। C-তে ভুল pointer-এর সেই বিখ্যাত segfault, এই ঘটনা।

এই design থেকে ফাউ পাওয়া superpower গুলো

  • Lazy loading: পুরো executable আগে load করার দরকার নেই — page fault হলে যে অংশ লাগবে সেটাই আসবে। বড় program-ও দ্রুত start হয়।
  • Shared memory: দুই process-এর page table-এ একই physical frame map করে দাও — ব্যস, memory shared। Shared library (libc) এভাবেই শত process-এ এক কপি থাকে।
  • Copy-on-write (CoW): Process copy করার সময় (fork, Chapter 15) memory সত্যি সত্যি copy না করে দুজনের page table-ই একই frame-এ point করাও, শুধু read-only mark করো। কেউ লিখতে গেলে তখনই সেই page-টা copy হবে। ফলে fork প্রায় instant।
  • Swap: RAM ভরে গেলে কম-ব্যবহৃত page disk-এ সরিয়ে frame খালি করা যায়। পরে দরকার হলে page fault-এর মাধ্যমে ফেরত আসবে।
COMMON MISCONCEPTION

"Virtual memory মানে disk-কে RAM হিসেবে ব্যবহার করা।" না — swap শুধু একটা side feature। Virtual memory-র আসল purpose হলো isolation আর address abstraction: প্রতিটা process-এর নিজস্ব, সুরক্ষিত, ধারাবাহিক address জগৎ। Swap বন্ধ থাকলেও (অনেক server-এ থাকে) virtual memory পুরোদমে চলে।

EXPERIMENT (Linux)

cat /proc/<PID>/status | grep -i vm চালাও। VmSize (virtual address space-এর মোট size) প্রায়ই VmRSS (আসলে physical RAM-এ বসে থাকা অংশ)-এর চেয়ে অনেক বড় হবে। এটাই lazy allocation-এর evidence — process অনেক address "reserve" করেছে, কিন্তু kernel frame দিয়েছে শুধু যেটুকু ছোঁয়া হয়েছে।
