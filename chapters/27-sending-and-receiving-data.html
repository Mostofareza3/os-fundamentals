PART 7 · NETWORKING AND SOCKETS

Chapter 27 — Data পাঠানো আর পাওয়া

write() থেকে তার/বাতাস পর্যন্ত — এবং উল্টো পথে।

Send path

Application — write(fd, "GET / ...", n)
   ↓ system call — data send buffer-এ copy, return!
TCP  — buffer-এর data segment-এ কাটে, seq number দেয়,
       retransmission timer বসায় (হারালে আবার পাঠাবে)
IP   — segment-কে packet-এ মোড়ে: source/dest IP, routing
Driver — packet-কে NIC-এর queue-তে দেয়
   ↓ DMA
NIC (network card) — bits হিসেবে তারে/বাতাসে

লক্ষ করো: write() return মানে data পৌঁছে গেছে না — মানে kernel-এর send buffer-এ ঢুকেছে (file write-এর গল্পটার যমজ ভাই, Chapter 21)। পৌঁছানো নিশ্চিত করা, হারালে আবার পাঠানো, order ঠিক রাখা — সব TCP-র চাকরি, background-এ।

Receive path — উল্টো ছবি

NIC — packet এলো → DMA-তে memory-তে → interrupt: "data এসেছে!"
IP  — packet খুলে দেখে: আমার জন্যই তো?
TCP — চার-টুপল দেখে কোন connection-এর, seq number মিলিয়ে
      সঠিক জায়গায় বসায়, ACK পাঠায়, receive buffer-এ রাখে
      → এই socket-এ অপেক্ষারত process থাকলে জাগাও!
Application — read() → buffer থেকে data → তোমার হাতে

সেই "জাগাও" শব্দটা মন দিয়ে দেখো — data আসা মানে waiting process-এর Ready হয়ে যাওয়া (Chapter 15-এর state machine)। তোমার server-এর প্রতিটা request-handling শুরু হয় আসলে একটা NIC interrupt থেকে।

আর buffering কেন অনিবার্য, এখন পুরো ছবিটা বলা যায়: network-এর data আসে যখন খুশি (packet-এ, এলোমেলো সময়ে), app পড়ে যখন সুবিধা। দুই অসমান ছন্দের মাঝে kernel-এর buffer-ই একমাত্র শান্তিচুক্তি।

EXPERIMENT (Linux)

ss -t চালাও (macOS: netstat -an | grep ESTABLISHED | head)। Recv-Q আর Send-Q column দুটো এই chapter-এর সেই দুই buffer-এর জমে থাকা data-র লাইভ পরিমাপ। Recv-Q বড় হয়ে থাকা মানে — app data পড়ছে না; Send-Q বড় মানে — অপর পাশ নিতে পারছে না।
