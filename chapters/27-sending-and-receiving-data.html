PART 7 · NETWORKING AND SOCKETS

Chapter 27 — Sending and Receiving Data

socket.write() থেকে তার পর্যন্ত, আর উল্টো পথে NIC থেকে তোমার 'data' event পর্যন্ত। কেন তিনটা write একটা event হয়ে আসে, reader ধীর হলে data কোথায় জমে, আর দুইটা ছোট write কীভাবে প্রতি request-এ ৪০ ms খেয়ে ফেলে।

Chapter 25-এ দেখেছি socket-এর ভেতরে পাঠানো আর আসা data জমানোর জায়গা আছে, আর Chapter 26-এ দেখেছি TCP sequence number, ACK আর window দিয়ে নির্ভরযোগ্যতা বানায়। এই chapter-এ দুই দিকের পুরো যাত্রা, আর সেই যাত্রা থেকে জন্মানো তিনটা বাস্তব সমস্যা।

পাঠানোর পথ আর আসার পথ

প্রতিটা TCP socket-এর জন্য kernel দুইটা buffer রাখে: send buffer (তুমি লিখেছ, এখনো পাঠানো বা ACK পাওয়া হয়নি) আর receive buffer (এসেছে, তুমি এখনো পড়োনি)। পাঠানোর পথ:

  1. write() system call: kernel তোমার byte send buffer-এ copy করে আর ফিরে আসে। ফেরা মানে data kernel-এর হাতে — ওপাশে পৌঁছেছে, এমন না (Chapter 21-এর file write-এর যমজ ভাই)।
  2. TCP: buffer-এর byte কেটে segment বানায় — একেকটার সর্বোচ্চ মাপ MSS (maximum segment size, সাধারণ Ethernet-এ ~১৪৬০ byte) — sequence number বসায়, retransmission timer চালায়।
  3. IP: segment-এর মাথায় source আর destination IP বসিয়ে packet বানায়, কোন network interface দিয়ে যাবে ঠিক করে।
  4. Driver আর NIC: packet NIC-এর descriptor ring-এ, তারপর NIC DMA দিয়ে RAM থেকে তুলে তারে পাঠায় (Chapter 11)।

আসার পথ ঠিক উল্টো: NIC packet পেয়ে DMA দিয়ে RAM-এ রাখে আর interrupt দেয় → IP দেখে packet এই machine-এর কি না → TCP four-tuple দেখে socket খোঁজে (Chapter 25), sequence number মিলিয়ে ঠিক জায়গায় বসায়, ACK পাঠায়, receive buffer-এ রাখে → ওই socket-এর জন্য কেউ অপেক্ষায় থাকলে তাকে জাগায় (ঘুমন্ত read(), বা epoll-এর ready তালিকায় fd — Chapter 29) → তুমি read() করলে receive buffer থেকে তোমার memory-তে copy।

বাঁয়ে পাঠানো: write() শুধু send buffer-এ copy করে ফেরে; তারপর TCP, IP, NIC নিজেদের গতিতে। ডানে আসা: NIC থেকে ওপরে উঠে receive buffer-এ জমে, অপেক্ষায় থাকা reader জাগে। Send buffer-এর data মোছা হয় কেবল ওপাশের ACK এলে — হারালে সেখান থেকেই আবার পাঠানো হয়।

Byte-এর স্রোত, message না

TCP তোমার write()-গুলোর সীমানা মনে রাখে না। সে দেখে শুধু byte-এর একটা লম্বা সারি, আর তার সুবিধামতো segment-এ কাটে; ওপাশের kernel receive buffer-এ যা জমেছে, read() তার যতটা পারে একবারে দেয়। তাই ওপাশের 'data' event আর তোমার write()-এর মধ্যে কোনো এক-এক মিল নেই:

EXPERIMENT — framing.js
// framing.js — TCP byte-এর স্রোত: write-এর সীমানা ওপাশে পৌঁছায় না
const net = require('net');
let events = [];
const server = net.createServer(c => {
  c.on('data', d => events.push(d.length));
  c.on('end', () => {
    console.log(`${events.length} 'data' events, sizes:`, events.slice(0, 6).join(', '), events.length > 6 ? '...' : '');
    events = [];
  });
});
server.listen(8080, '127.0.0.1', async () => {
  // ১) তিনটা ছোট write, পরপর
  await new Promise(r => {
    const c = net.connect(8080, '127.0.0.1', () => {
      c.write('msg1\n'); c.write('msg2\n'); c.write('msg3\n'); c.end();
    });
    c.on('close', r);
  });
  // ২) একটা বড় write: 1 MB
  const c = net.connect(8080, '127.0.0.1', () => c.end(Buffer.alloc(1024 * 1024)));
  c.on('close', () => setTimeout(() => server.close(), 50));
});

তিনটা আলাদা write (৫ byte করে) ওপাশে এসেছে একটা ১৫ byte-এর event হয়ে। আর একটা 1 MB-এর write এসেছে ১৭ টুকরোয়, Linux-এ এলোমেলো মাপে। কোনটা হবে, নির্ভর করে সময়, buffer, OS-এর উপর — তাই কখনোই ধরে নেওয়া যায় না। যে code ধরে নেয় "একটা 'data' = একটা message", সে local-এ ঠিক চলে (ছোট data, দ্রুত loopback) আর production-এ মাঝে মাঝে ভাঙে।

সমাধান: message কোথায় শেষ, সেটা data-র ভেতরেই চিহ্নিত করো — একে বলে framing। দুইটা চেনা উপায়: প্রতিটা message-এর শেষে একটা বিশেষ চিহ্ন (যেমন \n), বা শুরুতে message-এর দৈর্ঘ্য। আর গ্রাহক আসা byte জমিয়ে রেখে পুরো message হলে তবে কাজে লাগায়:

let pending = '';
socket.on('data', chunk => {
  pending += chunk;
  let i;
  while ((i = pending.indexOf('\n')) !== -1) {   // যতগুলো পুরো লাইন জমেছে
    handleMessage(pending.slice(0, i));
    pending = pending.slice(i + 1);                // বাকি আধা-লাইন পরের জন্য
  }
});

HTTP নিজেও framing করে: header শেষ হয় একটা খালি লাইনে, আর body-র দৈর্ঘ্য বলা থাকে Content-Length-এ (বা টুকরো টুকরো পাঠালে প্রতিটার আগে তার দৈর্ঘ্য)। Express-এ তুমি এটা টের পাও না কারণ Node-এর http module কাজটা আগেই সেরে রাখে।

Buffer ভরলে: flow control আর backpressure

Buffer গুলো অসীম না। Linux-এ মাপ kernel নিজে চাহিদা বুঝে বাড়ায়-কমায়, তিনটা সীমার মধ্যে:

cat /proc/sys/net/ipv4/tcp_rmem /proc/sys/net/ipv4/tcp_wmem    # Linux: min, শুরু, max (byte)

Docker VM-এ: receive buffer 4096 131072 6291456, send buffer 4096 16384 4194304 — শুরু ১২৮ KB আর ১৬ KB, বাড়তে পারে ৬ MB আর ৪ MB পর্যন্ত। এবার ওপাশের reader যদি পড়া বন্ধ রাখে? তার receive buffer ভরে যায়, আর তার kernel প্রতিটা ACK-এ জানায় "আমার জায়গা আছে ০ byte" (Chapter 26-এর window)। প্রেরকের kernel তখন পাঠানো থামায় — এর নাম flow control। তারপর প্রেরকের send buffer ভরে, আর তারপর তোমার write()-ও আর জায়গা পায় না:

EXPERIMENT (Linux / Docker) — backpressure.js
// backpressure.js — reader পড়ছে না; writer কতদূর লিখতে পারে?
const net = require('net');
const { execSync } = require('child_process');

const server = net.createServer(c => {
  c.pause();                                   // server কিছুই পড়ছে না
  setTimeout(() => { console.log('server starts reading'); c.resume(); }, 1000);
  c.on('end', () => server.close());
});
server.listen(8080, '127.0.0.1', () => {
  const c = net.connect(8080, '127.0.0.1');
  const chunk = Buffer.alloc(64 * 1024);
  let sent = 0;
  c.on('connect', function pump() {
    while (sent < 50 * 1024 * 1024) {
      sent += chunk.length;
      if (!c.write(chunk)) {                   // false = "আর দিয়ো না, আগে এগুলো যাক"
        console.log(`write() returned false after ${sent / 1024} KB; Node is holding ${c.writableLength / 1024} KB`);
        setTimeout(() => console.log(execSync("ss -tn '( sport = :8080 or dport = :8080 )'").toString()), 200);
        c.once('drain', () => { console.log('drain: kernel buffers have room again'); c.end(); });
        return;
      }
    }
  });
});

প্রায় ২.৬ MB লেখার পর write() false দিয়েছে। তখন data তিন জায়গায়: server-এর receive buffer-এ ১,২৮,৭০৪ byte (Recv-Q, ভরা), client-এর send buffer-এ ২৪,৫২,৮৭৪ byte (Send-Q, kernel বাড়াতে বাড়াতে ~২.৩ MB), আর বাকি ৬৪ KB Node-এর নিজের memory-তে (writableLength) — kernel-এ আর জায়গা নেই বলে। Reader পড়া শুরু করতেই জায়গা খুলল, আর 'drain' event জানাল "এখন আবার লিখতে পারো"। ধীর reader থেকে উল্টো দিকে চাপ এসে দ্রুত writer-কে থামানো — এটাই backpressure।

false উপেক্ষা করলে কী হয়? Node লেখা ফেলে দেয় না, নিজের memory-তে জমিয়ে রাখে — সীমা ছাড়াই:

EXPERIMENT — ignore.js
// ignore.js — write()-এর false উপেক্ষা করলে data যায় কোথায়?
const net = require('net');
const server = net.createServer(c => c.pause());          // reader কিছুই পড়ছে না
server.listen(8080, '127.0.0.1', () => {
  const c = net.connect(8080, '127.0.0.1', () => {
    const before = process.memoryUsage().rss;
    for (let i = 0; i < 800; i++) c.write(Buffer.alloc(64 * 1024, 1));   // 50 MB, false-এর তোয়াক্কা না করে
    setTimeout(() => {
      console.log(`Node is holding ${(c.writableLength / 2 ** 20).toFixed(1)} MB in its own memory`);
      console.log(`RSS grew by ${((process.memoryUsage().rss - before) / 2 ** 20).toFixed(0)} MB`);
      process.exit(0);
    }, 500);
  });
});

Kernel-এর buffer ভরে যাওয়ার পরের পুরো ~৫০ MB Node-এর heap-এর বাইরের memory-তে (Chapter 6) বসে আছে। একটা ধীর client-এর জন্য একটা বড় file stream করা server যদি false না মানে, হাজারটা ধীর client মানে হাজার গুণ memory — শেষে OOM। নিজে 'drain' সামলাও, বা stream.pipeline(source, socket) ব্যবহার করো, যেটা এই হিসাব নিজে রাখে।

ধীর reader থেকে চাপ উল্টো দিকে ছড়ায়: তার receive buffer ভরে → ACK-এ window ০ → প্রেরকের kernel পাঠানো থামায় → send buffer ভরে → write() false দেয়। শেষ ধাপটা মানা তোমার দায়িত্ব; না মানলে ignore.js-এর মতো Node-এর memory-তে জমে।

ছোট write-এর ফাঁদ: Nagle আর delayed ACK

TCP-র দুইটা পুরনো ভালো উদ্দেশ্যের নিয়ম একসাথে পড়লে একটা বিশ্রী দেরি বানায়:

  • Nagle's algorithm (প্রেরকের দিকে): আগের পাঠানো data-র ACK আসেনি এমন অবস্থায় আরেকটা ছোট টুকরো লিখলে, সেটা সাথে সাথে পাঠিয়ো না — জমাও, ACK এলে বা একটা পুরো segment ভরলে তবে পাঠাও। উদ্দেশ্য: এক-দুই byte-এর অসংখ্য packet দিয়ে network ভরে না ফেলা।
  • Delayed ACK (গ্রাহকের দিকে): data পেয়ে সাথে সাথে ACK পাঠিয়ো না, কিছুক্ষণ (Linux-এ কমপক্ষে ~৪০ ms) অপেক্ষা করো — হয়তো app উত্তর লিখবে, তখন ACK সেই উত্তরের সাথেই চলে যাবে।

এখন ভাবো client একটা request দুই টুকরোয় লেখে, আর server পুরোটা না পেলে উত্তর দেয় না। প্রথম টুকরো যায়। দ্বিতীয়টা Nagle আটকে রাখে (প্রথমটার ACK আসেনি)। Server-এর kernel ACK দেরি করে (app তো এখনো উত্তর লেখেনি — পুরো request-ই পায়নি)। দুজনেই অপেক্ষায়, যতক্ষণ না delayed ACK-এর timer ফুরায়:

EXPERIMENT — nagle.js
// nagle.js — দুই টুকরোয় request লিখে উত্তরের অপেক্ষা (write-write-read), Nagle চালু বনাম বন্ধ
const net = require('net');
const server = net.createServer(c => {
  let buf = '';
  c.on('data', d => {                       // পুরো লাইন ("...\n") এলে তবেই উত্তর
    buf += d;
    if (buf.endsWith('\n')) { c.write('ok\n'); buf = ''; }
  });
});
server.listen(8080, '127.0.0.1', async () => {
  for (const noDelay of [false, true]) {
    const c = net.connect({ port: 8080, host: '127.0.0.1', noDelay });
    await new Promise(r => c.on('connect', r));
    const times = [];
    for (let i = 0; i < 20; i++) {
      const t = performance.now();
      c.write('GET /item/' + i);            // প্রথম টুকরো
      c.write(' HTTP\n');                   // দ্বিতীয় টুকরো, আলাদা write
      await new Promise(r => c.once('data', r));
      times.push(performance.now() - t);
    }
    times.sort((a, b) => a - b);
    console.log(`noDelay=${noDelay}: median ${times[10].toFixed(2)} ms per request`);
    c.destroy();
  }
  server.close();
});

Linux-এ Nagle চালু থাকলে প্রতিটা request ~৪২ ms — delayed ACK-এর timer — আর noDelay: true দিলে ০.০৬ ms, প্রায় সাতশো গুণ। Mac-এর loopback-এ এই দেরি দেখা যায়নি (macOS-এর delayed ACK-এর নিয়ম আলাদা) — তাই এই bug প্রায়ই developer-এর Mac-এ লুকিয়ে থাকে আর Linux server-এ বেরোয়। noDelay (system call-এর ভাষায় TCP_NODELAY) Nagle বন্ধ করে। Node-এর default কী? Docker-এ strace করে দেখলাম: সাধারণ net server-এর socket-এ কিছু বসায় না (Nagle চালু), কিন্তু http server প্রতিটা নতুন connection-এ setsockopt(20, SOL_TCP, TCP_NODELAY, [1], 4) ডাকে। নিজের protocol net-এর উপর বানালে এটা মনে রেখো — বা আরও ভালো, একটা message একটা write()-এ পাঠাও।

COMMON MISCONCEPTION

"আমি একবার write() করলে ওপাশে একবার 'data' আসবে।" TCP message চেনে না, byte-এর স্রোত চেনে: framing.js-এ তিনটা write একটা event হয়ে এসেছে, আর একটা 1 MB-এর write ১৭ টুকরোয়। আর write() ফিরে আসা মানে data ওপাশে পৌঁছেছে, তাও না — শুধু kernel-এর send buffer-এ ঢুকেছে (বা, buffer ভরা থাকলে, Node-এর নিজের memory-তে)।

MENTAL MODEL

প্রতিটা TCP socket দুইটা kernel buffer-এর মাঝখানে একটা পাইপ। write() শুধু নিজের send buffer-এ ঢালে; kernel সেখান থেকে segment বানিয়ে পাঠায় আর ACK পেলে মোছে। ওপাশে packet উঠে receive buffer-এ জমে, reader জাগে। Byte-এর সীমানা পথে হারায় — message-এর সীমানা নিজে চিহ্নিত করতে হয়। পাইপের কোথাও জট হলে চাপ উল্টো দিকে ছড়ায় (window ০ → send buffer ভরা → write() false), আর সেই চাপ মানা app-এর কাজ। ছোট ছোট write-এর ক্ষেত্রে Nagle আর delayed ACK মিলে ৪০ ms বসিয়ে দিতে পারে।

CAN I EXPLAIN THIS?
  • socket.write() ফিরে আসার মুহূর্তে data কোথায়? Send buffer থেকে data কখন মোছা হয়, আর কেন তখনই?
  • আসার পথে NIC থেকে তোমার 'data' event পর্যন্ত কোন কোন ধাপ? Kernel কীভাবে জানে packet কোন socket-এর?
  • framing.js-এ তিনটা write একটা ১৫ byte-এর event হয়ে এল কেন? Newline দিয়ে framing-এর code-এ pending variable কী কাজে লাগে?
  • backpressure.js-এ write() false দেওয়ার মুহূর্তে data কোন তিন জায়গায় ছিল? ignore.js-এ false উপেক্ষা করায় কী হলো, আর সমাধান কী?
  • Nagle আর delayed ACK একসাথে কীভাবে প্রতি request-এ ~৪২ ms দেরি বানায়? এই bug Mac-এ ধরা না পড়ে Linux-এ ধরা পড়তে পারে কেন, আর noDelay কী বদলায়?
