PART 7 · NETWORKING AND SOCKETS

Chapter 26 — TCP Connection-এর ভিতরে

Connection "establish" হওয়া মানে আসলে কী তৈরি হয় — এবং কোথায়।

Three-way handshake

Client                          Server
  │── SYN ──────────────────────→│   "connection চাই" (+ আমার শুরুর sequence number)
  │←───────────────── SYN-ACK ───│   "রাজি, এই নাও আমারটাও"
  │── ACK ──────────────────────→│   "পাকা কথা"
  │                              │
  │═══════ connection ready ═════│

তিন ধাপ কেন? কারণ দুই পক্ষকেই নিশ্চিত হতে হবে — "আমার পাঠানো ওর কাছে পৌঁছায়, ওর পাঠানো আমার কাছে পৌঁছায়", আর দুজনের সেই শুরুর sequence number বিনিময় হতে হবে (এই নাম্বার দিয়েই TCP পরে হিসাব রাখে কোন byte পৌঁছেছে, কোনটা হারিয়েছে)।

সবচেয়ে জরুরি উপলব্ধি: "connection" জিনিসটা তারে-তারে কোথাও নেই। এটা দুই পাশের kernel-এর memory-তে রাখা state মাত্র — sequence number, window size, timers। মাঝের network শুধু স্বাধীন packet চেনে। TCP হলো দুই kernel-এর সম্মিলিত অভিনয়ে তৈরি "reliable stream"-এর illusion।

Buffers: প্রতিটা socket-এর দুই গুদাম

প্রতিটা established connection-এর জন্য kernel দুটো buffer রাখে:

  • Send buffer: তোমার write() data আগে এখানে জমা হয় → kernel নিজের গতিতে packet বানিয়ে পাঠায়। Buffer ভরা থাকলে (receiver ধীর!) write block করে — এটাই backpressure-এর জন্মস্থান।
  • Receive buffer: Network থেকে আসা data এখানে জমে → তুমি read() করলে এখান থেকেই পাও। তুমি না পড়লে জমতে থাকে; ভরে গেলে TCP অপর পক্ষকে বলে দেয় "আস্তে!" (flow control)।

দেখেছ pattern-টা? আবার সেই গল্প — দুই ভিন্ন গতির জগতের (তোমার app আর network) মাঝে buffer।

Server-এর দুই queue

Server-এর listening socket-এর পিছনে kernel দুটো লাইন রাখে:

SYN এলো → [SYN queue]          — handshake চলছে, আধা-পাকা connection
handshake শেষ → [accept queue]  — পুরো ready, app-এর accept()-এর অপেক্ষায়
app accept() করলো → connection app-এর হাতে

এই ভাগাভাগির মানে গভীর: handshake পুরোটাই kernel সামলায় — তোমার Node process ঘুমিয়ে থাকলেও connection establish হয়ে accept queue-তে জমা হতে থাকে। আর app যদি accept করতে ধীর হয় (event loop আটকে আছে?), accept queue ভরে যায় — নতুন connection তখন refuse/drop হয়। listen()-এর backlog parameter এই queue-র সাইজই ঠিক করে। Production-এ "connection refused under load"-এর একটা classic কারণ এই queue overflow।
