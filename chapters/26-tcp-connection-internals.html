PART 7 · NETWORKING AND SOCKETS

Chapter 26 — TCP Connection Internals

Network কোনো কথা দেয় না — packet হারায়, উল্টো ক্রমে আসে। TCP তার উপর একটা নির্ভরযোগ্য "connection" বানায়, যেটা আসলে দুই kernel-এর memory-তে রাখা কিছু সংখ্যা। Handshake, বিদায়ের অবস্থাগুলো, আর server-এর সেই queue যেটা ভরলে client ঝুলে থাকে।

Chapter 25-এ socket-কে দেখেছি "লিখলে ওপাশে পৌঁছায়" এমন একটা জিনিস হিসেবে। কিন্তু নিচের network — IP — শুধু একটা কথা দেয়: চেষ্টা করব। একটা packet পথে হারাতে পারে (কোনো router-এর queue ভরা), দুইবার পৌঁছাতে পারে, আর দুইটা packet আলাদা পথ ধরে উল্টো ক্রমে আসতে পারে। IP-র কাছে প্রতিটা packet স্বাধীন; "connection" বলে তার কোনো ধারণাই নেই। তাহলে তোমার write('hello') ঠিক ক্রমে, একবারই, নিশ্চিতভাবে পৌঁছায় কীভাবে? এই কাজটা করে TCP, দুই পাশের kernel-এ।

ক্রম, প্রাপ্তিস্বীকার আর আবার পাঠানো

TCP-র কৌশল তিনটা সরল ধারণায়:

  • Sequence number: পাঠানো প্রতিটা byte-এর একটা ক্রমিক নম্বর। প্রতিটা packet (TCP-র ভাষায় segment) বলে "আমার ভেতরে byte অমুক থেকে তমুক"। উল্টো ক্রমে এলে গ্রাহক নম্বর দেখে সাজিয়ে নেয়; দুইবার এলে দ্বিতীয়টা ফেলে দেয়।
  • ACK (acknowledgement): গ্রাহক জানায় "অমুক নম্বরের আগ পর্যন্ত সব পেয়েছি, এরপরেরটা পাঠাও"।
  • Retransmission: প্রেরক প্রতিটা পাঠানো segment-এর জন্য একটা timer চালায়। নির্দিষ্ট সময়ের মধ্যে ACK না এলে ধরে নেয় হারিয়েছে, আবার পাঠায়। এই সময়ের নাম RTO (retransmission timeout)।

ACK না পেয়ে প্রেরক কতটা data একসাথে পাঠাতে পারে, তারও দুইটা সীমা আছে: গ্রাহকের buffer-এ কতটা জায়গা (window, Chapter 27), আর network কতটা সইতে পারবে বলে TCP-র অনুমান (congestion window, cwnd — packet হারানো দেখলে কমায়, সব ঠিক থাকলে বাড়ায়)।

Handshake: তিন ধাপে পরিচয়

Data পাঠানোর আগে দুই পক্ষকে দুইটা জিনিসে একমত হতে হয়: আমার byte-এর নম্বর কোথা থেকে শুরু, আর তোমারটা কোথা থেকে। শুরুর নম্বর (initial sequence number) প্রতিবার এলোমেলো বাছা হয়, যাতে পুরনো connection-এর ভুলে পড়ে থাকা packet বা বাইরের কেউ অনুমান করে নতুন connection-এ ঢুকে পড়তে না পারে। তিন ধাপ লাগে কারণ দুই দিকেরই "পাঠালাম — পেয়েছি" নিশ্চিত হতে হয়: client নিজের নম্বর পাঠায় (SYN), server সেটা স্বীকার করে আর নিজেরটা পাঠায় (SYN-ACK), client server-এর নম্বর স্বীকার করে (ACK)। দুই ধাপে থামলে server জানতেই পারত না তার নম্বর client-এর কাছে পৌঁছেছে কি না।

পুরো একটা কথোপকথন ধরে দেখি। tcpdump network-এর packet ধরে দেখানোর tool; Docker-এর ভেতরে loopback (lo)-এ চালাব:

EXPERIMENT (Linux / Docker) — hello-tcp.js আর tcpdump
// hello-tcp.js — client "hello" পাঠায়, server "HELLO" ফেরত দেয়, তারপর বিদায়
const net = require('net');
const server = net.createServer(c => c.on('data', d => c.end(d.toString().toUpperCase())));
server.listen(8080, '127.0.0.1', () => {
  const c = net.connect(8080, '127.0.0.1', () => c.write('hello'));
  c.on('data', d => console.log('client got:', d.toString()));
  c.on('close', () => server.close());
});
docker run --rm -v "$PWD":/w:ro node:22-bookworm-slim sh -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq tcpdump >/dev/null
  tcpdump -i lo -n -l "tcp port 8080" 2>/dev/null > /tmp/cap.txt & sleep 1
  node /w/hello-tcp.js; sleep 1; cat /tmp/cap.txt'

ওপরের tcpdump-এর দশটা packet, সময় ওপর থেকে নিচে। তিন ধাপের handshake, তারপর দুই দিকে ৫ byte করে data আর তার ACK, শেষে দুই দিক থেকে FIN। যে পক্ষ আগে FIN পাঠায় (এখানে server), শেষে সে TIME-WAIT অবস্থায় যায় — একটু পরে।

Connection আসলে দুই kernel-এর memory-তে

তারে "connection" বলে কিছু নেই — তারে শুধু ওপরের মতো আলাদা আলাদা packet। Connection হলো দুই পাশের kernel-এ রাখা একগাদা সংখ্যা: কার কোন sequence number পর্যন্ত পাঠানো, কোন পর্যন্ত ACK পাওয়া, timer, window। ss -i দিয়ে সেই সংখ্যাগুলো সরাসরি দেখা যায়:

EXPERIMENT (Linux / Docker) — tcpinfo.js
// tcpinfo.js — একটা চালু connection-এর জন্য kernel কী কী মনে রাখে
const net = require('net');
const { execSync } = require('child_process');
net.createServer(c => c.pipe(c)).listen(8080, '127.0.0.1', () => {   // echo server
  const c = net.connect(8080, '127.0.0.1', () => {
    c.write(Buffer.alloc(100000));                                  // কিছু data আসা-যাওয়া করুক
    setTimeout(() => {
      console.log(execSync(`ss -tni '( sport = :${c.localPort} )'`).toString());
      process.exit(0);
    }, 300);
  });
  c.resume();
});

বিদায়ের পালা: FIN, TIME-WAIT, CLOSE-WAIT

TCP connection-এর দুই দিক আলাদাভাবে বন্ধ হয়: প্রতিটা পক্ষ "আমার আর পাঠানোর কিছু নেই" জানাতে FIN পাঠায়। ফলে একটা connection বন্ধ হওয়ার পথে কয়েকটা মাঝামাঝি অবস্থা (state) পেরোয়, আর দুইটা production-এ খুব চেনা:

EXPERIMENT (Linux / Docker) — states.js
// states.js — connection বন্ধের পরের দুই অবস্থা: TIME-WAIT আর CLOSE-WAIT
const net = require('net');
const { execSync } = require('child_process');

// server A (8081): client বিদায় (FIN) বললেও নিজে কখনো বন্ধ করে না — একটা bug
net.createServer({ allowHalfOpen: true }, () => {}).listen(8081, '127.0.0.1');
// server B (8082): নিজেই আগে বন্ধ করে
net.createServer(c => c.end()).listen(8082, '127.0.0.1');

setTimeout(() => {
  net.connect(8081, '127.0.0.1', function () { this.end(); });   // A-তে client আগে বিদায় বলে
  net.connect(8082, '127.0.0.1').resume();                        // B-তে server আগে বিদায় বলে
  setTimeout(() => {
    console.log(execSync("ss -tan state all '( sport = :8081 or sport = :8082 or dport = :8081 or dport = :8082 )' | grep -v LISTEN").toString());
    process.exit(0);
  }, 300);
}, 100);

CLOSE-WAIT 0      0          127.0.0.1:8081     127.0.0.1:49548
FIN-WAIT-2 0      0          127.0.0.1:49548    127.0.0.1:8081
TIME-WAIT  0      0          127.0.0.1:8082     127.0.0.1:39102

তারপর একই container-এ ss -tano state time-wait-এর timer: column: timewait,59sec, ৩০ সেকেন্ড পরে timewait,29sec, আর ৬১ সেকেন্ড পরে তালিকা খালি।

  • CLOSE-WAIT (server A): ওপাশ FIN পাঠিয়েছে, kernel ACK দিয়েছে, এখন অপেক্ষা তোমার code-এর close()-এর জন্য। Kernel নিজে থেকে এটা কখনো শেষ করবে না। Production-এ ss-এ হাজার হাজার CLOSE-WAIT মানে প্রায় নিশ্চিতভাবে তোমার code-এ connection বন্ধ করা ভুলে যাওয়ার bug — প্রতিটা একটা fd ধরে রাখে, আর শেষে fd ফুরিয়ে যায় (Chapter 30)। ওপাশের client তখন FIN-WAIT-2-এ: "আমি বিদায় বলেছি, তোমারটার অপেক্ষায়"।
  • TIME-WAIT (server B): যে পক্ষ আগে বন্ধ করে, সব শেষ হওয়ার পরেও সে connection-এর চিহ্ন কিছুক্ষণ রেখে দেয় — Linux-এ ঠিক ৬০ সেকেন্ড (উপরের timer)। দুইটা কারণে: শেষ ACK-টা হারালে ওপাশ FIN আবার পাঠাবে, তখন জবাব দেওয়ার কেউ থাকা চাই; আর network-এ দেরিতে ঘুরতে থাকা এই connection-এর কোনো পুরনো packet যেন একই four-tuple-এর নতুন connection-এ ঢুকে না পড়ে।

TIME-WAIT নিরীহ, কিন্তু দুই জায়গায় কামড়ায়। এক, server restart: পুরনো process-এর connection গুলো port 8080-এ TIME-WAIT-এ থাকলে নতুন process-এর bind() ব্যর্থ হতে পারে — Chapter 25-এর strace-এ Node যে SO_REUSEADDR দিয়েছিল, সেটা ঠিক এটা ঠেকায়। দুই, যে client প্রতিটা request-এর জন্য নতুন connection খোলে আর নিজে বন্ধ করে, তার প্রতিটা বন্ধ connection ৬০ সেকেন্ড একটা ephemeral port আটকে রাখে; Linux-এর range-এ ~২৮,০০০ port (Chapter 25), তাই একই server-এ সেকেন্ডে কয়েকশো নতুন connection খুললেই port ফুরিয়ে যেতে পারে। সমাধান: connection আবার ব্যবহার করো — HTTP keep-alive, database connection pool।

TCP-র অবস্থার ছোট করা মানচিত্র। ওপরে খোলার পথ — client আর server দুই রাস্তায় ESTABLISHED-এ পৌঁছায়। নিচে বন্ধের দুই রাস্তা: যে আগে close() ডাকে সে বাঁয়ে নামে আর ৬০ সেকেন্ড TIME-WAIT-এ থাকে; যে পক্ষ আগে FIN পায় সে ডানে CLOSE-WAIT-এ আটকে থাকে যতক্ষণ না তার code নিজে close() ডাকে।

Server-এর দুই লাইন: SYN queue আর accept queue

ওপরের handshake-এ তোমার Node code কোথায় ছিল? কোথাও না — পুরোটা kernel করেছে। Listening socket-এর পেছনে kernel দুইটা লাইন রাখে: আধা-শেষ handshake-এর জন্য SYN queue, আর পুরো শেষ হওয়া connection-এর জন্য accept queue — যেখানে তারা app-এর accept()-এর অপেক্ষায় থাকে। Accept queue-এর মাপ হলো listen()-এ দেওয়া backlog আর kernel-এর সীমা net.core.somaxconn-এর মধ্যে যেটা ছোট (Docker VM-এ cat /proc/sys/net/core/somaxconn = ৪০৯৬, Node-এর default backlog ৫১১)। App ব্যস্ত থাকলে কী হয়, দেখি — backlog ইচ্ছা করে ৪:

EXPERIMENT (Linux / Docker) — backlog.js
// backlog.js — server-এর event loop আটকে থাকলে নতুন connection-এর কী হয়
const net = require('net');
const { execSync } = require('child_process');

if (process.argv[2] === 'server') {
  net.createServer(() => {}).listen(8080, '127.0.0.1', 4, () => {   // backlog = 4
    process.send('ready');
    const end = Date.now() + 5000;
    while (Date.now() < end) {}          // ৫ সেকেন্ড event loop বন্ধ: accept() কেউ ডাকছে না
  });
} else {
  const server = require('child_process').fork(__filename, ['server']);
  server.on('message', () => {
    for (let i = 1; i <= 10; i++) {
      const t = Date.now();
      net.connect(8080, '127.0.0.1', () => console.log(`client ${i} connected after ${Date.now() - t} ms`))
         .on('error', e => console.log(`client ${i}: ${e.code}`));
    }
    setTimeout(() => console.log(execSync("ss -tan '( sport = :8080 or dport = :8080 )'").toString()), 1000);
    setTimeout(() => process.exit(0), 9000);
  });
}

Server process তখন পুরোপুরি জমে আছে, একটা JS লাইনও চলছে না — তবু প্রথম ৫টা client ২ ms-এ "connected"। Handshake kernel করেছে, connection গুলো accept queue-তে বসে আছে; LISTEN লাইনের Recv-Q 5 মানে queue-তে ৫টা অপেক্ষায় (Linux backlog-এর চেয়ে একটা বেশি রাখে), Send-Q 4 হলো backlog। Queue ভরা, তাই বাকি ৫টার SYN kernel নীরবে ফেলে দিয়েছে — কোনো "refused" না পাঠিয়ে। তারা SYN-SENT-এ ঝুলে থেকে SYN আবার আবার পাঠিয়েছে, আর server-এর loop ছাড়া পাওয়ার পরে ঢুকেছে ৫ সেকেন্ডেরও বেশি দেরিতে।

Production-এ এর উপসর্গ ধাঁধার মতো: server "up", health check হয়তো পাস করছে, অথচ কিছু client connect করতেই কয়েক সেকেন্ড নিচ্ছে বা timeout খাচ্ছে। কারণ event loop কোনো ভারী synchronous কাজে আটকে (Chapter 19), accept() হচ্ছে না, queue ভরে গেছে। ss -ltn-এ listening socket-এর Recv-Q backlog ছুঁয়ে থাকলে এটাই রোগ। আর backlog বাড়াতে চাইলে মনে রেখো, somaxconn-এর বেশি চাইলে kernel নীরবে ছেঁটে দেয়।

Listening socket-এর পেছনের দুই লাইন। Handshake পুরোটা kernel-এর, তাই তোমার JS জমে থাকলেও connection accept queue-তে জমতে থাকে (backlog.js-এর প্রথম ৫টা)। Queue ভরলে নতুন SYN নীরবে পড়ে যায়, client আবার চেষ্টা করে — ফলে "refused" না, দীর্ঘ অপেক্ষা।

COMMON MISCONCEPTION

"Client-এর connect সফল মানে server app connection-টা দেখেছে।" না — backlog.js-এ server-এর JS পুরো ৫ সেকেন্ড জমে ছিল, তবু ৫টা client ২ ms-এ connected। Handshake kernel-এর কাজ; app connection প্রথম দেখে accept()-এ, যেটা পরে। উল্টো দিকে, queue ভরা থাকলে client "connection refused" পায় না — সে ঝুলে থাকে।

MENTAL MODEL

TCP connection কোনো তার না — দুই kernel-এর memory-তে রাখা কয়েকটা সংখ্যা (sequence, ACK, timer, window), যেগুলো তারা packet দিয়ে মিলিয়ে নেয়। Sequence number ক্রম আর ডুপ্লিকেট সামলায়, ACK আর retransmission হারানো সামলায়। খোলা হয় তিন ধাপে, বন্ধ হয় দুই দিক থেকে আলাদা FIN-এ — আগে যে বন্ধ করে সে ৬০ সেকেন্ড TIME-WAIT-এ, আর যে FIN পেয়েও বন্ধ করে না সে CLOSE-WAIT-এ আটকে থাকে। আর পুরো handshake kernel নিজেই করে, app-এর অপেক্ষায় accept queue-তে জমিয়ে রাখে।
