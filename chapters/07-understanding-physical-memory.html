PART 3 · MEMORY

Chapter 7 — Physical Memory বোঝা

RAM-এর ভেতরের বাস্তবতা: আসল ঠিকানা কী, CPU-র তুলনায় সে কেন এত ধীর, "ধীর" কথাটার দুইটা আলাদা মানে, আর তোমার machine-এর RAM আসলে কে কতটা খাচ্ছে।

Chapter 2-এর কথা এক লাইনে: RAM হলো byte-এর একটা বিশাল array, প্রতিটা byte-এর একটা নম্বর — memory address; power গেলে সব মুছে যায়, আর একবার পড়তে মোটামুটি ১০০ ns লাগে। সেই chapter-এ একটা কথা ঝুলিয়ে রেখেছিলাম: %DebugPrint যে address দেখায় সেটা "virtual"। এই Part-এর কাজ সেই ঝোলানো সুতো ধরে টানা। শুরু করি hardware-এর নিজের দিক থেকে।

Physical address: RAM-এর আসল ঠিকানা

তোমার process যে address দেখে (Chapter 5-এর /proc/self/maps-এর aaaabb3d0000-এর মতো সংখ্যা), সেগুলো যদি সরাসরি RAM chip-এর ঠিকানা হতো, তাহলে দুইটা process একই সংখ্যা ব্যবহার করলে একই byte-এ গিয়ে পড়ত। অথচ Chapter 3-এ দেখেছ, দুই process-এর count আলাদা থাকে। তাহলে বোঝাই যায়, process-এর address আর RAM-এর আসল ঠিকানা আলাদা জিনিস।

Memory hardware নিজে বোঝে শুধু একটা নম্বর-ব্যবস্থা: physical address — machine-এর পুরো hardware-এর উপর একটাই, সবার জন্য এক। এই ঠিকানা নিয়ে কাজ করে শুধু kernel আর CPU-র ভেতরের একটা অংশ (যেটা Chapter 9-এ খুলব); কোনো user process কখনো physical address দেখে না।

মজার ব্যাপার হলো, physical address-এর সব নম্বর RAM-এ যায় না। Chapter 2-এ বলেছিলাম CPU device controller-এর register-এ command লেখে — সেই register গুলোও physical address-এর এক একটা range দখল করে থাকে। Linux kernel পুরো ম্যাপটা দেখায়:

EXPERIMENT (Linux / Docker)

এই file-এর আসল সংখ্যা দেখতে বিশেষ অনুমতি লাগে, তাই --privileged:

docker run --rm --privileged alpine sh -c 'head -6 /proc/iomem; grep "System RAM" /proc/iomem'

আমার output (Docker-এর Linux VM):

10000000-1000ffff : GICD
10010000-1018ffff : GICR
20050000-20050fff : pl031
  20050000-20050fff : rtc-pl031
40000000-4fffffff : PCI ECAM
50000000-6ffdffff : pci
70000000-269bfffff : System RAM

GICD/GICR হলো interrupt controller (Chapter 2-এর interrupt যে chip সামলায়), rtc-pl031 হলো ঘড়ির chip, pci হলো I/O bus-এর device গুলো। আসল RAM (System RAM) শুরু হয়েছে 0x70000000 থেকে। মানে physical address-এর জগতে RAM আর device-এর register পাশাপাশি বসানো; CPU একটা address-এ লিখলে সেটা RAM-এ যাবে নাকি কোনো device-এ, তা ঠিক হয় এই ম্যাপ দিয়ে।

macOS এই ম্যাপ দেখায় না, কিন্তু মোট মাপ বলে: sysctl -n hw.memsize আমার Mac-এ 25769803776 — ঠিক ২৪ × ২৩০ byte।

DRAM: প্রতিটা bit একটা ছোট্ট capacitor

RAM কেন power গেলে সব ভুলে যায়, আর কেন CPU-র register-এর মতো দ্রুত না — দুটোর উত্তর একই জায়গায়: RAM কী দিয়ে তৈরি। আজকের প্রায় সব RAM-এর প্রযুক্তির নাম DRAM (Dynamic RAM)। তোমার machine-এরটা দেখো:

system_profiler SPMemoryDataType      # macOS
sudo dmidecode -t memory | grep Type   # Linux (আসল machine-এ)

আমার Mac বলছে Type: LPDDR5 — DRAM-এরই একটা প্রজন্ম (LP মানে low-power, phone আর laptop-এর জন্য)।

DRAM-এর প্রতিটা bit হলো একটা অতি ক্ষুদ্র capacitor (বিদ্যুৎ-চার্জ ধরে রাখার একটা ছোট আধার) আর একটা transistor (সুইচ)। চার্জ আছে মানে ১, নেই মানে ০। একটা bit-এ মাত্র দুইটা অংশ — তাই এক chip-এ কোটি কোটি bit আঁটে, আর দামও কম। সমস্যা হলো capacitor-এর চার্জ চুপচাপ লিক করে যায়, কয়েক millisecond-এই। তাই memory controller (CPU-র পাশের যে circuit RAM-কে চালায়) প্রতিটা সারির চার্জ নিয়মিত পড়ে আবার লিখে দেয় — standard অনুযায়ী প্রতি সারি অন্তত প্রতি ৬৪ ms-এ একবার। এর নাম refresh, আর "Dynamic" নামটাও এখান থেকে। Power চলে গেলে refresh বন্ধ, চার্জ লিক হয়ে শেষ, data শেষ — RAM volatile হওয়ার আসল কারণ এটাই।

পড়ার প্রক্রিয়াও সরল না। Bit গুলো সারি (row) আর কলাম (column)-এ সাজানো। কিছু পড়তে হলে controller-কে আগে পুরো একটা সারি "খুলতে" হয় — সারির সব চার্জ একটা row buffer-এ তুলে আনা — তারপর সেখান থেকে দরকারি column পড়া, তারপর সারিটা বন্ধ করে পরের জন্য প্রস্তুত করা। প্রতিটা ধাপে কয়েক nanosecond।

তুলনার জন্য: CPU-র register আর cache-এ ব্যবহৃত হয় SRAM (Static RAM) — প্রতিটা bit ছয়টা transistor-এর একটা ছোট circuit, কোনো লিক নেই, refresh নেই, অনেক দ্রুত। কিন্তু প্রতি bit-এ অনেকগুণ বেশি জায়গা, বেশি বিদ্যুৎ আর অনেক বেশি দাম। ২৪ GB SRAM একটা laptop-এ বসানোর মতো আকার বা দামে বানানো সম্ভব না। তাই অল্প SRAM (cache) কাছে, অনেক DRAM একটু দূরে — এই আপসের উপরেই পুরো Part 3 আর Part 4 দাঁড়িয়ে।

Memory wall: RAM কেন CPU-র তুলনায় এত ধীর

CPU-র ভেতরের সব কাজ একটা ঘড়ির তালে এগোয়; ঘড়ির এক টিকের নাম cycle (Chapter 12-এ বিস্তারিত)। আধুনিক CPU সেকেন্ডে ৪০০–৫০০ কোটি cycle চালায় — এক cycle মোটামুটি ০.২২ ns। এখন RAM থেকে একটা মান আনতে যদি ১০০ ns লাগে, তাহলে প্রতিবার CPU-কে প্রায় ৫০০ cycle চুপচাপ অপেক্ষা করতে হবে — যে সময়ে সে কয়েক হাজার instruction চালিয়ে ফেলতে পারত।

এই দেরির উৎস তিনটা: RAM chip CPU-র chip-এর বাইরে (Apple Silicon-এ একই package-এ, তবু আলাদা chip), signal যেতে-আসতে সময় লাগে; controller-এর কাছে অনুরোধ লাইনে দাঁড়ায়; আর ওপরের row খোলা-পড়া-বন্ধ করার ধাপ। গত কয়েক দশকে CPU যে হারে দ্রুত হয়েছে, DRAM-এর latency সেই হারে কমেনি — দুইয়ের মাঝখানের এই ক্রমবর্ধমান ফাঁকের নাম memory wall।

এবার আসল সংখ্যাটা নিজের machine-এ মাপো। কৌশলটার নাম pointer chase: একটা বড় array-তে এলোমেলো একটা চক্র বানাও, যেখানে প্রতিটা ঘরে লেখা আছে পরের কোন ঘরে যেতে হবে। প্রতিটা ধাপের address আগের ধাপের ফলাফল না জেনে বের করা যায় না, তাই CPU আগেভাগে কিছু আনতে পারে না, একসাথে কয়েকটা অনুরোধও পাঠাতে পারে না — প্রতিটা access-এর পুরো দেরিটা গুনতে হয়।

EXPERIMENT — chase.js
function chase(bytes, steps = 20_000_000) {
  const n = bytes / 4;                          // Int32 = 4 byte
  const next = new Int32Array(n);
  const order = new Int32Array(n);
  for (let i = 0; i < n; i++) order[i] = i;
  for (let i = n - 1; i > 0; i--) {             // এলোমেলো ক্রম
    const j = Math.floor(Math.random() * (i + 1));
    const t = order[i]; order[i] = order[j]; order[j] = t;
  }
  for (let i = 0; i < n; i++) next[order[i]] = order[(i + 1) % n];  // একটা বড় চক্র
  let p = 0;
  for (let i = 0; i < 1_000_000; i++) p = next[p];                   // গরম করে নাও
  const t = process.hrtime.bigint();
  for (let i = 0; i < steps; i++) p = next[p];                       // শুধু এটাই মাপা হচ্ছে
  return Number(process.hrtime.bigint() - t) / steps;
}
const mb = Number(process.argv[2] || 512);
console.log(`${mb} MB array: ${chase(mb * 2 ** 20).toFixed(1)} ns per access`);

node chase.js 512 — আমার Mac-এ 512 MB array: 118.6 ns per access। এবার node chase.js 0.015625 (১৬ KB) চালাও: এসেছে 1.4 ns। একই code, একই RAM — তবু ৮০ গুণেরও বেশি দ্রুত। কারণ ছোট array-টা পুরোটাই CPU-র কাছের SRAM-এ (cache-এ) এঁটে গেছে; বড়টা আঁটেনি। সেই গল্প Chapter 8 আর 13-এর।

Cache-এ না পেলে একটা read-এর পথ: core থেকে memory controller হয়ে DRAM chip। Chip-এর ভেতরে একটা মান পড়তে পুরো একটা সারি row buffer-এ তুলতে হয়, তারপর একটা column পড়া, তারপর সারি বন্ধ। বাঁয়ের বাক্স বলছে কেন DRAM volatile: capacitor-এর চার্জ লিক করে, refresh বন্ধ হলেই data শেষ।

Latency আর bandwidth: "ধীর"-এর দুইটা মানে

একটা ধাঁধা: RAM যদি প্রতি access-এ ১১৯ ns নেয়, তাহলে ১ GB-র একটা array copy করতে (প্রায় ১০০ কোটি byte) কয়েক মিনিট লাগার কথা। অথচ লাগে কয়েক millisecond। দুটো কীভাবে একসাথে সত্যি?

কারণ "memory কত দ্রুত" প্রশ্নের দুইটা আলাদা উত্তর আছে:

  • Latency — একটা অনুরোধ পাঠানো থেকে উত্তর পাওয়া পর্যন্ত সময়। Pointer chase এটা মাপে: ~১১৯ ns।
  • Bandwidth — একসাথে অনেক অনুরোধ চললে প্রতি সেকেন্ডে কত byte আনা-নেওয়া হয়।

Highway-র উপমায়: latency হলো একটা গাড়ির ঢাকা থেকে চট্টগ্রাম যেতে কত ঘণ্টা লাগে, bandwidth হলো ঘণ্টায় কতগুলো গাড়ি পৌঁছায় — রাস্তা আট লেনের হলে যাত্রার সময় না কমেও পৌঁছানো গাড়ির সংখ্যা আটগুণ। Hardware-এ ঠিক কী ঘটে: পরের address আগে থেকে জানা থাকলে (যেমন array একটানা পড়া) memory controller একসাথে অনেকগুলো অনুরোধ পাঠিয়ে রাখে, একাধিক channel আর bank পাশাপাশি কাজ করে, আর CPU আগেভাগে পরের টুকরো আনিয়ে রাখে। প্রতিটা অনুরোধের latency একই থাকে, কিন্তু সেগুলো একটার পেছনে আরেকটা না, একসাথে চলে।

EXPERIMENT — bandwidth.js
const GB = 2 ** 30;
const src = new Uint8Array(GB).fill(1);   // ১ GB
const dst = new Uint8Array(GB);
dst.set(src);                              // একবার গরম করে নাও
const t = performance.now();
for (let k = 0; k < 5; k++) dst.set(src); // ৫ বার পুরো ১ GB copy
const sec = (performance.now() - t) / 1000;
console.log('copy speed:', (5 / sec).toFixed(1), 'GB/s');

আমার Mac-এ copy speed: 57.9 GB/s। Pointer chase-এ প্রতি ১১৯ ns-এ কাজের data আসছিল ৪ byte — মানে সেকেন্ডে প্রায় ০.০৩ GB। একই RAM, একই machine: একভাবে পড়লে ~৫৮ GB/s, আরেকভাবে পড়লে ~০.০৩ GB/s — প্রায় ১৭০০ গুণ পার্থক্য।

শিক্ষাটা সোজা: memory-র গতি তোমার access pattern-এর উপর নির্ভর করে। একটানা পড়লে তুমি bandwidth পাও; এক জায়গা থেকে আরেক জায়গায় লাফ দিলে (linked list, object-এর reference ধরে ঘোরা, hash table) তুমি latency-র দাস। Chapter 6-এর locality.js-এ এলোমেলো ক্রমের object ১০ গুণ ধীর হয়েছিল — এটাই তার নিচের কারণ।

তোমার RAM কে খাচ্ছে: free, available, buff/cache

অনেকে server-এ free -h চালিয়ে দেখে "free" খুব কম, আর ভয় পেয়ে যায়। কিন্তু kernel-এর দর্শন হলো: ফাঁকা পড়ে থাকা RAM মানে নষ্ট RAM। তাই কোনো process যে RAM চাইছে না, kernel সেটা file-এর data জমিয়ে রাখার কাজে লাগায় — Chapter 2-এর page cache। কেউ memory চাইলে kernel এই cache থেকে পুরনো জিনিস ফেলে দিয়ে জায়গা বানায়। তাই "কতটা memory আসলে পাওয়া যাবে" প্রশ্নের উত্তর "free" না, "available"।

EXPERIMENT (Linux / Docker)
docker run --rm alpine sh -c 'free -m | head -2; dd if=/dev/urandom of=/root/big.bin bs=1M count=500 2>/dev/null; free -m | head -2'

আমার output (MB-তে):

        total   used   free   shared   buff/cache   available
Mem:     7837    447   6122       35         1268        7156
Mem:     7837    457   5601       35         1779        7146

৫০০ MB-র একটা file লেখার পরে free কমেছে ৫২১ MB, buff/cache বেড়েছে ৫১১ MB — kernel file-এর data RAM-এ রেখে দিয়েছে। কিন্তু available কমেছে মাত্র ১০ MB, কারণ দরকার হলে ওই cache সঙ্গে সঙ্গে ছেড়ে দেওয়া যায়।

macOS-এ একই ছবি অন্য নামে। vm_stat page হিসেবে গুনে দেখায় (প্রথম লাইনেই বলে page size of 16384 bytes — page কী, Chapter 9-এ)। সেখানে free, active, inactive (সম্প্রতি ব্যবহৃত হয়নি, দরকারে ফেরত নেওয়া যায়) আর wired down (kernel-এর নিজের memory, যেটা কখনো সরানো যায় না) আলাদা করে দেখায়। সহজ সারাংশ চাইলে memory_pressure | tail -1 — আমার Mac-এ System-wide memory free percentage: 78%। Activity Monitor-এর Memory tab-এর "Cached Files" হলো page cache, আর নিচের "Memory Pressure" graph-টাই আসল সূচক: সবুজ থাকলে RAM নিয়ে চিন্তার কিছু নেই।

COMMON MISCONCEPTION

"RAM-এ যেকোনো address পড়তে সমান সময় লাগে — এজন্যই তো নাম Random Access।" নামটা এসেছিল tape-এর তুলনায়: tape-এ দূরের data-র জন্য ফিতা ঘোরাতে হয়, RAM-এ হয় না। কিন্তু সমান সময়? একদমই না। কাছের cache-এ থাকলে ~১ ns, RAM-এ গেলে ~১২০ ns, আর সদ্য খোলা row-তে থাকলে তার মাঝামাঝি। "Random" access আজকের machine-এ সবচেয়ে দামি access।

MENTAL MODEL

RAM হলো ধীর কিন্তু প্রশস্ত একটা পাইপ: প্রতিটা একক অনুরোধের উত্তর আসতে ~১০০ ns (latency), কিন্তু একটানা চাইলে সেকেন্ডে কয়েক দশ GB বয়ে আনে (bandwidth)। তোমার code কোনটা পাবে, তা ঠিক করে access pattern। আর physical address-এর এই জগৎ শুধু kernel দেখে — process দেখে তার নিজের বানানো address, যার গল্প Chapter 9।

CAN I EXPLAIN THIS?
  • Physical address কী, কে এটা ব্যবহার করে, আর process-এর address যে physical address হতে পারে না তার প্রমাণ কোথায় দেখেছ? /proc/iomem-এ RAM ছাড়া আর কী থাকে?
  • DRAM volatile কেন? Refresh না থাকলে কী হতো, আর cache-এ DRAM-এর বদলে SRAM ব্যবহার হয় কেন?
  • chase.js কেন latency মাপে, bandwidth না? ৫১২ MB-তে ~১১৯ ns আর ১৬ KB-তে ~১.৪ ns কেন?
  • একই RAM থেকে ~৫৮ GB/s আর ~০.০৩ GB/s — দুটো সংখ্যা কীভাবে একসাথে সত্যি?
  • free -h-এ "free" কম দেখালে ভয় পাওয়ার কারণ নেই কেন? buff/cache আর available কী বলে?
