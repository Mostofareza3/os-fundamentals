PART 9 · COMPILERS, LINKERS AND EXECUTABLES

Chapter 33 — Source Code থেকে Executable

Chapter 4-এ ছবিটা এঁকেছিলাম দূর থেকে — এবার একটু কাছে গিয়ে।

পুরো pipeline

hello.c
  ↓ Preprocessing  — #include/#define বসানো: শুধুই text-এর কাজ
expanded source
  ↓ Compilation    — C → assembly (এখানেই optimization-এর জাদু)
hello.s
  ↓ Assembly       — assembly → machine code
hello.o  (object file — code আছে, কিন্তু বাইরের ঠিকানাগুলো ফাঁকা)
  ↓ Linking        — সব object + library জোড়া, ঠিকানা বসানো
hello  (ELF executable)

Object file-এর সেই "ফাঁকা ঠিকানা"-গুলোর তালিকার নাম symbol table — "আমার printf লাগবে, কে দেবে?" Linker-এর কাজ এই চাওয়া-পাওয়ার ঘটকালি। কোথাও জোড়া না মিললেই পাও সেই বিখ্যাত undefined reference error — এখন জানো ওটা কার অভিযোগ।

Static vs dynamic linking — আসল সিদ্ধান্তটা

StaticDynamic
কী হয়Library-র code executable-এর ভিতরে copy হয়ে যায়Executable-এ শুধু নাম লেখা থাকে — "চলার সময় libc.so লাগবে"
ফলএকটাই বড় file, কোনো dependency নেই — যেখানে ফেলো চলে (Go-র binary-র জনপ্রিয়তার কারণ)ছোট executable; আর সবচেয়ে বড় জয় — এক libc-র code memory-তে একবার, শত process page table দিয়ে share করে (Chapter 9-এর shared memory এখানেই!)
দামLibrary-র bug fix মানে সব executable আবার build"Dependency hell" — ঠিক version-এর .so না পেলে চলে না

Node-এর জগতে এর আত্মীয় চেনো: node_modules bundle করে এক file বানানো (esbuild) ≈ static; runtime-এ require ≈ dynamic-এর আবহ।

ELF file-এর গঠনটাও এখন অর্থবহ: header (কী এই file, entry point), .text (code), .data/.bss (Chapter 5-এর সেই segments-এর জন্মস্থান!), symbol tables, আর dynamic section-এ দরকারি .so-দের তালিকা।

EXPERIMENT (Linux)

ldd /bin/ls — ls কোন কোন shared library চায় দেখো। file /bin/ls — "ELF 64-bit... dynamically linked" নিজের চোখে। আর readelf -h /bin/ls দিলে ELF header — entry point address সহ।
