PART 9 · COMPILERS, LINKERS AND EXECUTABLES

Chapter 33 — Source Code থেকে Executable

gcc-র ভেতরের চারটা আলাদা program, linker আসলে কী করে ("undefined reference" আর "multiple definition" নিজে ঘটিয়ে), static বনাম dynamic linking মেপে দেখা — size, memory, security fix — আর Node-এর native addon যে আসলে একটা shared library।

Chapter 4-এ পথটা এক নজরে দেখেছি: compiler তোমার C-কে machine code-এ অনুবাদ করে কিন্তু printf-এর জায়গা ফাঁকা রাখে (nm-এ U), linker সেই ফাঁকের হিসাব মেলায়, আর dynamic linking-এ library-র code copy না করে শুধু নাম লিখে রাখে। এই chapter সেই পথের প্রতিটা ধাপ খুলে দেখে। কারণ JS দুনিয়াতেও এর ফল রোজ চোখে পড়ে: native module-এর build error, Docker image-এ "library খুঁজে পাচ্ছে না", npm install-এ হঠাৎ gcc চলা।

C এখানে শুধু tool, প্রতিটা লাইন বলে দেব। সব Linux command চালিয়েছি Node-এর Docker image-এ gcc বসিয়ে:

docker run --rm -v "$PWD":/w -w /w node:22-bookworm-slim bash -c '
  apt-get update -qq >/dev/null && apt-get install -y -qq gcc libc6-dev file >/dev/null
  bash stages.sh'          # stages.sh-এর জায়গায় যে script চালাতে চাও

এক command-এর ভেতরে চারটা program

gcc hello.c -o hello দেখতে এক ধাপ, কিন্তু gcc আসলে একটা পরিচালক: সে পরপর চারটা আলাদা কাজ চালায়। প্রতিটা ধাপে থামিয়ে ফলটা দেখা যায়। Chapter 4-এর hello.c-এ একটা #define যোগ করেছি। #define মানে "এই নামের জায়গায় এই লেখা বসাও", JS-এর const-এর মতো, কিন্তু কাজটা হয় compile-এর আগেই, text বদলে দিয়ে:

// hello.c
#include <stdio.h>
#define ANSWER 42

int main(void) {
    printf("hello %d\n", ANSWER);
    return 0;
}
# stages.sh
gcc -E hello.c -o hello.i      # ১) preprocess: #include আর #define বসানো
gcc -S hello.c -o hello.s      # ২) compile: C থেকে assembly
gcc -c hello.s -o hello.o      # ৩) assemble: assembly থেকে machine code
gcc hello.o -o hello           # ৪) link: library জুড়ে executable
wc -l hello.c hello.i hello.s
ls -l hello.o hello | awk '{print $5, $9}'
./hello
    7 hello.c
  749 hello.i
   34 hello.s
  790 total
70448 hello
1616 hello.o
hello 42
  1. Preprocess (-E): ৭ লাইন থেকে ৭৪৯ লাইন! #include <stdio.h> মানে আক্ষরিক অর্থেই "ওই file-টা এখানে paste করো", আর stdio.h নিজেও আরও file include করে। hello.i-এর শেষে তোমার main আছে, তবে এখন printf("hello %d\n", 42); — ANSWER শব্দটা আর নেই। এই ধাপ C বোঝে না; শুধু text কাটা-জোড়া করে।
  2. Compile (-S): আসল compiler (cc1) C পড়ে এই CPU-র assembly লেখে। Assembly হলো machine code-এর মানুষ-পড়ার রূপ (Chapter 4)। hello.s-এর main-এ আছে mov w1, 42 আর bl printf। Optimization-এর সব কাজ এই ধাপেই হয় (নিচে দেখবে)।
  3. Assemble (-c): as নামের program assembly-কে machine code-এর byte-এ বদলায়। ফল hello.o, ১৬১৬ byte। অন্য file-এর function-এর জায়গায় থাকে ফাঁক।
  4. Link: collect2, যেটা ভেতরে ld (linker) চালায়, সব object file আর library জুড়ে দেয়। ফল hello, ৭০ KB।

gcc -### hello.c -o hello চালালে gcc কাজ না করে শুধু বলে সে কোন কোন program চালাত। আমার output-এ সেখানে ছিল /usr/lib/gcc/aarch64-linux-gnu/12/cc1, as, আর /usr/lib/gcc/aarch64-linux-gnu/12/collect2।

একটা gcc command-এর ভেতরে চারটা ধাপ, প্রতিটার পাশে stages.sh-এর মাপা ফল। বাঁয়ে প্রতিটা ধাপের পরে তৈরি হওয়া file, ডানে কোন program কাজটা করে আর কী করে।

Compile ধাপের জাদুটা দেখার মতো। একটা loop যেটা ০ থেকে n−1 পর্যন্ত যোগ করে, সেটা Mac-এর compiler (clang) দিয়ে দুইভাবে compile করো। -O0 মানে কোনো optimization না, -O2 মানে ভালোমতো optimize করো:

// sum.c — 0 থেকে n-1 পর্যন্ত যোগফল
int sum(int n) {
    int s = 0;
    for (int i = 0; i < n; i++) s += i;
    return s;
}
cc -O0 -S sum.c -o sum-O0.s
cc -O2 -S sum.c -o sum-O2.s
; -O0 (শুধু loop-এর অংশ; পুরো function-এ ২২টা instruction। মন্তব্যগুলো আমার)
LBB0_1:
	ldr	w8, [sp, #4]        ; i-কে memory থেকে আনো
	ldr	w9, [sp, #12]       ; n-কে আনো
	subs	w8, w8, w9
	b.ge	LBB0_4              ; i >= n হলে বেরিয়ে যাও
	...
	add	w8, w8, w9          ; s += i
	str	w8, [sp, #8]        ; s-কে memory-তে রাখো
	...
	b	LBB0_1              ; আবার loop-এর মাথায়

; -O2 (পুরো function)
_sum:
	sub	w8, w0, #1
	sub	w9, w0, #2
	umull	x9, w8, w9
	lsr	x9, x9, #1
	add	w8, w8, w9
	cmp	w0, #1
	csel	w0, wzr, w8, lt
	ret

-O2-এ loop-টাই নেই! Compiler বুঝে ফেলেছে এই যোগফল একটা সূত্র: (n−1)(n−2)/2 + (n−1), মানে n(n−1)/2। তাই একটা গুণ, একটা ভাগ (lsr, মানে ডানে shift করা, ২ দিয়ে ভাগ), আর n ১-এর কম হলে ০ (csel)। n যত বড়ই হোক, আটটা instruction। Chapter 4-এর V8 TurboFan চলার মাঝখানে ঠিক এই জাতের কাজ করে; C compiler সেটা আগেই সেরে রাখে।

Linker-এর আসল কাজ: নাম মেলানো আর ফাঁক ভরাট

বড় program মানে অনেক source file। প্রতিটা আলাদা করে compile হয় (একটা বদলালে শুধু সেটাই আবার compile করতে হয়)। কিন্তু তখন এক file-এর code অন্য file-এর function-এর ঠিকানা জানে না। Linker-এর দুটো কাজ: প্রতিটা "লাগবে" (U) নামের জন্য ঠিক একটা "আছে" (T) খুঁজে বের করা, আর machine code-এর ফাঁকগুলোতে আসল ঠিকানা বসানো। দুই কাজেই ভুল ঘটিয়ে দেখা যাক:

// main.c
#include <stdio.h>
int add(int a, int b);                 // ঘোষণা: "add নামে একটা function কোথাও আছে"

int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}

// math.c
int add(int a, int b) { return a + b; }

// extra.c
int add(int a, int b) { return a + b + 1; }   // ভুল করে আরেকটা add
EXPERIMENT (Linux / Docker) — link.sh
gcc -c main.c math.c extra.c           # তিনটা আলাদা object file
nm main.o math.o
echo "--- ১) math.o ছাড়া link"
gcc main.o -o app
echo "--- ২) দুইটা add নিয়ে link"
gcc main.o math.o extra.o -o app
echo "--- ৩) ঠিকমতো"
gcc main.o math.o -o app && ./app

0000000000000000 T main
                 U printf

দুটো error-ই /usr/bin/ld-এর, compiler-এর না। প্রথমটায় main.o add চেয়েছে (U), কিন্তু দেওয়া file-গুলোর কেউ দেয়নি (T নেই)। Error message ঠিক জায়গাটাও বলে দিচ্ছে: main-এর code-এর 0x10 byte-এ। দ্বিতীয়টায় দুজন একই নাম দিয়েছে, linker ঠিক করতে পারে না কোনটা নেবে।

COMMON MISCONCEPTION

"undefined reference মানে #include ভুলে গেছি।" না। #include শুধু ঘোষণা আনে ("এমন একটা function আছে"), আর ঘোষণা না থাকলে error আসে compile ধাপে। "undefined reference" আসে link ধাপে: ঘোষণা ঠিক ছিল, কিন্তু function-এর আসল code (T) যে file বা library-তে আছে, সেটা linker-কে দেওয়া হয়নি। সমাধানও তাই আলাদা: header না, link command-এ ঠিক .o বা library (-lfoo) যোগ করা। Native npm module build-এ এই error দেখলে প্রায় সবসময় একটা system library (যেমন libssl-dev) বসানো নেই।

এবার ফাঁক ভরাটের কাজটা byte ধরে দেখো। objdump -dr machine code আর তার পাশে linker-এর জন্য রাখা নোট (relocation) দেখায়:

objdump -dr main.o | grep -A1 -w bl    # link-এর আগে
objdump -d app | grep -E "<main>:|<add>:|bl.*(add|printf)"   # link-এর পরে
  10:	94000000 	bl	0 <add>
			10: R_AARCH64_CALL26	add
--
  20:	94000000 	bl	0 <printf>
			20: R_AARCH64_CALL26	printf
0000000000000754 <main>:
 764:	94000008 	bl	784 <add>
 774:	97ffffaf 	bl	630 <printf@plt>
0000000000000784 <add>:

Link-এর আগে add-কে ডাকার instruction-এর byte 94000000: bl ("লাফ দাও, ফেরার ঠিকানা রাখো", Chapter 4), আর দূরত্বের ঘরে শূন্য, মানে ফাঁক। নিচে linker-এর জন্য নোট: "0x10-এ add-এর ঠিকানা বসাও"। Link-এর পরে main বসেছে 0x754-এ, add 0x784-এ। 0x764-এর bl থেকে add 0x20 byte (৩২ byte) দূরে, মানে ৮টা instruction (প্রতিটা ৪ byte)। তাই linker byte বদলে 94000008 লিখেছে: শেষের ৮-ই সেই দূরত্ব।

printf-এর বেলায় অন্য ব্যাপার। সে libc.so-তে, আর libc কোন ঠিকানায় বসবে সেটা program চলার আগে জানা যায় না। তাই linker bl-কে পাঠায় program-এর ভেতরেই একটা ছোট stub-এ (printf@plt)। চলার সময় dynamic linker (Chapter 4) সেই stub-এর পাশের একটা table-এ printf-এর আসল ঠিকানা বসিয়ে দেয়। ফাঁক ভরাট তখনো হয়, শুধু পরে।

Relocation, byte ধরে। বাঁয়ে main.o-র bl-এ দূরত্ব শূন্য (লাল ঘর) আর linker-এর জন্য একটা নোট। ডানে link-এর পরে সেই ঘরে ৮ বসেছে, কারণ add ঠিক ৮ instruction দূরে। printf-এর ডাক যায় একটা stub-এ, যার গন্তব্য চলার সময় ভরা হয়।

Static না dynamic: মেপে দেখা

Chapter 4-এ বলেছিলাম সিদ্ধান্তটা এখানে নেব। দুই রকম binary বানাও। -static বলে "libc-র যা যা লাগে, সব executable-এর ভেতরে copy করো":

# sd.sh
gcc hello.c -o hello-dyn                 # default: dynamic
gcc -static hello.c -o hello-static      # static: libc-র দরকারি অংশ ভেতরে copy
ls -l hello-dyn hello-static | awk '{print $5, $9}'
ldd hello-dyn; ldd hello-static
nm hello-dyn | grep -c " T "; nm hello-static | grep -c " T "
70448 hello-dyn
703144 hello-static

	/lib/ld-linux-aarch64.so.1 (0x0000ffffbac38000)
	not a dynamic executable
4
732

Static binary দশ গুণ বড়। ভেতরে function (T) ৪টার জায়গায় ৭৩২টা: printf যা যা ডাকে, আর সেগুলো যা যা ডাকে, সব copy হয়ে গেছে। বিনিময়ে সে কারো উপর নির্ভর করে না: ldd বলছে "not a dynamic executable"। Dynamic-এর তালিকায় Chapter 32-এর linux-vdso.so.1-ও দেখতে পাচ্ছ; ওটা disk-এর কোনো file না, kernel নিজে map করে দেয়।

Dynamic linking-এর প্রথম লাভ memory-তে। Chapter 9-এ দেখেছি একই file-এর page অনেক process-এর page table একই frame-এ বসাতে পারে। libc.so-র code তিনটা আলাদা program-এ কীভাবে ভাগ হয়, /proc/<pid>/smaps থেকে দেখা যাক। smaps প্রতিটা mapping-এর memory-র হিসাব দেয়। Rss হলো এই mapping-এর কতটা এখন RAM-এ আছে। Shared_Clean হলো তার কতটা অন্য process-এর সাথে ভাগ করা, আর বদলানো হয়নি। Pss হলো ভাগ করা page-কে ভাগীদারের সংখ্যা দিয়ে ভাগ করে এই process-এর "ন্যায্য অংশ":

EXPERIMENT (Linux / Docker) — share.sh
# share.sh — তিনটা আলাদা program, তিনজনই libc.so ব্যবহার করে
sleep 300 &
tail -f /dev/null &
python3 -c 'import time; time.sleep(300)' &
sleep 0.5
for pid in $(jobs -p); do
  awk -v name="$(cat /proc/$pid/comm)" '
    / r-xp .*libc\.so/ {on = 1; next}           # libc-র code অংশের mapping শুরু
    /^[0-9a-f]+-/       {on = 0}                 # পরের mapping শুরু হলে থামো
    on && /^(Rss|Pss|Shared_Clean):/ {v[$1] = $2}
    END {printf "%-8s libc code: Rss %4s kB  Pss %4s kB  Shared_Clean %4s kB\n",
                name, v["Rss:"], v["Pss:"], v["Shared_Clean:"]}' /proc/$pid/smaps
done
kill $(jobs -p)
sleep    libc code: Rss  832 kB  Pss  172 kB  Shared_Clean  832 kB
tail     libc code: Rss  768 kB  Pss  162 kB  Shared_Clean  768 kB
python3  libc code: Rss 1152 kB  Pss  311 kB  Shared_Clean 1152 kB

(এই image-এ python3 নেই; apt-এর তালিকায় python3 যোগ করে নাও।) তিন program-এর প্রত্যেকে libc-র ৮০০ KB–১.১ MB code "দেখছে", আর তার পুরোটাই Shared_Clean। RAM-এ copy একটাই, সবার page table সেখানে তাকিয়ে। Pss ছোট, কারণ প্রতিটা page চার-পাঁচজনে ভাগ করছে (script চালানো bash আর awk-ও libc ব্যবহার করে)। Static হলে প্রতিটা আলাদা program নিজের file থেকে নিজের কপি আনত। একটা machine-এ শত শত program libc ব্যবহার করে, তাই এই সাশ্রয় বিশাল।

বাঁয়ে dynamic: তিনটা আলাদা program-এর page table একই libc frame-এ তাকায়, share.sh-এর Shared_Clean ঠিক এটাই। ডানে static: প্রতিটা program-এর ভেতরে নিজের কপি, RAM-এও আলাদা। (একই static program দুইবার চালালে তারা নিজেদের মধ্যে ভাগ করে; ভাগ হয় না আলাদা program-এর মধ্যে।)

দ্বিতীয় লাভ হলো security fix। ধরো libc-তে একটা bug ধরা পড়ল। Dynamic হলে library-র file বদলালেই (apt upgrade) পরের বার চালু হওয়া সব program ঠিক। Static হলে প্রতিটা program নতুন করে build করতে হবে। নিজের একটা ছোট library দিয়ে পুরো ঘটনাটা ঘটিয়ে দেখা যাক। ar দিয়ে বানানো .a file হলো static library (object file-এর বান্ডিল), আর -shared দিয়ে বানানো .so হলো shared library:

// app.c
#include <stdio.h>
const char *greet(void);                 // library থেকে আসবে

int main(void) {
    printf("greet(): %s\n", greet());
    return 0;
}
# fix.sh — library-তে "security fix" এলে static আর dynamic program-এর কী হয়
echo 'const char *greet(void) { return "v1 (has the bug)"; }' > greet.c
gcc -c -fPIC greet.c -o greet.o
ar rcs libgreet.a greet.o                                  # static library
gcc -shared greet.o -o libgreet.so                         # shared library
gcc app.c libgreet.a -o app-static
gcc app.c -L. -lgreet -Wl,-rpath,'$ORIGIN' -o app-dyn      # চলার সময় পাশের folder-এ খোঁজো
./app-static; ./app-dyn

echo "--- শুধু library বদলাই, program দুটো আবার build করি না"
echo 'const char *greet(void) { return "v2 (fixed)"; }' > greet.c
gcc -c -fPIC greet.c -o greet.o && ar rcs libgreet.a greet.o && gcc -shared greet.o -o libgreet.so
./app-static; ./app-dyn

echo "--- library-টাই যদি না থাকে"
rm libgreet.so
./app-static; ./app-dyn

Library বদলানোর পরে dynamic program নিজে থেকেই fix পেয়ে গেল, আর static program পুরনো bug নিয়েই চলছে। শেষ অংশে dynamic-এর উল্টো পিঠ: library না থাকলে program চালুই হয় না। এই error kernel-এর না, compiler-এর না; dynamic linker-এর (ld.so), program শুরু হওয়ার মুহূর্তে (Chapter 34)। (-fPIC মানে code এমনভাবে বানাও যাতে যেকোনো ঠিকানায় বসানো যায়; shared library-র জন্য এটা লাগে। -rpath binary-তে লিখে রাখে library কোথায় খুঁজতে হবে; $ORIGIN মানে "binary যে folder-এ আছে"।)

পুরনো static binary নতুন Linux kernel-এও নিশ্চিন্তে চলে, কারণ Linux নতুন syscall যোগ করে, কিন্তু পুরনোগুলোর নম্বর বা নিয়ম কখনো বদলায় না। macOS-এ ব্যাপারটা আলাদা। Apple syscall-কে স্থায়ী interface বলে কথা দেয় না, কথা দেয় শুধু libSystem-কে। তাই macOS-এ পুরো static binary বানানোই যায় না; প্রতিটা program libSystem-এর সাথে dynamic-ভাবে জোড়া (Chapter 4-এর otool -L)।

Node-এর native addon: আসলে একটা shared library

bcrypt, sharp, better-sqlite3-এর মতো কিছু npm package-এর ভেতরে .node extension-এর file থাকে। নাম দেখে মনে হয় Node-এর নিজস্ব কিছু, কিন্তু আসলে এটা এই chapter-এর libgreet.so-র মতোই একটা shared library। প্রমাণ দিতে নিজেই একটা বানাই। Node-এর stable C API (Node-API, আগের নাম N-API) দিয়ে লেখা একটা add(a, b):

// addon.c — Node-এর জন্য ছোট্ট একটা native addon: add(a, b)
#include <node_api.h>

static napi_value Add(napi_env env, napi_callback_info info) {
    size_t argc = 2;
    napi_value argv[2], result;
    double a, b;
    napi_get_cb_info(env, info, &argc, argv, NULL, NULL);    // JS থেকে আসা argument
    napi_get_value_double(env, argv[0], &a);
    napi_get_value_double(env, argv[1], &b);
    napi_create_double(env, a + b, &result);                   // JS-এর number বানিয়ে ফেরত
    return result;
}

NAPI_MODULE_INIT() {                                           // require()-এর সময় চলে
    napi_value fn;
    napi_create_function(env, "add", NAPI_AUTO_LENGTH, Add, NULL, &fn);
    napi_set_named_property(env, exports, "add", fn);
    return exports;
}

লাইন ধরে পড়ো:

  • file বলছে "ELF shared object", ঠিক libgreet.so-র মতো। নামের শেষে .node শুধু Node-কে বোঝানোর জন্য।
  • Addon-এর ভেতরে napi_* function-গুলো U, মানে ফাঁক। কে ভরবে? Node binary নিজেই এগুলো দেয় (T napi_create_double)।
  • require('./addon.node') ভেতরে dlopen() ডাকে। এটা dynamic linker-এর সেই কাজটাই, যেটা program চালুর সময় হয়, শুধু চলার মাঝখানে: file খোলো (openat), তার অংশগুলো address space-এ map করো (৪টা mapping), ফাঁকগুলো node-এর ঠিকানা দিয়ে ভরো, তারপর init function চালাও।

এর তিনটা ব্যবহারিক ফল আছে। এক: .node file একটা নির্দিষ্ট CPU আর OS-এর machine code। ARM Mac-এ build করা addon Intel Linux server-এ চলবে না। তাই এমন package প্রতিটা platform-এর জন্য আলাদা prebuilt binary রাখে; কোনোটা না মিললে অনেক package npm install-এর সময় নিজেই gcc চালিয়ে build করতে বসে (node-gyp)। দুই: addon-এর ভেতরের একটা bug (ভুল ঠিকানা ছোঁয়া) JS-এর exception না, পুরো process-এর SIGSEGV (Chapter 31)। তিন: glibc-ওয়ালা Debian-এ build করা addon musl-ওয়ালা Alpine-এ চালালে কী হয়, সেটা পরের chapter-এর শুরুতেই।

MENTAL MODEL

gcc চারটা program চালায়: preprocessor (text কাটা-জোড়া), compiler (C থেকে assembly, সব optimization এখানে), assembler (byte, সাথে ফাঁক আর নোট), linker (নাম মেলানো আর ফাঁক ভরাট)। "undefined reference" আর "multiple definition" linker-এর অভিযোগ: একটা নাম কেউ দেয়নি, বা দুজন দিয়েছে। Static linking library-র code binary-র ভেতরে ভরে দেয়: স্বয়ংসম্পূর্ণ, কিন্তু বড়, আর প্রতিটা fix-এ আবার build। Dynamic linking শুধু নাম লিখে রাখে, আর চলার সময় জোড়া দেয়: RAM-এ এক কপি, এক জায়গায় fix, কিন্তু ঠিক library না পেলে program চালুই হয় না। Node-এর .node addon ঠিক এমনই একটা shared library, require() যাকে চলার মাঝখানে জুড়ে নেয়।
